# Boardgame UI Imagegen

这个 skill 用来把“规则 + 素材”转成可靠的 UI 生图 brief。目标不是让图更花，而是少做少错：先证明理解了游戏和素材，再调用 `imagegen`。

## 使用顺序

1. 先读当前项目规范：`AGENTS.md`、`docs/ai-rules/ui-ux.md`、`docs/ai-rules/asset-pipeline.md`。
2. 若是新增游戏，先读 `.windsurf/skills/create-new-game/SKILL.md` 中素材驱动 UI 部分。
3. 读取规则真相源：优先 `src/games/<gameId>/rule/*.md`，没有 Markdown 才回到 PDF/OCR 流程。
4. 打开主地图、主棋盘或玩家面板素材；如果用户给的是本地图片路径，必须用 `view_image` 看图。
5. 先输出 UI 元素拆解，再生成 prompt；没有拆解，不要直接生图。
6. 如果用户要求保留/使用真实地图或棋盘素材，优先做 HTML/CSS/React 静态 mockup 并截图；不要直接 text-to-image 重绘素材。
7. 只有当目标是 moodboard、临时视觉占位或不要求保留真实素材结构时，才按 `.system/imagegen` skill 调用 `image_gen`。

## 生成方式裁决

- **保真 UI 稿**：用户说“使用地图素材 / 不要拆地图 / 核对每个细节 / 不能重复 UI”时，必须用真实素材做底图，再叠 HTML/CSS 控件并截图。禁止纯 text-to-image。
- **概念氛围图**：用户只要美术方向、风格 moodboard 或临时占位时，可以用 imagegen。
- **失败切换**：如果 imagegen 连续生成重复 HUD、拆图、重绘流程轨或遮挡素材，应停止调 prompt，切换到保真 UI 稿。

## UI 元素拆解门禁

生图前必须给出这四类清单：

- **素材已有 UI**：主图上已经印出来的轮盘、牌库槽、弃牌槽、流程轨道、计分轨、卡位、提示框、区域名、边界、图例等。已有 UI 只能数字化增强，不能复制一套。
- **规则必须常驻**：玩家每回合必须反复查看或操作的对象，例如当前回合状态、手牌、当前可执行动作、当前选中目标。
- **按需展开**：日志、详情、帮助、完整手牌、规则摘要、弃牌堆查看、战斗结算详情。默认不占整列。
- **禁止出现**：规则没有的系统、解释性 UI、工具/编辑器入口、重复控件、独立拆出来的地图区域。

拆解必须直接引用规则原文中的结构，不要用泛化策略游戏经验补空白。

## 素材优先规则

- 主地图/主棋盘是构图真相源。若它是一张完整桌面版图，prompt 必须说“整图作为一个画布使用”，不得拆成多个独立面板。
- 如果素材上已有某个控件，就不要在别处再做一个同类控件。例如左上已有行动轮盘，就不要再在底部做第二个轮盘解释器。
- 如果素材上已有某个区域的牌库/弃牌槽，就只在原槽位贴短标签或状态，不把它们移到右侧栏。
- 如果素材上已有战斗流程轨、计分轨、纪年卡位、检查流程框，默认保留原位置，不用新 HUD 重做。
- 地图上的区域、点线、城池、山河、边界、锚点是地图内容，不应被 HUD 盖掉。

## 控件所有权规则

- 同一信息只能有一个主出处。地图上已经印出来的，就不要再做一份独立数字版。
- 如果左上行动轮盘已经显示当前轮盘行动，就不要在底部再做“轮盘行动”控制器或解释器。
- 如果规则要求的是“一个主动作槽 + 一个当前状态”，不要把状态另做一个同名面板。
- 只有当素材本体没有表达该信息时，数字覆盖层才可以补它。
- 如果素材已有清晰文字标签，数字覆盖层不要再贴同名标签；避免“为了确认而重复 UI”。
- 默认优先级：`board printed control` > `one action slot` > `small state badge` > `optional detail`。

## 空间占用规则

- 地图/棋盘类主图优先保留可读面积。覆盖层宁可少，不可压住素材已有流程轨、牌槽、计分轨和关键区域名。
- 行动记录、规则摘要、完整日志默认禁止出现在主界面；只有用户明确要求常驻日志时，才允许做极小入口或临时浮层。
- 手牌区只展示“可操作入口 + 少量预览”。不要把完整手牌、动作菜单、结束按钮、日志同时铺满底部。
- 底部交互优先做成左下或右下紧凑浮岛，而不是横跨全宽的 rail；必须给原图底部流程轨、纪年卡轨和 VP 轨留出可见空间。
- 结束回合是普通命令，不应做成比地图对象更重的巨型面板。
- 如果一个覆盖层会让地图已有 UI 不可读，删除覆盖层，而不是移动地图。
- 首版 UI 草稿默认不展示完整卡面墙；除非用户明确要求检查手牌布局，否则手牌只显示折叠入口、数量、少量小缩略 chip。
- 素材上已有战斗流程轨时，禁止把它重绘成数字面板；只能保留原图或加极小阶段标记。
- 底部操作区宽度应尽量小于屏幕宽度的四分之一，且不要覆盖原图下沿关键轨道。

## 规则理解规则

- 先找“回合主动作模型”。不要把子选项误升为主按钮。
- 如果规则写“执行 A 及 B，顺序自定”，UI 应表达两个动作槽，而不是把 A 的子项和 B 并列。
- 卡牌子类型、势力行动、战斗步骤、维护步骤等，只有在当前动作展开时显示。
- 不确定某 UI 是否常驻时，默认降级为按需展开。
- 不要在 UI 里解释规则。按钮叫“结束回合”即可，不写“结束当前玩家回合并进入下一玩家”。
- 如果某元素已经在素材里承担“状态显示”，覆盖层不要再重复显示同一状态。

## Prompt 结构

生成 prompt 时按以下顺序写：

1. **画布原则**：主素材是否完整使用、是否允许裁剪、是否允许拆分。
2. **必须保留的素材 UI 位置**：逐条列出已有控件的位置和处理方式。
3. **最小数字覆盖层**：只写新增覆盖层，不写大段功能说明。
4. **主动作模型**：用规则术语描述，不发明 AP、任务、建造队列等系统。
5. **禁止项**：把本轮踩过的坑明确写进 negative constraints。
6. **可见文字限制**：只允许短标签、动作名、数字和状态；禁止解释句。

## 生成后自检

每次生成后必须打开图片并逐项核对，不能只交付生成结果：

- 是否出现重复控件：第二个轮盘、第二个牌库/弃牌、第二个纪年卡区、第二个当前行动。
- 是否轻重失衡：HUD 是否比地图更抢眼，底部/右侧是否变成仪表盘。
- 是否遮挡素材：流程轨、牌槽、区域名、朝鲜区、纪年卡位是否还可见。
- 是否出现“大块底部 HUD”：完整手牌墙、巨大动作菜单、巨大结束按钮、重绘战斗流程面板。
- 是否出现解释性 UI 文案。
- 是否出现用户已要求移除的元素，例如整列日志或行动记录大面板。
- 若任一项不合格，必须更新 prompt 或规范后重生，不得把图当成合格草稿。

## 文案限制

UI 里允许：

- 对象名：`手牌`、`牌库`、`弃牌`、`纪年卡`
- 动作名：`手牌行动`、`轮盘行动`、`结束回合`
- 状态：`已执行`、`未执行`、`当前`
- 数字和短字段：年份、VP、人口、部队、顺位

UI 里禁止：

- 规则说明句
- 教程句
- “点击这里...”类指令
- 解释按钮含义的文字
- 不属于规则的资源栏和系统名
