# Boardgame UI Imagegen

这个 skill 只定义通用产线：如何从规则、提示卡和素材生成可复现的桌游 UI 设计稿。它绝不写任何单个游戏的专属名词、按钮清单、地图区域、卡牌名称、版本号或当前任务结论。所有游戏专属裁决必须放在 `design-system/games/<gameId>.md`、该游戏 `rule/` 文档或本轮 prompt 中。

## 硬边界

- 通用 skill 只写方法，不写某个游戏该显示什么。
- 禁止把一次失败图的局部补丁沉淀为全局默认。
- 禁止把某个已生成候选图当通用风格答案；候选图只能拆出可复用的布局、密度、组件完成度或失败模式。
- 禁止把规则章节名、帮助卡父级词、实现命令名直接翻译成主按钮。
- 禁止未读规则书/规则摘录/玩家提示卡就编写轮盘、动作按钮、参数面板、代价、抽牌结果或结算标签。凡涉及规则内容的可见文字，必须能回指到规则原文、提示卡/帮助卡或游戏专属规范；不能用“看起来像”“按常识应该是”补标签。
- 禁止跳过“规则/参数图证据表”直接实现高规则密度 UI。轮盘、轨道、参数图、行动列表、费用表、结算阶段这类对象在实现前必须先列出 `源文件/图片 -> 原文标签 -> 玩家提示卡短标签 -> UI短标签 -> 是否常驻`；缺任一关键来源时只能标风险或继续查源，不能先画占位字、八卦名、数字序号或自造短词。
- 禁止把“动作按钮”和“执行/确认执行/应用”做成两套同义入口。若按钮本身已经代表叶子动作，点击该按钮就承担执行或进入必要支付/目标选择的语义；只有危险操作、不可逆提交、多人确认或规则明确要求二次确认时，才允许额外确认按钮，并必须写明例外依据。
- 禁止为了修假文字、修风格漂移或删控件，把设计稿退成灰块、线框、烟测截图或低细节占位稿。
- **如果用户已冻结最终设计稿，且真实运行时素材已存在，后续前端实现必须优先使用真实 UI 素材；设计稿只决定布局、层级、组件密度和状态，不授权继续使用占位卡面、伪牌背、伪地图或通用色块。**
- **如果当前实现与冻结稿差距过大，禁止走“旧底图上加遮罩/弱化/糊一层”近似路线冒充收口。** 当用户要求 UI-only 或非 UI 空白时，必须删除旧底图/地图依赖，按冻结稿重建独立 UI 层；只有用户仍要求棋盘/地图参与当前稿时，才回到真实素材重搭桌面结构。
- **如果用户要求“做一个工具”来辅助地图/棋盘/UI 的划区、涂色、裁切、映射、标注、校准或规则取证，默认实现为内部 devtools 页面，而不是临时塞进业务 Board、现有无关工具页或一次性脚本。** 允许例外只有两类：用户明确要求扩展某个现有工具；或该能力本身就是最终玩家可见功能。
- 工具页也必须遵守产品级 UI 规范：左侧固定、内部滚动、主画布稳定，不要把参数和说明堆成整页长列表。
- 工具产出如果会成为运行时真相源，默认只保留一个主动作按钮（`保存` 或 `应用`）；该动作应自动写入项目约定的数据目录。不要把 mask、regions、graph 拆成多个用户可见导出按钮。
- 真相源型工具一旦提供 `保存`，默认还必须提供刷新后的自动回读：页面重开后直接从项目数据目录恢复最近一次保存的 mask、边界提示、映射或配置，不能要求用户每次手工再导入刚保存的结果。
- 真相源型工具的回读逻辑必须与可编辑状态解耦：回读 effect 只能由显式加载/刷新触发，不能绑在会被 authoritative toggle、bootstrap memo 或派生视图状态反复改写的依赖上，否则会把尚未落盘或刚刚保存的真相源状态冲掉。
- 画布编辑/选区工具必须从结构化状态重绘可见层，禁止用重复半透明绘制污染视觉真相源；自动选区在写入前必须有边界可视化和异常面积保护。
- 诊断样本、快捷定位、bootstrap 对照按钮只能帮助用户选中对象、显示边界或准备种子点；除非按钮名称本身就在切模式，否则不得偷偷把用户切到无关编辑模式。用户点“样本/区域/定位”后，默认应仍能直接继续主路径（例如魔棒初选或锁链微调）。
- 地图/棋盘区域制图工具必须把“区域 mask”和“规则连通图”分开：区域 mask 负责点击、高亮、picking 和连续区域真相；规则连通图负责地点节点、相邻边、边界类型和规则参数。禁止只靠视觉高亮猜邻接，禁止把边界调试层当最终分区结果。
- 若工具里某块区域已经有**显式真相源**（authoritative guide / truth mask / formal hitmap / 用户已确认 polygon），主画布主链必须直接消费该真相源；它不能只在侧栏预览或 debug 对照里生效，更不能被启发式候选重新抢走。启发式 barrier / color / radial 只负责没有真相源的区域，或作为真相源缺失时的 bootstrap。
- 若某张截图、某个诊断样本或某块区域当前命中的是 `authoritative guide / truth-guide`，结论只能是“显式真相源已接进主链”；**不得**把它继续表述成“魔棒已经到边界停止”。真相源命中证据与启发式 bootstrap 证据必须分开记录。
- 编辑器工具的辅助图层必须按模式显示：路径节点/连线、锁链控制柄、桥接预览、诊断 guide、debug crop 各自只在相关模式或相关开关下出现。禁止让无关辅助图层长期覆盖魔棒主画布，污染“当前选区范围是否正确”的视觉判断。
- 区域选区默认按真实素材边界工作：先读取规则/参数图和实际地图，建立边界色或边界线数据，再用魔棒/画笔修正连续区域。地图色块高度相近时，不得只按种子颜色扩散；必须允许边界色模糊匹配、边界加粗或手工补边。
- 若地图底色彼此接近、真正决定分区的是边界线/海岸线/地块外轮廓，则颜色停线的画像不得只取“单个点击点附近一小圈像素”。至少要允许从**局部候选 seed patch / 局部候选 mask** 取样，再做颜色扩散；否则同一区域点不同位置就会换一套颜色门槛，主画布结果必然乱跳。
- 若工具使用粗轮廓、粗 polygon、历史 region shape 或任意 bootstrap ROI 约束自动初选，该约束只有在**确实包含当前 seed/起点**时才可生效；一旦 seed 落在约束外，必须自动禁用该约束并显式提示“粗轮廓与当前种子不一致”。禁止静默继续用错位 ROI 裁坏魔棒结果。
- 若主路径允许在一次点击后额外评估多个 seed 候选，`bootstrap guide / static shape / 旧 mask` 只能为**当前点击附近**提供候选点；不允许把用户点击静默改判成远处 guide 内部点，只因为后者面积更大或分数更高。用户实际点击位置始终是一级锚点，远离点击点的 guide 候选必须显式降权或直接禁用。
- 若同一次点击下有多个 seed 候选分数接近，不得只因为某个候选多涂出一圈像素就抢走主点击。候选差距落在同一 tie 区间时，必须优先保留**更接近用户点击位置**的 seed；否则工具会从“点击某地”退化成“在整块 guide 里自动巡航找最大块”。
- 若工具已经存在用户保存过的 `region mask / region outline / 当前区域底稿`，后续 bootstrap 必须**优先复用这份当前底稿**，但前提仍是它实际覆盖当前 seed；若旧底稿不覆盖当前 seed，必须自动让位给其他可用 bootstrap（如更新后的 shape、当前点击邻域或手工边界提示），不能因为“有旧文件”就继续锁死错误区域。
- 若页面加载时同时存在 `saved mask center / persisted seed` 与 formal `static shape`，不得因为 seed 落在 shape 外就静默改写为 shape 中心。已保存的中心点或 seed 默认比粗 shape 更接近当前真相；shape 只能作为不一致提示或 bootstrap 参考。只有在当前区域完全没有 seed/center 时，才允许退回 shape 中心。
- 若工具同时存在 `persisted/current mask` 与 formal `static shape / 粗 polygon`，则 persisted bootstrap 除了覆盖当前 seed 之外，还必须与 formal guide 至少保持基本重合；一旦两者几乎完全错位、互不相交或明显来自旧坐标系，persisted 只能降级为历史参考，不能继续作为强 fallback 或候选评分基线。
- 若正式区域已经有 formal `static shape / 粗 polygon`，则用户再次触发主路径自动选区（例如再次点魔棒）时，默认必须**优先从真实素材重算**，而不是静默继承上一次的临时 `persisted/current mask`。只有当 formal guide 缺失、用户明确选择“继续当前底稿”，或当前流程本来就是在已有底稿上局部修边时，才允许 persisted 继续主导 bootstrap。
- 若魔棒存在多条 bootstrap 候选（例如颜色停线、局部边界环、边界抠区），候选裁决必须按**真实边界贴合度**和连续区域结果比较，不能因为“存在 guide/ROI”就默认偏信最小色块。必要时允许对局部边界环候选做少量“向外长到边界再剔除障碍像素”的 refinement，但仍必须保持单连通且不得把边界线本身涂进选区。
- 若正式区域已经有粗 shape / 旧 mask / 旧 polygon 作为 bootstrap guide，候选 refinement 不能在**没有明显边界收益**的前提下把 guide 覆盖做差；一旦 refinement 让整体轮廓明显更怪、更瘦或更偏离区域大形，必须回退到更接近整体轮廓的基础候选。
- 若正式区域已有粗 shape / 旧 polygon 但它还不足以直接当最终真相，默认把它降级为**局部搜索护栏**：它只负责限制 magic wand 的搜索范围、外圈支持环和异常漏边，不得直接把整块 guide 当最终选区写入。最终候选仍必须从当前 seed 出发，并依靠边界停线得到单连通区域。
- 若 `static shape / 粗 polygon` 只是 formal bootstrap，而不是用户已经修过并保存的当前底稿，它默认只能做 **support / ROI / 候选评分参考**，不能因为“面积更完整”就强行盖过一个仍可继续锁链微调的自动初选。只有用户保存过的当前 mask/outline，才可以在自动候选明显失真时升格为强 fallback。
- 若 `shape-color / guide 内 flood / ROI 内颜色停线` 这类候选只是把 formal shape 大面积涂满，而不是基于真实边界停线得出的结果，则它只能作为 radial 不可用时的兜底，不能在 radial 或 radial-color 已可用时抢占第一候选。formal shape 的职责是 support，不是替代边界本身。
- 若边界图层里混进了内部文字框、图标、马纹、山纹或装饰噪声，允许在局部 ROI 内只保留**贴近候选外圈 support ring** 的边界组件，再做贴边扩张或 flood；禁止让深处噪声组件主导魔棒停线。
- 若全局 `filtered barrier` 太干净导致简单区根本闭不住边，而全局 `raw barrier` 又把整图文字/装饰/水线都带进来，则正确方向不是在“全局全开 raw”与“全局只用 filtered”之间来回切，而是：**全局仍用较稳的 filtered barrier 做 bootstrap，局部只在当前候选外圈附近引入 raw barrier 组件做 refinement。** raw barrier 的作用域必须限制在当前候选 search area 内，且只保留贴近 support ring 的组件。
- 若边界颜色已经给出但装饰/文字存在撞色，必须先做“边界链”判断：同色像素只有在预期边界带附近连续成链、具备足够长度和线性跨度时才允许进入 barrier；远离边界带的同色装饰分支即使通过细桥连接到边界，也必须剪掉。已知边界色的 raw mask 只能当原料，不能直接当链真相；应优先使用“边界色 + 线结构过滤”后的 mask 做链判断，raw 只能在局部、受 support ring 和链结构门禁约束后兜底。若 `line / expanded / raw-color / filtered barrier` 多个源都可形成局部链，裁决必须先看已知边界色源是否已有有效链；通用 filtered/gradient barrier 只能在已知边界色链缺失时兜底，不能仅凭像素更多抢走主链。允许对已知边界色主链做极小范围短缺口闭合，但闭合必须是端点同方向短桥接，闭合后仍必须重新做 support 接触、跨度/厚度和枝杈修剪校验。禁止把“撞色”直接等同于“算法无解”，也禁止把所有同色像素一股脑当边界。
- 若当前样本、临时区域或诊断区没有 formal guide，它只能验证 unguided bootstrap；不得把这类结果当作正式 guide 已接通或正式边界真相已正确的证明。
- 若局部 refinement 需要显著放大 search area，support 不得只靠候选周围一圈薄环；应允许“候选外圈 + 当前 search area 的边界带”一起约束保留哪些边界组件，避免 search area 一放大就把整块 raw 噪声一并放行。
- 若 `support ring / 贴边扩张` 候选只是把面积做大，却没有带来**肉眼可见**的边界贴合改善，必须自动拒绝并回退到更紧的基础候选（例如 `边界环` 或 `边界环内颜色停线`）。禁止把“像素更多”“范围更满”误当成更好结果。
- 若 `guide-local-color`、`局部护栏内颜色停线` 或其他 refinement 候选只是把同一区域削得更瘦、更碎，却没有带来足够明显的边界贴合收益，则它不得压过更完整的基础候选（如 `radial` / `边界环`）。refinement 的职责是收边，不是把整体区域越修越小。
- 若 `guide-boundary-interior / 外裁 inside / guided-edge-fill` 已经改用 ROI 内部 seed 或更大连通块选择后，简单区样本仍只产出几十像素碎块、`guideRecall` 近乎 0，或候选继续是 `0 px`，就必须判定当前 **barrier truth 本身不成立**。此时禁止继续把问题表述成“再调一点 seed/容差/closing 就行”；下一步应转向显式 boundary hint、formal hitmap/mask 或用户确认的 truth authoring。
- 区域必然是一个整体连续块时，默认工具链是“魔棒初选 + 锁链微调”：魔棒只负责生成初始单连通区域；锁链沿已选区域边界做局部加/减修边；提交前必须检查单连通，不允许产生碎岛。自由画笔/擦除只能作为兜底，不得成为主路径。
- 如果从最终装饰地图按边界颜色提取 barrier 后，样本区域（例如一个简单城市块）里最大的 barrier 连通块已经吞掉大面积内部，或 barrier 根本闭不住导致 flood 一下子漏到整图，就必须承认“启发式 barrier 失真”，停止继续只调容差/膨胀参数。此时正确方向是把边界本身升格为显式数据：允许手工补边、手工去噪、独立 boundary hint 层或权威 region mask；魔棒只做 bootstrap，不再假装自己是最终真相源。
- 边界桥接/补边如果会直接写入 `boundary hint` 或同类底层边界数据，默认必须是**细线 + 吸附到附近已识别边界**，目标是补窄缝而不是涂大块。若一笔桥接会让当前自动选区直接变成 `0 px`、整块消失或明显堵死主区域，视为默认参数失控，必须收窄线宽、缩短作用范围，或改成确认后应用。
- 锁链微调不是普通自由套索：它必须显示或引用当前区域边界，编辑一段局部边缘，并在写入后重算区域 mask 与中心点。若调整会把一个区域切成多个连通块，必须拒绝或回滚，不得静默保存。
- 若区域会进入后续路径、移动或战斗规则，工具必须提供节点/边编辑：节点默认来自已分区区域中心或人工锚点，边必须能保存规则边界类型、宽度/代价/限制等参数，参数必须回指规则书或游戏专属规范。
- 地图区域工具验收必须实际看截图，不能只用 E2E 断言“有 mask / 有中心点 / 有保存文件”收口。最低看图门禁：地图铺满主要工作区；选中区域是连续低透明填充；外轮廓贴近真实边界并有清晰描边；内部文字、马、山纹、图标不得把区域切碎或挖洞；锁链控制柄只能在编辑模式少量出现，不能像调试噪点铺满边界。出现红色糊块、错区、漏半张图、控制点噪声、边界完全不贴素材时，一律判为未达标并继续修。
- 若简单区样本的局部预览里仍能直接看到**内部文字、图标或装饰噪声把选区切穿/挖洞**，就必须判定“还没到边界停止”；不能因为主画布远看大形相似，或因为切到显式 truth 后看起来规整，就把启发式算法判成通过。
- 地图区域工具的验收主真相是**主画布实际点击后的结果**；侧栏诊断小预览、候选缩略图、debug crop 只能辅助判断，不能替代主画布 verdict。只要主画布选区仍明显错区、偏窄、过宽、退回旧轮廓或与侧栏说法不一致，就视为未通过并继续定位主链路。
- 截图证据必须对应当前实现。若代码已经把某辅助层限制到特定模式，但所谓 `current` 截图里仍出现该辅助层，默认先判定为旧证据或取证时机错误；未重拍前不得继续把这张图当最新收口依据。
- 区域工具截图证据必须区分状态：`净选区` 截图只展示魔棒/基础选区结果，用来判断范围和高亮是否正确；`编辑态` 截图可以展示锁链、画笔、擦除或控制柄，但不得作为唯一主验收图；`路径态` 截图只证明节点/边/规则参数。禁止把被锁链减去、正在拖拽或带调试控制点的编辑态截图当成“选区效果已达标”的证据。
- 魔棒工具默认应接近图像编辑器选区语义：点击种子点后按局部相近色扩散，并由边界数据停线；点击到边界/文字/图标时应优先吸附到附近可选区域内部，而不是直接失败或复用上一次颜色。边界色、区域 mask、连通图是数据，不得靠重复半透明涂色叠深来制造“看起来选中”的假效果。
- 对于边界本身就是后续游戏规则数据的地图，编辑器应至少区分三层：`启发式边界`、`手工边界修正（补边/去噪）`、`最终区域 mask`。用户可见主保存动作仍然只能有一个，但该动作应自动把这些底层数据一起写入游戏目录，不能只保存最后一层着色结果。
- 诊断样本、bootstrap 临时区域、对照区或任何仅供 devtools 调试的对象，必须显式标成“仅工具内使用”，并在主保存动作里自动从正式 `mask / regions / graph` 导出中过滤掉。禁止让这类临时对象混进运行时真相源文件。
- 如果需要写入具体游戏的动作、区域、牌型、势力、资源、固定槽位或素材文件名，立刻停止编辑本 skill，改写到 `design-system/games/<gameId>.md`。

## 0. 必读输入

开始写 prompt 或生图前，必须收集以下输入；缺失项要在拆解里标为风险，不要用猜测填补：

1. 项目规范：`AGENTS.md`、`docs/ai-rules/ui-ux.md`、`docs/ai-rules/asset-pipeline.md`、`design-system/game-ui/MASTER.md`。
2. 设计方法：`frontend-design` 和 `ui-ux-pro-max` 只作为审美/UX 方法来源；项目设计系统优先。
3. 游戏专属规范：`design-system/games/<gameId>.md`，若不存在则只能产出低承诺草稿。
4. 规则真相源：优先 `src/games/<gameId>/rule/*.md`；没有再读 PDF/OCR/扫描件。轮盘格、行动按钮、代价、抽牌/弃牌结果、结算阶段等内容必须从这里取，不得猜。
5. 玩家提示卡/帮助卡/reference sheet：用于判断玩家实际入口层级、常查信息、参数图和短标签。凡项目资源里存在 `aids/`、`reference sheet`、玩家帮助卡、参数图或同类文件，必须实际打开看图；若提示卡与规则能互相印证，才允许把短标签写进主 UI；无法印证则只能进入风险记录或临时说明，不进可见主界面。
6. 核心素材：主棋盘/地图、玩家面板、卡牌正面、牌背、公共牌堆、token、骰子、轨道、真实图标。
7. 项目已有 UI：从当前项目中找机制相近的游戏或组件模式，提炼布局规律，不照抄主题。

## 1. 三源裁决

先写三源结论，再写 prompt：

| 来源 | 决定什么 | 不决定什么 |
| --- | --- | --- |
| 规则书 | 行为真值、合法动作、动作顺序、代价、目标、公开/隐藏信息、结算反馈 | 不自动决定按钮文案和视觉风格 |
| 玩家提示卡/帮助卡 | 玩家实际理解的入口层级、动作分组、常查信息、快捷参考 | 不决定整体美术风格；父级词不自动常驻 |
| 核心素材 | 空间结构、已有实体/槽位、风格不变量、组件材质、哪些对象本体可点击 | 不改写规则和动作顺序 |

冲突处理：

- 规则与提示卡冲突：规则决定行为，提示卡只作 UI 分组候选。
- 提示卡与素材冲突：素材决定空间归属，提示卡决定入口层级。
- 生成图与核心素材冲突：核心素材胜出。
- 未看提示卡，不裁决主入口；未看核心素材，不裁决风格；未读规则，不裁决动作顺序和代价。

## 2. 可见 UI 溯源矩阵

每个可见 UI 元素都必须先进入矩阵：

```text
UI 元素 | 规则依据 | 提示卡/帮助卡依据 | 核心素材依据 | 当前用途 | 删除损失 | 可见层级
```

判定规则：

- `规则依据` 回答能做什么、何时能做、代价/目标/结算是什么。
- `提示卡依据` 回答玩家从哪个入口或分组理解它。
- `核心素材依据` 回答它应占哪个真实区域、沿用哪套视觉语言、是否已有实体本体。
- `当前用途` 必须是当前状态能直接决策、执行、查看或反馈的事情。
- `删除损失` 答不上来，元素删除或折叠。
- 同一含义只能保留一个可见入口。若实体、具体动作或具体目标已经无歧义，父级词和同义按钮必须折叠。
- 轮盘、轨道、参数表这类高规则密度对象必须逐格列出 `规则原文标签 -> 提示卡/参数图标签 -> UI短标签`，并记录源文件路径或图片名。任一格没有来源，不能用八卦、数字、占位字或通用装饰替代。

### 2.1 规则到 UI 分层裁决

规则名词进入 UI 前，必须先判定它属于哪一层：

| 类型 | 默认 UI 形态 | 禁止误判 |
| --- | --- | --- |
| 规则实体 | 卡牌、牌堆、token、轨道格、角色板等实体本体 | 不得改成规则说明面板 |
| 可查看对象 | 对象本体、对象旁 inspect、hover/focus tip、临时详情 overlay | `可查看` 不等于必须常驻一个牌堆或大面板 |
| 动作入口 | 对象本体点击、紧凑按钮、segmented control、对象旁菜单 | 不得把父级规则标题和叶子动作同屏堆叠 |
| 状态反馈 | 数字、短标签、边框、选中态、禁用态、目标高亮 | 不得用半透明罩子大面积遮住实体 |
| 提示/说明 | hover/focus/tap tip 或临时 overlay | 默认不得常驻占位挤压布局 |

落位规则：

- 规则中“公开 / 可查看 / 牌堆存在”只证明玩家能访问该信息，不自动证明它要在主界面常驻。
- 没有当前操作依赖的可查看对象，默认折叠为对象旁入口或 hover/focus tip；只有当前回合需要频繁决策时才常驻。
- 提示、解释、结果摘要默认是 `absolute/fixed` 悬浮层；禁止插入正常流挤占手牌、牌堆、地图、玩家面板。
- 按钮必须保持按钮形态：边框、底色、hover/press/focus/disabled 态齐全。禁止为了“风格统一”退化成淡薄文字块或不可识别白块。
- **对象本体优先是通用门禁，不是轮盘特例。** 凡规则实体、参数图格子、轨道格、地图区域、牌堆、卡牌槽、token、骰子面、轮盘扇区等已经有可识别本体或可叠加命中区，短分支默认从属于对象本体；分支名称、代价、结果摘要只在 hover/focus/tap tip 中出现。禁止把 `走 1 / 走 2 / 走 3`、`选 A / 选 B / 选 C`、`模式 1 / 模式 2` 这类实现分支常驻成旁边一列占空间按钮，除非对象本体没有可点击区域、分支无法由本体自然消歧，或无障碍需求要求保留显式入口。
- 当用户或游戏专属规范明确“点击按钮即执行”时，按钮正文只保留动作名和必要状态反馈；代价、支付进度、弃置数量、结果说明、实现命令名只能进入 hover/focus/tap tip、详情层或规则帮助，禁止常驻在按钮正文、角标、圆章或旁边说明块里。
- 命中区、高亮、tooltip 和结算目标必须来自同一份对象定义。地图区域、轨道格、轮盘扇区、卡槽等不允许一套坐标负责点击、另一套图形负责高亮、第三套文案负责提示；若必须分层实现，先建立共享数据源，再由 hitmap/SVG/DOM/canvas 分别派生。

## 3. 风格一致性合同

生图前写出风格合同，禁止只写“高级、精致、商业级”。合同至少包含：

```text
风格基线：哪些真实素材决定整体风格
布局参考：哪些历史图或项目 UI 只参考构图/密度
素材族：主棋盘/地图、玩家面板、卡牌正面、牌背、token、提示卡各自承担什么角色
色彩材质：底色、强调色、暗面板、文字色、透明度、纹理粗细
线条边框：描边粗细、圆角、阴影、发光、边框层数
字体密度：顶部摘要、按钮、卡牌、数字、提示的字号层级
图标语言：来自真实素材、项目图标体系、同一套线性/剪影/印刷风，还是禁用图标
组件族复用：牌库/弃牌/公共牌堆/卡槽/按钮/chip/手牌/地图 token 如何共享材质
```

风格门禁：

- 核心素材是风格真相源；提示卡只决定入口层级，不当整体皮肤来源。
- UI overlay 是对真实素材的最小增强：可点击态、选中态、数量、状态、目标反馈。
- 选中态必须来自同一视觉语言：边框、底色、短色条、小点、轻发光或轻抬起。没有来源时不发明图标、纹章或装饰徽章。
- 若真实素材是低饱和、扫描、印刷、朴素桌游风，生成图也保持该密度；不要升级成奇幻、手游、厚金属、电影光照或 3D 桌面。
- 修假文字时只弱化不可裁决文字，不能弱化卡牌结构、插画区、角标、牌堆、按钮点击感和组件完成度。

### 3.1 风格确认门禁

风格不能靠“像素材”“统一”“高级”这类形容词验收。写 prompt、生图或前端实现前，必须先生成一份可检查的风格确认表：

```text
风格名称：
参考来源：项目 UI/UX 风格文档、核心素材、同类项目 UI，各自采纳/拒绝什么
核心色板：底色、纸色、暗面、主文字、弱文字、主强调、危险/选中、边框、阴影
材质语法：纸本、印刷、金属、木质、玻璃、像素、现代 Web 等，只能选择少数主材质
组件族语法：按钮、牌堆、手牌、玩家条、tip、modal、token、轨道各自如何共享边框/圆角/阴影/标签
状态语法：hover、press、selected、disabled、valid-target、payment、danger 各自的视觉规则
禁用风格：明确列出不能出现的风格方向
```

最低证据：

- 至少从 3 类真实素材取样：例如牌背/卡面、token/marker、主棋盘/轮盘/玩家板。没有素材就标为风险，不能声称“风格一致”。
- 若使用 `ui-ux-pro-max` 或其他通用 UI 建议，必须逐条裁决采纳/拒绝；通用推荐与核心素材冲突时必须拒绝通用推荐。
- 每个新 UI 组件必须映射到同一套 `组件族语法`。按钮像现代网页、轮盘像印刷素材、牌堆像另一套卡皮，判失败。
- 每个可交互组件至少有 `default / hover / press / selected 或 disabled` 中的相关状态；按钮没有按压感或 focus 态，判失败。
- 截图验收必须做风格横向对照：同屏比较按钮、牌堆、手牌角标、tip、玩家条的边框粗细、圆角、阴影、纸色、强调色。只看单个组件好不好看不算风格确认。

风格漂移处理：

- 如果布局已经通过但风格不统一，只允许改色板、边框、阴影、圆角、字号、状态语法，不得重排布局或新增无关 UI。
- 如果通用生图 prompt 一次塞入太多目标导致风格失控，必须按 `结构稿 -> 风格稿 -> 交互态稿 -> 复杂对象复刻` 拆分。
- 如果无法用一句风格名约束模型，必须改用 token 表和组件族矩阵；不要继续追加形容词。

## 4. 布局合同

先分配空间，再写元素：

- 用户提供布局草图、框线图或手绘位置图时，草图优先成为坐标合同：所有点名 UI 必须落在对应区域、贴近对应边界和中心线；禁止把“参考布局”理解成可自由重排的灵感图。
- 用户要求“非 UI 部分空白/不要无关 UI”时，只表示删除地图、装饰、规则说明、日志和无关控件；不表示可以在底部、侧边或指定区域留下无效留白。指定在底边/侧边的 UI 必须贴近对应边缘并占满合理视觉高度。
- 若布局草图点名底部手牌、左右牌堆或弃牌区，底部实体簇必须贴底组织；空白背景不能把手牌区抬到半屏，不能在画面下方留下未被任何 UI 使用的大空带。
- 若真实素材中已经存在可作为 UI 本体的独立素材（例如独立牌背、轮盘 PNG、玩家板、token），生图和实现应优先复用该独立 UI asset。禁止从会平移/缩放/拖拽的地图底图、主棋盘截图或背景图里裁切 UI 本体来冒充“素材一致”；这会把 HUD 锚点绑到场景坐标，导致地图一动就错位。
- “风格与素材一致”只约束 UI 的材质、色彩、边框、密度和真实卡面使用，不等于把所有 UI 元素都从素材图里抠出来。凡是会交互、会固定在屏幕边缘、或未来不应随地图移动的 UI，必须作为独立前端组件重建；没有独立素材时按素材风格抽象形状，不允许把可移动场景图当组件来源。
- 对“必须一模一样”的对象，验收口径是同形、同分区、同材质、同标记关系；只做到同功能、同颜色或同大致位置一律不算通过。
- 用户要求“非 UI 部分空白”时，空白只允许出现在未分配区域；已点名的底部、顶部、左上、右侧锚点必须按 UI 元素的实际占位贴边落地，不能用空白把元素垫离边缘。
- 用户要求 UI-only 时，主舞台不是地图/棋盘，而是空白坐标面；此时只验收 UI 元素和布局位置。不要为了“风格一致”补背景、底图、地图纹理、装饰角、说明分隔线或登录框式边框。
- 主棋盘/地图/战场是最大舞台；HUD 不得把中间挤碎。
- 当前决策对象最重：手牌、骰子、单位、目标区域、可支付资源、待结算效果等。
- 玩家状态、分数、阶段、轮到谁等做贴边轻摘要；薄而可读，不能肥成导航栏，也不能小到不可点。
- 实体区只放实体本体和实体反馈；高层动作按钮、确认/取消、设置、帮助、日志默认不占实体主空间。
- 牌库、弃牌、公共堆、卡槽靠近其所属玩家或真实素材区域；不因为屏幕角落有空就贴角乱放。
- 用户提供布局草图时，不得拿其他游戏的牌库/弃牌/手牌位置作为优先参考；已有项目 UI 只能参考组件密度和可读性，不能覆盖用户草图的锚点合同。
- 手牌/实体主行按主舞台中心线居中；旁边的侧栏、公共堆、工具入口不得把主行挤偏。
- 低频工具、日志、帮助、规则摘要、调试入口默认折叠。若删除后不影响当前状态游玩或查看，就不要显示。
- 临时支付、目标、确认、放大、详情用 overlay 或对象旁浮层，不挤压主布局。
- 固定版图已有轨道、槽位、图例、规则文字只安静保留；不能重做一套同名数字系统。
- 若棋盘会缩放/拖拽，可用轻量摘要补偿离屏信息，但摘要不能复制完整第二套系统。

### 4.1 工具页默认落点

当任务不是“直接给玩家玩的正式主界面”，而是为了辅助实现、校准、取证或生成交互真相源的工具时，默认按以下落点执行：

- 页面文件放在 `src/pages/devtools/<ToolName>.tsx`；游戏专属工具优先命名为 `<GameId><Purpose>Tool.tsx`。
- 路由在 `src/App.tsx` 下追加独立 `/dev/...` 入口；不要劫持正式 `/play/...` 路由。
- 若项目已有工具路由表，则同步登记到 `src/config/toolRoutes.ts`。
- 默认做成独立工具页；除非用户明确要求扩展现有工具，否则不要把新能力硬塞进 `AssetSlicer`、已有 mapping tool 或业务 Board。
- 交付时必须明确告知工具位置：至少写出页面文件路径和访问路由；若还接了工具路由表，也要一并告知。
- 如果工具产出会成为运行时真相源，导出物必须是可落地资产或配置，例如 `mask PNG`、`JSON`、`atlas mapping`、`region color table`；不能只停留在临时画布状态。
- 如果工具产出会成为运行时真相源，并且用户只能看到一个主保存动作，那么该动作必须自动把必要底层数据一并落盘并支持刷新后的自动回读；不能要求用户每次重新导入刚保存的 mask、边界提示或 graph。
- 对地图区域、格子、轮盘扇区、路径边这类“点击范围本身就是规则数据”的工具，先明确三层真相源：`运行时命中/高亮数据`、`规则连通/邻接数据`、`启发式辅助层`。只有前两层可以作为运行时真相；启发式层只能用于 bootstrap、诊断或人工修边。

## 5. 交互合同

必须模拟一段真实玩家流程，而不是摆控件：

- 当前稿先声明类型：`主回合态`、`入口展开态`、`支付态`、`目标选择态`、`结算反馈态` 或其他单一状态。
- 只展示一个当前状态；不要把父入口、子分支、孙动作、支付、目标和结算全摊在同屏。
- 若规则要求先选动作/目标，再计算代价，就必须先进入动作/目标态，再显示支付数量。
- 若对象本体足以承载入口，例如卡牌、骰子、单位、区域、轨道格、牌堆、参数图格子、轮盘扇区，优先让对象本体可点击/可拖拽/可选中；不要另做同义按钮。若确实需要显式按钮，必须先写明本体为什么不能承担入口。
- 复杂地图或大棋盘可使用离屏 canvas/WebGL color picking 做命中，但可见高亮、悬浮提示和结算仍必须回到同一份区域/格子数据；禁止为了性能把交互真相藏成不可审查的临时坐标。
- 若地图交互依赖真实素材中的边界线、地块或海岸线，必须先读规则书、参数图/帮助卡和实际地图，再决定实现方向。未经看图验证，不得把“纯 RGB 阈值 / 全图魔棒 / 边界色膨胀图”直接提升为真相源。
- 只要使用启发式边界、颜色匹配、魔棒或同类自动选区，必须至少抽一个样本区实际看图，判断边界层是否已被文字、纹理、图标、山纹、马纹或装饰噪声吞掉。若样本图已经糊成大块，结论只能是“启发式层不可直接用”，必须降级为 bootstrap/诊断，并补手工边界修正、区域 mask 或显式 graph 数据。
- 若多个互斥分支无法由对象自然消歧，使用紧凑 action rail、segmented control 或对象旁菜单。它是模式选择，不是规则说明面板。
- 所有可交互对象必须有 hover/press/selected/disabled/armed/valid-target 等可见态。
- 直接操控优先：拖拽、上滑、armed 点击、落点高亮、吸附、回弹、合法/非法反馈；按钮只做模式入口、确认、取消、无障碍或危险操作防误触。
- 叶子动作按钮禁止重复“执行”入口：若口径是点击即执行，第一次点击就必须完成动作或进入唯一必要的目标选择层，不得再放同义“执行/确认执行/应用”按钮。若规则确实要求多步支付或危险确认，也只能使用同一个动作入口的状态变化或临时 overlay，且必须写明例外依据。
- 按钮不是规则摘要卡。行动代价、支付数量、抽牌结果、目标解释等只在玩家需要查看时悬浮显示；除非这些数字本身就是当前必须直接操作的控件，默认不常驻。
- 点击流程必须能说清：点击哪里、出现什么、下一步怎么执行、状态如何变化。说不清就不是合格设计稿。

## 6. Prompt 结构

prompt 按这个顺序写，避免模型自由重构：

1. `产物类型`：implementation-facing 2D board-game UI design mockup；不是插画、海报、3D 场景、运行烟测截图。
2. `三源依据`：规则、提示卡、核心素材各自决定了什么。
3. `风格一致性合同`：风格基线、组件族、材质、选中态、图标来源。
4. `风格确认表`：色板、材质、组件族、状态语法、拒绝的通用风格。
5. `游戏专属依据`：只引用 `design-system/games/<gameId>.md` 中的当前游戏事实，不写进通用 skill。
6. `当前状态`：只选一个状态。
7. `当前决策对象与交互流程`：玩家操作什么、顺序是什么、代价/目标/反馈是什么。
8. `布局合同`：主舞台、顶部摘要、侧边控件、底部实体区、临时 overlay 的位置和空间预算。
9. `可见 UI 白名单`：只允许短动作、对象名、状态、数字。固定素材文字不得由模型发明。
10. `禁止项`：列本轮必须删除的重复控件、父级词、假系统、假文字、风格漂移、无来源图标、中心大面板。
11. `实现范围`：React/CSS/SVG/canvas/DOM overlay 可复现；不做真实 3D、电影光照和不可复刻材质。
12. `质量基线`：若有用户认可的候选图，拆出要保留的构图、密度、组件完成度和要降级的问题；不要整体继承其风格。

### 6.1 Prompt 拆分门禁

复杂 UI 不允许把规则、布局、风格、交互态和精细对象全部塞进一次大 prompt 后期待模型自动裁决。

- 第一步只产结构稿：白底或空白舞台，验证 UI 白名单、锚点、贴边、尺寸、空白区域。
- 第二步只加风格：按核心素材抽象材质、颜色、边框和按钮形态，不新增布局对象。
- 第三步只加交互态：hover/selected/disabled/payment/target/tip，不能改结构。
- 对用户要求“必须一模一样”的复杂对象，单独拆 prompt 或单独前端复刻；先锁形状、分区、标记关系，再合回全局布局。
- 若某对象未来不能随地图/场景移动，prompt 必须明确它是独立屏幕 UI，不得从地图、背景、主棋盘截图裁切。

## 7. 三轮自迭代

用户要最终设计稿时，不把第一张失败图丢给用户。最多三轮内部自迭代：

### 第 1 轮：结构正确

目标：规则入口、动作顺序、可见元素、布局大关系正确。

失败即重生：

- 漏读规则或提示卡，导致入口层级错误。
- 多出无来源按钮、日志、流程条、工具、重复轨道。
- 当前状态混杂，或代价/目标顺序错误。
- 主舞台被 HUD 挤压，当前实体过小，手牌/实体行偏心。
- 用户给了布局草图但生成图改了区域位置、底部实体没有贴底、或把“空白非 UI”误生成大块无效留白。

### 第 2 轮：风格统一

目标：核心素材风格、组件族、交互态统一。

失败即重生：

- 地图、按钮、卡牌、牌堆像几套不同游戏。
- 风格偏离核心素材，变成奇幻、手游、厚金属、3D 或烟测灰块。
- 修假字导致卡牌、按钮、牌堆失去组件完成度。
- 选中态、图标、装饰没有来源。
- 同一稿内组件材质不统一，例如轮盘像印刷素材、按钮像现代网页、牌堆像另一套卡牌皮肤；必须回到核心素材族重新统一边框、纸色、阴影、角标、描边和选中态。

### 第 3 轮：可复现与交付

目标：设计稿能让前端 1:1 复现。

失败即不交付：

- 看不出哪些对象可点击、可拖拽、选中、禁用或可落点。
- 尺寸、边距、层级、焦点态不可实现或不可读。
- 仍有假规则文本被画成可读真相。
- 比用户认可候选图明显更简陋、偏心、拥挤或风格漂移。
- 用户明确要求复刻某个已有 UI 对象时，生成图只做到“相似概念”而非同形、同分区、同材质、同标记关系。

三轮后仍失败，停止生图，更新 skill 或游戏专属规范；不要继续微调参数。

## 8. 看图验收

生成后必须先做总览和关键裁图，再下结论：

- 总览：主舞台比例、顶部高度、底部/侧边是否居中与贴合、整体风格是否统一。
- 风格表对照：逐项检查色板、材质语法、组件族语法和状态语法是否被执行；没有风格表不得宣称风格统一。
- 用户布局草图对照：每个点名 UI 是否在草图指定区域；底部/侧边对象是否贴近对应边界；是否因为“空白背景”产生了不该有的大留白。
- UI-only 对照：如果用户明确要求非 UI 空白，必须检查截图里是否仍有背景图、地图、地图裁切、纹理装饰或无关 UI；任一存在都不得收口。
- 核心交互区：当前实体是否可读、可点击态是否明确；如果游戏口径是点击即执行，必须确认没有支付数字、代价圆章、同义执行按钮或常驻说明块回流。若规则明确要求多步支付/目标/确认，再检查它们是否按顺序出现。
- 固定素材区：已有轨道/槽位/图例是否被重画、重复、遮挡或改写。
- 命中同源对照：点击热区、hover/selected 高亮、tooltip 名称和领域结算对象是否引用同一份对象定义；若截图只能证明能点，不能证明点中对象与高亮/结算一致，不得收口。
- 侧边/顶部/底部：是否有低价值控件占位置，是否把主对象挤进中间。
- 风格对照：核心素材、组件族和候选质量基线是否一致。
- 组件族对照：按钮、牌堆、手牌、tip、玩家条是否共享同一套纸色/边框/圆角/阴影/强调色；任何组件明显像另一套 UI，判失败。
- 实现对照：如果当前任务已进入真实前端实现，必须额外检查“是不是直接用了真实棋盘/真实卡面/真实牌背/真实 token”。若截图里主体仍是占位牌、遮罩板、伪槽位或被旧底图噪声主导，则不能宣称“接近最终设计稿”。
- 布局对照：如果当前任务已进入真实前端实现，必须把冻结稿转成空间合同后逐项核对。重点检查主舞台比例、顶部高度、侧边 rail 宽度和顺序、底部完整实体簇中心线、选中态/支付态出现顺序，而不是只看配色和局部组件是否相似。
- 分层对照：大地图/大棋盘/大桌面类实现必须区分场景层与 HUD 层。地图可缩放/可拖拽时，地图对象随地图坐标变换，顶部状态、侧边 rail、底部 dock 默认保持屏幕坐标；截图若显示 HUD 被地图缩放、地图对象脱离坐标、或底部 dock 被侧栏挤偏，判失败。UI-only 稿则不应存在地图层，所有点名 UI 都直接锚定屏幕布局。
- 素材对照：必须逐类确认主图、独立交互部件、牌背、正面 atlas、公共牌堆、token/marker 是否使用了真实素材。只接了主图或只接了牌背，但公共牌、正面 atlas、token 仍是伪元素时，不能宣称素材接入达标。
- 旧底图对照：若主图中的印刷元素与冻结稿要求的前端交互对象冲突，不能靠遮罩/压暗旧底图冒充实现；必须裁决交互所有权，必要时用前端组件重建该对象的可点击、hover、selected、disabled 等状态。

验收结论必须分为：

```text
通过项：
失败项：
删除/折叠项：
下一轮只改项：
是否可交付：
```

不能只写“看起来不错”。若不达标，自己重来，不让用户逐项指出。

## 8.1 冻结稿实现阶段的失败门禁

当用户已冻结最终设计稿并要求前端实现时，imagegen 产线的任务结束，前端实现必须执行以下门禁：

- **禁止重新生图改方向**：冻结稿只作为布局、层级、组件密度和状态参考；不能用新图覆盖用户已确认的方向。
- **禁止表面一模一样**：实现目标是布局一致和交互语义一致，不是复制生成图里的假字、假地图、假卡名或错牌面。
- **禁止旧结构微调冒充重做**：如果现有 Board 的层级与冻结稿不一致，先拆 `Scene/MapLayer/ScreenHudLayer`，再放组件；不要继续在旧 flex/absolute 混合结构上调数值。
- **UI-only 冻结稿不得回流地图链路**：用户要求只保留 UI、非 UI 为空白时，前端实现不得继续保留主地图图片、地图容器、地图拖拽缩放、地图裁切 UI 或地图背景处理痕迹。
- **完整实体簇按簇中心验收**：手牌类底部区域必须按 `牌库 + 手牌 + 弃牌` 整体居中；不能按扣掉侧栏后的剩余空间居中，也不能让侧边 rail 把它推偏。
- **短 HUD 文案按可读性验收**：顶部玩家签、状态 badge、短动作按钮、牌堆角标这类固定尺寸 HUD 文案必须显式防止意外换行、截断和重叠。实现时应使用稳定宽度、`nowrap`、合理字号和 overflow 策略；截图或 DOM 量测必须证明关键短词没有被压成两行。允许例外是规则本身要求竖排或多行的版图文字，但不能把容器挤压造成的换行解释成设计。
- **支付态按流程验收**：如果游戏专属规范要求点击行动即自动支付/执行，截图必须证明行动按钮正文不显示代价、弃置数量、支付进度或花费圆章，且不存在独立执行按钮。如果规则要求先选动作/目标再出现支付，截图必须证明支付提示只在动作已选后出现；不能先显示弃牌/支付区再让玩家选择用途。
- **失败即回结构合同**：截图中只要出现贴角、偏心、重复系统、真实素材缺席、父级词和叶子动作同屏、中心大面板遮挡主舞台等问题，必须回到布局合同重做，不得继续给失败结构补样式。

## 9. 微调规则

用户说“差不多”“继续”“再来一下”“微调”并指向上一版时：

- 先列 `保留项` 和 `只改项`。
- 保留主舞台比例、顶部高度、底部实体区、侧边相对位置、整体风格、已删除的无用控件。
- 只改用户点名问题和相邻小缺陷；禁止换状态、换风格、重排主结构。
- prompt 必须写 `preserve / keep unchanged / change only`。
- 若新图解决点名问题但带来风格漂移、布局重排、控件回流、组件变简陋，判失败，回到上一版窄修。
- 用户确认“就这样 / 用这版 / 作为最终设计稿”时，停止继续重构或再生图；只做最终稿别名、验收记录和必要的通用 skill 缺口修正。除非发现新的通用根因，不再因为单个游戏局部问题改写本 skill。
