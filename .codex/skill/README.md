# BoardGame 项目 Skill 约定

这个目录是 **BoardGame 项目内 skill 的唯一目录**。只要属于本仓库项目 skill，就必须放在 `./.codex/skill/`。

## 放置规则

新增或改动 skill 前，先判断落点：

1. **跨项目可复用的通用能力**  
   例如通用 TDD、通用 UI/UX、通用 PR 审查。  
   这类优先放到全局 / 用户级 skill；项目目录只保留 BoardGame 的增量约束。

2. **BoardGame 专属 workflow**  
   只要内容依赖本仓库目录、脚本、游戏模型、验收门禁、evidence、服务器素材主源、manifest、E2E 口径，就应放在本目录。

3. **BoardGame 对通用 skill 的补充层（overlay）**  
   如果只是“在通用 skill 之上再加本项目约束”，本目录里只保留增量规则：
   - 先说明“先用哪个全局 skill”
   - 再写本项目补充
   - 不要把通用 skill 正文整份复制进来
   - 不要把本项目事故、项目口径、项目补丁反写回 `D:\\codex-home\\skills\\**`

## 目录硬规则

1. 项目 skill 只允许出现在 `./.codex/skill/`。
2. 不允许在 `./.codex/skill/` 之外保留项目 skill 正文、README、重定向说明或副本。
3. 调整目录结构时，必须同步清理多余入口和过时引用，保持单目录状态。
4. 未经用户当轮明确要求，禁止把项目 skill 的新增条款、项目事故结论或项目 overlay 规则上升到全局 skill。
5. 任何准备写进项目通用 skill、项目 overlay、`docs/ai-rules/**` 的规则，默认先过一次“放到未来第 100 个游戏里还成立吗”自检；不成立就必须下沉到单游戏文档、单游戏 skill、覆盖矩阵或当前实现。
6. “第 100 个游戏自检”至少要同时回答三件事：这条规则拦的是哪类跨游戏都会出现的错误、它不会替单游戏预写哪些答案、当前单游戏结论最终下沉到哪里。三件事说不清，就不允许进入通用层。
7. 只要争议已经落到“当前这个游戏这章该不该合并”“这个起手路线更适合示范”“某个专属机制该放哪一章”，默认直接判为单游戏答案，不得借着更新 skill 或规范把它抬成项目通用规则。
8. 通用 skill 或项目 overlay 若需要举例，示例也必须保持跨游戏抽象；禁止把单游戏机制名、地名、势力名或专有控件名写成“通用例子”。
9. 项目内“通用层”同样服务整个 BoardGame 仓库，不是服务当前正在修改的某一个游戏；只要规则离开该游戏就不成立，就必须下沉到该游戏专属文档或 skill。
10. 改写通用层时，默认按“未来大量游戏共用”来写，而不是按“当前这个游戏先能用”来写；如果一条描述放到第 100 个游戏时会显得莫名其妙，就说明它不该留在通用层。
11. 通用层允许引用仓内具体实现文件作为成熟来源，但这类引用只能当证据，不能把实现里的单游戏机制词、地名、势力名或流程术语抬升成通用规则正文。
12. 只要在通用层正文里已经出现“离开当前单游戏就无法理解”的机制词、步骤词或对象名，默认直接判为落点错误；先改回抽象职责，再把专有内容下沉。
13. 只要本轮是在补项目通用 skill、overlay 或 `docs/ai-rules/**`，默认第一步就先做“第 100 个游戏自检”；不要等写到一半、或被用户指出“这不是通用规则”后才回头补判层。
14. “时刻考虑未来 100 个游戏”不是要求提前替未来游戏设计答案，而是要求持续区分两件事：哪些是跨游戏通用判断方法，哪些只是当前游戏这次的章节、案例、起手路线或专项实现；后者一律不得抬进通用层。
15. 只要本轮准备输出章节方案、规范正文、skill 条款或 overlay 规则，默认必须先给出一版最小判层结果：`跨游戏判断方法`、`当前单游戏答案`、`单游戏答案下沉位置`。这三项没先写清，就不得开始写正文。
16. 上一条的目的，是先锁“这一条到底在服务多少游戏”，而不是等正文写出来后再事后解释；凡是跳过这一步直接写章节名、固定顺序、起手路线或专属机制说明，默认按落点错误处理。
17. 项目通用层默认始终处于“百游戏模式”：只要文件落在项目通用 skill、项目 overlay、`docs/ai-rules/**`，就默认是在给未来大量游戏写判断方法，而不是在替当前游戏找最顺手答案。若当前内容一离开这个游戏就失效，默认先停在判层结论，不得继续往通用层写。
18. 用户当轮如果明确要求“先更新 skill / 先更新规范，不要只考虑一个游戏”，默认动作不是补更多当前游戏案例，而是先补三类内容：`怎么判通用与专项`、`什么时候必须下沉`、`没做判层前不得开始写正文或实施`。除非用户明确要求，否则不要把当前游戏章节设计、起手路线或案例顺序直接写进项目通用层。

## 最低门禁

任何新建或改写的项目 skill，至少要回答四个问题：

1. 这份内容离开 BoardGame 还能成立吗？
2. 它是否依赖本仓库路径、脚本、资源链路或验收口径？
3. 它是在补充全局 skill，还是想替代全局 skill？
4. 如果别的项目也看到了这份 skill，会不会被误导成通用规则？
5. 这条内容如果写进 `D:\\codex-home\\skills\\`，会不会把 BoardGame 的局部经验冒充成跨项目默认？
6. 如果这里只是为了举例，我用的示例名是否仍然绑定了某一个具体游戏？
7. 如果这条内容只对一个游戏成立，我是不是已经把它误写进了项目通用层，而不是该游戏专属文档？
8. 如果未来第 100 个游戏接进来，这条规则会帮它避坑，还是会强迫它照抄当前游戏的章节答案、起手路线或专属机制？
9. 我现在补进去的到底是“跨游戏判断方法”，还是“当前这个游戏这次最顺手的答案”？如果是后者，为什么还没有下沉？
10. 如果用户此刻要我“先更 skill”，我补进去的是能拦很多游戏共性错误的门禁，还是只是把当前这款游戏的方案换个地方再写一遍？
