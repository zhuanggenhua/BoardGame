# Tutorial Workflow

这是 BoardGame 项目专用的教程 workflow。它处理的不是“教程能不能走通”，而是“教程是否真的在教玩家玩这款游戏”。

## 使用时机

- 用户明确说 `教程`、`新手引导`、`onboarding`
- 用户说教程 `只在教按钮`、`像规则书`、`看不懂`、`不是真实游玩`
- 你准备新增、重做、压缩或补审某个游戏的教程步骤、教程文案、教程 E2E

## 必读入口

1. `src/games/<gameId>/rule/*.md` 与该游戏当前可用的规则真相源
2. `docs/ai-rules/tutorial-design.md`
3. `docs/ai-rules/e2e-verification.md`
4. `.codex/skill/game-audit-workflow/SKILL.md`

## 核心不变量

0. 任何准备写进教程通用 skill 或通用规范的规则，默认先做一次“放到第 100 个游戏里还成立吗”判断；不成立就下沉到对应游戏的专项文档、覆盖矩阵或教程实现，不得滞留在通用层。
0.1 在通用层写规则前，先明确这条内容是在约束“怎么判断教程是否合格”，还是已经落到了“当前这个游戏这次该怎么拆、先教什么、合并哪几章”的专项答案；后者不得写进通用 skill。
0.2 如果本轮分歧本质上是“当前这个游戏这一章该不该并进上一章、哪条路线更适合首教、哪种案例更适合示范”，默认先把它翻译成跨游戏仍成立的抽象失误，再决定是否值得回写通用层；翻译不出来，就说明它仍是单游戏答案。
0.3 改教程通用层时，必须同时说清三件事：这条规则会拦住哪类跨游戏错误、它不会替单游戏预写什么答案、当前游戏的专属结论下沉到哪里；三件事缺一，就不要改通用层。
0.4 “考虑未来 100 个游戏”在本 workflow 里是默认前置动作，不是只在准备改规范时才补的一次检查；只要本轮开始讨论章节设计、起手路线、示范案例或教学顺序，就先判这是不是单游戏答案。
0.5 只要准备输出教程章节草案、覆盖矩阵、规范条款或 skill 改写，默认先写最小判层结果：
  - 哪些是跨游戏仍成立的教程判断方法
  - 哪些已经是当前游戏这次的章节/案例/起手路线答案
  - 这些单游戏答案最终下沉到哪个专项文档、覆盖矩阵或实现
  - 这一步未完成前，不得开始写教程章节正文或通用层条款
0.6 用户如果明确要求“先更新 skill，不要只考虑一个游戏”，默认先补的是通用判断方法和下沉门禁，不是把当前游戏这次的章节拆法、案例顺序或教学路线换个地方重写一遍。
0.7 只要这轮还在“当前游戏这章该不该并”“这一手要不要先教”“这条路线是不是更适合示范”这种粒度打转，就说明内容仍停留在单游戏答案；在翻译成跨游戏判断方法之前，不得把它写进教程通用 skill 或教程通用规范。
0.8 只要准备重写教程文案、输出章节草案、压缩教程或新增章节，必须先列“重复机制归并表”：把每个拟教学机制标成 `首次完整教学 / 后续复用 / 分支或反例 / 应合并删除`。如果两个相邻章节都在重新讲同一核心机制，默认先合并或压缩，而不是继续润色两章文案。
0.9 重复机制归并表只判断跨游戏都成立的章节边界问题，不替当前游戏预写固定章节数、章节名或起手路线。单游戏的最终合并方案必须落到该游戏的教程实现、覆盖矩阵或专项文档。
0.10 教程必须按玩家因果链组织，而不是按代码模块、测试文件、截图生成顺序或验收清单排序。任何用户可见章节或阶段图都必须能让玩家回答三件事：刚才发生了什么、现在为什么轮到这个动作、做完会改变什么。
0.11 如果某一阶段图单独看会让玩家问“为什么突然到这里”，默认不是标签没写清，而是教程链断了。必须回到章节结构、文案、截图顺序和 E2E 取图点一起重构；不得只给图片补标签或只在汇报里解释。
0.12 使用注入态、预设局面或中段剧本状态时，第一张用户可见图必须先交代“上一步如何导致当前状态”和“当前目标为什么变了”。不得让玩家从基础行动直接跳到终局动作、战斗收口、驱魔、结算或胜负页。
0.13 全链路截图交付必须按玩家游玩顺序排序；技术门禁、素材加载、debug、review 或测试辅助截图必须和玩家链路分离，不能混在阶段流里让用户误以为这是教程的一部分。
0.14 教程文案只要点名某个规则入口、参考入口或正式动作，例如打开剧本、查看目标、攻击、防守、敌方行动、投骰、使用道具或结算，就必须把它归类为 `只读参考` 或 `正式动作` 并提供对应端到端证据。只读参考也要真实打开、切到必要页、关闭并截图；正式动作必须真实点击、触发结算、保存动作前与结果后的截图。禁止只用一句介绍或覆盖矩阵文字宣称已教会该规则。
0.15 如果某个规则是当前章节理解后续目标的必要前提，例如“为什么现在能驱魔”“为什么要攻击”“敌方会怎样获胜”，教程不能把它藏在说明句里带过。要么新增真实章节/分支截图链，要么在覆盖矩阵里标成未覆盖缺口；不得把“主线暂时不走这条分支”当作省略理由。
0.15.1 教程玩家文案不得把用户给助手的设计裁定、验收要求或防回归要求原句上屏，例如“不要常驻写公式”“放到悬浮提示”“卡图已有不要复写”。如果这些要求背后有玩家需要学习的内容，必须改写成玩家动作与规则因果；如果只是实现裁定，只能留在测试、审计、覆盖矩阵或专项合同里。
0.15.2 教程使用预设中段局面时，玩家可见文案不能只写“已经学会 / 已经获得 / 已经完成”。必须补清前置动作、成功条件和当前步骤为什么成立；若该前置没有真实实操截图，覆盖矩阵必须标成“前置说明 / 未实操演示”，不能报成完整教学链。
0.16 只读参考入口必须语义命中玩家文案。文案写“剧本页 / 目标页 / 胜利条件”时，截图和断言必须打开对应目标内容；玩家参考卡、帮助卡、规则摘要、素材图或默认翻面卡不得冒充剧本目标页。
0.17 同类正式动作必须复用同类主流程 UI，除非已有明确设计裁决。攻击、驱魔、发现牌检定等都会投骰时，教程 E2E 必须比较它们是否落在同一类主骰盘、同一交互优先级和同一可见层级；不能一条链居中主流程，另一条链退化成角落小面板或新壳层。
0.18 首剧本 / 首场景教程只要规则里存在怪物、敌方单位、召唤物、复活体或等价非玩家敌人，就必须在覆盖矩阵里逐项标成 `已覆盖 / 明确不必要并说明 / 待补端到端证据`。不能因为主英雄胜利链不经过该实体，就默认省略怪物行动、攻击或目标说明。
1. 基础教程默认只教常规对局，不掺双人变体或扩展规则，除非用户明确要求。
2. 先出完整教程文案，再改实现；文案方向没锁定前，不得先改 `tutorial.ts` 硬做一版。
3. 教程文案默认必须先以规则原文和项目内规则真相源为依据，不得先看现有教程文案就顺着旧口径改写；具体按 `docs/ai-rules/tutorial-design.md` 的“规则原文优先，禁止把实现关系翻译给玩家”门禁逐句过账。
3.1 每次教程语言包改动后，必须对中英文 `tutorial` 区块做静态扫描，并由教程单测拦截“同一画面 / 结果面板 / 摘要 / 队列 / 为了演示 / 待放置状态 / 主视区”等实现或作者话术；E2E 通过不能替代文案扫描。
3.2 规则书或剧本书已有简洁原文时，先复用原文或做最小转写，再追加当前界面所需的动作补充；禁止把“同一画面 / 结果面板 / 摘要 / 队列 / 演示 / 横幅 / 面板”等实现关系写给玩家。每次审查必须能指出每条玩家句子的规则、剧本、动作或状态来源。
4. 如果用户当前在审文案、改文案或明确要求“先给我文案”，则在用户明确认可前，不得实施到 `tutorial.ts`、语言包、测试或 E2E。
5. 开场第一句默认固定成：`目标 + 一个基础回合动作 + 结束/胜负条件`。
6. 后续步骤不得复读已经讲过的规则。
7. 禁止空提示句、过渡废话和“本局教学目标”这类作者口吻标题。
8. 文案应贴真实局面，能直接点名当前牌、当前收益和当前动作。
9. 教程不只教显式规则，也要教真实隐性交互，例如点卡/悬浮看分数、读懂关键提示。
9.1 基础教程必须覆盖本游戏首次上手时高频但不明显的“桌面读局操作”；例如切换/查看对手公开视角、打开自己的牌库/弃牌堆、查看牌堆数量、放大看单张牌、查看战力/分数来源。不能只教出牌和结算。
9.2 这些桌面读局操作必须贴在真实需要它们的局面里教：对手刚打完牌时教看对手公开区，抽牌/弃牌/回收刚发生时教打开牌库或弃牌堆，计分前教查看力量来源；禁止单独塞一段“界面功能介绍”。
9.3 如果某个不明显操作在当前游戏里是理解局势的必要能力，但教程没有覆盖，基础教程不得收口为“玩家已经知道怎么玩”；必须在覆盖矩阵里单列“桌面读局操作”并给出步骤落点或明确暂不处理原因。
9.3.1 非直觉 UI 必须单列覆盖：带计数的确认按钮（如 `确认 1/2`）、多次确认/分步确认、聚焦到自己位置/房间/对象的按钮、观察视角切换、只读规则/剧本/目标入口、状态色、进度轨、可取消选中态、等待归属、可改骰/重掷入口，都要在教程覆盖矩阵里写清现实含义、教程或帮助落点、E2E 截图证据；缺落点时不得称为教程完整。
9.3.2 教程解释非直觉 UI 时必须贴真实局面，说明“什么时候用、点了改变什么、怎么退出/恢复”。不得只复读图标名、按钮文案或内部字段；如果正式控件本身看不懂，先修正式 UI 的短提示或可见语义，再补教程。
9.3.2.1 带计数的确认按钮必须按玩家实际看到的结果解释。文案应说明“同一次公开结果/发现/结算里还有几项需要阅读并确认、当前画面已经显示了什么、确认后会回到哪里或进入哪一步”，不得用画面数量来描述确认次数，也不得暗示已经同屏显示的获得、判定、抽牌或检定是分开发生的结果；不得用 `阻塞结算`、`队列`、`pending`、`stepKind` 这类内部流程词解释给玩家。
9.3.2.1A 如果多个内部结果事实已经在同一个结果画面里由正式对象承载，且下一步都是“读完关闭 / 回到牌桌 / 进入同一个后续状态”，玩家 UI 只能给一次确认；不得因为领域层有两条记录、两条日志、两个 reducer 步骤或两个测试断言，就生成 `确认 1/2`、`确认 2/2` 这类多次玩家动作。
9.3.2.2 观察视角、镜头聚焦和返回上下文必须分开写。点玩家/队友若承担“切观察视角”，教程要说明首次点击切到谁、镜头是否随之移动、再次点击或关闭后恢复到进入观察前的上下文；不得默认写成固定回自己，也不得把“聚焦到自己位置/房间”的按钮写成通用返回按钮，除非该控件确实承担返回职责。
9.3.3 教程覆盖“所有元素”默认指所有玩家可用元素：影响决策、操作、状态读取、规则回看或结果理解的常驻/阶段性 UI。纯装饰纹理、无交互背景和正式素材已自解释的图面细节不需要逐个教学，但必须在覆盖矩阵中与玩家可用元素区分开。
9.4 如果某个正式操作允许从“默认来源”之外选择对象，例如除中央池/手牌/公共区外还能拿别人面前、弃牌堆、地图边缘、临时区或上一轮遗留区里的对象，教程必须先解释这些额外来源为什么也是合法对象，再要求玩家点击。不得直接写“点某处对象”让玩家猜该区域也可交互。
9.5 这类非默认来源教学必须至少覆盖三件事：默认来源是什么、额外来源是什么、拿/选额外来源后原对象或原持有人会发生什么变化。E2E 不能只断言文案出现，还必须实际点击该额外来源对象并验证状态变化。
10. 计分制游戏必须出现一次清晰的计分因果，不得只展示一个结果数字。
11. 结语必须短，只做收口与鼓励，不再重讲规则。
11.1 基础教程必须先设计一个“玩家可感知的最小乐趣闭环”，再决定步骤和文案；不得只把规则条目排成能跑通的操作清单。
11.2 “最小乐趣闭环”必须同时满足三项：① 玩家做出至少一个真实选择；② 两个或以上动作之间存在可见因果；③ 最终产生分数、战力、控制权、资源、伤害或局势优势等可见收益。
11.2.1 规则真相源里直接决定胜负、结算或结果判定的核心规则，必须进入教程正文或覆盖矩阵的明确教学项；不能只靠 UI 上短标签、结果截图、测试通过或“玩家能看到结算”来替代教学。若规则涉及排序/比较/牌型/伤害类型/资源换算/控制权判定，教程必须至少教一次“怎么读”和“怎么用它判断结果”。
11.2.2 如果基础教程声称已经覆盖端到端结算，必须同时覆盖结算前的判定依据和结算后的读法：玩家在结算前知道系统会比较什么，结算后知道每个结果行为什么成功或失败。缺任一项，只能称为“跑到结果界面”，不能称为“教会结算规则”。
11.2.3 如果某类判定表会被玩家在正式局中反复查阅，例如牌型强弱、伤害/费用表、资源转换表或控制权比较表，基础教程不能把它只写死在一次教程文案里；正式游戏界面也必须提供随时可打开的辅助入口，并优先由规则数据驱动，便于后续替换不同规则集。
11.2.4 如果教程覆盖胜负、结算、摊牌或计分，不能只演示失败或只演示成功；至少要证明主教程链能跑到“正确操作得到正向结果”，并在测试或覆盖矩阵里记录反向结果如何出现。只看到失败结算，不得称为完整结算教学。
11.3 以组合、构筑、派系混搭、连锁效果、职业/角色协同为核心卖点的游戏，基础教程必须出现一次“首个可感知组合”；至少两个系统、牌组、派系、角色能力或资源来源都要对结果有不同贡献。禁止把多个动作并排讲完，却没有说明它们如何互相成就。
11.4 如果当前示范路线只能证明“玩家会点按钮 / 会按阶段推进 / 知道规则名”，但不能让玩家看到“这样玩为什么有意思”，该路线不得进入教程正文；默认先换案例、换起手、换局面或缩短到能展示乐趣的闭环。
11.5 “首个可感知组合”是通用判断门禁，不是替单游戏预写固定章节、固定牌组或固定起手路线；具体选哪张牌、哪条路线、哪次计分，必须下沉到对应游戏的覆盖矩阵、专项文档或 `tutorial.ts` 实现。
12. 即使是“示范题教学”，也必须从首次教学所需的第一个**正式决策入口**进入；不得直接把玩家切到中段预设题面，再让他突然支付、结算或收口。
12.1 如果某个开局入口只是低信息量前置，例如纯确认、纯进入、纯选择外壳，而本游戏规则书并不要求玩家在这里理解关键规则或做真实判断，则它可以作为真实进入链路的一部分存在，但**不应自动单独占一章或占掉基础教程的大部分篇幅**。
12.2 判断“要不要教这个入口”时，先问两件事：规则书有没有把这里当成首次理解点；玩家在这里是否需要做会影响后续理解的真实判断。两者都不是，就默认把它压缩成过场或并入后续主章节，不单独扩写。
12.3 教程不得把“选了一级行动之后才需要选的目标/地区/支付对象”，提前伪装成首个正式决策入口；如果规则是先选行动、后选目标，教程就不得改教成先选目标。
12.3.1 如果规则文本把“弃牌、消耗资源、支付费用、花费行动点”等写在行动效果之前，教程和正式流程必须先完成费用支付，费用支付成功后才允许进入效果触发带出的目标、地区、部队或接收区选择；不得为了截图顺手把效果目标提前成第一步，也不得在支付前写“目标已锁定”。
12.3.2 审计这类链路时必须写清 `费用/成本 -> 效果触发 -> 后续目标选择 -> 结果反馈` 四段各自的真实承接物；如果支付后才出现的目标是地图、棋盘或场景对象，E2E 主路径仍必须回到该对象本身，不得用右侧按钮列表证明主路径合格。
12.4 提示横幅、步骤卡、状态条默认只承担提示，不是正式交互载体；除非它自己真的承接点击，否则教程与文案都不得把它写成“现在点这里”。
12.5 只要当前教程涉及回合主循环、一级行动、目标地区、支付对象或动作顺序，动手前必须先列一张“一级交互审查表”；没有这张表，不得开始写教程正文或改 `tutorial.ts`。
12.5.1 这张“一级交互审查表”必须先按规则书或权威真相源列出**该回合所有同层一级行动全集**，再逐项映射到当前正式 UI；不得只按当前屏幕上最显眼、最容易截图或当前案例正好走到的几个入口来反推一级动作。
12.5.2 如果规则书同层同时存在 `打牌 / 升级 / 弃牌行动 / 轮盘行动 / 结束 / 公开区拿牌 / 桌面直点对象` 这类多个一级入口，教程与审查都必须先把它们完整列齐，再判断本章教哪一条；缺任何一类，都不能声称“基础回合”或“一级交互”已经审清。
12.5.3 如果用户明确要求“所有交互都要审查”“别再漏一级动作/支付/战后收口”或语义等价表达，除了一级交互审查表，还必须再补一张“主要交互清单表”，至少覆盖：`开局公共推进`、`一级行动入口`、`支付/弃牌`、`二级目标或来源选择`、`地图目标选择`、`待结算战斗`、`战后/围城/占领`、`年度或阶段结算`。没补这张表前，不得把教程或正式流程判成“已经审完”。
12.5.4 如果用户目标包含“基础回合 / 完整回合 / 首回合 / 基本流程端到端 / 看出这个游戏怎么运作”，或当前争议已经落到“第一步到底先做什么”，还必须再补一张“首回合动作顺序表”。这张表至少写清：
  - 规则书从正式主入口开始要求玩家依次决定什么
  - 当前正式局在每一步首先暴露给玩家的真实对象
  - 当前玩家在这一格是否真的已经拥有选择权，还是只在经过强制公共推进/前置处理
  - 哪些属于同层一级动作
  - 哪些只是后续目标/支付/确认
  - 默认预选在这一格里只是弱聚焦，还是已经进入正式确认
  没补这张表前，不得写基础章开场步骤，也不得声称“这是完整回合”。
12.5.4.1 如果某个阶段只是强制公共推进、低信息前置或纯进入壳层，而玩家尚未在这里做会影响后续理解的真实判断，则它可以存在于流程里，但不得被误写成“第一步正式决策”或占掉基础教程的大部分 `requireAction`。
12.5.4.2 只要本轮已经进入“当前玩家真正有选择权的一级动作层”，教程的第一个主操作步骤就必须落在这一层的真实承接物上；不得跳过它，直接去教后面的目标地区、支付对象、来源区或结果确认。
12.5.5 只要当前在争议“第一步该点哪里”“为什么会被教成先选地区”“按钮和地图谁是主入口”“横幅是不是交互”，还必须补一张“当前屏幕可见可点对象盘点”。必须把该阶段玩家第一眼能看到并可能尝试点击的对象逐项标成 `一级动作入口 / 二级目标 / 支付对象 / 确认控件 / 提示UI / 非当前步骤对象`；不得只按最后成功点击的那一个对象，倒推出教程的第一步。没补这张表前，不得把任何默认高亮、默认聚焦或案例地区写成第一步。
12.6 正式流程里如果存在“默认选中的地区/牌/轮盘项/行动项”，这只能算便捷初始态，不等于玩家已经做出该决策；教程不得把这种默认预选写成“第一步先选这里”。
12.6.2 不只文案不能误写，正式 UI 视觉也不得把默认聚焦直接画成“已确认 / 已锁定 / 正在执行”。如果某个对象只是默认焦点，它最多只能表现为弱聚焦；只有玩家实际点过、确认过，或流程已正式进入支付/执行阶段时，才允许使用强确认视觉。
12.6.1 如果正式流程已经锁定了某个 `来源区 / 出发对象 / 已确认主动作对象`，而当前阶段只是继续选目标、继续看地图、继续支付或继续确认，教程与正式 UI 都不得把后续焦点切换写成“重新选择来源”。这时必须明确区分：`已锁来源`、`当前焦点`、`真实下一步点击对象`。
12.6.3 只要已经进入支付、二级目标、地图目标、战后或结算步骤，任何不承接点击的横幅、摘要卡、步骤标题、状态条都不得再把默认焦点、已锁来源区或当前候选区写成“第一步先点这里”。这类文案只能说当前在处理什么步骤、还剩几次、结果会怎样；若真正要点的是地图、手牌、轮盘格或右侧选项按钮，教程与正式 UI 都必须继续把主语义留给这些真实承接物。
12.7 只要当前阶段的真实操作是直点地图、卡牌、轮盘格或列表项，这些可操作对象进入该阶段时就必须给出清晰高亮或等价可点击语义；不得让玩家靠读横幅、读右侧说明或点替代按钮去猜主入口。
12.7.1 如果规则目标是地图、棋盘或场景里的现实对象，例如地区、地点、基地、部队、随从、牌面或轮盘格，且该对象在当前场景里能稳定命中，那么正式主流程和教程 E2E 主路径必须直接点击该场景对象；文字按钮、右侧列表、摘要卡按钮只能作为备用、无障碍入口，或作为场景对象已经选定后的效果/数量/确认控件。只要 E2E 仍通过按钮完成该目标选择，就不能判定这一步交互合格。只有对象命中、身份映射或消歧确实不稳定时，才允许按钮暂作主入口，并必须把原因写成正式缺口继续追踪。
12.7.2 判断按钮是否越界时先问“规则目标是什么”：如果现实目标是选择地区、地点、部队、基地、随从或牌面，按钮不得承接这次目标选择；如果现实目标已经由场景对象锁定，按钮只是在确认建军数量、效果分支、战后处理或继续结算，则按钮可以保留。E2E 和审计文档必须分别记录 `场景目标选择` 与 `后续确认按钮`，不得用后者证明前者合格。
12.8 教程覆盖矩阵如果声称覆盖“基础回合”或“完整回合”，必须把该链路中的一级动作、支付/弃牌、二级目标、结果反馈逐项列出来；缺任一层都不能叫完整回合。
12.9 只要本轮准备合并章节、压缩教程、删续章、收教程目录或把多条链并成一章，就必须先做一版“覆盖差异表”：明确哪些规则点、真实截图链、正式入口证明会被保留，哪些会降级成缺口，哪些由新章节等价接替。没有这张差异表，不得静默移除任何已存在的规则覆盖、截图链或教程步骤。
12.10 任何教程重构只要删掉了一个先前已覆盖的核心规则点、真实交互链或截图证据，而新方案又没有在同轮提供等价或更强的替代证明，结论必须降级为“覆盖退化/待补回”，不得继续使用“教程更简洁了”“结构更合理了”来收口。
12.11 `implementation-map / 覆盖矩阵 / 章节草案 / 教程脚本草案 / 实施前映射` 都只属于计划层，不是运行态真相源；任何“教程已实现”“正式局已具备入口”“新游戏已收工”的结论，都必须回到当前 `tutorial.ts`、当前正式进行页源码和真实 E2E 截图核对，不能拿计划文档代替。
12.12 如果用户明确要求“所有交互都要审查”“新游戏收工”“给我一个能看出怎么运作的端到端”，除了一级交互审查表和主要交互清单表，还必须再补一张“正式进行页一级入口核对表”，逐项标出规则书同层一级动作在正式局当前是 `真实可用 / 抽象替代 / 教程注入专供 / 尚未实现`。没补这张表前，不得宣称正式流程完整。
12.13 任何已存在的教程章节、隐藏续章、真实截图链或独有规则覆盖点，只要本轮还没拿出等价或更强的替代证明，就默认不得移除、降隐藏或降级；若确需删除，除了覆盖差异表，还必须满足“用户当轮明确允许”或“同轮已给出更强替代证据”之一。
12.14 教程覆盖矩阵、implementation-map、脚本草案只要与当前 `tutorial.ts`、当前目录显隐、当前 `nextTutorialId`、当前 E2E 截图链有任何一项不一致，就必须先标成“过时计划态”并回写；在回写完成前，不得继续把它们当作当前真相源推进教程设计、正式交互审计或“新游戏收工”判断。
12.14.1 如果当前游戏同时存在一份明确面向运行态的专项审计真相源，例如 `primary-interaction-audit`、`formal-flow-audit`、`runtime-closeout-audit`，那么凡是“正式局当前有没有这个入口”“当前还能不能报收工”的判断，一律以这类运行态审计文档为准；`implementation-map / 覆盖矩阵 / 脚本草案` 只能继续作为计划输入，不得反压运行态审计结论。
12.14.2 如果本轮代码已经改变了正式入口、交互承接物、提示文案、默认聚焦语义或教程/正式局一致性，而运行态专项审计真相源里仍保留旧口径，那么默认动作不是“先按旧文档继续推”，而是必须先把这份运行态审计文档同步回写到当前真相，再继续后续教程设计、正式交互审计或收工判断。
12.14.3 回写运行态专项审计真相源时，禁止把当前状态继续二值化成“完全没有入口/完全已完成”。如果正式局已经对一部分真实对象接上了一级入口、但仍受低保真对象或覆盖面限制，就必须明确写成类似“局部真实可用 / 仅限已识别对象 / 仍有正式缺口”的状态，并把边界写清；不得继续沿用“当前无正式入口”这类已经失真的旧句子。
12.15 只要用户目标里明确包含“图呢 / 打开图片 / 看图确认 / 每步都要截图并指出点哪里 / 端到端看出怎么运作”，截图就不只是证据路径，还必须被实际打开核图；只报绝对路径不算完成。
12.16 只要当前范围要求“所有交互都要审查”，`一级交互审查表 / 主要交互清单表 / 正式进行页一级入口核对表` 三张表都必须逐行给出当前状态（例如 `真实可用 / 抽象替代 / 教程注入专供 / 尚未实现`）；仍有空行、抽样行或未定状态时，不得宣称“已经审完”。
12.17 上述审查表只负责锁定真相与缺口，不构成“任务已完成”的证据；只要表里仍有 `抽象替代 / 教程注入专供 / 尚未实现 / 教程与正式局不一致 / 上屏文案误导顺序` 任一行，本轮就必须继续回到当前 `tutorial.ts`、当前正式进行页源码、当前 worktree 门禁和真实截图链处理，不能停在审查文档、覆盖矩阵或口头审计结论上。
12.18 如果用户明确要求“skill 先更新一下再继续”“不要再犯低级错误”“所有交互都要审查”，更新通用 skill 后必须立刻继续做当前游戏的运行态审查与实现收口；禁止把“skill 已补”本身当成这轮任务的完成或主要进展。
12.18.0 全交互审查不得从几张教程截图或 E2E 成功链倒推全集；必须从规则书同层动作、当前状态字段、command/event、builder/reducer 和当前 E2E 入口共同反查。截图只用于验证某一行当前长什么样，不得替代交互清单来源。
12.18.0.1 每个交互行必须分别写清 `真实承接物` 和 `提示 UI`；如果一行只有横幅、步骤卡、摘要或状态条，却没有按钮、卡牌、地图、轮盘格、列表项或系统交互入口，就说明教程还没锁定真实操作对象，不得写教程正文或实施。
12.18.0.2 教程步骤进入二级目标、支付、战后或结算选择时，`highlightTarget` 必须命中该步骤当前真实承接物本身；不得继续高亮上一阶段的手牌条、地图层、横幅、摘要、已完成入口、空占位容器或被结算/弹窗遮住的旧底层容器。E2E 也必须同时等待教程步骤标记、真实承接物出现，并用几何断言确认高亮锚点宽高大于 1、落在当前可视层中，防止“业务面板已出现但蓝框框空处”的假通过。
12.18.0.2.1 如果教程步骤讲的是结果、结算、摊牌、战斗或计分，蓝框必须落到当前结果主体或被结算对象本体；不得落在外层 portal 容器、fixed 子层外面的占位 div、提示气泡、纯逻辑锚点或只含 sr-only 文案的节点。文字说明只能辅助，不能替代蓝框指向真实游戏对象。
12.18.0.2.2 如果结果主体本质是卡牌、棋子、骰子、地图地区或单位，结算 UI 和教程蓝框必须优先指向这些真实游戏对象；不得只显示“对子 / 命中 / 成功 / 失败 / +3 分”之类文字摘要来替代对象本体。
12.18.0.2.3 教程文案框不得遮挡本步骤要教学或要求点击的目标主体、按钮、卡牌、棋子、骰子或地图对象。只要目标仍在当前可视层，tooltip/气泡必须选择与目标不相交的位置；E2E 至少要对关键步骤断言教程卡片与高亮目标没有几何重叠。不能用“按钮还能被 force click”证明教学画面合格。
12.18.0.2.4 如果教程步骤高亮的是一个可能因前置条件未满足而禁用的确认/推进按钮，教程必须二选一：要么延后进入该步骤直到前置条件已满足，要么把补齐前置条件所需的真实操作也列入本步骤允许命令，并确保提示框不遮挡这些前置操作入口。不得让教程进入“按钮被高亮但永远点不了”的状态，也不得用 force click 绕过。
12.18.0.2.5 `requireAction` 文案里的动作对象必须和真实高亮/点击对象同名同位。文案写“点击 / 点 / 选择 / 确认 / 结算”时，必须使用当前屏幕真实可见的按钮文案或对象名；不得写一个概念性动作名让玩家去猜。E2E 至少断言：文案包含真实控件名、该控件有 `data-tutorial-id` 或等价锚点、点击它后进入预期结果。只断言步骤推进、命令成功或结果出现，不算审清“玩家该点哪里”。
12.18.0.3 当规则目标是地图、棋盘、场景里的现实对象，且当前场景对象可命中时，正式 UI 与教程必须以场景直选为主；按钮列表只能作为备用、无障碍入口，或作为目标已锁定后的效果/数量/确认控件。若目标是“来源对象 → 目标对象”的组合选择，场景直选必须同时表达这组关系，不能让一组文字按钮替代主流程。只有对象命中、身份映射或消歧无法稳定时，才允许暂用按钮主入口，并必须把原因写成正式缺口。
12.18.1 全交互审查落表后，必须把每一行继续分流为 `可立即真修 / 需要建模或真相源补齐 / 明确暂不处理且说明原因`。其中 `可立即真修` 必须继续回到源码、语言包、测试或截图链处理；不得把“已写入审计表”当成这些行的完成证据。
12.18.2 对 `需要建模或真相源补齐` 的行，必须明确缺的是哪类真相，例如规则级对象映射、素材合同、状态字段拆分、交互承接物或阶段收口；不得用一句“后续优化”吞掉。若缺口会阻止“新游戏收工”，最终回复必须原样保留。
12.19 只要规则书同层一级动作里仍有 `抽象替代 / 教程注入专供 / 尚未实现`，教程就不得把某条单独示范链、某个默认选区、某个后续目标选择或某个隐藏续章，包装成“基础流程第一步”“正式主入口已完整”或“新游戏已收工”。这类缺口必须在教程结论里原样保留，并继续回到正式进行页实现处理。
12.20 只要正式局某个一级动作当前依赖的可见对象仍是 `低保真预览 / 错 atlas / 混入别类对象 / 没有规则级身份`，它就不得被记成“正式一级入口已具备”，即使玩家眼前已经能点到某个局部 seam。
12.20.1 这里的“别类对象”包括但不限于：人物牌、纪年卡、剧本卡、牌背、帮助卡、占位壳，或其它不属于该一级动作对象集合的可见对象。
12.20.2 一旦命中这条，当前状态只能写成 `低保真替代 / 局部真实可用 / 正式缺口` 这类精确状态；不得继续把教程示范链、局部直点 seam 或抽象按钮链包装成“正式主入口已经有了”。
12.20.3 命中这条后的默认动作不是继续补文案、补高亮或强行在这层上挂教程，而是先追 `素材合同 / atlas 裁切合同 / 卡牌真相表 / 规则级 defId 映射`；这些真相没锁定前，不得继续在该对象层上补“正式入口”结论。
13. 教程要求玩家处理某张具体牌时，必须高亮到单牌级；禁止只高亮整片手牌区、整片中央区或整段面板。
14. 教程步骤一旦完成，上一张目标牌的高亮/选中/聚焦态必须及时退场；禁止把旧目标牌描边残留到下一步。
15. 基础教程必须覆盖这款游戏自己的核心规则面，不能只靠一条最短闭环冒充“学会了怎么玩”。
16. 如果某一步只是当前案例前提，玩家文案只能解释当前局面为什么从这里开始，不得出现“这道示范题”“为了教学”“这不是通用规则”之类作者口吻。
16.1 教程玩家文案默认优先使用规则里的动作名、对象名、结果名，不得用“这一步 / 下一步 / 这里 / 这次 / 现在先”这类作者旁白腔代替规则概念。若去掉这些旁白后文案就说不清，说明当前句子本身没有落到真实规则语义。
16.2 玩家可见教程文案不得混入验收口吻。像“真实链路”“运行态”“不是动画”“不是说明图层”“不是假按钮”“E2E 已覆盖”“正式验证”这类说法只能写进测试、截图证据、审计文档或开发汇报；玩家正文必须改写成游戏内动作和结果，例如“房间会翻开，并抽取对应的发现牌”。
16.3 这条规则只拦跨游戏都会出现的“把验收证明写给玩家看”错误，不替任何单游戏预写章节、路线或固定案例；当前游戏的专属路线仍下沉到对应教程实现、覆盖矩阵或专项文档。
16.4 教程里的随机结果过程不得被一行摘要替代。凡是规则动作包含投骰、重掷、翻牌、抽牌亮相或结算型 reveal，玩家必须看到对应的结果承载，例如骰面、牌面、抽到的对象名和效果区；不得只用日志、横幅或“无事发生 / 即时生效 / 成功”这类摘要收口。
16.4.1 如果翻开的牌、发现牌、事件牌或效果文本会立即要求投骰/检定，则牌面和本次骰面必须作为同一个阻塞主结果展示；不得只显示牌面、只在角落/日志/小条显示骰子，或只用一行文字摘要“检定结果”。
16.5 这条规则只拦跨游戏都会出现的“把随机过程压扁成摘要”错误，不规定单个游戏必须使用哪种视觉形式；具体骰子、牌面、轮盘或其它承载仍下沉到对应游戏实现与截图证据。
16.6 判断“缺骰子 / 缺牌面 / 缺模型 / 缺素材”前，必须先区分：素材包真不存在、素材已在来源包里但未接入运行时、运行时已有低保真等价承载。最终汇报只能按证据写“未找到 / 已找到但未接入 / 已临时承载”，不得把“运行时没接”说成“素材没有”。
16.7 阻塞式随机/揭示结果必须进入主视线区域。只要翻牌、投骰、抽牌亮相、事件选择或战斗结算会阻塞当前流程，就不能把结果缩到角落 HUD、侧栏小条或教程气泡旁的一行说明；教程提示层只能引导玩家看正式结果承接，不能替代正式 UI 的牌面、骰面或结果本体。
16.7.1 阻塞式牌面、骰面或参考页已经成为当前主结果时，教程说明卡必须退让主视线：只保留底部/既有动作锚点的最小确认控件，或使用一句“看清后继续”的短提示；不得把长段教程总结并排贴在正式素材旁边。
16.7.2 正式牌面、房间板块、骰面或参考页已经包含标题、正文、点数或结果说明时，用户可见 UI 不得在旁边再复读同一内容。教程层只负责引导玩家看正式素材，交互层只保留必要选择、确认或跳过；若看不清，先查图集切片、裁切坐标、压缩产物、显示尺寸或放大承接，而不是用旁边正文替代素材。
16.7.3 图集裁片进入教程或阻塞式揭示时，裁片本身就是主信息承载。不得再用底部条、侧栏、toast 或教程卡把裁片中的标题/正文/结果重新写一遍；可见层只留短按钮或必要选择，读屏文本可以保留。
16.8 用户可见教程注入态不得使用测试专用假对象。凡是教程会让玩家看到抽牌、翻牌、投骰或结算结果，预设状态必须引用正式规则对象和正式素材承载；“测试事件 / 测试牌 / 中性占位结果”只能留在开发测试里，不得进入玩家教程截图链。
16.9 教程让玩家点击某个可见游戏对象时，提示文案和高亮必须同时指向同一个对象本体；例如卡牌、房间、骰子、棋子、地图区块能直接点，就不得只高亮后续动作按钮、整片容器、角落圆点或替代列表。文案必须写清“先点哪个对象本体，再点哪个确认/使用/继续入口”，否则玩家无法知道真正操作顺序。
16.9.1 如果真实流程是“先选择对象本体，再使用/确认”，教程 E2E 必须证明对象本体有清晰可见的全对象高亮或选中态，并且后续按钮只在对象选中后推进；不得用按钮可用、测试点击成功或内部状态变化替代玩家可见证据。
16.9.2 如果对象已经使用、禁用或暂不可用，放大预览/详情查看不得继承会降低可读性的透明、灰化、模糊、遮罩或禁用层。真实持有区可以弱化已用状态，但详情预览必须保持清晰，让玩家能读牌面。
16.9.3 如果正式流程是先选择卡牌、棋子、骰子、地图对象或列表项，再点确认/使用/结算才消耗或生效，第一次点击必须产生清楚的选中反馈，例如抬起、描边、发光或等价状态；再次点击同一对象应取消选中，除非规则明确要求单击立即执行。教程 E2E 必须覆盖未选中、选中态可见且确认按钮出现、取消或确认后状态正确三段；只看命令成功、对象消失或结果出现，不算验证了选择交互。
16.10 教程涉及发现、事件、抽牌、投骰、重投、改骰或其它阻塞结果时，截图证据必须覆盖完整用户步骤链：触发前对象高亮、结果主体出现、可修改/可选择对象高亮、选择对象本体、结算后结果。只交一张最终图、只看日志文本、只看一行结果摘要，不能判定教程 UI 合格。
16.10.1 对“重投 / 改骰 / 选择骰子”类流程，截图必须证明玩家选择的是可见骰子或其投影命中区，而不是数字按钮、列表项或代理控件；重投结束图必须等待物理骰或等价动画落定后再截，不得截瞬移中间态冒充完成。
16.11 教程首帧不得先露出默认样式、错误图集、纯色占位或错位布局，再闪成正确样式。凡首屏或当前步骤依赖正式图集、牌背、房间牌、骰子皮肤、角色图或阻塞式发现牌，这些素材必须进入关键加载门禁；未就绪时显示明确 loading/扫光/转圈，而不是让玩家看到错误态。
17. 动手前必须先列教程覆盖矩阵：规则条目、对应章节/步骤、截图证据三者先对齐，再写教程文案。
18. 教程进度不会持久化时，默认优先拆成多个短章节，而不是一条超长教程。
19. 战争、推图、区域控制类游戏的教程体系，必须单独覆盖真实战斗；若城战/围城/占领显著不同，也必须单独覆盖。
20. 章节只是控制教程长度和刷新风险的手段，不是固定交付模板；如果一条短教程已经完整覆盖当前规则面，不必强拆。
21. 同一基础回合链里的资源使用、目标选择、主行动推进与结果反馈，默认合并在“基础回合”主章节里教学；不要按程序模块名机械拆章。
22. 章节划分按玩家心智任务命名，不按 UI 面板、代码模块或内部系统命名；先回答“这一章学会哪段玩法”，再决定是否拆章。
23. 本 skill 只保留可复用教程方法，不承载单游戏机制名、专有地名、固定起手路线或固定章节答案；这类内容必须下沉到对应游戏的专项文档、覆盖矩阵或教程实现。
24. 本 skill 不提供固定章节数、固定章节主题或固定章节顺序模板；“基础回合 / 战斗 / 结算 / 特例”这类骨架只有在当前游戏规则面确实需要时才成立，不得把某一款游戏当前这套拆章直接抬成全仓默认。
25. 写进项目通用 skill 的教程规则，默认必须先过“放到第 100 个游戏里还成立吗”自检；如果离开当前游戏就不成立，说明它不属于通用层，必须下沉到 `docs/games/<gameId>/**` 或该游戏专项 skill。
26. 若某一章被命名为“完整回合 / 基础回合 / 首回合 / 一个完整行动轮”或语义等价，则该章必须覆盖这条主循环从正式主入口开始到本轮主要公共推进节点结束的完整链路；不得把同一条基础回合链中的后半段公共机制另拆成下一章再重教。
27. 同一核心机制只允许有一个主教学落点。后续章节只能补第一主章节没有覆盖到的分支、例外、进阶结果或特殊结算，不得把同一基础机制作为新的平级章节再教一遍。
28. 当发现“第二章只是把第一章后半截单独重讲一次”时，默认结论不是继续优化文案，而是章节边界错了；应先合并章节，再决定哪些步骤需要保留。
29. 教程文案如果点名某个当前状态，例如剩余移动、剩余行动、当前资源、当前目标、当前可支付量或当前控制权，就不能空讲；该状态要么被当前高亮直接覆盖，要么在当前画面里有清楚稳定的真实承载并被明确指到，否则就要拆成单独步骤，或先补正式 UI 表达。
30. 如果教程文案要解释的状态在正式 UI 中没有清楚落点，这首先是实现缺口，不是“文案再解释一下”能解决的问题；默认先补真实表达，再继续教程。
31. 只要用户目标已经升级为“新游戏教程收工 / 新游戏基本流程端到端 / 教程证明这个游戏怎么运作”，就不得只凭教程链本身收口；必须额外核对正式进行页是否已经具备该教程所声称的一级入口、主交互承接物和结果反馈。若教程只能靠注入态或隐藏技术入口示范，而正式局并无对应规则级入口，结论必须降级为“教程示范已补，正式流程仍缺口”，不得报成新游戏完成。
32. 当教程章节涉及 `打牌 / 弃牌行动 / 升级 / 事件 / 轮盘 / 结束 / 公开区拿牌 / 棋盘直点对象` 这类一级入口时，教程覆盖矩阵除了写“本章教了什么”，还必须单列“正式局是否已具备同口径入口”。只要有任何一项仍是教程注入态专供、抽象按钮替代、低保真预览替代或隐藏续章专用承接，就不得把这一章写成“正式主流程已经教完”。
33. “端到端教程”必须跑到玩家能看到核心结果反馈：计分、胜负、收益、结算、摊牌或等价反馈。只跑到第一个动作、第一轮、第一张图或某个中间提示，不得称为端到端。
34. 若用户要求过程态截图或满元素截图，教程 E2E 必须覆盖“历史选择/标记已存在 + 当前新选择/标记 + 中央主对象/公共资源 + 下一步主按钮”同屏状态；只给开场、空桌或最终结算图不算满足。
35. 教程收口必须区分三种状态：`教程局部已通过`、`桌面教程端到端已通过`、`新游戏整体完成`。前两者不能自动升级成第三种；若服务器素材主源发布、素材录入、正式桌面 UI、手机验收或用户验收仍未关闭，整体仍是 `in_progress`。

## 通用层落点门禁

在修改教程通用 skill、`docs/ai-rules/tutorial-design.md`、项目通用 overlay 或教程流程规范前，先做这 4 个判断：

1. 这条规则放到第 100 个游戏里还成立吗。
2. 这条规则约束的是“怎么判断教程是否合格”，还是只是在描述“当前游戏这次最好怎么拆”。
3. 这条规则是否偷带了当前游戏的专属机制、专属章节名、专属起手路线、专属 UI 壳层或专属地图结构。
4. 如果另一个游戏根本没有这套回合结构/资源结构/战斗结构，这条规则是否仍然可执行。

只要其中任一题答案是否定，这条内容就不得进入通用层，必须下沉到：

- `docs/games/<gameId>/**`
- 当前游戏教程覆盖矩阵
- 当前游戏 `tutorial.ts`
- 当前游戏专项 skill / workflow

尤其注意：

- 不得把“当前这款游戏最合理的章节拆法”写成整个项目的默认章节模板。
- 不得把“当前这款游戏这一步应该先教什么”写成所有游戏的固定顺序。
- 不得因为某个游戏这次需要“合并章节”或“拆出独立章节”，就把这次裁剪结果直接提升成通用答案。
- 不得因为本轮正在改一个游戏，就把它的局部最优解误写成通用教程原则。
- 若用户要求“先更新 skill / 先更新规范”，默认优先补“判断方法”和“分层门禁”，而不是把当前游戏这次的拆章答案直接抬进通用层。

## 固定流程

### 1. 先锁教程真相

- 先判本轮新增规则属于哪一层：
  - 这一步默认在教程正文设计前就做，不要等到写完一版章节稿后才回头判断能不能进通用层。
  - 若放到第 100 个游戏里仍成立，才允许写进通用 skill / 通用规范。
  - 若依赖当前游戏的专属机制、专属章节结构、专属起手路线或专属 UI，必须直接下沉到当前游戏专项实现或专项文档。
  - 若当前争议其实是“这章该不该并进上一章”“这个标题配不配叫完整回合”，先判断这是通用章节原则，还是当前游戏的专项拆章答案；只有前者才能回写通用层。
  - 默认先把判层结果写成 3 行：`跨游戏判断方法 / 当前游戏专项答案 / 专项答案下沉位置`；没有这 3 行时，不得进入章节设计。
  - 如果用户当前先要的是 skill/规范收口，这 3 行就是本轮正文的第一交付；在它们写出来之前，不得提前补教程章节名、固定顺序、固定起手路线或固定案例编排。
- 读取当前：
  - `src/games/<gameId>/rule/*.md` 与该游戏当前规则真相源
  - `src/games/<gameId>/tutorial.ts`
  - 对应语言包
  - 对应教程测试
  - 对应教程 E2E
- 明确当前教程到底在教哪条真实流程：
  - 常规局还是变体
  - 是不是从首次教学所需的第一个正式决策入口开始
  - 点按钮还是点卡牌
  - 有没有真实案例
  - 有没有结果反馈
- 先列“一级交互审查表”，至少写清：
  - 规则书规定的回合骨架
  - 规则书同层一级行动的完整全集，而不是当前案例抽样
  - 当前正式 UI 可直接进入的一级行动
  - 哪些动作是选了一级行动后才需要选目标/地区/支付
  - 哪些动作确实必须先选目标/地区才成立
  - 哪些 UI 只是提示，不承接点击
  - 哪些对象只是默认预选/默认高亮，不等于玩家已经做出选择
  - 当前阶段的真实直点入口有没有即时高亮，还是被错误地藏在横幅/侧栏描述后面
  - 当前教程是否把一级动作入口和后续目标入口教反
- 如果当前范围包含“基础回合 / 完整回合 / 首回合 / 端到端看出怎么运作”，再补“首回合动作顺序表”，至少写清：
  - 规则书从正式主入口开始的动作顺序
  - 当前正式局每一步先暴露给玩家的真实对象
  - 哪些是一级动作入口
  - 哪些只是后续目标/支付/确认
  - 默认预选在每一步属于弱聚焦还是已确认
- 如果用户明确要求“所有交互都要审查”“整个基础流程都要过一遍”，再补“主要交互清单表”，至少写清：
  - 开局公共推进
  - 一级行动入口
  - 支付/弃牌
  - 二级目标或来源选择
  - 地图目标选择
  - 待结算战斗
  - 战后/围城/占领
  - 年度或阶段结算
- 这张表必须同时标出：
  - 玩家第一眼看到的入口
  - 真正承接点击的现实对象
  - 哪些只是提示 UI
  - 这一类当前是“正式局真实可用 / 低保真替代 / 教程注入专供 / 尚未实现”中的哪一种
  - 若承接物本身仍是低保真预览、错 atlas、混入别类对象或没有规则级身份，必须单列写出，不得并入“正式局真实可用”
  - 当前问题究竟落在教程、正式 UI、还是两者都有
- 教程收口前必须补“玩家可用元素覆盖矩阵”，至少写清：
  - 元素名称
  - 现实职责
  - 所在正式 UI
  - 是否高频 / 非直觉
  - 教程、帮助或 tooltip 落点
  - 端到端截图证据
  - 未覆盖原因或当前缺口
- 玩家可用元素覆盖矩阵必须至少过账：常驻 HUD、阶段/回合状态、资源/属性/生命/进度轨、牌堆/弃牌堆/持有区、主要动作入口、目标选择、确认/取消、只读规则入口、观察/聚焦/视角切换、随机/结算承接、结果反馈。
- 如果当前争议已经落到“第一步到底该点哪里 / 哪个按钮只是提示 / 为什么默认高亮被误读成已选”，再补“当前屏幕可见可点对象盘点”，至少写清：
  - 这一屏玩家第一眼能看到哪些可见可点对象
  - 每个对象属于 `一级动作入口 / 二级目标 / 支付对象 / 确认控件 / 提示UI / 非当前步骤对象` 哪一类
  - 当前默认高亮是不是只属弱聚焦
  - 玩家此刻真正该点的是谁
- 如果首回合或基础回合里同时存在“强制公共推进”和“当前玩家真实可选动作”，还必须额外标出：哪一格只是流程经过点，哪一格才是当前玩家第一次真正开始作判断的地方。没有这个裁决，不得把后面的目标区、支付对象或默认聚焦对象写成“第一步”。
- 若规则真相与正式 UI 不一致，先把它标成“正式流程实现问题”或“交互合同未锁定”；不得只改教程把矛盾粉饰过去。
- 若你手上同时有 `implementation-map / 章节草案 / 覆盖矩阵 / 教程脚本稿` 和当前实现，前者只能当候选方案输入；凡是“当前已经实现到什么程度”“正式局现在有没有这个入口”的判断，一律回到当前 `tutorial.ts`、`Board.tsx`、当前 worktree 的测试与截图。
- 若发现 `覆盖矩阵 / implementation-map / 章节草案` 已经和当前 `tutorial.ts`、目录显隐、`nextTutorialId` 链或当前截图链对不上，默认先停止引用它们的现状结论，回写成“当前真相”后再继续；不得一边知道它过时，一边继续拿里面的旧章节数、旧显隐关系或旧缺口判断推进实现。
- 如果准备压教程结构、移除旧章节或把隐藏续章并回主章节，必须同时输出“覆盖差异表”：
  - 旧覆盖点
  - 新落点
  - 当前是否仍有真实正式入口与截图证据
  - 若没有，必须显式降级成缺口，不能静默删除
- 若本轮先做的是“表格审查 / 规范补丁 / skill 门禁 / 文案问题清单”，后续默认动作不是汇报结束，而是继续把表里命中的正式局缺口逐条回到实现与验证：
  - 上屏文案误导动作顺序：回到正式进行页源码改短语
  - 默认聚焦冒充已确认：回到真实视觉与状态承接改语义
  - 横幅被写成交互：回到教程/提示文案和真实承接物修正
  - 一级入口缺口：回到正式局入口核对表与当前实现状态继续处理
  - 同层一级动作仍缺规则书原入口：继续回到正式手牌/地图/轮盘等真实承接物，不得再用教程注入态、隐藏续章或抽象按钮顶交
  - 若真实承接物本身仍是低保真预览、错 atlas、混入别类对象或没有规则级身份：先转去补素材合同、atlas 裁切合同或规则级对象真相表，不得继续在这层硬补教程
- 没完成这一步，不得收口

### 2. 先写完整教程文案

- 先给出教程覆盖矩阵，再给分章节或单教程结构；不要直接跳到某一章的句子级微调。
- 先输出完整步骤文案，不要只给 2 句样例。
- 若用户正在强审文案，默认先停在文案稿，不直接实施；只有用户明确认可当前文案方向后，才进入实现。
- 文案自检时至少过这 12 问：
  1. 玩家第一句能不能立刻知道怎么赢
  2. 有没有只教常规对局
  3. 有没有从首次教学所需的第一个正式决策入口进入，而不是直接切到中段题面
  4. 有没有重复前面已经说过的规则
  5. 有没有空提示句或作者腔废话
  6. 有没有一个玩家可感知的最小乐趣闭环，而不是规则清单
  7. 如果游戏卖点是组合、混搭或连锁，有没有一次首个可感知组合
  8. 有没有覆盖首次上手高频但不明显的桌面读局操作
  9. 桌面读局操作是不是贴在真实需要它的局面里，而不是单独做界面导览
  10. 有没有一次真实案例和一次真实计分因果
  11. 结语有没有保持简短
  12. 有没有讲到这款游戏真正靠什么资源运作
  13. 有没有覆盖这款游戏首次上手就会碰到的核心结算概念
  14. 有没有把示范题前提误说成通用规则

### 2.1 先列覆盖矩阵

- 至少列出三列：
  - 规则条目
  - 教程章节 / 步骤
  - 证据截图
- 如果当前教程会因为刷新丢进度，默认先设计为多短章：
  - 第 1 章：首次教学所需的第一个正式决策入口与一个完整基础回合
- 中间章节：战斗 / 资源 / 特殊结算
- 后续章节：阶段结算 / 另一类主行动 / 终局前关键结算 / 终局等重规则
- 上面只是通用骨架，不是固定章节模板；如果某个游戏没有这些系统，或核心规则面完全不同，必须按该游戏自己的规则组织重写。
- 若角色选择、剧本选择、确认开始这类入口只承担低信息量前置，而不承担规则理解或关键判断，默认不要把它们拆成独立教学章节；可以保留为真实进入链路，但应尽快进入真正要教的主循环或主决策。
- 如果第 1 章已经被定义为“完整基础回合”，则该章默认必须把同一回合链里的资源使用、主行动、支付、结果反馈和公共推进节点一起讲完；不要再把这一链中的公共推进机制拆成单独平级章节。
- 只有覆盖矩阵能证明“核心规则都有人教”，才进入具体文案。

### 3. 文案锁定后再改实现

- 同步更新：
  - `tutorial.ts`
  - `public/locales/**/game-<gameId>.json`
  - 教程单测
  - 教程 E2E
- 如果教程口径改成常规对局，注入态也必须切回常规对局语义，不能只改文案。
- 教程默认应是“正常对局运行时 + 教程浮层”。本地教程必须复用正常本地开局的人数、座位控制器、AI 默认配置和玩家视角规则；不得用热座切玩家、测试专用命令或教程专用脚手架替代正常 AI / 正常按钮来证明流程跑通。若某一步必须使用教程脚手架，必须在覆盖矩阵里标明差异和原因。
- 若步骤目标是单张牌，同步检查：
  - `highlightTarget` 是否命中单牌锚点
  - 完成操作后旧目标牌的选中态是否被清掉
  - 下一步是否只保留当前步骤真正需要的目标高亮

### 4. 跑真实教程验证

- 至少跑：
  - 教程单测
  - 教程 E2E
- E2E 截图必须覆盖：
  - 开场目标/基础回合
  - 开局后的第一个主要交互入口
  - 第一条正式行动
  - 至少一个真实案例
  - 教程覆盖矩阵里的关键非直觉 UI：带计数确认、聚焦/回到自己位置、观察视角、只读规则入口、状态/进度读法等命中的项目
  - 计分或等价结果反馈
  - 结语/结束态
- 如果某个非直觉 UI 只在特定阶段出现，E2E 必须先触发该阶段或构造等价代表态，再截图证明玩家能看到、能理解、能返回；只在文案里解释或只断言 DOM 存在不算覆盖。
- 若教程提到只读参考入口，例如剧本页、规则卡、帮助页、目标页或状态页，E2E 必须真实打开该入口、断言关键内容/素材加载、保存打开后的截图，再关闭回到牌桌；只截图打开前按钮或只在文案里说“打开看看”不算覆盖。
- 若教程提到攻击、敌方行动、怪物行动、驱魔、战斗、投骰或类似结算动作，E2E 必须真实点击正式入口并保存至少两张图：动作前可见入口、结算后结果主体。若动作会投骰，还要保存骰盘或结果面板，能看出骰子、总点数/加成和结果。
- 若截图文件名或教程文案写的是“剧本目标页 / 胜利条件 / 任务目标”，E2E 必须断言目标页里的标题、双方目标和关键敌方实体；断言玩家参考卡素材加载不算命中。
- 若某个战斗、检定或改骰流程已有批准过的主骰盘 UI，同类新教程截图必须断言同一容器或同一数据属性；测试只找 `recent roll` 这种通用结果面板不够，必须证明玩家看到的是同一主流程骰盘。
- 若首剧本里存在怪物或非玩家敌方实体，教程验收至少要有一条截图链证明它的目标、可行动入口和攻击/结算结果；若本轮不做，覆盖矩阵必须明确写 `待补端到端证据`，不得写“已介绍”。
- 若教程含“指定这张牌”的步骤，E2E 还必须验证：
  - 当前目标牌确实是单牌级高亮
  - 步骤推进后旧目标牌不再残留描边/选中态
- 若本轮验收依赖“看图判定 UI 是否达标”，必须实际打开当前 worktree 下的关键截图逐张核图；不得拿历史截图、旁支 worktree 截图或只报路径代替肉眼审查。
- 若教程端到端包含投骰、改骰、重掷或使用道具改结果，截图链必须逐步覆盖：投掷结果出现、可介入对象可见且高亮、选择要改/重掷的骰子、改/重掷后结果。每一步都要按玩家视角核对主对象是否在主视线、骰面是否能直接算出合计、合法对象描边是否单层对称；测试通过但截图里骰面误读、对象遮挡、描边叠层或按钮抢焦点时，不得收口。
- 若教程文案写了“先 A 再 B”这类连续操作，截图验收必须至少覆盖 A 未选中前、A 已选中且 B 可用、B 执行后三个阶段；只拍 A 前和 B 后不能证明玩家知道中间该怎么继续。若 E2E 实际操作了教程没有显式文案说明的可选流程，例如使用道具改骰、选中目标后确认、先选资源再选目标，必须补玩家可见文案和对应过程截图，否则不得算教程验收完成。
- 若选中对象本身带旋转或透视投影，例如物理骰、斜放卡牌、Token 或房间牌，选中框必须跟随对象几何；能拿到旋转信息时不得画固定正矩形。截图里如果对象是斜的但高亮框是正的，只能判为选中态未达标。
- 若教程步骤让玩家选择一个画面里已经可见的对象，例如卡牌、骰子、Token、房间、地图格、单位或目标区域，主流程必须直接选中该对象本体或其投影命中区；数字按钮、编号列表、文字选项和重复说明按钮只能作为备用/无障碍入口。教程截图必须让人看出玩家是在选真实对象，而不是在选旁边的代理数字或文字。
- 若教程让玩家选择某颗骰子进行改值、锁定、重掷或应用道具效果，且真实骰子本体、物理骰投影或等价骰子元素当前可见并可稳定命中，教程主流程和 E2E 必须直接点击该骰子元素；数字按钮、文字列表或“第 N 颗骰子”只能作为备用/无障碍入口，不能替代主流程截图。截图链必须能看出玩家是在点骰子本体或其投影命中区，而不是点旁边的编号按钮。
- 若用户明确说“图呢 / 打开图 / 用 PureRef 看 / 我看看”，必须先区分这是不是已经通过验证的最终验收图。只有最终验收图或用户明确要求查看的指定图，才用 PureRef 给用户打开；失败图、候选图、中间截图、AI 自己核验图不得自动打开到 PureRef。
- AI 自己核图必须走轻量预览、低分辨率拼图、OCR 或局部裁图，并在汇报里明确称为“AI 核图”；给用户看图才是“打开到 PureRef/图片查看器”。两者不能混成一个动作。
- 多张最终验收图需要用 PureRef 时，必须一次性传入全部图片路径并复查 PureRef 进程；不得循环一张图启动一次 PureRef。

### 5. 收口规范与 skill

- 如果本轮暴露的是可复用教程问题，而不是某个单游戏私货，回写：
  - `docs/ai-rules/tutorial-design.md`
  - 本 skill
- 如果只是当前游戏局部特例，则写进项目内对应教程实现或专项文档，不要抬升成全局规则。

## 最终回复门禁

1. 不得只说“教程跑通了”。
2. 必须说清这轮教的是哪条真实流程。
3. 若提到 E2E 通过，必须附真实截图绝对路径。
4. 若用户明确要看图、要打开图或本轮是否达标只能靠截图判断，必须主动打开当前关键截图并在回复里写出实际核图结论；只给路径不算交付。
5. 新游戏或现有游戏补完教程时，必须明确教程当前属于 `局部已通过 / 桌面教程端到端已通过 / 新游戏整体完成` 哪一类；没有玩家可用元素覆盖矩阵、真实教程 E2E、关键截图核图和未覆盖项说明时，不得报“新游戏整体完成”。
