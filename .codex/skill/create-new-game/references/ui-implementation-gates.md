# 新游戏 UI 实现与截图链门禁

> 来源：从 `SKILL.md` 无损拆出。本文档承载 UI 端到端完成门禁、设计稿顺序、Board/UI 模块、交互映射和基础玩法截图链模板。

## 阶段 5：Board/UI 与交互闭环

**目标**：提供最小可玩 UI，完成交互闭环。

### 5.0A 新 UI 端到端完成门禁（强制）

- 只要本阶段新增或重做了游戏主 UI、主 Board、关键面板、核心交互布局，就必须把“完成”定义为**真实页面端到端通过**，而不是“组件存在 / 局部截图可看 / 测试通过”。
- **端到端不能替代前置缺口闭合（强制）**：如果 Board/UI 实现前或 E2E 过程中发现缺规则对象、缺素材、缺正式运行时资源、缺主交互承载、缺实现任务或 OpenSpec 范围不足，必须先停止“完成”口径，回到 proposal/tasks/spec、规则对象素材矩阵和实现清单补齐缺口；不得继续缩小路径、删断言、跳过对象或用相似元素制造端到端通过。
- **禁止用 HTML/CSS/程序化 UI 冒充规则素材（强制）**：规则、物理配件、官方素材或用户素材目录已经指向的牌面、牌背、token、棋子、筹码、桌面、牌槽、帮助卡、地图格、角色/怪物/状态标记等对象，必须优先接入真实素材并完成语义命名、正式落盘、压缩/manifest 和运行时引用。只有规则对象素材矩阵明确裁定“不需要图片”，或用户明确批准程序化替代时，才允许用纯 HTML/CSS、文字或程序化图形承载；否则必须标为 `blocked`，不得继续实施或收口。
- **布局真相源优先（强制）**：当用户给了 DOM/HTML、TTS Workshop JSON、XmlUI、对象 `Transform`、截图、PureRef 图板或桌面存档时，主 UI 实现前必须先抽取布局合同，至少包含桌面/牌槽/牌库/弃牌区/玩家区/token 区/帮助区的相对位置、层级和承载关系。不得因为单个 DOM 文件为空，就忽略其它非空布局真相源；也不得用项目通用布局替代已有桌面结构。
- **点名参考缺失必须阻塞（强制）**：当用户明确要求使用 DOM、BGG 电子版、截图、PureRef 图板、规则书或某个素材文件时，该来源就是本轮 UI 真相源之一。未找到、为空、读取失败或无法覆盖目标时，必须停止 UI 完成判断并汇报缺口；不得用 TTS、通用布局、历史截图或程序化页面顶替。
- **素材/布局来源不等于视觉风格（强制）**：TTS/Workshop/BGG/DOM/HTML 可以提供素材、对象位置、信息层级和交互关系，但不能直接决定视觉风格。新游戏主 UI 的风格必须按 `docs/ai-rules/ui-ux.md`、`design-system/styles/` 和游戏主题另行裁定；禁止因为用了 TTS 素材、TTS 坐标或 Workshop 存档，就把网页 UI 设计成 TTS 桌面风格。
- **每个游戏必须有自己的视觉风格合同（强制）**：新增或重做游戏主 UI 时，必须先形成该游戏独立的 `design-system/games/<gameId>.md` 风格合同，并在实现前写清“本游戏为什么长这样”：题材气质、主视觉素材、布局语法、色彩/字体/材质、按钮家族、HUD 语气、动效语法、与其它已接入游戏的差异。禁止把通用 Tailwind 卡片、其它游戏的壳层、TTS/BGG/DOM 原始样式，或“先能跑起来”的框体堆叠直接当作该游戏风格。
- **风格合同必须可被截图裁判（强制）**：`design-system/games/<gameId>.md` 不能只写抽象形容词，必须写出首屏第一视觉、主对象优先级、允许保留的容器层数、禁止出现的通用壳层、桌面端验收截图、移动端降级边界。AI 复看真实截图时，若第一眼看到的是多层框体、说明面板或其它游戏同款壳层，而不是该游戏的核心对象和主题语法，必须判为 `in_progress`。
- **BGG/DOM/运行时截图必须拆成结构合同与视觉裁定（强制）**：BGG 电子版、DOM、结算界面、运行时截图只能直接决定区块关系、对象承载、交互顺序和状态节点；视觉上哪些继承、哪些重绘、哪些只作参考，必须在风格合同里逐项裁定。禁止“看了 DOM/BGG 但实现完全不像结构”，也禁止“照搬 BGG/TTS 原始样式后说这是项目 UI 风格”。
- **同仓游戏只能作参照，不能复制成同款（强制）**：查看其它游戏时，只允许复用经过验证的交互锚点、可达性原则和系统组件；视觉方向必须重新裁定。若截图里看不出这款游戏与其它游戏的主题差异、素材语法差异和桌面气质差异，默认判为风格合同未过，不得进入“UI 完成”口径。
- **桌面源样式基线先过，移动端后适配（强制）**：当任务同时涉及桌面端和移动端，默认先完成桌面端真实页面：主视觉、布局合同、核心交互、结算/终局态、截图与 AI 复看全部通过后，才能进入移动端适配。除非用户当轮明确说“先做手机”或“桌面暂不验收”，不得因为手机横屏拥挤就提前改动桌面主视觉、整体比例或交互家族。
- **移动适配不得反向污染桌面视觉（强制）**：手机横屏、小屏或容器高度不足时，只能在已通过的桌面风格合同上做响应式降级，例如整体缩放、局部折叠、减少非关键辅助区、触控尺寸调整、HUD 让位；不得用新增多层框体、重复面板、说明卡、外壳嵌套、过度圆角/边框或压缩卡牌来“把东西塞进屏幕”。如果小屏需要改变承载关系，必须先更新移动端设计合同并重新截图验收，不能把它伪装成桌面 UI 已完成。
- **桌面到手机的验收顺序不可倒置（强制）**：默认验收链为 `桌面真实页面 -> 桌面首轮截图 -> 桌面结算/终局截图 -> AI 复看通过 -> 手机横屏/竖屏适配 -> 手机截图 AI 复看`。手机截图未重叠只能证明移动适配阶段局部通过；桌面未过时，手机不得作为完成证据。手机修复也不得改坏桌面已通过的构图、对象比例和风格合同。
- **框体数量必须有来源和职责（强制）**：牌桌、公共区、玩家区、手牌区、结算区只允许保留能对应真实桌面结构、交互边界或可读性需求的容器。每新增一层边框/背景/卡片壳，都必须能回答“现实对应物是什么、保护了哪个交互、是否抢走卡牌/筹码/棋盘焦点”。不能回答时默认删除或弱化；禁止用一圈圈卡片壳替代真正的游戏风格。
- **UI 完成不得只看可玩**：真实页面 E2E 只能证明流程可操作；如果布局合同尚未抽取或当前 Board 未按合同核对，结论只能是“流程可跑，布局仍未验收”，不能说主 UI 复刻完成。
- **不得重复实现全局日志/撤回入口（强制）**：新游戏 Board 只接入通用行为日志和撤回系统，不把悬浮球已经承载的操作日志、最近记录、撤回按钮再做一遍。若需要证明动作可追溯，应验证 `GameHUD` / FAB 里的日志入口和撤回入口可用；不得用主牌桌上的第二日志面板作为完成标准。
- 若该阶段同时包含桌面端与移动端工作，默认顺序固定为：**先让桌面端真实页面通过，再进入移动端适配**。除非用户当轮明确要求并行推进，或明确说先做移动端，否则不得把“移动端适配”升级成下一主阶段。
- **桌面失败时禁止转场到手机完成（强制）**：只要桌面真实页面还存在崩溃、页面保护、遮挡主结果、视觉风格错误、布局合同不符、核心交互不可读等阻塞问题，当前 UI 状态仍然是“桌面未完成”。此时可以记录手机风险，但不得把主工作切到手机适配、不得用手机截图当完成证据、不得把“手机也能打开”写成阶段推进。
- **在线房间的前置选择默认必须在对局内完成（强制）**：
  - 只要游戏存在 `scenario / faction / character / armament / loadout` 这类会影响具体席位、阵营、可见信息或后续前置流程的选择，且该游戏支持联机房间，就默认做成**进入 match 后的局内 setup 层**。
  - 其中 `scenario` 若还承担**剧本介绍、候选对比、全员投票、房主裁定同票**中的任一职责，则剧本本体也默认属于局内 setup，不得继续在建房页直接预设最终剧本结果。
  - 局内 setup 必须是独立页面或独立壳层，不得把投票、选阵营、人物/军备/loadout 选择压在正式棋盘 HUD 上；setup 未完成前，主行动控件、手牌、牌库、弃牌、动作栏等正式对局主 HUD 不应同时渲染。
  - 建房页只允许承载房间级公共参数，例如人数、密码、是否有 AI，或“是否启用局内剧本投票”这类房间模式开关；不得把某个席位/阵营的私有前置决定，或本应在局内阅读介绍后再决定的剧本结果，偷偷写死在建房页默认值里。
  - 若某些前置项确实要在建房页完成，必须证明它们不是 seat-private 信息，不依赖局内介绍/投票，且不会让后续联机页面缺少真实操作入口；否则视为流程不完整。
- **联机游戏先锁 seat/viewer 语义，再做主 Board（强制）**：
  - 只要目标包含在线房间、多人或 spectator，主 Board 开发前必须先裁定每个页面到底代表哪个 seat / viewer，以及哪些信息属于该 viewer 的私有视图。
  - 默认要有 `playerView`、私有 overlay 或等价过滤层，确保手牌、prompt、局内 setup、waiting 态都按 viewer 隔离；不得先按本地同屏心智把所有页面做成“谁回合到谁就切过去看谁”。
  - 若当前 viewer 对应的 seat / faction 解析失败，默认动作是留空、等待或报错提示；不得回退成“当前行动势力的私有视图”，更不得因为 `currentPlayer` 变化把页面自动切成别人的手牌和私有候选。
  - 联机验收必须至少有一条**多浏览器上下文** E2E，证明不同 seat 页面看到的是不同私有内容；hotseat/local 只能当辅证，不能冒充联机验收。
- **一级行动与二级步骤必须分层呈现（强制）**：
  - 当流程存在“先选主行动，再选目标/成本/确认”的两段式结构时，UI 必须先明确锁定当前一级行动，再暴露二级步骤。
  - 未进入当前一级行动前，不得让地图、手牌、主行动控件、确认按钮、次级候选同时都像并列主入口那样可点；否则用户无法判断现在到底该先做什么。
  - 若对象本体承担二级点击，仍必须给出贴近对象的短提示或当前行动状态，让用户能从截图中直接看出下一步落点。
- 若真实路由或真实牌桌里仍存在以下任一项，本阶段不得收口为完成：
  - 信息层级错误，主次关系与设计/规则不符
  - 空态、终局态、等待态等关键状态误导用户
  - 文案溢出、标题挤压、卡面/面板比例失真、首屏结构被空白或次级区错误撑大
  - 固定牌桌/棋盘类 PC live 需要滚动页面才能看到完整游戏、手牌或主操作
  - 为了“提质感”给牌桌、公共区、手牌区、HUD 叠出多层无依据边框，导致主交互对象被一圈框体抢焦点
  - 关键操作虽存在，但在真实页面路径中阅读顺序、可达性或可理解性仍失败
- 组件测试、领域测试、局部截图都只能证明“部分约束成立”；**只要真实页面还有已知 UI bug，就不能说新游戏 UI 已实施完毕**。
- 只要桌面端真实页面仍有阻塞级 UI bug，就不能把“已经开始做移动端适配”描述成自然的下一步完成阶段；此时正确状态仍然是“桌面端未完成”。
- **已知截图问题不得被 E2E 绿灯覆盖（强制）**：如果 AI 复看或用户指出截图中存在主区重叠、主对象被遮挡、框体过多、布局不像参考结构、素材未出现、按钮/帮助区抢焦点等问题，即使 E2E 和单测通过，UI 状态仍是 `in_progress`。必须先修真实页面并重新生成截图、打开给用户看、AI 复看通过，才能恢复完成判断。
- **流程跑通的截图定义（强制）**：
  - `主流程已跑通` 默认是指从本轮承诺的**开始点**走到本轮承诺的**结束点**；必须先把两端写死，不能只说“跑过一遍”。
  - 若起点是首页真实入口，就必须真从首页真实入口起跑；若起点只是已进入 `match` 的 opening 代表态，就必须直说“当前只证明对局内从 opening 到 X”。
  - 只要对外说“新游戏主流程已跑通”，必须按核心决策位给出 `触发前 -> 触发后` 截图对，而不是只给终点图。
  - 至少覆盖：入口前/入口后、首个核心决策前/后、至少一个中段关键决策前/后、终局前/终局后；若本轮范围未到终局，必须明确写“当前只证明到哪一步”。
  - 每张 `触发前` 图都必须让人直接看出下一步主操作落在哪里；如果截图看起来像“没有可点对象 / 不知道做什么 / 像页面卡死”，即使规则状态合法，也不得收口。
  - 每张关键图都必须由 AI 自己实际打开并给出肉眼 verdict；禁止只靠断言通过、文件已生成或截图路径存在就宣称流程已证明。
  - 资源、筹码、卡牌、棋子等实体发生“拿走 / 消耗 / 移动 / 支付”时，截图链和 E2E 必须同时证明源区域不再保留原实体、目标区域出现实体或明确占位。禁止只看内部状态数量、日志或目标区数量就宣称真实交互已完成。
- **新游戏基础玩法截图链（强制）**：
  - 只要对外声称“这是一个新游戏最基本的端到端”或“别人能看懂这个游戏怎么运作”，就必须额外补一条**基础玩法截图链**，目标受众默认是第一次看这款游戏的人。
  - 这条链必须回答五件事：`从哪里开始`、`现在轮到谁做什么`、`关键对象点哪里`、`点完发生什么`、`然后怎么进入下一步`；缺任一项，都不能说“基础流程已讲清楚”。
  - 开始点与结束点必须先写死。默认优先从“进入对局后第一次真正可操作的状态”起跑；结束点至少要到“完成一次核心动作并进入可继续的下一阶段”。如果本轮暂时无法到终局，必须明确写“当前基础玩法链只证明到 X”，不得偷换成“整局都讲清楚了”。
  - 每一步都必须有真实截图，且步骤顺序必须可以回放。每步最低要同时给出：`步骤号`、`截图绝对路径`、`这一步玩家要做什么`、`下一步点击哪里`、`点击后会看到什么结果`。
  - **中局满元素截图必须覆盖资源累积与新选择（强制）**：截图链不得只给空首轮、单一对象或终局结果。凡是核心玩法会累积筹码、token、手牌、场上牌、基地分数、骰子结果、资源池或类似状态，至少要有一张中局过程态整屏图，能同时看见：`历史资源/筹码已经被所有相关玩家拿过或结算过`、`当前正在选择或获取新的资源/筹码`、`中央/主区域同时存在关键牌/棋子/筹码等满元素`、`下一步主动作可见`。如果截图看不出“已经拿过旧资源，现在正在拿新资源”，不得用它证明核心流程或视觉布局已达标。
  - `下一步点击哪里` 必须先用玩家听得懂的现实对象名表达，例如“点击手牌区这张牌”“点击地图上发亮的地区”“点击右侧确认按钮”“点击中央弹窗里的继续”；禁止只写 `locator`、`data-testid`、内部字段名或“触发下一步交互”。
  - 如果整张真实截图里点击落点已经一眼可见，可以直接在步骤说明里指出；如果整图里落点不够明显，允许补一张**从同一真实截图派生的局部辅助图**标出点击区域，但必须明确注明“这是同一张真实截图的局部指引，不是替代证据”。
  - 基础玩法链默认至少覆盖以下节点：`进入可操作状态`、`第一次主动作选择`、`第一次目标/对象选择或资源支付`、`第一次结果落地`、`进入下一步或交接到下一位/下一阶段`。缺任一类节点，不得宣称“已经能看懂这游戏怎么运作”。
  - 如果游戏的核心体验依赖特殊节点，例如 `战斗掷骰`、`基地计分`、`角色技能结算`、`区域移动`、`多人响应窗口`，基础玩法链还必须至少展示其中一个；否则这条链最多只能证明“界面能点”，不能证明“玩法怎么运作”。
  - **禁止把描述性正文写成截图链的一部分**：逐步说明文档可以告诉读者“这一步要点哪里”，但玩家界面本身不得为了配合截图链，新增 `这一步做什么`、`现在执行`、`下一步点击哪里` 这种常驻说明正文。若某张图必须靠这种正文才能解释流程，优先判定为 UI 本身不合格，而不是去补更多说明文案。
  - **主提示落点必须先服从正式 UI 槽位**：基础玩法链里若存在“当前唯一下一步”，正式玩家提示默认应复用棋盘上方横幅、中央 CTA、对象本体高亮或其他已批准主槽位；不得把“为了让截图更好讲”当理由，把主步骤提示常驻塞进右侧说明区。
  - **联机基础流程必须固定同一 viewer/seat**：若目标口径是“固定玩家视角看懂这游戏怎么运作”，整条基础玩法链只能来自同一 viewer 页面。不得因为测试态或本地教程态能自动切势力，就把 `玩家 A -> 玩家 B -> 玩家 C` 串成单玩家连续流程；那种链路只能标成“本地教程 / 多势力演示”，不能冒充联机玩家流程。
- **新游戏用户友好底线（强制）**：
  - 开局态、空态、等待态、owner prompt 出现前的过渡态，都不得做成“需要靠规则知识猜下一步”的死板空画面。
  - 当只剩单一合法主动作时，必须给出显式入口或贴近入口的短提示；当处于等待态时，必须写清当前在等谁。
  - 这条底线默认先于“画面简洁”；只要简洁导致用户误判成卡死，就算失败。
- **独特高风险交互必须有独立 E2E（强制）**：
  - 只有“同一类交互只是换内容”时，才允许复用现有 E2E。
  - 若本轮新增的是新的联机 setup、seat-private 选择、独特响应窗口、独特支付/弃牌模式、独特棋盘直选模式，就必须单独补一条针对该流程的真实 E2E，不得拿相邻流程的通过结果代替。
- **交互模式来源门禁（强制）**：
  - 风格参考、题材 moodboard、竞品气质图，默认不能直接推出交互模式。
  - 若正式设计稿没有画清交互，而仓内也没有已验证的 sibling 模式，就必须把该交互标记为 `待裁定` 并向用户说明；禁止静默发明一套新交互，再把它写成项目规范。
- 最终汇报必须显式区分三类状态：
  - `已完成`：真实页面主路径已端到端通过，未留已知阻塞级 UI bug
  - `未完成`：真实页面仍有阻塞级 UI bug
  - `可选 polish`：不影响主路径验收的后续微调
- 若存在下一条可本地推进的 UI 工作，例如读取 DOM/BGG/结算截图、修桌面截图问题、修手机重叠、重新跑真实 E2E、打开截图给用户看、AI 复看截图、更新状态文件，则最终汇报前必须继续推进。不得把“下一步可以做”写成收尾。
- 禁止把“我还在继续收最后几处真实页面问题”和“这一阶段已经完成”同时成立地对外汇报；如果前者成立，默认后者不成立，除非已明确证明剩余项只是非阻塞 polish。

### 5.0 UI 设计规范生成（强制前置）

**强制先读（权威单一来源）**：

> 每个游戏的视觉风格各不相同，**禁止直接复用已有游戏的样式规范**。必须为新游戏生成独立的设计规范。

0. **默认四步走（强制）**
   - 没有明显说明时，UI 设计默认按四步走，且**通过前一步才进入下一步**：
     1. **规则提炼 UI**：先从规则、素材、图面结构里提炼必须常驻、按需展开、禁止出现、素材已有 UI，先确认必要元素和基础布局；默认优先生成**运行时主界面/主交互界面**的结构稿。
     2. **布局收敛 UI**：当 Step 1 布局大致没问题后，默认直接收敛到 **1 张** 可继续执行的布局定稿；只有用户明确要求比较方案时，才额外做多版布局对比。布局收敛仍必须优先使用原本素材语法，并先回答“最大承载量、动作入口、玩家先看哪里”。
     3. **风格统一 UI**：在已选定布局上收成唯一风格，默认只检查是否和素材统一；除非用户明确要求，否则不再默认做风格分叉。
     4. **分界面 UI**：在已选定风格下，再分别生成选择角色、运行时、结算等不同界面的 UI；若用户没有特别说明，默认先做最关键的运行时界面，再补其它界面。
   - `design-system/games/<gameId>.md` 是复刻约束与风格合同，不是前四步的替代品。
   - 用户如果只想要其中一步，必须当轮明确说出跳过哪些步；否则默认视为要完整四步。
   - 四步都必须围绕“本游戏自己的风格”收敛：Step 1 可以抽象规则结构，但 Step 2 起必须能看出该游戏的主题、素材语法和桌面气质；若输出仍像通用模板或其它游戏换皮，必须退回 Step 2/3，不得进入实现。

1. **先看素材再设计（强制）**
   - 若用户提供了图片目录，先识别并打开主地图/主棋盘/角色板/卡牌 atlas/牌背/缩略图。
   - `design-system/games/<gameId>.md` 必须写明至少 1 张主视觉素材的路径、尺寸和肉眼观察结论。
   - 素材本身就是 UI 元素的一部分：地图自带的牌库区、行动轮、流程轨道、区域名称、边界、卡位、图例、槽位都要先作为 UI 约束处理，不能当纯背景。
   - 若素材里包含 `Player reference`、回合顺序卡、帮助卡、`Traitor reference`、`Monster reference` 这类规则摘要卡，默认必须先把它们提炼成运行时的按钮、动作条、短状态或帮助入口；**不得**把整张参考卡直接放进运行界面冒充交互设计。
   - 禁止先用泛化风格词生成一套 UI，再回头硬套用户素材。
   - 生图前必须先按 `boardgame-ui-imagegen` 输出 UI 元素拆解：素材已有 UI、规则必须常驻、按需展开、禁止出现；未完成拆解不得直接调用 imagegen。
   - 若用户点名 BGG/DOM/运行时截图/结算界面，必须把这些资料拆成两层：`结构合同`（区块位置、对象承载、交互顺序）和 `视觉裁定`（哪些原样继承、哪些按本项目风格重绘、哪些只作参考）。禁止把来源样式整体照搬，也禁止完全忽略来源后做成通用面板。
2. **执行 ui-ux-pro-max `--design-system`**：根据新游戏的类型、题材、美术风格生成专属设计系统：
   ```bash
   python D:\codex-home\skills\ui-ux-pro-max\scripts\search.py "<游戏类型> <题材> <风格关键词>" --design-system --persist -p "<游戏名>" --page "game-board"
   ```
3. **产出保存到 `design-system/games/<gameId>.md`**：作为该游戏的 UI 复刻约束参考，后续 Board/组件开发以此为准。
4. **移动端适配写入同一份规范（强制）**
   - 必须写桌面基线与移动端基线。
   - 必须明确 `mobileProfile / preferredOrientation / mobileLayoutPreset` 推荐值。
   - 地图类游戏必须说明拖拽缩放、双指缩放、触控查看、HUD 让位策略。
5. **与通用规范的关系**：`design-system/game-ui/MASTER.md` 中的交互原则（反馈/状态清晰/动画时长等）仍然适用，但配色/字体/视觉风格以游戏专属规范为准。

### 5.0.1 设计稿 / 架构审查 / 需求对齐三联门禁（强制）

- **真实问题定义**：很多“新游戏最后和需求对不上”的根因，不是某一步没做，而是协作者只做了其中一项，例如只出了 proposal、只出了 UI 设计稿、只做了架构审查、只把资源录进目录，然后就直接开始实现。
- **进入正式实现前必须同时满足三项**：
  1. **UI 设计稿已落地**：
     - 必须同时存在：
       - `docs/games/<gameId>/design/generated/step1-*.png|jpg|webp`：规则提炼 / 布局确认稿；
       - `docs/games/<gameId>/design/generated/step2-*.png|jpg|webp`：布局收敛稿（默认 1 张继续执行的布局母版；只有用户明确要求时才做多版对比）；
       - `docs/games/<gameId>/design/generated/step3-*.png|jpg|webp`：同布局风格统一稿；
       - `docs/games/<gameId>/design/generated/step4-*.png|jpg|webp`：分界面稿（至少覆盖本轮明确要求的界面类型）；
       - `design-system/games/<gameId>.md`：实现约束与 UI 规范；
       - `docs/games/<gameId>/design/README.md`：明确当前每一步的唯一有效稿。
     - 仅有 `design-system/games/<gameId>.md`，或只有单张壳层图，不算“UI 设计稿已完成”。
  2. **架构审查已落地**：至少存在 `evidence/<gameId>/<gameId>-architecture-review-<date>.md`、OpenSpec `design.md` 专门小节，或 `design-system/games/<gameId>.md` 中的“对象模型与架构边界”章节。
  3. **需求对齐表已落地**：至少能逐项回答“用户要什么 / 当前不做什么 / 设计落点 / 实现落点 / 验证落点 / 当前状态”。
- **禁止行为**：
  - 禁止只做 `design-system/games/<gameId>.md`，就宣称 UI 设计稿已完成；
  - 禁止只做单张位图生图，却没有按四步把结构、布局收敛、风格统一、分界面走完，就开始实现；
  - 禁止只做架构审查就开始录入数据；
  - 禁止只补 proposal/design/tasks，而缺 `design-system/games/<gameId>.md`；
  - 禁止只在对话里口头说“后面会补设计稿/审查表/对齐表”。
  - 禁止在设计稿未获用户批准时，启动 `dev server`、跑真实页面、补 `Board.tsx` 行为、做前端交互验真。
  - 禁止把“已经有个能点的页面”当成骨架完成；没有通过骨架门禁的页面，一律视为探索性假前端，不得作为正式实现入口继续堆逻辑。
- **默认关系**：
  - Step1 位图回答“必要元素与基础布局是什么”；
  - Step2 位图回答“哪一种布局最适合这款游戏，其中哪一张最贴近原素材语法”；
  - Step3 位图回答“同一布局可以长成哪些风格”；
  - Step4 位图回答“同一风格下不同界面分别长什么样”；
  - `design-system/games/<gameId>.md` 回答“这些稿如何被前端高保真复刻”；
  - 架构审查回答“系统内部如何承接这些对象和规则”；
  - 需求对齐表回答“这三者是否仍对着用户原始目标”。
  - 三者缺任意一项，或四步未走完，就不得进入正式数据录入、正式 Board 实现或正式玩法实现。
- **运行态最低交互门槛（强制）**：
  - 只要 Step1 做的是运行时主界面，图上就必须能看出“当前玩家现在到底能点什么”。
  - 像 `移动`、`探索`、`交易`、`使用 Item/Omen 特殊动作`、`结束回合` 这类从规则或参考卡提炼出的操作，必须至少以按钮、动作条、状态切换或贴近对象的短入口出现其一。
  - 若画面里出现了参考卡大图、帮助卡大图，却看不出当前玩家如何执行这些动作，默认判 Step1 失败。

### 5.0.2 设计批准 → 骨架 → 前端实现 顺序门禁（强制）

- **顺序不可打乱**：新游戏正式进入前端实现前，必须严格满足：
  1. 位图设计四步稿已产出；
  2. 当前进入实现所需的设计稿已经过用户明确批准；
  3. 骨架已完成并可回查边界；
  4. 然后才允许写前端与启动真实页面验证。
- **这里的骨架至少包括**：
  - `proposal / design / tasks / spec delta` 或等价的正式边界文档已说明本轮做什么、不做什么；
  - 需求对齐表能回答“必要按钮为什么存在、哪些按钮暂不该出现、后续界面有哪些”；
  - 运行时对象、主交互入口、状态来源、资源合同已有可实现的最小合同，而不是只剩一张图。
- **禁止行为**：
  - 禁止在“设计稿还没批”时直接写页面，事后再拿页面截图反过来当设计确认；
  - 禁止在“骨架未完成”时进入前端实现，把探索性页面堆成正式运行页；
  - 禁止把“先写一个能点的页面看看”包装成设计阶段的一部分。

### 5.5 基础玩法截图链模板

- **什么时候必须产出**：
  - 当用户明确说“给我一个最基本的端到端”“让我看懂这个新游戏怎么运作”“要每步操作截图”“要能指出每一步点哪里继续”时，必须产出这条模板化截图链。
  - 当本轮准备把新游戏对外表述为“已经有基础可玩流程”“已经能看懂玩法主闭环”时，也默认必须产出。
  - 如果当前只验证局部交互、单个 bug、单个组件、单个 prompt，而没有要证明“这款游戏怎么运作”，则不强制套这条模板，但不得反过来声称“基础流程已完成”。
- **默认目录**：
  - 截图本体默认落在 `test-results/evidence-screenshots/_shared/<gameId>-基础玩法流程/`
  - 文字说明默认落在 `evidence/<gameId>/<gameId>-basic-flow-e2e-<date>.md`

- **逐步模板**：每一步至少按下面格式填写，不得省略 `下一步点击哪里` 与 `点击后结果`。
- **需要现成示例时**：读取 `references/basic-flow-screenshot-template.md`，里面包含一份已填好的示例和交付前自查清单；不要在每次新游戏任务里重新发明写法。

### 5.6 桌面少框门禁

- 固定牌桌/棋盘/桌面区位类游戏必须先通过桌面截图验收，再进入手机适配；桌面未过时不得切到手机。
- 用户说“框多/这么多框/不需要框”时，先按现实含义处理：半透明面板、黑色矩形容器、重复胶囊壳、占位边框、按钮壳、全局悬浮黑圆都属于框感来源；扑克牌、筹码、棋子、骰子等实体素材自身边界不属于要删除的 UI 框。
- 桌面主视图默认不放常驻说明正文。只能保留对象名、数值、短状态、按钮标签和单步动作提示；规则解释、玩法说明、策略建议必须进教程、帮助层或临时提示。
- 桌面主视图不得出现只服务本地热座、测试切座、debug 或截图夹具的可见控件；如果参考图、真实游戏规则或正式交互没有对应意义，即使 E2E 依赖它也必须删掉并改测试。
- 主 UI 的每个可见数字、角标、按钮、面板和状态点都必须能对应到规则对象、玩家决策、公共状态、正式操作或无障碍说明；不能解释现实用途的元素默认删除。若它只服务测试、截图或本地排障，必须下沉到测试命令、开发工具层或不可见夹具，不得让正式玩家看到。
- BGG/DOM/TTS/截图只能作为结构、位置、交互或素材参考；最终 UI 必须有该游戏自己的风格合同，不能用通用 Tailwind 面板或多层框体堆叠冒充风格。
- E2E、单测和截图生成只证明链路可运行，不等于用户视觉验收。只要截图里仍有明显框感、遮挡、重叠、通用壳层或用户未通过，状态只能保持 `in_progress`。
