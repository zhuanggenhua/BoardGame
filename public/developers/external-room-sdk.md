# 易桌游网页游戏 SDK · 房间 v1

易桌游负责建房、入座、就绪和开局。游戏负责显示等待状态、连接自己的联机服务或其他玩家，并在收到开局事件后进入对局。托管 SDK 随平台房间加载，开发者只需修改自己的游戏代码并上传网页 ZIP。

## 快速接入

1. 在构建后的入口 HTML 的 `<head>` 中声明房间协议 v1。

```html
<meta name="boardgame-room-sdk" content="1">
```

2. 游戏从平台房间打开时，读取平台提供的 `window.BoardGameRoomSDK` 和 `meta[name="boardgame-platform-origin"]`，调用 `createClient`。用 `client.ready` 渲染第一份房间数据，用 `onRoom` 更新名单。游戏连接成功后调用 `setReady(true)`，收到 `onStart` 时进入对局。
3. 在易桌游的「上传」页选择「网页 ZIP」，上传游戏构建产物。作品审核上架后，从游戏详情创建房间，用两个独立浏览器会话验证。

直接打开自己的网页或点击「开始游戏」时，游戏可以走原有入口。从「创建房间」或「加入」进入时，才使用房间 SDK。

## 跑通一个双人示例

示例由 [index.html](./examples/external-room-v1/index.html) 和 [boardgame-room.json](./examples/external-room-v1/boardgame-room.json) 组成。右键另存两个链接到同一目录，保留文件名，压缩成游戏 ZIP 后按上面的流程上传。示例用平台房间同步座位、昵称、就绪和开局状态。

1. **识别声明**。打开已收录的游戏详情，确认出现「创建房间」。选择 2 人和 5 × 5 棋盘。按钮出现说明平台已识别房间能力，发送和接收房间消息要在下面两步验证。
2. **连上房间**。房主建房后，示例显示 SDK 版本、房间 ID、房主昵称和「等待开局 · 1/2」。用另一个浏览器或无痕窗口打开邀请链接，或从游戏详情加入。两边应看到相同的房间 ID、两个玩家和 5 × 5 棋盘。此时 `client.ready` 已成功，房主的「开始对局」仍需等待双方准备。
3. **收到开局**。双方都点示例里的「准备」，房主再点易桌游的「开始对局」。两边都应显示「对局已开始」。接实际游戏时，再确认双方能在同一场对局正常操作，这一步由游戏自身的联机逻辑决定。

上传保存成功表示 ZIP 已托管。投稿阶段目前没有自动联机验收，以上检查要用实际房间完成。

### 常见问题

- **没有「创建房间」**。检查打开的是已上架的网页 ZIP 游戏，且最终构建产物的入口 HTML 包含 v1 声明。
- **SDK 对象不存在**。从易桌游的建房或加入入口打开；本地直开 HTML、作品预览和普通「开始游戏」不会注入房间 SDK。
- **房间连接失败或超时**。检查游戏是否调用了 `createClient`，并把平台注入的来源原样传给 `platformOrigin`。在游戏代码里处理 `client.ready` 的错误。
- **无法点击「开始对局」**。确认房间坐满，并且每个游戏客户端都已调用 `setReady(true)`。确认两边名单里的玩家均显示就绪。

## 在平台的建房弹窗提供配置

在自己的发布目录里把 `boardgame-room.json` 放到入口 HTML 旁边。平台读取这个文件来显示可选人数、字段名和选项。上面的双人示例附有一份可以直接用的配置。

`playerCounts` 为 2–32 范围内的整数列表，例如 `[2, 4]` 只提供两人和四人房。`fields` 可省略，最多 12 个下拉字段，每个字段最多 16 个选项。字段 ID 以小写字母开头，最多 32 字符，可以使用小写字母、数字、下划线和连字符。字段 ID 及单个字段中的选项值须唯一，显示文字和选项值均为最多 80 字符的非空字符串，默认值必须在选项中。文件最多 16 KiB。已提供声明的游戏以文件为准，已有包可以继续使用投稿资料的人数范围。

房间创建时固定设置。房主和访客首次收到房间快照时就能读取同一份 `room.settings`。例如用 `room.settings.board === 'expanded'` 选择 5 × 5 棋盘。平台负责表单和校验，只有游戏本身知道该怎样应用这些选项。

建房弹窗只在声明多个可选人数时显示人数控件。易桌游负责房间名称和可选密码。加密房间在入座前由平台验证密码，游戏通过 SDK 接收已入座的玩家。

## 接口参考

- `createClient({ platformOrigin, onRoom, onStart, onSignal, onClose })` 创建连接。回调按游戏需要传入，`platformOrigin` 使用平台注入的值。
- `client.ready` 在收到第一份房间数据时完成，连接失败时拒绝。后续变化通过 `onRoom(room)` 通知，`client.room` 可读取最新快照。
- `client.setReady(true)` 报告已准备，传入 `false` 取消准备。收到 `onStart(room)` 后进入游戏对局。通过 `onClose(reason)` 接收连接关闭原因。
- 房间快照包含 `roomId`、本机 `seatId`、`hostSeatId`、`capacity`、`settings` 和 `players`。每名玩家有 `seatId`、`displayName` 和 `ready`。

游戏在房间尚未坐满时就会加载。可以直接显示游戏的等待界面，并用 `players.length` 和 `capacity` 显示人数。需要齐员才能建立连接的游戏可以等到两者相等再开始连接。成员变化时平台可能重新载入游戏，接入代码应从收到的房间快照恢复等待状态。同一份名单的就绪状态变化不会重载游戏。

使用房间 ID 作为同局标识，用平台座位和昵称建立自己的对局。如果游戏用 WebRTC，可用 `client.sendSignal(toSeatId, kind, value)` 转发 `offer` 和 `answer`，在 `onSignal({ fromSeatId, kind, value })` 中接收。外部服务器型游戏可用自己的联机传输。

《永恒之谷》的接法是房主按名单初始化本机游戏房间，按座位向访客发送 offer，访客返回 answer，两边连接后分别报告就绪。房主在易桌游开局，游戏端收到 `onStart` 后进入同一局。独立打开页面时，作者可以保留游戏原有入口。

## 更新、兼容与迁移

- `window.BoardGameRoomSDK.version` 是协议主版本。接入 v1 时用 `version === 1` 判断协议。
- `window.BoardGameRoomSDK.release` 是本次实际加载的发布版本，例如 `1.0.0`。游戏使用新能力前，按该能力的接口文档判断当前运行环境是否提供它。
- 托管 v1 随易桌游发布。玩家下次加载新版易桌游网页，再进入房间时会取得最新兼容版。已打开的对局继续使用载入时的 SDK。开发者无需为同一主版本的兼容更新重新打包或上传游戏。
- 使用包内 v1 SDK 的开发者可以在入口 HTML 加上版本声明，将本地 SDK 导入替换为 `window.BoardGameRoomSDK?.createClient`，重新构建并上传游戏 ZIP。已有的房间事件、座位和 WebRTC 回调可沿用。变更协议主版本时，会另行提供迁移指南。


## 后续接入排行榜等能力

新能力会通过易桌游托管 SDK 交付，其接入方式和发布记录继续更新在这份文档。需要游戏提供专有分数或结算数据时，要使用该能力的游戏由开发者补对应调用。平台能从已有接入获得所需数据时，可以直接在平台实现。排行榜接口开放后会在本指南中列出支持场景、调用方法和版本。
