## 当前结论

1. 枪手 `ability-cards.webp` 不是“沿用老派系顺序即可”的安全例子；但 atlas 是否失配，必须回到原始图与老角色同位对照裁定，不能再直接信历史核对图。
2. 旧结论“`slot-22 / 23 / 24` 应拆成上下两张正式运行时卡”已被端到端与老派系对照共同证伪。
3. 当前已确认的正式合同是：
   - `slot-22 / 23 / 24` 都是复合物理升级牌
   - 手牌、放大预览、技能槽叠层都必须显示整张物理牌
   - 下半区 `枪托击打 / 标记目标 / 执法者` 属于升级后基础技能内部的 `variants`
   - 日志语义必须区分“打出升级卡”和“发动技能变体”
4. 端到端已验证：
   - `死亡之眼 II` 打出后进入玩家面板，不进弃牌堆
   - `执法者 / 枪托击打 / 标记目标` 以“发动技能”进入日志，而不是以独立手牌进入弃牌流程
5. `Loaded / 装填弹药` 的通用时机已裁定为“攻击掷骰阶段结束后加伤”；`Wild West`、`Fill'Em With Lead`、升级 `Quick Draw` 等具体文本维持显式重掷例外。

- 当前端到端收口顺序已经完成：

## 与老派系升级合同逐张对照

### 老派系基线

先确认老派系已经长期成立的升级合同：

- 升级卡永远替换一个`基础技能 ID`，不是替换某个 `variant`。
- 即使升级后的 `newAbilityDef` 内部含多个 `variants`，`newAbilityDef.id` 也仍然等于基础技能 ID。
- II / III 级共存时，仍然是多张升级卡分别指向同一个基础技能 ID。
- 老派系里大量升级本身就是“复合升级”：
  - 一张升级卡替换的是同一个基础技能
  - 该基础技能内部可能有多个阈值、多个子效果、多个 `variants`
  - 同类升级取最高，不会因为子效果多就拆出多张手牌图

可直接复查的老派系样例：

- `monk/card-thrust-punch-2 -> replaceAbility('fist-technique', FIST_TECHNIQUE_2, 2)`
- `monk/card-thrust-punch-3 -> replaceAbility('fist-technique', FIST_TECHNIQUE_3, 3)`
- `barbarian/upgrade-slap-2 -> replaceAbility('slap', SLAP_2, 2)`
- `barbarian/upgrade-slap-3 -> replaceAbility('slap', SLAP_3, 3)`
- `paladin/upgrade-righteous-combat-2 -> replaceAbility('righteous-combat', RIGHTEOUS_COMBAT_2, 2)`
- `paladin/upgrade-righteous-combat-3 -> replaceAbility('righteous-combat', RIGHTEOUS_COMBAT_3, 3)`
- `paladin/upgrade-holy-defense-2 -> replaceAbility('holy-defense', HOLY_DEFENSE_2, 2)`
- `paladin/upgrade-tithes-2 -> replaceAbility('tithes', PALADIN_TITHES_UPGRADED, 2)`

结论：

- 枪手已经确认没有偏离老派系的，是`升级卡 -> 基础技能`这条规则。
- 之前最可疑、且已经被修正的，是`slot-22 / 23 / 24` 被拆成多个独立手牌对象的错误合同。
- 当前需要继续守住的，是：升级卡只替换基础技能；下半子区只作为 `variants`；UI 不得再把这些变体渲染成独立手牌或独立弃牌语义。
