# 游戏 UI 交互规范 (Game UI Interaction Principles)

> **核心理念**：游戏感 = 即时反馈 + 状态清晰 + 操作愉悦
> 
> 本规范定义**交互原则**，不限定具体颜色/风格。视觉风格见 `design-system/styles/`。

---

## 1. 交互反馈原则

### 1.1 即时反馈 (Immediate Feedback)

**所有可交互元素必须有反馈**，让玩家知道"我的操作被接收了"。

| 交互类型 | 必须反馈 | 可选增强 |
|----------|----------|----------|
| Hover | 视觉变化（亮度/颜色/边框） | 轻微位移、光晕 |
| Press/Tap | 缩放或位移 | 音效、涟漪 |
| 禁用点击 | 无反馈 + 视觉暗淡 | 抖动提示"不可用" |
| 长按 | 进度指示 | 震动反馈 |

**反馈时机**：
- Hover/Press 反馈必须 < 100ms（感知即时）
- 状态切换动画 150-300ms（感知流畅）
- 复杂动画 300-500ms（感知完整）

### 1.2 状态清晰 (State Clarity)

玩家必须能**一眼区分**元素的当前状态：

| 状态 | 视觉特征 | 实现方式 |
|------|----------|----------|
| 可交互 | 明显可点击 | cursor-pointer + 视觉提示 |
| 悬停中 | 高亮/突出 | 亮度提升、边框、阴影 |
| 按下中 | 下沉/收缩 | scale 或 translate |
| 选中/激活 | 持续高亮 | 颜色变化、边框、图标 |
| 禁用 | 明显不可用 | 降低透明度、灰度、去除阴影 |
| 加载中 | 进行中提示 | spinner、骨架屏、进度条 |

**选中态底线**：开关、卡牌、目标、tab、模式卡片这类可切换对象，已选态必须在整屏截图里和未选态一眼拉开。不能只靠小角标、轻微亮度、文案、`aria-pressed` 或内部状态证明“已选中”；至少要有完整外框、明显底色/亮度/饱和度变化、徽标/图标或等价视觉信号，并在 E2E 中对这些视觉信号做几何或样式断言。外部依据按 WCAG 1.4.1 / 1.4.11 口径执行：颜色不能是唯一信息来源，组件状态所需的非文本视觉信息必须有足够可辨识度。

### 1.2A 用户友好底线 (Never Looks Dead)

**合法状态不能长得像卡死。** 只要当前仍有合法下一步，玩家必须能在首屏直接看出“接下来做什么”。

最低要求：
- 若只剩一个合法主动作，UI 必须把该动作做成显式可发现入口，或给出紧贴该入口的短提示。
- 若存在多个合法候选，候选本体必须可见，且能一眼看出它们就是这一步的操作对象。
- 若当前是等待别人、等待 AI 或等待系统推进，必须明确显示等待归属，不能让等待态和死页面长得一样。
- 空态、开局态、等待态、终局前临门一脚这类“容易像没内容”的状态，默认都属于高风险态，必须单独设计可继续性。

禁止：
- 规则上还能继续，但首屏像“什么都没有，也不知道点哪里”。
- 合法等待态没有任何等待归属，用户只能猜是卡住还是在等别人。
- 关键主操作只能靠 hover、经验、隐藏热区或测试人员记忆才能发现。

### 1.2B 文案不得复述视觉信号

**画面已经表达的内容，不要再用常驻文字复述一遍。** 高亮、箭头、连线、选中态、禁用态、数字徽章、颜色分组和按钮位置已经承担了视觉语义时，文案只补玩家还不知道的动作意图、成本、对象或结果。

最低要求：
- 绿色高亮或可点击样式已经标出候选时，常驻文案写“选择目标 / 选择当前行动”，不要再写“绿色区域都能点 / 点击绿色目标”。
- 箭头和路线已经显示方向时，文案写“从 A 出发 / 进攻 B”，不要再解释“沿箭头走 / 按绿色路线点击”。
- 按钮本体已经在场、可点击样式已经成立时，不要再给每个按钮补一个“可选”状态词；只有真正进入当前前景、处理中或禁用原因需要额外表达时，才额外加状态。
- 选中、占用、可选、已准备这类状态如果能通过描边、光效、角标、禁用态、透明度和图标表达，就不要把“已选目标 / 点击作为目标 / 已选择 / 已占用”这类文字条压在对象本体上；文字只能放在不遮挡本体的摘要区、tooltip 或无障碍标签里。
- 按钮 hover 提示可以说明功能、花费和结果，但不能把按钮本身的 hover 变亮、可点击、位置等视觉状态再讲一遍。

禁止：
- 用颜色名、布局方位或高亮状态替代真实动作，例如“点绿色格”“点右侧红按钮”“看发光区域”。
- 在同一屏同时用高亮/箭头表达候选，又用一段正文重复“这些是可点击目标”。
- 在候选对象、角色头像、卡牌或棋盘目标上覆盖大块状态文字，遮挡对象本体；除非这是唯一能表达禁用原因的临时错误提示，否则优先改成图标/描边/tooltip。
- 为了让测试好找，把 `source/target/pending/fallback`、源区、目标区、待结算、低保真这类实现口径写进玩家常驻 UI。

### 1.3 操作愉悦 (Satisfying Interaction)

**游戏感的核心**：让玩家觉得"点这个按钮很爽"。

实现手段（按效果排序）：
1. **物理感**：按钮有"厚度"，点击有"下沉"
2. **音效配合**：点击、拖拽、放置有声音
3. **动效强化**：成功操作有庆祝动画
4. **触觉反馈**：移动端震动（可选）

## 2. 动画规范

### 2.1 时长标准

| 场景 | 时长 | 缓动函数 |
|------|------|----------|
| 微交互（hover/press） | 100-200ms | ease-out |
| 状态切换 | 200-300ms | ease-in-out |
| 元素进入/退出 | 300-400ms | ease-out |
| 复杂动画（翻牌/掷骰） | 400-800ms | spring/bounce |
| 全屏转场 | 300-500ms | ease-in-out |

### 2.2 性能规则

**必须遵守**：
- 只动画 `transform` 和 `opacity`（GPU 加速）
- 禁止动画 `width`、`height`、`margin`、`padding`
- 禁止 `transition-all`，必须指定具体属性
- 尊重 `prefers-reduced-motion`

**Framer Motion 推荐配置**：
```tsx
// 标准弹簧
const spring = { type: "spring", stiffness: 300, damping: 25 }

// 快速响应
const snappy = { type: "spring", stiffness: 500, damping: 30 }

// 柔和
const gentle = { type: "spring", stiffness: 200, damping: 20 }
```

### 2.3 禁用状态动画

禁用元素**不应有交互动画**：
```tsx
whileHover={disabled ? undefined : { scale: 1.02 }}
whileTap={disabled ? undefined : { scale: 0.98 }}
```

## 3. 组件交互模式

### 3.1 按钮 (Button)

**必须**：
- 有 hover 反馈
- 有 press 反馈（缩放或下沉）
- 禁用时视觉明显不同
- 加载时显示 spinner 并禁用
- 可见按钮文案必须短且尺寸稳定。右侧 rail、横幅、工具按钮、页角按钮、小型 CTA 默认只写 2-5 个中文字符的动作名或对象名，例如 `剧本`、`关闭`、`确认`；剧本编号、章节名、长标题、验收语义和说明句只能放在内容标题、邻近状态、tooltip、aria-label 或阅读页正文里，不得拼成 `剧本1查阅` 这类长按钮。只要真实截图里按钮因文字换行、撑宽、挤压相邻控件或改变固定槽位，就按 UI 失败处理，不能用“热区仍可点”放过。
- 真正承接点击、切换、确认、跳过、取消、筛选或模式选择的控件，不能长得像正文小字、注脚、弱标签或普通状态文本。最低要求是 `44px` 级命中区、可见边界或底色、hover/focus/选中反馈；如果视觉上只是小字提示，它就不能承担交互。测试只证明 `onClick` 能触发不够，截图里玩家必须一眼看出这是按钮。

**推荐**：
- 主要操作按钮有"厚度感"（底部阴影 + 点击下沉）
- 危险操作有确认步骤

### 3.2 卡牌 (Card)

**可选中卡牌**：
- Hover：轻微上浮 + 边框/光晕
- 选中：持续高亮 + 选中标记
- 禁用：灰度 + 降低透明度

**可拖拽卡牌**：
- 拖拽时：提升 z-index + 阴影增强
- 放置时：有落地动画
- 无效放置：回弹到原位

### 3.3 面板 (Panel)

**信息面板**：
- 半透明背景 + 模糊（可选）
- 不遮挡关键游戏区域

**模态面板**：
- 有遮罩层
- 支持点击遮罩关闭（可配置）
- 进入/退出有动画

### 3.4 资源指示器 (Resource Indicator)

**数值变化**：
- 增加：绿色闪烁 + 数字上浮
- 减少：红色闪烁 + 数字下沉
- 变化动画 200-400ms
- 结算计分：如果用户要求“像结算/跳分/计分动画”，必须让数字从旧值或 0 跳到目标值，并提供过程态截图；只把最终分数变大不算计分动画。
- 结算计分主体：如果分数来自卡牌、棋子、随从、骰子或其它已在场对象，**主动画主体必须是这些被结算对象本体**，例如牌面跳分、对象高亮、对象附近弹出 `+N/-N`，再让总分同步累加；右侧排名、结果榜单、总结面板默认只负责承载结果，不得反客为主变成主要动画舞台。

## 4. 游戏特有交互

> 当任务涉及主交互壳层、prompt、waiting、手牌区、右侧 rail、中央响应层时，先看 [source-families.md](D:/gongzuo/webgame/BoardGame/design-system/game-ui/source-families.md) 选择批准家族，再决定是否需要新模式。

### 4.1 回合/阶段指示

- 当前阶段必须**视觉突出**
- 阶段切换有过渡动画
- 玩家回合有明确提示（颜色/动画/音效）
- PC 牌桌进行态的`当前行动者/你的回合`是主 HUD，不是装饰小标签；真实截图里如果需要放大才能看清，直接判失败。
- 短提示横幅只承担当前状态提示时，必须是短条/徽章级，不能做成横跨牌桌的大块操作容器。
- 提示横幅不得进入底部手牌安全区，也不得贴着手牌上沿压迫手牌；若真实截图中提示条遮挡、贴边或挤占手牌槽位，必须重做布局。
- 绝对定位提示、浮动按钮、飘字必须挂在独立 overlay/rail 层，不得参与手牌区、公共牌区、棋盘格或战场单位区的布局计算；验收必须量矩形证明主区域尺寸不变且未被覆盖。
- 卡牌放大镜/详情按钮属于检视工具，桌面端只允许在 hover 或键盘可见焦点时出现；`actionable` 不等于工具常驻。
- 触屏卡牌若同时承担预览和执行，默认第一次点击聚焦/预览，第二次点击执行；长按只作为大图辅助入口。
- 手牌操作带在对局中必须尺寸稳定，临时多 1 张牌应通过预留槽、稳定扇形或稳定重叠解决，不得触发整排缩放或密度切换。

### 4.2 选择与确认

**单选**：点击即选中，再次点击取消
**多选**：点击切换选中状态
**确认操作**：选择后需要额外确认按钮

- 模式选择、目标槽位、对象归属这类分段按钮，按钮文案必须同时表达“动作 + 对象”，不能只复用对象名本身。若按钮会决定后续点击结果，文案必须让玩家不看解释也知道它影响什么，例如“给上手 / 给下手”优于“上手 / 下手”。对象名可以保留在卡牌行、玩家区或状态标签里；承接操作的按钮必须说清动作。
- 若同屏已经存在同名对象标签（例如手牌行也叫“上手 / 下手”），新增操作按钮不得再只写同名标签，否则玩家会误读为行标题或选牌状态。必须通过动作词、图标、位置或摘要把“这是操作目标选择器”与“这是对象标签”分开。
- 可直接在对象本体上完成的选择，必须优先做成本体直选：卡牌点卡牌、房间点房间、角色点角色、棋子点棋子。不得把本来可点的对象退化成一排文字按钮、顶部黑框按钮或旁路列表。
- 同一语义的选择高亮必须复用同一套视觉语言：候选态、悬停态、选中态、不可用态在卡牌、房间、角色、棋子之间只能按对象形状适配，不能在同一游戏里一处用圆圈、一处用黑框、一处用文字下划线。
- 非骰子对象默认禁止用圆圈表达选中或可选。骰子可用圆形命中区，因为投影近似圆形；卡牌、房间板块、角色五边形、物品牌、人物头像等对象必须让描边贴合对象本体轮廓或外接形状。
- 同一游戏内同类数值和状态标识必须使用同一套形状语法。属性格、资源数、候选数、选择徽章这类同类元素不能一处方形一处椭圆；除非对象现实形态不同，发现一处不一致时必须同步扩审同游戏其它同类 UI。
- 如果对象已经承载了玩家归属，例如角色被 P1/P2 选中、目标属于某玩家，选中标识必须同时表达归属；只放一个对钩、圆点或泛用高亮而不显示归属，判为信息不完整。
- 当一个交互已经存在成熟家族，新增同类交互前必须主动搜索同类并复用。像“鉴定/属性选择”“目标房间选择”“物品卡选择”这类同类选择，不得各自临时发明一套按钮样式。
- 局内开局设置中的剧本、人物、军备、阵营卡等实体对象，只要正式卡面、辅助卡、剧本页或图集裁片已经存在，必须让正式对象本体成为主要可见内容和点击区域；不得把对象名重新排成文字按钮、列表行或摘要卡来替代原素材。缺少正式正面素材时，正式对局 UI 最多只能用牌背、对象名、类别做临时可玩承接；素材缺口必须转入资源 intake、向用户索要素材或锁定补源路径，不得把该状态收口为完成。禁止把 `缺正面`、`front missing`、`缺图` 这类排障标签当成玩家可见短状态。

### 4.3 拖放交互

- 可放置区域有视觉提示
- 拖拽过程中显示预览
- 无效放置有反馈（抖动/回弹）

### 4.4 唯一下一步必须有常驻明文入口

- 当某一步是玩家当前唯一可继续的下一步时，界面必须提供常驻的显式入口。
- 这个入口必须直接落成明文按钮、横幅按钮组、确认条或等价 CTA，让玩家一眼知道“下一步点这里”。
- 关键推进步骤不得只靠 hover、tooltip、透明热区、地图隐式点击区或“点盘面试试看”这类猜测式交互承接。
- 如果主视图里还保留原始热区，它也只能作为附加入口，不能成为唯一入口。
- CTA 文案必须直接说明动作与对象，例如“进入下一步行动”“确认并进入棋盘”，不能只写抽象名词。
- 若 CTA 只是打开目标选择态，打开后必须让玩家立即分清“现在该点牌桌对象，不是继续点这个 CTA”。原 CTA 应转成状态提示或退为辅助，目标对象必须提供可量的热区、对象旁动作提示和取消入口。

### 4.5 消耗型动作必须先显式选择并允许取消

- 任何会消耗手牌、资源、部队、人口，或会触发不可逆提交的动作，默认都必须先进入显式选择态，不能在第一次点击动作按钮时直接吞掉成本。
- 显式选择态至少要同时提供：当前动作名、需要支付的成本、已选内容、确认执行入口、取消当前动作入口。
- 若成本来自可枚举对象，例如手牌、资源牌、候选部队，玩家必须能逐项选择与反选，不能由系统静默替玩家自动决定“前几张”“默认几张”。
- 取消入口必须把本次临时选择清空，并允许玩家回到未提交状态改选动作或直接放弃。

### 4.6 共享证据截图必须中文命名且直接表达含义

- 凡是用于共享、汇报、验收、回归对照的关键证据截图，文件名必须使用中文；不得只用英文、拼音、内部字段名、`current`、`debug`、`before-click`、`after-action` 这类只能让实现者自己看懂的命名。
- 文件名至少要同时表达三个信息：当前页面或阶段、交互对象或动作、截图处于动作前/动作中/动作后哪一种状态。推荐格式为 `序号-页面或阶段-动作对象-状态.png`。
- 如果截图承接的是弃牌、支付、确认、取消、目标选择这类关键交互，文件名必须直接出现对应中文词，例如 `弃牌选择`、`确认执行`、`选择目标`；不得让读图者再去猜“哪张才是这一步”。
- 如果为了最终汇报把多张验收图做成联系图、拼图、对照图或索引图，图内所有用户可见标签也必须使用中文业务语义；不得用英文、拼音或内部缩写规避中文渲染问题。
- 联系图/拼图生成脚本必须显式使用可渲染中文的字体，并在交付前核对图内中文标签无乱码、无方块、无问号替代。只把乱码标签改成英文不算修复，直接判证据图不合格。
- 同一流程目录内不得长期并存两套语义重叠但命名不同的截图；一套新命名生效后，旧编号、旧英文名、重复语义截图必须清理或迁走，避免目录本身再次变成歧义源。
- 联机截图文件名除阶段与动作外，还必须表达**视角归属**。如果是固定玩家流程，文件名里要明确写 `玩家 A 视角 / 房主页 / 接收方页` 之类 viewer 身份；如果是多席位对照，必须把每张图各自标明 `玩家 B 页 / 玩家 C 页 / 发送方页`，不得再用会把不同 seat 页面混成一个用户流程的命名。
- 当验收目标是“固定某个玩家端连续体验”时，整条截图链必须来自同一 viewer 页面；中途切到别的 seat 页面拍图，再把结果放回这条链里，直接判截图证据无效。
- `temp/`、`debug/`、`current/`、工作区根目录散图默认都不是正式共享证据；只有落在约定共享目录、命名合规、可回查到真实 E2E 的截图，才算正式验收资产。
- 对于 `指挥 / 进攻 / 投掷 / 弃牌 / 支付 / 目标选择 / 确认 / 取消 / 等待` 这类关键交互类型，目录里至少要能找到一条中文命名的真实截图链；用户点名要看某一类交互时，不能只给最终态或调试图顶上。
- `进攻 / 调度 / 战斗 / 投掷` 这类多步骤攻击链，截图链至少要覆盖三个时刻：`目标出现或选择前`、`处理中`、`结算后`；缺任一时刻，都不能宣称这条链已经有完整端到端证据。

### 4.7 用户可操作 UI 必须占有固定槽位

- 任何承担真实点击、确认、选择、取消、继续推进职责的 UI，都必须有固定槽位；不得随着提示块、说明块、日志块、状态块的出现而被重新挤位、下推、横向压窄或部分移出视口。
- 如果本轮只是给排名、结算、状态条补王冠、金银铜、徽章或数值动画，必须保留原排名/牌桌/手牌/中央牌区槽位；禁止把“增强结算表现”升级成“重做终局布局”。
- 固定槽位至少要能回答三件事：入口长期停在哪里、该槽位由谁保留、哪些元素禁止侵入。没有这三个答案时，不得直接实现新的交互布局。
- 常驻操作栏、手牌区、底部 dock、右侧 rail、中央 modal、底部 prompt 条属于可复用槽位家族；新交互默认先复用既有槽位，不得临时在地图上、牌面上或 HUD 空隙里再发明一块“差不多能放”的面板。
- 牌桌/卡牌类游戏里，`摸牌`、`确认选择`、`确认弃置`、`结束回合` 这类反复点击的主动作，默认固定在**右侧偏下动作槽**；禁止放进顶部状态轴、标题条、左上统计角或其它高移动成本区域。顶部区域只负责状态，不承接这类高频主点击。
- 翻牌、抽牌亮相、发现牌、事件牌、投骰结果、战斗结算这类会阻塞当前流程的结果对象，默认固定在中央或等价主舞台；不得缩成右上角小条、侧栏摘要、日志行或一块不起眼的 HUD。后续确认/继续按钮可以留在既有动作槽，但真实牌面、骰面或结果本体必须进入主视线。
- 作祟开始、终局触发、阵营目标改变、Boss/怪物登场这类重大阶段揭示，默认按信息职责选型：若玩家只是需要知道“阶段已变、可去既有剧本/规则入口查详情”，使用**可关闭的非模态阶段横幅（stage-change banner）**，形态是短条/徽章级强阶段信号 + 一句事实提示 + `关闭`，例如 `作祟开始，剧本发生变化，可以打开剧本查阅`。若已有常驻剧本书/规则书入口，横幅不得再放第二个“打开剧本书”按钮，也不得做成流程面板、action panel、步骤清单或规则摘要墙。只有规则明确要求“当前必须读完/确认某个阻塞内容才能继续”时，才使用阻塞式 overlay 或手动继续按钮；否则关闭横幅即可回到牌桌后续动作。
- 重大阶段横幅不得承载规则细节：规则步骤清单、公开/私密边界、阵营目标分读、隐藏身份说明、设置队列、秘密目标和胜负条件不得进入阶段横幅或常驻主 HUD。详细规则、目标、秘密边界和设置流程进入剧本书、规则书、帮助层或后续专门的目标/动作 UI。验收用连续截图证明：阶段横幅出现、既有规则/剧本入口可手动打开、关闭阅读层后横幅仍在、玩家关闭横幅后才进入后续动作。
- 阻塞结果主舞台默认是开放式承接，不是整块弹窗背景。事件牌、发现牌、骰盘和战斗结果可以有对象阴影、轻量压场和按钮边界，但不得把牌面与选项一起包进一张大深色框、厚边框容器或封闭说明盒；若主舞台第一视觉是背景框而不是真实对象，判为未达标。
- 阻塞流程里的可选项必须肉眼可读、手指可点。属性、伤害、跳过、确认这类当前需要玩家点击的控件不得低于常规触控命中区；测试和截图验收必须量到可点尺寸，不能只断言按钮文字存在。
- 小字按钮直接判失败：任何当前流程候选、声明开关、跳过/放弃、确认/取消、下一步入口，如果视觉尺寸、字体、边界或底色让它更像提示文字而不是控件，即使热区在 DOM 里存在，也必须重做成明确按钮、对象本体高亮或等价主交互入口。
- 固定槽位在正式实现前必须落成 `主交互对象 / 固定槽位 / 让位顺序 / 禁止侵入对象 / 来源家族` 五联单；没有五联单，就不能宣称“这块 UI 已经有合同”。
- 验收必须覆盖交互前、交互中、交互后 3 个时刻，证明主交互槽位没有漂移、没有被顶走，也没有留下抢位残影。
- 同一游戏的开局、对局中、终局默认共用同一套壳层语言：顶栏、总分摘要、主牌桌锚点、右侧摘要壳层只能做轻量显隐和密度调整，不能在某个状态突然切到另一套完全不同的 UI 家族。若切完后像“另一个游戏”，说明没有守住家族连续性。

### 4.8 瞬时面板不得抢占另一块可操作 UI

- 弃牌确认、目标选择、响应窗口、步骤提示、检查面板这类瞬时 UI，只能进入自己的交互槽位、overlay 或 modal；不得靠插队进 DOM 流把另一块主交互 UI 顶走。
- 如果某个瞬时面板只是补充说明某块现有交互，例如“先在手牌里选牌，再在右侧确认”，它必须附着在对应主交互槽位附近，且主入口仍保持原位可见。
- 当屏幕空间不足时，优先让位对象是说明、日志、帮助、提示、次级状态块；不得先压缩按钮点击区、手牌点击区、地图主判断区或当前唯一下一步入口。
- `waiting`、`hint`、`confirm strip`、流程横幅、短提示条都属于瞬时 UI；它们只能作为附着提示，不得侵入底部手牌槽位、右侧动作槽位或中央主选择壳层，把界面做成两组并列主入口。
- **响应链里一旦已经存在真实交互承接面，ownership/waiting 壳必须整层退场（强制）**：像手牌直选、基地直选、棋盘对象直选、`PromptOverlay`、右侧动作槽这类已经直接承接“下一步点击”的 UI，一旦活着，中央 `Me First / waiting / ownership` 壳层就只能退场，不能继续以“状态提示”“中间让过窗”或其他名义并列显示。否则会把同一步做成两个主入口。
- **禁止用 `sourceId` / 交互名特判决定哪层还能继续显示（强制）**：是否保留中央壳层，判断依据只能是“当前有没有真实交互承接面”，不能写成“某个 `sourceId` 继续显示、另一个 `sourceId` 隐藏”。如果某条链看起来需要例外，先回去重判交互对象、固定槽位和来源家族，而不是补一个名字特判。

### 4.9 新交互模式必须有可回查来源

- 新增或重做交互模式前，必须先锁定来源，并能说明“参考的是哪一类成熟模式、为什么适合当前语义、当前实现保留了哪些不变量”。没有来源时，不得靠感觉发明新模式。
- 可接受来源包括：当前项目内已验证的成熟实现、用户明确给的参考图/流程图、真实产品截图、规则书/设计稿中已经表达清楚的交互语义。只说“我觉得这样更顺手”不算来源。
- 汇报或规范里必须把来源落成可回查证据，例如文件路径、截图路径、规则章节或设计稿路径；否则后续实现与审查无法判断你到底在复用哪一套模式。
- 来源必须点名到真实家族，而不是抽象说“参考成熟游戏”。当前项目内可直接回查的成熟来源至少包括：`src/games/smashup/ui/HandArea.tsx` 的底部常驻手牌槽位、`src/games/smashup/ui/PromptOverlay.tsx` 的底部非阻塞卡牌查看/选择面板、`src/games/smashup/ui/MeFirstOverlay.tsx` 的中央 ownership/waiting shell、`src/games/smashup/Board.tsx` 中 `activePromptSurface` 的单一承接面路由。
- **可见卡牌候选不得退化成文字按钮（强制）**：当候选对象本身是卡牌、持有物、手牌、弃牌或 revealed cards，且当前视角按规则允许显示正面或牌背时，默认必须让卡图本体成为选择/查看入口。文字按钮、chips、列表行只能用于非卡牌操作（跳过、确认、关闭、取消、分组筛选）或确无素材的例外；不能在已有卡图素材时用纯文字按钮替代卡牌本体。仓内来源是大杀四方 `PromptOverlay.displayCards` 的 `CardPreview + data-card-uid` 选择面，以及 `HandArea` 对手视角把允许查看的手牌直接渲染到手牌槽位。
- **当前流程候选不得丢到角落（强制）**：如果某组候选决定当前步骤能不能推进，或属于当前步骤的对象选择，它必须附着在当前行动/确认/流程条附近，进入同一个主交互视线区。交易这类协商请求里，己方持有物和对方持有物都属于当前流程候选，必须和交易摘要、最终确认同屏；禁止把候选放到顶部角落、侧边状态栏、牌堆旁、日志旁或远离确认按钮的位置，那些位置只能承载状态提示、查看入口或非当前流程信息。
- **空侧选择不得做成模式标签（强制）**：如果 `跳过 / 放弃 / 不执行` 本身会结束机会、推进流程、放弃奖励或改变规则状态，它是独立动作，必须有清楚按钮并和候选本体同屏可见。如果“不选”只是某组对象候选的默认空侧，且主确认按钮已经能提交完整结果，就不得把 `无 / 不选择 / 索要 / 换回 / 不换回` 做成与真实卡牌、房间、角色并列的候选或玩家-facing 模式。交易的正确表达是双方真实持有物清单：摘要只写 `你给出 X`、`对方给出 Y`，未选的一侧不写成模式；双方全空时不允许出现 `提出交易`。
- **请求型流程的最终确认必须和摘要同块（强制）**：当一步会把“已选对象清单”打包成请求发给别人同意时，最终确认按钮必须贴在该请求摘要/候选条同一块里，并且同屏只允许一个最终确认。禁止让玩家先在中间读摘要、再去底部导航或角落找确认；也禁止流程条和底部动作栏同时各放一个 `发送请求 / 确认`。典型例子：山屋惊魂交易的按钮必须叫 `提出交易`，贴着摘要，摘要只复述双方给出的真实对象；接收方同意的是这条对象清单请求。

### 4.10 主交互壳层必须先锁五件事

- 任何会承载真实点击、确认、选择、取消、推进的 UI，在动手前必须先锁定五件事：`主交互对象`、`固定槽位`、`让位顺序`、`禁止侵入对象`、`来源家族`。
- `主交互对象` 指这一步真正要被用户操作的对象本体，例如手牌、目标、主行动控件、基地或候选卡；`固定槽位` 指这一步长期停留的视觉区域；`让位顺序` 指当空间不足时优先退场的对象；`禁止侵入对象` 指哪些临时 UI 不得顶走它；`来源家族` 指本轮复用的成熟承载方式。
- 如果五件事里任意一项说不清，禁止实现新布局、禁止临时发明面板、禁止用“看着能放下”作为理由。
- 当用户要求“参考成熟实现”时，优先复用当前项目内已经验证过的壳层家族，例如 `PromptOverlay`、`HandArea`、`MeFirstOverlay` 这类已经证明过的模式；若没有可复用家族，先补来源，不得先做。
- 这类来源必须同时落到可回查证据和真实截图，不得只写口头总结。
- 正式验收时还必须证明两件事：① 当前只有一组主操作焦点；② 临时 UI 不会在交互中侵入主交互槽位。任一不成立，都不能收口。

### 4.11 用户可见文案禁止流程黑话

- 面向玩家的主 UI 文案，禁止直接暴露实现层或审查层黑话，例如 `一级/二级`、`pending`、`fallback`、`待结算`、`后处理`、`source/target`、`交互壳层` 这类只对程序员有意义的词。
- 如果领域模型里确实存在这些内部状态，UI 必须翻译成玩家此刻要做的动作或看到的结果，例如 `选择目标`、`决定是否占领`、`退回相邻友方区域`，而不是把内部状态名原样贴上去。
- 判断标准不是“这个词在代码里是不是准确”，而是“一个第一次玩的人看到这句会不会立刻知道自己该做什么”。答不上来，就不允许上主 UI。
- 黑话判定不能退化成固定黑名单。即使文案里没有出现 `pending/source/target` 这些词，只要整句话本质上是在把内部字段直接拼给玩家，例如 `源区 A · 可选目标 2 · 压力 3`、`阶段完成后进入下一步`、`目标选择中` 这类“开发视角句子”，一样按不合格处理。
- 玩家可见文案和内部验收问题必须分层：主 UI 文案写游戏内对象、动作和能力名；规则原文只放在能力原文句、规则书、剧本书或帮助层。验收问题只放在测试、审查或截图核验文档里，用来判断画面是否可操作，不得改写成上屏模板。
- AI 过程话术、验收口令和给助手的指令不得进入玩家 UI。像“看清后可关闭”“阅读后关闭”“如果有就给我看图”“确认一下是否受影响”这类句子只能留在对话、测试或审查记录里；进入玩家 UI 前必须改成玩家动作短语，例如“关闭特写”“继续”“返回牌桌”。这里的玩家 UI 包括可见文本、按钮 title、aria label、sr-only、状态播报和截图标签；不能把看不见的无障碍文本当作内部记录偷塞规则外信息。这条只管玩家文案，不允许被解释成“所有特写都必须手动关闭”。
- 审查结论不得伪装成玩家提示。像“上屏 / 不上屏 / 前景 / 不暴露 / setup 队列 / 公开状态墙 / 验收是否通过”这类用来约束实现的判断，只能写在测试、规范或审查记录的反例或禁词清单里；玩家主 UI 只能改写为玩家动作短语，例如“打开剧本书”“继续牌桌”“关闭特写”。“公开读英雄介绍 / 设置”“不要公开谁是叛徒”“之后各自阅读自己的目标 / 秘密规则”这类规则执行细节只能放在规则书、剧本书、帮助层或测试断言里，不能作为常驻牌桌 UI。
- 规则能力摘要不得压缩成内部状态句。像 `叛徒忽略事件` 这种把规则角色、内部条件和动作揉在一起的短句，不能直接出现在按钮、小字状态、结果摘要或无障碍文本里；按钮写玩家动作（如 `跳过事件`），结果写发生了什么（如 `没有抽取或结算事件卡`），规则解释只放到规则书、剧本书或帮助层。
- 能力触发横幅默认写成 `能力名：规则原文或原文摘句`，例如 `血腥急袭：可以对本单位造成 1 点伤害以将其推拉 1 格`。如需补当前选择态，只补短状态或按钮，不展开成说明清单。
- 交互家族差异写在 `design-system/game-ui/source-families.md`；单游戏 workflow 只引用对应家族和本条文案总原则，不重复维护同一套文案规则。
- 设计或审查时，优先把动作提示写成玩家看得到的对象与动作，例如 `选择当前行动`、`从这里出发调兵`、`战后决定是否占领`；不要把“因为代码里正好有 source / target / restriction / count”当成直接上屏的理由。

### 4.12 指向式引导必须同时满足“全部目标高亮 + 明显箭头”

- 任何需要玩家在地图、棋盘、战场或牌桌本体上继续点击的步骤，若使用路径引导，必须同时做到两件事：所有合法落点都明确高亮；方向线本身带清晰可辨的箭头头部。
- 只给虚线、描边、发光、编号圆点、路线标签或“看起来像方向”的装饰，不算箭头引导。
- 若地图上还有其它通路文字、边界标签、状态描边会与箭头竞争视觉焦点，必须在该步骤临时降噪，保证玩家第一眼先看到“从哪来、往哪去、哪里能点”。

### 4.13 提示横幅与悬浮说明不得遮挡主对象

- 横幅、tooltip、短说明条、下一步提示、hover 说明默认都属于辅助 UI，只能附着在空余槽位，不能压住主行动控件、玩家信息、手牌、牌堆、棋盘主对象或当前唯一可点击入口。
- 只要提示层与主对象发生覆盖冲突，默认优先移动提示层、缩短文案、改为侧向附着或切到固定槽位；不得要求用户“自己挪开看”或靠 hover 细看。
- 看图验收时，若提示层已经出现，但主对象被盖住、裁掉或阅读路径被打断，直接判为不通过。

## 5. 无障碍要求

### 5.1 必须遵守

- 颜色对比度 ≥ 4.5:1（正文）
- 可交互元素最小 44x44px
- 键盘可导航（Tab 顺序合理）
- Focus 状态可见

### 5.2 推荐

- 重要信息不仅靠颜色区分
- 支持屏幕阅读器（aria-label）
- 动画可关闭

## 6. 风格引用

本规范不限定具体视觉风格。根据游戏类型选择合适的风格：

| 风格 | 适用场景 | 规范文件 |
|------|----------|----------|
| 街机立体 | 休闲、派对、骰子类 | `styles/arcade-3d.md` |
| 战术简洁 | 策略、卡牌对战 | `styles/tactical-clean.md` |
| 经典羊皮纸 | 复古、桌游模拟 | `styles/classic-parchment.md` |

游戏可以：
1. 直接引用某个风格
2. 基于风格做专属覆盖
3. 创建全新风格

## 7. 反模式 (Anti-Patterns)

| ❌ 禁止 | ✅ 应该 |
|--------|--------|
| 无 hover 反馈的可点击元素 | 所有可点击元素有 hover 变化 |
| 瞬间状态切换 | 使用 transition 过渡 |
| `transition-all` | 指定具体属性 |
| 动画 width/height | 动画 transform/opacity |
| 禁用元素仍有交互动画 | 禁用时移除动画 |
| 颜色是唯一状态区分 | 结合形状/图标/文字 |
| 无 cursor-pointer | 可点击元素加 cursor-pointer |

## 8. 快速检查清单

开发游戏 UI 时检查：

- [ ] 所有按钮有 hover + press 反馈
- [ ] 禁用状态视觉明显
- [ ] 动画只用 transform/opacity
- [ ] 动画时长在合理范围
- [ ] 当前回合/阶段清晰可见
- [ ] 可交互元素有 cursor-pointer
- [ ] 合法下一步在首屏可被直接发现，不会看起来像卡死
- [ ] 颜色对比度达标
- [ ] 支持键盘导航
