# 游戏 UI 交互规范 (Game UI Interaction Principles)

> **核心理念**：游戏感 = 即时反馈 + 状态清晰 + 操作愉悦
> 
> 本规范定义**交互原则**，不限定具体颜色/风格。视觉风格见 `design-system/styles/`。

---

## 1. 交互反馈原则

### 1.1 即时反馈 (Immediate Feedback)

**所有可交互元素必须有反馈**，让玩家知道"我的操作被接收了"。

| 交互类型 | 必须反馈 | 可选增强 |
|----------|----------|----------|
| Hover | 视觉变化（亮度/颜色/边框） | 轻微位移、光晕 |
| Press/Tap | 缩放或位移 | 音效、涟漪 |
| 禁用点击 | 无反馈 + 视觉暗淡 | 抖动提示"不可用" |
| 长按 | 进度指示 | 震动反馈 |

**反馈时机**：
- Hover/Press 反馈必须 < 100ms（感知即时）
- 状态切换动画 150-300ms（感知流畅）
- 复杂动画 300-500ms（感知完整）

### 1.2 状态清晰 (State Clarity)

玩家必须能**一眼区分**元素的当前状态：

| 状态 | 视觉特征 | 实现方式 |
|------|----------|----------|
| 可交互 | 明显可点击 | cursor-pointer + 视觉提示 |
| 悬停中 | 高亮/突出 | 亮度提升、边框、阴影 |
| 按下中 | 下沉/收缩 | scale 或 translate |
| 选中/激活 | 持续高亮 | 颜色变化、边框、图标 |
| 禁用 | 明显不可用 | 降低透明度、灰度、去除阴影 |
| 加载中 | 进行中提示 | spinner、骨架屏、进度条 |

### 1.2A 用户友好底线 (Never Looks Dead)

**合法状态不能长得像卡死。** 只要当前仍有合法下一步，玩家必须能在首屏直接看出“接下来做什么”。

最低要求：
- 若只剩一个合法主动作，UI 必须把该动作做成显式可发现入口，或给出紧贴该入口的短提示。
- 若存在多个合法候选，候选本体必须可见，且能一眼看出它们就是这一步的操作对象。
- 若当前是等待别人、等待 AI 或等待系统推进，必须明确显示等待归属，不能让等待态和死页面长得一样。
- 空态、开局态、等待态、终局前临门一脚这类“容易像没内容”的状态，默认都属于高风险态，必须单独设计可继续性。

禁止：
- 规则上还能继续，但首屏像“什么都没有，也不知道点哪里”。
- 合法等待态没有任何等待归属，用户只能猜是卡住还是在等别人。
- 关键主操作只能靠 hover、经验、隐藏热区或测试人员记忆才能发现。

### 1.3 操作愉悦 (Satisfying Interaction)

**游戏感的核心**：让玩家觉得"点这个按钮很爽"。

实现手段（按效果排序）：
1. **物理感**：按钮有"厚度"，点击有"下沉"
2. **音效配合**：点击、拖拽、放置有声音
3. **动效强化**：成功操作有庆祝动画
4. **触觉反馈**：移动端震动（可选）

## 2. 动画规范

### 2.1 时长标准

| 场景 | 时长 | 缓动函数 |
|------|------|----------|
| 微交互（hover/press） | 100-200ms | ease-out |
| 状态切换 | 200-300ms | ease-in-out |
| 元素进入/退出 | 300-400ms | ease-out |
| 复杂动画（翻牌/掷骰） | 400-800ms | spring/bounce |
| 全屏转场 | 300-500ms | ease-in-out |

### 2.2 性能规则

**必须遵守**：
- 只动画 `transform` 和 `opacity`（GPU 加速）
- 禁止动画 `width`、`height`、`margin`、`padding`
- 禁止 `transition-all`，必须指定具体属性
- 尊重 `prefers-reduced-motion`

**Framer Motion 推荐配置**：
```tsx
// 标准弹簧
const spring = { type: "spring", stiffness: 300, damping: 25 }

// 快速响应
const snappy = { type: "spring", stiffness: 500, damping: 30 }

// 柔和
const gentle = { type: "spring", stiffness: 200, damping: 20 }
```

### 2.3 禁用状态动画

禁用元素**不应有交互动画**：
```tsx
whileHover={disabled ? undefined : { scale: 1.02 }}
whileTap={disabled ? undefined : { scale: 0.98 }}
```

## 3. 组件交互模式

### 3.1 按钮 (Button)

**必须**：
- 有 hover 反馈
- 有 press 反馈（缩放或下沉）
- 禁用时视觉明显不同
- 加载时显示 spinner 并禁用

**推荐**：
- 主要操作按钮有"厚度感"（底部阴影 + 点击下沉）
- 危险操作有确认步骤

### 3.2 卡牌 (Card)

**可选中卡牌**：
- Hover：轻微上浮 + 边框/光晕
- 选中：持续高亮 + 选中标记
- 禁用：灰度 + 降低透明度

**可拖拽卡牌**：
- 拖拽时：提升 z-index + 阴影增强
- 放置时：有落地动画
- 无效放置：回弹到原位

### 3.3 面板 (Panel)

**信息面板**：
- 半透明背景 + 模糊（可选）
- 不遮挡关键游戏区域

**模态面板**：
- 有遮罩层
- 支持点击遮罩关闭（可配置）
- 进入/退出有动画

### 3.4 资源指示器 (Resource Indicator)

**数值变化**：
- 增加：绿色闪烁 + 数字上浮
- 减少：红色闪烁 + 数字下沉
- 变化动画 200-400ms
- 结算计分：如果用户要求“像结算/跳分/计分动画”，必须让数字从旧值或 0 跳到目标值，并提供过程态截图；只把最终分数变大不算计分动画。

## 4. 游戏特有交互

> 当任务涉及主交互壳层、prompt、waiting、手牌区、右侧 rail、中央响应层时，先看 [source-families.md](D:/gongzuo/webgame/BoardGame/design-system/game-ui/source-families.md) 选择批准家族，再决定是否需要新模式。

### 4.1 回合/阶段指示

- 当前阶段必须**视觉突出**
- 阶段切换有过渡动画
- 玩家回合有明确提示（颜色/动画/音效）

### 4.2 选择与确认

**单选**：点击即选中，再次点击取消
**多选**：点击切换选中状态
**确认操作**：选择后需要额外确认按钮

### 4.3 拖放交互

- 可放置区域有视觉提示
- 拖拽过程中显示预览
- 无效放置有反馈（抖动/回弹）

### 4.4 唯一下一步必须有常驻明文入口

- 当某一步是玩家当前唯一可继续的下一步时，界面必须提供常驻的显式入口。
- 这个入口必须直接落成明文按钮、横幅按钮组、确认条或等价 CTA，让玩家一眼知道“下一步点这里”。
- 关键推进步骤不得只靠 hover、tooltip、透明热区、地图隐式点击区或“点盘面试试看”这类猜测式交互承接。
- 如果主视图里还保留原始热区，它也只能作为附加入口，不能成为唯一入口。
- CTA 文案必须直接说明动作与对象，例如“点击轮盘按钮推进回合”“确认并进入棋盘”，不能只写抽象名词。

### 4.5 消耗型动作必须先显式选择并允许取消

- 任何会消耗手牌、资源、部队、人口，或会触发不可逆提交的动作，默认都必须先进入显式选择态，不能在第一次点击动作按钮时直接吞掉成本。
- 显式选择态至少要同时提供：当前动作名、需要支付的成本、已选内容、确认执行入口、取消当前动作入口。
- 若成本来自可枚举对象，例如手牌、资源牌、候选部队，玩家必须能逐项选择与反选，不能由系统静默替玩家自动决定“前几张”“默认几张”。
- 取消入口必须把本次临时选择清空，并允许玩家回到未提交状态改选动作或直接放弃。

### 4.6 共享证据截图必须中文命名且直接表达含义

- 凡是用于共享、汇报、验收、回归对照的关键证据截图，文件名必须使用中文；不得只用英文、拼音、内部字段名、`current`、`debug`、`before-click`、`after-action` 这类只能让实现者自己看懂的命名。
- 文件名至少要同时表达三个信息：当前页面或阶段、交互对象或动作、截图处于动作前/动作中/动作后哪一种状态。推荐格式为 `序号-页面或阶段-动作对象-状态.png`。
- 如果截图承接的是弃牌、支付、确认、取消、目标选择这类关键交互，文件名必须直接出现对应中文词，例如 `弃牌选择`、`确认执行`、`选择目标`；不得让读图者再去猜“哪张才是这一步”。
- 同一流程目录内不得长期并存两套语义重叠但命名不同的截图；一套新命名生效后，旧编号、旧英文名、重复语义截图必须清理或迁走，避免目录本身再次变成歧义源。
- 联机截图文件名除阶段与动作外，还必须表达**视角归属**。如果是固定玩家流程，文件名里要明确写 `大明视角 / 房主页 / 接收方页` 之类 viewer 身份；如果是多席位对照，必须把每张图各自标明 `蒙古页 / 后金页 / 发送方页`，不得再用会把不同 seat 页面混成一个用户流程的命名。
- 当验收目标是“固定某个玩家端连续体验”时，整条截图链必须来自同一 viewer 页面；中途切到别的 seat 页面拍图，再把结果放回这条链里，直接判截图证据无效。

### 4.7 用户可操作 UI 必须占有固定槽位

- 任何承担真实点击、确认、选择、取消、继续推进职责的 UI，都必须有固定槽位；不得随着提示块、说明块、日志块、状态块的出现而被重新挤位、下推、横向压窄或部分移出视口。
- 如果本轮只是给排名、结算、状态条补王冠、金银铜、徽章或数值动画，必须保留原排名/牌桌/手牌/中央牌区槽位；禁止把“增强结算表现”升级成“重做终局布局”。
- 固定槽位至少要能回答三件事：入口长期停在哪里、该槽位由谁保留、哪些元素禁止侵入。没有这三个答案时，不得直接实现新的交互布局。
- 常驻操作栏、手牌区、底部 dock、右侧 rail、中央 modal、底部 prompt 条属于可复用槽位家族；新交互默认先复用既有槽位，不得临时在地图上、牌面上或 HUD 空隙里再发明一块“差不多能放”的面板。
- 牌桌/卡牌类游戏里，`摸牌`、`确认选择`、`确认弃置`、`结束回合` 这类反复点击的主动作，默认固定在**右侧偏下动作槽**；禁止放进顶部状态轴、标题条、左上统计角或其它高移动成本区域。顶部区域只负责状态，不承接这类高频主点击。
- 固定槽位在正式实现前必须落成 `主交互对象 / 固定槽位 / 让位顺序 / 禁止侵入对象 / 来源家族` 五联单；没有五联单，就不能宣称“这块 UI 已经有合同”。
- 验收必须覆盖交互前、交互中、交互后 3 个时刻，证明主交互槽位没有漂移、没有被顶走，也没有留下抢位残影。

### 4.8 瞬时面板不得抢占另一块可操作 UI

- 弃牌确认、目标选择、响应窗口、步骤提示、检查面板这类瞬时 UI，只能进入自己的交互槽位、overlay 或 modal；不得靠插队进 DOM 流把另一块主交互 UI 顶走。
- 如果某个瞬时面板只是补充说明某块现有交互，例如“先在手牌里选牌，再在右侧确认”，它必须附着在对应主交互槽位附近，且主入口仍保持原位可见。
- 当屏幕空间不足时，优先让位对象是说明、日志、帮助、提示、次级状态块；不得先压缩按钮点击区、手牌点击区、地图主判断区或当前唯一下一步入口。
- `waiting`、`hint`、`confirm strip`、流程横幅、短提示条都属于瞬时 UI；它们只能作为附着提示，不得侵入底部手牌槽位、右侧动作槽位或中央主选择壳层，把界面做成两组并列主入口。

### 4.9 新交互模式必须有可回查来源

- 新增或重做交互模式前，必须先锁定来源，并能说明“参考的是哪一类成熟模式、为什么适合当前语义、当前实现保留了哪些不变量”。没有来源时，不得靠感觉发明新模式。
- 可接受来源包括：当前项目内已验证的成熟实现、用户明确给的参考图/流程图、真实产品截图、规则书/设计稿中已经表达清楚的交互语义。只说“我觉得这样更顺手”不算来源。
- 汇报或规范里必须把来源落成可回查证据，例如文件路径、截图路径、规则章节或设计稿路径；否则后续实现与审查无法判断你到底在复用哪一套模式。
- 来源必须点名到真实家族，而不是抽象说“参考成熟游戏”。当前项目内可直接回查的成熟来源至少包括：`src/games/smashup/ui/HandArea.tsx` 的底部常驻手牌槽位、`src/games/smashup/ui/PromptOverlay.tsx` 的底部非阻塞卡牌查看/选择面板、`src/games/smashup/ui/MeFirstOverlay.tsx` 的中央 ownership/waiting shell、`src/games/smashup/Board.tsx` 中 `activePromptSurface` 的单一承接面路由。

### 4.10 主交互壳层必须先锁五件事

- 任何会承载真实点击、确认、选择、取消、推进的 UI，在动手前必须先锁定五件事：`主交互对象`、`固定槽位`、`让位顺序`、`禁止侵入对象`、`来源家族`。
- `主交互对象` 指这一步真正要被用户操作的对象本体，例如手牌、目标、轮盘、基地或候选卡；`固定槽位` 指这一步长期停留的视觉区域；`让位顺序` 指当空间不足时优先退场的对象；`禁止侵入对象` 指哪些临时 UI 不得顶走它；`来源家族` 指本轮复用的成熟承载方式。
- 如果五件事里任意一项说不清，禁止实现新布局、禁止临时发明面板、禁止用“看着能放下”作为理由。
- 当用户要求“参考成熟实现”时，优先复用当前项目内已经验证过的壳层家族，例如 `PromptOverlay`、`HandArea`、`MeFirstOverlay` 这类已经证明过的模式；若没有可复用家族，先补来源，不得先做。
- 这类来源必须同时落到可回查证据和真实截图，不得只写口头总结。
- 正式验收时还必须证明两件事：① 当前只有一组主操作焦点；② 临时 UI 不会在交互中侵入主交互槽位。任一不成立，都不能收口。

## 5. 无障碍要求

### 5.1 必须遵守

- 颜色对比度 ≥ 4.5:1（正文）
- 可交互元素最小 44x44px
- 键盘可导航（Tab 顺序合理）
- Focus 状态可见

### 5.2 推荐

- 重要信息不仅靠颜色区分
- 支持屏幕阅读器（aria-label）
- 动画可关闭

## 6. 风格引用

本规范不限定具体视觉风格。根据游戏类型选择合适的风格：

| 风格 | 适用场景 | 规范文件 |
|------|----------|----------|
| 街机立体 | 休闲、派对、骰子类 | `styles/arcade-3d.md` |
| 战术简洁 | 策略、卡牌对战 | `styles/tactical-clean.md` |
| 经典羊皮纸 | 复古、桌游模拟 | `styles/classic-parchment.md` |

游戏可以：
1. 直接引用某个风格
2. 基于风格做专属覆盖
3. 创建全新风格

## 7. 反模式 (Anti-Patterns)

| ❌ 禁止 | ✅ 应该 |
|--------|--------|
| 无 hover 反馈的可点击元素 | 所有可点击元素有 hover 变化 |
| 瞬间状态切换 | 使用 transition 过渡 |
| `transition-all` | 指定具体属性 |
| 动画 width/height | 动画 transform/opacity |
| 禁用元素仍有交互动画 | 禁用时移除动画 |
| 颜色是唯一状态区分 | 结合形状/图标/文字 |
| 无 cursor-pointer | 可点击元素加 cursor-pointer |

## 8. 快速检查清单

开发游戏 UI 时检查：

- [ ] 所有按钮有 hover + press 反馈
- [ ] 禁用状态视觉明显
- [ ] 动画只用 transform/opacity
- [ ] 动画时长在合理范围
- [ ] 当前回合/阶段清晰可见
- [ ] 可交互元素有 cursor-pointer
- [ ] 合法下一步在首屏可被直接发现，不会看起来像卡死
- [ ] 颜色对比度达标
- [ ] 支持键盘导航
