# 七大恨 UI 设计规范

> 游戏类型：历史题材、卡牌驱动、地图区域控制、多人桌游  
> 当前阶段：新游戏前置设计与工具需求记录  
> 适用范围：`qidahen` 的 Board、地图层、HUD、素材录入与移动端适配

## 设计方向

七大恨 UI 必须先参考用户提供的图片素材，尤其主地图图。当前已识别的主地图素材为：

```text
D:\gongzuo\webgame\gameasset\七大恨 中文mod\Images\httpcloud3steamusercontentcomugc102169888736738691048B601613C24D513EBDD128FF9BA9B61411C6E82.png
尺寸：1265 x 893
```

这张图不是单纯背景，而是完整桌面版图：左上自带行动轮与检查手牌/弃卡区，右侧有朝鲜牌库/弃牌区与额外卡区，中央有陆地区域、河流、山脉、海域、锚点、城池、VP/同化等标记，底部有野战/攻城流程轨道。后续 UI 设计必须把它当成结构真相源，不得先凭空设计另一张地图。

七大恨不走通用蓝绿扁平后台风，也不走厚重羊皮纸模拟器。界面应像一张可操作的军事态势图：主地图保留原版图的羊皮纸、黑线、朱砂批注和墨色地名，HUD 克制、清晰、低装饰，状态反馈像战报标记与军令签。

推荐基调：

- 主舞台：旧地图纸色、墨线边界、红黑军令标记。
- HUD：深墨、骨白、朱砂、铜金，避免一整屏米色或棕色。
- 图标：优先 lucide 或项目图标体系；军事/人口/控制标记可使用小型 SVG 或位图 token。
- 字体：正文使用项目默认可读字体；标题可使用较窄的宋体/仿宋风格备选，但不能牺牲移动端清晰度。

## 桌面基线

默认桌面参考分辨率为 `1920x1080`。

布局结构：

- 主地图素材本身为主舞台，尽量完整呈现，不拆分朝鲜区、轮盘区或纪年卡区。
- 素材已有 UI 拥有显示所有权：左上行动轮盘、左侧检查/年中/新年框、右侧朝鲜牌库/弃牌槽、右下纪年卡槽、底部野战/攻城流程轨都不再另做一套独立 HUD。
- 顶部只放极窄状态 chip，用于年份、当前势力、当前阶段这类素材未直接表达的状态；不要做流程提示条。
- 底部或侧边只放手牌、当前卡牌焦点与当前需要玩家点击的最小操作，不重复地图上已有的轮盘/流程/卡槽。
- 地图上的单位、城市、人口、控制标记必须挂在地图坐标系内，随地图缩放和平移同步移动。

### UI 轻重与去重

- **地图本体最重**：区域、轮盘、朝鲜牌库/弃牌、纪年卡、战斗流程等已经在主地图素材中出现的内容，只允许轻量增强。
- **当前交互次重**：只突出当前必须操作的对象。七大恨是卡牌驱动，手牌与当前选中卡牌应是最主要的数字 UI；左上轮盘已经承担轮盘行动显示，底部不应再出现第二个轮盘行动解释器。
- **辅助信息最轻**：区域详情、完整手牌、战斗详情默认折叠或浮出，不能占整列或压过地图；行动记录默认不出现在主界面。
- **一个概念只出现一次**：同一张牌库、同一个轮盘、同一个纪年卡区、同一个当前行动，不得同时在地图上和 HUD 里各出现一份。
- **原图文字清晰时不再贴同名标签**：朝鲜牌库、朝鲜弃牌、行动轮盘等若在地图素材中可读，不额外增加重复标签。
- **UI 文案只写名词/动作/状态**：禁止在界面里写规则解释句。按钮叫“结束回合”即可，不解释结束回合的含义。
- **不显示流程说明**：不要在 UI 指导图里写“检查手牌 → 转动轮盘 → 手牌行动 / 轮盘行动”这类流程提示；原图已有流程轨，数字 UI 只显示当前状态。
- **保真草稿优先用素材截图，不优先用 text-to-image**：如果要求“按原地图素材保真生成 UI”，应优先做静态 mockup/screenshot；只有当用户只要风格图或 moodboard 时才用生成图。

右侧信息区优先级：

- 七大恨主界面默认不显示行动记录。它会抢占地图和底部动作空间，除非用户明确要求调试/回放/争议核对，否则不出现在第一版 UI 草稿。
- 只有进入回放、审计、争议确认等模式，才允许展开行动记录。
- 待处理效果、战斗/结算面板默认临时浮出，收口后关闭。

底部空间优先级：

- 第一优先：不遮挡主地图已有底部流程轨和纪年卡得分轨。
- 第二优先：手牌入口、3-5 张可读手牌或 1 张焦点卡较大预览。卡牌不能小到无法看出类型与作用。
- 第三优先：当前需要玩家点击的最小操作，如“手牌行动”和小型“结束回合”按钮。
- 不允许：行动记录面板、完整规则摘要、第二个轮盘行动面板、巨型结束回合面板。
- 底部操作区应尽量做成左下或右下角落浮岛，宽度小于屏幕四分之一，不横跨整条底边。
- 首版 UI 草稿不展示完整手牌卡墙；手牌默认折叠为入口、张数和少量小缩略 chip，避免压住地图底部。
- 原图已有野战/攻城流程轨，禁止重绘为独立数字战斗面板；最多在原轨上加一个小阶段标记。

主舞台要求：

- 地图使用 `MapContainer` 类交互：拖拽平移、滚轮缩放、双指缩放、重置视角、聚焦目标。
- 地图区域不按网格处理，使用多边形区域、邻接边、关键点位。
- 地图层与 hit-test 层共享同一套归一化坐标，禁止 UI 层另写一套坐标。
- 原图中已有的行动轮、牌库框、流程轨道默认作为地图/桌面对象的一部分处理；若后续为了可读性把它们 UI 化，也必须先保留原始空间关系，再用 overlay 增强，不得直接删掉。

## 移动端策略

七大恨属于地图主导游戏，默认移动策略应选：

- `mobileProfile: 'landscape-adapted'`
- `preferredOrientation: 'landscape'`
- `mobileLayoutPreset: 'map-shell'`

移动端主验收不是竖屏单列化，而是手机横屏下保持地图为主：

- 手机横屏采用同一套 Board 主体，地图独立拖拽缩放，HUD 通过 rail/dock/overlay 让位。
- 地图不可要求用户长期依赖浏览器页面缩放；游戏内必须提供自己的地图缩放。
- 常驻 HUD 压缩为左右边缘抽屉和底部行动 rail。
- 需要 hover 查看详情的对象，移动端改为长按或点选后打开检查浮层。
- 所有关键触控目标不小于 `44px`；地图区域本体如果小于触控目标，需要命中扩展但不能改变区域几何真值。

验收视口：

- 桌面：`1920x1080`
- 手机横屏：优先使用项目移动端横屏基线，若走 E2E 采样可使用 `936x432`
- 若用户明确要求竖屏可读，再另做竖屏降级视图；默认不把竖屏作为主玩法基线。

## 地图区域数据合同

七大恨地图必须先明确区域合同需求，再进入 Board 实现。前置阶段记录字段、待标注对象和素材依据；精确点位与区域边界应在真实 Board/地图壳初版可运行后，用嵌入式校准模式完成。

推荐文件：

```text
src/games/qidahen/config/mapRegions.ts
public/game-data/qidahen.map-regions.json
```

最低字段：

```ts
interface QidahenMapRegion {
  id: string;
  name: string;
  type: 'region' | 'city' | 'route' | 'offmap';
  polygon: Array<{ x: number; y: number }>;
  labelPoint: { x: number; y: number };
  stackPoints: Array<{ id: string; x: number; y: number; role: 'army' | 'city' | 'population' | 'control' | 'marker' }>;
  adjacentRegionIds: string[];
}
```

坐标要求：

- 所有坐标均为地图原图归一化坐标，范围 `0-1`。
- 区域边界用多边形，不用矩形近似长期替代。
- 单位堆叠点、城市点、人口点、控制标记点必须独立记录，不能只依赖区域中心。
- 邻接关系必须显式导出，不能在运行时靠多边形相交临时推断。

## 区域/坐标校准工具时机

当前不应先做脱离游戏运行时的独立区域工具。推荐路线：

1. **前置阶段**
   - 记录需要标注的区域、多边形、城市点、人口点、控制点、军队堆叠点和邻接关系。
   - 先产出 `QidahenMapRegion` 合同与空/粗略数据结构，保证 Board 实现知道要消费什么数据。
2. **Board 初版阶段**
   - 先把主地图放进真实 `map-shell`，跑通拖拽、滚轮缩放、双指缩放、重置视角和归一化坐标换算。
   - 地图、overlay、hit-test、实体堆叠点必须共享同一套坐标系。
3. **嵌入式校准阶段**
   - 在七大恨真实 Board 或 MapContainer 中加入开发编辑态，类似 SummonerWars 的游戏内地图模式。
   - 直接在真实缩放/拖拽/资源加载环境下标注和校准，避免独立页面坐标与运行时坐标不一致。

最终校准能力至少包括：

- 导入地图图片。
- 标注区域多边形。
- 标注单位堆叠点、城市点、人口点、控制点。
- 为区域填写 `id/name/type/adjacentRegionIds`。
- 导出 JSON，作为后续 `qidahen` 地图配置的真相源。

独立页面只允许作为临时低保真/离线数据采集方案；如果使用，必须在证据里标注“临时工具”，并在真实 Board 内复核后才能把数据作为最终运行时真相源。

工具产物必须能回溯：

- 使用的地图图片文件名。
- 图片原始宽高。
- 每个区域的点位和邻接关系。
- 每个 stack point 的用途。

## 交互模型

地图对象：

- 点击区域：选中区域并显示该区域可执行命令。
- 点击单位堆叠：打开单位堆叠面板；多单位时不要直接展开全屏列表。
- 长按/放大镜：查看区域、单位、卡牌详情。
- 拖拽地图：只移动视角，不触发区域选择；需要阈值区分点击和拖拽。
- 行动记录：默认移出主界面；需要回放或争议核对时通过临时浮层打开，不能常驻占用地图或底部空间。

卡牌与命令：

- 手牌默认在底部 rail；移动端可折叠成手牌抽屉。
- 打牌后进入“选择区域/目标/单位”模式，地图区域高亮来自领域层可选目标，不在 UI 层复制判定。
- 所有确认命令必须能显示代价、目标、结算摘要。

状态反馈：

- 可选区域：朱砂描边 + 半透明填充。
- 当前选中：铜金描边 + 标签升层。
- 禁用/不可达：降低地图标记亮度，不改变地图原图颜色。
- 战斗/结算：在地图目标附近短暂显示战报标记，同时在右侧日志落正式记录。

## 素材清单

新游戏开工前应主动确认下列素材：

- 规则书 PDF/Markdown。
- 主地图原图，最好无透视、无裁切、边界完整。
- 区域名称、边界、邻接关系说明；若没有，先记录待标注合同，等真实 Board 初版可运行后用嵌入式校准模式人工标注。
- 单位木块/军队 token 正反面或颜色区分。
- 人口、控制、城市、战斗、叛乱等标记图。
- 卡牌正面、牌背、帮助卡、玩家面板、缩略图。
- 若有隐藏信息，需确认哪些素材只对所属玩家显示。

## image2 / 图像生成使用口径

可以用图像生成产出 UI 概念图或缺失的临时视觉占位，但不能把生成图当成规则真相源。建议用途：

- 生成一张 `1920x1080` UI moodboard，帮助确定地图与 HUD 气质。
- 生成临时 token 占位图，等待真实素材替换。
- 生成教程/大厅缩略图草案。

禁止用途：

- 根据生成图臆造地图区域边界。
- 用生成的卡面文字替代规则书或真实卡牌。
- 未经用户确认，用生成素材覆盖用户提供的正式素材。

## 后续实现检查

- Board 根容器不得写死 `100vh/100dvh`，必须跟随 `map-shell`/页面壳层。
- 地图平移缩放层只能有一套主真值，HUD/浮层必须与地图坐标换算清晰分离。
- 区域命中、单位摆放、邻接判断必须使用同一份地图配置。
- 移动端截图必须证明地图没有缩在左上角，HUD 与地图处于正确坐标关系，且没有被误改成窄布局。
