# BoardGame AI 系统规则

本文件经 `CLAUDE.md` 的 `@import` 强制载入 Claude Code 上下文；其它宿主读完 `.spec/AGENTS.md` 后也必须读取本文件。
这里只写必须遵守的硬边界；怎么做放 `knowledge/standards/` 或 `skills/`。

## 体系边界

- `.spec/` 是项目 AI 规范的唯一真相源；宿主入口、旧路径和生成目录只能适配或跳转，不能维护规则正文。
- 项目实际执行需要的 skill 正文必须放在 `.spec/skills/`。禁止把项目 skill、宿主适配入口或协作者默认流程指向个人系统 skill 目录、个人用户目录或其它仓库外 skill；经确认只属于本项目的系统 skill 迁入项目后不再保留为个人系统层正文，本项目用到但仍需跨项目保留的系统 skill 复制固定副本到 `.spec/skills/`，以项目副本作为本项目唯一执行入口。
- 产品任务编排不属于 `.spec/`；它不参与 AI 规范加载、迁移或校验。`.spec/` 也不建立第二套产品任务清单。

## 行为边界

- 会改变代码、配置、规则数据、测试、正式文档或交付结果时，先按 `skills/before-you-code` 渐进加载，不能用摘要、历史计划或相似任务替代当前真相源。
- 用户当轮明确的对象、范围、环境和交付级别优先；不得擅自升级到额外重构、发布、删除或验证链路。
- **执行规范与规范维护分开**：`.spec/rules/system.md`、`.spec/AGENTS.md`、`knowledge/standards/` 和具体项目 workflow 负责指导工作；系统 `skill-governance` 负责治理方法与层级裁决，项目 `spec-steward` 负责仓内落地。
- **用户明确指出是通用规范或规范治理问题时先处理执行规范**：保留用户原话，锁定对象、范围、层级和验收口径；在系统 `skill-governance` 完成治理判定或明确“不需更新”前，不得进入领域专项审查，也不能把问题先改写成单游戏、局部实现或测试问题。
- **原话已明确时不得伪装成需求不清**：对象、范围、目标和验收已经明确时，直接进入找源、治理或执行；只有缺少会改变交付物的字段，才允许补证据或问最小问题。
- **执行偏差不得直接归类为“执行不到位”**：至少先排除规范缺失 / 含糊、规范入口错误、规范可被绕过和证据不足；不能证明已排除时，不得使用“单纯执行失误”收口。
- **证据不能越权改变问题对象**：测试通过、截图生成、局部状态改善、结构校验或 evidence 落盘只能证明其直接覆盖的事实，不能把通用规范问题收口成领域问题，也不能单独宣告用户原始目标已解决。
- **网页媒体交付必须走项目网页查看器**：用户要求截图、录屏、GIF、视频或实际动效查看时，必须先按项目 `show-image-to-user` skill 完成 PASS 清单与路径校验，再通过 `scripts/verify/open-verified-image.mjs` 注册并交付 `VIEWER_URL`；不得用系统播放器、裸本地路径、内联预览或其它旁路替代。只有用户明确指定其它查看器，或网页查看器已被证据确认不可用并经用户接受降级时，才允许改用其它通道。
- **规范整理必须先走治理门禁**：详细的原话锁定、唯一主源、逐条处置、批量扫描和四项收口以系统 `skill-governance` 为唯一方法源；完成前不得先改游戏实现、专项测试或 evidence。
- **规范更新后必须回到原问题闭环**：`npm run spec:lint` 只证明规范结构、索引和链接合格；若用户同时要求重审 / 修复，仍须回查原问题对象、实现、配置、测试和 evidence，并分别说明已修复、未证明或仅止血。
- 用户只是追问原因、含义或规范落点时，先解释和归因，不自动实施；是否已授权实施按当前用户指令和 [`conversation-handoff-target-lock`](../knowledge/standards/conversation-handoff-target-lock.md) 判断。
- 目标、词义、入口或验收口径无法唯一定位时，停在定位并补证据或问最小问题；多游戏候选不能靠“更像”、摘要或近期改动代替锁定。具体停手格式和四项锁定表只在 [`conversation-handoff-target-lock`](../knowledge/standards/conversation-handoff-target-lock.md) 定义。
- 任何会改变服务器、CI、发布产物或用户可见结果的任务，必须完成对应的真实外部动作并回查真实结果后才能宣告完成。
- 真实外部动作需要权限时，必须先列出所需权限、作用范围、最小授权方式和失败后的现实后果，并向用户请求。
- 迁移或删除 AI 规范前，必须逐项保留有效内容，并证明新入口可到达；不能按目录新旧、文件数量或“看起来重复”直接删边。
- 同一规则只能有一个可执行正文。其它出现位置必须是导航、适配、链接、裁决记录或证据，不能成为平行规范。
- 同一代码职责只能有一个正式 owner。规则结算、读模型、玩家交互、UI 装配、传输恢复、反馈训练、测试夹具和项目脚本等职责，不得同时保留旧实现、共享默认、游戏特化和新增实现多套并行链路。
- 不得用桥接层、中转层、包装层、兼容壳、浅模块、空壳系统、巨型测试套件或第二套状态掩盖职责没有收口；设计模式、反模式和防护性架构裁决见 [`knowledge/standards/code-design.md`](../knowledge/standards/code-design.md)。
- 修改代码、规范、测试或校验时遵守最小必要改动：`最小` 指只做达成本轮目标、修正已证实职责错误、消除已证实漂移或提升当前能力可扩展性所必需的改动，不等于改得越少越好。能减少重复真相、明确职责边界、让已有流程自然扩展的重构属于必要改动；为了理论上可能发生但没有现实入口或证据的问题新增兜底、门禁、状态、测试、文档层或第二套真相，属于非必要改动。

## 校验

完成 AI 规范结构改动后运行 `npm run spec:lint`。它验证结构、索引和链接；不要求 AI 伪造“已阅读回执”。
框架、目录、职责或模块 owner 的代码重构前，必须先完成规范单一口径、索引同步和 `npm run spec:lint`。
