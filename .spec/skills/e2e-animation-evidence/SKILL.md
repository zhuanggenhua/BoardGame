# E2E Animation Evidence

把连续动效的“跑过了”收敛成可复核的真实动态证据。该 skill 是项目内动效录制与 GIF 证据的唯一执行入口；它不替代：

- [`animation-effects`](../../knowledge/standards/animation-effects.md)：定义 FX 的职责、时序和表现质量；
- [`e2e-verification`](../../knowledge/standards/e2e-verification.md)：定义真实入口、状态注入、截图资格和 E2E 证据边界；
- [`ui-audit-loop`](../ui-audit-loop/SKILL.md)：负责玩家视角的图面 / 动效 PASS 或 REVISE；
- [`show-image-to-user`](../show-image-to-user/SKILL.md)：负责把已通过验收的 GIF / 录屏 / 图片交给用户查看。

## 唯一真相源与吸收边界

- 本文件是 BoardGame 项目动态证据录制的 `canonical-source`。
- `animation-effects`、`e2e-verification` 和各游戏专项只做入口、适配或证据引用，不复制本文件的完整录制 SOP。
- 当前项目继续使用已有 Playwright runtime、正式游戏路由、现有截图 / evidence 目录和本地网页查看器；不因为吸收外部方法而新增第二个测试框架、第二套录制器或第二个查看器。
- 外部候选只吸收可迁移的方法：持久浏览器上下文、基于语义状态采集、过程媒体与测试结果绑定、原始帧保留、动态时间保真和失败后可追溯。
- 不吸收外部候选的仓库结构、命令、浏览器插件、UI 组件、临时注入方式或与 BoardGame 现有入口冲突的证据格式。外部候选与吸收裁决见 [`references/absorbed-patterns.md`](references/absorbed-patterns.md)。

## 录制前锁定

开始录制或修改测试前，先按
[`conversation-handoff-target-lock`](../../knowledge/standards/conversation-handoff-target-lock.md) 锁定通用四项前提。本 skill 只补动效专属合同：动作语法、FX cue / tuning、操作者视角、目标视口、证据目录，以及来源 / 过程 / 命中 / 收口四段是否必须自然流程。前提未锁定时，只做定位和证据盘点，不录制、不改实现、不把代表态命名成完整流程。

## 录制合同

### 1. 真实页面与真实动作

- 录制必须来自正式游戏页面，而不是孤立组件、静态 mock、预览页、标注图或只渲染 FX 的诊断页。
- 玩家可完成的动作必须由真实浏览器点击、拖拽、选择和确认产生；测试不能用内部状态直接替玩家完成本轮要证明的决策。
- 状态注入只允许建立与本轮动作无关的前置条件，或控制随机 / 骰子结果本身。注入法师、法术、目标、资源等前置条件时，必须在 evidence 中标为 `representative-state`，不能写成“从新局自然走到攻击”。
- 要证明完整自然流程时，必须从正式入口走到动作发生；要证明特效局部合同时，可以使用正式页面代表态，但标题、manifest 和汇报必须明确是代表态。
- 测试辅助不得给玩家 UI 注入 `source`、`target`、`legal`、`selected` 等解释标签，也不得提供只有测试存在的点击按钮来替代真实对象本体。

### 2. 四段动态证据

每个连续动效至少覆盖同一条动作链的四段：

1. **来源唤醒**：玩家刚完成合法动作，来源对象仍可辨；
2. **过程 / 路径**：能看出对象如何移动、蓄力、投射、斩击、爆发或发生其它规则相关变化；
3. **命中 / 结果**：目标本体、命中反馈、骰子 / 伤害 / 状态结果同时成立；
4. **稳定收口**：残留 ghost、临时高亮、阻塞层和结果层退场，主界面恢复可继续操作。

同格效果可以没有路径段，但不能省略来源、结果和稳定收口。只截“来源出现”和“最终静态结果”不能判为动态证据。

### 3. 独立动作语法覆盖

- 远程攻击和近战攻击必须分别录制、分别等待、分别验收，不能用远程 GIF 推断近战已正确。
- 一个 GIF 只能证明一个连续动作族的一条动作链；召唤、远程攻击、近战攻击、治疗、推斥、传送等不同动作语法必须各自独立录制、独立等待来源 / 过程 / 结果 / 收口、独立生成 GIF 和 PASS 条目，不能把多个动作串在一个混合 GIF 里再宣称“全部动效已覆盖”。
- 选择模式、响应窗口、目标高亮、确认 / 拒绝、阶段推进等没有独立连续运动语义的交互，不强行伪造成 GIF；改用按真实玩家动作顺序排列的静态截图组或短录屏，并在覆盖矩阵中逐项列出触发前、交互出现、玩家提交、结果和收口。
- 普通移动不复用远程攻击 / 飞弹 / 投射物语法；移动是否需要轨迹必须由规则语义和现有 tuning 决定。
- 骰子结果层只表达骰子 / 随机结果；行动、守卫、就绪、资源和其它单位状态继续由具体单位本体、单位附属 token 或玩家板上的正式承载对象表达。`ready / 就绪` 不是骰子内容，也不是全局攻击反馈；截图和断言必须能指出它属于哪一个单位 / 玩家对象。
- 行动 token、守卫 token、资源条、生命值和单位本体不能因为攻击结果层出现而被误读成骰子内容，也不能覆盖骰子、目标或当前合法交互对象。录制前后都要核对层级和几何关系。
- 攻击过程期间，来源和目标本体必须保持可辨；不能因为特效挂载、遮罩、放大卡、骰子或提示卡把正在证明的单位遮住。

## 时间保真

- GIF / 录屏必须保留真实动作的时间比例。截图采样可以降低帧数，但生成 GIF 时不得把所有帧强制改成固定短延时来“看起来完成”。
- 优先使用真实录屏或带时间戳的截图帧；如果从截图帧生成 GIF，帧间延时必须来自实际采样时间，并在 manifest 记录起止时间、帧数和最终时长。
- 证据应能解释最终媒体时长与正式 FX tuning / 页面实际等待之间的关系。若 GIF 只有几帧或明显压缩到无法看清来源、路径、命中和收口，判为证据无效，不得用“测试通过”替代。
- 等待条件必须对应玩家可见状态：来源已出现、过程正在进行、目标本体可见、命中 / 结果已出现、临时层已退场。只等待事件日志、DOM 节点或服务端状态，不足以给媒体命名为“命中”“结算”或“恢复”。
- 物理骰子或其它连续随机表现必须在同一次真实运行中分别采集“滚动中”和“停稳结果”帧，并让断言对应玩家可见的运动 / 稳定状态；只有停稳帧或静态骰面不能命名为物理滚动证据。
- 若当前随机结果是面向全桌公开、会影响后续结算的判定，过程证据必须保留确认中间态和结果层可见性，直到所有真人完成确认；不能在本人确认后直接截稳定收口图。物品或能力只证明结果窗口内存在使用时机；普通物品发现不是判定结果证据，不能混录或替代本流程。

## 录制实现要求

当前 Mage Wars 动效证据默认检查：

- 正式 E2E：`e2e/mage-wars/online-runtime.e2e.ts`
- FX renderer：`src/games/mage-wars/ui/fxRenderers.tsx`
- FX tuning：`src/games/mage-wars/ui/fxTuning.ts`
- 牌桌状态承载：`src/games/mage-wars/Board.tsx`
- 最终媒体查看器：`scripts/verify/open-verified-image.mjs`

修改录制实现时：

- 保留正式页面点击链，先修采集时序，再修 GIF 编码，不要用更快的固定延时掩盖页面动作慢或采样缺段；
- 远程、近战必须有独立的动作入口、过程等待、帧组和 PASS 条目；
- 失败时保留原始媒体 / 运行日志并降级为诊断证据，不能复用旧 GIF 继续宣称当前实现通过；
- 当行动 token、守卫或就绪标记出现在骰子画面附近时，先检查渲染层归属和同帧布局，再决定是拆分层、避让还是暂时降噪；不要把它们改名成骰子内容。

## Evidence 结构

动态 evidence 至少记录：

- 测试文件、测试用例、真实入口和运行时间；
- 动作类型：远程 / 近战 / 移动 / 召唤 / 投骰等；
- `natural-flow` 或 `representative-state`；
- 玩家实际动作；
- 四段媒体文件或 GIF 中对应的帧范围；
- 规则 / cue / tuning 来源；
- 是否看见来源、过程、目标、命中 / 结果和稳定收口；
- 是否存在 token、资源、骰子、提示卡或其它外围 UI 误入结果层；
- 测试结果与媒体路径是否来自同一次运行；
- 尚未覆盖的动作语法或剩余风险。

### 证据运行生命周期

- 常驻证据目录按“游戏 / E2E 文件 / 用例合同”唯一分配，不按每次运行新建一个常驻目录；`runId` 只用于 `_temporary` staging 隔离。
- 录制期间截图、原始帧、GIF、日志和 manifest 必须全部写入同一个 staging；失败、超时、共享 runtime 被占用或断言未完成时只能保留为诊断，不得清空或半写入常驻目录。
- 只有同一次运行完成自动断言、媒体完整性检查和逐张图面复核后，才能把该 staging 原子晋升为常驻证据；旧常驻目录若需替换，先迁到 `history / diagnostic`，不得直接删除后再假装当前运行连续。
- 需要 GIF / 录屏的动效用例必须在录制能力未开启时直接失败，不能让“截图通过、GIF 缺失”的半套产物晋升为 PASS；可选录制只能用于明确标注为静态诊断的用例。
- 任何跨运行拼接（本次截图 + 上次 GIF、本次 manifest + 历史截图、当前代码 + 旧 runtime）都自动降级为未证明；必须整组重跑。

文件名使用玩家能理解的对象和动作，不使用内部状态名冒充画面结论。例如：

- `01-远程攻击-来源唤醒.png`
- `02-远程攻击-飞行过程.gif`
- `03-远程攻击-命中结果.png`
- `04-远程攻击-稳定收口.png`
- `05-近战攻击-完整动效.gif`
- `远程与近战动效-PASS.json`

## PASS 门禁

只有以下条件全部满足，才能把动态证据判为 PASS：

- 真实页面、真实浏览器、真实玩家动作已证明；
- 来源、过程、命中 / 结果、稳定收口四段可见；
- GIF / 录屏时间没有被固定短延时压缩；
- 远程和近战等不同动作语法独立覆盖；
- 目标本体在关键帧可辨，没有被反馈层遮挡；
- 行动 / 守卫 / 就绪等单位状态仍在正确承载对象上，没有混入骰子结果语义；
- 测试结果、媒体、PASS manifest 来自同一次当前运行；
- 当前实现、等待条件或验收口径变化后，旧媒体已降级为历史 / 诊断并重新生成；
- 规则没有声明的效果骰、状态机会或结果层没有出现在媒体与事件链中；有声明的对象与无声明的对象都各有一条直接回归证据；
- AI 已逐张核对原始媒体；用户要求查看时，再通过 [`show-image-to-user`](../show-image-to-user/SKILL.md) 打开最终媒体。

“测试 passed”“GIF 文件存在”“动画容器存在”“截图已落盘”只能证明链路触发，不能单独证明动态表现合格。

## 推荐执行顺序

1. 锁定动作对象、来源、入口、视口和 PASS 清单；
2. 读取正式 FX cue / tuning、真实页面承载和现有 E2E；
3. 先用最窄真实入口复现，确认当前是否真的发生了用户描述的视觉问题；
4. 让录制记录真实时间戳和语义等待点；
5. 分别跑远程 / 近战或其它动作语法；
6. 生成 GIF、原始帧和同次运行 manifest；
7. AI 逐张核对，失败就回到实现或录制等待条件；
8. PASS 后再调用 `show-image-to-user` 的查看器入口交付。
