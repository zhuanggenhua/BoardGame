# Boardgame UI Imagegen

这个 skill 用来把“规则 + 素材”转成可靠的 UI 设计稿前置包，并裁定本轮走 imagegen 位图路线、Open Design artifact 代码设计稿路线，还是 Open Design media 生图路线。目标不是让图更花，而是少做少错：先证明理解了游戏和素材，再进入对应出稿工具。默认不是“一次出完所有图”，而是先过结构，再过布局收敛，再过分界面；风格默认只收成一版，且必须和素材统一，除非用户明确要求才额外做风格分叉。

## 规范来源与职责边界

- 本 skill 是 `workflow`：只承载 BoardGame 生图/设计稿执行步骤、证据块、输入包和返工流程。
- UI 设计原则以 `.spec/knowledge/standards/ui-ux.md` 为 `canonical-source`；UI 改动验收和截图门禁以 `.spec/knowledge/standards/ui-change-gates.md` 为 `canonical-source`。
- 资源和素材链路以 `.spec/knowledge/standards/asset-pipeline.md` 为 `canonical-source`。
- 本 skill 不把这些标准复制成第二份规范；如发现冲突，先改标准文档，再同步本 workflow 的引用或步骤。

## 使用顺序

1. 先读当前项目规范：`AGENTS.md`、`.spec/knowledge/standards/ui-ux.md`、`.spec/knowledge/standards/asset-pipeline.md`。
2. 若是新增游戏，先读 `.spec/skills/create-new-game/SKILL.md`。新增游戏默认建议独立 worktree，但创建、切换或派生分支前必须取得用户当轮明确授权；当任务已进入具体布局、单一风格收敛、玩家关注点排序、proposal/spec/design/tasks 拆分时，必须同步进入 OpenSpec，而不是只把这里当作一份孤立的生图 prompt skill。
3. 读取规则真相源：优先 `docs/games/<gameId>/rule/**`、`docs/games/<gameId>/intake/**` 和该游戏设计前置矩阵；若项目没有这些合同，再读 `src/games/<gameId>/rule/**`；若仍没有 Markdown 合同，回到 PDF/OCR 导出页。不得只因为 `src/` 下没有规则文件就跳过读规则。
4. 读取规则对象素材矩阵或建立本轮最小矩阵：`规则对象 -> 应用素材 -> 当前素材状态 -> 画面表达 -> 是否允许出现`。没有矩阵，不得生成 prompt、HTML 预览或 AI PASS 结论。
5. 打开主地图、主棋盘或玩家面板素材；如果用户给的是本地图片路径，必须看图。大图先降采样或裁局部，再用 `view_image` 看，避免直接打开超大原图。
6. 先输出 UI 元素拆解，再生成 prompt；没有拆解，不要直接生图。
7. 如果用户明确要“生成图 / image2 / UI 指导图”，交付物仍然是 imagegen 概念图；真实素材 mockup/screenshot 只能作为辅助校验和 prompt 参考，不能替代生成图。
8. 如果用户要求保留/使用真实地图或棋盘素材，prompt 必须把“完整地图素材作为结构参考”写清楚；必要时先做 HTML/CSS/React 静态 mockup 辅助定位，但最终仍按用户要求输出生成图。
9. 如果默认 imagegen 路线不可用，而 Open Design 工具链可用，必须自动转入 **Open Design artifact 候选稿路线**，不得停在“缺 imagegen / 缺 API key”。Open Design 候选稿仍必须继承本 skill 的规则重读、素材输入包、出图前硬回执、少边框和 AI 图面核验门禁；只有渲染导出的 PNG/JPG/WebP 或等价图片证据通过 AI 核验后，才允许进入用户验收展示。

### 设计启动门禁（强制）

本 skill 里的“设计”不是从调用 imagegen 才开始。只要开始写布局、风格方向、Open Design brief、HTML/CSS 预览、Design I/O 声明、prompt、截图审计或实现骨架，就已经进入设计动作，必须先过规则与素材前置。

- **先读适用 skill，再出任何布局**：新游戏 / 规则驱动桌游 UI 在写布局、风格、Open Design artifact 或 prompt 前，必须先读取并消费项目 `.spec/skills/ui-design-pipeline/SKILL.md`、`.spec/skills/game-design/SKILL.md` 中 UI / 控制 / 玩家错误相关主题、`.spec/skills/ui-audit-loop/SKILL.md`，再叠加本项目 `.spec/knowledge/standards/ui-ux.md`、`.spec/knowledge/standards/ui-change-gates.md` 和 `design-system/game-ui/MASTER.md`。这些读取不是审图补救步骤，而是设计启动条件。
- **把审计硬失败前置成设计禁止项**：出稿前置包必须把本轮适用的 `REVISE` 条款写成禁止清单，例如重叠 / 裁切 / 漂移、当前结算主体边栏化、目标对象被浮层挡住、按钮不像按钮、玩家不知道下一步点什么、普通蓝圆或无材质占位、同母版权重变化冒充多方案。没有这张清单时，不得生成 Open Design artifact、HTML 预览或位图。
- **先读规则再想布局**：Step 1 的第一步是从本轮刚读取的规则页段 / 合同中抽对象、状态、隐藏信息、操作入口和禁止项；不得先凭桌游经验、旧稿印象或素材外观排版，再把规则补进去。
- **读取动作必须可追踪**：本轮已读规则不能只表现为 artifact 里列了路径、引用了旧矩阵或复述了交接摘要；必须能反查到当前轮次实际打开规则真相源 / 素材合同 / 输入包的动作，或当前轮次重新生成的前置证据文件。若上下文压缩、换会话或切 worktree 后无法确认读取动作，默认重新读取，不得继承“我之前看过”。
- **先锁素材再定视觉主语**：凡是规则对象有正式棋盘、卡牌、角色板、token、骰子、牌背、状态板或 atlas crop，这些素材必须先被登记为主体输入，再决定布局。不能先设计一套框体 / 面板 / 胶囊壳，再把素材当小图标塞进去。
- **风格不得绕过规则 / 素材**：主题、色彩、材质和氛围只能在规则主体和素材职责已经成立之后收敛；如果当前 imagegen 入口不可用，但 Open Design 能把正式素材作为项目内图片、reference sheet、拼接基底或可追溯 crop 使用，必须自动转 Open Design artifact 候选稿；只有 imagegen 和 Open Design 都不能接入正式素材时，才输出 blocked brief。不得用纯 prompt、无素材 HTML/CSS 壳层或手工拼贴补一张“概念稿”。
- **设计声明也要带证据**：`spec/domain/design/components/craft/template/evaluator` 里必须直接引用本轮规则结论和素材账本；没有这些证据的设计声明只能标 `draft-blocked`，不得成为下游 prompt 或实现合同。
- **框体默认无权先行**：除素材自带印刷边、真实交互命中高亮和必要按钮底板外，任何常驻边框 / 面板 / 底板都必须在设计启动时写明现实对象和交互职责；写不出职责就不能进入布局稿。
- **用户标注与桌游物理件守恒**：用户标注图、参考图或当轮点名对象必须先进入规则对象交互权重表。玩家区、计划区、法术书 / 牌库浏览、弃牌堆、骰子、token、状态标记、资源读数、回合命令和等价桌游物理件，默认都要在饱和态设计稿中有可见主体、可读入口或明确恢复方式。不得为了“画面干净”“减少元素”“目标选择态不结算”“先做基础布局”而擅自省略这些对象；若某对象确实与当前阶段互斥、素材 blocked 或只能在后续状态出现，必须在出图前硬回执中写出阶段理由，并在用户明确同意后才可不显示。用户标注里的非规则名称只改变上屏命名，不改变区域和交互意图。
- **启动自证先于设计动作**：开始布局、风格、prompt、Open Design、HTML 预览、AI 核图或实现骨架前，必须先在当前 worktree 的前置包 / prompt brief / 随图审计里写出 `本轮已读 skill / 规范`、`本轮规则来源`、`三条以上画面结论`、`正式素材输入链`、`前置硬失败禁止清单`、`人工验收状态`。缺任一项时，只能补证据或标 `blocked`，不得继续设计。

### 规则与素材前置证据（强制）

- 任何 imagegen prompt、Open Design artifact、HTML/CSS 预览、静态 mockup、AI 图面核验或人工验收候选，开始前都必须先形成本轮前置读数：`规则真相源已读文件/页段`、`规则对象素材矩阵`、`可见对象准入状态`、`禁止出现在画面里的对象`、`用户验收前置状态`。
- 如果本轮不能明确指出“刚刚读取了哪份规则真相源”和“画面每个主要对象对应矩阵哪一行”，立即停止出稿；不得用交接摘要、旧 PASS、旧截图、旧合同印象或旧设计稿继续生成。
- “刚刚读取规则”必须能落成至少三条具体规则对象结论，例如组件数量、setup 摆放、隐藏信息、行动标记、骰子、牌区、状态轨道或胜负条件；只写“已读规则”或只读旧设计合同不算通过。
- 规则对象素材矩阵必须为每个会出现在画面里的主体写出正式资源路径、atlas id / frame id、`visible-subject` / `reference-only` / `approved-programmatic` / `approved-programmatic-runtime-ui` 裁定；只写“有素材”“用卡牌素材”“后续接入”不算通过。
- 需要正式素材的对象，只有处于 `design-asset-ready`、`pass` 或 `approved-programmatic`，并且角色允许可见时，才允许进入位图设计稿和 AI 图面核验；`reference-only` 只能进入证据链、输入包或详情 / 帮助语义，不能作为主画面可见主体；`planned-not-moved`、`frame-candidate`、`temp-only`、`blocked` 或未登记对象不得被画成正式卡牌、token、棋盘、骰子、角色板、状态标记或其它完成态素材。
- `design-asset-ready` 只允许证明“可作为视觉设计输入”，不能证明运行时已接线或 UI 已完成；若最终口径是运行时完成截图，必须另有运行时代码引用、真实页面截图和资源链验证。
- AI 图面核验必须先核矩阵再看图。前置矩阵不过，或图中出现素材状态不允许的对象，即使画面好看也只能判 `REVISE`。
- 人工验收只能发生在 AI 图面核验给出 `PASS` 后；未通过 AI 自检的候选图不得进入用户验收展示。

### 同稿同源证据块（强制）

- 每一份准备进入 imagegen、Open Design、HTML 预览、AI 图面核验或人工验收的 artifact，必须在同一个文件或同一份随图审计文档里带上 `设计前置证据块`；只在别处存在旧矩阵、旧合同或对话摘要不算通过。
- `设计前置证据块` 最少包含五项：`本轮实际读取的规则文件/页段`、`至少三条具体规则对象结论`、`可见主体素材账本`、`禁止替代清单`、`当前是否允许人工验收`。
- 规则结论不能只列出来，必须逐条落到画面决策：每条结论至少写清 `规则结论 -> 影响的画面主体 -> 设计决策 / 禁止项`。如果说不出某条规则如何改变布局、可见对象、隐藏信息或交互入口，不能把它当作已读规则证据。
- `可见主体素材账本` 必须逐对象写清：现实对象名、正式素材路径或 atlas/frame、当前状态、artifact 中的实际呈现方式、是否允许出现。路径必须能在当前工作树存在；atlas/frame 必须能在正式 config 中查到。查不到就只能标 `blocked`，不得写成“已用素材”。
- 素材账本必须写明复查证据：普通图片至少有 `path-exists + dimensions`；atlas 对象至少有 `atlas-config-exists + frame-id-found + source-image-exists`；程序化对象至少有来源文件 / 规则页 / workshop 对象证据。只写路径、只写文件名或只写 prompt 引用，都不能进入出图。
- “使用素材”必须是图面主体实际由该正式图片、正式 atlas crop、正式牌背、正式 token 或来源锁定程序化对象承担；只在 prompt 里写素材名、用文字描述重画、用相似图标、用 CSS/边框壳或临时裁图表达，都按未使用素材处理。
- 证据块必须记录素材如何真实进入当前 artifact：例如复制到输入包、拼入 reference sheet、作为 imagegen / Open Design 图像输入、作为 atlas crop 或运行时渲染来源。只有素材账本、没有输入动作或渲染来源时，不能宣称“已用素材”。
- 如果当前工具不能把正式素材作为图像输入、拼接基底、可追溯 crop 或运行时渲染来源，先检查 Open Design 是否可用并能承接这些素材；可用时自动转 Open Design artifact 候选稿路线。只有 imagegen / Open Design / 其它正式设计工具都不能承接素材时，本轮才只能产出 brief / 缺口清单；不得生成或打开完成态设计稿。
- 若 artifact 缺少该证据块，或证据块没有覆盖画面主体，默认判 `REVISE`，并先补规则/素材证据，而不是继续调风格、边框、配色或 prompt 形容词。

### 出图前硬回执（强制）

任何准备调用 imagegen、Open Design 生成图、HTML 预览截图或人工验收的动作前，必须先在当前 worktree 落一份可复查的 `出图前硬回执`。默认写入当前游戏 `docs/games/<gameId>/design/reference/` 下的前置包、prompt brief 或随图审计文件；只写在对话里不算通过。

硬回执必须同时包含：

- **本轮规则读取回执**：列出本轮实际读取过的规则文件 / 页段，并写出至少三条规则对象结论；如果本轮只看了交接摘要、旧设计合同、旧 PASS 审计或旧前置包，必须标 `blocked-rule-source-not-reread`，不得出图。
- **规则到画面的映射回执**：每条规则结论必须对应到画面主体和设计决策 / 禁止项；如果某条规则没有影响画面，只能作为背景参考，不能算出图依据。
- **素材进入生成链回执**：逐个主体写清 `正式资源 -> 输入包文件 -> 生成命令参数 / 图像输入 -> 预期图面主体职责`；任一主体只在 prompt 或账本里出现、没有成为图像输入或可追溯渲染来源，必须标 `blocked-asset-not-in-generation-input`。
- **核心交互落位回执**：逐步列出本稿的主决策 / 主结果对象，例如当前选中卡、合法目标、攻击掷骰、翻牌揭示、伤害 / 治疗结果、支付成败。每个对象必须写清为什么锚在目标、来源、主棋盘上层或当前动作链路中，以及哪些辅助 UI 必须让位。若把当前结算主体放到边栏、日志、牌区旁、仪表盘或空白角落，只能标为历史摘要 / 详情入口，不能作为当前主承载。
- **框体职责回执**：列出所有非素材自带边界的常驻边框 / 底板 / 面板；每一项必须说明它保护的真实交互对象。说不出对象或只是“为了清楚 / 好看 / 分区”的，生成前先删除或降级。
- **人工验收状态回执**：明确当前是否允许人工验收；默认值必须是 `human-review-not-allowed`，只有随图 AI 审计按规则、素材、少边框和可复刻门禁给出 `PASS` 后才能改为允许。

硬回执是生成前门禁，不是生成后补说明。缺任一项时，当前动作只能是补回执或报告阻塞，不能继续出图、不能进入用户验收展示，也不能把旧稿改名为新设计稿。

### 正式素材输入包门禁（强制）

- 位图设计稿出图前必须先形成 `素材输入包`，并在设计前置包或随图审计中记录：包内文件、来源正式路径、尺寸 / frame、在生成或拼接中的用途、是否为画面主体。只有素材账本，没有输入包，不得调用 imagegen / Open Design 生成完成态图。
- `素材输入包` 的内容必须来自正式资源或正式 atlas crop：棋盘、角色板、卡牌、牌背、token、骰子、状态板等已有正式素材必须按角色进入图像输入、拼接基底、可追溯裁片或运行时渲染来源之一。若矩阵裁定为 `reference-only`，它可以进入 reference sheet / 证据链帮助推导，但不得在最终主界面设计稿里复现为可见主体。只把路径写进 prompt，或让模型凭文字重画，仍按未使用素材处理。
- 若使用 Open Design，本项目素材必须先复制或导入到 Open Design 当前项目目录下的相对路径，再通过 `image` / `images` / composition 输入给生成链路；不得把工作树绝对路径写进 prompt 后声称素材已参与。
- 若素材过多，先生成一张或多张 `reference sheet / composition`：保留主棋盘、状态板、卡背、代表性卡牌、token、骰子等真实像素，附最少对象标签；该 reference sheet 也必须持久落盘并列入输入包。纯文字 prompt 不能替代 reference sheet。
- 若当前 imagegen 模型、CLI 或参数无法接受这些素材输入，但 Open Design MCP / artifact 路线可用，必须把素材导入 Open Design 项目或项目内相对路径，并继续生成 artifact 候选稿；不得停在 `blocked`。只有所有可用设计工具都无法接受正式素材输入时，本轮才输出 `blocked` 的 brief、缺口清单和下一步接线任务；不得退回无素材 HTML/CSS、纯 prompt、线框稿、手工拼贴稿或旧截图冒充正式设计稿。
- AI 图面核验时先查 `素材输入包 -> 生成输入 -> 图面主体` 三段是否连通；任一主体对象只在账本中存在、没有进入输入包或没有在图面承担主视觉，直接判 `REVISE`。

### 读规则 / 用素材 / 少边框事故拦截（强制）

- 用户指出“没看规则”“该用素材处没用素材”“边框太多 / 重新设计”时，默认这是流程规范事故，不是普通视觉微调；必须先把当前候选稿标为 `rejected / failed-candidate`，再回到本节前置证据，而不是沿旧稿继续加减边框、改配色或补几句 prompt。
- “已读规则”必须能回到本轮实际读取动作和 artifact 内证据块：至少写明规则页段 / 文件、三条以上具体规则对象结论，以及这些结论如何决定画面主体。只读设计合同、任务摘要、上一轮压缩摘要或旧矩阵，不得算作本轮已读规则。
- “已用素材”必须能证明像素或渲染来源：正式图片、正式 atlas crop、正式牌背、正式 token、正式棋盘 / 状态板，或来源锁定程序化对象必须实际进入生成输入、拼接基底、可追溯裁片或运行时渲染链。若素材角色是 `reference-only`，只能证明“已用作参考来源”，不能证明“主界面用了该素材主体”。只在 prompt 点名路径、用文字壳重画、用 CSS 形状模拟、用临时裁图、或把素材缩成角标，都必须写成“未使用正式素材”。
- “素材优先”不等于所有运行态信息都必须直接贴原物理素材。生命、资源、能量、冷却、进度、临时增减值、当前可读状态这类动态读数，如果原素材不适合实时显示或会降低可读性，可以在矩阵中标 `approved-programmatic-runtime-ui`，使用血条、蓝条、数值条、短状态 chip、轻量 token 或等价自制 UI；前提是规则来源已读、对应对象明确、不冒充原素材、不泄露隐藏信息、不抢占正式素材主体。
- 对已有正式素材且角色为 `visible-subject` 的主体对象，素材必须承担画面主语：棋盘、卡牌、token、骰子和角色板的可读面积、语义职责和视觉层级必须高于外框、面板、文字壳和装饰底板。若素材被裁定为 `reference-only`，不得因为“素材优先”把它硬贴到主界面；应把对应动态读数或运行态反馈裁成 `approved-programmatic-runtime-ui`。若第一眼看到的是容器分舱而不是真实桌游对象，直接判 `REVISE`。
- 边框只允许服务三类目的：素材自带印刷边、真实交互命中区的轻量高亮、必要按钮底板。不能说明现实对象或交互职责的外框、内框、卡片壳、玻璃板和分栏底板默认删除；不得用“更清楚 / 更像 UI / 后续再换素材”放行。
- 如果当前 imagegen / Open Design / HTML 预览链不能把正式素材作为图像输入或可追溯渲染来源，本轮只能产出 `设计前置证据块`、素材输入包、prompt brief 和缺口清单；不得产出或打开“完成态设计稿”。
- 设计前置包必须落成当前 worktree 内的持久文件，默认放在 `docs/games/<gameId>/design/reference/` 或项目约定的等价目录；只在对话里口头列规则、只在旧矩阵里已有、只在 prompt 中写“使用素材”，都不得进入 imagegen、Open Design、HTML 预览或人工验收。
- 设计前置包必须能被机器或人工复查：正式素材路径必须存在，atlas/frame 必须能在正式 config 中查到；若复查失败，先修素材账本或标 `blocked`，不得把失败对象画进完成态图。

### 生图交付物类型门禁（强制）

- 这个 skill 的正式交付物默认必须是**生图生成的位图设计稿**，不是手工拼贴稿、不是线框稿、不是资产切片排版图、也不是“看起来像 UI 排版图”的半成品。
- **Open Design 自动接力例外**：当 imagegen 路线不可用且 Open Design 可用时，Open Design artifact 渲染导出的 PNG/JPG/WebP 可以作为本轮设计稿候选交付物，但必须在随图审计中明确标注 `open-design-artifact-candidate`，并证明 `正式资源 -> Open Design 项目/输入包 -> artifact 渲染 -> 图面主体` 连通。它不是运行页截图，也不是无审计 HTML 预览；未通过 AI 图面核验前仍不得人工验收。
- 允许存在内部辅助 mockup，但它只能服务：
  - 校准 prompt；
  - 核对空间比例；
  - 审查素材是否缺失。
- 内部辅助 mockup **不得**直接交付给用户充当 Step 1 / Step 2 / Step 3 / Step 4 设计稿。
- 如果你准备交付的图明显具有以下任一特征，默认判为**跑偏**，必须停下并改回 imagegen 生图路线：
  - 大量重复的圆角大面板、外框、内框、细线框；
  - 明显的素材切片拼盘、卡面拼贴、占位框、标签块；
  - 过强的“仪表盘 / 后台面板 / 线框图 / 拼贴稿”观感；
  - 画面主要质感来自框体，而不是来自桌面材质、卡牌层次、房间图面、光影与氛围。
- 如果图里出现规则对象素材矩阵标为 `planned-not-moved`、`frame-candidate`、`temp-only`、`blocked` 或未登记的对象，却被表现成正式卡牌、token、棋子、地图、骰子、角色板或状态标记，默认判为**跑偏**；不得进入用户验收。
- 如果规则对象有正式素材路径，但图中用边框、文字壳、纯 CSS 形状、通用图标、相似 token 或抽象占位承担该对象主视觉，默认判为**跑偏**；不得用“后续实现再换素材”放行。
- 自检口径：
  - 用户要的是“生图设计稿”时，必须反问自己这张图是不是像**真实游戏设计稿/概念图**，而不是像“给前端看的手工布局草图”；
  - 如果更像后者，就算结构没错，也不得交付。

### 桌游牌桌生图的少框体门禁（强制）

- 默认视觉方向是 **2D 印刷桌游设计稿**，不是 3D 实体渲染图。
- 这里说的“更像桌游”默认指：
  - 更像印刷版面、卡面、板块、牌背、标记与平面插画系统的统一；
  - 更少软件后台面板感；
  - 允许少量体积感，但不能靠 3D 建模、真实摄影光影、重材质渲染来成立。
- 对桌游运行时主界面的生图稿，默认优先级必须是：
  1. 印刷棋盘 / 房间板块 / 卡牌 / 角色板等平面桌游对象
  2. 少量必要的层级与投影
  3. 少量必要数字增强与状态高亮
  4. 最后才是容器、边框、按钮底板
- 默认不允许把每一组信息都装进独立大面板。像：
  - 当前玩家区
  - 队友区
  - 牌堆区
  - 帮助区
  - 动作区
 这些信息默认应先尝试作为“同一张印刷桌游画面里的对象组合”存在，而不是各自再套一层厚容器。
- 允许存在边框，但边框优先来自卡框、印刷描边、板块边线和素材自带装饰；不要默认升级成厚木边、金属雕花、机械机关件。
- 如果看图后一眼感受更像“深色后台面板 + 多个功能框”，而不是“鬼屋桌游牌桌”，默认判失败。
- 如果看图后一眼更像“3D 渲染宣传图 / 实物拍摄风概念图”，而不是“可前端复刻的 2D 运行时设计稿”，也默认判失败。

## 默认四步走（强制）

- 没有明显说明时，默认按四步走，且**通过前一步才进入下一步**：
  1. **规则提炼 UI**：先从规则和素材里提炼必要元素、主次关系和基础布局；默认优先生成运行时主界面的结构稿。
  2. **布局收敛 UI**：当 Step 1 的必要元素和大致布局已成立后，默认直接收敛到 **1 张** 可继续执行的布局定稿；只有用户明确要求对比时，才额外做多版布局。
  3. **风格统一 UI**：在已选定的布局上收成唯一风格，默认只检查是否和素材统一，不再默认做风格裂变。
  4. **分界面 UI**：在已选风格下，再生成角色选择、运行时、结算等不同界面。
- 如果用户没有特别指定“先看哪一屏”，第一步默认先做运行时主界面，因为它最容易暴露必要元素和空间关系是否正确。
- `design-system/games/<gameId>.md` 是复刻约束，不是这四步的替代品；单张“壳层图”“资料页图”“资源目录图”不算完成其中任一步。
- 用户若明确要求只做某一步，才允许跳过其余步骤；否则一律按完整四步交付。
- 如果用户明确要求“先出 UI 设计，我看过没问题才开始设计稿”，Step 1 必须先交付文字版 UI 设计，不能生成 Open Design artifact、imagegen 图、HTML 预览或前端页面。UI 设计必须包含必须交互元素和饱和交互状态；用户明确批准后才进入 Step 2/设计稿。
- Step 1 的饱和交互状态必须模拟高压力对局：场上多个对象、规则命名牌区 / 持有物 / 计划区有内容、当前存在可执行动作、合法 / 非法目标同时出现、资源读数与结果反馈同时可见。空态、首回合低压态或单对象理想态不能作为设计稿输入。
- 卡牌类 UI 必须先建立牌区语义白名单：`规则名 -> UI 名称 -> 可见性 -> 流转关系 -> 可操作入口`。规则没有“手牌”就禁止在设计声明、artifact、class / aria、审计和汇报中写“手牌”；应使用规则自己的名称，例如牌库、法术书、已计划法术、弃牌堆、公开区、市场、持有物等。
- 如果规则命名对象是大型私有库、法术书、持有物库或等价“可检索但不能全量常驻展开”的对象，UI 允许采用底部或边缘浏览器模式：一排当前候选对象 + 规则分类切换 + 页码 / 上一页 / 下一页。浏览器必须继续使用规则名称，不能因为交互形态像另一款卡牌游戏就改名成该游戏没有的牌区；当前可执行来源仍以规则真正允许的对象为准，例如已准备、已计划、已装备或已公开对象。
- 卡牌区必须区分 `当前可执行 / 可浏览候选 / 归档入口` 三种职责：当前可执行卡必须可读且能承接主动作；可浏览候选可以缩小但必须有焦点预览、hover / focus 放大、分页抽屉或详情区；归档入口默认只显示数量、所属关系、极小堆叠或卡背轮廓。除非当前规则步骤要求从该归档中选择、回收、复活、结算或高频比较，不得常驻展示顶牌正面、放大图或完整清单。三者混成一条小牌墙时直接判 `REVISE`。
- 远处重复一张大卡不等于解决卡区可读性。若当前可执行卡仍留在底部 / 侧边不可读混合区，另一处大图只能算详情预览，不能算主交互成立；必须把当前可执行卡、费用 / 目标 / 结果短状态和相关入口整合成真实工作台，或者删除原不可读槽位。
- “当前阶段需要多少牌区空间”必须由规则容量和任务决定，不能按模板给一条小栏。计划 / 浏览态若规则要求从大型私有库、法术书、牌库或背包中选择，必须给足分页 / 分类 / 焦点预览 / 可读候选；执行 / 目标确认态则只保留当前可执行来源、已选目标和提交 / 取消，大集合退为入口。把计划态需要的浏览能力压进确认态小角落，或把确认态需要的来源卡缩成候选缩略，都判 `REVISE / phase-capacity-mismatch`。

### Step 2 布局收敛的额外硬约束

- 默认只产出 **1 张** 布局定稿，不再强制做 3 张裂变。
- 如果用户明确要求“比较布局”“给我几版布局看看”“同题多解”，才允许临时切回多张布局对比；否则直接沿当前已选方向继续。
- 布局必须优先照顾实际可玩性：
  - 先估算这张图里最多要容纳多少物品、规则命名牌区对象、状态 chip、目标卡和动作入口；
  - 如果规则没有写明固定上限，不得按“通常只会有 2-3 张”偷懒布局；必须先根据规则动作、牌池规模、补充来源、可持有机制与回合节奏，写出一个**可辩护的峰值估算**，再决定是否需要溢出机制；
  - 如果这些对象会把主视区挤爆，先重排布局，不要先生成再补救；
  - 如果规则动作没有对应入口，先补入口再出图。
- 布局定稿至少要明确这 3 件事：
  - 玩家先看哪里；
  - 当前可点击的对象集中在哪；
  - 结束当前动作或回合的入口放在哪里。
- 如果用户已经点名某个继续母版，后续默认先把它当成**视觉基线**，不是规则真相源：
  - 默认优先保留它的主构图、主次关系与大区块关系；
  - 但只要规则审计证明这版母版本身缺少必要入口、必要承载量或必要对象关系，必须先指出母版失效点，再允许改它；
  - 不得把“继续沿用某版”理解成“规则可以让位给母版”。
- 布局仍然必须优先复用素材语法：
  - 尽量复用原本素材中的图形、槽位、牌框、印刷行动指示器、徽记、角标、属性标识、几何轮廓；
  - 即使你已经知道某个原素材不完全适合表达动态等级、技能层级或数值状态，布局阶段仍然优先保留它的形状语言，再考虑后续如何数字增强；
  - 例如素材里属性更像五角星/徽章，就先按五角星/徽章的视觉语言做，而不是擅自替换成一套更“通用”的圆点、进度条或仪表盘。
- 如果用户已经点名某个版本名，例如 `betrayal-runtime-prehaunt-board-v4`，后续默认沿用该版继续收敛，不再默认重开布局裂变。

## 设计批准前的实现禁令（强制）

- 用户要的是“设计稿 / Open Design 稿 / 视觉稿 / 先看图”时，本阶段只能交付设计稿候选和随图审计；不能把任务升级成真实页面实现、技术 E2E 或可玩页面。
- 只要当前仍处于 Step 1 / Step 2 / Step 3 任一步的设计稿阶段（位图稿，或用户明确指定的 Open Design artifact），**默认不得**：
  - 启动 `dev server`、联机房间、本地运行页去做“真页验真”；
  - 编写或继续扩展 `Board.tsx`、运行时 HUD、动作条、PromptOverlay、页面骨架等前端实现；
  - 用未被用户指定或未通过设计门禁的 HTML/React 静态页、真实运行页截图或可玩页面，冒充“设计稿已经出了”。
- 正确顺序必须是：
  1. 先出本轮指定的设计稿（默认位图稿；用户明确指定 Open Design 时为 Open Design artifact / 导出审计截图）；
  2. 用户明确同意该步设计稿；
  3. 再进入下一步设计，或回到 `create-new-game` 继续骨架/实现前门禁；
  4. 只有在设计稿与骨架都过门禁后，才允许进入前端实现与真页验证。
- **批准语义**：
  - 用户说“继续”不等于批准当前设计步；
  - 只有用户明确认可该步布局/风格/分界面稿，才可进入下一步；
  - 未获批时，只能继续改 prompt、重生图片、补拆解与审计，不能切去实现线。

## PC 基线未过禁止移动端转场（强制）

- 固定构图类棋盘 / 牌桌 / 战场设计，PC 桌面设计稿或桌面真实页是主基线；移动端只能在 PC 基线通过后做适配。
- 当用户指出 PC 端没好、PC 端未通过、边框 / 素材 / 规则主链仍失败，当前稿必须标为 `REVISE / implementation-blocked / mobile-blocked-by-desktop`。
- 在上述状态下不得生成移动端验收图、不得把移动端截图当完成证据、不得跑移动端 E2E 作为收口；移动风险可以记录，但不能成为下一主阶段。

## 实现导向生图的可复刻门禁（强制）

- 当这张生图的后续目标是“据此做前端实现”时，必须先把画面元素分成三类，再允许继续：
  - **前端刚性结构**：前端需要高保真复刻的位置、主次、尺寸关系、交互入口和对象分组。
  - **可替换氛围材质**：允许在实现时降级或替换的木纹、铜锈、纸张颗粒、蜡烛、景深、照片级纹理、桌面小道具。
  - **纯概念点缀**：只服务气质，不应承担信息表达职责的装饰物。
- 默认必须能明确说出这张图里哪些属于前端刚性结构。对桌游运行时主界面，通常至少包括：
  - 房间板块主视区的构图和连接关系；
  - 当前探索者板、队友摘要、牌堆组、持有区、动作条的相对位置；
  - 焦点房间、当前动作、可交互入口的高亮方式；
  - 主要对象的轻重层级。
- 出图前必须先过“友好性自审”：
  - 我最多会有几个物品 / 规则命名牌区对象 / 目标 / 状态同时存在，画面是否还能正常落位；
  - 玩家这一轮能做的事情是否都有明确入口，不能只靠看说明猜；
  - 如果队友、同房间对象、可交易对象会影响这一轮决策，是否有最小可读入口，而不是只剩几个没语义的头像；
  - 常驻文字是否只在承担对象名、数值、短状态和按钮标签，没把规则说明塞进主界面；
  - 这个布局是不是能让第一次接触的人先找到可点对象，再理解规则，而不是先看懂术语。
- 主 UI 的描述性正文默认禁止：
  - 主界面里只允许 `对象名`、`数值`、`短状态`、`按钮标签` 这四类常驻文字；
  - 不允许把“按钮是干什么的”“现在为什么该点它”“点击后会发生什么”写成常驻说明句；
  - 如果确实需要解释按钮功能，只能做成 **tooltip / 小问号 tip / 帮助入口展开层 / 临时说明浮层**，不能直接写在按钮下方或主界面正文里。
- 对“以既有稿继续收敛”的任务，还要额外过一条 **母版对比门禁**：
  - 新稿的主棋盘权重不能低于母版；
  - 新稿的常驻区块数量不能多于母版；
  - 新稿若需要用户先适应一套新分区关系，默认判失败；
  - 如果它不比母版更克制、更稳定或更可实施，就不应继续保留。
- 默认不得把以下内容当成“前端必须按图复刻”的正式合同：
  - 蜡烛火焰、体积光、景深、摄影级阴影；
  - 雕花浮雕、木雕裂纹、金属旧化细节、随机污渍；
  - 依赖生成纹理才成立的房间内部细节、墙纸花纹或桌面噪点；
  - 仅靠细腻材质差异才看得出的状态变化。
- 对当前默认路线，还应额外避免把这些当成主视觉支撑：
  - 厚木边、古铜机关、立体铭牌、桌边机械件；
  - 强烈俯拍摄影感、实物模型感、3D 板块厚度表演；
  - 靠真实烛光与实体道具撑起来的“高端概念图”气质。
- 如果某个关键信息只有在高阶材质或复杂光效存在时才看得清，默认判为**不可直接实施的设计稿**；必须把该信息改成前端可稳定复刻、且不抢素材主语的表达，例如贴对象的轻量高亮、素材内徽记、状态色块、实体令牌、原卡槽标记或必要按钮态。不要把“加一圈边框”作为默认修法。
- 默认承诺口径：
  - “可复刻”指前端能高保真复刻构图、层级、尺寸关系、交互入口和对象语法；
  - 不承诺逐像素复刻 AI 生成的随机纹理、雕花、摄影光影或不可控笔触。
- 默认 prompt 口径：
  - 优先写 `2D printed board game UI concept`、`flat illustrated board tiles`、`printed card language`、`implementable runtime layout`；
  - 避免默认写 `realistic tabletop materials`、`carved wood`、`antique brass`、`candlelight cinematic`、`premium 3D render` 这类会把结果推向实体渲染的词。
- 如果任务是“在某张图上继续优化”，prompt 必须直接写明：
  - `preserve the approved macro layout unless rule audit proves it insufficient`；
  - `do not add new permanent regions unless rules require them`；
  - `prefer solving within existing slots or by lightweight regrouping`；
  - `fail if the result feels busier or more segmented without rule justification`。
- 向用户汇报实现导向设计稿时，默认要同时说两句话：
  - 哪些部分是后续前端必须守住的结构合同；
  - 哪些部分只是概念气质参考，实现时允许降级。

## 新游戏分支与工作树口径

- 新增/添加游戏时，分支与工作树要求以 `.spec/skills/create-new-game/SKILL.md` 为准：默认建议独立 worktree，但创建、切换或派生分支前必须取得用户当轮明确授权。
- 未获授权前不得创建、切换、重建 worktree 或分支；如果 UI 生图工作必须依赖隔离现场，先说明目标路径、候选分支名、影响范围和最小授权动作。
- 本 skill 只负责 UI 生图 brief；如果它在新游戏 workflow 中被触发，应继承上游 `create-new-game` 的授权口径。
- 一旦上游已经为该新游戏选定 worktree，本 skill 后续的读图、写 prompt、写 evidence、落静态稿、截图与验证，都必须继续使用同一个 worktree；不得因为这里只做 UI 草稿，就回到主工作区继续推进。

## 新游戏 UI 生图与 OpenSpec 收口门禁

- **本 skill 不替代 OpenSpec**：当用户只是要看一个方向稿，这里可以先做规则理解、UI 拆解和 prompt；但只要用户开始要求“按这个方向做新游戏”“收敛成单一风格”“确定布局不变量”“拆 implementation task”，就必须把结论写入该游戏的 OpenSpec change。
- **流程完整度口径继承上游 create-new-game**：
  - 用户说“走流程”时，这里默认要做的是把 UI 方向对应的主文档补齐，不是退回“先最小提案”；
  - 如果当前 UI 方向已经实质影响 foundation 之外的边界，必须同步审计并补对应 change，不能只把图继续挂在最早那条 change 下面；
  - “最小”只可用于局部 prompt 收紧、局部控件删减，不可用于弱化 proposal / design / spec / tasks 的完整度。
- **默认动作**：
  1. 先按本 skill 完成规则理解、素材拆解、玩家关注点排序与禁止项清单；
  2. 若新游戏已进入具体方案阶段，把这些结论写进 proposal/design/spec/evidence，并先核对当前 UI 结论属于哪条或哪几条 change；
  3. 再继续 imagegen / SVG / 静态稿迭代。
- **禁止行为**：
  - 禁止把“生了一张图”当成方案已经走完流程；
  - 禁止在没有 proposal/design 边界的情况下，反复生成多个方向并把它们都算当前有效方案；
  - 禁止继续使用“最小提案”这类表述弱化当前具体方案应有的流程完整度。
  - 禁止用“先出一张图再补流程”当默认顺序；若当前图已经承载正式布局不变量，就要先补回 OpenSpec 主文档。
  - 禁止只更新 `design-system` 或 `evidence`，却不把已经确定的布局不变量、禁止项和主次关系同步写回 proposal / design / spec / tasks。
  - 禁止把“方向稿已经收敛”为由，继续沿用旧 change 的边界不升级；如果 UI 方向已经推动到 gameplay、scoring 或 runtime-entry 边界变化，必须回到上游 `create-new-game` workflow 补下一条 change。

## 生成方式裁决

- **UI 指导图**：用户要生成图时，目标是指导后续 UI 实现，不是最终可运行截图。可以视觉概念化，但必须守规则结构、素材构图和去重约束。
- **imagegen 不可用时自动转 Open Design**：如果内置 imagegen 不可用、CLI 缺 API key、模型/参数不能接正式素材，且 Open Design MCP / CLI / artifact 工具可用，默认立即改走 Open Design artifact 候选稿路线。转线后仍要使用同一份规则与素材前置包，把正式素材复制/导入 Open Design 项目或 artifact 相对目录，产出可渲染 artifact，再导出 PNG/JPG/WebP 进行 AI 图面核验。不得要求用户再次确认“是否改走 Open Design”，除非用户当轮明确禁止 Open Design 或要求只能用 imagegen。
- **辅助保真 mockup**：当需要核对空间关系时，可以先用真实素材做 HTML/CSS/React 静态 mockup 或截图；它只用于校准 prompt，不作为生成图交付替代品。
- **禁止把 mockup 做成正式稿**：即使 mockup 已经能表达布局，也不得把它继续美化成“多层边框 + 深色面板 + 素材拼贴”的伪正式稿直接交付；这类图要么留在内部，要么废弃，不能顶替 imagegen 设计稿。
- **失败处理**：如果 imagegen 连续生成重复 HUD、拆图、重绘流程轨或遮挡素材，应先收紧 prompt 和规范；不要直接把截图当成“已完成生图”。

## 看图与降采样规则

- 必须看主素材和生成图；不能只凭 prompt 自评。
- 不要直接打开超大图片。满足任一条件时先降采样或裁图：最长边超过 `1800px`、文件超过 `2MB`、或包含大量细字/密集 UI。
- 原图必须保留。降采样、裁图、标注图只放 `temp/<gameId>-ui-imagegen-review/`，不得覆盖 `$CODEX_HOME/generated_images/**` 或正式素材。
- 优先产出两类核对图：
  - **总览图**：最长边约 `1400-1600px`，用于判断整体构图、轻重、遮挡。
  - **局部图**：按关键区域裁切，例如规则命名牌区 / 焦点卡、底部轨、右侧牌槽、主行动指示器、当前目标浮层。
- 只要总览看不清某个判断点，就必须补局部图；不能用“看不清”当作通过。
- 可以用标准工具生成核对图，例如 PowerShell + Python/Pillow；若 Pillow 不可用，用系统现有图片工具或浏览器截图降采样。不要为了看图引入新运行时依赖到项目。

示例原则：

```text
source image -> temp/<gameId>-ui-imagegen-review/overview-1600.png
source image -> temp/<gameId>-ui-imagegen-review/crop-card-zone.png
source image -> temp/<gameId>-ui-imagegen-review/crop-bottom-tracks.png
source image -> temp/<gameId>-ui-imagegen-review/crop-action-indicator.png
```

## UI 元素拆解门禁

生图前必须给出这四类清单：

- **素材已有 UI**：主图上已经印出来的行动指示器、牌库槽、弃牌槽、流程轨道、计分轨、卡位、提示框、区域名、边界、图例等。已有 UI 只能数字化增强，不能复制一套。素材本身就是 UI 元素的一部分，不得当纯背景。
- **规则必须常驻**：玩家每回合必须反复查看或操作的对象，例如规则明确命名的牌区、当前选中卡牌、当前可执行动作、当前选中目标。
- **参考卡必须转成交互**：像 `Player reference`、`Traitor reference`、`Monster reference`、回合顺序卡、步骤卡这类“告诉你怎么做”的卡，默认只作为规则来源，不应在运行界面中整张展开；它们必须优先被提炼成按钮、短状态、动作条、步骤 chip 或可折叠帮助入口。
- **按需展开**：日志、详情、帮助、完整持有区 / 牌区、规则摘要、弃牌堆查看、战斗结算详情。默认不占整列。
- **禁止出现**：规则没有的系统、解释性 UI、工具/编辑器入口、重复控件、独立拆出来的地图区域。

拆解必须直接引用规则原文中的结构，不要用泛化策略游戏经验补空白。

拆解之前必须先给出素材状态表：

- **正式可用素材**：已语义命名、正式落盘、压缩/manifest 或 atlas config 可追溯的素材；设计稿可以直接使用。
- **候选 / 临时素材**：只用于录入、OCR、核对、contact sheet、布局参考或未压缩未接线的素材；只能作为内部参考，不能冒充正式视觉。
- **程序化批准对象**：矩阵明确 `approved-programmatic`，或用户当轮明确批准不使用图片的对象。
- **运行态自制 UI**：矩阵明确 `approved-programmatic-runtime-ui`；只用于正式素材不适合直接承载的动态读数、条形反馈、短状态和交互反馈，不得替代棋盘、卡牌、牌背、token、骰子、角色板等物理主体。若某个物理素材被裁成 `reference-only`，对应运行态 UI 必须说明继承了哪条规则语义，且不复现原素材为常驻面板。
- **阻塞对象**：规则要求出现但素材状态不闭合、替代未批准；图中不得把它画成已完成对象。

补充约束：

- Step 1 的目标是确认“必要元素和基础布局”，不是提前做风格炫技；这一步如果已经把元素放错、主次做反，后续全部作废。
- Step 2 的目标是把当前游戏收成一个真正能用的布局，不是默认做裂变；只有用户明确要求时才进入多版布局对比。
- Step 2 默认要先回答“最大承载量放不放得下”“玩家可做动作有没有入口”“玩家先看哪里”这三个问题，再去生成。
- Step 3 必须复用 Step 2 已选中的布局，并收成与素材统一的唯一风格；不得借“换风格”偷偷改主结构。
- Step 4 必须继承 Step 3 选定风格，不得每个界面各换一套视觉语言。
- 对卡牌驱动游戏，Step 1 默认必须包含“当前持有区 / 当前决策入口 / 回合推进入口”这类运行时交互骨架；具体是不是按钮、牌位、行动指示器入口、棋盘直点，以规则和素材为准；如果把参考卡画出来却没有可执行入口，那不是 Step 1 合格稿。

## 生成图元素审计门禁

看图后必须列出生成图里每一个主要数字 UI 元素，并给出来源归属：

- **规则动作**：规则明确要求玩家选择/执行/确认的对象，例如规则命名牌区行动、势力行动、选择目标、打出卡牌。
- **当前决策**：玩家当前必须看懂才能行动的对象，例如规则命名牌区、焦点卡、可选区域、当前目标、可用命令。
- **素材已有职责**：地图/棋盘已经印出的行动指示器、牌库槽、弃牌槽、流程轨、计分轨、卡位、提示框等。
- **实现必要状态**：年份、当前玩家/势力、阶段、选择模式等运行时必要但不应变重的状态。

判定规则：

- 找不到上述任一归属的 UI 元素，默认判为不应存在，下一轮 prompt 必须删除。
- 属于“素材已有职责”的元素，不应另做同名独立 HUD；最多做轻量状态增强。
- 属于“当前决策”的元素不能过小，尤其卡牌驱动游戏的规则命名牌区 / 焦点卡必须可读。
- 卡牌驱动游戏里，如果规则来源卡明确描述了可执行动作，必须把这些动作转成界面上的明确按钮或动作条；不能把规则卡替代成大图说明。
- 卡牌驱动的桌面对局默认不需要“游戏标题大栏”。如果壳层已有游戏名、连接态或房间状态，生成图与静态稿里不得再复制一整条 `标题 + 已连接 + 当前玩家` 板头。
- 计分若主要服务终局或复盘，默认只保留紧凑摘要，不得在常规对局态生成巨型记分纸、整列总结卡或中央成绩单。
- 若规则里存在固定上限的公共牌列，例如幻想国度公共区最多 7 张，图上必须按完整上限一次性展开，不得用“部分露出 + 还有更多”的泛化牌桌模板。
- 生成图里如果出现流程提示、日志、规则摘要、第二套主行动指示器/牌库/战斗轨、编辑器工具栏，即使画面好看也判失败。
- 审计结论要写“保留 / 删除 / 降级 / 放大 / 移位”，不能只写“好看/正常”。

## 素材优先规则

- 主地图/主棋盘是构图真相源。若它是一张完整桌面版图，prompt 必须说“整图作为一个画布使用”，不得拆成多个独立面板。
- 规则对象有正式素材且角色为 `visible-subject` 时，设计主体必须先由该素材承担；不得用多层边框、玻璃面板、文字壳、图标壳或抽象占位，把真实牌、token、棋盘、骰子、卡背挤成背景或替代掉。若素材被裁为 `reference-only`，不得把它当可见主体硬贴；只能把它作为规则 / 轨道 / 比例来源，并用已批准的运行态 UI 承担动态读数。
- 对实时变化、需要高可读性的状态读数，正式素材可以作为规则和视觉来源，但不必机械直贴为最终控件；若矩阵裁定为 `approved-programmatic-runtime-ui`，应优先做清晰、轻量、贴近对象的自制 UI，并在审计里说明为什么原素材不适合直接承担该读数。
- 程序化运行态 UI 必须像正式控件，不得像调试占位。骰子、血条、蓝条、费用、冷却、状态点这类对象必须从当前游戏素材推导形状、颜色、材质和尺寸；普通蓝色圆点、随机亮色胶囊、默认 CSS 圆形、无材质无来源的数字球或与桌面材质割裂的占位，一律判 `REVISE`。
- 如果画面主要靠边框分舱成立，而不是靠真实桌面素材和规则对象关系成立，默认判为 `REVISE`；下一轮必须减少外框、合并面板或改为贴对象的轻量覆盖层。
- 判断“素材优先”时先看图面占比、素材角色和语义承担：正式棋盘、牌、token、骰子等 `visible-subject` 若只是小角标、背景纹理或被容器包成装饰，而主要信息由框体/文字壳表达，仍按素材未承担主体处理；`reference-only` 素材若被复现成主界面可见面板，同样直接判 `REVISE`。
- 任何新加边框、卡片壳、底板、面板都必须能回答它保护哪个真实交互对象；回答不上来时直接删或降到贴对象的轻量覆盖层，不得用“更清楚”“更像 UI”放行。
- 如果素材上已有某个控件，就不要在别处再做一个同类控件。例如素材上已有主行动指示器，就不要再在底部做第二个同名解释器。
- 如果素材上已有某个区域的牌库/弃牌槽，就只在原槽位贴短标签或状态，不把它们移到右侧栏。
- 如果素材上已有战斗流程轨、计分轨、年份/回合卡位、检查流程框，默认保留原位置，不用新 HUD 重做。
- 地图上的区域、点线、城池、山河、边界、锚点是地图内容，不应被 HUD 盖掉。
- 素材里已经存在且不会变化的固定内容，不需要在 UI 指导图里再强调、标注或解释。真正需要设计的是玩家要操作、选择、检查、确认的动态部分。

## 控件所有权规则

- 同一信息只能有一个主出处。地图上已经印出来的，就不要再做一份独立数字版。
- 如果素材上的主行动指示器已经表达当前行动，就不要在底部再做第二个同义控制器或解释器。
- 如果规则要求的是“一个主动作槽 + 一个当前状态”，不要把状态另做一个同名面板。
- 只有当素材本体没有表达该信息时，数字覆盖层才可以补它。
- 如果素材已有清晰文字标签，数字覆盖层不要再贴同名标签；避免“为了确认而重复 UI”。
- 默认优先级：`board printed control` > `one action slot` > `small state badge` > `optional detail`。

## 轻重判定规则

- UI 轻重按“玩家是否需要用它做决策”排序，不按视觉面积平均分配。
- 当前掷骰、攻击结算、伤害 / 治疗结果、翻牌揭示、检定结果、支付成败这类阻塞式结算主体，必须排在当前决策层级内：它们要贴近目标、来源、主棋盘上层或当前动作链路，不能被放进右侧栏、日志区、牌区旁、边缘摘要或仪表盘作为主视觉。骰子、效果骰和伤害结果默认按“当前结算浮层 / 弹窗层”处理，允许高于棋盘、卡牌和 HUD，但必须证明它们锚定目标 / 来源 / 动作链，且没有挡住仍需点击或持续读取的关键对象。边栏只允许承载结算后的摘要 / 历史回看 / 可检视详情。
- 卡牌驱动游戏里，规则命名牌区、当前选中卡牌、卡牌代价 / 类型 / 效果摘要通常比年份、阶段、流程提示更重要。
- 固定不变的版图文字、流程轨、牌库槽、地图区域属于背景信息；即使它们规则重要，也不应抢当前操作 UI 的层级。
- 当前可行动作和当前选中目标次于卡牌，但高于年份/玩家名/流程状态。
- 年份、当前势力、阶段状态只做轻量状态 chip，不做大标题或流程条。
- 布局里的“左区 / 右区 / 底区 / 摘要区”默认只是阅读责任区，不自动等于独立面板。除非素材本身就有明确框体或目标就是仪表盘，否则不要把每个区都做成一块带边框底板。

## 牌桌层级与重叠规则

> 本节是 BoardGame 项目适配层；底图 / 地图最低层裁决来自设计启动门禁。这里不另建独立真相，只把该裁决落到桌游素材、棋盘、牌区、骰盘和 token 场景。

- 桌游主界面默认按层级建模，而不是只按上下左右分区：`table/background`、`board/map`、`physical objects/cards/tokens`、`interactive overlays`、`resolution overlays`、`edge HUD`。出稿前必须列出每层对象、允许重叠对象和必须保护对象；没有层级表，不得生成 Open Design artifact、HTML 预览或位图稿。
- 合理重叠是桌游 UI 的常规手段。法术书、已计划法术、持有物、主动作 dock、目标选择条、骰盘和结算标记可以作为 overlay 压在桌面 / 底图 / 主棋盘的低权重区域上，只要不遮挡当前必须点击 / 阅读的棋盘格、卡牌、token、骰子或素材印刷信息。
- 不得把“避免和底图重叠”当成主目标。若为了不压底图，把当前可支配牌区、已计划牌、主动作、骰盘或结果反馈挤到角落、边缘、无关空白区，导致玩家动作路径变长或首焦点丢失，直接判 `REVISE / layer-model-failed`。
- 大块空白必须有现实职责：临时结算层、安全区、未来展开区、对象溢出容量或明确留白。右下角、底边、侧边空着不自动代表设计好；如果重要动作因为空白被挤走，空白就是失败证据。
- 底部 HUD、法术书浏览器或持有物栏若是持续主交互，应使用贴底 overlay / portal / absolute 类承载，把中央棋盘高度留给主舞台；不得把它放进正常文档流后吃掉整条高度，再让棋盘或当前动作让位。
- 如果规则当前只使用半张版图、局部战场或部分区域，主设计稿应优先放大当前可交互空间；未用空间可以作为背景记忆或完全退场，但不得占据主画布并把当前来源、目标或结算挤到一侧。

## 空间占用规则

- 地图/棋盘类主图优先保留可读面积。这里的可读面积指规则格、区域名、流程轨、牌槽、计分轨、当前对象和关键印刷信息；不等于完整露出底图纹理。覆盖层宁可少，但允许压住低权重桌面 / 石砖 / 空地纹理来换取主交互可读性。
- 行动记录、规则摘要、完整日志默认禁止出现在主界面；只有用户明确要求常驻日志时，才允许做极小入口或临时浮层。
- 规则命名牌区必须足够清楚。不要铺满整屏，但不能把卡牌缩成无意义小点；至少要让玩家能区分当前可支配的对象，以及当前决策真正依赖的是哪几张 / 哪几个对象。只有规则明确存在手牌时，才允许把该区域命名为手牌。
- 当前可执行卡牌的可读性是硬门槛：在 1920x1080 PC 稿 100% 缩放下，当前来源卡 / 焦点卡应有足够面积让玩家辨认卡名、费用 / 类型 / 状态和主动作含义；候选卡若低于可读尺寸，必须同时提供同屏焦点预览或展开策略。只要玩家必须猜缩略图内容、放大脑补或阅读旁边解释句才知道能用什么，设计稿不得送人工验收。
- 卡面已有字段不得被 UI 复读。若当前来源卡 / 焦点卡已经可读，费用、射程、目标栏、行动图标、骰数、类型、等级和效果正文默认由卡面承担；主 UI 只补当前运行态，例如选中态、已选目标、支付前确认 / 取消、资源不足、等待响应和结算结果。看不清字段时先修卡牌尺寸 / 裁切 / hover / focus / 详情，不得在旁边堆 `费用 / 目标 / 射程` chip 来代替读卡。
- 施法 / 攻击 / 行动卡使用必须统一为一条动作工作台链路：`选中来源卡或行动对象 -> 选择合法目标 -> 在同一工作台确认 / 取消 -> 确认后进入骰子 / 伤害 / 状态结算浮层`。确认和取消如果被规则或支付前状态授权，必须贴近来源卡和已选目标摘要；不得把来源、目标、确认、结果拆到两个以上无关位置，也不得在结算态继续保留确认 / 取消。
- 动作工作台审计必须写玩家视角，不准只写机器通过。最低句式是：`玩家第一眼先看 <来源对象>，再点 / 已选 <目标对象>，最后在 <同一工作台位置> 提交或取消；法术书 / 弃牌堆 / 日志此刻只是 <入口或抽屉>`。写不出这句话，或句子需要额外解释才能成立，不能送人工验收。
- 卡牌浏览区不能同时承担全库浏览、当前来源、已计划对象、弃牌堆和分页控制。若底部或侧边空间不足，优先保留 `当前来源 / 已计划` 和 `焦点预览`，把完整法术书 / 持有物库降为抽屉或分页；不得用一排不可读小牌把所有职责硬塞进去。
- 当前可执行卡牌和可浏览候选不是同一层级：施法 / 打牌 / 结算态中，当前可执行卡必须是可读大对象；法术书、牌库、弃牌堆、完整候选库默认只保留入口、分类、页码或抽屉触发。除非当前规则步骤就是“从该库中选择”，不得把候选库展开成和当前可执行卡同权的小牌墙。
- 满载空间预算必须落表：每次设计稿前先列 `主棋盘 / 当前来源 / 当前目标 / 结算浮层 / 牌区浏览 / 归档入口 / 玩家资源` 的最大可见对象数、最小可读尺寸、默认展开方式和让位顺序。中央棋盘如果已经同时承载场上卡、目标高亮、骰子、伤害 / 状态 token、路径线和候选牌，必须先减少或移出低权重对象；不能用“不相交”替代“不拥挤”。
- 用户标注 / 点名元素必须落表：出稿前必须列出用户标注或点名的每个区域 / 对象，在图中对应的规则名称、位置、职责和审计选择器。若用户写了“手牌”但规则没有该概念，必须转写为规则真实牌区（例如法术书浏览、已计划法术或可用候选），保留它的底部浏览 / 切换 / 分页意图；不得把“术语不对”当作删除该区域的理由。
- 规则对象“存在”不等于“中间展开”。任何牌堆 / 弃牌区 / 已消耗区 / 归档区 / 公开检视区，默认只是可访问入口，优先贴边或靠近所属玩家的牌组区域；只有当前规则步骤明确要求从该区选择、回收、复活、结算或高频检视，才允许把它提升到主视线。把弃牌堆这类归档对象放到中央舞台，必须先有规则步骤和交互频率证据。
- 外部范式复核不能只写成“已搜索”。若用户指出设计不符合基本游戏 UI 常识，下一稿前置包必须把外部来源落成 `来源 -> 采用的不变量 -> 本稿空间/交互决策 -> 禁止项`，例如主游戏区居中、桌面对象本体承接动作、交互物不小于 32px、不可用控件隐藏、卡牌 hover / focus 放大。不能从搜索结果直接抄皮肤，也不能拿本地旧稿自证。
- 外部范式复核必须变成出稿前的空间问责表，至少包含：`主游戏区 / 当前可执行对象 / 当前结算层 / 可浏览大集合 / 归档入口 / 空白职责`。每一项必须写出当前稿的放置位置、最小可读尺寸、交互职责、默认展开策略和失败时让位对象；缺任一项不得生成 Open Design artifact、HTML 预览、位图稿或 AI PASS。
- 机器几何审计不得替代玩家视角。若截图里小牌仍不可读、右下或底边仍无明确职责、结算骰 / 伤害 / 状态 / 目标框形成一团、玩家第一眼不知道当前来源和目标，必须撤销 `AI_PASS`，即使 bbox 没有相交、截图尺寸正确、对象数量正确。
- 中央结算层必须按注意力密度验收。攻击骰、效果骰、伤害、状态 token、目标高亮、路径线和短标签可以同处目标附近，但不能形成一个多焦点团块；修正时先减少路径线和重复标签、缩小或分行骰子、把状态贴附宿主、把历史摘要移出中心，不得把当前结算主体放到侧栏或日志里。
- 交互区应优先借现有空白区、贴边区或素材语法自然落位，不默认横跨全宽；若底部存在关键流程轨或印刷信息，必须先让位给原图可读性。
- 结束回合是普通命令，不应做成比地图对象更重的巨型面板。
- 如果一个覆盖层会让地图已有 UI 不可读，删除覆盖层，而不是移动地图。
- 首版 UI 草稿默认不展示完整卡面墙；除非用户明确要求检查某个规则牌区布局，否则规则牌区只显示必要入口、数量、少量小缩略 chip 或当前焦点。
- 若游戏核心是卡牌驱动，应在不遮挡主图关键轨道的前提下保证规则命名牌区或持有物可读；展示数量、排列方式与是否需要焦点预览，必须由规则上限、当前决策密度和素材空间共同决定，不得按固定张数模板套用。
- 素材上已有战斗流程轨时，禁止把它重绘成数字面板；只能保留原图或加极小阶段标记。
- 底部操作区不得为了“看起来完整”而吃掉原图下沿关键轨道；具体宽度、排布和是否需要滚动，必须由规则动作数量、素材空白区和当前决策密度共同决定。
- 若同一张图主要靠“整张牌桌 / 整张地图 / 整张书页”成立，辅助信息默认做成贴边、贴角、贴对象的轻量区，而不是左一盒、右一盒、下一盒的分舱式布局。
- 若当前动作正在结算，主舞台必须先安排结算槽位：骰子 / 翻牌 / 命中章 / 伤害章应作为临时上层贴在目标、来源或路径附近，并证明不遮挡目标本体、token、牌堆和确认按钮。把结算主体移到侧栏来换取“画面干净”，默认判为 `REVISE`。

## 规则理解规则

- 先建立 `规则对象交互权重表`，再画布局。每个对象至少写清：规则来源、当前阶段角色、是否当前主动作、是否需要高频点击、是否只是公开检视 / 归档、可见性 / 隐藏信息、最大承载量、默认收起还是展开、默认靠近哪个现实主体。没有权重表时不得把任何规则对象放进中央主舞台。
- 设计前还必须按设计启动门禁中的“规则对象实体锚点守恒”和“开放式直选裁决顺序”补 `规则对象 -> 唯一实体锚点 -> 状态 / 详情引用` 表，以及 `当前选择 -> 可直选对象 -> 本体高亮 -> 代理 UI 是否必要` 表。`已选`、`当前来源`、`目标摘要`、详情和放大检视只能引用实体锚点，不能复制成第二个规则对象；棋盘格、场上卡、token、骰子等可见对象能直接承接选择时，不得用目标摘要块、文字按钮、编号圆点或大空 UI 替代。
- 固定区域、格子、地图房间、战场格、基地或等价空间单位是规则单位时，先建立 `区域 / 格子 -> 对象锚点 -> 容量 / 堆叠 -> token 贴附 -> 高亮` 合同，再摆卡牌、棋子、token 或结算层。对象必须有唯一所属区域，中心点不得在边界 / 缝隙 / 格外；允许轻微旋转和自然偏移，但不得让玩家无法判断对象属于哪一格。可参考仓内成熟格子游戏的“格子先行、对象在格内、点击对象本体”交互不变量，不复制其皮肤或术语。
- 先找“回合主动作模型”。不要把子选项误升为主按钮。
- 如果规则写“执行 A 及 B，顺序自定”，UI 应表达两个动作槽，而不是把 A 的子项和 B 并列。
- 卡牌子类型、势力行动、战斗步骤、维护步骤等，只有在当前动作展开时显示。
- 不确定某 UI 是否常驻时，默认降级为按需展开。
- 确认 / 取消 / 提交 / 下一步类控件必须先找规则动作或真实系统状态。若规则没有要求玩家先确认，且当前交互没有可撤销目标、多目标分配、费用选择、响应窗口、网络请求或不可逆危险动作，就不得常驻确认按钮；当前牌、合法目标、高亮对象或短状态反馈应直接承接动作。
- 确认控件如果被允许出现，必须在前置包里写清三件事：确认前玩家还能改什么；确认后系统发生什么；为什么不能点击当前对象本体直接完成。答不上来时，确认按钮必须删除或降级为仅在临时选择态出现的退出 / 取消入口。
- 确认控件的阶段必须和画面一致。支付 / 提交前的“目标已选，待确认”可以出现确认 / 取消；一旦进入攻击掷骰、效果骰、伤害、治疗、燃烧等结算层，确认 / 取消必须退场，主 UI 只显示结算反馈和必要等待态。不得在同一张设计稿里同时表达“待确认”和“已结算完成”，除非它明确是多状态分镜而不是单一运行时画面。
- 和仓内成熟游戏对比时，只比较交互不变量。例如某游戏把抽牌堆 / 弃牌堆贴玩家边缘、点击后展开，就说明“归档牌堆通常是边缘入口 + overlay 检视”，不能说明新游戏也应该继承该游戏的牌区名称、视觉皮肤或中心布局。
- 不要在 UI 里解释规则。按钮叫“结束回合”即可，不写“结束当前玩家回合并进入下一玩家”。
- 如果某元素已经在素材里承担“状态显示”，覆盖层不要再重复显示同一状态。
- 不要在 UI 指导图里显示流程说明或流程箭头。素材中的流程轨保留即可，动态 UI 只显示当前状态或当前操作。
- 如果要解释按钮功能，默认只留 hover tip 或帮助入口，不在主 UI 常驻解释句。

## Prompt 结构

生成 prompt 时按以下顺序写：

1. **当前步骤**：先写明这是 Step 1 结构稿、Step 2 布局定稿、Step 3 风格统一稿，还是 Step 4 分界面稿。
2. **画布原则**：主素材是否完整使用、是否允许裁剪、是否允许拆分。
3. **必须保留的素材 UI 位置**：逐条列出已有控件的位置和处理方式。
4. **友好性前提**：先写清最大承载量、关键动作入口、玩家视线顺序是否已经成立；没成立就不要进入生图。
5. **最小数字覆盖层**：只写新增覆盖层，不写大段功能说明。
6. **主动作模型**：用规则术语描述，不发明 AP、任务、建造队列等系统。
7. **层级与允许重叠**：列出背景层、物理对象层、主交互 overlay、结算 overlay、辅助 HUD；说明哪些重叠允许，哪些对象必须保护。
8. **确认控件授权**：若出现确认 / 取消 / 下一步，必须写明规则或系统状态依据；没有依据则明确禁止出现。
9. **风格口径**：默认只允许与素材统一的单一风格；除非用户明确要求，否则不写多种风格方向。
10. **禁止项**：把本轮踩过的坑明确写进 negative constraints。
11. **可见文字限制**：只允许短标签、动作名、数字和状态；禁止解释句。
12. **复刻边界**：点明本轮图里的前端刚性结构与可降级氛围材质，避免 prompt 把不可控细节写成正式合同。

## 生成后自检

每次生成后必须看图并逐项核对，不能只交付生成结果。

- 看 `$CODEX_HOME/generated_images/**` 下的生成图时，先按“看图与降采样规则”生成总览/局部核对图；不要直接打开超大原图。
- 可以用 `view_image` 查看降采样图和局部裁图。
- 不要用 HTML/CSS mockup 截图替代用户要的 UI 指导生成图。
- 不合格时必须更新 prompt 或规范后重生；继续迭代直到达到本轮验收标准，或明确记录阻塞原因。

自检清单：

- 是否出现重复控件：第二个主行动指示器、第二个牌库/弃牌、第二个年份或回合卡位、第二个当前行动。
- 是否所有主要数字 UI 元素都能对应规则动作、当前决策、素材已有职责或实现必要状态；没有对应就删除。
- 是否所有可见规则对象都能回查到素材矩阵；需要正式素材却只用了 CSS 图形、文字壳、抽象点位、临时裁图、未接线 atlas 或相似素材时，直接判失败。
- 若游戏有固定区域 / 格子 / 地图房间 / 基地，是否每个场上对象都能回查到唯一所属区域，中心点和大部分包围盒都在该区域内，token 是否贴附宿主；卡牌骑线、格外摆放或区域归属不可辨时直接判失败。
- 是否把真实素材降级成装饰背景，再靠边框和面板表达主要信息；如果是，直接判失败。
- 是否在本轮重新读取了规则真相源；如果只是沿用旧摘要或旧 PASS 结论，直接判失败。
- 如果去掉蜡烛、雕花、旧化纹理、景深和摄影级阴影，这张图的主结构是否仍然成立；如果不成立，说明它还不是可实施设计稿。
- 若当前是 Step 1：是否已经能看出必要元素和基础布局是否成立；如果还在靠“风格挺像”掩盖布局问题，判失败。
- 若当前是 Step 2：是否真的给出了当前能直接执行的唯一布局定稿；如果还在为了“多一版更好看”反复裂变，判失败。
- 若当前是 Step 2：这版布局是否能回答“最多几个物品也放得下”“动作入口在哪”“玩家先看哪”；答不上来，判失败。
- 若当前是“基于已选母版继续”，新稿是否仍然保持相同主构图与区块数量；如果靠新增面板/新增分栏/新增焦点区来解决问题，判失败。
- 若当前主 UI 出现“Move to... / Draw a... / Trade with...”这类按钮功能说明句，默认判失败；按钮只保留标签，解释退到 tooltip、帮助入口或临时说明层。
- 若当前是 Step 3：是否严格复用 Step 2 已选布局，只收成与素材统一的单一风格；若结构也跟着变，判失败。
- 若当前是 Step 4：是否严格继承 Step 3 已选风格；若角色选择、运行时、结算像三套产品，判失败。
- 是否轻重失衡：HUD 是否比地图更抢眼，底部/右侧是否变成仪表盘。
- 是否把当前结算主体降级到边栏 / 右侧仪表盘：若攻击骰、翻牌结果、命中 / 伤害 / 治疗等结果不在主舞台目标或来源附近，直接判失败。
- 是否遮挡素材：流程轨、牌槽、区域名、特殊区域、年份/回合卡位是否还可见。
- 是否出现“大块底部 HUD”：完整牌墙 / 持有区、巨大动作菜单、巨大结束按钮、重绘战斗流程面板。
- 是否出现解释性 UI 文案。
- 是否出现流程提示/流程说明条，尤其是素材中已经有流程轨时。
- 卡牌是否过小，是否无法看出这是卡牌驱动游戏的主要决策区。
- 是否出现用户已要求移除的元素，例如整列日志或行动记录大面板。
- 若任一项不合格，必须更新 prompt 或规范后重生，不得把图当成合格草稿。

## 文案限制

UI 里允许：

- 对象名：规则真实名称，例如 `牌库`、`弃牌`、`法术书`、`已计划法术`、`回合标记`
- 动作名：`打出卡牌`、`选择当前行动`、`结束回合`
- 状态：`已执行`、`未执行`、`当前`
- 数字和短字段：年份、VP、人口、部队、顺位

UI 里禁止：

- 规则说明句
- 教程句
- “点击这里...”类指令
- 解释按钮含义的文字
- 不属于规则的资源栏和系统名

## 单游戏私有规则下沉（强制）

- 通用 skill 不得直接写某个游戏的专有机制名、专有地名、专有势力名或专有控件名。
- 即使只是举例，也不得拿单游戏机制名充当通用示例；示例必须抽象成职责，例如“共享行动指示器”“年份或回合卡位”“特殊区域”。
- 像“某个游戏独有的主交互构件”“某个游戏专属势力”“某个游戏专属地区/关隘”这类只属于单游戏的约束，只能写进该游戏自己的项目 skill 或该游戏的 `design-system` 文档；`docs/games/<gameId>/` 只保留事实资料、规则来源、历史记录或证据说明。
- 如果当前任务明显依赖某个游戏的主板结构特例，先保留这份通用 skill 的共性约束，再去读取该游戏的专项文档；不要把专项提醒反写回通用 skill。
