# UI Design Pipeline

把一句 UI 需求变成可执行、可评估、可回流的设计链路。这个 skill 不替代具体项目 UI 规范、位图生图流程或前端实现 skill；它负责在它们之前把“要做什么、为什么这样做、用什么标准验收”说清楚。

## 核心分工

- **设计声明**：定义什么算对，包括 `spec`、`domain`、`design`、`components`、`craft`、`template`。
- **执行契约**：定义怎么进入流程，包括本 skill 的步骤、项目 workflow、implementation contract 和 evaluator。
- **评估回流**：把问题写成 `issue/source/fix`，明确回到哪份声明修，不用笼统说“版式不对”。

## 交付形态裁定

- **Open Design artifact 设计稿**：HTML/CSS/JS 或 Open Design 可编辑 artifact，加真实素材与可复刻布局；导出的 PNG/PDF 只是 artifact 的渲染验收证据，不是图片模型生成结果。
- **Open Design media 生图**：`od media generate`、OpenAI / Flux / Seedream / SenseAudio 等图片模型生成链；只有用户明确要求生图、位图生成、图片模型或项目规则裁定默认位图稿时才允许进入。
- **用户明确说“使用 Open Design / OD / opendesign，不要生图”时**：默认走 Open Design artifact 设计稿；禁止调用 `od media generate`，也不得把 media provider 凭据问题当作 artifact 设计稿阻塞。
- **artifact 也要过设计门禁**：Open Design artifact 不能绕过规则真相源、素材账本、少边框、隐藏信息和 AI 图面核验；未 PASS 的 artifact 或导出截图仍只是候选 / 失败稿。
- **设计稿不是实现**：用户要“设计稿 / 视觉稿 / Open Design 稿 / 先看图”时，当前交付物就是设计稿候选；用户明确人工批准前，不得启动真实运行页、编写或扩展前端实现、跑实现 E2E，或用运行页截图反推设计通过。
- **PC 基线先于移动端**：棋盘、牌桌、战场、固定栏位等固定构图 UI 默认先过 PC 桌面基线。PC 未通过或用户指出没好时，移动端设计 / 移动截图 / 移动 E2E 只能记录为阻塞后的风险，不得作为完成证据或下一主阶段。

## 何时使用

使用本 skill：

- 新建或重做复杂 UI、dashboard、主界面、游戏 Board、核心面板。
- 用户要“设计稿 / 视觉方向 / 多个设计稿 / 多方案 / 先规划 UI / 重整 UI skill / 加入新游戏流程”。
- UI 已反复出现同类问题，例如状态缺失、组件语义混乱、token 绕过、AI 味、布局像模板。
- 用户要求“商业级”“复刻成熟产品”“已有大量案例”或指出当前 UI 完全不合格。
- 实现前需要把视觉规格、信息架构、组件语义、交互状态和验收标准沉淀成文档。

不要单独使用本 skill：

- 小范围样式修复、单个按钮对齐、简单 copy 调整。
- 用户只要求修 bug，且 UI 设计前提已经锁定。
- 用户明确要求直接实现且已有批准设计合同；此时读取已有合同即可。

## 工作流

### 0. 锁定现场

改文档、出图或写代码前，先锁定四项：

1. **问题对象**：哪个页面、组件、游戏、路由或设计稿。
2. **真相来源**：用户素材、规则文档、现有页面、Figma、截图、设计系统或项目规范。
3. **目标入口/环境**：设计稿、真实页面、移动端、桌面端、项目 workflow 或通用 skill。
4. **验收口径**：用户批准、evaluator 达标、截图复看、真实页面 E2E、项目门禁。

缺任一项时，只能补证据或问最小问题。

### 0.5 设计启动硬门禁

只要 UI 设计依赖规则书、业务数据、用户素材、产品截图、地图、棋盘、卡牌、物理配件或其它领域真相源，**设计本身**就受前置门禁约束。这里的设计包括：设计声明、布局草图、风格方向、Open Design brief、imagegen prompt、HTML/CSS 静态预览、组件骨架和实现方案。

- **先读 task-relevant skills，再设计**：设计动作开始前必须先读取与当前任务匹配的 skill / 项目规范，并把它们的硬失败项前置成设计约束。游戏 UI 默认至少读取本 skill、项目 `.spec/skills/game-ui-design/SKILL.md`、游戏设计 / 玩家任务相关 skill、UI 审计 / 看图验收 skill，以及项目 UI / 素材规范；通用游戏 UI 的对象守恒、玩家任务、饱和态、结算层和设计稿前置方法以后以 `game-ui-design` 为更具体正源，本 skill 只负责设计生成链路。若本轮没有可追踪的 skill 读取动作，不能出布局、Open Design artifact、prompt、HTML 预览或实现骨架。
- **审计规则必须前置为设计规则**：`REVISE` 硬失败项不是生成后的评分表，而是生成前的禁止清单。重叠、裁切、漂移、遮挡关键对象、当前结算主体边栏化、玩家不知道点什么、粗糙占位、伪按钮、小热区、同母版多方案等问题，必须先写进设计前置包；生成后才发现这些问题时，当前稿直接降为失败候选。
- **游戏 UI 必须先写玩家任务**：进入画面设计前必须写清玩家此刻要解决的问题、下一次点击对象、点击后发生什么、取消 / 放弃路径、哪些对象只是检视或归档。只有“画面上放哪些东西”的列表不算 UI 设计。
- 进入任何布局或风格判断前，必须先在当前轮次读取领域真相源，并写出至少三条会改变画面的结论；只读摘要、旧设计合同、旧截图或上一轮 PASS 结论不算。
- 本轮读取必须有可追踪动作证据：不能只在设计声明或 brief 里列出路径，必须能回查到当前轮次实际打开领域真相源 / 素材合同 / 输入包的动作，或当前轮次重新生成的前置证据文件。换会话、上下文压缩或切换工作树后，读数动作不可确认就默认重读。
- **领域真相源必须先做阅读理解，不是只做素材检索**：当 UI 依赖规则书、TTS / Workshop JSON、Lua / 脚本、旧平台实现、卡牌图集、PDF 导出或其它外部真相源时，读取动作必须产出 `对象职责表`，至少写清：物理对象 / 规则对象是什么、它在规则中承担什么职责、玩家何时会操作或检视、它与相似素材或同名对象是否是同一东西、它是否只是规则 / 轨道 / 参考来源、以及隐藏信息边界。只找到图片、CardID、文件名、变量名、atlas frame、脚本对象名或截图相似物，不算理解完成。
- **TTS / 脚本对象不得按名字或素材外观直接上屏**：TTS 里的 `Card`、`Custom_Model`、`Bag`、`Infinite_Bag`、`Deck`、token、状态板、提示卡、规则卡、角色模型等对象，必须先从脚本、ContainedObjects、CardID、GMNotes、规则页和图面职责反查其现实语义。若同一业务对象有多张相似图、同名卡、规则卡 / 肖像 / 模型 / 提示卡 / 状态板等成对素材，必须先拆成多行对象职责；禁止凭 `card`、`portrait`、`status`、`token` 这类变量名或视觉直觉决定 UI 承载。
- **规则理解失败时不得用测试或截图绿灯补票**：如果事后发现 UI 把两个规则对象合并、把提示 UI 当实体、把参考素材当主界面、把隐藏信息画成公开信息、或把公开归档画成隐藏信息，当前候选必须降为 `REVISE / source-comprehension-failed`。修复顺序是先补领域真相源阅读理解和对象职责表，再改设计 / 实现 / E2E；不得只改样式、测试名或截图审计结论。
- 结论必须映射到画面：`规则 / 数据 / 素材结论 -> 影响的主体 -> 设计决策 / 禁止项`。如果说不出某条结论如何改变对象、布局、隐藏信息、操作入口或禁止替代，就不能把它作为设计依据。
- 对需要真实素材承载的主体，必须先列出素材账本：来源、路径或输入文件、当前状态、在画面中的职责和允许的替代方式。只有文字描述、相似图标、抽象框体或临时裁片时，不得继续做完成态设计。素材优先不等于所有运行态信息都必须直接贴原物理素材；生命、资源、能量、冷却、进度和短状态等动态读数，如果原素材不适合实时显示，可以在账本中标为 `approved-programmatic-runtime-ui`，使用清晰自制 UI，但必须写明规则来源、对象语义、不冒充原素材、不泄露隐藏信息。
- 真实素材必须有输入链证据：素材需要进入图像输入、拼接基底、reference sheet、atlas crop 或运行时渲染来源，并在画面承担主体职责；只写路径、prompt 点名、把素材当角标或让边框/文字壳承载主体，不算用素材。`approved-programmatic-runtime-ui` 只覆盖动态读数和交互反馈，不得替代棋盘、卡牌、token、骰子、角色板、地图格等物理主体。
- 进入 reference sheet、输入包或素材账本的素材必须标明 `visible-subject`、`reference-only` 或 `programmatic-runtime-ui-source`。`reference-only` 素材只允许帮助推导比例、颜色、轨道、规则来源或细节，不得在最终主界面设计稿里作为可见面板、样本托盘或联系表复现；如果生成工具容易把 reference sheet 当布局复制，必须拆分输入包或在 prompt / brief 中把 reference-only 素材排除为可见主体。
- 如果项目内已有同类成熟实现、组件或截图，例如骰子、卡牌、token、目标高亮、牌桌 HUD、资源读数或阻塞结果承接，必须先读取该实现和对应验收证据，再决定新 UI 的对象职责。不能凭主题相似、默认组件或个人审美重新发明同类交互；成熟参考只抽取可复用不变量，不强迫继承另一个游戏的视觉皮肤。
- 规则里“存在某对象 / 某牌堆 / 某区域”只证明它需要被表达或可访问，**不自动证明它应该占据中央、常驻展开或成为主交互**。布局前必须为每个规则对象写清：当前阶段是否要反复点击、是否影响当前决策、是否只是公开检视 / 归档、是否包含隐藏信息、最大承载量、以及默认收起 / 展开 / 边缘入口策略。没有这张交互权重表，不能进入视觉稿。
- 固定区域、格子、地图房间、战场格、基地或等价空间单位是规则单位时，布局前必须先建立 `区域 / 格子 -> 对象锚点 -> 容量 / 堆叠 -> token 贴附 -> 高亮` 合同。场上对象必须有唯一所属区域，中心点不得落在区域边界、区域缝隙或格外；允许轻微旋转 / 偏移，但不得让玩家无法判断对象属于哪一格。缺少区域坐标 / 锚点合同，或对象跨格导致归属不可辨时，不得生成完成态设计稿、Open Design artifact、HTML 预览截图或 `AI_PASS`。
- 当前结算主体必须按“当前决策 / 当前结果”处理。掷骰、翻牌、命中、伤害、治疗、检定、支付结果、揭示结果等会阻塞下一步操作的对象，必须放在主舞台上层、目标附近、来源附近或当前动作链路中；不得把它们降级到右侧栏、日志栏、工具栏、摘要栏或边缘 HUD 作为主承载。边栏只能保存已结算摘要、历史回看或非阻塞详情。骰子 / 效果骰 / 伤害结果默认属于当前结算浮层，可以高于棋盘、卡牌和 HUD，但必须锚定来源 / 目标 / 动作链；目标选择阶段不得遮挡仍需点击的目标，结算完成后必须退场或折叠。
- 核心交互落位必须能解释“为什么在这里”。当某个对象承担本步主决策或主结果，例如一次攻击掷骰、当前翻牌、目标伤害或治疗结算，设计前置包必须写出 `核心对象 -> 玩家当前问题 -> 空间锚点 -> 让位对象 -> 参考不变量`。如果只能回答“这里有空间 / 看起来干净 / 右侧可放”，默认判为未完成设计；正确依据必须回到目标、来源、规则步骤和玩家下一步动作。
- UI 设计必须先分层，再分区。布局网格只回答“各对象大致在哪里”，层级模型还必须回答哪些对象是背景层、实体对象层、主交互 overlay、结算 overlay、辅助 HUD。地图、棋盘、牌桌底图默认是最低层承载，不是必须完整避让的前景主体；设计只保护当前必须阅读 / 点击的格子语义、区域标签、实体对象、token、骰子、角色读数和素材关键印刷信息，不保护低权重石砖、桌布、空地纹理或未参与当前任务的底图细节。合理重叠不是错误：主交互 overlay 可以压在背景、桌面、地图或棋盘的低权重区域上；只有遮挡关键可读 / 可点对象、让归属关系不清、或没有层级职责的重叠才是失败。反过来，若为了完整露出底图把主交互、当前可支配对象、已计划对象、骰盘、token、分页或结果反馈挤到边缘、角落或无关空区，默认判为层级模型失败。
- **背景底图不得成为布局排斥体**：地图、棋盘、牌桌纹理只能提供空间语义和沉浸底层，不能把当前可支配对象、法术书 / 牌库 / 背包候选、分页、计划区或主要行动入口挤到不可读的底边、角落或侧缝。设计前置包必须把底图拆成 `必须保护的规则热区` 与 `可被 overlay 覆盖的低权重纹理区`；只要底图整张被当作不可覆盖矩形，导致牌区缩水、字号不可读、翻页/选择热区难点、或玩家误以为当前可用对象不存在，当前稿直接判 `REVISE / background-dominates-actionable-objects`。几何“不相交”只能证明没有压叠，不能证明底图没有错误支配布局。
- **视觉垫层必须有语义职责**：阴影、暗角、背板、毛玻璃、纸页、桌沿、托盘和遮罩都必须在设计前置包里写清职责：材质承载、可读遮罩、交互热区、状态反馈或空间分层之一。无规则对象、无材质来源、无交互职责的模糊黑影 / 大色块 / 玻璃壳只能算补丁；如果它只是为了让过小或过挤的对象勉强可读，当前稿直接判 `REVISE / visual-pad-without-semantics`。需要遮罩时，优先做成能解释的领域材质或同源层级，例如书页、桌边、棋盘阴刻、雾化结算层，而不是悬空阴影。
- **当前可支配卡牌尺寸必须来自可读性预算**：法术书、牌库、背包、市场、持有物或等价候选集进入当前决策时，设计前置包必须先写 `视口 / 卡牌比例 / 每页数量 / 候选卡最小可读尺寸 / 焦点或 inspect 策略 / 分页数量`。不得先决定“显示多少张”，再把牌缩到看不清；若常驻候选在 100% 桌面缩放下无法读出卡名、费用 / 状态和基本图面，必须减少每页数量、增加分页、提供同屏焦点预览或可退场 inspect，而不是把字段复写到卡外或用小牌墙冒充可玩。
- 空白不是默认优点。设计前置包必须说明大块空白承担的是安全区、可展开目标、临时结算层、未来对象容量，还是明确留白；若重要动作或当前对象被移走，只是为了保留右下角、底边或侧边空白，默认判为未完成设计。
- **当前可支配对象守恒**：设计不能为了让当前动作工作台、结算浮层或主舞台更干净，就删除、隐藏、弱化或不可读化玩家仍需持续比较 / 切换 / 使用的对象。卡牌、法术书、计划牌、持有物、装备、单位、行动来源、可用资源和等价候选集必须先列成 `当前主对象 / 仍可用候选 / 可浏览但非当前候选 / 归档历史` 四类，并为每类写默认可见性、最小可读尺寸、展开方式、恢复入口和退场条件。缺少这张守恒表，不得生成设计稿、Open Design artifact、HTML 预览或实现骨架。
- **规则对象实体锚点守恒**：每个当前可见 / 可操作的规则对象必须先分配唯一实体锚点，再决定选中态、来源态、目标态、详情态和摘要态如何引用它。`已选`、`当前来源`、`当前目标`、`详情预览`、`放大检视`、`目标摘要` 这类 UI 状态只能作为引用层、贴附层或只读详情层，不得被画成第二个可操作实体。若同名对象确实有多份物理副本，必须在设计前置包里写清各自所属区域、牌堆、数量或副本身份；写不清时按同一对象处理，不得重复展示。缺少 `规则对象 -> 唯一实体锚点 -> 状态 / 详情引用` 表，不得生成设计稿、Open Design artifact、HTML 预览或实现骨架。
- **开放式直选裁决顺序**：当真实对象本体已经可见并能承接当前动作，例如棋盘格、地图区域、场上卡牌、单位、token、骰子或等价规则对象，默认流程必须是 `选择来源 / 进入模式 -> 在真实对象本体上高亮合法候选 -> 玩家直选对象本体 -> 结算或进入有依据的确认`。代理面板、目标摘要块、悬浮列表、文字按钮、编号圆点、问号占位和大块空白 UI 只能在本体不可见、对象过多需要检索、无障碍入口或规则确有二次确认时出现；否则一律按替代真实交互处理，当前稿不得 PASS。
- **开放式设计不是边框数量问题，而是交互裁决顺序**：优先判断“当前动作能不能由真实对象本体承接”。能承接时，UI 只负责让真实对象更可点、更可辨、更可恢复，例如高亮合法格 / 卡 / token、让非候选降噪、给来源对象贴短状态；不能再增设一个同义工作台、目标摘要、箭头说明、问号占位或空白代理区。删代理 UI 时也必须过账：被删对象对应什么规则职责、是否仍可从本体或边缘入口恢复、是否会误导玩家以为对象不存在。
- **当前选择只产生合法动作高亮**：选中某张牌、单位、行动、技能或道具后，画面应优先改变可被它影响的真实对象状态，例如合法目标描边、可移动格高亮、不可用对象降噪、来源对象贴附短状态。不得因为进入选择态就在屏幕上新增第二工作台、第二目标卡、解释正文、箭头大标注或“已选目标”卡片。若玩家能直接点高亮对象推进，主 UI 不应再要求读一个独立摘要区。
- **选中态不得改变常驻布局占位**：选中、焦点、来源、悬浮和可用态只能通过描边、阴影、抬升、轻微旋转、亮度、局部贴附短状态或临时 inspect / spotlight 层表达，不得把原对象常驻放大成另一个尺寸档、挤压相邻对象、改变列表 / 牌列 / 棋盘 / 操作区的布局流，或让玩家误以为出现了第二个实体。需要读完整卡面或物件细节时，使用不占常驻布局空间的临时检视层；该检视层必须可退场，并不得遮挡当前仍需点击 / 阅读的关键对象。
- **收起不是删除**：大集合可以降权为抽屉、分页、扇形槽、书页、边缘入口或焦点预览，但入口必须让玩家第一眼知道这里仍有多少可用对象、当前已准备 / 已计划 / 可执行的对象是什么、如何切换或展开。规则上不叫“手牌”不等于可以让当前可用牌不可见；命名必须来自规则真相源，但可见性必须服务玩家任务。若玩家第一眼看不到自己仍拥有哪些当前可用牌、计划牌、行动来源或资源，当前稿直接判 `REVISE / actionable-objects-lost`。
- **局部动作链不得牺牲全局可玩性**：`来源 -> 目标 -> 确认 / 结算` 同台只说明当前动作链可能成立，不能覆盖持续候选区、资源区、状态区或计划区被删除的问题。每次移动、合并、收起或删除一个 UI 区域前，设计前置包必须写负向影响清单：被影响的是哪个规则对象、它当前阶段是否仍影响决策、玩家如何重新查看 / 切换 / 使用、是否会让玩家误以为对象不存在。没有负向影响清单，不得判设计完成。
- **用户标注 / 参考图元素守恒**：用户提供标注图、参考图、草图或明确点名对象时，这些对象默认是设计约束，不是可自由删减的装饰。设计前置包必须列出 `用户标注元素 -> 规则 / 业务术语 -> 默认可见性 -> 若收起的恢复入口 -> 若不显示的阶段理由`。除非规则阶段互斥、目标环境不支持、素材状态 blocked，或用户当轮明确同意省略，否则不得为了干净、少拥挤、风格统一、节省空间或“当前还没结算”而删除、隐藏、弱化用户点名元素。若用户口头标签与规则术语不一致，应保留布局和交互意图，改用规则术语上屏；不得因为标签名不规范而把对应区域删掉。
- 当前可支配对象必须可读。卡牌、棋子、单位、库存物、候选项或等价主交互对象如果承载当前决策，就不能缩成只剩缩略图、色块或小图标；小缩略只允许作为浏览入口，必须同时存在可读焦点卡、详情预览、hover / focus 放大、抽屉展开或分页工作台。若玩家在 100% 桌面缩放下看不清当前对象名称、代价 / 状态和动作含义，当前稿直接判 `REVISE`。
- 远处重复预览不是可读性修复。如果当前可支配对象仍留在不可读的底部 / 侧边混合槽位，另放一张大图只能算详情辅助，不能算主交互成立；下一稿必须把当前对象、代价 / 目标 / 结果短状态和相关入口整合成真实工作台，或删除原不可读槽位。
- 饱和状态必须先做空间预算。设计前置包必须列出主舞台、当前来源 / 焦点对象、可浏览候选、结算浮层、玩家资源、归档入口和临时提示各自占用的区域、最小可读尺寸、展开策略和让位顺序。没有空间预算时，不得用“画面看起来干净”“底部能放下”“右下还有空”作为布局依据；中央主舞台被候选牌、骰子、token、路径线、提示和 HUD 同时挤成一团时，直接判为主舞台超载。
- 当前可执行对象与可浏览候选必须分层。当前要操作 / 结算的卡牌、棋子、单位或物品是主对象；牌库、法术书、背包、弃牌堆、历史列表等大集合默认只是入口或抽屉。除非当前规则步骤明确要求从该集合中选择，不得把完整集合展开成和当前主对象同权的小对象墙；否则即使不重叠也判为认知拥挤。
- **公开归档不等于常驻展开，也不等于隐藏信息**：弃牌堆、历史牌堆、日志、战斗记录、已消耗对象和其它公开可检视集合，默认只承担“可回看入口”职责。除非当前规则步骤要求从中选择、回收、复活、结算或高频比较，它们不常驻展开完整清单或与当前来源同权的大卡面；但若规则允许玩家检视公开内容，不得把降权误做成隐藏信息。默认用所属关系、数量、紧凑顶牌正面 / 半露正面、堆叠轮廓或项目裁定的低权重入口表达；卡背只适用于隐藏信息、未知牌库，或项目明确裁定的纯归档轮廓。用户问“这个是给人看的吗”时，先裁定它是隐藏、公开归档还是当前候选，再决定正面 / 背面 / 展开层。
- 卡面 / 物件本体已经清楚印刷的信息，不得机械复写成 UI chip。若当前可执行卡牌已经以可读大图出现，费用、射程、目标栏、类型、骰数、效果正文等卡面字段默认由卡面自己承担；UI 只补充当前运行态：已选 / 未选、已选目标、支付前确认 / 取消、资源不足、等待响应、结算结果。若玩家看不清卡面字段，正确修法是放大、hover/focus、裁切或详情检视，不是在旁边重写一套费用 / 射程 / 目标标签。
- 施法、攻击、使用行动卡、使用道具等“来源对象驱动”的动作必须统一成一条任务链：`选中来源对象 -> 选择合法目标 -> 同一动作工作台确认 / 取消 -> 结算浮层反馈`。确认 / 取消如果有规则或系统状态授权，必须贴近来源对象与目标摘要，不能放在远离来源和目标的角落、侧栏、底部导航或第二个工作台；确认后确认 / 取消退场，骰子、伤害、状态等结算层才出现并锚定目标 / 来源。
- 单一动作工作台必须按玩家任务验收，而不是按 DOM 或几何验收。最低要同时回答：当前来源对象是哪一个、当前合法 / 已选目标在哪里、确认前还能改什么、确认后进入哪种结算、法术书 / 牌库 / 弃牌堆这类大集合为何只是入口或为何展开。若只能证明“没有重叠 / 没有复写字段 / 按钮在同一容器”，但玩家仍不能第一眼按来源、目标、确认行动，当前稿必须判 `REVISE / player-workflow-failed`。
- 当前规则只使用版图、地图或战场的一部分时，设计稿要优先放大当前可交互区域；未用区域只能作为低权重背景、缩略提示或退场。若未用空间占住主画布，导致当前来源、目标或结算被挤到边缘，判为主动区域分配失败。
- 外部范式复核是对“基本体验不成立”的必选项。当用户指出“这能不能给人看”“为什么这里空着”“中间这么挤”“要不要搜其它游戏 UI 范式”等问题时，下一版设计前置包必须引用可回查的成熟产品、平台规范或 UI/UX 资料，并写清 `来源不变量 -> 本稿决策 -> 禁止项`。本地规则和几何审计只能证明没有犯规则错，不能替代玩家友好性证据。
- 外部范式复核必须转成可执行空间裁决，而不是停在“已搜索 / 已参考”。至少要逐项裁定：主游戏 / 主工作区是否占据第一视线；当前可执行对象是否可读可点；当前结算是否贴近来源 / 目标并分层显示；归档 / 历史 / 大集合是否降为边缘入口或抽屉；大块空白是否承担真实职责。任一项没有裁决时，不得生成下一版 artifact、HTML 预览、位图设计稿或 AI PASS 审计。
- 几何审计只算基础工程证据，不算玩家视角通过。若截图中没有元素相交，但玩家仍需要在一团骰子、状态、目标框、小卡、HUD 和标签之间猜下一步，必须撤销通过结论并回到玩家任务链与空间预算重做。
- 当前结算区域按“注意力团块”验收：骰子、伤害、状态、目标高亮、路径线和短标签集中到同一小区域时，即使彼此没有重叠，也可能失败。修正顺序是减少重复信息、拆出层级、把状态贴附宿主、让低权重对象退场；不得把当前主结果移到无关边栏或空白角落。
- 确认 / 取消 / 下一步 / 提交类控件必须有规则或真实交互状态授权。设计前置包必须写清：确认前玩家还能改变什么，确认后系统发生什么，为什么不能直接通过点击当前对象、合法目标、高亮对象或来源卡完成。若规则流程或当前状态没有可撤销选择、多目标分支、支付分支、响应窗口、网络提交或危险不可逆动作，不得为了 UI 完整感造常驻确认按钮；应优先让对象本体、目标高亮和短状态反馈承担交互。
- 使用成熟游戏作对比时，只能比较“交互职责和信息权重”，不能复制该游戏的皮肤、牌区名称或素材语义。若参考游戏把某牌堆放在边缘并点击后展开，新游戏只有在规则同样要求当前阶段高频操作该牌堆时，才允许提升其视觉权重。
- `approved-programmatic-runtime-ui` 不是低质占位许可。血条、蓝条、骰子、计数点、冷却标记等自制 UI 必须先定义来源规则、形状、材质、尺寸层级、状态变化和与主体素材的关系；普通蓝圆、随机胶囊、默认 CSS 图形或与游戏素材不协调的临时形状，默认判为 `REVISE`。
- 视觉风格必须从当前领域核心素材重新推导：主色、材质、密度、动作层级和分区方式应来自当前产品 / 游戏的真实主体，而不是套用通用暗色面板、玻璃卡、厚边框或其它游戏模板。若第一眼看到的是壳层、边框或说明框，而不是领域主体和当前动作，必须回到素材账本重做。
- 任何设计动作开始前，执行者必须能写出一段可复查的启动自证：`本轮读过的规则来源`、`三条以上影响画面的规则结论`、`正式素材如何进入输入链`、`当前人工验收是否允许`。四项缺任一项时，只能补证据或标记 blocked，不能继续布局、风格、prompt、HTML 预览、Open Design run 或实现骨架。
- 如果当前工具链不能把必要素材作为输入、拼接基底、可追溯裁片或运行时渲染来源，本轮只能产出 brief / 缺口清单 / 接线任务；不得把无素材参与的图或页面称为设计稿。
- 用户指出“没看规则”“没用素材”“该用素材处没用素材”“边框太多”“不像这个游戏”或“明显不合适直接用素材的可以自己做 UI”时，默认是设计流程事故。当前候选稿先降为失败候选，再回到本门禁补真相源、素材账本、`approved-programmatic-runtime-ui` 裁定和框体职责，而不是继续调色、改边框或补 prompt 形容词。
- **用户纠正必须形成覆盖账本**：当同一 UI 设计连续被用户指出规则误读、素材缺失、布局拥挤、对象省略、阶段越界、验收误判或同类低级错误时，下一版设计前必须建立或更新一份可复查的纠正覆盖账本。账本至少包含 `用户原话 / 现实问题 / 规则或素材真相源 / 设计门禁 / 当前稿检查方式 / 未覆盖后果`，并在出稿前逐项判定 `PASS / REVISE / blocked`。账本是 drift-check / evidence，不替代本 skill 或项目 skill；若账本发现新规则，必须先回到对应 canonical-source 补规则，再重新审图。没有覆盖账本时，不得把新 artifact、HTML 预览、位图稿或 AI 图面核验送人工验收。
- **用户纠正先分类再回代**：用户反复指出的问题不能直接改写成固定版式规则。先分类为 `通用不变量`、`设计模式`、`本项目基线裁定`、`当前候选修正` 或 `一次性偏好`：通用不变量进入跨项目通用层，设计模式写成可选承载和选择理由，本项目基线进项目 skill / 设计合同，当前候选修正进审计或账本。禁止把“这张稿这样放才对”升级成“以后所有游戏都必须这样放”；也禁止只记局部坐标而不抽象玩家任务、对象职责和验收方式。

### 1. 收集输入

先读离当前动作最近的规则：

- 项目存在 `AGENTS.md` 或 UI 规则索引时先读项目入口。
- 有现成设计系统、组件库、项目 style guide、素材或截图时先读真实来源。
- 如果领域有成熟答案或用户要求商业级复刻，先读 `references/reference-backed-ui.md`，产出参考基线和差距矩阵；不要直接凭空实现。
- 如果领域没有标准答案或用户要求探索原创 UI，先读 `references/exploratory-ui.md`，产出约束、假设、发散方向和收敛矩阵；不要只给单一即兴方案。
- 新游戏或素材驱动 UI 不能跳过素材/规则 intake。
- 需要前端实现时再叠加 `frontend-design`、`ui-ux-pro-max` 或项目 UI overlay。
- 需要位图设计稿时再叠加 `imagegen` 或项目 imagegen skill；用户明确指定 Open Design / OD / opendesign 时，按项目 Open Design 入口产出 artifact，不得强制改走 imagegen。

### 2. 产出设计声明

按任务复杂度产出临时小节或持久文件。若项目已有正式落点，写入项目约定目录；否则在回复中给出可复制结构。

#### 2.1 视觉 UI 设计包先于设计稿

当目标是从规则、玩法、业务流程或复杂领域对象推导界面时，必须先交付**视觉 UI 设计包**，再进入精细视觉稿、Open Design 完成稿、imagegen、HTML 预览或真实前端实现。视觉 UI 设计包回答“界面必须有哪些对象、交互和状态”，但用户可见形态默认是图、草图、带标注截图或 Open Design artifact，不是长文字版。文字表、对象职责、规则结论和空间预算只作内部证据 / 审计附件，除非用户明确要求。

- **用户审核门**：如果用户明确要求“先出 UI 设计，我看过没问题才开始设计稿”，必须停在视觉 UI 设计包交付点；没有用户批准，不得生成精细设计稿、启动 Open Design 完成稿 run、写 HTML mock 或改前端。交付给用户看的默认是一张或一组直观图，不是文字版。
- **设计稿审核门**：如果用户要求先看设计稿，必须停在设计稿交付点；没有用户明确批准该稿，不得进入实现、真实页面验证、移动端适配或用实现截图替代设计稿验收。
- **必须交互元素**：UI 设计必须列出当前玩家能点击什么、点击后进入什么选择态、如何确认 / 取消、哪些目标合法 / 非法、哪些信息隐藏、资源和结果如何反馈。只写布局区块、视觉风格或素材列表不算 UI 设计。
- **饱和交互状态**：UI 设计必须模拟接近真实压力的状态，而不是空桌、首回合空态或理想单对象态。饱和意味着完整、有组织、有主次：当前动作、合法目标、隐藏信息、资源消耗、结果反馈、等待响应和溢出策略都可读；不意味着把素材、面板和标签堆满画面。若界面在饱和状态下放不下、看不懂、无法确认下一步，就不能进入设计稿。
- **设计稿继承约束**：后续设计稿必须继承已批准视觉 UI 设计包的交互结构、信息显隐和状态模型；出图阶段不得重新发明主交互、删掉必要入口或把饱和状态退回空态。

#### 2.2 多设计稿 / 多方案硬门禁

当用户要求“多个设计稿”“多方案”“不同 skill 出不同稿”“哪套最好”或需要并列候选时，必须把多稿当作多条独立设计路线，而不是同一母版的同页变体。

- **基线保留**：进入多稿前，先锁定并记录当前最后一个可用基线稿的源文件、导出图和审计结论；新候选不得覆盖、删除或改写基线。基线只作对照，不自动变成通过稿。
- **独立交付物**：每套候选必须拥有独立 artifact / 源文件和独立导出 PNG/PDF。总览页、联系表、缩略图合集或同一 HTML 页面里的多个区域，只能作为索引或复盘，不能冒充多个设计稿。
- **独立设计轴**：每套候选必须有不同的设计 brief，至少改变主焦点、玩家操作路径、空间比例、信息密度、视觉语法、素材主体职责中的三项；只改颜色、边框、圆角、装饰、标题或局部权重，默认判为同母版失败。
- **子代理分工**：如果同一执行者已经连续产出趋同方案，主 agent 应只负责规则 / 素材约束包、基线冻结、候选编号和验收整合；具体候选可交给多个子代理或独立设计 brief 产出。每个子代理必须拿到不同设计轴、禁止继承点和必须保留的规则 / 素材硬约束。
- **差异矩阵**：交付前必须附差异矩阵，逐项比较基线和每个候选的主焦点、主要点击路径、核心对象落位、可见素材主体、隐藏信息处理、溢出策略和失败风险。矩阵证明不了实质差异时，不得送人工验收。
- **实现冻结**：多稿候选通过 AI 图面核验也只表示“可以给用户选”；用户明确批准某一稿前，不得进入真实实现、移动端适配或用运行页截图替代设计稿验收。

视觉 UI 设计包最低图面要求：

- 一眼能看到当前阶段、当前玩家、当前来源、合法目标和下一步动作。
- 当前可支配对象、可浏览集合、归档入口、隐藏信息边界、资源读数、骰子 / token / 结算层必须在饱和态图上可判断。
- 能直选的真实对象必须以高亮、热区或短标注表现；不要用文字解释代替图上可点性。
- 确认 / 取消必须在图上有规则或状态理由；无理由则不画。
- 背景、地图、牌桌和 overlay 的层级关系必须通过图面看出来；不要靠文字解释“其实可以重叠”。
- 若需要输出对象职责表、守恒表、负向影响清单，默认写入项目证据文件或设计源文件，不作为用户默认验收交付。

牌区名称必须来自规则真相源或项目合同。规则没有“手牌”时，UI 设计、设计稿、artifact class / aria、审计文本和验收描述都不得引入“手牌”或等价的默认手牌区；必须先列出 `规则名称 -> UI 名称 -> 可见性 -> 流转关系 -> 可操作入口`，再画牌区或写交互。

规则命名对象还必须补一列 `交互权重 / 默认位置`：主动作对象才能进入主视线；当前阶段次要但可检视的对象默认贴边、收起或以小牌堆入口承载；归档 / 已消耗 / 公开检视类对象默认不能放进中央舞台，除非规则当前步骤明确要求从其中选择、复活、回收或结算。

| 声明 | 回答的问题 | 最低内容 |
| --- | --- | --- |
| `spec` | 为谁做，覆盖哪些状态，什么算验收 | 用户目标、主路径、空/加载/错误/权限/等待态、验收标准 |
| `domain` | 业务对象和状态如何表达 | 对象、状态、风险/优先级、敏感信息、禁止混用语义 |
| `design` | 视觉系统如何取值 | 密度、token、字体、颜色、间距、动效时长、禁止 hardcode |
| `components` | 信息应该映射到哪些组件 | Badge/Tag/Dialog/Drawer/Button/Table/Card 等组件职责 |
| `craft` | 怎么避免 AI 味和粗糙感 | 层级、空态、动效目的、工艺禁区、信息密度 |
| `template` | 页面骨架为什么这样排 | 区域、主视线、操作入口、响应式去向、承载量 |

详细模板见 `references/design-io-contracts.md`。

### 3. 建执行契约

把设计声明接入真实流程：

- 指定每份声明的读取时机和下游使用者。
- 标记哪些内容是“实现必须守住的结构合同”，哪些只是“概念气质参考”。
- 若后续要出图，明确 imagegen prompt 或 Open Design artifact 只承载设计稿候选，不替代实现验收。
- 若后续要实现，明确代码落点、组件来源、真实路由和截图验收点。
- 对新游戏，先完成项目定义的规则/素材/对象 intake，再按项目 workflow 锁定方案、批准设计并完成真实页面验收；本 skill 只承载可复用的 UI 设计声明、执行契约和 evaluator。

### 4. 评估与回流

实现、设计图或截图出来后，用 evaluator 逐项检查：

```text
issue:
  具体问题，不写泛泛的“不够好”
source:
  回到哪份声明，例如 spec/domain/design/components/craft/template
fix:
  下一轮具体改什么
```

详细评分与回流格式见 `references/evaluator-rubric.md`。

### 5. 交付判断

- 如果用户要的是设计稿，默认交付位图/视觉稿和“前端刚性结构 vs 可降级氛围材质”说明；如果用户明确指定 Open Design / OD / opendesign，Open Design artifact 及其导出审计截图可以作为设计稿候选。无论哪种形态，都不能用未审网页、代码、旧 artifact 或运行页截图冒充已通过的设计稿。
- 如果设计稿或 PC 桌面基线被用户指出未通过，当前状态必须降为 `REVISE / implementation-blocked`；移动端适配与实现验收同时冻结，直到 PC 基线和用户人工批准恢复。
- 如果用户要的是实现，必须先确认设计声明和执行契约已经足够，并回到真实页面验证。
- 如果 evaluator 不通过，继续回流到对应声明或实现步骤；不要用测试通过替代视觉问题已解决。
- 如果用户指出“有标准答案但你做得很丑”，先回到 reference baseline 和 gap matrix，再改代码；不要只微调颜色、圆角或阴影。
- 如果用户指出“没有标准答案但设计不成立”，先回到 exploration baseline、设计轴和 decision matrix；不要把多个方向混在一起硬实现。
- 如果项目已有更具体规范，以项目规范为准，本 skill 只负责把链路串起来。
