# Reference-Backed UI Baseline

用于处理“有成熟答案”的 UI，例如商业棋牌游戏、常见 SaaS 后台、经典移动端模式或用户明确指出已有大量案例的界面。

## 触发

读取本文件，当任务满足任一条件：

- 用户说“商业级”“复刻”“参考很多案例”“有标准答案”“像某类成熟产品”。
- 当前 UI 被评价为“太丑、模板味、不像正式产品、完全不合格”。
- 目标领域已有稳定行业模式，不能靠模型即兴设计。

## 先做参考基线

参考的实际查证、逐功能 PC/移动端覆盖及来源适用性，执行 [UI 主规范](../../../knowledge/standards/ui-change-gates.md#开工门槛)。以下基线从同一份逐功能对照提炼，不以某个功能的参考替其他功能背书。

实现前必须产出 reference baseline，至少回答：

1. **成熟案例的第一眼信号**：用户 3 秒内应看到什么，才会相信这是该类产品。
2. **对象关系**：核心对象在哪里，谁最大，谁承接点击，谁只显示摘要。
3. **状态链路**：主路径每一步的可见状态、当前行动、下一步入口。
4. **视觉语法**：颜色、材质、密度、形状、动效、按钮/卡片/面板家族。
5. **禁区**：哪些模式会暴露原型感，例如调试面板、解释正文、无意义框体、纯程序图形。

如果不能保存版权图，保存抽象基线和可验证观察项；不要复制第三方资产。

## 再做差距矩阵

实现前或重做前写一个 gap matrix：

| 基准要求 | 当前实现 | 差距 | 修复落点 | 验收证据 |
| --- | --- | --- | --- | --- |

差距必须具体到用户看得见的问题，例如：

- “当前玩家只在标题里，座位无高光”
- “对象选择靠代理按钮，不是点击对象本体”
- “底部主对象太小，辅助面板抢焦点”
- “程序化占位冒充正式素材”

禁止只写“提升质感”“优化布局”“更商业化”这类无法验收的词。

## 实现门禁

进入代码实现前，至少要有：

- reference baseline
- gap matrix
- 截图链或状态链要求
- evaluator 的 blocking 项
- 明确哪些是结构必须复刻，哪些只是材质/资产可降级

如果是游戏 UI，还要把规则状态映射到屏幕对象：当前行动、可点击对象、隐藏信息、历史动作、下一步入口。

如果成熟案例的第一眼信号依赖行业对象本体，例如扑克牌牌面、棋子、骰面、地图、头像、token、商品图、仪表盘指标卡，代码实现前必须先裁定这些对象由哪条资源链承载：

- `formal asset`：已有正式素材或可追溯裁切。
- `self-made pending approval`：本轮自制资源，必须有源文件、压缩产物、manifest/索引和用户批准缺口。
- `temporary-placeholder`：只为排障或原型服务，禁止进入完成口径。
- `programmatic fallback`：只能作为缺图容错，不能当成熟 UI 成品。

禁止把“程序化绘制看起来差不多”“HTML/CSS/Canvas 能表达规则”“E2E 里看得到”当成资源链闭合。

## 成品保真门禁

实现后不能只问“链路是否能跑”，还必须逐项核对成品是否真的接近参考基线：

1. **对象保真**：核心对象是否像成熟产品里的真实对象，而不是文字壳、程序图形、调试块或网页组件。
2. **资产保真**：规则对象需要图片/材质/牌面/token 时，是否已进入正式素材链路；若只是自制或程序化替代，必须标为 prototype / self-made pending approval，不能称为商业级完成。
3. **动作保真**：关键操作是否有成熟产品级反馈，例如按压、选中、移动、落点、切换、结果揭示；只有静态状态变化不算完整动效生命周期。
4. **场景保真**：截图第一眼是否能脱离说明识别出该行业/游戏类型；如果还需要解释“这代表什么”，默认不通过。
5. **证据保真**：必须用真实页面截图链和肉眼 verdict 证明，不得用 E2E 绿灯、DOM 存在、canvas 非空或代码行数替代。

如果任一项不达标，结论只能写成“技术链路通过 / 商业方向骨架 / 可继续推进”，不得写成“商业级复刻完成”。

成品复看时必须至少抽查一组核心对象的资源化证据：源文件、运行时压缩物、运行时代码消费、真实截图同屏可见。只看到截图里有对象，不足以证明不是程序化 fallback；只看到 manifest 有资源，也不足以证明真实页面消费了它。

## 截图验收

截图集合由已锁定功能、状态及 [E2E 独特界面采集合同](../../../knowledge/standards/e2e-verification.md#独特-ui-状态采集合同) 推导，不固定要求五张，也不机械重拍未变界面。每张需要重审的图回到同一份逐功能对照与 gap matrix，说明已解决的差距和未证明项。

截图如果暴露以下任一情况，必须回到实现或资源链，不得通过：

- 关键对象仍像纯文字壳、调试图形、程序化几何图或网页组件。
- 资源已落盘但截图未证明真实页面消费。
- 图面需要旁白解释“这是什么成熟产品/游戏对象”。
- 交互只改变静态状态，没有按压、选中、移动、落点或切换反馈。
- 多步链路里只有第一张好看，后续状态退回占位或低保真对象。

## 回流到 skill

如果实现后仍被用户判定不合格，按这个顺序回流：

1. reference baseline 是否太抽象，没抓住行业第一眼信号。
2. gap matrix 是否漏掉了真实可见问题。
3. design 是否只写气质，没有可执行 token / 对象比例 / 承载位置。
4. components 是否把业务对象错误映射成网页组件。
5. craft 是否放过了程序化占位、解释正文、脏影、框体过多或主对象过弱。
6. evaluator 是否只看测试通过，没有肉眼截图审计。
