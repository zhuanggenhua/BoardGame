# Exploratory UI Baseline

用于处理“没有标准答案”的 UI，例如原创玩法、新型交互、未成熟工具、混合型 dashboard 或用户明确要求探索方向的界面。

## 触发

读取本文件，当任务满足任一条件：

- 用户说“没有标准答案”“不知道该长什么样”“先探索设计方向”。
- 目标领域没有稳定商业范式，成熟案例只能类比不能直接复刻。
- 规则、素材或业务流程是新的，现有 UI 只能作为局部参考。
- 上一版 UI 像模板，但问题不是“没照成熟案例”，而是设计假设没有被验证。

## 先锁约束，不先画样子

实现或生图前必须产出 exploration baseline，至少回答：

1. **不可变约束**：规则对象、玩家目标、必须常驻的信息、隐藏信息、平台尺寸、素材能力。
2. **核心循环**：用户反复完成什么任务，当前界面服务哪一步；节奏由实际产品决定。
3. **主要风险**：用户可能看不懂什么、点错什么、误判什么、信息过载在哪里。
4. **可借鉴类比**：只借交互或信息结构，不直接照搬视觉皮肤。
5. **待验证假设**：哪些只是设计判断，必须用截图、原型或 playtest 验证。

## 发散必须有轴，不是随机出三版

需要比较多方案时，提出沿不同设计轴发散的方向；用户只要求一个方向时，可先评估候选思路并收敛为一条有依据的方案：

| 方向 | 设计轴 | 核心假设 | 适合场景 | 主要风险 | 验证方式 |
| --- | --- | --- | --- | --- | --- |
| A | 信息架构 |  |  |  |  |
| B | 空间隐喻 |  |  |  |  |
| C | 交互模型 |  |  |  |  |

常见设计轴：

- **信息架构轴**：状态总览优先、任务流优先、对象图谱优先。
- **空间隐喻轴**：牌桌、地图、时间线、工作台、仪表盘、故事书。
- **交互模型轴**：对象直选、分步向导、命令面板、拖拽编排、上下文菜单。
- **密度轴**：专家高密度、首次使用低密度、双层渐进披露。
- **情绪轴**：竞技、探索、经营、仪式感、轻量工具。

禁止只做“颜色不同 / 圆角不同 / 风格不同”的伪三版。

## 快速证伪再收敛

每条方向都必须配一个最小验证问题：

- 第一次看的人能否在 3 秒内说出“我现在要做什么”？
- 当前唯一主动作是否贴近真实对象？
- 核心对象是否比辅助状态更大、更靠主视线？
- 错误操作是否被视觉层提前阻止或弱化？
- 高信息状态下是否仍能看出主路径？

收敛时写 decision matrix：

| 标准 | 权重 | 方向 A | 方向 B | 方向 C | 结论 |
| --- | --- | --- | --- | --- | --- |
| 主路径清晰 | 高 |  |  |  |  |
| 规则对象承接 | 高 |  |  |  |  |
| 实现成本 | 中 |  |  |  |  |
| 扩展性 | 中 |  |  |  |  |
| 风格独特性 | 中 |  |  |  |  |

只能把胜出方向进入实现。落选方向必须记录为什么放弃，不能在后续实现里混搭成无边界 UI。

## 实现门禁

进入代码实现前，至少要有：

- exploration baseline
- 与用户范围匹配的设计方向；需要比较时说明不同设计轴
- 每条方向的核心假设和主要风险
- decision matrix 和胜出方向
- 当前版本的可验证截图链或原型验收问题

如果是游戏 UI，还必须把规则动作映射到屏幕对象：当前行动、可点击对象、历史状态、失败反馈、下一步入口。

## 探索成品门禁

没有标准答案时，也不能把“方向新颖”当成实现通过。胜出方向进入代码后，必须额外证明：

1. 核心对象在成品里仍然强于装饰、说明和框体。
2. 第一次进入、高信息状态、等待/错误态都能验证最初设计假设。
3. 自制素材、程序化纹理或临时图形是否足以表达规则对象；不足时必须标为素材缺口，而不是把缺口解释成“原创风格”。
4. 若实现偏离 decision matrix 的胜出方向，必须回到矩阵重新裁定，不能把多条方向混搭成无边界 UI。
5. 真实截图若推翻假设，要回流到 exploration baseline；不能用测试通过覆盖假设失败。

## 截图验收

没有标准答案时，截图验收不是“像不像参考”，而是验证假设是否成立。按实际适用状态选择截图链：

1. 首次进入态：能否看懂目标和第一步。
2. 第一次操作前后：能否看出点击对象和状态变化。
3. 高信息密度态：能否保持主路径清晰。
4. 错误/等待/不可操作态：能否防止误判成卡死。
5. 完成或交接态：能否看出结果和下一步。

每张图都要回到 exploration baseline：哪些假设被证明，哪些被推翻。

## 回流到 skill

如果实现后仍被用户判定不合格，按这个顺序回流：

1. 约束是否漏了真实规则对象或平台限制。
2. 方向是否只换皮，没有沿设计轴发散。
3. 假设是否无法被截图或 playtest 验证。
4. 收敛是否没有 decision matrix，导致多方向混搭。
5. craft 是否放过模板壳、解释正文、主对象过弱或交互不可发现。
6. evaluator 是否只看“看起来不错”，没有验证玩家目标和主路径。
