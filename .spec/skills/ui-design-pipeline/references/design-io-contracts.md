# Design I/O Contracts

用于把模糊 UI 需求拆成设计声明和执行契约。只加载与当前任务相关的部分。

## 链路顺序

1. **理解规划**：把一句话需求变成目标、用户、状态、边界和验收。
2. **参考基线**：如果该 UI 有成熟答案，先写 reference baseline 和 gap matrix，再进入骨架。
3. **搭骨架**：确定信息区域、主视线、操作入口、密度和响应式去向。
4. **填充组件**：把业务语义映射到正确组件，不把不同职责混成同一种标签。
5. **细化工艺**：补空态、加载、错误、动效、层级、token 和视觉细节。
6. **评估回流**：按声明逐项检查，失败时回到对应环节。

## 最小通过标准

- 用户目标、主路径、边界态和验收口径同时存在。
- 有成熟答案的 UI 已先建立参考基线和差距矩阵。
- 没有标准答案的 UI 已先建立探索基线、不同设计轴和收敛矩阵。
- 业务语义有组件映射，不靠视觉外观猜职责。
- 视觉取值来自 token、设计系统或明确记录的缺口。
- 骨架说明主视线和主操作入口，不只是组件清单。
- evaluator 能指出问题回到哪份声明。
