# Mage Wars UI Design Memory

这是 BoardGame 项目内、Mage Wars 设计稿与真实 Board/UI 实现专用的用户纠偏索引 / drift-check。它只记录 Mage Wars 的具体对象、素材职责和用户纠正实例；通用 UI、响应式、动效、E2E、看图和审计方法均以 `.spec/knowledge/standards/` 与对应项目 skill 为准，本 skill 不承载这些规范正文。

## 角色与优先级

- 本 skill 的角色是 `drift-check / evidence`，不是 `canonical-source`。它只能提醒 Mage Wars 专项对象是否被漏掉、职责是否混淆、送验前是否踩过用户纠正项。
- 多端布局、PC/移动同构、手机横屏、是否新增移动专用承载，以 `.spec/knowledge/standards/ui-responsive-layout.md` 为唯一规范正文；不得用本 skill 的底部空间、槽位分离或基础布局自审条款覆盖它。
- 可见 UI 改动门禁以 `.spec/knowledge/standards/ui-change-gates.md` 为准；通用 UI/UX 以 `.spec/knowledge/standards/ui-ux.md` 为准；动效和特效以 `.spec/knowledge/standards/animation-effects.md` 为准；E2E 与截图证据以 `.spec/knowledge/standards/e2e-verification.md` 为准。
- 用户开图由项目 `show-image-to-user` skill 决定，正式图面审计由项目 `ui-audit-loop` skill 决定。本 skill 不授权“每轮截图 / 每轮打开图片”，也不把技术截图落盘解释成可送人工验收。
- 若本 skill 的历史措辞能被解读为要求改布局、改移动 HUD、新增承载或顺手重构，应先回到上述规范裁决；确认冲突时修正或删除本 skill 的问题措辞，而不是在更下层加反向覆盖。

## 使用顺序

1. 先按 `.spec/knowledge/README.md` 选择本轮真正命中的规范正文；涉及 PC/移动、横屏、响应式或承载变化时，必须先读 `ui-responsive-layout.md`。
2. 当前任务确实涉及 Mage Wars 设计稿、真实 Board/UI、用户标注图或送验自审时，再读本 skill 作为专项 drift-check。
3. 锁定用户当前指出的**具体对象**，不要把一个局部问题扩大成整套 UI 重排，也不要把特效、技能流程或 E2E 修复顺手升级成 HUD / 移动布局改版。
4. 改 Open Design artifact 前，写一段“用户原话 -> 本轮动作”的自审；若本轮不是设计稿 / UI 布局任务，只记录风险或后续项，不直接重构布局。
5. 改 Open Design artifact 前，先更新并消费 `docs/games/mage-wars/design/reference/user-correction-traceability-ledger.md`；它是本主题的纠正覆盖账本 / drift-check，不是独立规范来源。
6. 出图后，按当前任务合同、上位规范、“用户原话反思表”和纠正覆盖账本逐条判定 `PASS / REVISE`；有任一条犯错，不得送人工验收。
7. 用户可见交付默认给图：Open Design 截图、草稿图、标注图或真实 UI 截图；是否打开、何时打开、打开哪些图，必须服从项目看图和 UI 审计规范。规则对象覆盖矩阵、纠正账本和自审结论只作内部证据或最终极短回执。

## 规则到 UI 到实现执行顺序

本节只在 Mage Wars 设计稿、真实 `Board.tsx` / UI 实现、实现截图送人工验收这三类任务中作为专项检查表使用。它约束“规则对象是否被正确承载”，不替代通用 UI、响应式、动效、E2E 或看图规范；任何一段都不得只看最后一张图或只看 E2E 结果。

1. **先锁规则对象**
   - 当前轮次重新读取规则真相源、素材 / atlas 合同、区域锚点合同和本 skill。
   - 写出本轮画面里每个规则对象的现实职责：当前主对象、仍可用候选、可浏览归档、隐藏信息或程序化运行态 UI。
   - 规则没有的概念不得进入 UI 文案、class、aria、审计或汇报；用户口语里的“手牌”只在解释时映射为规则术语 `法术书`，不得上屏。

1.5. **建立规则对象覆盖矩阵**
   - 任何 UI 设计、Open Design artifact、真实 `Board.tsx` 实现或实现截图送验前，必须先建立或更新 `规则对象 -> UI 承载` 覆盖矩阵；不能只靠最后一张图或用户纠正账本倒推有没有漏项。
   - 当前项目默认落点是 `docs/games/mage-wars/design/implementable/rule-to-ui-element-list.md`；它负责把规则、TTS / Workshop、atlas 和素材合同提炼为布局、交互和 UI 元素输入。运行时截图覆盖表只能作为 evidence / drift-check，不能替代这份设计前置清单。
   - 每一行至少写清：规则对象、规则真相源、当前阶段职责、默认可见性、实体锚点、玩家可执行动作、素材来源 / `approved-programmatic-runtime-ui` 裁定、截图验收方式。
   - Mage Wars foundation 最低覆盖行包括：2x3 竞技场区域、法师战场实体、玩家 / 法师提示卡、法师牌详情 / 规则回看入口、双方学徒法师生命 24 / 法力 / 聚魔、己方法术书 6 张、己方已计划法术 2 张、对手已计划卡背、公开弃牌堆正面 + 数量 + 展开入口、隐性结界 / 隐藏信息卡背、攻击骰、效果骰、伤害状态 / 伤害数值、燃烧 token、守卫 token、行动 token、来源对象、合法目标高亮、可移动区域高亮、当前阶段 / 当前动作、回合结束入口。
   - 矩阵中的每一行必须有明确结论：`visible`、`collapsed-with-visible-entry`、`hidden-by-rule`、`out-of-scope`、`blocked` 或 `approved-programmatic`。没有结论的对象按遗漏处理，当前稿不得 `AI_PASS`。
   - 用户纠正账本里的每一条纠正必须回指到矩阵中的至少一行；若找不到对应规则对象，先补规则对象裁定，再改设计或实现。

1.6. **法师对象职责与 v80 基线裁定**
   - `法师战场实体 / 法师本体`：代表法师本人在竞技场中的当前位置、来源 / 目标身份、伤害状态、守卫 / 状态 token 宿主。数字 UI 中不得用密密麻麻写满能力文字的法师规则 / 提示卡当场地本体；场地本体必须优先使用人物可识别素材、模型、standee，或由人物素材裁定出的轻量战场实体标记。主锚点是 `mageZoneId` 所属区域；当该区域还有生物 / 魔物时，法师必须进入同一方的场上单位集合、同一尺寸预算和同一密排算法，不得另起法师层或被场上生物 / 魔物挤没。
   - `玩家 / 法师规则提示卡`：承载法师能力、玩家归属和当前操作归属的规则参考；它不是战场实体，不占竞技场区域锚点。当前 v80 基线按用户反复标注裁定为放在玩家 HUD / 玩家面板；未来若重做布局，必须先说明替代承载如何保持“提示 / 参考”和“战场实体”分离，并经用户重新认可。
   - `法师规则 / 提示卡详情`：从规则提示卡或法师本体打开的放大 inspect / 规则回看层；它引用规则提示卡，不再创造第二个可操作法师实体。
   - TTS / atlas 中同一法师若同时存在文字规则卡与人物 / 肖像 frame，必须先查 `CardID`、图面密度和对象职责；禁止凭变量名把 `card` 用到所有位置。当前 foundation 已知基线：邪术师 `2600`、女祭司 `2605`、兽王 `2606`、巫师 `2603` 是密集文字法师规则 / 提示卡，当前 v80 基线放在玩家 HUD / 规则回看；邪术师 `2601`、女祭司 `2604`、兽王 `2607`、巫师 `2602` 是人物 / 肖像 frame，当前 v80 基线放在竞技场作为法师本体素材。
   - 代码 / 测试 / 审计命名必须拆开：战场实体使用 `mage-entity` / `mage-battle-entity`，HUD 规则提示使用 `mage-hud-rule-card` / `player-rule-hint-card`，放大规则详情使用 `mage-rules-card` / `mage-reference-card`；禁止继续使用 `identity-card` 这类无法区分职责的名称作为验收锚点。

2. **再定唯一实体锚点**
   - 每个可见规则对象只能有一个主实体锚点；选中、已计划、来源、目标、摘要、详情、inspect 都只能引用这个实体，不得画成第二个可操作实体。
   - 场上对象先分配 `zoneId` 和锚点，再决定高亮、token、骰子和结算层。
   - 弃牌堆先裁定公开归档 / 当前候选 / 隐藏信息；公开归档默认正面半露 + 数量，不能用卡背伪装成未知信息。

3. **再落交互链**
   - 主交互默认是 `选来源对象 -> 高亮合法目标本体 -> 点击目标本体 -> 结算层锚定来源 / 目标`。
   - 没有规则或系统授权时，不得常驻确认 / 执行 / 取消。
   - 攻击骰、效果骰、伤害状态、燃烧 token、守卫 / 行动 token 是用户点名的规则信息；设计和实现都不能为了画面干净删掉。按 `ui-change-gates.md` 的主源判别：守卫 / 护卫、燃烧、行动准备等是离散规则身份或后续规则会引用的状态，必须用真实 Mage Wars token 图或等价正式状态物件；守卫状态和守卫动作入口都贴宿主中下方，不做右上角按钮堆、护盾 icon 或小卡片壳。墙体法术的交互目标是两个区域之间的边界，边界热区可以承接选择；但结算后的可见墙体对象必须消费 `sourceSpellCardId` 对应的正式墙法术牌面 / 墙牌素材并贴在该边界上，不得只用泛化彩色墙条、纯 CSS 渐变、文字壳或场上生物卡位冒充。其它单位能力入口不是场上规则牌或 token；当前真实 Board 采用类 Summoner Wars 的触发模型：先点来源单位 / 法师本体，来源本体保持选中 / 来源框；顶部横幅 / 阶段条只承载描述和提示，不承载能力按钮；一级能力按钮进入屏幕中下统一动作 dock，点能力后合法目标回到棋盘 / 场上对象本体高亮。能力按钮不得锚到格子角落、守卫 token 轨、状态 token 轨、顶部描述横幅或用牌面缩略图 / 小卡片壳冒充实体。伤害是连续累计数值，当前真实 Board 默认用本体受伤遮罩 + 类 Summoner Wars 的贴宿主剩余 / 总生命读数承载，读数默认 hover / 聚焦显示，眼睛按钮切换全场常显；不强制复刻物理伤害 token 图，也不得用右下角圆形数字球、爱心 / 护盾等通用 icon 冒充状态或伤害。

4. **实现前逐条消费账本**
   - 真实 `Board/UI` 实现前必须读取 `user-correction-traceability-ledger.md`，并把每一条映射到代码或截图里的承载位置。
   - 只照 v75 最终图的大概构图实现，漏掉用户纠正过的对象、规则术语、隐藏信息、分页样式、公开弃牌堆正面或骰子 / token，一律判为实现未完成。

5. **实现截图再验收**
   - E2E、lint、单测只能证明链路可运行，不能证明 UI 通过。
   - 设计稿和真实 `Board/UI` 的验收截图必须是规则对象齐全的饱和交互态；空开局、无已计划法术、无公开弃牌、无骰子 / token、无结算链的截图只能作为技术诊断，不能作为 UI 验收图。
   - 实现截图必须逐项对照：v75 原图、v75 审计、几何证据、区域锚点合同、本 skill 和纠正覆盖账本。
   - 任一用户点名项缺失、弱化、误用规则术语或低质替代，判 `REVISE`，不得打开给用户人工验收。

## 用户原话反思表

每次设计稿送验前，至少逐条回答：

| 用户原话 / 意图 | 送验前必须反思 |
| --- | --- |
| `分页按钮就保持原样啊` | 如果用户只质疑页码 / 占位比例，不得顺手改变分页按钮的样式、方向、位置和视觉语法。需要改页码时，只改页码或占位，不改按钮本体。 |
| `页码占据这么大空间合理吗` | 问题是页码 / 分页读数的视觉占比是否合理，不是“页码没有职责”。分页可以存在，但不能撑出大空槽或成为主对象。 |
| `为什么要放底下` | 除非用户明确要求，分页按钮不得被挪到最底边、右下角或远离法术书卡列的位置；按钮应贴近法术书浏览本体。 |
| `是没地方放页码吗` | 页码是附属读数，可以并入容量读数、贴在书页边角或放在按钮附近；不能因为找页码位置就牺牲按钮样式或卡牌可读性。 |
| `卡牌是没写费用吗非要你来写` | 卡面已有的名称、费用、类型、射程和效果，不要机械复写成外部 chip；如果看不清，先解决卡面尺寸 / 检视层。 |
| `规则上有手牌吗` | Mage Wars 这里用 `法术书`、`已计划法术`、`弃牌堆`、`对手已计划法术卡背`，不得写成手牌或默认持牌区。 |
| `不要凭直觉设计，一切基于规则` | 每个常驻对象必须能回到规则或用户标注：法术书、已计划、弃牌堆、骰子、效果骰、token、法师战场实体、玩家 / 法师提示卡、法师牌详情、区域格。 |
| `开放式设计 / 场地直选优先` | 能由棋盘格、场上卡、token、骰子等真实对象承接的动作，优先让本体高亮和直选；不要新增代理面板、问号块或第二目标卡。 |
| `玩家提示卡在场地，不应该是角色头像这个吗` | 当前玩家是谁、当前玩家下一步做什么，默认挂在当前法师头像 / 角色 HUD 上；竞技场和场上卡只承接来源、合法目标、token、骰子和结果高亮。不得把“选择目标 / 行动中”这类玩家提示做成卡在地图中央或顶部的第二提示条。 |
| `法师的提示卡，和代表法师本人的卡不是一个东西` | 必须先拆 `玩家 / 法师规则提示卡`、`法师战场实体 / 法师本体`、`法师规则 / 提示卡详情` 三行对象矩阵。核心不是固定位置，而是提示 / 参考、战场实体、详情三种职责不能混成一个对象。 |
| `场地里的红框牌密密麻麻写满了字是提示卡` | 看到密集规则文字时，先裁定它是提示 / 规则参考，不得因为它叫 mage card 就放进竞技场当法师本人。当前 v80 基线用人物可识别素材承载场地本体。 |
| `规则提示卡和玩家卡图的位置错了，应该交换` | 这是 Mage Wars v80 基线裁定，不是全局 UI 规范：场地红框位置 = 人物 / 肖像法师本体；玩家面板 / HUD 红框位置 = 密集文字规则提示卡。后续如果改布局，必须先解释新承载如何不再混淆这两个职责。 |
| `地图是最下层，不要被底图支配` | 竞技场底图是底层，不是不可覆盖矩形；保护格子语义、场上实体、token、骰子和关键文字，不保护低权重石砖纹理。 |
| `弃牌堆是给人看的吗` | 弃牌堆是公开归档入口，不是隐藏信息；默认显示所属、数量和紧凑顶牌正面 / 半露正面。降权用尺寸、透明度、角度、边缘位置和“归档”语义，不得用卡背把公开信息画成未知牌。除非当前规则步骤要从中选择，不常驻展开完整清单或正面大卡。 |
| `确认使用的位置真的需要吗` / `别显示确认了` | 没有规则授权的确认 / 执行 / 取消常驻按钮不得出现；选中来源后应高亮合法目标并直接承接动作。 |
| `骰子、token 都被你省略掉了` | 用户点名的规则信息不能为了干净而删除，但必须先辨别承载职责：攻击骰、效果骰、燃烧 token、守卫 / 行动 token 必须在饱和态可见；伤害是连续数值状态，当前真实 Board 用本体受伤遮罩 + 贴宿主剩余 / 总生命读数承载，不强制显示物理伤害 token 图。 |
| `伤害 token 没必要，现代 UI 代替更合适` | 伤害不是必须复刻的离散 token 物件；送验前检查伤害是否贴在受伤对象本体、数值是否可读、是否来自正式 damage 状态、是否采用同游戏或平台成熟样本中的条 / 遮罩 / 读数，而不是孤立 HUD 文本、右下角圆形数字球或无来源通用 icon。 |
| `守卫必须用 token，伤害可以走现代 UI` | 先按状态职责判别，不按“有没有 token 图”机械照搬：守卫 / 护卫是离散规则身份、行动义务或目标保护关系，必须有真实 token 图或等价正式状态物件；守卫状态和守卫动作入口都贴宿主中下方，不能做成右上角按钮堆、护盾 icon 或小卡片壳。伤害是连续累计数值，优先用贴宿主的进度、遮罩或生命读数，禁止用右下角圆球把它伪装成另一种 token。 |
| `护盾、爱心，右下角圆球都是什么鬼` | 这是 Mage Wars 的素材语法纠偏：守卫 / 状态不得用通用护盾或爱心图标替代真实 token；治疗 / 能力动作若没有正式 token，应优先用来源牌面、法师头像、正式对象或文字 fallback 承载；伤害 / 血量参考 Summoner Wars 的受伤遮罩 + 剩余 / 总生命读数，不用右下角圆形徽章。 |
| `守卫不是说放中间下方吗？现在上面守卫底下那个是什么鬼东西？怎么有个小卡片在那里？` | 守卫不是动作栏里的小卡片按钮，也不是和其它能力卡堆在一起的竖向控件；守卫状态 token 和可点击守卫动作 token 都要贴选中宿主中下方。其它能力入口不能贴守卫附近，也不能锚到格子角落或顶部提示横幅；应进入屏幕中下统一动作 dock，来源仍由单位 / 法师本体选中框表达。 |
| `为什么有个守卫单位的小牌` | 先判断它是否真是规则对象：守卫只能是守卫 token，单位能力入口不是场上小牌。能力触发应复用 Summoner Wars 的职责分层：来源本体可选 / 选中；顶部横幅只做描述；能力按钮在屏幕中下统一动作 dock；目标回到棋盘本体高亮。测试必须证明能力入口没有 `source-card` 缩略图、没有图片小卡片，且 placement 是 `middle-lower-action-dock`。 |
| `能力按钮改到屏幕中下位置吧，上面显示横幅代表描述` | Summoner Wars 的顶部横幅是状态 / 描述提示，不是按钮容器；Mage Wars 能力入口必须放在屏幕中下统一动作 dock。顶部区域只保留阶段 / 描述提示和必要视图开关，不能再把能力按钮放回顶部横幅。 |
| `伤害的显示要和召唤师保持一致，不要给我乱搞。也加一个眼睛来控制显示` | Mage Wars 伤害读数沿用 Summoner Wars 的显隐合同：红色受伤遮罩常驻在受伤对象本体，剩余 / 总生命读数默认 hover / 聚焦显示，眼睛按钮切换全场生命读数常显；不得把读数改成永久压牌面的自创样式。 |
| `墙的法术是哪条规范让你不直接把墙的牌摆上去的` | 没有规范授权用泛化墙条替代正式墙牌。墙体目标仍是区域边界，点击和高亮锚在边界；结算后玩家看到的墙体对象必须来自源墙法术牌面 / 墙牌素材，贴在对应边界上，并由 E2E 断言 `sourceSpellCardId` 的墙牌预览可见。 |
| `描边不贴边` | 这是几何问题，不是“整格高亮 vs 对象高亮”的语义问题；检查目标描边是否沿目标卡牌 / 法师本体可见边界，不能用外扩悬浮框、CSS outline 或圆角不一致的框冒充贴边。 |
| `选中没有更好的效果吗，避免选中等效果改变布局` | 选中态只能描边、抬升、发光、短状态贴附或临时检视，不得生成左右特大牌、第二实体或挤压布局。 |
| `你看不出布局的问题吗，下面为什么还有空隙` | 删除底部文案、容量条、按钮或面板后，释放出的空间应回到法术书、已计划法术、弃牌堆、分页或回合结束等真实对象；但这只在本轮已授权布局稿、布局实现或送验收口时触发重排。若当前任务是技能、特效、流程或测试修复，只能记录为布局风险 / 后续项，不得顺手重构 HUD 或移动端承载。 |
| `手牌现在也有问题，计划牌也是你是真的看不出来吗` | 用户口语说“手牌”时，若标注或上下文指向底部可用牌列，按规则术语映射为 `法术书牌列`；不得用“规则没有手牌”回避布局问题。送验前必须同时审 `法术书牌列` 和 `已计划法术`：它们要可读、可辨、各有槽位，不得和分页、弃牌、回合结束互相挤压。 |
| `这种基础的东西我不希望每次再说` | 基础布局自审必须前置：空隙、挤压、主次、可读性、槽位分离、标签/按钮归属、计划牌是否像当前来源。只要自己能看出问题，不得打开人工验收图，也不得停在“候选”。 |
| `每次设计完毕都用我的话反思一下` | 最终回复和审计必须有“按用户原话自审”的明确结论；不能只报几何、DOM 或 OpenSpec 通过。 |

## 分页专项裁决

- 按钮本体：保留用户已认可 / 已标注的样式和贴近法术书的位置；不要把按钮缩成小圆点、挪到屏幕底边或改成无关方向。
- 页码读数：是附属信息，优先轻量放在按钮附近或容量读数中；不得独立撑出大栏。
- 卡牌优先级：法术书当前页卡面比页码更重要；分页调整不得让卡牌变小、不可读或被底图挤走。
- 热区与可见面分离：实现阶段可用透明热区补点击面积，但设计稿里的可见按钮面不能为了触控下限变成主对象。

## 法术书 / 已计划 / 底部空间裁决

本节只描述 Mage Wars PC 基线和规则对象职责。若改动触及移动端、横屏、响应式、承载替换或 PC/移动同构，先回到 `ui-responsive-layout.md` 裁决；本节不得作为新增移动布局、隐藏 PC 同源承载或重排 HUD 的授权来源。

- 法术书牌列是当前可支配对象集合，不是底边装饰条。它必须在 PC 100% 缩放下能读出卡面主体，并和分类标签、分页 rail 形成同一浏览组件。
- 已计划法术是当前可施放来源，不是右下角挂件。它必须有独立计划槽，至少能看清卡面、数量和当前来源态；不得被分页、弃牌堆或回合结束按钮挤成一团。
- 弃牌堆是公开归档，不是隐藏区。PC 主态默认用紧凑顶牌正面 / 半露正面 + 数量表达可检视内容；只有对手已计划法术、未公开法术书内容和隐性结界这类隐藏信息才强制卡背。
- 底部空隙必须有职责。若只是删掉底部文案 / 容量读数 / 面板后留下的空带，在已授权布局收口任务中必须回到上位 UI 规范和对象矩阵重排，直到空间回到法术书、已计划法术、弃牌堆、分页或回合结束等真实对象；非布局任务不得借此顺手改版。
- 槽位分离必须用整屏图验收：己方法师状态、左侧分类标签、法术书牌列、分页 rail、已计划法术、弃牌堆和回合结束都要同时可见，并逐项检查是否相交、抢焦点或职责不清。
- 几何不相交只是底线。若玩家第一眼仍觉得牌列像硬塞、计划牌像角落挂件、底部留白像死区，当前稿仍是 `REVISE`。

## 送验最低回执

每次打开给用户人工验收前，写清：

- 本轮用户当前反馈对象是什么。
- 本轮是否授权 UI 布局 / 设计稿 / 送验收口；若只是技能、特效、流程或测试任务，发现布局问题只能记录为风险 / 后续项，不得顺手改已定 HUD 或移动布局。
- 若涉及 PC/移动、横屏或响应式，`ui-responsive-layout.md` 的裁决结论是什么；本 skill 只补 Mage Wars 专项 drift-check。
- 哪些元素保持原样，哪些元素被改动。
- 是否删掉或弱化了用户点名元素；如果有，必须说明规则阶段互斥或用户授权。
- 规则对象覆盖矩阵是否完整；若有 `out-of-scope`、`blocked` 或 `approved-programmatic`，必须逐项说明现实原因。
- 用用户原话逐条自审的结论。
- 纠正覆盖账本逐项自审的结论；不得只挑当前一条反馈说明。
- 基础布局自审结论：底部是否还有无职责空隙、法术书牌列是否像当前可支配对象、已计划法术是否像当前来源、各槽位是否仍在抢位；任一项未达标时，布局 / 设计稿 / 送验收口任务必须回到上位规范和对象矩阵处理，非布局任务只记录风险 / 后续项，不得顺手重构。
- `AI_PASS` 只表示可人工看图，不表示已批准实现。
- 回执必须短，默认不交长文字版 UI 设计；真正给用户判断的是图面本身。
