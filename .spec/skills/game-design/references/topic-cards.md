# Game Design Topic Cards

本文件是给 AI 执行的设计判断卡，不是游戏设计教材。回答时只取和用户问题直接相关的卡片，输出具体建议、取舍、风险和验证动作。

## 立项和框架

### Game Pillars / 项目支柱

- **用在**：新游戏、重做方向、提案、范围失焦。
- **核心判断**：支柱必须是玩家动作或体验承诺，通常 3 条以内，并能合成一句话。
- **执行动作**：检查每个支柱是否会改变镜头、操作、系统、关卡、资源或 UI 决策。
- **失败信号**：支柱只是题材、氛围词或美术风格，无法指导删减。

### Problem Statement / 问题定义

- **用在**：需求太宽、方案互相打架、团队不知道先做什么。
- **核心判断**：问题要有具体对象、可观察结果和能讲给另一个设计师听懂的边界。
- **执行动作**：把“做一个 X”改成“让哪个玩家在什么场景完成什么行为，并用什么现象证明变好”。
- **失败信号**：范围宽到无法验证，或窄到排除了更好的解决路径。

### 80/20 资源判断

- **用在**：资源不足、功能太多、打磨顺序不清。
- **核心判断**：玩家 80% 时间会重复的 20% 动作优先被打磨。
- **执行动作**：列出最高频动作、最高风险摩擦和最常见失败路径，再删减低频花活。
- **失败信号**：把稀有功能做得很精致，但移动、选择、确认、反馈等主循环粗糙。

### Fast / Cheap / Good

- **用在**：排期、预算、质量三者冲突。
- **核心判断**：默认只能保两项，第三项必须明说如何牺牲或约束。
- **执行动作**：若必须快且好，就增加成本或减少范围；若必须便宜且好，就接受慢；若必须快且便宜，就只做验证原型。
- **失败信号**：承诺快、便宜、好三者同时成立，但没有范围下降。

## 核心循环和迭代

### Core Loop / 核心循环

- **用在**：玩法不聚焦、系统堆很多但不好玩。
- **核心判断**：核心循环是玩家愿意反复做的动作链：行动 -> 结果 -> 反应 -> 再行动。
- **执行动作**：用具体动词描述循环，检查是否易懂、易操作、有即时反馈、可变化、可组合、可扩展。
- **失败信号**：循环只能靠奖励、剧情或 UI 解释撑住，本身不值得重复。

### Brainstorming / 发散方法

- **用在**：概念早期或机制卡住。
- **核心判断**：早期用自由联想找可能性；结构已成形后用 flowchart / tree 收敛顺序和层级。
- **执行动作**：先保留多条候选，再按核心循环、资源约束和验证成本筛掉。
- **失败信号**：还没锁问题就写实现清单，或一直发散不进入可测原型。

### Iteration / 迭代

- **用在**：原型、玩法测试、版本推进。
- **核心判断**：每轮只验证一个关键假设，并把结果作为下一轮输入。
- **执行动作**：先做低成本原型；每轮记录假设、改动、观察、下一步。
- **失败信号**：每轮同时改很多变量，导致无法知道哪项有效。

## 机制和平衡

### Flow / 心流

- **用在**：难度曲线、教学、关卡节奏。
- **核心判断**：挑战略高于玩家当前能力；新手、练习者和熟练者需要不同压力。
- **执行动作**：为每阶段定义技能前提、挑战增量、反馈方式和失败恢复。
- **失败信号**：新手被默认知识卡住，或熟练玩家只在重复低压任务。

### Dynamic Difficulty / 动态难度

- **用在**：连续失败、挫败退出、单人挑战。
- **核心判断**：只在非竞技公平场景中，按失败次数、耗时、成功率和放弃迹象做细微调整。
- **执行动作**：小幅降低生命、伤害、数量、时间窗或资源压力；保持玩家仍需努力。
- **失败信号**：明示“系统放水”、调整过大、或在竞技场景破坏公平。

### Reinforcement / 奖惩反馈

- **用在**：失败代价、奖励结构、留存循环。
- **核心判断**：惩罚塑造风险感，奖励塑造重复行为；过重会劝退，过轻会失去意义。
- **执行动作**：明确想鼓励 / 抑制的行为，再选择固定奖励、随机奖励、生命损失、重来、衰减或永久死亡。
- **失败信号**：奖励只延长刷取却不改善决策，或惩罚清掉太多投入时间。

### Min / Max

- **用在**：角色构筑、单位属性、职业 / 卡组优化。
- **核心判断**：允许专精，但专精必须牺牲真实选择空间。
- **执行动作**：用预设值、随机成长、属性互相牵制、主题限制或递减收益控制极端解。
- **失败信号**：某一维数值压倒其它玩法，导致“正确答案”唯一。

### Doubling / Halving

- **用在**：不知道哪个数值真正影响平衡。
- **核心判断**：这是内部设计工具，不是给外部玩家的 A/B 测试。
- **执行动作**：把一个候选变量放大 2 倍或减半，观察体验是否明显变化；无变化则该变量可能不重要。
- **失败信号**：一次改多个变量，或把极端测试值当正式平衡值。

## 关卡、谜题和引导

### Competency / 谜题能力类型

- **用在**：谜题无趣、玩家卡关、辅助机制设计。
- **核心判断**：先判断挑战主要考记忆、操作、观察、推理、空间还是系统理解。
- **执行动作**：按能力类型设计提示、练习、失败反馈和可选辅助。
- **失败信号**：以为在考推理，实际卡在操作或信息不可见。

### Visual Guidance / 视觉引导

- **用在**：玩家不知道点哪里、去哪里、看哪里。
- **核心判断**：可供性、注意力抓取和路径指示必须来自画面对象本身，而不只是说明文字。
- **执行动作**：用形状、颜色、运动、层级、对比、空间朝向和反馈指向下一步。
- **失败信号**：关键对象只靠文字解释，或视觉最强元素不是下一步。

### Environmental Storytelling / 环境叙事

- **用在**：想减少说明文本，提升场景信息密度。
- **核心判断**：环境物件应承载角色、事件、关系或后果，而非纯装饰。
- **执行动作**：先列要传达的信息，再选择空间、道具、破坏痕迹、路径和交互反馈承载。
- **失败信号**：场景好看但玩家无法推断任何玩法或故事事实。

### Pacing / 节奏结构

- **用在**：体验拖沓、过载、留存下降。
- **核心判断**：玩家注意力需要分块、预告、休息和高潮；sandbox 与 rails 需要不同节奏工具。
- **执行动作**：设计预告、短目标、节奏峰谷、恢复点和返回动机。
- **失败信号**：连续高压导致疲劳，或连续低压导致无目标感。

## UI、控制和错误

### User-Centered Design

- **用在**：UI / 交互方案、上手体验、可访问性。
- **核心判断**：先定义真实用户、任务、环境、限制和成功标准，再设计控件。
- **执行动作**：围绕用户目标建流程，测试完整体验，而不是只评单个功能。
- **失败信号**：只按开发结构摆 UI，用户无法从屏幕理解下一步。

### Hick's Law

- **用在**：选项太多、决策变慢。
- **核心判断**：选择数量越多，决策时间越长；但专家模式可接受更多选项。
- **执行动作**：分组、排序、渐进披露、默认推荐和隐藏低频选项。
- **失败信号**：所有按钮同级暴露，玩家第一眼无法判断优先级。

### Fitts' Law

- **用在**：点击、拖拽、瞄准、触控热区。
- **核心判断**：目标越小、距离越远，操作越慢且错误率越高。
- **执行动作**：高频目标更大更近；移动端关键热区至少满足项目触控标准；难度可以通过大小、距离、移动和时间窗调节。
- **失败信号**：高频按钮小且远，或难度来自误触而非策略。

### Error Handling

- **用在**：玩家误操作、漏步骤、流程迷失。
- **核心判断**：先区分操作控制错误、流程多走一步、漏步骤、做错动作。
- **执行动作**：轻错给微反馈，中错给清晰恢复，重错给检查点 / 撤回 / 明确指导。
- **失败信号**：把玩家错误全部归咎为“不认真”，没有恢复路径。

## 玩家心理和测试

### Cognitive Bias

- **用在**：玩家误读风险、奖励、概率或反馈。
- **核心判断**：确认偏误、可得性、锚定、框架效应会改变玩家对同一事实的判断。
- **执行动作**：在 UI、奖励、教程和测试问题里避免诱导性表达，并观察玩家真实决策。
- **失败信号**：用设计者理解替代玩家感知。

### Attribution Error

- **用在**：playtest 反馈被误判、设计师怪玩家。
- **核心判断**：设计师容易把失败归因于玩家能力，而忽略 UI、规则、教程和系统反馈。
- **执行动作**：对每个失败先查环境、信息、控制、反馈和规则入口，再评价玩家理解。
- **失败信号**：测试结论写“玩家笨 / 不会玩”，但没有证据排除设计原因。

### Prototyping / Testing

- **用在**：验证玩法假设、发现上手问题。
- **核心判断**：纸面原型测规则，数字原型测操作和反馈；黑盒看体验，白盒看机制，压力测试看规模。
- **执行动作**：每轮只测一个核心假设，记录观察而非辩解。
- **失败信号**：原型已经像产品开发，但核心乐趣还没被证明。

## 团队、主题和结构

### Team Decision

- **用在**：多人设计、意见冲突、审批链。
- **核心判断**：协作能增加信息，但最终决策权必须清楚。
- **执行动作**：定义谁提出、谁评审、谁拍板、谁验证；共同愿景先于细节投票。
- **失败信号**：委员会式折中让核心体验变钝，或强主导没有解释取舍。

### Theme / Synergy

- **用在**：机制、美术、叙事不一致。
- **核心判断**：主题不是装饰；它应让机制、视觉、音效、文案和奖励互相加强。
- **执行动作**：检查每个系统是否强化同一个玩家幻想；不强化的系统删、改或降级。
- **失败信号**：机制好玩但和题材无关，或题材强但玩法没有表达。

### Golden Ratio / Proportion

- **用在**：布局、节奏、资源比例、紧张感。
- **核心判断**：比例工具只能服务体验目标；和谐、紧张、留白、权重都必须被玩家感知验证。
- **执行动作**：先定义想要稳定、压迫还是强调，再用比例调整空间、时间或资源分配。
- **失败信号**：为了“好看比例”牺牲可读性、操作效率或规则清楚度。

## 输出格式

设计建议默认包含：

- 目标玩家和玩家幻想。
- 当前核心行为或问题对象。
- 推荐方向。
- 主要取舍和滥用风险。
- 下一步原型、测试或观察指标。
