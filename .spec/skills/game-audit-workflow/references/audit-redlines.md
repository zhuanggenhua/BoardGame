# 审计默认执行红线

本文件承载高风险审计红线；主 `SKILL.md` 保留 workflow 骨架与读取入口。
若本文件与 `.spec/knowledge/standards/testing-audit.md`、`testing-audit-core-principles.md`、`testing-audit-dimensions.md` 冲突，先改规范主源，再同步本 reference。

## 默认执行口径（强制）

- **审计不是录入，默认不回卡图（强制）**：审计阶段的默认输入是当前项目里已经存在的规则文档、配置、实现、测试、evidence、已建立的数据合同或用户当轮明确提供的材料；不得把“继续审计”解释成重新读图、重新 OCR、重新查 Wiki、重新抄文本包或重新录入数据。只有用户当轮明确要求“录入/复核录入/核图/核索引”，或当前任务本身就是新增数据录入，才进入数据录入 workflow。
- **先查已有录入合同，不得默认判“没录入”（强制）**：当用户质疑数据是否已录入，或审计发现规则原文、对象归属、能力描述存在缺口时，第一动作必须是在当前仓库既有录入合同、规则原文矩阵、source map、crop manifest、evidence 和状态文件里检索该对象；只有确认这些入口都没有对应记录，才允许说“未找到录入”。若找到的是 `blocked/disputed/待建合同`，结论必须写成“已有录入入口但合同未锁定/归属未裁定”，不得说成“用户没录入数据”或“需要重新录入”。
- **中文录入优先中文汇报（强制）**：若录入合同、卡图、i18n、用户截图或用户故事里的对象名/能力名/规则描述是中文，审计和修复汇报必须优先展示中文对象名、中文能力名和中文规则描述/合同原文；英文官方名、英文原文、能力 id、代码标识只作为附证或定位补充。禁止只给英文原文、英文能力名或代码 id，让用户自己反推中文能力。
- **原文列必须填原文，不得用状态句顶替（强制）**：凡表格列名包含“规则原文 / 合同原文 / 中文规则描述 / 能力描述”，该单元格只能填已录入的逐字原文或明确写“未找到原文记录”。不得填“已有录入入口”“合同未锁定”“对象归属未裁定”“待裁定候选线索”“规则原文/归属未锁定”这类状态句来冒充原文。若原文未找到，必须另列“已查入口/合同状态/下一步”，把状态和原文分开。
- **审计发现来源问题只能登记缺口，不得现场补录入（强制）**：如果审计中发现规则来源不足、对象归属不清、配置与已有证据冲突，只能把该对象标成 `blocked/disputed` 并写清缺的是哪一类证据；不得在审计流程里临时查 Wiki、网页资料、在线文本包、旧脚本 bundle 或第三方数据库来补成“权威结论”，也不得直接因此改机制代码。
- **录入来源优先级只属于录入阶段（强制）**：本地清晰卡图、完整单对象图、用户截图、在线文本包、Wiki、网页文本、OCR、翻译文案、实现字段、旧测试和代码注释之间的优先级裁定，是数据录入/合同建立阶段的事情；审计阶段不得重新排序这些来源。审计只能消费已经落地的合同/证据；没有合同就标缺口，不把卡图读取变成审计必经步骤。
- **已有证据先于新增真相源（强制）**：当对象已有 `locked`、实现矩阵、测试证据或历史 evidence 时，普通续跑先消费这些现有材料进入实现对照、真实入口、负向断言、回放/重复消费和 L3/L4 补证。只有能点名具体缺失字段、冲突对象或用户要求复核，才允许单独开录入复核任务；不得用“数据录入可能不扎实”作为泛化理由倒退阶段。
- **图片/子代理只按当前需求返回结论（强制）**：审计中需要读图、OCR 或让子代理看图时，交给它的是当前业务需求里依赖图片回答的那一部分，不是让它接管整轮任务。若需求是录入，返回原文、子句、结构化字段和合同状态；若需求是验收或对比，返回是否满足用户预期、失败点和最小证据。不得把图片读取结果写成过程文档，也不得让子代理产出泛泛缺口清单，除非当前需求本身就是制作缺口清单。
- **普通续跑顺序（强制）**：当用户说“继续”“更新后继续”“数据录入要做好”时，先读当前 evidence/矩阵/状态文件确定现有状态；若对象已有可消费证据，就继续实现审计，不重读图片、不 OCR、不重新录入。若证据缺失或冲突，只写明缺口并停在 `blocked/disputed`，等待明确进入录入复核；不能把缺口处理伪装成审计继续。
- **图片链路只能由录入任务触发（强制）**：safe-image-reading、atlas 裁图、OCR、图片子代理、卡图逐字读取，只能在数据录入/素材核对/用户明确要求核图时触发；普通机制审计不得主动启动这些链路。
- **修复汇报必须同时附规则原文和现有实现（强制）**：凡修复、候选修复、撤销修复或降级某个卡牌/技能/token/状态能力，最终汇报和 evidence 必须同时写清：中文对象名、代码标识、能力中文名、能力 id、中文规则描述/已消费合同原文、必要的英文官方原文附证、现有实现行为、这次改了什么、当前状态（已证实修复/候选改动/disputed/blocked）和验证证据。禁止用“现有实现描述”替代规则原文；若规则原文尚未找到，原文列必须写“未找到原文记录”，并把合同状态单独标为候选或 disputed，不得称为已证实修复。
- **合同状态变更必须回写 evidence（强制）**：任何对象从 `blocked` 转 `locked`、从 `locked` 降级为 `disputed`，或从待建合同进入实现审计，都必须写入 `evidence/<gameId>/` 的审计文档；临时矩阵可以辅助，但不能替代正式 evidence。
- **审计留档优先集中总账（强制）**：审计要留档，不等于每个 E2E 截图目录都要导出一个 `e2e-test.md`。默认优先把命令、测试结果、关键截图、人工观察、不外推边界和旧结论回写到当前专项审计文档、full-audit 总账或运行态审计真相源。只有截图目录本身要作为独立交付物、没有可承接的上级审计文档，或用户明确要求单独证据包时，才新增目录级说明文档。
- **缺目录说明不得混成功能缺口（强制）**：`e2e-test.md`、截图目录说明或相册说明缺失，只能叫“审计留档未索引 / 截图证据未被总账消费”；不得写成“功能未实现 / E2E 未覆盖 / 基本功能没做到位”。汇报必须分开三类：`功能实现缺口`、`验证缺口`、`审计留档缺口`。
- **审计缺口必须先分类（强制）**：每个 finding / 待补项必须先归入 `功能实现阻塞`、`当前范围验证缺口`、`审计留档缺口`、`非阻塞扩展` 四类之一。功能实现阻塞指规则对象、玩家合法动作、结算结果、最终权威状态或共享消费者确实不对；当前范围验证缺口指实现可能已对但还缺必要证据；审计留档缺口只说明证据没被总账消费；非阻塞扩展指不改变当前发布范围规则正确性的额外覆盖。禁止把后两类写成“功能没实现”，也禁止用“非阻塞扩展未做”阻塞当前规则实现收口。
- **高风险对象先过 fail-close 审计门禁（强制）**：凡对象涉及 `phase/阶段推进`、`pending/continuation`、`共享伤害链`、`共享状态/token 消费链`、`选择支付/拒绝`、`来源例外`、`攻击后续结算`，正式判定“已审过/已收口”前，必须先逐项回答下面四问；缺任一项，默认继续审，不得收口：
  1. **最终权威状态问**：这条对象最终要落到什么权威状态，证据是 `HP/资源/token/区域/阶段/final state` 哪一项？若当前只看到 `prompt/overlay/pending/sourceAbilityId/currentChoice` 之类中间态，只能算命中了流程中段，不能算完成。
  2. **流程收口问**：这次交互或结算结束后，`phase/queue/interaction/pending/continuation` 是否按规则收口？必须至少补 1 条负向断言，明确证明“不会误跳阶段 / 不会残留 pending / 不会卡在 halt / 不会吞后续链”中的至少一项。
  3. **共享链来源问**：若效果进入 shared helper / shared resolver / shared consumer，必须写清“谁授予、谁持有、谁消费、谁清理”，并证明“缺少该来源时不会误生效”。只看最终数值对了，不算通过。
  4. **来源例外问**：若该对象属于共享家族但规则里存在特定来源、特定时机或特定目标例外，必须单列“这个来源不应被家族共性自动外推”的断言；没有这条断言，不得判通过。
- **审计范围必须先锁定，禁止自动升级（强制）**：`审计 / 补审 / 重审 / 继续` 只承接当前任务已明确写出的对象、规则子句、共享链路和证据层级；`全面 / 全量` 也只作用于这份已锁定范围，不等于整批、全牌库或全仓库。
- **新增批次不自动扩全（强制）**：新增派系、角色、英雄或新批次中发现一个漏审项时，先判断它是单对象缺口、共享消费者直接影响，还是用户/任务明确要求的整批审计。没有直接影响证据时，兄弟对象只能登记候选，不得启动同类复核。
- **范围升级必须留证（强制）**：扩审前必须在 evidence / 任务记录里写清触发证据、最小受影响对象集、排除对象及理由；未回写范围表不得生成新的测试或截图队列。
- **“全面审计”具体做什么必须服从审计文档，不得口头缩写**：只要任务、evidence 标题或对外汇报里用了“审计 / 全面审计 / 深入审计 / 收口审计 / 做到底 / 已审计完成”，就必须以 `.spec/knowledge/standards/testing-audit.md`、`.spec/knowledge/standards/testing-audit-core-principles.md`、`.spec/knowledge/standards/testing-audit-dimensions.md` 和 `.spec/knowledge/standards/audit-evidence-template.md` 作为动作清单真相源；执行者不得自行发明“链审计”“代表链差不多看过了”“我这轮主要补了几条测试所以算全面审计”之类缩写口径来替代对象全集、子句矩阵、D 维度、L1-L4、共享链判等和旧结论回写。
- **组合审计只看关键消费者组合（强制）**：审计组合不是穷举所有房间、卡牌、玩家、时机、骰面和状态的笛卡尔积。只有组合会改变合法动作、候选生成、资源消耗、触发时机、流程态、最终权威状态、共享消费者或玩家可见结果时，才升级为必须补证的关键组合；其它仅增加排列数量、不改变规则结果的组合，只能记录为非阻塞扩展或不适用，不得冒充当前实现缺口。
- **漏审可机器发现时必须补脚本（强制）**：如果本轮发现的漏审点可以由 evidence 结构提前暴露，例如缺全面审计自检表、缺对象全集、缺 C1/C2 规则子句、缺实现入口、缺 L0-L4、缺 D 维度、缺最终状态、缺负向断言、缺真实入口或旧结论未回写，则不能只更新文档和当前 bug。必须同步补 `scripts/verify/audit-evidence-completeness.mjs` 或同级机器门禁，并在审计后用本轮 evidence 复跑 `npm run audit:evidence:selfcheck -- <evidence 文件>`；否则只能汇报“规则已补，但审计后自检未补”，不得说防再犯已完成。该自检不默认阻塞发布。
- **房间/场地效果必须作为独立审计对象（强制）**：当当前范围包含房间、地图格、区域、场地、事件触发点或等价非卡牌对象时，审计清单不得只列空间数据、门位、朝向、楼层、图集帧或可渲染状态；凡对象带有规则效果，必须单独列“房间/场地效果”矩阵，逐项覆盖触发时机、目标、掷骰/支付、状态写入、持续时间、清理、负向断言和最终玩家可见结果。
- **卡牌审计必须显式包含具体效果实现（强制）**：当当前范围包含物品、预兆、事件、行动牌、装备牌、状态牌或等价牌对象时，审计矩阵必须在同一对象下同时列出“对象真相/牌堆归属”和“具体效果实现”。前者用于确认审的是正确对象，后者才证明规则生效；只证明牌名、正面图、atlas 格位、抽取顺序、持有区渲染、数量不重复，不得替代该对象的效果实现维度。
- **每回合一次按钮必须审使用后 UI 状态（强制）**：当对象存在“每回合一次 / once per turn / usesPerTurn”且通过按钮或按钮后目标选择发动时，审计证据必须覆盖首次效果、使用次数/资源写入、使用后按钮隐藏或禁用、重复按钮命令不再打开选择与不二次结算。只证明第一次效果落地，不得判该按钮链路已收口。
- **系统交互必须审真实 UI 可见入口（强制）**：当实现创建 `sys.interaction.current`、simple-choice、prompt、状态横幅或等价交互时，不能只把系统状态存在当成 L3 证据。必须继续证明真实 Board/PromptOverlay/StatusBanners/手牌区/棋盘区显示了对应按钮、候选或高亮，并且点击提交的是同一份 `optionId/value`；缺这条只能写“领域交互已创建”，不得写 UI 链路已收口。
- **图片读取只服务需求，不作为交付物（强制）**：当卡图、房间图、规则页截图或其它图片素材是录入/审计真相源时，可以把图片文件直接交给子代理做视觉读取或校验；交给子代理的是业务需求，不是单独看图。需求交接只写当前要补的数据或要验证的判断，例如“从这张卡图录入牌名、规则文本、子句和 locked 状态”或“校验这张房间图是否满足已锁合同”。子代理默认只返回需求结果：录入类返回详细数据；校验类返回是否满足预期、差异和阻塞字段。不得要求子代理单独汇报过程信息；若无法完成，只返回阻塞的具体字段、判断点或交付点。
- **教程/新手引导默认要对齐真实游玩交互（强制）**：只要当前范围包含 `tutorial / 新手引导 / 教学步骤 / onboarding`，审计时必须把每一步提示的“点击对象/高亮目标/按钮文案”与正式牌桌或正式流程里的真实交互承接点逐项对照。禁止出现“正式游玩点按钮，教程却让人点牌堆”“正式游玩点手牌，教程却高亮说明面板”这类分叉；也不得因为底层命令相同，就把教程里错误的点击对象判成通过。
- **教程默认还要审“有没有真正教会玩家”（强制）**：只要当前范围包含 `tutorial / 新手引导 / 教学步骤 / onboarding`，除了交互一致，还必须同步阅读 `.spec/knowledge/standards/tutorial-design.md`，逐项核对：是否先讲赢法、是否解释行动收益、是否有真实案例、是否让玩家看到计分或等价结果反馈。只能证明“教程能走通/按钮点对了”，不得判为教程合格。
- **教程审计结论写回通用层前，必须先过“未来很多游戏”自检（强制）**：如果本轮准备把教程审计结论回写到项目通用 skill、`.spec/knowledge/standards/**` 或其它通用层，必须先确认这条结论约束的是“怎么识别教程问题”，而不是在替当前这个游戏预写“哪章合并、哪章先教、哪条路线更适合示范”。离开当前游戏就不成立的内容，只能下沉到该游戏专项文档、覆盖矩阵或教程实现，不得借“审计经验”之名抬升成通用规则。
- **教程审计一旦开始抽象结论，就立刻做“未来很多游戏”分层，不要事后补判（强制）**：只要审计结论已经开始讨论“教程结构该怎么收”“哪类章节应该合并”“哪种教学顺序更合理”，默认当场先判断这到底是跨游戏判断方法，还是当前游戏的专项答案。后者只能落到该游戏专项文档、覆盖矩阵或实现，不能先写进通用审计规则再回头解释。
- **教程像规则书或按钮说明书时必须直接打回（强制）**：只要当前范围包含 `tutorial / 新手引导 / 教学步骤 / onboarding`，如果文案主要在复述完整规则、堆术语、解释按钮顺序，或离开长段文案后玩家仍不知道为什么这么做，审计结论必须直接判为“不合格/需重写教学结构”；不得因为步骤能推进、断言能通过，就降格判成“教程基本可用”。
- **教程不得靠长段说教替玩家下判断（强制）**：只要当前范围包含 `tutorial / 新手引导 / 教学步骤 / onboarding`，审计时必须额外核对教程关键步骤是否把主要判断交给了真实局面本身，而不是靠长段文案直接告诉玩家“现在该拿哪张/该丢哪张”。若去掉这段长说明后，牌面自身无法解释强弱，默认判为案例设计缺陷，不得用“文案已经解释清楚了”收口。
- **教程里的“判断提示”和“操作提示”不得混成一步（强制）**：只要当前范围包含 `tutorial / 新手引导 / 教学步骤 / onboarding`，必须额外核对：说明步是不是只在提醒玩家该看什么，动作步是不是只在教玩家点哪里。若一个 requireAction 步同时在替玩家下结论、解释收益、又指挥点击对象，默认判为教学结构失焦，需要拆步或重写。
- **教程与正式流程凡涉及一级行动顺序时，必须先审“交互合同”而不是先改文案（强制）**：只要当前范围包含 `tutorial / 新手引导 / 教学步骤 / onboarding`，并且争议涉及“先选行动还是先选目标”“先点按钮还是先点地图/卡牌”“横幅是不是交互入口”“为什么教程从某个地区起手”，审计必须先产出一张 `一级交互审查表`。至少写清：规则书回合骨架、正式 UI 当前一级行动入口、后续目标/地区/支付入口、提示 UI 与真实交互载体的区别，以及教程是否把它们教反。没有这张表，不得进入教程实现或给出“教程已修好”的结论。
- **一级交互不得按当前显眼入口抽样（强制）**：只要当前范围在审“基础回合 / 一级行动 / 主循环入口 / 所有交互”，`一级交互审查表` 就必须先按规则或权威真相源列出同层一级行动的**完整全集**，再逐项映射到当前 UI。不得只因为某几个入口当前更显眼、案例正好走到、E2E 更容易拍，就跳过同层别的一级入口，例如 `打牌`、`升级军备`、`势力行动`、`轮盘行动`、`结束`、`公开区拿牌`、`桌面对象直点` 等。
- **若正式 UI 与规则顺序冲突，不得只改教程粉饰（强制）**：只要审计结论已经证明“规则是先选一级行动，当前实现或文案却把后续目标选择提前成了首入口”，必须把它明确记为正式流程实现问题、交互合同问题或两者兼有；不得只重写教程文案，把正式流程的问题留在运行态里继续误导玩家。
- **默认预选不等于玩家已决策（强制）**：只要正式 UI 在某阶段一进入就带有默认选中的地区、卡牌、轮盘项、行动项或候选目标，审计必须明确区分三层语义：`默认预选`、`真实可点击对象`、`玩家已确认选择`。不得把默认预选写成“玩家先选了这里”，也不得因为画面上已有高亮，就跳过“这一步真正承接点击的是谁”的核对。
- **默认聚焦不得伪装成已确认（强制）**：只要某个高亮只是默认焦点、默认候选或系统便捷起点，而玩家还没实际点击、确认、支付或进入执行阶段，审计就必须把它标成“弱聚焦”，不能接受 UI 用“已锁定 / 当前执行 / 强确认描边 / 强确认底色”去呈现它。若视觉层把默认焦点和已确认态混成一个样式，直接判为交互合同错误。
- **后续目标阶段不得反写已锁来源对象（强制）**：只要某条交互已经完成了一级动作决策，并且真实运行态已经锁定 `来源区 / 出发对象 / 支付对象 / 已确认主动作对象`，后续地图点击、列表重聚焦、逻辑区切换或默认高亮变化都只能改变“当前焦点/当前候选”，不能反向改写这份已锁来源。审计时必须单列：`当前焦点对象`、`已锁来源对象`、`真实提交对象`；三者混成一个字段或一个 UI 语义时，直接判为交互合同错误。
- **后续步骤摘要不得冒充一级入口（强制）**：只要当前已经进入 `支付 / 弃牌 / 二级目标 / 地图目标 / 战后 / 年度结算` 这类后续步骤，任何**不承接点击**的摘要卡、步骤标题、状态条、右侧说明、横幅文案，都不得再把 `默认焦点 / 默认候选 / 已锁来源区 / 当前候选区` 包装成“现在第一步先点它/从这里开始/进攻这里/查看这里”。这类文案只能说明`当前动作层`、`当前步骤目的`、`剩余次数`、`结果约束`；若一个非点击摘要同时承担了“点击指令 + 地区主语 + 步骤主语”，直接判为交互合同错误。
- **主要交互默认要做全清单审查（强制）**：用户要求“所有交互都要审查”“继续收口交互合同”“教程和正式流程一起重审”时，默认不是抽两条代表链，而是至少列出：`开局公共推进`、`一级行动入口`、`支付/弃牌`、`二级目标选择`、`地图目标选择`、`待结算战斗`、`战后选择`、`年度/阶段结算`。任一类目未落表，不得声称“主要交互已审完”。
- **基础回合/端到端默认先补“首回合动作顺序表”（强制）**：当用户要求“基础回合”“完整回合”“基本流程端到端”“看出这个游戏怎么运作”时，除了一级交互审查表，还必须先补一张 `首回合动作顺序表`。至少写清：规则书从正式主入口开始要求玩家依次决定什么、当前正式局每一步首先暴露的真实对象、哪些属于一级动作、哪些只是后续目标/支付/确认、默认预选在该步只是弱聚焦还是已经进入正式确认。没补这张表前，不得把任何教程开场步骤或正式流程入口判成正确。
- **首教动作必须先落在当前玩家真实可选层（强制）**：若某个阶段只是强制公共推进、低信息前置、纯进入壳层或系统自动过场，而当前玩家尚未在这里做会影响后续理解的真实判断，审计时必须把它标成“经过点/前置层”，不能把它误判成首个正式决策入口。只要下一层已经是当前玩家真正有选择权的一级动作层，教程首个主操作和正式主提示都必须回到这一层的真实承接物。
- **第一步入口不得靠最后成功点击倒推（强制）**：只要当前争议涉及“第一步该点哪里”“为什么会被教成先选地区”“横幅是不是交互”“按钮和地图谁是主入口”“默认高亮是不是已选”，就必须再补一张 `当前屏幕可见可点对象盘点`。必须把该阶段玩家第一眼能看到并可能尝试点击的对象逐项标成 `一级动作入口 / 二级目标 / 支付对象 / 确认控件 / 提示UI / 非当前步骤对象`；不得只按最后成功点击的那个对象，反推这一步的主入口。
- **玩家文案不得用作者旁白腔替代规则语义（强制）**：教程文案、正式进行页短提示、步骤标题、摘要卡若主要依赖“这一步 / 下一步 / 这里 / 这次 / 现在先”来串步骤，而没有点明规则动作、对象或结果，审计必须直接记为文案失真。短提示可以说明阶段，但不能用流程旁白腔代替规则概念。
- **压结构不得静默删覆盖（强制）**：只要本轮在合并教程章节、删除隐藏续章、收口审计目录、把多条链并成一条基础流程，审计必须先补一张“覆盖差异表”，写清旧覆盖点、旧截图链、旧正式入口证明在新结构里的对应落点。若任何核心规则点、真实交互链或正式入口证明被删掉而未被等价替代，结论必须明确降级为“覆盖退化/仍有缺口”，不得继续使用“更精炼/更收口”口径。
- **提示横幅与交互入口必须分列审计（强制）**：顶部横幅、步骤卡、状态条、地图短提示只要不承接点击，就必须在审计表里单列为“提示 UI”；不得和按钮、地图区域、卡牌本体、轮盘格这类真实承接物混成一列。
- **实施前映射/脚本草案不是运行态证据（强制）**：`implementation-map / 覆盖矩阵 / 教程脚本草案 / 目录重组草案 / 实施前映射` 只能证明“计划怎么改”，不能证明“当前正式局已经这样工作”。只要结论里出现“正式进行页已有这个入口/这一章已实现/新游戏可收工”，证据必须来自当前 worktree 的正式源码、当前运行态截图或真实 E2E，而不是计划文档。
- **运行态专项审计真相源优先于计划文档（强制）**：如果当前游戏同时存在 `primary-interaction-audit / formal-flow-audit / runtime-closeout-audit` 这类明确面向运行态的专项审计文档，以及 `implementation-map / 覆盖矩阵 / 教程脚本草案` 这类计划文档，那么凡是“正式局当前有没有这个入口”“当前还能不能报收工”的判断，一律以运行态审计文档为准；计划文档只能作为待实施输入，不得反压运行态审计结论。
- **运行态专项审计真相源一旦被代码改动打旧，必须先回写（强制）**：如果本轮已经修改了正式入口、交互承接物、提示文案、默认聚焦语义或教程/正式局一致性，而现有 `primary-interaction-audit / formal-flow-audit / runtime-closeout-audit` 仍保留旧状态，默认动作必须是先把这份运行态审计文档回写到当前真相，再继续用它指导后续实现、教程判断或收工结论；不得一边知道文档已失真，一边继续引用里面的旧句子推进任务。
- **入口状态不得被过时文档二值化（强制）**：如果正式局已经对部分真实对象接上了一级入口、但仍受低保真对象、覆盖面或真相源缺口限制，审计状态必须写成“局部真实可用 / 仅限已识别对象 / 仍有正式缺口”这类精确状态；不得继续沿用“当前无正式入口”“手牌完全不承接”这类已经被当前代码证伪的旧口径。
- **正式进行页一级入口必须单独核对（强制）**：当用户要求“所有交互都要审查”“新游戏收工”“给我一个能看出游戏怎么运作的基本流程”时，除了教程表和交互清单，还必须再补一张“正式进行页一级入口核对表”，逐项把规则书同层一级动作标成 `真实可用 / 抽象替代 / 教程注入专供 / 尚未实现`。没补这张表前，不得用“正式流程已具备”口径。
- **审查表不是完成证据（强制）**：`一级交互审查表 / 首回合动作顺序表 / 当前屏幕可见可点对象盘点 / 正式进行页一级入口核对表 / 主要交互清单表` 只能证明“缺口被锁定”，不能单独证明“问题已解决”。只要表里仍有 `抽象替代 / 尚未实现 / 文案误导顺序 / 提示 UI 冒充交互 / 默认聚焦语义错误 / 教程与正式局不一致`，执行者必须继续回到当前源码、当前门禁和当前截图链处理；不得停在审计文档或口头结论。
- **更新 skill 后必须继续做运行态（强制）**：当用户明确要求“skill 先更新一下再继续”“不要再犯低级错误”“所有交互都要审查”，补 skill 只是防再犯动作，不是本轮主要交付。更新完通用 skill 后，必须立刻继续当前游戏的运行态审查、实现修正和验证；不得把“skill 已更新”当成本轮收口理由。
- **全交互清单必须从运行态全集反推，不得从截图抽样倒推（强制）**：当用户要求“所有交互都要审查”时，交互全集必须同时从 `规则书同层动作 / 当前状态字段 / command 或 event / builder / reducer / 当前 E2E 入口` 反查出来；截图只能验证已列出的行，不能用几张图反推出“主要交互只有这些”。若没有逐项覆盖这些运行态来源，不得说“所有交互已审完”。
- **每个交互行必须点名真实承接物和提示 UI（强制）**：全交互表的每一行都必须分别写出“真正消费点击/选择的对象”和“只是提示的 UI”。如果这一行只能写出横幅、步骤卡、摘要、状态条，却说不出按钮、卡牌、地图区域、轮盘格、列表项或系统交互入口，默认说明承接物未锁定，不能实施或收口。
- **全交互审查必须分流到执行队列（强制）**：主要交互清单、一级入口表或当前屏幕可点对象盘点完成后，必须逐行标成 `可立即真修 / 需要建模或真相源补齐 / 明确暂不处理且说明原因`。`可立即真修` 行必须继续落到源码、语言包、测试或截图链；`需要建模或真相源补齐` 行必须点名缺的是对象真相、素材合同、状态字段拆分、交互承接物还是阶段收口。没有这层分流，不得说“所有交互已审完”。
- **同层一级动作有缺口时不得拿示范链顶交（强制）**：只要正式进行页一级入口核对表里仍存在 `抽象替代 / 教程注入专供 / 尚未实现` 的同层一级动作，就不得把某条教程示范链、某个隐藏续章、某个默认预选路线或某个局部 E2E，包装成“基础流程完整”“正式局已经能看出怎么运作”或“新游戏已收工”。审计结论必须同时保留这些正式入口缺口，并继续回到真实承接物实现。
- **低保真或错素材对象不得冒充正式入口（强制）**：如果某个一级动作当前依赖的可见对象仍是 `低保真预览 / 错 atlas / 混入别类对象 / 没有规则级身份`，审计状态只能写成 `低保真替代 / 局部真实可用 / 正式缺口`，不得记成“正式入口已具备”。
- **对象集合混类必须直接打回真相源（强制）**：这里的“混入别类对象”包括但不限于：人物牌、纪年卡、剧本卡、牌背、帮助卡、占位壳，或其它不属于该一级动作对象集合的可见对象。一旦命中，默认动作不是补文案或补高亮，而是先回到 `素材清单 / atlas 裁切合同 / cardDefId 真相表 / 规则级对象映射` 锁真相。
- **局部 seam 不能越权外推正式入口（强制）**：就算当前代码已经让少量已识别对象、少量注入态对象或某个抽象按钮链能走通，也只能证明“局部真实可用”；在同类对象全集仍未完成规则级识别前，不得把这条 seam 外推成“该一级动作已正式实现”。
- **截图验收必须真的核图（强制）**：只要当前结论依赖“关键截图看起来是否达标”“图里是否仍有重复提示/错误高亮/错误交互载体”，执行者就必须按本 skill 完成 AI 核图，并完成用户可见展示；只报截图路径、文件名或“E2E 通过”都不算完成。
- **用户明确说‘打开图/看图’时不得只报路径（强制）**：必须完成用户可见开图；原图选择、编号、多图顺序和失败回退不在本审计 redline 重写。
- **新游戏“收工/完成”不得只凭教程或局部链路宣布（强制）**：如果用户目标已经升级为“新游戏收工”“要一个能看出游戏怎么运作的基本流程”“教程证明这个游戏已具备正式玩法”，审计必须同时给出两层结论：① 教程/示范链是否成立；② 正式进行页是否已经具备同口径的一级入口、真实承接物和结果反馈。只要其中任一层仍依赖注入态、隐藏技术入口、抽象按钮替代、低保真对象替代或局部 E2E 代表链，就只能判为“局部流程已验证，正式流程仍缺口”，不得使用“新游戏完成/收工”口径。
- **正式规则仍是固定序列或占位实现时不得判完成（强制）**：只要当前游戏的正式局内仍存在 `固定顺序房间池 / 固定顺序牌堆 / 固定遭遇池 / 假随机结果 / 占位房间对象 / 占位卡牌对象 / 教程注入专供入口 / 调试入口替代正式入口` 这类实现，审计结论必须明确降级为“正式规则未完成”。即便教程、截图或代表性 E2E 已跑通，也不得写成“游戏完成 / 第一剧本完成 / 可归档”。
- **“测试固定”与“正式逻辑固定”必须强制分开写（强制）**：如果某条链路为了 E2E 稳定而固定随机种子、固定首抽、固定布局，审计文档必须单列说明这是测试夹具；并额外核对正式局内同一规则对象是否仍是固定序列。两者若被混写，默认判为结论失真，不得收口。
- **新增批次默认需要审计留档，但不自动扩全**：如果任务语义是“新增派系 / 新英雄 / 新角色 / 新对象接入 / 从素材做到可玩”，默认交付包含当前锁定范围的对象级审计与 evidence 留档；只有明确写出整批对象全集，或有共享消费者直接影响证据时，才扩到对应对象集。
- **不能拿局部证据冒充全面审计完成**：如果当前只有代表性 E2E、局部截图、局部对象修复、单维度专项复核或少量自动化测试补齐，而没有达到审计文档要求的对象级和批次级收口，结论只能如实降级为“专项审计 / 抽样审计 / 代表性玩法已验证 / 仍有残余范围”，不得继续使用“全面审计完成”口径。
- **发现同维度漏项后按直接影响扩审**：如果当前审计命中共享消费合同、同类技能 family、同类 UI 入口、同类时机或同类资源链的漏项，先列出实际共享消费者；只有能证明同一缺口直接影响的对象才纳入复审，并同步回写旧 evidence / rule。仅有相似命名或同批次归属时，兄弟对象只登记候选，不自动复核。
- **状态/token 家族不能只凭对象级直证收口**：如果同一新英雄/新派系里有多个对象写入同一状态/token，或用户反馈集中在某个状态 family，默认必须继续拆出该状态的 `写入 seam -> 共享消费者 -> 清理/后续 -> 已验证入口`。只证明“多张牌都能写这个状态”不等于状态家族已到 `L4`；至少要继续查 `stack limit / accept-decline / upkeep / passiveTrigger / transfer / cleanup` 这些共享消费者。
- **点入口 / 点变体不等于已结算**：对真实玩家板槽位、变体 modal、simple-choice、攻击修正或其他交互入口，看到 `SELECT_ABILITY`、按钮点击或 modal 选择，只能证明对象进入了流程，不能直接算对象级 L3。若真合同是“先建 `pendingAttack`，再由 `ADVANCE_PHASE` / Continue / 选择确认收口”，审计必须把这两段都补齐。
- **不可防御必须同时审“声明层 + 共享消费层”**：看到 `damage(unblockable=true)` 或文案写“不可防御”时，不能直接判定收口。还必须反查 `isDefendable` 的共享来源是 ability/variant `tags`、choice effect patch、`ATTACK_MADE_UNDEFENDABLE` 还是其他 seam，并补证据证明真实流程不会误开防御窗口。
- **停止条件只能是收口或用户显式缩范围**：只要当前范围内还存在未回写旧结论、未补对象矩阵、未补关键 L3/L4、或未澄清的共享链判等，就不能把任务表述成“已审完”。只有矩阵收口，或用户明确把范围缩小，才允许停止推进。
