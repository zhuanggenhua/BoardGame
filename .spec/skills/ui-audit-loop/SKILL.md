# UI Audit Loop

把 UI 验收当成独立门禁。代码正确、元素存在、点击成功和 E2E 通过都不能单独证明玩家看到的界面合格。

## 用户可见图验收触发口径

截图 / 录屏审计和打开图片 / 录屏是稳定交付候选的最终验收动作，不是每次过程性 UI 修改的默认门禁；换句话说，开图或开录屏是完整重构或稳定候选完成后的胜利号角，不是实现过程中的例行动作。只有当本轮 UI 已经完成到可以宣称“可验收 / 可交付”、用户明确要求截图验收/玩家视角检查/打开图/录屏，或测试虽通过但界面仍存在高风险可用性疑点时，才进入本循环。

仍在搭建框架、跑通功能链、修流程、处理临时测试界面、占位 UI，或后续步骤会继续改造同一界面时，只做与当前风险匹配的功能、结构或私有诊断；局部截图不得冒充最终验收图进入 PASS 目录；用户明确要求查看特定原图或诊断标注时，按下方原图核查分流交付。不得因为改了可见 UI 就主动把中间图或诊断录屏当作最终验收物打开给用户。用户可见交付必须是整屏整体，口径以 [`e2e-verification`](../../knowledge/standards/e2e-verification.md) 和 [`show-image-to-user`](../show-image-to-user/SKILL.md) 为准。等完整重构完成并形成稳定候选后，再按本 skill 产出真实入口截图 / 录屏、AI 图面裁决和用户可见最终图 / 录屏。

新交互 / 新 UI 的端到端覆盖要求由 `.spec/knowledge/standards/e2e-verification.md` 与 `.spec/knowledge/standards/ui-change-gates.md` 维护；它要求覆盖矩阵和真实页面 E2E，但不等于每轮都打开图片、录屏或重跑全量截图。进入本 skill 时，只处理稳定候选或用户明确要求的图面 / 动效审计；最终验收展示须等同一组图或录屏明确 `PASS`；用户点名的原图和诊断证据按下方分流。

- **主助手直接审图**：主助手应直接读取原始候选截图 / 录屏，按玩家视角记录图面事实和 `PASS` / `REVISE`；不因审图而要求子代理。宿主在读取时显示预览也可以继续审计，但预览不是最终交付或用户验收；未通过的图继续返工，不得标成通过或当作最终图交付。
- **验收范围只限本轮要求（强制）**：进入截图验收时，先把用户本轮明确要求拆成可判定清单，例如“推斥必须看到来源唤醒 / 飞行路径 / 命中帧”“传送必须看到来源轨迹落点”“截图说明必须中文”。`PASS` 只要求这些清单项全部达标。这里的“本轮”是尚未关闭的用户目标，不是最近一次代码补丁或最近补拍的两张图；用户要求完整重构时，必须从原始目标、已批准提案和全部改动建立完整视觉范围，不能自行缩成局部增量。不要把整页 UI、其它系统、非目标布局缺陷或历史未完成项塞进本轮硬门禁；它们只能作为备注，除非它们直接让本轮清单项无法被截图证明。反过来，E2E 绿、像素亮点、文件存在或其它非目标证据，也不能替代清单项本身达标。
- **本轮新增或改造的可见 UI 自动进入视觉范围（强制）**：用户本轮清单若包含新增、改造或返工的可见界面，这些界面的视觉质量属于本轮要求，不能只验元素存在、可点击或 E2E 绿。最低必须按 [`ui-change-gates`](../../knowledge/standards/ui-change-gates.md) 判定正式素材优先、同一信息一个主承载、每个可见元素唯一职责、提示 UI 不冒充承接物、关闭不占内容槽位。空态“暂无”、自我命名 CTA 和同屏重复横幅不得记成非本轮基础问题。本条只补触发条件，不复制那些质量规则正文。
- **未解决本轮问题禁止最终交付（强制）**：如果用户刚指出的问题尚无直接证据证明已解决，不得因为其它 UI 通过、E2E 通过或截图已经生成就交付最终验收图；主助手仍应直接读取候选图以完成审计。非本轮问题不升级为阻塞，非本轮通过项也不计入达标。
- **用户可见展示只在触发后执行**：当用户明确要求看图 / 打开图 / 截图验收 / 录屏，或本轮交付物本身就是图片型验收图 / 动效验收录屏时，同一张原始验收图、同一组原始验收图或同一份录屏被选为最终候选且 AI 判定 `PASS` 后，必须交给项目 `show-image-to-user` 入口展示，再汇报完成。若本轮只是补 evidence、盘点截图 / 录屏、汇报测试或记录核图结论，未触发用户可见展示时，只汇报路径和结论，不自动打开查看器。
- **不通过就循环**：只要 AI 判定 `REVISE`，且失败项属于当前 UI 目标范围，就继续改同一实现、回同一真实入口重拍、重新审计；不得把失败图伪装成通过结果或把找错工作推给用户；用户明确要求查看失败证据时，应按诊断模式展示并说明裁决。
- **流程 UI 默认多图**：如果 UI 改动涉及进入、选择、投掷、翻页、展开/关闭、前后状态、PC/移动对照或完整链路，最终验收物默认是有序截图集，而不是只给最新一帧。每张图必须用中文说明它证明哪一步；用户本轮点名的每个状态都要有对应原始整屏图，缺一项就判 `REVISE`。
- **动效验收通过后优先录屏展示**：如果本轮验收对象是召唤、攻击、投射物、伤害飘字、拖拽、翻页或其它连续动画，关键帧截图仍用于 AI 自检和证据定位；当用户明确要看实际效果且本轮清单已 `PASS` 后，最终用户展示优先使用短录屏 / GIF，而不是让用户从多张静态截图推断动作连贯性。录屏只证明它覆盖的那段动作，不能替代未录到阶段的验收。
- **联系表不能替代逐图审计**：contact sheet、拼图、缩略图或低清总览只能用于索引和初筛；涉及目标选择、对象可读、遮挡、候选高亮、按钮归属或多步流程时，主助手直接检查对应原始截图。未改写且已有有效 PASS 的媒体沿用记录，不要求再打开原图。没有检查本轮变化媒体的原图，就不得输出 `PASS` 或把该图放入最终验收集。
- **逐图账本是最终门禁**：最终媒体目录中的每一张图 / 每一段录屏都必须登记目标对象、动作前后、玩家可见结果、同屏保护槽位、遮挡 / 裁切 / 内部 ID 泄漏检查和 `PASS | REVISE | carried-forward`。任一条为 `REVISE`，整组只能保留为失败 / 诊断证据，禁止生成最终 `PASS` manifest、`finalPassBeforeOpen: true` 或 `VIEWER_URL`。账本全量不等于每轮重读全部原图。
- **逐图账本必须可机器校验**：最终清单必须写入 `visualReview.mode=all-media`、`claimScope=interaction-ui`、真实的 `visualReview.reviewer` 和逐媒体报告文件；报告条目数、路径和状态必须与 `media/images` 一一对应。视觉报告只判 UI / 交互可见性，不承担数值或规则正确性，后者必须回到 Vitest / 领域测试。增量核图、必须重读范围、`carried-forward` 和固定悬浮层不得逼走主栏，以 [`e2e-verification`](../../knowledge/standards/e2e-verification.md) 为唯一主源。
- **用户指出后只失效相关结论**：用户话语分类以 [`conversation-handoff-target-lock`](../../knowledge/standards/conversation-handoff-target-lock.md) 为准。用户明确否决整体体验、整体设计或覆盖完整性时，整项交付立即退回 `REVISE`，已通过的局部观察仅作诊断事实，不能恢复最终展示资格。仅当用户限定为某张图不合格或某条新增条件时，才只把被点名 / 被新条件覆盖的图面结论降为历史 / 诊断并重拍重审；陈述、观察和流程问题不触发整组失效。E2E 绿灯、DOM 存在、截图生成成功和 viewer 注册不得恢复已失效条目的旧 `PASS`。
- **阻塞口径**：如果真实入口、截图生成、素材加载或图面审计被环境阻断，只能按阻塞汇报，说明现实后果、证据、为什么阻止继续、最小补救动作；不得宣称 UI 已完成。

产品最终验收图与用户点名的原图核查，按 [`e2e-verification`](../../knowledge/standards/e2e-verification.md#用户点名原图核查) 分流。后者交付原始诊断证据，不受本 skill 的产品最终 PASS 展示门禁约束。

## 锁定输入

审计前先按 [`conversation-handoff-target-lock`](../../knowledge/standards/conversation-handoff-target-lock.md) 锁定通用四项前提。本 skill 额外确认 UI 审计字段：页面状态、交互步骤、目标用户、目标视口、布局层、阻塞关系、同层竞争元素和当前必须看见 / 可操作 / 退场的对象。对每个拟判定的遮挡，在审查记录中先写明 `前后对象及各自层级 | 当前玩家任务 | 是否必须同时读取或操作及依据 | 实际受阻 / 命中证据 | 裁决`，按 [`ui-responsive-layout`](../../knowledge/standards/ui-responsive-layout.md#场景层与界面锚点) 判断；缺少依据记为未核明，不得仅因重叠判失败。

局部修复的验收范围按 [`ui-change-gates`](../../knowledge/standards/ui-change-gates.md#验收范围冻结) 锁定；逐项标明用户原始症状、实际修改、直接受影响对象和仅作背景的既有对象。未修改且无直接影响证据的状态不能只因同屏存在或有通用测试建议就升级为本轮必验；若它属于用户明确描述的原症状，则仍应作为原问题证据缺口，而不是声称它被修改或已修复。

**历史 / 旧版 UI 必须先锁历史证据**：当用户问“旧版 / 之前 / 原来 / 改之前 / 以前是不是这样”时，当前截图、当前 DOM、当前 HEAD、修后图或新生成 evidence 只能证明“现在”，不能反推“以前”。必须先查旧截图、旧 evidence、旧代码、历史提交、last-known-good / first-known-bad 或用户提供的历史图；没有命中证据时，只能说“旧版位置未锁定”，继续查或问用户，禁止把当前实现当旧版合同实施或验收。

**空间语义必须先唯一锁定**：当用户使用“上面 / 下面 / 外面 / 里面 / 旁边 / 右上角 / 贴着 / 压着 / 手上 / 手边”等可能有多个解释的空间表达时，先锁定目标对象、参照物、锚点、层级关系和是否占位。必须区分屏幕方向上的“上方”、容器外侧的“上方/右侧”、覆盖在对象表面的“上层”、另占一行/一列的布局空间，以及挂到另一块面板里的显示。若旧截图、旧代码、当前整屏图或用户描述不能排除多个合理匹配，必须先问清楚；禁止先挑一个解释实施、测试、截图或宣称验收。

截图必须来自上述同一现场，并晚于相关实现改动。历史图、预览页、错误路由、候选图和静态 mock 不得冒充当前实现。

## 审计流程

### 1. 先确认层级与真实链路

- 走用户真实入口抵达目标状态，先按 [`ui-responsive-layout`](../../knowledge/standards/ui-responsive-layout.md#场景层与界面锚点) 确认层级、阻塞关系和当前操作对象，再进行下列检查。
- **状态型 UI 必须先触发再截图**：如果要验收的对象只会在某个动作、选择、输入、结算、加载完成或错误发生后出现，截图前必须先执行该动作或用项目正式测试夹具构造等价目标状态。禁止用动作前、邻近流程、默认空态或“元素理论上会出现”的截图替代。截图说明必须写清前置动作，例如“先拿筹码后”“先选中目标后”“提交失败后”“加载完成后”。
- **内部布局审查**：按 [`e2e-verification` 的视觉与动态证据](../../knowledge/standards/e2e-verification.md#视觉与动态证据)检查真实可同屏元素和竞争状态。内部取证与给用户的图组按[内部验收与用户展示范围](../../knowledge/standards/e2e-verification.md#内部验收与用户展示范围)分开，不在本流程重复定义展示范围。
- **单游戏专项**：新英雄玩家板几何对照回到 [Dice Throne 玩家板合同](../dicethrone-hero-intake/SKILL.md#共享玩家板几何实现门禁)，不把单游戏槽位写成通用验收正文。
- **选择态截图必须显示被选候选本体**：当截图声称证明“选择某个对象 / 目标 / 支付物 / 顺序项 / 数量项”时，必须能在原图中清楚看见当前需同时判断或操作的合法候选本体、候选高亮或确认入口，以及它和当前 prompt 的关系。若预览、提示或其它层使这些当前必需对象无法辨认或操作，即使 DOM 存在、E2E 能点也判 `REVISE`。按合同有意阻断底层的独立检视态，应分别验证其关闭和返回选择路径，不因跨层相交直接判失败，也不能用检视态截图冒充选择态证据。
- **测试解释标签不得进入玩家 UI**：E2E、调试或审计为了定位状态所需的 `可选目标 / 来源 / 对手 / 你 / target / source / legal / selected / debug` 等解释语言，不得作为棋盘、场上单位、目标对象或行动候选旁的可见标签。除非这些词本身就是游戏规则文本或真实无障碍替代，玩家可见界面必须用对象本体高亮、描边、发光、抬升、禁用态、光标和可点击反馈表达候选 / 来源 / 目标；截图里出现测试解释标签直接判 `REVISE / debug-label-leaked`。
- **用户标注 / 点名元素必须逐项审计**：如果本轮有用户标注图、参考图、草图或点名对象，审计输出必须逐项回答这些元素是否仍在图中、是否按规则术语承载、是否可读可点、是否被合法收起，以及收起入口在哪里。不能用“画面更干净”“当前流程更聚焦”“不是本阶段主动作”直接抵消用户点名元素；若确实不显示，必须写出规则阶段互斥、素材 blocked、目标环境不支持或用户明确同意的证据。
- **验收口径变更后只重审被覆盖截图**：如果用户刚补充了新的验收条件，或本轮规范刚新增了压力态、完整上下文、状态触发、对照分支等要求，只把不满足新条件的旧图标为历史、局部诊断或失败/过期证据并重拍；仍满足新条件且本轮未改写的媒体沿用已有 `PASS`。不得因为口径变更而重审整组无变化媒体。
- 运行与风险匹配的功能测试，确认目标操作确实可完成。
- 在要求的桌面端、移动端或两者视口生成原始截图。
- 对图片、canvas、3D 或异步素材增加可见性检查；仅检查 DOM 节点存在不够。
- 浮层、特写、popover、提示条的几何检查按第一步已确认的层级与交互合同进行，检查同层竞争区域及当前操作命中链。
- 改 UI 不能只审新增 UI 自己。截图前列出同屏影响清单，逐项判断 token/状态/资源、玩家面板、阶段条、骰盘、牌库/弃牌堆、手牌/持有物、主动作入口、当前 prompt 和日志/目标摘要是否与当前任务相关；按 [`ui-responsive-layout`](../../knowledge/standards/ui-responsive-layout.md#场景层与界面锚点) 的层级合同选择截图、命中或同层几何证据。缺少必要证据判未覆盖，不把跨层相交或无关对象未做几何断言直接判失败。
- **持续可支配对象必须审计守恒**：审计不能只看当前来源、目标和确认按钮。截图和裁决必须逐项证明玩家当前仍能看见或恢复查看所有会影响决策的可支配对象，例如可用卡牌 / 法术、计划牌、持有物、装备、单位、行动来源、资源、可选目标和当前阶段候选集。若某类对象被收起，必须同时证明入口可见、数量 / 当前焦点可理解、展开路径明确、展开后达到最小可读尺寸；否则直接判 `REVISE`。
- **负向影响清单是 PASS 前置条件**：凡是本轮把某个区域移动、合并、缩小、折叠、隐藏或删除，审计输出必须写清该区域对应的规则对象、它是否仍参与当前玩家决策、等价新承载在哪里、玩家第一眼如何找回。不能只写“布局更干净 / 操作链更集中 / 没有重叠”。没有负向影响清单时，即使局部动作链可点击，也不得判 `PASS`。
- 保护槽位按 [`ui-change-gates`](../../knowledge/standards/ui-change-gates.md#布局与空间) 执行，跨层覆盖按 [`ui-ux`](../../knowledge/standards/ui-ux.md#审美原则) 的层级合同裁定；此处只登记原图中的对象、所属层、当前任务及对应结论。
- **操作控件必须审空间关系**：如果用户目标包含“好按 / 顺手 / 贴近对象 / 不要放到底部 / 上下手 / 左右手 / 给某对象 / 选择目标归属”等人体工学或归属语义，几何断言必须同时覆盖控件与现实操作对象的距离、锚点和手势路径。`离屏幕边缘足够远`、`触控热区达到 44px`、`DOM 挂在某个容器里` 只是底线，不能替代玩家视角判断；控件远离对象、贴近错误对象或让玩家误判它控制的对象时，直接判 `REVISE`。
- **触控下限不得冒充视觉比例合格**：`44px` / `48dp` 只证明控件最低可点，不证明它大小正确。对象旁的辅助按钮、分段选择器、模式开关和目标归属控件必须区分“可见按钮面”和“真实点击热区”，并量相对主体的宽度、面积或视觉权重；如果可见面接近或超过被控制对象本体，让玩家第一眼看到按钮而不是对象，直接判 `REVISE`。需要保留大热区时，优先用透明命中区或外扩 hitbox，不要把可见按钮面画成主对象尺寸，也不要把可见面画成 44px 高的大主按钮。三四个字的对象旁辅助选择器不能因为文字可读就扩到接近半个主体宽度；默认应先做成小标签 / 小胶囊，再用透明热区补触控。
- 对需要玩家阅读的展示型 UI，例如其他玩家打出的卡牌特写、对手进攻技能/升级卡特写、揭示牌、场景页、道具详情或结算说明，必须验证它会持续可见直到用户明确关闭或规则明确推进；只断言“曾经出现过一瞬间”不得判定通过。
- 当项目同时存在通用 UI 组件和游戏/页面自建旧实现时，必须逐一确认真实入口用的是哪一套实现；只修通用组件、只看共享 hook、或只测一个游戏，不能证明其它游戏的同类 UI 已通过。若用户反馈来自具体游戏/页面，审计必须命中该游戏/页面的实际实现文件和真实运行截图。
- 需要玩家阅读的展示型 UI 按规则和交互合同保持可阅读，不能因无关的 timer、重同步或重挂载意外消失；规则允许推进或自动退场时，验证对应条件及玩家可读时间。适用时检查旧超时、同步后可见及明确关闭路径；合法的背景点击也可以是关闭动作。

### 2. 先审整体版式，再审控件与状态

先核对要求是否来自用户目标或批准合同，再按 [布局与空间](../../knowledge/standards/ui-change-gates.md#布局与空间) 审原始整图的三项整体判定，记录具体对象关系。局部改动只审目标及直接影响面；整页改造必须审整页。整体存在失败或未核明项时直接退回，不进入细节评分，也不以控件齐全抵消。游戏 UI 另按 [元素职责审计](../../knowledge/standards/ui-change-gates.md) 对照同一份职责总账，复核商业表达、必要性与保留/删除裁决，输出未覆盖项。


必须实际读取原始截图并逐项审计：

| 维度 | 分值 | 通过标准 |
| --- | ---: | --- |
| 任务清晰度 | 20 | 第一眼能识别当前目标和下一步动作 |
| 视觉层级 | 15 | 单一主焦点成立，无关内容不争夺注意力 |
| 对象可识别性 | 15 | 当前操作层的目标本体可识别，素材正确 |
| 状态与动作载体 | 15 | 可交互对象和提示 UI 角色清楚，不靠重复说明正文补救 |
| 布局完整性 | 15 | 引用已完成的 [整体版式判定](../../knowledge/standards/ui-change-gates.md#布局与空间)，再核对当前状态下的越界、裁切和漂移；不以栅格类名或父容器齐整代替实际控件关系 |
| 素材完整性 | 10 | 图片、图标、字体和特效真实渲染，无破图、替代色块或素材比例失真 |
| 操作人体工学 | 10 | 点击热区、间距、反馈、移动端触控尺寸，以及控件与被操作对象的空间关系可用 |

总分只评价本轮要求及其证据有效性；整体判定全部通过、总分达到 `90/100` 且没有本轮范围内硬失败项，才能判定 `PASS`。若用户本轮要求就是“整页 UI / 全流程视觉验收 / 全局审计”，评分覆盖整页；若用户只要求某个技能过程帧、某个按钮、某个布局关系或某组截图说明，评分和硬失败项只覆盖这些目标及会直接影响它们可判定性的同屏问题。

**自见失败不得送验**：审计者自己已经能从原始截图看出本轮目标仍未达标，不能留给用户人工验收才发现，也不能用“候选”“比上一版好”“几何无重叠”包装成 `PASS`。范围内失败包括：本轮主对象不可见、目标特效不明显、目标状态未触发、截图说明不符合用户要求、关键牌面空白、目标控件离被控制对象太远、或截图状态无法证明用户要求。只要仍能指出这类本轮范围内的问题，当前裁决就是 `REVISE`，继续重构、重拍、重审；不得打开为最终人工验收图。非本轮基础问题只写进备注或后续清单，除非它直接遮挡、混淆或破坏本轮目标证据。本轮自己新增或改造的可见 UI 上的素材缺失、信息重复、无效空态或职责重叠，一律算范围内失败。

### 3. 硬失败项

逐图裁决前必须读取并按本轮范围执行 [硬失败项清单](references/hard-failures.md)；该清单是本流程的分卷，不是新的验收主源。

### 4. 输出裁决

每轮输出：

```text
verdict: PASS | REVISE
score: 0-100
layoutAudit: # 判定规则只引用 ui-change-gates 的“布局与空间”，不另定标准
  scopeSource: 用户原话或批准合同的可回查位置
  checks:
    - criterion: 空间主次 | 对齐栅格 | 分组与装饰 # 分别记录三项
      status: PASS | REVISE | 未核明
      evidence: 当前原始整图
      observation: 具体对象、可见边缘或层级关系及判定理由
target_requirements:
  - requirement: 用户本轮给出的可判定要求
    status: PASS | REVISE
    evidence: 直接证据
element_responsibility_audit: # 游戏 UI 必填；其它已定稿页面不因本字段重开设计
  ledger: 同一份元素职责总账的路径或引用
  uncovered_elements: []
  decisions: 逐项商业表达与必要性复核后的保留/删除/合并/迁移裁决
hard_failures: []
negative_impact_checks: []
issues:
  - evidence: 截图中可直接指出的现象
    impact: 对玩家造成的现实问题
    fix: 下一轮具体修改
```

禁止输出“基本没问题”“功能上没问题”“可以先过”这类模糊结论。

### 5. 未通过就继续重构

当结论为 `REVISE`：

1. 按影响排序，只修改能直接解释截图问题的实现。
2. 回到同一真实入口和同一失败状态验证。
3. 重新生成晚于本轮改动的新截图。
4. 重新审计本轮失败项与本轮改写媒体，不沿用这些项的旧分数；未改写且已 PASS 的媒体沿用上次记录。完整组账本仍要全量。
5. 持续循环，直到 `PASS`；若真实环境阻塞，明确停在阻塞项，不得宣称通过。

**不要停在“未达标候选”**：只要工具仍可继续修改并重新取证，且失败项属于当前目标范围内的视觉 / 布局 / 槽位问题，就继续循环，不把未达标图或录屏交给用户做人工挑错。只读审查或用户要求诊断时，如实交付发现和证据；授权修复时持续推进，直到通过，或明确说明实际阻塞及其证据和补救动作。

## 证据与交付

- 功能测试证据和视觉证据分别汇报，不能互相替代。
- 记录最终截图来源、视口、目标状态、生成时间和裁决；使用网页查看器时保留脚本返回的 `VIEWER_URL`。
- 候选图、失败图和中间图的读取按本流程“主助手直接审图”执行；读取时出现预览不等于最终交付。
- 触发用户可见开图 / 录屏时，最终 `PASS` 图或录屏按项目 `show-image-to-user` 入口和宿主支持的方式交付；打开图片 / 录屏不是 AI 审计本身。未触发用户可见展示时，汇报 AI 审计结论和证据角色，无需为内部截图额外注册查看器。
- UI 改动最终回复必须包含：AI 审计结论、玩家第一眼会怎么行动、以及仍未覆盖的视口或状态；若触发用户可见开图 / 录屏，还必须包含用户可见验收图 / 有序图集 / 录屏的展示结果。缺任一适用项不得用完成口径。
- 项目存在更严格 UI、E2E、截图或发布门禁时，叠加执行，不降低项目标准。
