# UI Audit Loop

把 UI 验收当成独立门禁。代码正确、元素存在、点击成功和 E2E 通过都不能单独证明玩家看到的界面合格。

## 用户可见图验收触发口径

截图 / 录屏审计和打开图片 / 录屏是稳定交付候选的最终验收动作，不是每次过程性 UI 修改的默认门禁；换句话说，开图或开录屏是完整重构或稳定候选完成后的胜利号角，不是实现过程中的例行动作。只有当本轮 UI 已经完成到可以宣称“可验收 / 可交付”、用户明确要求截图验收/玩家视角检查/打开图/录屏，或测试虽通过但界面仍存在高风险可用性疑点时，才进入本循环。

仍在搭建框架、跑通功能链、修流程、处理临时测试界面、占位 UI，或后续步骤会继续改造同一界面时，只做与当前风险匹配的功能、结构或局部截图 / 录屏诊断；不得因为改了可见 UI 就主动把中间图或诊断录屏当作最终验收物打开给用户。等完整重构完成并形成稳定候选后，再按本 skill 产出真实入口截图 / 录屏、AI 图面裁决和用户可见最终图 / 录屏。

新交互 / 新 UI 的端到端覆盖要求由 `.spec/knowledge/standards/e2e-verification.md` 与 `.spec/knowledge/standards/ui-change-gates.md` 维护；它要求覆盖矩阵和真实页面 E2E，但不等于每轮都打开图片、录屏或重跑全量截图。进入本 skill 时，只处理稳定候选或用户明确要求的图面 / 动效审计；用户可见展示仍必须等同一组图或录屏明确 `PASS` 后才允许。

- **先 AI 验，再给用户验**：助手必须先检查原始最终候选截图 / 录屏做玩家视角审计，明确写出图面 / 动效事实、`PASS` / `REVISE` 结论、失败点或通过理由。用户已明确要求“打开图 / 录屏”但当前尚未 `PASS` 时，不得展示；继续审计或返工。不得先产生 PureRef / 系统查看器 / Codex 内联图 / `view_image` / `Viewed Image` 等用户可见事件，再把它冒充验收。
- **验收范围只限本轮要求（强制）**：进入截图验收时，先把用户本轮明确要求拆成可判定清单，例如“推斥必须看到来源唤醒 / 飞行路径 / 命中帧”“传送必须看到来源轨迹落点”“截图说明必须中文”。`PASS` 只要求这些清单项全部达标。不要把整页 UI、其它系统、非目标布局缺陷或历史未完成项塞进本轮硬门禁；它们只能作为备注，除非它们直接让本轮清单项无法被截图证明。反过来，E2E 绿、像素亮点、文件存在或其它非目标证据，也不能替代清单项本身达标。
- **未解决本轮问题禁止开图（强制）**：如果用户刚指出的问题本身还没有直接证据证明已解决，不能因为“其它 UI 通过”“E2E 通过”“截图已经生成”“只是想让用户看一下”而开图。开图门禁只问本轮要求有没有逐条达标；非本轮问题不升级为阻塞，非本轮通过项也不计入达标。
- **用户可见展示只在触发后执行**：当用户明确要求看图 / 打开图 / 截图验收 / 录屏，或本轮交付物本身就是图片型验收图 / 动效验收录屏时，同一张原始验收图、同一组原始验收图或同一份录屏被选为最终候选且 AI 判定 `PASS` 后，必须交给项目 `show-image-to-user` 入口展示，再汇报完成。若本轮只是补 evidence、盘点截图 / 录屏、汇报测试或记录核图结论，未触发用户可见展示时，只汇报路径和结论，不自动打开查看器。
- **不通过就循环**：只要 AI 判定 `REVISE`，且失败项属于当前 UI 目标范围，就继续改同一实现、回同一真实入口重拍、重新审计；不得把失败图交给用户人工挑错，也不得等用户催促才继续。
- **流程 UI 默认多图**：如果 UI 改动涉及进入、选择、投掷、翻页、展开/关闭、前后状态、PC/移动对照或完整链路，最终验收物默认是有序截图集，而不是只给最新一帧。每张图必须说明它证明哪一步。
- **动效验收通过后优先录屏展示**：如果本轮验收对象是召唤、攻击、投射物、伤害飘字、拖拽、翻页或其它连续动画，关键帧截图仍用于 AI 自检和证据定位；当用户明确要看实际效果且本轮清单已 `PASS` 后，最终用户展示优先使用短录屏 / GIF，而不是让用户从多张静态截图推断动作连贯性。录屏只证明它覆盖的那段动作，不能替代未录到阶段的验收。
- **联系表不能替代逐图审计**：contact sheet、拼图、缩略图或低清总览只能用于索引和初筛；涉及目标选择、对象可读、遮挡、候选高亮、按钮归属或多步流程时，必须用不向用户展示的方式逐张检查对应原始截图。没有逐图检查原图，就不得输出 `PASS` 或把该图放入最终验收集；如果当前宿主没有私有看图能力，只能停在证据不足或补非展示型机器检查，不能先把未通过图打开给用户。
- **阻塞口径**：如果真实入口、截图生成、素材加载或图面审计被环境阻断，只能按阻塞汇报，说明现实后果、证据、为什么阻止继续、最小补救动作；不得宣称 UI 已完成。

## 锁定输入

审计前必须确认：

1. **对象**：页面、状态、交互步骤和目标用户。
2. **真相源**：需求、批准设计、现有设计系统或明确的玩家任务。
3. **运行现场**：当前工作目录、真实路由、当前代码、目标视口和数据状态。
4. **验收口径**：必须看见什么、能做什么、哪些 UI 应退场。

**历史 / 旧版 UI 必须先锁历史证据**：当用户问“旧版 / 之前 / 原来 / 改之前 / 以前是不是这样”时，当前截图、当前 DOM、当前 HEAD、修后图或新生成 evidence 只能证明“现在”，不能反推“以前”。必须先查旧截图、旧 evidence、旧代码、历史提交、last-known-good / first-known-bad 或用户提供的历史图；没有命中证据时，只能说“旧版位置未锁定”，继续查或问用户，禁止把当前实现当旧版合同实施或验收。

**空间语义必须先唯一锁定**：当用户使用“上面 / 下面 / 外面 / 里面 / 旁边 / 右上角 / 贴着 / 压着 / 手上 / 手边”等可能有多个解释的空间表达时，先锁定目标对象、参照物、锚点、层级关系和是否占位。必须区分屏幕方向上的“上方”、容器外侧的“上方/右侧”、覆盖在对象表面的“上层”、另占一行/一列的布局空间，以及挂到另一块面板里的显示。若旧截图、旧代码、当前整屏图或用户描述不能排除多个合理匹配，必须先问清楚；禁止先挑一个解释实施、测试、截图或宣称验收。

截图必须来自上述同一现场，并晚于相关实现改动。历史图、预览页、错误路由、候选图和静态 mock 不得冒充当前实现。

## 审计流程

### 1. 先验证真实链路

- 走用户真实入口抵达目标状态，不用手工拼出的孤立组件替代。
- **状态型 UI 必须先触发再截图**：如果要验收的对象只会在某个动作、选择、输入、结算、加载完成或错误发生后出现，截图前必须先执行该动作或用项目正式测试夹具构造等价目标状态。禁止用动作前、邻近流程、默认空态或“元素理论上会出现”的截图替代。截图说明必须写清前置动作，例如“先拿筹码后”“先选中目标后”“提交失败后”“加载完成后”。
- **布局验收必须构造关键元素齐全的压力态**：如果要判断位置、遮挡、空间是否合理，截图状态必须同时包含会与目标竞争空间的关键元素，例如主要操作按钮、玩家面板、状态/资源/token、手牌/牌堆/弃牌堆、公共区、提示/当前 prompt、可见浮层或侧边工具。只让目标元素单独出现、只截空桌面、只截局部容器、或只截元素刚出现但其它关键 UI 尚未进入的状态，不能判定布局 `PASS`。若某些元素在规则上不能与目标同屏，必须写明为什么不可能同屏，而不是省略不提。
- **选择态截图必须显示被选候选本体**：当截图声称证明“选择某个对象 / 目标 / 支付物 / 顺序项 / 数量项”时，必须能在原图中清楚看见当前合法候选本体、候选高亮或确认入口，以及它和当前 prompt 的关系。若候选被大卡预览、hover 特写、toast、提示条、遮罩、手牌、HUD 或其它浮层遮住，即使 DOM 可点击、E2E 能点、状态里存在 option，也判 `REVISE`；必须重构或重拍到玩家第一眼知道该点什么。
- **测试解释标签不得进入玩家 UI**：E2E、调试或审计为了定位状态所需的 `可选目标 / 来源 / 对手 / 你 / target / source / legal / selected / debug` 等解释语言，不得作为棋盘、场上单位、目标对象或行动候选旁的可见标签。除非这些词本身就是游戏规则文本或真实无障碍替代，玩家可见界面必须用对象本体高亮、描边、发光、抬升、禁用态、光标和可点击反馈表达候选 / 来源 / 目标；截图里出现测试解释标签直接判 `REVISE / debug-label-leaked`。
- **用户标注 / 点名元素必须逐项审计**：如果本轮有用户标注图、参考图、草图或点名对象，审计输出必须逐项回答这些元素是否仍在图中、是否按规则术语承载、是否可读可点、是否被合法收起，以及收起入口在哪里。不能用“画面更干净”“当前流程更聚焦”“不是本阶段主动作”直接抵消用户点名元素；若确实不显示，必须写出规则阶段互斥、素材 blocked、目标环境不支持或用户明确同意的证据。
- **验收口径变更后旧截图必须重新归类**：如果用户刚补充了新的验收条件，或本轮规范刚新增了压力态、完整上下文、状态触发、对照分支等要求，之前生成/打开过的截图不能继续沿用为最终 `PASS` 图。必须先按新口径复核：不满足新条件的旧图只能标为历史、局部诊断或失败/过期证据；最终验收必须重拍或证明旧图确实已经满足新口径。
- 运行与风险匹配的功能测试，确认目标操作确实可完成。
- 在要求的桌面端、移动端或两者视口生成原始截图。
- 对图片、canvas、3D 或异步素材增加可见性检查；仅检查 DOM 节点存在不够。
- 对浮层、特写、popover、提示条这类会压在主界面上的 UI，几何断言必须覆盖整屏所有竞争区域，例如主对象、目标、token/状态标记、资源条、玩家面板、手牌、牌库/弃牌堆、骰盘、侧边工具、HUD、确认按钮和当前 prompt；只证明“不遮挡某一个对象”不得判定视觉通过。
- 改 UI 不能只审新增 UI 自己。截图前必须列出同屏影响清单，至少覆盖 token/状态/资源、玩家面板、阶段条、骰盘、牌库/弃牌堆、手牌/持有物、主动作入口、当前 prompt、日志/目标摘要，并逐项判断保留、避让、迁移、折叠或不相关。缺少清单或清单中任一保护槽位未在截图/几何断言里覆盖，直接判 `REVISE`。
- **持续可支配对象必须审计守恒**：审计不能只看当前来源、目标和确认按钮。截图和裁决必须逐项证明玩家当前仍能看见或恢复查看所有会影响决策的可支配对象，例如可用卡牌 / 法术、计划牌、持有物、装备、单位、行动来源、资源、可选目标和当前阶段候选集。若某类对象被收起，必须同时证明入口可见、数量 / 当前焦点可理解、展开路径明确、展开后达到最小可读尺寸；否则直接判 `REVISE`。
- **负向影响清单是 PASS 前置条件**：凡是本轮把某个区域移动、合并、缩小、折叠、隐藏或删除，审计输出必须写清该区域对应的规则对象、它是否仍参与当前玩家决策、等价新承载在哪里、玩家第一眼如何找回。不能只写“布局更干净 / 操作链更集中 / 没有重叠”。没有负向影响清单时，即使局部动作链可点击，也不得判 `PASS`。
- 新 UI 不得抢占 token、状态、资源、生命/属性、骰盘、牌堆、手牌等玩家持续读取的保护槽位。除非用户明确批准迁移，并且截图证明旧信息有等价新承载、玩家第一眼能找到，否则把浮层、特写、提示条、toast、关闭按钮或阅读卡放进这些槽位都判 `REVISE`。
- **操作控件必须审空间关系**：如果用户目标包含“好按 / 顺手 / 贴近对象 / 不要放到底部 / 上下手 / 左右手 / 给某对象 / 选择目标归属”等人体工学或归属语义，几何断言必须同时覆盖控件与现实操作对象的距离、锚点和手势路径。`离屏幕边缘足够远`、`触控热区达到 44px`、`DOM 挂在某个容器里` 只是底线，不能替代玩家视角判断；控件远离对象、贴近错误对象或让玩家误判它控制的对象时，直接判 `REVISE`。
- **触控下限不得冒充视觉比例合格**：`44px` / `48dp` 只证明控件最低可点，不证明它大小正确。对象旁的辅助按钮、分段选择器、模式开关和目标归属控件必须区分“可见按钮面”和“真实点击热区”，并量相对主体的宽度、面积或视觉权重；如果可见面接近或超过被控制对象本体，让玩家第一眼看到按钮而不是对象，直接判 `REVISE`。需要保留大热区时，优先用透明命中区或外扩 hitbox，不要把可见按钮面画成主对象尺寸，也不要把可见面画成 44px 高的大主按钮。三四个字的对象旁辅助选择器不能因为文字可读就扩到接近半个主体宽度；默认应先做成小标签 / 小胶囊，再用透明热区补触控。
- 对需要玩家阅读的展示型 UI，例如其他玩家打出的卡牌特写、对手进攻技能/升级卡特写、揭示牌、剧本页、道具详情或结算说明，必须验证它会持续可见直到用户明确关闭或规则明确推进；只断言“曾经出现过一瞬间”不得判定通过。
- 当项目同时存在通用 UI 组件和游戏/页面自建旧实现时，必须逐一确认真实入口用的是哪一套实现；只修通用组件、只看共享 hook、或只测一个游戏，不能证明其它游戏的同类 UI 已通过。若用户反馈来自具体游戏/页面，审计必须命中该游戏/页面的实际实现文件和真实运行截图。
- 需要玩家阅读的展示型 UI 禁止靠短 timer、自动关闭、点击卡面/技能本体、hover/blur、prompt 切换、联机确认、重同步信号或组件重挂载退场；验收必须包含“超过旧自动关闭时间仍可见”“同步/重挂载后仍可见”和“触发明确玩家关闭动作才退场”三个断言。卡牌特写若按项目表现事件规范允许“点击空白背景关闭”，该空白点击属于明确玩家关闭动作。

### 2. 再做玩家视角看图

必须实际读取原始截图并逐项审计：

| 维度 | 分值 | 通过标准 |
| --- | ---: | --- |
| 任务清晰度 | 20 | 第一眼能识别当前目标和下一步动作 |
| 视觉层级 | 15 | 单一主焦点成立，无关内容不争夺注意力 |
| 对象可识别性 | 15 | 目标本体清楚、无遮挡、无错误素材或空占位 |
| 状态与动作载体 | 15 | 可交互对象和提示 UI 角色清楚，不靠重复说明正文补救 |
| 布局完整性 | 15 | 无重叠、裁切、溢出、漂移、异常留白或失衡 |
| 素材完整性 | 10 | 图片、图标、字体和特效真实渲染，无破图或替代色块 |
| 操作人体工学 | 10 | 点击热区、间距、反馈、移动端触控尺寸，以及控件与被操作对象的空间关系可用 |

总分只评价本轮要求及其证据有效性；总分达到 `90/100` 且没有本轮范围内硬失败项，才能判定 `PASS`。若用户本轮要求就是“整页 UI / 全流程视觉验收 / 全局审计”，评分覆盖整页；若用户只要求某个技能过程帧、某个按钮、某个布局关系或某组截图说明，评分和硬失败项只覆盖这些目标及会直接影响它们可判定性的同屏问题。

**自见失败不得送验**：审计者自己已经能从原始截图看出本轮目标仍未达标，不能留给用户人工验收才发现，也不能用“候选”“比上一版好”“几何无重叠”包装成 `PASS`。典型失败包括：本轮主对象不可见、目标特效不明显、目标状态未触发、截图说明不符合用户要求、关键牌面空白、目标控件离被控制对象太远、或截图状态无法证明用户要求。只要仍能指出这类本轮范围内的问题，当前裁决就是 `REVISE`，继续重构、重拍、重审；不得打开为最终人工验收图。非本轮基础问题只写进备注或后续清单，除非它直接遮挡、混淆或破坏本轮目标证据。

### 3. 硬失败项

以下硬失败项只在它们落入本轮要求、被用户明确点名，或直接导致本轮截图无法证明目标要求时判定 `REVISE`；否则记录为范围外备注，不阻塞本轮开图，也不能替代本轮要求达标。出现范围内任一项直接判定 `REVISE`，不允许用平均分抵消：

- 主目标不可见、不可识别、被遮挡或不在合理首屏位置。
- 当前仍可用的卡牌 / 法术、计划牌、持有物、装备、单位、行动来源、资源或候选目标不可见、不可读、无法恢复查看，或玩家会误以为这些对象不存在。
- 用户标注图、参考图或当轮明确点名的元素在最终截图中缺失、被弱化到不可识别，或没有等价规则术语承载；除非审计同时证明该元素与当前规则阶段互斥、素材 blocked、目标环境不支持，或用户当轮明确同意省略。
- 为了减少拥挤、突出工作台或避开重叠，把仍参与当前决策的对象降级成不可读缩略图、弱入口、无数量提示的图标、隐藏抽屉或完全移除。
- 只验证局部 `来源 -> 目标 -> 确认 / 结算` 链路，却没有验证其它合法行动来源、候选对象、资源和计划区是否仍能被玩家发现、比较和切换。
- 当前结算主体被放到边栏、日志区、工具区、摘要区或辅助 HUD，导致玩家第一眼无法把掷骰、翻牌、命中、伤害、治疗、检定或揭示结果和主舞台目标 / 来源连起来。
- 图片加载失败、空白、红块、占位符、错误图标或 canvas 实际为空。
- 本轮截图依赖卡牌、法术、技能、装备、附件、单位或牌库 / 法术书让玩家理解来源、目标、动作或流程，但这些关键牌面 / 素材在图中是空白、未加载、只剩壳层、纯色占位或只能靠旁边说明猜测真实对象。
- 控件、文字、卡牌、token、角标或浮层发生重叠、裁切、漂移。
- 固定区域、格子、地图房间、战场格、基地或等价空间单位中，场上对象中心落在区域边界、区域缝隙或格外，卡牌 / 棋子大面积跨区，token 脱离宿主，或玩家无法判断对象属于哪个区域。
- 新增 UI、浮层、特写、toast、提示条或关闭按钮占用 token/状态/资源/生命属性/骰盘/牌堆/手牌等保护槽位，或把这些槽位挤出、遮住、抢焦点。
- 浮层/特写虽然没有遮挡被测试的单一目标，但压住同屏其它关键控件、玩家仍需读取的区域或可点击入口。
- 需要玩家阅读的浮层/特写在未触发明确玩家关闭动作前，因为 prompt、waiting、联机确认、重同步、组件重挂载、回滚信号、hover/blur 或短 timer 而自动退场；卡牌特写若按项目表现事件规范允许“点击空白背景关闭”，该空白点击属于明确玩家关闭动作，不算自动退场。
- 选择高亮遮住对象本体，或视觉效果让目标更难辨认。
- 选择态截图里的目标候选本体不可见、被卡牌预览 / hover 特写 / displayCard / 提示浮层遮住，或只能从内部状态、文件名、测试名推断“这里应该有候选”。
- 目标对象被多层边框、描边、发光环、选择框或装饰框包住，导致玩家第一眼看到的是 UI 边框而不是对象本体。
- 结果符号被错误地当成飞行动效使用，例如叉号、骷髅、对勾、伤害章在命中前沿路径飞行；这些符号必须锚定在命中帧或最终目标状态。
- 玩家不知道该点什么，或提示 UI 被误做成实际交互载体。
- 操作按钮虽然尺寸达标、能点击、离屏幕边缘也够远，但被放到远离现实操作对象的位置，或贴近了错误对象，导致玩家第一眼无法判断它控制哪张牌、哪个目标、哪一手、哪一侧或哪块区域。
- 同一指令在多个位置重复，靠说明文字掩盖层级或交互问题。
- 只让某个主物体居中，但同一任务的指令条、主物体和关键操作没有共享构图中轴。
- 目标选择态仍保留无关 HUD、调试按钮、开发控件或竞争焦点。
- 移动端必要操作热区小于 `44x44 CSS px`，且没有等价可用入口。
- 截图不是当前工作区、当前路由、当前实现或当前目标状态。
- 截图停在目标动作发生前，或没有把验收对象实际触发到可见/可审计状态。
- 布局/遮挡/空间验收截图没有构造关键同屏元素齐全的压力态，导致无法判断是否遮挡按钮、状态、资源、手牌、玩家面板、牌堆、提示或其它持续可见 UI。
- 删除、隐藏、折叠或移动 UI 后留下无职责大空白、死区、异常安全边距或父布局塌陷；如果空白不能解释为真实安全区、展开容量、结算层预留或规则对象槽位，直接判 `REVISE`。
- 当前可支配对象、当前来源对象、计划/准备对象、候选列表、分页、归档入口和主操作按钮互相挤压或抢同一视觉槽位；即使几何上刚好不相交，只要玩家第一眼难以区分各自职责，直接判 `REVISE`。
- 审计者已在截图中口头指出仍有基础布局、可读性、槽位、空白或对象主次问题，却仍输出 `AI_PASS`、打开给用户验收或停止继续重构。
- 用户的位置描述存在多个合理解释，尚未唯一锁定目标锚点、参照物或层级关系，却已经实施、截图或给出 `PASS`。
- 用户问旧版、之前或原来样式时，尚未拿到旧截图、旧代码、旧 evidence 或等价历史基线，却用当前图、当前 DOM 或修后图回答、实施或给出 `PASS`。
- PC 同构任务没有当前 PC 同状态基线截图或等价当前 DOM 证据，却给出 `PASS`。
- 用户已经看图指出不合格后，仍用旧截图、旧 PC 图、E2E 通过或局部元素断言维持 `PASS`。

### 4. 输出裁决

每轮输出：

```text
verdict: PASS | REVISE
score: 0-100
target_requirements:
  - requirement: 用户本轮给出的可判定要求
    status: PASS | REVISE
    evidence: 直接证据
hard_failures: []
negative_impact_checks: []
issues:
  - evidence: 截图中可直接指出的现象
    impact: 对玩家造成的现实问题
    fix: 下一轮具体修改
```

禁止输出“基本没问题”“功能上没问题”“可以先过”这类模糊结论。

### 5. 未通过就继续重构

当结论为 `REVISE`：

1. 按影响排序，只修改能直接解释截图问题的实现。
2. 回到同一真实入口和同一失败状态验证。
3. 重新生成晚于本轮改动的新截图。
4. 重新执行完整审计，不沿用旧分数或旧结论。
5. 持续循环，直到 `PASS`；若真实环境阻塞，明确停在阻塞项，不得宣称通过。

**不要停在“未达标候选”**：只要工具仍可继续修改并重新取证，且失败项属于当前目标范围内的视觉 / 布局 / 槽位问题，就继续循环，不把未达标图或录屏交给用户做人工挑错。只有两种情况可以停：① 已按本 skill 判定 `PASS`，并在触发用户可见展示时准备打开最终验收图或录屏；② 真实环境或输入缺失导致无法继续，且已完整说明阻塞后果、证据、为什么阻止继续、最小补救动作。

- 功能测试证据和视觉证据分别汇报，不能互相替代。
- 保存最终截图绝对路径、视口、目标状态、生成时间和裁决。
