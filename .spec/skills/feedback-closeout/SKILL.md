# 反馈收口

## 单一真相

本 skill 是 BoardGame 反馈收口 workflow 的唯一规范真相源。`references/feedback-open-api.md` 只描述 HTTP 接口；服务器、SSH 和 Mongo 入口按根 `AGENTS.md` 指向的共享用户环境文档读取。

临时材料只作证据或镜像：

- `temp/feedback-closeout/**`
- `evidence/feedback-closeout/**`
- 截图、诊断包、导出文本
- `temp/feedback-closeout/status-board.json`

这些都不能冒充本地数据库当前状态，也不能冒充线上正式反馈记录。

## 默认口径

用户说“处理反馈 / 收口反馈 / 修复反馈”且没有明说线上、生产、远端、真实反馈或回写线上时，默认目标是本地数据库反馈记录。

| 口径 | 真相源 | 允许写哪里 | 禁止 |
| --- | --- | --- | --- |
| 本地数据库 | 本机反馈数据库或本地开发 API | 本地数据库 + 本地状态镜像 | 自动拉线上或说成线上已回写 |
| 线上真实 | 线上真实反馈接口或经确认的线上真实写入口 | 线上真实记录 + 本地状态镜像 | 用本地导出替代线上记录 |
| 离线快照 | 用户明确指定的导出、诊断包或本地文件 | 指定文件 / 状态板 | 说成本地数据库或线上当前状态 |

找不到本地数据库入口时，停在“缺少本地数据库反馈来源”；不要自动改拉线上替代。

## 完成门槛

- 目标范围内仍有 `open / in_progress / resolved` 任一未收口项时，不得宣称完成。
- 数量多不是停止理由；继续批量处理直到清零，或报告真实阻塞。
- **每条反馈都必须建立“原文 + 处理方式”双字段记录，缺一不可。** 反馈原文必须来自本轮确认的真实来源，逐字保留；处理方式必须说明本轮实际做了什么、依据什么证据、当前结果是什么。只写“已修复”“已关闭”“验证通过”“不是 bug”均不算处理方式。
- **没有反馈原文，禁止开始收口；没有具体处理方式，禁止状态回写和最终汇报。** 该限制同时适用于 `resolved`、`closed` 和仍在 `in_progress` 的代表项，不得用反馈 ID、摘要、分类、测试名、内部结论或诊断包路径代替。
- **`resolved` / `closed` 是强门槛，不是文案可选项。** `resolved` 必须同时具备用户可读的 `resolvedMethod`；`closed` 必须同时具备用户可读的 `closedReason`。字段为空、泛化、只写内部术语或无法说明实际动作时，必须退回 `in_progress` 并继续补证据 / 补处理记录。
- **真实规则 / 卡牌 / 技能 / 状态 / 卡图反馈必须完成源头到本地修复的全链路排查。** 最低链路是：反馈原文 → 主真相源原图 / 规则原文 → 数据录入与锁定合同 → 运行时数据 / i18n / assetRef 映射 → 规则实现与消费点 → 同一玩家路径的真实入口回放。根因确认、本地代码 / 数据修复完成、真实入口或有效现场验证完成后，本轮直接写 `resolved`；生产部署和线上版本回查不再是 `resolved` 的前置门槛，只决定能否声称“线上已生效”。
- **“看过代码、测试通过、当前树未复现、当前生产版本已恢复”都不能替代源头排查。** 对卡牌图、效果文字、技能数值、Token、状态、基地或资源索引相关反馈，必须先核对主真相源，再判断是录入错、索引错、消费错、实现错、UI 展示错还是历史现场失效。
- **历史终态默认不可信，必须可复审。** 读取到已有 `resolved / closed` 时，先按上述全链路逐项复核；缺少主真相源、录入合同、消费映射、真实入口或线上版本证据的，立即标为 `needs_review`，实际状态回退为 `in_progress`，不得沿用旧的“已解决”结论。
- **高置信度结论必须逐链路列证据。** `resolvedMethod` / `closedReason` 必须分别写明源头结论、录入结论、实现结论和真实入口结果；若生产尚未部署，额外写明“本地已修复，生产待发布”，但不得因此把本地 `resolved` 延后或再次改写。只有尚未完成本地根因确认、修复或真实入口验证时，结论才保持“部分确认 / 未完成”。
- 每条人类玩家反馈在进入 `resolved` 或 `closed` 前，必须先从最近真实入口做一次端到端尝试：优先恢复原房间 / 回放 / 诊断包；没有时按反馈文字重建最小可玩局面。只读代码、只看触发日志、只看到额度变化、只看到交互弹窗或只跑单测，都不算完成这一步。
- `in_progress` 只表示当前仍在具体复现、修复或验证；不得把“证据不足”作为无限期停车位。真实入口已按反馈步骤尝试，但原始症状没有出现时，记录实际入口、操作步骤、版本 / 工作树和结果，按“本次未复现，不等于已修复”关闭。
- 每次阶段汇报和最终汇报必须写清口径和绝对时间。
- 对用户展示问题时，以“反馈内容 / 现实症状”为标题；反馈 ID 只放追溯证据，不作为主标题。
- 玩家反馈要写清游戏中文名、命中的对象 / 页面 / 效果、规则本应发生什么、实际坏在哪条玩家可见链路。
- 玩家反馈命中卡牌、技能、状态、基地、教程步骤或其它规则效果时，必须同时给出“效果描述原文”：从本轮确认的规则书、牌面图、录入合同、运行文案或其它真相源逐字摘出对应效果文本，并标明来源；不能只给实现摘要、测试名或自己的改写。
- 每条真 bug 反馈收口前，必须补“漏审复盘 / 规范回代判断”：旧测试、旧审计或旧规范为什么没挡住；属于已有规范未执行、规范缺口、测试缺口、审计留档缺口还是单游戏合同问题；若需要更新规范，先按系统 `skill-governance` 判断并写清唯一真相源，再同轮更新，若不需要，写清哪条现有规范已经覆盖。
- 系统自动反馈要写清自动检测场景、现实影响、监控触发条件、止血动作和根因证据是否存在。

## 处理顺序

默认优先级是人类反馈 > 系统自动反馈。系统单可以作为并行止血支线，但不能因为更容易查或数量更多挤占人类反馈。

系统自动反馈即使暂缓，也必须先做最低分诊：

- 自动反馈类型；
- 错误消息；
- 状态快照 / 行动日志里的原因；
- 当前是否存在 interaction、legal actions、AI decision preview；
- 是否属于共享 / 私有视图不一致、0 个合法动作、恢复 / 跳过被拒绝、或基础设施告警。

基础设施告警只有重启、恢复、阈值和采样证据时，只能说已止血 / 已恢复；没有 profiler、堆栈、房间 / 请求关联或循环位置证据，不得称为根因已定位。

## 工作流

1. **定位来源**：先确认本轮口径和真实读写源；线上口径必须确认接口返回反馈 JSON 而不是前端 fallback HTML。
2. **排重归并**：按内容和错误签名归并重复组，只处理代表项。
3. **分类**：至少分为 `bug_candidate`、`non_bug`、`needs_owner_decision`、`needs_review`。
4. **检查近期状态**：先看本轮口径下该反馈是否已经 `resolved / closed`，再看本地镜像、历史 evidence 和最近相关代码 / 测试，避免重复修。
5. **分诊真假 bug**：先锁反馈真实症状、真相源和可复现链路；若反馈涉及规则 / 卡牌 / 效果，先摘出效果描述原文并对照当前实现，再决定是否改代码。真实入口尝试是人类反馈的必经步骤，不能用中间触发证据替代。
   - **场景真实性校验**：用最小可玩局面或 TestHarness 状态重建时，必须先证明注入的前置条件被运行时真正消费，目标阶段、响应窗口和目标对象确实进入牌桌状态；不能把夹具输入值当成运行事实。若输入字段没有反映到真实画面或权威状态（例如仍显示默认阈值、仍处于普通回合而非计分响应窗口），本次只算“复现入口无效”，应修正夹具或改用受支持的状态注入方式，不得据此判定反馈未复现、关闭反馈或宣称已修复。
6. **修复与验证**：真实入口按原步骤复现出反馈本体时，修复后必须回到同一入口和同一症状验证并保留证据；满足本地根因、修复和验证条件后，本轮直接写 `resolved`。真实入口按原步骤未复现时，记录实际尝试范围、入口、版本 / 工作树和最终状态，说明“未复现不等于已修复”，然后关闭，不得继续无期限保持 `in_progress`。
7. **漏审复盘与规范回代**：真 bug 修完后按 `regression-closeout.md` 反思旧测试 / 旧审计 / 旧规范为什么没挡住，并明确本轮是否更新规范；需要更新时先锁 `canonical-source`，不能把结论只留在对话或 evidence。
8. **立即回写**：接手即写 `in_progress`；结论成立即写 `resolved / closed`，并同步本地状态镜像。
9. **回查收口**：最终回复前回查本轮口径下的真实状态和本地镜像。
10. **用户决策门**：如果真实入口尚未尝试，或尝试过程中明确需要用户决定规则 / 产品取舍，必须保留为 `in_progress`，并在汇报中先逐字给出真实反馈原文（保留换行、标点和语气），再给证据和待判断事项。真实入口已经按原步骤尝试且原始症状未出现时，不再把“未证实”作为无限期状态；按实际尝试结果写 `closedReason` 关闭，并明确“本次未复现，不等于已修复”。

## 关键分诊门槛

### 规则 / 效果类玩家反馈

反馈内容指向卡牌、技能、状态、基地、教程步骤或其它规则效果时，交付给用户和写入 evidence 的第一组事实必须包含：

- 反馈原文：玩家提交的真实描述，保留关键限定词。
- 效果描述原文：本轮确认真相源里的完整效果文本；若只有摘要、翻译或录入合同，也必须明确它是哪一种来源。
- 当前现场：操作记录、状态快照、截图或回放里实际发生了什么。
- 对照结论：原文要求、现场表现和当前实现哪里一致、哪里不一致。

缺少效果描述原文时，只能说“缺少规则 / 牌面 / 录入合同原文”，并继续查找或把它列为阻塞；不得用实现代码、测试断言、历史修复摘要或内部字段替代效果原文。

### 带操作记录 / 状态快照的玩家反馈

反馈自带操作记录、状态快照、事件流、资源采样或恢复上下文时，必须先还原玩家提交前最近的可见情景：谁在操作、处于哪个阶段、刚触发了哪个玩家可见效果、该效果实际作用到了谁或什么对象。反馈词同时可能指“界面标识看不懂”和“规则效果上错对象”时，先用操作记录和状态快照追到触发效果与目标归属；没有证明二者一致前，不得只凭“标记 / 玩家编号 / 看不清 / 反了”等关键词改 HUD、座位标签、规则目标或测试基线，也不得回写 `resolved`。

未锁定反馈原文、操作记录和当时触发效果前，禁止修改 UI 外观、布局、视觉基线或截图验收口径；只能继续补证据、复现原始位点，或把已做的外观改动标为误判并撤回 / 隔离。

如果发现此前已经按未锁定前提做了 UI、规则、数据、测试或状态回写，必须先把该改动标为误判并撤回或隔离，再重新分诊原始反馈。撤回说明要区分：已撤回的是哪类改动；原始反馈当前已确认的事实是什么；尚未确认的是 UI 选择文案混淆、玩家误选、规则目标写反，还是其它链路问题。

### 体验 / 策略反馈

反馈主要是“卡、慢、太重、不舒服、建议改默认、动画太多、交互节奏不好”，且没有功能错误证据时，先判为产品 / 体验取舍。可以收集证据和给方案；改默认表现、开关、节奏、文案或流程前必须让用户决策。

### 卡死 / 阻塞反馈

反馈是“卡死、不能继续、一直弹、操作后没下文”时，优先使用它自带的真实 `stateSnapshot`、`actionLog`、`eventStream`、截图或同批导出回放到原始位点。只构造相似局面、只看 prompt 出现或只写单测，不能宣称真实反馈已复现。

### 带图反馈

只要反馈自带截图、牌面图、局面图或录像首帧，必须先核图：图上实际写了什么、显示了什么、发生了什么，再核对录入数据、文案、规则源和实现链。图面和录入冲突时，先判录入 / 实现候选错误，不得优先按玩家误解关闭。

### 录入冲突

如果实现、审计、测试和文案都一致，但都依赖同一份旧录入数据，不能据此证明正确。必须回到主真相源重查录入合同，再判断是录入错、实现错，还是两者都错。

## 反馈本体结论

每条反馈进入已修 / 已关闭前，必须落入一类：

| 结论 | 含义 | 状态建议 |
| --- | --- | --- |
| 已用真实反馈状态复现 | 用反馈自带真实证据回放到原始位点并修复 | `resolved` |
| 当前树已恢复 / 已失效 | 用真实证据回放后当前代码不复现 | 通常 `closed`，必要时 `resolved` |
| 真实入口尝试后未复现 | 已从最近真实入口按反馈步骤操作，原始症状没有出现 | `closed`；必须写清尝试范围、入口、版本 / 工作树和结果，并注明“未复现不等于已修复” |
| 尚未完成真实入口尝试 | 还没有按玩家路径进入真实页面，或入口 / 局面无法启动 | `in_progress`；继续补入口、局面或外部依赖，不得用日志和单测替代 |
| 证据不足 / 未证实且未完成真实入口尝试 | 仍缺少真实入口、原始位点或必要规则真相源 | `in_progress`，直到完成真实入口尝试或形成明确外部阻塞 |
| 仅修相关风险或通用防线 | 修到邻近风险，但未复现反馈本体 | 不能写成反馈本体已修 |

如果顺手补了采集或诊断能力，汇报必须分开写：反馈本体当前结论，以及本轮额外补了什么诊断能力。

## 原文与处理方式硬门

这是反馈收口的**一票否决项**，优先级高于状态板、测试结果、evidence 文件和数量清零：

1. **反馈原文**：从本轮真实来源读取 `content`，逐字引用玩家或系统提交内容；保留换行、标点、重复措辞、大小写和语气。不得用摘要、翻译、分类名、内部标题或自己的改写替代。
2. **处理方式**：必须写清“做了什么 + 为什么这样做 + 用什么验证 + 当前状态”。至少包含实际入口 / 代码或配置动作 / 验证动作 / 结果；若是系统反馈，还要包含止血动作、根因证据现状和剩余风险。
3. **规则类反馈**：处理方式之外，仍必须单独给出规则 / 牌面 / 录入合同的“效果描述原文”和来源；代码、测试断言、历史总结不能顶替它。
4. **未解决或未收口项**：先展示反馈原文，再写当前事实、已做处理、未完成事项和下一步；不能只给“证据不足”“待确认”“处理中”。
5. **状态写回前检查**：`resolved` 必须有 `resolvedMethod`，`closed` 必须有 `closedReason`；两者都必须是提交者能看懂的现实描述。任何一项缺失、空泛或不可追溯，都不得写回终态。

最低合格记录格式：

```text
反馈原文：
<逐字原文>

处理方式：
<实际采取的动作、依据、验证和结果>

当前状态：
<in_progress / resolved / closed>
```

如果是规则 / 效果类反馈，在“反馈原文”和“处理方式”之间必须插入：

```text
效果描述原文：
<真相源逐字文本>
来源：
<规则书 / 牌面图 / 录入合同 / 运行文案 / 其它已确认来源>
```

## 源头到本地修复全链路硬门

凡是反馈涉及卡牌、技能、状态、Token、基地、效果文字、数值、卡图、图集槽位、资源索引或玩家可见规则结果，必须逐项完成以下链路：

1. **反馈原文**：确认玩家实际描述和限定词，没有把相邻反馈或内部摘要当成目标。
2. **主真相源**：打开并核对正式卡牌图、规则书、官方组件、用户指定来源或已锁定规则原文；卡图反馈必须核对完整卡面和对应图集 / 槽位，不能只看名称或代码字段。
3. **数据录入**：确认对象全集、`id / defId / variant / slot`、原文、特殊含义元素、图面数据、图片登记和录入合同状态；缺失、`partial`、`blocked` 或 `disputed` 时不得进入已解决结论。
4. **消费映射**：确认 i18n、静态数据、`assetRef / previewRef`、运行时对象、规则实现、UI 展示和资源 manifest 是否消费同一份锁定合同；发现冲突先回录入层，不得用实现迁就源头。
5. **玩家链路**：按反馈原步骤进入真实页面，确认目标对象、阶段、响应窗口、交互和可见结果；夹具没有被运行时真正消费时，本次复现无效。
6. **生产发布与线上回查（附加）**：如已部署，确认目标生产版本 / 资源版本 / API 真实入口已经包含结论对应的改动，并回查同类线上反馈或同一房间结果；未部署时只记录“生产待发布”，不阻塞本地 `resolved`。

最低验收矩阵：

| 链路 | 必须留下的证据 | 缺失时 |
| --- | --- | --- |
| 反馈原文 | 真实来源逐字 `content` | 不得开始收口 |
| 主真相源 | 原图 / 规则原文定位与摘录 | `in_progress` |
| 数据录入 | 合同、槽位、assetRef、状态 | `in_progress` |
| 消费映射 | 数据到实现 / UI / 资源的对照 | `in_progress` |
| 玩家链路 | 同路径回放、状态 / 截图 / 日志 | `in_progress` |
| 生产发布 / 线上回查 | 版本、入口、远端结果 | 不得声称“线上已生效”，不阻塞本地 `resolved` |

### 历史终态复审

- 对已有 `resolved / closed` 的真实规则反馈，先建立上述本地验收矩阵，再决定是否保留终态；生产发布 / 线上回查缺失本身不构成回退理由。
- 缺少源头、录入、消费映射、修复或真实入口验证中的任一关键本地链路时，必须记录 `reopenReason: "缺少源头到本地修复全链路证据"`，把状态回退为 `in_progress`，并保留原状态、原文和旧结论作为历史追溯。仅缺生产部署 / 线上回查时，不得回退本地 `resolved`。
- 只能证明当前代码或测试通过，不能证明主真相源、录入和消费一致时，结论不得高于“实现侧部分确认”。
- 只能证明当前入口未复现，不能证明历史现场已被修复时，必须明确“本次未复现，不等于已修复”，不能写“当前已恢复”。
- 源头、录入、消费映射、本地修复和真实入口证据齐全且相互一致时，直接恢复 `resolved` 或 `closed`；生产部署 / 线上回查只作为“线上已生效”的附加证明，不得成为第二次状态更新的理由。同批重复项跟随代表项，但不能跳过代表项的本地全链路复审。

### 未解决反馈的原文交付

以下情况都视为“未解决”：没有真实回放证据、只确认了触发条件或止血动作、修的是邻近风险、需要产品 / 规则 / 体验取舍，或无法判断反馈描述对应哪条链路。

- 未解决反馈不得只用摘要、内部分类或诊断结论向用户汇报。必须从本轮真实来源读取 `content`，逐字引用原文；原文中的换行、标点、重复措辞和语气都要保留。
- 反馈 ID、游戏名、时间和诊断包路径只能作为追溯证据，不能替代原文。
- 原文之后再说明：当前已确认的事实、尚未确认的事实、为什么不能继续自动处理，以及需要用户判断的最小选项。
- 在用户作出下一步决定前，状态保持 `in_progress`；不得为了清零数量而写成 `closed`，也不得把“已止血 / 当前未复现 / 证据不足”说成“问题已解决”。
- 用户明确选择继续、关闭或接受某个方案后，才按该决定执行代码修改、状态回写或 `closed` / `resolved` 收口。

## 状态语义

| 状态 | 使用条件 | 必填字段 |
| --- | --- | --- |
| `in_progress` | 已明确接手，预计继续处理 | 接手说明 / owner |
| `resolved` | 真实 bug 已定位、完成本地代码 / 数据修复、真实入口验证并有证据；生产未部署时可在处理方式中注明待发布 | `resolvedMethod` |
| `closed` | 误报、建议、已失效，或用户明确决定不再继续处理 | `closedReason` |

重复 / 同根因反馈跟随代表项最终结论：代表项是已修复 bug，则同组都 `resolved`；代表项关闭，同组才 `closed`。不得因为重复就把已解决 bug 降级成 `closed`。

`closedReason` 和 `resolvedMethod` 默认是给反馈提交者看的。必须用现实语言说明发生了什么、为什么这样处理、用户是否还要做什么；禁止直接写“不是 bug、证据不足、当前树已恢复、按非现存业务 bug 关闭、验证通过、状态回写”等内部裁定词。

## 本地状态镜像

- 本地数据库口径：本地数据库是正式源，`status-board.json` 是镜像。
- 线上口径：线上真实记录是正式源，`status-board.json` 是镜像。
- 离线快照口径：只更新用户指定的本地文件 / 状态板，并明确没有覆盖数据库或线上。
- 真实源写成功但镜像失败，本轮状态回写仍未完成；必须继续修镜像或标 `blocked`。
- 镜像写成功但真实源失败，只能称为阻塞记录，不能宣称真实反馈已收口。

## 并行处理

并行前必须确认：

- 每个 worker 只接一个代表项；
- 只挑脚本给出的 `parallelCandidates`，或确认 `conflictKey` 不冲突；
- 多个 worker 不写同一批关键文件；
- 同一重复组只允许一个 worker 处理代表项。

worker 任务必须包含反馈 ID、诊断包路径、文件 / 模块边界、真假 bug 判定要求、验证要求和状态回写要求。使用子 agent 时默认继承主 agent 的模型与推理强度，不写死具体模型版本。

## 专项路由

通用反馈收口只负责来源锁定、排重、状态回写和证据口径。若反馈命中某个游戏专项 workflow，具体规则链、E2E 门禁、看图断言和游戏规则事实回到专项 skill；不得把专项游戏名、卡牌名、状态名或链路字段复制回本文件当通用规范。

## 脚本入口

- `triage-open-feedback.mjs`：线上口径下拉取开放反馈、排重、分类、生成诊断包与并行候选。
- `sync-feedback-status-board.mjs`：从 `summary.json` 初始化或刷新本地状态镜像，覆盖代表项和同组反馈 ID。
- `update-feedback-status.mjs`：线上口径下自动选择 HTTP 管理接口或生产机 Mongo 回写状态，并同步本地镜像。
- `finalize-feedback-group.mjs`：按 `summary.json` 收口代表项，并默认同步同组反馈状态。
- `update-local-feedback-board.mjs`：更新本地状态镜像；它不等于本地数据库回写。

线上 HTTP 管理接口可用时可用 token；缺凭证、401/403 或接口不是真实线上写入口时，线上口径可切到已确认的生产机 / Mongo 最小写入口。这个授权只覆盖反馈状态回写，不扩展为任意生产改数、部署、清理或旁路修复。

## 交付口径

最终汇报必须写清：

- 本轮口径：本地数据库、线上真实或离线快照；
- 统计时间；
- 总共抓到多少未收口反馈、归并为多少代表项、当前剩余多少；
- 哪些是真 bug，改了什么，验证了什么，状态是否 `resolved`；
- 规则 / 卡牌 / 效果类反馈对应的效果描述原文和来源；
- 真 bug 的漏审复盘与规范回代判断：为什么旧测试 / 旧审计 / 旧规范没挡住，本轮是否已更新唯一规范源；
- 哪些不是 bug / 已失效 / 证据不足，为什么 `closed`；
- 系统反馈是否只是止血，根因证据是否存在；
- 实际回写的真实入口和本地镜像是否一致；
- 哪些还未处理，以及为什么不能并行或继续。
- **逐条列出每个代表项的“反馈原文 + 处理方式 + 当前状态”。** 只列统计数字、反馈 ID、分类或测试结果，均不满足交付。
- **最终汇报前逐条检查双字段。** 任一代表项缺反馈原文或缺具体处理方式，最终汇报必须判定为未完成；不得用“本轮已处理”“已同步状态”“已验证”代替。

同批反馈默认合并为一个提交；除非用户明确要求拆分，不为单条小修复制造多次提交。
