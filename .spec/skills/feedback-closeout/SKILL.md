# 反馈收口

## 单一真相

本 skill 是 BoardGame 反馈收口 workflow 的唯一规范真相源。`references/feedback-open-api.md` 只描述 HTTP 接口；服务器、SSH 和 Mongo 入口按根 `AGENTS.md` 指向的共享用户环境文档读取。

临时材料只作证据或镜像：

- `temp/feedback-closeout/**`
- `evidence/feedback-closeout/**`
- 截图、诊断包、导出文本
- `temp/feedback-closeout/status-board.json`

这些都不能冒充本地数据库当前状态，也不能冒充线上正式反馈记录。

## 默认口径

用户说“处理反馈 / 收口反馈 / 修复反馈”且没有明说线上、生产、远端、真实反馈或回写线上时，默认目标是本地数据库反馈记录。

| 口径 | 真相源 | 允许写哪里 | 禁止 |
| --- | --- | --- | --- |
| 本地数据库 | 本机反馈数据库或本地开发 API | 本地数据库 + 本地状态镜像 | 自动拉线上或说成线上已回写 |
| 线上真实 | 线上真实反馈接口或经确认的线上真实写入口 | 线上真实记录 + 本地状态镜像 | 用本地导出替代线上记录 |
| 离线快照 | 用户明确指定的导出、诊断包或本地文件 | 指定文件 / 状态板 | 说成本地数据库或线上当前状态 |

找不到本地数据库入口时，停在“缺少本地数据库反馈来源”；不要自动改拉线上替代。

## 完成门槛

- 目标范围内仍有 `open / in_progress / resolved` 任一未收口项时，不得宣称完成。
- 数量多不是停止理由；继续批量处理直到清零，或报告真实阻塞。
- 每次阶段汇报和最终汇报必须写清口径和绝对时间。
- 对用户展示问题时，以“反馈内容 / 现实症状”为标题；反馈 ID 只放追溯证据，不作为主标题。
- 玩家反馈要写清游戏中文名、命中的对象 / 页面 / 效果、规则本应发生什么、实际坏在哪条玩家可见链路。
- 系统自动反馈要写清自动检测场景、现实影响、监控触发条件、止血动作和根因证据是否存在。

## 处理顺序

默认优先级是人类反馈 > 系统自动反馈。系统单可以作为并行止血支线，但不能因为更容易查或数量更多挤占人类反馈。

系统自动反馈即使暂缓，也必须先做最低分诊：

- 自动反馈类型；
- 错误消息；
- 状态快照 / 行动日志里的原因；
- 当前是否存在 interaction、legal actions、AI decision preview；
- 是否属于共享 / 私有视图不一致、0 个合法动作、恢复 / 跳过被拒绝、或基础设施告警。

基础设施告警只有重启、恢复、阈值和采样证据时，只能说已止血 / 已恢复；没有 profiler、堆栈、房间 / 请求关联或循环位置证据，不得称为根因已定位。

## 工作流

1. **定位来源**：先确认本轮口径和真实读写源；线上口径必须确认接口返回反馈 JSON 而不是前端 fallback HTML。
2. **排重归并**：按内容和错误签名归并重复组，只处理代表项。
3. **分类**：至少分为 `bug_candidate`、`non_bug`、`needs_owner_decision`、`needs_review`。
4. **检查近期状态**：先看本轮口径下该反馈是否已经 `resolved / closed`，再看本地镜像、历史 evidence 和最近相关代码 / 测试，避免重复修。
5. **分诊真假 bug**：先锁反馈真实症状、真相源和可复现链路，再决定是否改代码。
6. **修复与验证**：真 bug 必须有修复、匹配验证和证据；误报 / 建议 / 已失效只写结论，不改代码。
7. **立即回写**：接手即写 `in_progress`；结论成立即写 `resolved / closed`，并同步本地状态镜像。
8. **回查收口**：最终回复前回查本轮口径下的真实状态和本地镜像。
9. **用户决策门**：只要反馈本体没有被证明解决，或下一步需要用户判断，必须保留为 `in_progress`，并在汇报中先逐字给出真实反馈原文（保留换行、标点和语气），再给证据和待判断事项；不得把“证据不足 / 未证实 / 需要判断”直接回写成 `closed`。

## 关键分诊门槛

### 带操作记录 / 状态快照的玩家反馈

反馈自带操作记录、状态快照、事件流、资源采样或恢复上下文时，必须先还原玩家提交前最近的可见情景：谁在操作、处于哪个阶段、刚触发了哪个玩家可见效果、该效果实际作用到了谁或什么对象。反馈词同时可能指“界面标识看不懂”和“规则效果上错对象”时，先用操作记录和状态快照追到触发效果与目标归属；没有证明二者一致前，不得只凭“标记 / 玩家编号 / 看不清 / 反了”等关键词改 HUD、座位标签、规则目标或测试基线，也不得回写 `resolved`。

未锁定反馈原文、操作记录和当时触发效果前，禁止修改 UI 外观、布局、视觉基线或截图验收口径；只能继续补证据、复现原始位点，或把已做的外观改动标为误判并撤回 / 隔离。

如果发现此前已经按未锁定前提做了 UI、规则、数据、测试或状态回写，必须先把该改动标为误判并撤回或隔离，再重新分诊原始反馈。撤回说明要区分：已撤回的是哪类改动；原始反馈当前已确认的事实是什么；尚未确认的是 UI 选择文案混淆、玩家误选、规则目标写反，还是其它链路问题。

### 体验 / 策略反馈

反馈主要是“卡、慢、太重、不舒服、建议改默认、动画太多、交互节奏不好”，且没有功能错误证据时，先判为产品 / 体验取舍。可以收集证据和给方案；改默认表现、开关、节奏、文案或流程前必须让用户决策。

### 卡死 / 阻塞反馈

反馈是“卡死、不能继续、一直弹、操作后没下文”时，优先使用它自带的真实 `stateSnapshot`、`actionLog`、`eventStream`、截图或同批导出回放到原始位点。只构造相似局面、只看 prompt 出现或只写单测，不能宣称真实反馈已复现。

### 带图反馈

只要反馈自带截图、牌面图、局面图或录像首帧，必须先核图：图上实际写了什么、显示了什么、发生了什么，再核对录入数据、文案、规则源和实现链。图面和录入冲突时，先判录入 / 实现候选错误，不得优先按玩家误解关闭。

### 录入冲突

如果实现、审计、测试和文案都一致，但都依赖同一份旧录入数据，不能据此证明正确。必须回到主真相源重查录入合同，再判断是录入错、实现错，还是两者都错。

## 反馈本体结论

每条反馈进入已修 / 已关闭前，必须落入一类：

| 结论 | 含义 | 状态建议 |
| --- | --- | --- |
| 已用真实反馈状态复现 | 用反馈自带真实证据回放到原始位点并修复 | `resolved` |
| 当前树已恢复 / 已失效 | 用真实证据回放后当前代码不复现 | 通常 `closed`，必要时 `resolved` |
| 证据不足 / 未证实 | 缺少能回到原始位点的关键证据 | 默认保持 `in_progress`，把原文交给用户判断下一步；只有用户明确决定不再继续时才 `closed` |
| 仅修相关风险或通用防线 | 修到邻近风险，但未复现反馈本体 | 不能写成反馈本体已修 |

如果顺手补了采集或诊断能力，汇报必须分开写：反馈本体当前结论，以及本轮额外补了什么诊断能力。

### 未解决反馈的原文交付

以下情况都视为“未解决”：没有真实回放证据、只确认了触发条件或止血动作、修的是邻近风险、需要产品 / 规则 / 体验取舍，或无法判断反馈描述对应哪条链路。

- 未解决反馈不得只用摘要、内部分类或诊断结论向用户汇报。必须从本轮真实来源读取 `content`，逐字引用原文；原文中的换行、标点、重复措辞和语气都要保留。
- 反馈 ID、游戏名、时间和诊断包路径只能作为追溯证据，不能替代原文。
- 原文之后再说明：当前已确认的事实、尚未确认的事实、为什么不能继续自动处理，以及需要用户判断的最小选项。
- 在用户作出下一步决定前，状态保持 `in_progress`；不得为了清零数量而写成 `closed`，也不得把“已止血 / 当前未复现 / 证据不足”说成“问题已解决”。
- 用户明确选择继续、关闭或接受某个方案后，才按该决定执行代码修改、状态回写或 `closed` / `resolved` 收口。

## 状态语义

| 状态 | 使用条件 | 必填字段 |
| --- | --- | --- |
| `in_progress` | 已明确接手，预计继续处理 | 接手说明 / owner |
| `resolved` | 真实 bug 已定位、修复、验证并有证据 | `resolvedMethod` |
| `closed` | 误报、建议、已失效，或用户明确决定不再继续处理 | `closedReason` |

重复 / 同根因反馈跟随代表项最终结论：代表项是已修复 bug，则同组都 `resolved`；代表项关闭，同组才 `closed`。不得因为重复就把已解决 bug 降级成 `closed`。

`closedReason` 和 `resolvedMethod` 默认是给反馈提交者看的。必须用现实语言说明发生了什么、为什么这样处理、用户是否还要做什么；禁止直接写“不是 bug、证据不足、当前树已恢复、按非现存业务 bug 关闭、验证通过、状态回写”等内部裁定词。

## 本地状态镜像

- 本地数据库口径：本地数据库是正式源，`status-board.json` 是镜像。
- 线上口径：线上真实记录是正式源，`status-board.json` 是镜像。
- 离线快照口径：只更新用户指定的本地文件 / 状态板，并明确没有覆盖数据库或线上。
- 真实源写成功但镜像失败，本轮状态回写仍未完成；必须继续修镜像或标 `blocked`。
- 镜像写成功但真实源失败，只能称为阻塞记录，不能宣称真实反馈已收口。

## 并行处理

并行前必须确认：

- 每个 worker 只接一个代表项；
- 只挑脚本给出的 `parallelCandidates`，或确认 `conflictKey` 不冲突；
- 多个 worker 不写同一批关键文件；
- 同一重复组只允许一个 worker 处理代表项。

worker 任务必须包含反馈 ID、诊断包路径、文件 / 模块边界、真假 bug 判定要求、验证要求和状态回写要求。使用子 agent 时默认继承主 agent 的模型与推理强度，不写死具体模型版本。

## 专项路由

通用反馈收口只负责来源锁定、排重、状态回写和证据口径。若反馈命中某个游戏专项 workflow，具体规则链、E2E 门禁、看图断言和游戏规则事实回到专项 skill；不得把专项游戏名、卡牌名、状态名或链路字段复制回本文件当通用规范。

## 脚本入口

- `triage-open-feedback.mjs`：线上口径下拉取开放反馈、排重、分类、生成诊断包与并行候选。
- `sync-feedback-status-board.mjs`：从 `summary.json` 初始化或刷新本地状态镜像，覆盖代表项和同组反馈 ID。
- `update-feedback-status.mjs`：线上口径下自动选择 HTTP 管理接口或生产机 Mongo 回写状态，并同步本地镜像。
- `finalize-feedback-group.mjs`：按 `summary.json` 收口代表项，并默认同步同组反馈状态。
- `update-local-feedback-board.mjs`：更新本地状态镜像；它不等于本地数据库回写。

线上 HTTP 管理接口可用时可用 token；缺凭证、401/403 或接口不是真实线上写入口时，线上口径可切到已确认的生产机 / Mongo 最小写入口。这个授权只覆盖反馈状态回写，不扩展为任意生产改数、部署、清理或旁路修复。

## 交付口径

最终汇报必须写清：

- 本轮口径：本地数据库、线上真实或离线快照；
- 统计时间；
- 总共抓到多少未收口反馈、归并为多少代表项、当前剩余多少；
- 哪些是真 bug，改了什么，验证了什么，状态是否 `resolved`；
- 哪些不是 bug / 已失效 / 证据不足，为什么 `closed`；
- 系统反馈是否只是止血，根因证据是否存在；
- 实际回写的真实入口和本地镜像是否一致；
- 哪些还未处理，以及为什么不能并行或继续。

同批反馈默认合并为一个提交；除非用户明确要求拆分，不为单条小修复制造多次提交。
