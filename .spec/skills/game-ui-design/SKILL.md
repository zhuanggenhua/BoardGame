# Game UI Design

本 skill 是跨项目通用的游戏 UI 设计 `canonical-source`。它负责把游戏规则、玩家任务、素材对象和饱和状态转成可送审的 UI 设计；项目 skill 负责项目路径、素材合同、组件约定和用户专项纠正。

## 连续流程基线

- 先把回合拆成“系统自动结算阶段”和“玩家决策阶段”。没有选择、响应或并行确认的阶段应自动进入下一个决策阶段，不能把系统结算伪装成需要点击的结束回合。
- 所有需要阅读的卡牌、规则提示和计划对象都必须有统一、可发现的放大入口；关闭控件使用叠加在右上角的叉号，不为关闭文字单独占用布局空间。实现优先复用共享检视组件。
- 地图缩放与拖拽只作用于地图视窗及其内容父级，不能让页面壳层、手牌或 HUD 一起移动；验收必须在拖拽前后确认 HUD 锚点保持不变。
- 阶段指示器按游戏模型选择：卡牌中心、直接出牌的流程默认采用上下文动作提示，不强行加入 Dice Throne 式阶段轨道；仅当阶段顺序本身是玩家决策信息时才独立展示。
- 开放式地图不得被固定 `aspect-ratio` 或百分比小框限制。视窗占据牌桌可用空间，地图内容在独立变换层中自由平移/缩放，HUD 保持固定锚点。

## 使用顺序

1. 先锁四项前提：问题对象、真相来源、目标入口/环境、验收口径。
2. 先读当前项目 `AGENTS.md`、项目 UI/素材 skill、规则书/状态机/脚本/素材合同，再读本 skill。
3. 若 UI 依赖规则、卡牌、棋盘、token、骰子、TTS/Workshop、旧平台或物理配件，先读 `references/rule-to-ui-design.md`。
4. 进入布局和交互前，读 `references/layout-interaction-patterns.md`。
5. 用户点名已有游戏、旧实现或成熟产品作为参考时，先读取该参考的真实实现与当前截图，提炼可迁移不变量；参考截图必须处在同类任务的实际操作态，例如组牌要进入真实编辑页、地图要进入真实对局页，入口页、导入页、选角色页、营销页或空态不能冒充参考依据；不得只凭印象复制视觉，也不得跳过参考直接改目标游戏。若参考已具备卡牌放大、分类筛选、地图拖拽缩放、详情层、视角切换等基础交互，目标游戏必须复用、抽共享或写出不采用理由。
6. 送设计稿、截图或实现验收前，读 `references/quality-gates.md`。
7. 若用户明确指定 Open Design，走 Open Design artifact 设计稿；不得改走图片模型生图。若用户要求位图视觉稿，则按项目位图设计交付规则执行。

## 核心流程

### 0. 设计模式，不是固定版式

本 skill 输出的是可迁移的设计模式语言，不是把某个游戏、某张截图或某轮用户裁定固化成所有游戏的版式模板。

- 通用层只写不变量：玩家任务、对象职责、信息权重、隐藏边界、实体锚点、层级、可读性、输入路径和验收方法。
- 具体位置、皮肤、构图比例和素材落点是设计裁定：必须由当前游戏规则、素材、玩家任务、用户标注和当前候选稿共同决定。
- 用户反复纠正的内容先拆成两类：`可迁移原则` 和 `本游戏基线裁定`。可迁移原则进入本 skill；本游戏基线裁定进入项目 skill、设计合同或用户故事。
- 禁止把“这次这张图这样放才对”改写成“以后所有游戏都必须这样放”。正确写法是“这个对象承担什么职责；哪些条件下适合放在 HUD / 场地 / 牌区 / 弹层；当前项目采用哪一种，并说明理由”。
- 硬失败只针对职责错、对象漏、隐藏信息错、玩家不知道下一步、关键对象不可读、结算层脱离来源/目标、素材语义误用等不变量；不针对某个固定坐标或单一布局答案，除非用户或项目合同已经明确批准为当前基线。

### 1. 规则到对象

先证明自己理解了游戏，而不是只找到了素材。

- 写 `真相源账本`：规则页、状态机、TTS/Workshop、atlas、素材路径、现有截图或项目合同。
- 写 `对象职责表`：每个规则对象是什么、玩家何时操作/检视、是否隐藏、是否公开归档、是否只是提示或规则参考。
- 拆相似对象：角色实体、角色头像、角色规则卡、提示卡、token、状态牌、日志和归档堆不能凭名字或图像相似合并。
- 为相似对象写 `职责 -> 可选承载模式`，例如身份提示可以是头像、规则卡缩略、座位牌、状态板或角色模型旁标签；战场实体可以是 mini、standee、人物卡、token 或卡牌本体。先比较职责和玩家任务，再选落位。
- 用规则术语命名 UI。用户口语可以映射，但上屏、审计和实现命名不能引入规则里不存在的默认概念。

### 2. 对象到玩家任务

UI 设计先回答“玩家此刻要做什么”。

- 写当前阶段、当前玩家、下一次点击对象、点击后发生什么、是否能撤销。
- 写 `交互合同`：用户先看见什么、点哪个真实对象或控件、出现哪些候选、如何选择、选择后进入草稿 / 确认 / 提交 / 退场中的哪一步、错误或取消如何恢复。没有这条合同，不进入实现或截图验收。
- 能由真实对象本体承接的交互，默认本体直选：来源对象、棋盘格、场上卡、token、骰子、牌堆入口。
- 如果用户目标是“把 A 关联到 B”“从一组选项里配置正确对象”“选择图片 / token / 卡牌 / 枚举 / 资源”，默认交互是 `点击当前值或素材本体 -> 展示合法候选集合 -> 用户选择候选 -> 形成可撤销草稿或确认结果`，不能只交一个自由文本输入框。
- 有限候选集合来自规则对象全集、素材 manifest、配置枚举、角色列表、牌库、token 目录或其它正式索引时，UI 必须优先提供候选选择器；自由文本只能作为高级补充入口，并且必须有校验、错误提示和提案语义。
- 面向玩家、配置者或人工审查者的主交互语言必须是人能识别的对象名称、缩略图、业务状态或可预览结果；内部路径、素材 ID、字段 key、文件名、源码路径和 debug 标识只能作为维护追踪证据，放在 `title`、`data-*`、payload、隐藏上下文、折叠技术信息或维护者辅助列。候选卡、按钮、提示和提案弹窗不得把这些技术定位符当作主标签。
- 如果候选本身就是视觉对象，例如 token 图、骰面、图标、卡背或纯素材缩略图，主交互优先展示图像网格、悬停 / 选中反馈和必要的短动作提示；不要为了避免显示路径而改成“候选编号”“正式素材候选”等无意义文字墙。只有名称能帮助玩家区分对象时才把名称作为主标签。
- 展示、检索、结算和确认必须分流：翻牌、展示手牌、展示牌库顶、检索直到命中、预览将被埋葬 / 放回 / 弃置的对象，默认是同一次规则效果的过程可见性，不等于多个独立阻塞点。一个规则效果只有一个玩家必须等待的现实决策或最终确认时，UI 只能建立一次阻塞；过程牌可以按顺序翻看 / 下一张 / 自动排队展示，最后在可获得、可选择或可提交的对象出现后再确认。旁观或非操作者需要知道结果时，应能直接确认整件事，不得被迫逐张执行操作者的检索步骤。
- 玩家决策点不得因“只有一个候选”被系统隐式代选。只要规则语义仍要求玩家选择对象、目标、支付物、顺序、数量或模式，即使当前合法候选只有 1 个，也必须让玩家看见该候选并手动确认 / 点选；只有所有玩家决策都已完成、剩下的是固定结果收口时，才允许自动推进。
- 代理面板、问号块、摘要卡、确认按钮只在本体不可见、对象过多需要检索、无障碍入口、网络提交或规则确有二次确认时出现。
- 归档、历史、弃牌、日志默认低权重入口；若规则允许公开检视，不能画成隐藏信息。

### 3. 饱和状态设计

不要用空场证明 UI 成立。

- 建 `当前主对象 / 仍可用候选 / 可浏览非当前候选 / 归档历史` 四类守恒表。
- 建 `规则对象 -> 唯一实体锚点 -> 选中/来源/目标/详情引用` 表。
- 建空间预算：主舞台、候选区、计划/装备/持有物、资源读数、骰子/token 结算层、归档入口、临时提示、退场条件。
- 当前可支配卡牌或物件必须可读；若看不清，优先放大、分页、焦点检视或减少同页数量，不把卡面已有字段机械复写到卡外。
- 卡池 / 组牌 / 法术书等编辑器的卡外信息归属按 `references/layout-interaction-patterns.md` 执行：卡面可读时，外部 UI 只补构筑成本、数量、合法性和操作状态，不重写卡名、类型、费用、射程、目标或正文。

### 4. 布局和层级

先分层，再分区。

- 背景、地图、棋盘、桌布是底层承载，不是不可覆盖矩形；保护规则热区和可点对象，不保护低权重纹理。
- **同格阵营锚点必须稳定**：固定棋盘、格子战场、地图区域或等价空间单位中，同一格同时承载多个阵营 / 玩家对象时，必须使用稳定的席位 / 阵营 / 队伍锚点来排布对象；不得按当前观看者的 `自己 / 对手`、当前行动者、鼠标焦点或临时状态翻转左右 / 上下位置。若规则或当前 UI 约定左席位是左侧，左席位的单位、召唤物、建筑、附着战场实体在所有格子里都应稳定落在左 lane；右席位同理。其它棋盘朝向也必须先定义等价稳定轴，例如上 / 下、内 / 外、顺时针座位序。只有用户明确要求“跟随观看者翻转整张棋盘”并且整套棋盘、HUD 和坐标也一起翻转时，才允许视觉 lane 随视角改变；禁止只翻同格对象 lane。
- 本段的席位只裁定对局 / 棋盘所有权和同格 lane，不授权在卡组、法术书或 loadout 编辑器里把玩家位置作为主对象；编辑器是否应用到玩家，应在 setup 或提交摘要处理。
- 当前结算主体，如骰子、伤害、治疗、支付、揭示、命中，必须处在来源/目标附近或主舞台上层，不能降级到边栏。
- 选中态不得改变常驻布局占位；用描边、抬升、发光、短状态贴附或临时 inspect 表达。
- UI 可重叠，但必须有层级职责；遮挡关键可读/可点对象、对象归属不清或无语义垫层即失败。

### 5. UI 设计交付

从规则推界面时，默认交付**视觉 UI 设计包**，不要把长文字版 UI 设计交给用户验收。规则理解、对象职责表、空间预算和质量门禁仍必须做，但它们是内部证据、设计源文件或审计附件，不是默认用户交付物。

视觉 UI 设计包最低包含：

- 一张主视图草稿或 Open Design artifact 截图，必须表现饱和交互状态，而不是空态。
- 必须在图上直接可见或用极短标注表达：当前玩家、当前阶段、当前来源、可点目标、资源读数、结算层、候选区、计划 / 准备区、归档入口和隐藏信息边界。
- 若需要说明交互，用箭头、编号、热区、高亮、局部放大或一屏内短注释表达；不要另交一篇文字说明。
- 若图面不够直观，继续改图，不用文字解释补票。

用户批准视觉 UI 设计包前，不进入更精细的设计稿或实现；用户批准设计稿前，不进入真实实现。除非用户明确要求，不输出 standalone 文字版 UI 设计。

## 外部参考吸收口径

可参考成熟游戏 UI、桌游、卡牌游戏、平台规范和临时拉取的外部 skills，但它们只能提供不变量，不能替代本项目规则真相源。

- 吸收不变量：可读性、玩家任务、对象权重、层级、输入/焦点、归档降权、状态反馈。
- 不吸收皮肤：不要复制另一个游戏的视觉壳、牌区名、素材语义或交互职责。
- 多次被用户指出“看不懂/拥挤/像模板/对象省略”时，下一版必须引用成熟范式并转成空间裁决。
- 当参考实现承担地图、棋盘或格子定位时，必须同时检查：图片是否保持原始宽高比、网格/卡牌/特效是否挂在同一坐标父容器、交互命中是否由同一份坐标配置驱动；这些是可迁移不变量，参考游戏的具体尺寸和皮肤不是通用模板。
