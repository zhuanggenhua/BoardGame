# Layout Interaction Patterns

本文件吸收通用游戏 UI、桌游和卡牌游戏范式，转成可执行的布局裁决。

## 玩家任务优先级

顺序是：

1. 当前生存/资源/行动资格。
2. 当前目标/胜负/回合阶段。
3. 当前动作反馈：来源、目标、骰子、伤害、支付、状态变化。
4. 仍可用候选和可浏览集合。
5. 归档、历史、风味、装饰。

任何视觉元素占空间前都要回答：玩家现在是否需要它做下一步决定。

## 模式语言与可变落位

布局模式要先描述职责，再选择位置。不要把某个游戏的成功稿变成所有游戏的固定模板。

- 先写 `对象职责 -> 可选承载模式 -> 当前选择理由`。例如角色信息可以由场上模型、头像、状态板、规则卡缩略、座位牌或临时详情层承载；哪一种成立取决于当前游戏的规则、素材和玩家任务。
- 同一职责可以有多种合法落位：HUD、棋盘边缘、场地本体、牌区、弹层或抽屉都可能成立。验收看职责是否清楚、玩家是否能行动、信息是否可读，不看是否复刻某个固定坐标。
- 用户已经批准的当前稿位置，是该项目的基线裁定，不是跨项目强制规范。下个游戏要重新做对象职责表和空间预算。
- 如果用户反复强调某个设计意图，记录为“这个项目的已批准裁定 / 偏好”，同时抽象出可迁移原则。例如“别把规则提示卡当场地实体”可迁移为“提示/参考对象与实体对象先拆职责”，但不迁移成“规则卡必须放 HUD”。
- 只有对象职责错、信息丢失、隐藏边界错、关键对象不可读、交互路径不明或素材语义误用才是硬失败；具体落位不合当前稿只是设计差异，必须回到本轮任务和用户批准基线裁决。

## 本体直选

默认链路：

`选择来源对象 -> 高亮合法真实对象 -> 点击真实对象 -> 结算或进入有依据的确认`

可直选对象包括棋盘格、地图区域、场上卡、单位、token、骰子、牌堆顶牌、当前候选卡。只有本体不可见、数量过多、需要搜索过滤、无障碍入口或危险不可逆动作时，才允许代理列表或确认区。

## 卡牌和大集合

- 当前候选卡必须可读。看不清卡名/费用/关键图面时，减少每页数量、提供焦点检视或分页。
- 卡面已有字段不机械复写到外部 UI；运行态只补已选、资源不足、合法目标、等待响应、结算结果。
- 卡池、组牌、法术书、装备库等编辑器里，只要卡牌正面在同屏可见且可读，卡外可见 UI 禁止重复卡名、类型、法力费用、射程、目标、骰数、规则正文和卡面已经印刷的标签；允许补充的只有构筑成本、合法 / 非法原因、选中状态、筛选命中、操作控件和一处唯一数量 owner。若卡面看不清，先放大卡牌、减少同页数量、提供焦点预览或分页，不用外部文字把卡面重写一遍。
- 构筑合法性不能默认等于总张数。只要该游戏存在法术点 / 构筑点、训练倍数、颜色 / 学派 / 职业限制、每卡数量上限、史诗 / 稀有度 / 初级例外或其它硬约束，必须先拆清总体容量 owner 与单卡 / 单行 owner：顶部容量区只显示总体资源 `当前 / 上限` 和剩余额度；已选清单每行只显示该卡数量 `当前 / 上限`、本条占用、非法原因和调整动作；总张数 / 条目数只能作为次级读数，不得单独冒充合法性检查，也不得在右侧标题、摘要、详情层再复写同一个总体 `当前 / 上限`。
- 组牌计数必须先指定唯一 owner：若右侧清单、deck list、表格行或等价集合已经显示 `当前 / 上限`、数量、成本和可移除动作，卡池卡图、已选缩略图和问题队列不得再额外贴 `xN`、角标、底部徽章或第二套数量文案。卡池只负责展示可选卡牌和添加 / 不可用动作；已选构成由清单承担。只有没有独立清单、且卡堆本体就是唯一数量 owner 时，才允许在卡堆或缩略图上显示数量。卡池加入动作优先由卡牌本体点击、hover/focus 动作层或轻量不可用原因承接；不得给每张卡下方常驻同权重按钮，把收藏册主视觉做成按钮网格。
- 已选清单、deck list 或表格行代表具体卡牌时，行首身份优先使用真实卡图缩略、正式卡背或已批准的等价素材；不得用无来源圆球、首字母、抽象几何、普通 icon 或类型色块替代卡牌身份。类型 / 学派 chip 只能作辅助筛选信息，不能成为卡牌身份 owner。
- 卡池、组牌、法术书、装备库等编辑器中的状态标签必须给玩家可执行判断：还剩多少、具体要花多少、为什么不能加入、下一步能点什么。禁止只写规则类别名或空泛提示，例如“排斥成本”“下一张到上限”“再加一张”“上限看能力牌”“规则示例”；应改成“需 9 点；火焰相斥三倍”“5/6；再加 1 张封顶”“4/4；先移除 1 张”“限定邪术师；当前兽王不可用”。如果关键数值尚未录入，必须明确显示为数据缺口或阻塞，不得把“看某处资料”作为正常成功状态。
- 当候选卡、配置卡、角色卡、法术书或 loadout 本体已经是可点击对象时，卡外可见文字不得复述可点击性本身，例如 `点击使用`、`点击选择`、`点此加入`、`Click to use`、`Tap to select`。这类提示只允许作为无障碍标签、tooltip 或首次教学中的临时引导；默认态可见状态必须表达真实差异，例如已选归属、数量、合法性、资源不足、锁定原因或保存状态。若选中关系已经由高亮、席位 / 玩家标记、aria-pressed 或同等反馈表达，不得再用 `已使用`、`已选择` 这类同级文字重复。
- 搜索和筛选是工具，不是主对象。除非当前任务就是检索，搜索框不得占据主视觉宽度、不得用长示例词撑大界面、不得被相邻筛选行拉伸成高面板、不得压缩候选卡可读尺寸；默认用紧凑输入、筛选按钮或折叠入口服务卡池，并在截图审计里同时检查宽度和高度。
- 成熟组牌 / 构筑页的主视觉必须是卡池本体和已选清单，而不是说明文案或筛选墙。设计稿和截图审计必须检查：顶部说明已退场或降到低权重，筛选区没有把卡池推到下半屏，首屏卡池有足够密度且不是靠少数样例卡填空。若使用网格卡池，当前视口里完整可见的卡牌行必须由真实卡面连续填满；不能在第二行、第三行或其它完整可见行留下无职责空洞、少数散卡或“可滚动所以空着”的样本页感。元素存在、DOM 通过或无重叠不能替代玩家第一眼能浏览卡池。
- 吸收成熟组牌参考时，参考截图必须来自实际编辑态：玩家已经进入卡池浏览、筛选、加入 / 移除和右侧清单调整的界面。导入 deck code、选择职业 / 英雄、空白欢迎页、营销页或只露出局部标题的首屏，都只能说明入口流程，不能作为卡池密度、筛选权重或 deck list 布局证据。
- 点名成熟参考后必须做正反对照，而不是只挑相似结论：`参考有 / 目标没有` 的每一项都要写缺失理由；`目标有 / 参考没有` 的每一项都要写保留理由。只有当前游戏规则、素材比例、可访问性、保存模型或玩家任务能解释的差异才允许保留；解释不成立的目标独有 UI 必须删除、折叠或降权，解释不成立的参考缺失项必须补齐。若参考组牌页有费用 / mana 过滤，且当前游戏卡牌也有打出费用字段，应优先补同层费用过滤；不得用另一套状态 / 范围按钮组替代。
- 做卡组 / 法术书 / loadout 流程时，每一步常驻控件都要先问“为什么成熟参考没有这个，我这里必须有”。没有规则动作、玩家当下任务、可访问性、保存模型、错误恢复或明确项目裁定支撑时，不得保留为同权重主控；应删除、折叠到选中对象、降为更多菜单或交给编辑器内部状态承接。预设配置卡尤其不能默认给每张卡常驻 `编辑并另存`、`编辑保存副本`、`复制并进入` 这类次动作按钮；常规路径应是点击配置选择它，再由统一的“编辑选中配置”入口进入编辑器，保存 / 命名副本在编辑器内完成。
- 卡池里的卡牌必须保留官方素材比例；如果同一游戏存在横向墙牌、竖向法术牌、方形 token 或其它不同官方比例，不能强行塞进同一种卡框。正确做法是按规则对象比例分配网格跨度、焦点预览或独立分组；黑边、拉伸、压扁和错误纵横比都按素材语义失败处理。
- 卡池 / 组牌 / 法术书编辑器面对几十张以上候选或已选对象时，必须提供多级筛选和溢出承载。筛选至少按玩家真实决策维度分层，例如类型、派系 / 学派 / 元素、等级 / 构筑成本、打出费用、合法性 / 冲突、书内 / 未加入；不得只用一排类型按钮假装能浏览完整集合，也不得把同一维度同时做成下拉和按钮组。
- 多级筛选必须保持每一层的现实语义，不得为了“补全筛选”把所有原始标签、子类型、装备槽、种族、关键词或实现字段塞进一个“学派 / 元素”下拉。若原始数据把类型、学派、元素、子类或特性混在同一字段，UI 必须先抽取当前层真正需要的合法词；需要子类 / 特性筛选时另设独立低权重入口，不能让它污染学派筛选。
- 大集合默认是入口、抽屉、分页、分组列表、虚拟滚动、扇形或焦点预览；当前规则步骤要求从中选择时才展开。已选集合若可能达到几十张，必须显示总量、已显示范围和分组 / 滚动 / 分页入口，不能只摆少数几个样例格子冒充完整列表。
- 计划牌、装备牌、已承诺动作必须像当前来源，而不是角落装饰。
- 玩家位置 / 席位只属于对局设置、所有权归属、先后手 / 行动顺序或棋盘 lane 锚点；卡组 / 法术书 / loadout 编辑器默认只编辑“这份配置绑定哪个角色 / 法师 / 阵营”。只有保存后要把配置应用到某个玩家时，才在对局 setup 或提交摘要里出现玩家位置，不得把 P1 / P2 当成编辑器主对象。
- 卡组 / 法术书 / loadout 编辑器里的所选角色、法师、英雄或派系切换入口必须指定唯一身份 owner。选中的身份可以用一个卡图 / 肖像 / 名称控件承接并允许切换，但不得同时在主缩略图、active 选项、来源 tab、标题和摘要中重复展示同一身份。来源入口只命名真实构筑来源，例如标准起始书、导入列表或已保存配置；所选身份由身份 owner 负责。
- 被高亮、选中或正在编辑的库项已经表达“正在使用 / 正在编辑”时，界面标题、按钮和说明不得再写成 `当前 X`、`当前书`、`当前法术书`、`当前配置` 等第二套概念。可见文案应直接说对象职责，例如 `法术书库`、`法术书清单`、`编辑选中书`、`更新选中副本`、`从选中书保存命名副本`；只有计数语义需要表达数量现值时，才保留 `当前 / 上限`。
- 当可使用对象本身就是已绑定角色 / 法师 / 派系的卡组、法术书或 loadout 时，setup / 选择页的主对象必须是这些配置本身：标准预设、官方配置和玩家命名副本同屏同级，点击配置同时带出其绑定身份。除非规则真的允许“角色”和“配置”独立组合，或配置尚未绑定身份，不得做成先选角色 / 法师再从属选择配置的两段主流程。
- 卡组 / 法术书 / loadout 的“预定义配置”和“玩家命名保存副本”必须先按同一个库模型裁决：如果玩家实际是在一个角色 / 法师 / 阵营下选择要使用哪份配置，标准起始书、官方预设、命名副本、已保存配置应在同一个库 / loadout library 里同级出现。不得把预设放主流程、把命名副本管理藏成角落的 DIY 小面板、空态补丁或第二套入口。
- 新建自定义配置的默认起点必须服从游戏真实流程：若该游戏通常从官方 / 标准起始配置改起，`创建新配置` 应从标准预设或已选配置创建可命名副本；空白构筑只能作为明确标注的高级 / 次级入口，并且不得成为新手主路径、默认 E2E 路径或验收截图里的唯一自定义路径。
- 当同类成熟配置库使用 `+` 作为新建入口，且当前游戏确实允许保存玩家命名配置时，`+` 应属于同一个库模型：若新配置尚未绑定角色 / 法师 / 派系，而该身份会决定起始配置、构筑合法性或可用卡池，`+` 后必须先显式选择或确认绑定身份，再用该身份的标准 / 官方起始配置进入可命名草稿；不能隐式沿用当前身份，也不能在编辑态常驻第二套身份 owner。已绑定配置的更新或另存为新配置由编辑器保存动作承担。若存在保存数量上限，上限必须由数据层拒绝越界，并在库入口或新增入口上以可见或可测试属性表达；不得只靠按钮文案、隐藏空态或失败 toast 承担上限。
- 第二个游戏出现同类卡组 / 法术书 / loadout 构筑器时，必须先审查项目内已有成熟实现，抽出可复用不变量：库入口、身份 owner、卡池、已选清单、保存 / 载入 / 删除、合法性 owner 和端到端路径。若不抽共享组件或不复用既有结构，必须用规则差异说明为什么共享会破坏当前游戏职责；不能直接另造一套 UI 再用局部测试证明可用。
- 所选身份会影响构筑合法性、训练、派系限制、技能或起始配置时，必须有可发现的详情 / 规则回看入口。详情入口优先由身份 owner 本体承接，例如点击 / hover / focus / 长按所选英雄、法师或派系控件打开详情；除非本体不可点击、无障碍路径不足或用户明确批准，不得新增同级“详情”按钮、新行控件或第二块身份卡。打开后可展示角色牌、能力牌、规则卡或正式素材原图及必要的构筑影响；详情卡默认收起，只引用身份 owner，不常驻成第二个身份 owner。
- 检索 / 展示序列不是多次结算：当规则要求“翻到符合条件为止”“展示若干张后放回 / 埋葬 / 置底”“查看牌库顶直到命中”时，UI 应把它设计成同一个过程视图。操作者可以逐张翻看、下一张或查看完整队列；只有出现需要拿走 / 选择 / 提交 / 结束该规则效果的点时才进入一次阻塞确认。非操作者只需要确认整件事的公开结果，不需要重复执行操作者逐张检索动作。

## 信息归属与不重复

- 新增、保留或移动任何常驻 UI 元素前，设计阶段必须先完成 `元素 -> 唯一玩家任务 -> 成熟参考是否有同类元素 -> 当前游戏为什么需要 / 为什么可以缺省 -> 退场或收纳条件` 自审。不能等用户指出一个再删一个，也不能只对被怀疑重复的控件做局部解释；送验前应把当前画面所有按钮、标签、徽章、输入框、状态条、图标、提示、列表行、弹层入口和装饰性壳层逐项过一遍，说不清唯一职责的元素默认删除、折叠或降权。
- 每条玩家需要读取的信息先指定唯一视觉 owner，例如身份由座位/头像承担，数值由 token/卡牌/骰子本体承担，方向由线条/箭头/动效承担，状态由短标签或图标承担。
- 已有 owner 在同屏同状态下清楚可读时，不再用浮动标签、徽章、toast、说明句或第二个面板复写同一事实。
- 属性轨、刻度尺、血条、资源条或等价连续数值控件如果已经同时显示对象身份、当前值、目标值和变化方向，该控件本体就是默认点击目标和唯一可见 owner；相邻按钮、chip、摘要句或徽章不得再写“属性名 + 承担 / 损失 / 选择 N 点”或 `×N` 来复写同一决策。需要精确读数时只能放在同一控件内部，作为这个 owner 的辅助读数，不另建第二个同级承载物。
- 只补缺失信息：当对象离开原锚点、被遮挡、临时漂浮、多人同时操作或归属会混淆时，补最少字段；锚点恢复可读后，补充字段随临时层退场。
- 连接线、箭头、拖拽 ghost 和结算动效默认负责关系和动作，不默认复写两端对象的名字；只有其中一端不可见或同屏多条关系会混淆时才加短标签。
- 审计时必须能回答“谁负责显示这条信息”；如果两个同级可见元素都在显示同一字段，除非它们服务不同用户任务，否则判 `REVISE`。
- 对用户已经指出过的重复 UI、同页容量 / 身份 / 数量 owner、全员相同基础属性、卡面字段复写、构筑资源复写和 `当前 X` 选中态复写，送验前必须做机械检查：代码检索、DOM 文本扫描、静态断言或真实入口 E2E 至少一种。扫描要列出被禁止重复的可见文本、属性或组件锚点；重复项重新出现时必须失败，不能只靠人工自审或“规范已写”防复发。若重复来自正式牌面图像本身，扫描只禁止额外 UI 文案复写，不把牌面原文当违规。用户已经纠出的一类重复必须沉淀成可复用 owner 合同，不得只为当前截图、当前卡牌或当前按钮写死一次性断言。

## 动效与直接操控生命周期

- 拖拽、长按、滑动、投放、飞行、转移和回收这类动效必须有稳定生命周期 owner：开始、持续、命中、取消、松手、退场分别由谁接管要先设计清楚。
- 直接操控开始后，后续输入不得继续依赖会被隐藏、重渲染、移动到别处或离开命中区域的源元素；源对象可以隐藏占位，但移动与结束事件必须交给稳定控制器、全局指针生命周期或等价输入 owner。
- 源对象隐藏和拖拽 ghost 不是两个独立实体：隐藏源对象必须保留必要占位和归属，ghost 承担当前运动；禁止源对象与 ghost 双显，也禁止因为隐藏源对象而切断后续移动事件。
- 过程态验收不能只看起点和终点。直接操控至少验证：第一次启动是否及时、中途持续按住后是否仍响应、指针离开源对象后是否仍跟随、取消/松手是否清理、源与目标归属是否仍清楚。
- 多人或远端动效要验证并发实例：一个实例结束不得清掉其它仍在运动的实例，关系线和 ghost 只补缺失归属，不重复已有座位、token 或卡面信息。

## 骰子、token 和结算层

- 骰子、伤害、治疗、支付、揭示和状态 token 是当前结算层，默认高于棋盘/卡牌/HUD。
- 它们必须锚定来源、目标或动作链；不能放到无关边栏。
- 如果来源对象、事件牌、卡牌、角色板或目标本体已在同屏清楚可见，结算层不再用同级标题、浮动标签或提示句复写来源名；只有来源离屏、被遮挡或多条结算关系会混淆时，才补一处短来源标签。
- 骰种 / 阶段标签只在玩家需要区分多个可同时操作的骰池、选择可重掷对象或理解特殊骰面时可见；派生伤害骰、追加骰或独立随机结果已经由骰子本体和主合计承接时，骰种说明进入日志、无障碍摘要或详情，不占主可见层。后续分配、承伤或选择有独立面板承接时，重新投骰阶段不提前显示“待分配 / 待选择”类结果句。
- 目标选择阶段不得遮挡仍需点击的合法目标；结算结束后退场、折叠或进入日志。
- 用户点名的骰子/token 不得为了画面干净被省略。

## 背景和重叠

- 地图、棋盘、桌布默认是最下层，不是布局排斥体。
- 可覆盖低权重纹理；必须保护格子语义、实体归属、token 宿主、卡牌关键印刷信息和当前可点目标。
- 阴影、背板、遮罩、纸页、桌沿必须有职责：可读遮罩、材质承载、交互热区、状态反馈或空间分层。
- 无职责暗带、死空、硬塞牌列或为了避开底图牺牲可读性，判 `REVISE`。

### 地图素材保真与坐标父容器

- 正式地图 / 棋盘图片是视觉真相源，必须保持源图片的宽高比；禁止用 `object-fill`、独立宽高强行拉伸或非等比 `scaleX/scaleY` 让印刷分界线去追逐一个错误的 UI 矩形。
- 地图需要只显示一部分时，使用保持源比例的裁切视窗、遮罩或可平移的图片父容器；裁切改变可见范围，不改变图片几何。未使用区域是否退场由当前游戏规则与设计合同决定。
- 网格、区域热区、卡牌、棋子、轨迹和 FX 必须挂在同一个地图内容父坐标系上，并由同一份归一化区域 / 格子配置驱动；不得一边拉伸图片、一边另画一套脱离图片的 CSS 棋盘。
- 当视窗比例与素材比例不一致时，只能在 `contain`、等比裁切、改变视窗尺寸或保留安全留白之间裁决；不能牺牲地图比例换取几何断线对齐。
- 验收必须同时检查：源图关键印刷线的相对位置、运行时图片的实际宽高比、区域矩形与同一父容器的坐标关系。任何地图变形即使逻辑点击和 E2E 通过，也判 `REVISE`。

## 稳定布局

- 选中、hover、来源、目标、焦点不能改变常驻布局流。
- 用描边、发光、抬升、亮度、短状态、临时 inspect 层表达，不生成第二实体。
- 数字和读数使用稳定宽度；状态变化不能推挤其它控件。
- PC 基线未通过前，不用移动端截图证明完成。

## 输入与焦点

- 鼠标、触控、键盘/手柄都要有等价意图路径。
- 可点击对象要有足够热区；视觉面可以小，但交互面不能小到误触。
- 焦点不能只靠颜色；需要形状、描边、亮度、动效或图标冗余。
- 确认/取消控件必须有规则或真实状态授权；否则优先直接执行或本体直选。
