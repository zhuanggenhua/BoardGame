# 新游戏前置门禁与 Intake 裁定

本分卷负责新游戏 S0：在创建目录、录数据、写 Board、出设计稿或跑 E2E 前，先把来源、对象、素材、资源和进入下一阶段的条件锁住。

## 启动裁定

开始实质改动前先确认：

- `gameId`、玩家人数范围、核心机制、回合/阶段复杂度、i18n 标题与简介。
- 主真相源：官方规则书、用户图片、官方站点、用户指定网站、数据库或其它来源。
- 对照源：Wiki、官网、数据库或用户整理表是否参与比对；对照源只发现冲突和补索引，不默认覆盖主真相源。
- 当前素材形态：PDF、规则图片、图片目录、atlas、位置表、网站、TTS/Workshop/DOM/截图/桌面存档等。
- 素材处理授权：是否允许自动语义重命名、移动到正式目录、压缩和上传。
- 移动端基线：移动端适配默认纳入新游戏设计，只询问横屏 / 竖屏 / 平板优先级，不询问“要不要适配”。
- 执行现场：新游戏可以建议独立 worktree，但创建、切换或派生分支必须另获用户当轮明确授权；详见 [workflow-boundaries](workflow-boundaries.md)。

缺以上任一关键项时，继续补来源或问最小问题；不得用相似游戏、旧摘要或现有实现替代。

## 启动输入清单

最低输入：

- 游戏标识：`gameId` 与目录名一致。
- 规则来源：规则书、规则图片、帮助卡、FAQ、勘误或用户指定网页。
- 素材来源：缩略图、棋盘/地图、玩家面板、卡牌正反面、牌背、token、骰子、参考卡等按实际游戏判断。
- 空间承载：无空间、网格、区域地图、点位网络、轨道、桌面区位、玩家面板槽位或混合。
- 初始目标：先做 intake、可行性、设计稿、骨架、基础规则链路，还是完整本体。

用户只是问“怎么添加新游戏”时，不要只说“给规则和素材”。默认说明：先转规则、盘点素材、判断空间承载、建立对象素材矩阵、产出设计/架构/需求边界，再进入骨架、数据、规则、UI 和验证。

## S0 核心产物：规则对象 × 素材矩阵

新增游戏第一批实质动作必须建立这张矩阵。它是目录骨架、Board/UI、E2E 和完成判断的前置条件。

| 列 | 要求 |
| --- | --- |
| 规则对象 | 从规则真相源抽出的现实对象：卡、筹码、token、玩家板、桌面区位、帮助卡、回合标记等 |
| 基础版必要性 | `基础版必需` / `基础版可程序化` / `只作视觉参考` / `扩展后续` / `待补证据` |
| 素材来源 | 原始路径、页码、序号、裁片坐标、atlas 区域；没有则写 `missing` 或 `blocked` |
| 正式命名 | 运行时语义名或 defId；不能长期保留 URL 哈希名、随机导出名或无语义文件名 |
| 正式落点 | 资源目录、atlas config、i18n key 或“不接入运行时”的原因 |
| 使用方式 | 运行时主体、参考资料、程序化替代、扩展后续、待用户确认 |
| 证据文件 | 规则文本、审计表、裁切合同、压缩产物、manifest、代码引用或用户批准记录 |
| 合同状态 | `locked` / `blocked` / `disputed` / `unknown-slot` / `not-in-runtime`，并说明是否阻塞后续阶段 |

矩阵未闭合时：

- 可以继续从主真相源、atlas、裁图、已有合同和只读代码里补证。
- 可以分批录入已锁定对象。
- 不得进入目录骨架、Board/UI、机制实现、E2E、截图验收、设计稿实现或“基础版完成”汇报。
- 当前运行池、测试池、manifest、截图对象和现有实现只能做覆盖对照，不能冒充官方或基础版对象全集。

一票否决：

- 规则对象、规则原文、素材/atlas/槽位或对象归属未裁定，就进入后续阶段。
- 基础版必需对象在用户素材中有明显候选，却没有命名、落盘、引用或程序化替代批准。
- 运行时代码引用图片、token、棋子、敌方单位、卡面或图集路径，但源图、压缩图、manifest / 索引 key 不存在。
- 用户点名的 DOM、BGG、截图、PureRef、规则书或某个素材文件未读取、为空或不可解析，却改用相邻来源继续完成。
- 用 CSS 图形、文字壳、占位色块、临时 HTML 或程序化对象冒充真实素材闭环。

## 素材驱动 UI 与布局真相

UI 设计、设计稿、Open Design、HTML 预览和 Board 实现前必须先完成素材与布局证据：

- 识别主地图/棋盘、角色板、卡牌 atlas、牌背、token、参考卡等主视觉素材，记录路径、尺寸和疑似职责。
- 有空间载体时，先裁定坐标/槽位合同需求：区域、格子、点位、轨道、邻接、命中区、实体定位点和堆叠方式。
- 用户提供 DOM/HTML、TTS/Workshop JSON、XmlUI、对象 Transform、截图、PureRef 或桌面存档时，先抽布局合同；单一来源为空不能否定其它非空来源。
- TTS/Workshop/BGG/DOM 只能提供素材、对象位置、信息层级和交互关系；视觉风格必须另按项目 UI 标准和游戏专属风格合同裁定。
- 空间校准工具默认等真实 Board、真实资源、真实缩放/拖拽和真实坐标系跑通后，再做嵌入式编辑/校准；独立工具只能是临时低保真数据采集方案。

对象粒度、空间数据、随机池和 setup 归属的详细合同见 [mechanics-data-design](mechanics-data-design.md)，不要在本分卷重复展开。

## 正式资源准入白名单

规则书、PDF、素材包、Workshop/TTS 导出或用户素材目录中出现组件表、素材清单、起始设置表或牌表时，先整理成资源准入白名单，再移动、压缩或上传运行时图片。

准入状态只能是：

- `runtime`：规则或本轮运行态需要，允许进入正式资源目录。
- `reference`：规则、帮助、场景或人工核对资料；不得当运行时主体。
- `candidate`：可能有用但依据不足，只进临时 intake 清单或临时目录。
- `excluded`：无规则对象对应、重复、占位、编辑器贴图、装饰图或不进入本轮。

准入表最低字段：

`sourceFile | sourceSize | dimensionGroup | visualLabel | ruleRef | requiredComponent | carrierRole | intakeStatus | targetPath | canonicalName | decisionReason | reviewerNotes`

约束：

- 缺 `ruleRef` 或 `decisionReason` 的文件不得进入正式运行时目录。
- 大拼版、扫描页、整页说明卡、多对象 atlas 原图默认先是 `candidate` 或 `reference`；裁成单对象运行时资源后才可升为 `runtime`。
- 进入正式目录的文件必须在白名单中是 `runtime` 或明确 `reference`。
- 正式命名使用小写 kebab-case 语义名；下载哈希、扫描流水号、`unknown-*`、`misc-*`、`image-01` 只能停在临时层。
- 正式资源目录不得混入 `candidate/excluded`；发现已混入时，先报告对象、依据和最小补救，按删除/降级规则处理。

## PDF 与规则转档

用户提供规则 PDF 或要求先判断新游戏可行性时，先完成转档和可行性评估，不直接建游戏骨架。

默认动作：

1. 用项目脚本转 Markdown：`npm run pdf:md -- "<输入PDF>" -o "src/games/<gameId>/rule/<规则名>.md"`。
2. PDF 无原生文字时，说明限制并改走 OCR / 截图转写；中间图放临时 intake 目录。
3. Markdown 顶部写明来源、转换日期、转换方式和质量说明；转写不得改写规则语义。
4. 生成图片 inventory，至少记录原文件名、尺寸、类型和疑似用途。
5. 按白名单规则裁定资源，再执行必要压缩、manifest 重建、校验和上传闭环。
6. 在 evidence 中记录可行性：核心机制、引擎映射、状态模型难点、UI/资源难点、MVP 切分、主要风险和建议阶段。

验收：

- 规则 Markdown 可读且可追溯来源。
- 素材准入表能回溯原始文件、规则依据、状态和目标路径。
- 正式资源目录无 `candidate/excluded`。
- 正式资源有压缩产物或明确说明不能压缩。
- 资源 manifest / validate / check 按本轮资源变更范围完成。
- 可行性结论能指导是否进入骨架和 OpenSpec。

## 图片 / 位置驱动快速 intake

用户还没完整讲规则，但已给图片路径、裁片位置、行列数、顺序说明或对象定位时，可以直接开始资源 intake。

最小输入：

- `gameId`。
- 原图路径或文件列表。
- 素材类别：缩略图、卡牌 atlas、角色板、棋盘、通用插图等。
- 位置口径：行列数、row-major 顺序、裁图坐标或对象列表。
- 主真相源和对照源裁定。

默认动作：

- 建素材录入契约：真相源表、配件白名单、切图表、核对表、对照表和冲突待裁定表。
- 先读图识别对象，再判断原文件名是否随机或无语义；明显随机名可按图片语义自动重命名，有语义的用户命名默认保留。
- 移动正式资源前完成 `runtime/reference/candidate/excluded` 裁决。
- 大拼版或扫描页先裁成单对象运行时资源，再落正式目录。
- 用户给位置/顺序时，直接建立索引映射和命名合同，不等待后续手工整理。
- 如果运行态依赖远端资源，本轮新增或变更资源后继续跑资源检查和上传闭环，直到远端对象可访问或明确阻塞。

## 进入后续阶段的门槛

只有同时满足以下条件，才能进入骨架、Board/UI、机制实现、E2E 或完成汇报：

- 规则源、对照源、用户点名来源和当前范围已裁定。
- 规则对象 × 素材矩阵闭合，基础版必需项没有未解释缺口。
- 运行时资源路径能追到源图、压缩产物和 manifest / 索引 key。
- 布局真相源已读取或明确不可用，并记录影响。
- 空间载体、setup、随机池、对象粒度和权限矩阵缺口已转入 [mechanics-data-design](mechanics-data-design.md) 对应合同。
- OpenSpec 是否需要介入已裁定；进入具体方案或正式范围管理时切到 `openspec/AGENTS.md`。
- 若当前范围包含 `board-ui`、`runtime-entry` 或玩家可见交互，Open Design artifact、UI 前置包和批准状态已闭合；否则只能停在非 UI intake / 模型草稿，不能进入正式 Board、UI-facing 数据模型定稿或 UI 实施。
- 已知缺口写入任务、proposal、evidence 或矩阵，不能被截图、E2E 或代表态覆盖。
