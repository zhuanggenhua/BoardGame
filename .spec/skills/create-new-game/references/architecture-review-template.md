# 新游戏架构审查字段

本文件只定义正式实现前必须锁定的审查字段，不提供可复制样板。审查结论写入当前任务的 evidence、设计文档或 OpenSpec 产物。

## 使用时机

在正式录数据、写 `domain/types.ts`、`setup`、`game.ts`、`Board.tsx` 或主 UI 前使用。目标是确认“规则对象 -> 工程对象 -> 真相层 / 系统层 / 派生层职责”已经收清。

## 基本信息

必须写清：

- `gameId`。
- 主真相源与对照源。
- 当前用户目标和明确拒绝项。
- 当前产品规格、增量任务或“不涉及产品规格”的原因。
- 当前执行模式：默认单游戏实现，还是用户明确授权的共享能力抽取。

## 需求对齐

每个用户目标至少对应：

- 设计落点。
- 实现落点。
- 验证落点。
- 当前状态：`locked` / `blocked` / `deferred` / `out-of-scope-approved`。

任一项填不出，说明目标未冻结，不得进入正式实现。

## UI 设计门槛

若本轮会做主 UI 或设计稿，必须写清：

- Step 1：规则必要元素与布局是否通过。
- Step 2：风格方向是否在同一布局上收敛。
- Step 3：本轮需要的分界面是否在已选风格下完成。
- 通过后的下一阶段：继续出稿、实现、录入还是验收。

任一步未通过，不得把后续稿、实现截图或 E2E 写成 UI 已完成。

## 候选共享抽取

每个看起来可复用的机制或模块必须裁定：

- 留在游戏层，还是准备上升共享层。
- 候选落点。
- 本轮为什么抽 / 不抽。
- 若未来抽象，至少服务哪些已知游戏或机制家族。

默认不因“以后可能复用”就改总框架；只有明确复用对象和当前收益时才抽共享层。

## 规则对象映射

每类规则对象必须写清：

- 现实规则作用。
- 工程对象类型。
- 是单对象还是可聚合资源。
- 稳定 id 是否需要以及落点。
- 正式真相落点。
- 是否有空间、朝向、等级、拥有 / 控制 / 宿主等单体差异。

只要同类对象可能拥有不同位置、朝向、等级、耐久、控制者、宿主、附着、冷却或已行动状态，就不能用一个汇总数量替代单对象。

## 分层审查

分别列出：

- 正式真相层：规则验证、执行、结算、终局会读取或写入的状态。
- 系统层：当前交互、等待选择、自动推进、会话权限、临时结算窗口。
- 派生读模型：地图、棋盘、列表、面板、摘要等展示结构。
- 纯 UI 状态：hover、展开、tab、动画、局部视觉偏好。

禁止 Board、显示 helper、overlay 或派生结构反向承担规则真相。

## 写入路径

每类对象必须有唯一写入路径：

- 创建入口。
- 更新入口。
- 删除 / 离场入口。
- setup 初始入口。
- 显示派生入口。

同一状态若需要多处手工同步，默认说明模型未收口。

## 数据驱动边界

明确区分：

- 架构裁定：对象粒度、控制 / 拥有关系、状态分层、单对象还是资源池。
- 数据录入：卡表、setup 数值、标签、费用、图片引用、目标规则。
- 禁止交给数据顺带决定的内容：真相层职责、对象粒度、空间合法性、权限模型。

## 压力测试

至少回答这些场景是否成立：

- 单对象单独降级、受伤、移动或离场。
- 同区域只影响部分对象。
- 控制者变化但拥有者不变。
- 单对象 hover、动画和截图核对。
- 新增“只影响其中一枚 / 一格 / 一张”的效果。

## 结论

结论只能是：

- `允许进入数据录入`。
- `允许进入 Board / UI 派生`。
- `blocked:<现实缺口>`。

若 blocked，必须写清缺的是规则、素材、对象模型、空间数据、权限矩阵、共享能力还是 UI 承接，以及最小补救动作。
