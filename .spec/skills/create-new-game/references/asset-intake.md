# 新游戏图片 Intake 快速参考

## 适用场景

当用户只给了图片、图片位置、裁片顺序、行列数、网站链接或部分素材清单，但希望**先开始做新游戏接入**时，使用这条快车道。

它解决的不是完整玩法实现，而是：

- 素材落盘
- 根据图片内容自动命名
- 自动移动到正式目录
- 压缩与图集配置
- 真相源 / 对照源合同
- 静态资源索引与 i18n 录入前置

## 启动前默认询问

1. 是否授权先同步 `main`，并从最新基线申请 `feat/game-<gameId>` / 独立 worktree。
2. 是否先执行 `npm run assets:download -- --game <gameId> --dry-run` 检查并按游戏拉本地缺失运行时资源。
3. 本轮主真相源是什么，是否要把 Wiki / 官网 / 用户指定站点作为对照源一起比。
4. 是否允许 AI 根据图片内容自动重命名、自动移动、自动压缩素材。
   默认只对明显随机名/默认名自动改名；如果原名看起来就是用户有意命名，先询问，默认不改。

## 可直接开工的最小输入

1. `gameId`
2. 图片路径或链接
3. 素材类别
4. 位置口径：行列、顺序、坐标、对象列表之一
5. 主真相源 / 对照源裁定

## 默认目录与命名

| 素材类型 | 默认命名 | 默认目录 |
| --- | --- | --- |
| 缩略图 | `cover.png` | `public/assets/i18n/zh-CN/<gameId>/thumbnails/` |
| 卡牌 atlas | `<batch>.png` | `public/assets/i18n/zh-CN/<gameId>/cards/` |
| 基地 atlas | `<batch>_base.png` | `public/assets/i18n/zh-CN/<gameId>/base/` |
| 角色/英雄面板 | `<entityId>-board.png` | `public/assets/i18n/zh-CN/<gameId>/hero/` |
| 棋盘/地图/公共插图 | 按语义命名 | `public/assets/i18n/zh-CN/<gameId>/board/` 或 `common/` |
| atlas 配置 | `<name>.atlas.json` | `public/assets/atlas-configs/<gameId>/` |

## 正式命名依据

1. 正式命名默认依据图片内容语义，不依据原文件名。
2. 原文件名只作为输入线索；像 `IMG_1234.png`、`scan0007.png`、`image(1).png` 这类随机名/默认名不能直接当正式资产名。
3. 如果原文件名已经是明显语义化的用户命名，默认保留，先询问是否要统一改成项目规范名。
4. atlas 命名看整张图承载的对象集合；单张裁片命名看具体对象内容。
5. 若图面名与 canonical 名冲突，必须在合同里分开记录“显示名”和“正式命名/defId”。
6. 图片看不清时不得强行命名，必须进入待确认或对照源比对。
7. 默认自动改名只适用于随机字符串、设备默认导出名、截图默认名、扫描流水号、下载站无语义序号等情况。

## 执行顺序

1. 先写来源合同：真相源表、切图表、核对合同表、对照表、冲突待裁定表。
2. 如果是新增游戏完整接入，先从规则文本抽取基础版必需对象，再按对象查素材；不要从素材目录随手挑图反推规则需求。
3. 先读图确认对象，再判断原文件名是否明显随机：
   - 随机/默认名：按图片内容改成正式名后再移动
   - 用户语义名：先询问，默认保留原名并移动
4. 若当前文件是大拼版图、扫描页或整版说明图，先裁成代码会直接引用的单对象资源，再移动到正式目录；不得把整版图直接判成“正式素材已到位”。
5. 运行 `npm run compress:images -- public/assets/i18n/zh-CN/<gameId>` 或最小必要子目录。
6. 如果用户给的是行列/顺序，直接生成索引映射与命名合同。
7. 若涉及远端默认资源，交付前执行 `npm run assets:check`。

## 点名来源阻塞

- 用户当轮点名 DOM、BGG 电子版、截图、规则书、TTS 存档、哈希文件名或某个素材目录时，必须把该来源作为单独行写入来源合同，并记录路径、大小、读取结果、覆盖范围和结论。
- 点名来源不存在、为空、读取失败、不可解析或内容不覆盖目标时，当前任务只能保持 `blocked/in_progress`，并汇报“缺的是哪个来源、已查哪里、下一步最小解阻动作”。不得改用其它素材继续收口，也不得把 E2E 通过当作缺口已解决。
- 若后续用户补放新来源，必须回到该来源所在同族素材重新 intake；不得沿用旧的“未找到/不阻塞”结论。
- TTS/Workshop/BGG/DOM/HTML 的素材和坐标只用于语义、结构、位置或交互参考；视觉风格另走 UI skill 和游戏专属风格裁定，不能因素材来自 TTS 就做 TTS 桌面风格。

## 规则对象素材矩阵（完整接入强制）

新增游戏完整接入时，第一步必须建立矩阵；矩阵不是审计附录，而是后续 proposal、tasks、spec、实现和验收的输入。

矩阵每一行至少包含：

- 规则对象中文名与来源段落。
- 基础版状态：`基础版必需` / `基础版可程序化` / `只作视觉参考` / `扩展后续` / `无法识别待补证据`。
- 是否需要图片或音频素材，以及判断原因。
- 源文件、原始对象或裁片位置；找不到时写具体搜索位置和失败原因。
- 正式语义名、正式落点、压缩产物、manifest key 或运行时引用方式。
- 当前状态：`pass` / `approved-programmatic` / `out-of-scope` / `blocked`。
- 下一步动作；不能只写“后续优化”。

矩阵状态规则：

- `pass` 只能用于已经找到源素材、完成语义命名、正式落盘、压缩/manifest，并在运行时引用到目标位置的对象。
- `approved-programmatic` 必须有规则依据或用户明确批准；不能由实现者自行决定。
- `out-of-scope` 必须说明为什么不属于当前基础版。
- `blocked` 必须写明缺的具体源素材、已查找位置、失败动作和最小解阻动作。

如果矩阵缺失、行未覆盖基础版必需对象，或任一必需素材仍无上述状态，新增游戏整体只能保持 `in_progress`。不得用提案、E2E、截图、单测、可点击 UI 或“核心玩法可跑”替代矩阵闭合。

## 录入账本一致性门禁

素材录入必须把“候选发现 -> 分类合同 -> 裁切/抽取合同 -> 正式落盘 -> 压缩/manifest -> 运行时引用 -> 完成状态”当成同一条账本。完成判断前必须做一次交叉扫描：

- 候选表或分类合同里写 `blocked`、`base-runtime-candidate`、`基础版不接入`、`intake-closed` 的源文件，不能同时出现在裁切合同、正式资源目录、manifest 或运行时代码引用里。
- 只要源图已经被裁切成规则对象素材，原候选行必须回写为 `pass`，并写清语义命名、落盘目录、压缩产物和运行时引用；不得保留旧的“需要裁图确认”。
- 若正式资源目录或 manifest 已有素材，但候选表仍说“未接入/不接入”，状态文件不得标为 `complete/pass`，必须先修正账本或把缺口写回 `blocked`。
- 如果运行时代码引用了程序化牌面、筹码、桌面、token 或帮助入口，而素材矩阵没有 `approved-programmatic`，不得继续收口。

## 完成判据

- 图片已落正式目录
- 压缩产物已生成
- 素材命名与索引合同已写
- 真相源 / 对照源已裁定
- 后续静态数据或 i18n 录入可直接继续

## 新游戏完整接入的阻塞判据

如果当前任务不是“只整理素材”，而是“新增游戏 / 完整接入游戏”，图片 intake 不能停在候选分类。必须额外满足：

- 规则对象清单已列出基础版必需对象。
- 已基于规则对象主动查找用户素材，并为每个基础版必需对象记录源文件、裁片/区域、正式语义名、正式落点和运行时使用方式。
- 每个基础版必需对象都已映射到正式素材、程序化替代批准或明确缺口。
- 进入运行时的图片已经语义重命名、移动、压缩并写入 manifest/索引。
- 仍为 `base-runtime-candidate` 或 `blocked` 的素材，不得被口头排除后继续宣称游戏完成。
- 如果使用程序化牌面、筹码、桌面或 token，必须在合同中逐项写明对应真实素材为什么不是本轮必需，以及谁批准该降级。
- 单测、E2E 或页面截图通过不能替代素材 intake；只有矩阵闭合、资源产物存在、或替代批准明确后，才允许恢复 complete。
- 不能只生成 contact sheet、分类 CSV 或候选列表就停止；只要候选仍能继续裁切、命名、落盘或核验，就必须继续推进到正式资源或明确 blocker。
- “提案”必须建立在已录入规则数据和素材矩阵之上；没有矩阵的提案只是草案，不能作为新增游戏闭环证据。
- 禁止用 HTML/CSS 绘制的相似物、纯文字牌、程序化图形或 mock 图片替代规则中明确存在的正式素材；只有规则矩阵明确裁定“不需要图片”或用户批准程序化替代时才允许。
- 发现缺失素材后，下一步是补 proposal/tasks/spec 和素材矩阵，然后继续查找、裁切、命名、落盘；不是继续跑端到端验收。
- 若 E2E、截图或人工核图暴露素材缺失、规则对象漏录、运行时资源未接线或 UI 承载缺失，必须先退回矩阵和 OpenSpec 状态更新；禁止为了让 E2E 继续通过而临时画相似物、塞文字占位或跳过该对象。
