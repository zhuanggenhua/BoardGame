# 新游戏机制分解与数据设计

本分卷只回答一件事：新游戏在录数据、写 Board、接 UI 或跑 E2E 前，机制和数据是否已经被拆成可实现、可验证、可扩展的合同。

## 目标

- 把规则文本拆成玩家动作、权限、状态真相、结算路径和可见结果。
- 先确定对象模型、数据字段和共享引擎能力，再录入静态数据。
- 区分正式状态、系统交互状态、派生展示和纯 UI 状态，避免显示层反向承载规则。
- 标出缺口、延后项和阻塞项，不能用代表场景、自动代选或截图好看来冒充基础功能完成。

## 适用范围

- 新游戏创建、规则 intake 后准备进入实现。
- 新游戏的机制、数据结构、权限矩阵、配置包、空间规则、领域模型和阶段 2 数据录入。
- 旧游戏只在主动重构或迁移到同一合同口径时适用；不因本文档自动重写旧实现。

## 机制分解合同

每个核心机制都要映射到共享引擎能力或明确的游戏层封装：

| 机制 | 最低裁决 |
| --- | --- |
| 随机性 | 骰子、抽牌、洗牌、抽取池和当前局结果态分别建模 |
| 资源 | 消耗、上限、刷新、临时值和可见压力进入正式状态 |
| 状态效果 | 层数、持续时间、净化、层级和来源进入统一状态模型 |
| 数值修改 | 基础值、修正、优先级和最终值可追踪 |
| 能力 | 触发、限制、目标、参数和执行器有同一份定义 |
| 目标选择 | 合法目标、授权玩家、取消/跳过和非法拒绝有正式路径 |
| 条件判断 | 触发时机、触发条件和关闭条件可复查 |
| 结算 | 命令、事件、状态变更和日志/表现事件能对上 |
| 空间关系 | 坐标、邻接、朝向、开放边、连接和合法放置结构化 |
| 终局 | 胜负、平局、失败、提前结束和分支文本有状态与 UI 承接 |

输出必须包含：

- 复用清单：哪些机制直接用现有 primitives / systems。
- 扩展清单：哪些共享能力需要补强，优先级是什么。
- 游戏层封装：哪些语义只属于当前游戏，但仍消费共享能力。
- 阻塞清单：缺规则、缺素材、缺引擎能力或缺 UI 承接时，写明挡住哪条玩家合同。

## 基础规则语义覆盖矩阵

基础版不是“能走一轮”，而是基础规则的玩家合同闭合。实现前至少建立一张矩阵：

| 列 | 要求 |
| --- | --- |
| 规则语义 | 用玩家能理解的话写清现实含义，保留数量、范围和例外 |
| 基础版必要性 | `基础版必需` / `用户批准程序化` / `场景或扩展后续` / `blocked` |
| 状态真相 | 规则落在哪个正式状态字段；没有就写 `missing` |
| 输入路径 | 哪个命令、交互或自动结算接收动作 |
| 权限与拒绝 | 谁能操作；哪些动作必须不可见、不可用或被明确拒绝 |
| 可见承接 | 玩家在哪里看到选择、风险、进度、结果或失败原因 |
| 消费者一致性 | UI、命令验证、AI 合法动作和自动推进是否消费同一份授权真相 |
| 验证证据 | 单测、集成测试、窄真实入口 E2E、截图或用户批准记录 |
| 当前状态 | `done` / `in_progress` / `blocked` / `out-of-scope-approved` |

基础版一票否决：

- 玩家必须选择目标、方向、朝向、放置边、分配方式或是否触发，但实现自动代选且未获用户批准。
- 权限从焦点玩家、视角玩家或当前回合玩家推断，而不是按 [规则驱动交互设计](../../../knowledge/standards/rule-driven-interaction-design.md) 建立授权矩阵。
- 多候选 setup、模式、地图、场景或 boss 被一个代表项冒充完整系统。
- 轨道、档位、临界、非线性属性或失败标记被压成裸数值加减。
- 风险、进度、倒计时、概率压力或胜负压力只写在日志里，没有状态真相和 UI 承接。
- 空间放置、朝向、连接、邻接或合法落位缺结构化数据。
- 测试只覆盖 happy path，没有覆盖玩家决策、非法/边界规则和 UI 承接。

存在以上问题时，当前只能称为代表场景原型或低保真规则链路，不能称为基础功能完成。

## 多场景子账本

游戏存在场景、关卡、模式、boss、地图、事件包、敌方方案或胜负分支时，不能只抽一条代表链。必须建立子账本索引：

| 列 | 要求 |
| --- | --- |
| 条目识别 | 编号、标题、模式、触发条件、来源页或素材位置 |
| 来源状态 | `source-mapped` / `source-blocked` / `ocr-needs-manual-check` |
| 规则类型 | 合作、对抗、隐藏身份、自由混战、单人 boss、场景目标等 |
| 特殊机制焦点 | 倒计时、空间变化、token、敌方单位、隐藏信息、特殊行动等 |
| 子账本状态 | `contract-ready` / `source-mapped-contract-pending` / `representative-only` / `blocked` |
| 实现准入 | 是否允许进入实现；若不允许，缺的最小合同是什么 |

每个可实现条目至少闭合：公开/私密信息、setup 顺序、随机源、玩家决策点、特殊行动、持续规则、token / 敌方单位 / 空间状态 / 计数轨 / 终局文本，以及对应测试或截图证据。

## 对象模型与架构审查

正式录数据或落实现前，必须完成对象模型审查；模板见 [architecture-review-template](architecture-review-template.md)。

### 规则对象映射

对每类主要对象写清：

- 规则对象名和工程对象类型。
- 是单对象还是可聚合资源。
- 稳定 `id` 落点。
- 主状态归属：正式状态、系统交互状态、派生读模型或纯 UI。

默认把单卡、棋子、token、marker、槽位占用物等按单对象审查。只有规则上完全可替换、且不会出现单体差异状态时，才允许建成可聚合资源。

### 状态粒度

以下任一状态可能在同类对象之间不同，就不能用 `count + sharedFields` 代替单对象：

- 位置、朝向、旋转、翻面。
- 等级、士气、耐久、剩余次数。
- 控制者、拥有者、持有者、宿主。
- 附着、装备、承载关系。
- 冷却、禁用、已行动、已受击等局部状态。

### 真相层分离

- 正式状态：命令验证、执行、结算和终局判定会读取的字段。
- 系统交互状态：当前流程、待选择、自动推进、会话权限和临时结算窗口。
- 派生读模型：地图、棋盘、列表、面板等展示结构。
- 纯 UI 状态：hover、展开、tab、动画和局部视觉偏好。

禁止 Board、显示 helper、overlay 或派生结构反向承担规则真相；若同一对象需要多处手工同步，说明模型未收口。

### 生命周期与延迟交互

存在跨区移动、控制者变化、宿主变化、跨阶段结算、清场后继续选择或 UI 根据 payload 形状猜展示模式时，必须先定义：

- 决策权限来源：谁在当前窗口有权操作。
- 对象身份与归属：稳定身份、真实拥有者、当前控制/持有/宿主和默认终点。
- 延迟快照：交互创建时冻结哪些事实，解决时还能读取哪些 live state。
- 交互描述：展示模式由显式 descriptor 给出，UI 不从业务 payload 猜语义。

## 数据最低合同

每类实体先写字段合同，再录入数据。最低包括：

- 稳定 `id` 和类型区分。
- 规则数值、资源/费用、触发条件、使用限制和持续时间。
- 目标选择、合法性、取消/跳过和非法拒绝。
- 效果结构、参数、标签/状态和引用关系。
- 素材引用、图集 frame、显示名称和玩家可见说明。
- 扩展字段边界：不存在的规则不建字段；暂不实现的规则标 `deferred` 或 `blocked`。

静态事实默认进入 `GameConfigPackage`，边界以 [游戏配置包标准](../../../knowledge/standards/game-config-package.md) 为准。若暂不配置包化，必须写清临时真相源、跳过原因、影响范围和后续迁移范围，不能因 TypeScript 写起来快就把静态事实直接写死为长期结构。

## 必要数据与缺口处理

必要数据的判断原则：

- 规则判定会读取：必须录入。
- 实体行为差异依赖：必须录入。
- UI 正确展示依赖：必须录入。
- 引用关系依赖：必须录入。
- 数量、分布、随机性或资源分配依赖：必须录入。

缺口处理：

- 缺规则、缺素材或有歧义时，列缺口、来源和阻塞影响；不能猜默认值。
- 可分批录入已锁定数据，但缺口必须保留在同一对象全集或规则矩阵中。
- 基础版必需项是 `missing`、`blocked`、`disputed`、`unknown-slot` 或 `not-in-runtime` 时，依赖它的 Board/UI/机制/E2E 不得收口。
- 用户提供对照源时，必须先确认是否作为对照；对照源只发现冲突和补索引，不默认覆盖主真相源。

每批数据录入后输出核对表，列必须覆盖该实体类型的必要字段，不只列名称。待确认项写成“待确认清单”，不要把代码注释模板当规范。

## 空间规则数据

对象落在地图、棋盘、场地、区域、板块、楼层、槽位、轨道或任何空间载体上时，空间数据是规则数据，不是 UI 细节。

至少判断并录入相关字段：

- 门位、开放边、可连接边、朝向、旋转、楼层、相邻规则。
- 槽位坐标、区域锚点、图集 frame 与对象对应关系。
- 合法放置、合法移动、合法探索和阻挡条件。
- 随机布局的候选池、抽取规则和当前局结果态。

进入 Board 实现、真实页面联调或空间玩法 E2E 前，必须有：

- 空间规则合同：对象、来源、关键字段和解释口径。
- 结构化落点：字段进入 scenario / setup / catalog / atlas 等正式数据层。
- 验证证据：运行时展示或判定逻辑确实读取这些字段。

缺空间数据时，只能停在素材 intake、对象建模或数据录入；不得用 Board 临时布局、假门块、固定空槽或显示补丁顶替。

## 引擎能力缺口

对照 `src/engine/primitives/` 和 `src/engine/systems/`，把每个规则需求分为：

- 可直接复用：已有能力足够。
- 需要扩展：已有能力方向正确，但缺参数、状态或结算点。
- 需要新增：共享层没有对应能力。

每个缺口写清优先级、阻塞对象和预计阶段。能用已有共享能力表达的，不写成游戏私有字段；共享能力不足时，优先补共享 primitive / system，领域语义仍留在游戏层。

## 领域建模门槛

写 validate / execute / reduce / isGameOver 前，至少完成：

- 规则术语到事件或状态变化的映射。
- 决策点清单：强制、可选、无选择、自动推进分别列明。
- 权限矩阵：授权玩家、禁止动作、关闭条件和消费者一致性。
- 机制分解表、数据字段合同、基础规则语义覆盖矩阵和引擎缺口清单。

没有这些产物时，只能继续建模或补真相源；不能直接写实现后再补解释。

## 验收

- 机制分解表、规则语义覆盖矩阵和多场景子账本已建立，基础版必需项无未解释缺口。
- 对象模型审查已落地，单对象 / 可聚合资源、真相层、系统层、派生层和纯 UI 层边界清楚。
- 静态数据字段合同已完成，必要数据可追溯到主真相源；缺口、延后和阻塞有清单。
- 空间规则数据已结构化，运行时不是从显示补丁推断规则。
- GameConfigPackage 使用或延后边界已说明。
- 引擎能力缺口有优先级和补齐阶段。
- 至少有一个低层测试或窄真实入口证明玩家决策、非法拒绝和可见结果能闭合。
