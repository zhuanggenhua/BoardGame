# 新游戏流程边界与现场锁定

本分卷规定新游戏 workflow 的范围、执行现场、OpenSpec 关系、需求对齐、附加能力和完成判定。它不承载具体游戏方案，也不复制 UI、数据或资源门禁正文。

## 流程完整度

当任务进入 proposal、design、tasks、spec delta、approval gate 或 change 拆分阶段时，默认追求流程边界真实，不是“先挂一条最小 proposal”。

用户说“走流程 / 补 spec / 提 proposal / 按流程来”时，必须先审计：

- 当前已有哪个游戏主 spec。
- 当前已有哪些 change，各自边界是什么。
- 用户当前请求实际跨到哪些范围：foundation、catalog、gameplay、scoring、runtime-entry、board-ui、mobile、AI、tutorial 等。
- 缺哪层主文档：proposal、design、tasks、spec delta、approval gate。
- 哪些范围已经获批，哪些只是流程产物待批准。

禁止：

- 把“实现先最小”偷换成“流程交付物也最小化”。
- 明知范围已跨到玩法、计分、运行时入口或 UI 不变量，却只补一条 foundation。
- 用 evidence、截图、design-system 或探索实现替代 OpenSpec 主文档。

## 执行现场与授权

新游戏可以建议独立 worktree，但“新增游戏 / 创建 gameId / 先看素材”不等于授权创建、切换或派生分支 / worktree。

未获用户当轮明确授权时：

- 不创建、不切换、不重建分支或 worktree。
- 继续做读取、规则/素材核对、计划和证据整理。
- 若实施必须依赖隔离现场，说明现实后果、当前证据和最小授权动作。

获授权并选定 worktree 后：

- 记录 worktree 路径、分支名和 `gameId`。
- 第一次继续实施前核对当前仓库根和当前分支。
- 后续与该游戏直接相关的读写、验证、截图和 OpenSpec 更新都落在同一现场，直到用户明确切回。
- 发现命令落错现场时，立即停止编辑，审计主工作区与目标 worktree 是否已有重复产物，再重新裁定正式现场。

## 共享基线与游戏实现分线

新游戏 workflow 中必须分开两类改动：

- 共享基线：项目 skill、通用 workflow、共享规范、共享引擎或框架能力。
- 单游戏实现：`src/games/<gameId>`、该游戏资源、i18n、OpenSpec、测试、evidence、design-system 等。

处理规则：

- 共享基线先在职责正确的主线现场整理；游戏实现留在该游戏现场。
- 主工作区只保留本轮应进入共享基线的改动。
- 误落到主工作区的单游戏实现不得顺手提交进主线。
- 主工作区与 worktree 同时出现同一 `gameId` 改动时，先列交集文件，按共享基线 / 游戏实现分组，再决定保留与迁移。

## 框架抽象边界

默认模式：未被用户当轮明确要求时，不主动改总框架、共享 engine primitives / systems 或 framework 协议。先把当前游戏在既有框架能力内落到正确边界；发现复用缺口时，记录为候选抽取项。

只有用户明确要求“按跨游戏复用设计 / 上升到总框架 / 做成通用模块 / 抽共享能力”等语义时，才进入共享抽象模式。

共享抽象模式下必须先回答：

- 抽象落在游戏内可复用层、项目 framework 层，还是 engine primitives / systems 层。
- 至少服务哪两个明确游戏或哪两类机制。
- 哪些 API / 数据结构会成为共享合同。
- 哪些仍留在当前游戏层。
- 当前游戏实现与共享抽象如何拆成独立 change 和独立验证。

场景、章节、任务、campaign、encounter-script、多视角目标等是高概率共享候选，但在未开启共享抽象模式前，只做当前游戏可落地的语义壳层，不直接升级成总框架。

## OpenSpec 边界

`create-new-game` 负责 intake、来源裁定、阶段切分、现场和实施门禁；具体游戏的范围、设计、任务、proposal、spec delta 归 `openspec/`。

出现以下任一情况，必须切到 `openspec/AGENTS.md`：

- 用户要求某个新游戏的具体布局、风格、玩家关注点、UI 不变量。
- 用户要求实现阶段拆分、proposal、spec、design 或 tasks。
- 探索性 Board、design-system、evidence、manifest、game.ts、domain 等产物要纳入正式范围管理。
- 需求已从“能不能做 / 先 intake”变成“本轮到底做什么、不做什么、先后顺序是什么”。

OpenSpec 规则：

- 一个新游戏默认只有一个游戏主 spec，回答整体状态和整体边界。
- 阶段性 change 只是增量推进，不能替代游戏主 spec。
- 可以拆 foundation、card-catalog、gameplay、scoring、runtime-entry、board-ui、mobile、ai-support、tutorial 等 change，但它们必须回写或扩展同一个主 spec。
- proposal 未批准前，不得把探索实现包装成正式接入完成。

## 需求对齐表

进入正式实现前，必须有可回溯的需求对齐表，至少逐项列出：

- 用户原始目标和明确拒绝项。
- 对应 OpenSpec change。
- 对应设计产物：design、design-system、架构审查或其它正式设计。
- 对应代码、数据或资源落点。
- 对应验证方式。
- 当前状态和缺口。

任何宣称“已完成 / 已可交付 / 已进入下一步”的结论，都必须能被需求对齐表逐条证明。某一步完成不等于用户要的游戏完成；多步到位也必须保证每一步是可独立验收的完整子目标。

## Approval 与范围升级

用户说“继续 / 继续任务 / 按 OpenSpec 走流程 / 先补 spec / 先提 proposal”只代表允许继续推进流程产物，不等于批准任意 change 的实现范围。

只有用户明确点名当前 proposal / change，并表达按该范围继续，才可把对应 Approval Gate 记为已批准。批准一条 change 不外溢到后续 catalog、gameplay、scoring、runtime-entry 等 change。

若实现已经越过当前 change 边界：

- 先新建后续 change，或显式更新当前 proposal、design、tasks 和 spec delta。
- 已先行存在的实现标为探索产物或待对齐实现。
- 不得继续用“还是同一条最小 foundation”承载后续范围。

## 阶段完成后的继续规则

完成一个阶段、change、任务组或验证门禁后，立刻回到需求对齐表、游戏主 spec、现役 change 和未完成项，找下一条可执行工作。

允许停止的理由只有：

- 整体完成并有逐项证据。
- 真实阻塞，并说明阻塞后果、证据、为什么阻止目标继续、最小补救动作。
- 用户明确暂停或缩小范围。

阶段完成只能作为进度，不能作为停止理由。foundation 完成尤其不能自动宣称新游戏整体完成或关闭长期目标。

## 基础版完整闭环

用户明确把范围裁定为基础版、核心玩法、主流程或 base game 时，扩展、变体、宣传包、可选规则和替代开局不再自动阻塞本轮完成。但基础版本身必须闭合。

基础版完整闭环最低要求：

- S0 规则对象 × 素材矩阵闭合。
- OpenSpec 缺口已同步。
- 没有未批准程序化替代。
- 核心流程端到端从真实游戏入口进入，通过玩家可见 UI 控件推进。
- 允许测试读取 harness 状态做断言或截图辅助，但不能用 harness command dispatch、隐藏调试入口、状态注入或脚本直发命令替代玩家操作。

如果只能证明夹具链路或教程示范链路，只能汇报为“辅助链路通过”，不能称为基础版完整闭环。

## 附加能力矩阵

本节的“可选 / 附加能力”指游戏支撑能力，不是规则文本里的可选效果或 optional rule。

默认矩阵：

- `action-log`：操作日志 / HUD 日志。
- `undo-system`：撤回 / 撤回审批。
- `audio-feedback`：事件音效、BGM、UI 反馈音。
- `game-ai-system`：本地 AI、强单机、AI 座位。
- `tutorial-engine`：教学步骤 / 引导。
- `debug-config`：局内开发态调试配置。

状态只能是 `实施本轮` / `本轮明确跳过` / `仅保留底层接口，UI 暂不交付`。

用户说“接入可选 / 可选都接 / 把可选接上”时，默认以上全部为 `实施本轮`；除非用户或 OpenSpec 明确排除，不得只审计或只接其中一部分。不能完成的能力必须报告现实阻塞和最小补救动作。

本体优先级：

- gameplay、scoring、runtime-entry、board-ui 是本体能力。
- action-log、undo、audio、完整 AI、tutorial、debug 默认是本体后的附加能力，除非用户当轮纳入主交付。
- 为了可重复测试，本体阶段至少要保留一种人机测试路径：本地 AI 座位、在线 AI 座位或可拉起 AI 座位的 E2E/helper。这不等于完整 AI 系统已完成。

游戏本体准备交付、提 PR、请求合并或宣称可发布前，必须再次汇报附加能力矩阵：已实施、跳过、是否仍被接受。

## 正式局内完成门禁

宣称游戏完成、可交付、可归档、可发布、第一场景完成、正式玩法完成或准备关闭目标前，必须单独回答正式局内核心规则是否成立。

最低核对：

- 随机系统：牌堆、遭遇、起始物、场景分发是否是真实候选池 + 抽取规则 + 当前局结果，而不是固定序列。
- 空间系统：移动、探索、连接点、开放边、朝向、相邻判定是否由结构化数据驱动，而不是 UI 特判。
- 对象真相：卡牌、场地、token、单位、指示物是否还有占位、错素材、未建模对象混进正式入口。
- 正式入口：玩家动作是否依赖教程注入、调试按钮、隐藏入口、脚本专供入口或抽象替代按钮。
- 胜负和阶段收口：本轮目标模式的胜负、阶段推进和结算收尾是否仍是硬编码捷径或测试专供逻辑。

命中任一问题时，只能说：

- `基础对象/局部流程已验证，正式规则仍缺口`
- `教程或测试链已成立，正式局内未完成`
- `实现探索已存在，但不得归档为已完成游戏`

测试、E2E 和教程为了稳定复现可以固定随机种子、首抽或布局；但必须区分“测试固定”和“正式逻辑固定”。正式逻辑若仍是固定序列，不能说只是测试固定。

## 大任务和 UI 债务

当任务同时涉及规则、数据、运行时、主 Board、移动端、AI、截图、入口开放中的两类以上，或单个主 UI 文件开始承载多套布局分支时，必须拆成可验收 change，不直接堆实现。

最低要求：

- 每条 change 绑定一个可验收结果；涉及跨模块架构或 UI 家族切换时必须有 design。
- 主 Board 只能保留一套正式 UI 家族，旧家族只能作为明确期限的过渡或删除任务。
- 单个主 UI 文件过大或混入领域推演、布局分支、CSS、交互状态、截图状态时，在 tasks 中安排拆分。
- 桌面主 UI 默认先过桌面真实页面和截图复看，再进入移动适配；桌面未过时，手机不得作为完成证据。
- 每个新游戏必须有独立风格合同；其它游戏只能作交互模式参照，不能复制视觉壳层。
- 常驻主命令、短状态和区块标题在首屏只能有一个主承载位；debug、切座、截图夹具控件不得混入正式玩家 UI。

UI 细节门禁以 [ui-implementation-gates](ui-implementation-gates.md) 为主源，本分卷只保留流程级进入和完成口径。
