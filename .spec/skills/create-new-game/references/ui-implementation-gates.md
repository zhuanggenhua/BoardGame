# 新游戏 UI 实现与截图链门禁

本分卷规定新游戏主 UI、设计稿、Board 实现、真实页面验证和基础玩法截图链的完成口径。资源和素材准入先看 [preflight-gates](preflight-gates.md)，机制和对象模型先看 [mechanics-data-design](mechanics-data-design.md)。

## 阶段目标

Board/UI 阶段的目标是让玩家通过正式页面控件完成核心交互闭环，并能从截图中看懂当前要做什么、点哪里、点完发生什么。

“完成”必须同时满足：

- 前置规则、素材、布局和 OpenSpec 缺口已闭合或明确批准为后续范围。
- 真实页面主路径通过，不是组件存在、局部截图可看或测试夹具可跑。
- AI 已复看截图并确认没有阻塞级 UI 问题。
- 若对外声称“基础流程可理解”，已产出基础玩法截图链。

## UI 前置证据

进入设计稿、Open Design、HTML 预览、imagegen prompt、Board 实现、AI 图面核验或人工验收前，必须先落一份可复查的 UI 前置包。

前置包至少包含：

- 本轮实际读取的规则真相源、素材矩阵、布局来源或用户点名参考。
- 至少三条会影响画面的规则结论。
- `规则结论 -> 画面主体 -> 设计决策 / 禁止项` 映射。
- 规则对象素材账本：主体对象、素材状态、正式路径 / atlas frame、画面职责。
- 程序化替代裁定：`visible-subject`、`reference-only`、`approved-programmatic`、`approved-programmatic-runtime-ui` 或 `blocked`。
- 边框 / 容器职责清单。
- 当前人工验收状态。

约束：

- 旧摘要、旧截图、旧 PASS、旧合同印象不能替代本轮读取证据。
- 只在 brief、任务表或 prompt 里列路径，不等于已经读取。
- 没有前置包时，只能补证据或标 `blocked`，不得继续出图、实现或验收。
- 设计候选图生成发生在前置包之前时，该图只能算过程稿或失败候选。

## 素材使用门槛

已有正式素材且角色为 `visible-subject` 的对象，必须让正式图片、atlas crop、牌背、token、棋盘、骰子或来源锁定的程序化对象成为图面主体。文案声明、prompt 点名、CSS 形状、边框壳模拟、临时裁图或把素材缩成装饰角标，都不算使用素材。

允许不直接使用素材的情况只有：

- 规则对象素材矩阵裁定该对象不需要图片。
- 对象是 `reference-only`，只服务规则 / setup / 帮助 / 详情。
- 实时读数或交互反馈被裁定为 `approved-programmatic-runtime-ui`，例如生命、资源、冷却、进度和短状态。
- 用户明确批准程序化替代。

禁止：

- 用 HTML/CSS/程序化 UI 冒充已有牌面、牌背、token、棋子、筹码、桌面、地图格、角色板、状态标记等物理主体。
- 用临时 OCR 裁图、contact sheet、debug 截图或待命名 atlas 当正式素材。
- 在素材链路断开时进入 AI PASS 或人工验收。
- 让正式素材退成小背景、角标或被多层面板/说明壳抢走主语。

Open Design 使用素材时，正式素材必须先进入当前 OD 项目目录并作为项目相对输入；只在 prompt 写本机路径不算已用素材。

## 布局与风格来源

DOM、HTML、TTS/Workshop JSON、XmlUI、对象 Transform、截图、PureRef、桌面存档和 BGG 页面只能提供结构、对象位置、信息层级、交互顺序和素材关系。

规则：

- 用户点名的来源未找到、为空、读取失败或不覆盖目标时，必须阻塞，不得换相邻来源冒充。
- 单个来源为空不能否定其它非空来源。
- 外部桌面或网页来源不直接决定视觉风格；风格必须按 [ui-ux](../../../knowledge/standards/ui-ux.md)、项目设计系统和游戏主题裁定。
- 每个新游戏必须有独立 `design-system/games/<gameId>.md` 风格合同，写清首屏主视觉、主对象优先级、容器层数、禁止通用壳层、桌面验收截图和移动降级边界。
- 同仓游戏只能复用交互锚点、可达性原则和稳定组件职责，不能复制视觉壳层。

## 设计顺序

### Open Design 默认门与模型依赖

新游戏 proposal 获批后，UI 相关实现默认必须先使用 Open Design 产出设计稿。工具安装、启动和健康检查按 [`docs/infra/open-design.md`](../../../../docs/infra/open-design.md) 执行；正式素材必须导入当前 OD 项目并由 artifact 引用。

对包含 UI / runtime 的 change，未完成以下任一项，不得把 UI-facing 数据模型标记完成，不得写 Board、运行时 HUD、动作条、PromptOverlay，不得启动真实页面实现 E2E，也不得宣称进入 UI 实施阶段：

- Open Design artifact 已创建且可渲染；
- 导出设计图已完成 AI 图面核验；
- 当前设计稿已获用户明确批准；
- 设计稿对应的 UI 前置包、素材账本和风格合同可回查。

规则源中的纯领域事实可以先做草稿，但玩家决策、权限、状态显隐、事件反馈、空间承载和容量 / 溢出策略等 UI-facing 模型必须在已批准设计稿 / 交互合同之后定稿；不能先写一套临时模型，事后用设计稿解释。

设计稿批准后，必须继续跑真实玩家入口的基础端到端流程；只有真实控件推进、关键状态截图和结果复核都成立，才允许把该 UI 阶段标记完成。夹具、教程注入、脚本直发命令或单纯页面加载不能替代基础 E2E。

如果用户要“设计稿 / 视觉稿 / Open Design 稿 / 先看图”，当前目标停在设计稿候选；用户明确批准前，不写 Board、运行时 HUD、动作条、PromptOverlay，也不启动真实页面或跑实现 E2E。

默认设计顺序：

1. 规则提炼 UI：必要元素、禁止出现对象、隐藏信息边界、素材已有 UI、基础布局。
2. 布局收敛 UI：选定一张继续执行的布局母版，回答最大承载量、动作入口和玩家先看哪里。
3. 风格统一 UI：在已选布局上收敛唯一风格，确保与素材语法和主题一致。
4. 分界面 UI：在同一风格下补角色/场景选择、运行时、结算等本轮需要的界面。
5. `design-system/games/<gameId>.md`：记录前端可复刻约束，不替代前四步。

用户只要求文字版 UI 设计时，必须先交文字方案，包含交互元素、饱和状态、信息显隐、素材职责和程序化运行态 UI 裁定；不得直接出图或实现。

进入正式实现前必须同时满足：

- UI 设计稿或用户指定的 OD artifact 已落地，并有 AI 图面核验状态和人工验收状态。
- 架构审查已落地。
- 需求对齐表已落地。
- 当前要实现的设计稿已获用户明确批准。
- 骨架边界、运行时对象、主交互入口、状态来源和资源合同可回查。

## 饱和交互底线

新游戏运行时主界面不能只按空桌、首回合低压态或单对象理想态设计。饱和状态至少覆盖：

- 当前阶段、当前玩家、场上多个对象。
- 手牌、持有物、计划区或等价私有区。
- 可选目标、禁用对象、确认 / 取消。
- 资源、生命、状态、结果反馈。
- 溢出、折叠或展开策略。

如果玩家第一眼看不出“我现在能点什么、点了选谁、怎么确认、结果是什么”，不得进入设计稿或实现。

## Board 实现边界

Board 只负责展示、玩家输入和调用正式命令；不得直接改规则状态。

最低要求：

- 点击、拖拽、确认、取消等用户动作通过正式 command / interaction payload 进入规则层。
- Board 不持有规则真相，不把显示 helper、overlay、局部 state 反向当领域状态。
- 选择阶段、setup 阶段和正式对局阶段清楚分层；setup 未完成前，不同时渲染正式主 HUD。
- 事件消费、音频、教程、动画、日志和撤回接项目通用入口；不要在游戏 Board 里重复实现全局日志/撤回入口。
- 同类 UI 查找时只复用职责边界、输入输出和稳定 hook，不复制其它游戏视觉语法、对象名或规则分支。

当主 Board 过大或混入领域推演、布局分支、CSS、交互状态和截图专用状态时，拆到 `ui/` 子模块；不要继续把样式堆进单文件。

## 联机与前置选择

在线房间、多玩家或 spectator 相关 UI 必须先锁定 seat / viewer 语义。

- 存在场景、阵营、角色、装备、loadout 等会影响席位、私有信息或后续流程的前置选择时，默认做成进入 match 后的局内 setup 层。
- 建房页只承载房间级公共参数，例如人数、密码、是否启用 AI 或是否启用局内投票。
- 私有选择、玩家手牌、prompt、setup、waiting 态必须按 viewer 隔离；不得随 `currentPlayer` 自动切成别人的私有视图。
- 联机验收至少需要一条多浏览器上下文 E2E，证明不同 seat 页面看到不同私有内容；hotseat/local 只能作辅证。

两段式操作必须分层：先锁当前一级行动，再暴露目标、成本、确认等二级步骤。未进入一级行动前，不得让地图、手牌、主行动控件和确认按钮全部像并列主入口一样可点。

## 桌面与移动顺序

默认顺序：

`桌面真实页面 -> 桌面首轮截图 -> 桌面结算/终局截图 -> AI 复看通过 -> 手机横屏/竖屏适配 -> 手机截图 AI 复看`

规则：

- 桌面端未过时，移动端只能记录风险或做不影响桌面语义的准备；不得把手机截图当完成证据。
- 手机适配只能在已通过桌面风格合同上做响应式降级：缩放、折叠、减少非关键辅助区、触控尺寸、HUD 让位。
- 不得为了小屏新增多层框体、重复面板、说明卡、外壳嵌套或压缩核心对象，反向污染桌面。

## 少框与可读性门禁

牌桌、公共区、玩家区、手牌区和结算区只保留能对应真实桌面结构、交互边界或可读性需求的容器。每一层边框、背景或卡片壳都必须能说明现实职责。

禁止：

- 用多层面板、通用 Tailwind 壳层或其它游戏换皮冒充风格。
- 把规则解释、策略建议或截图说明作为桌面常驻正文。
- 把热座切座、测试座位切换、debug helper、截图夹具按钮暴露在正式玩家 UI。
- 同一主命令、短状态或区块标题在首屏出现多个主承载位。
- 只为 E2E、截图或排障保留无游戏意义按钮、角标、数字或状态点。

只要截图仍有主区重叠、主对象遮挡、框体过多、素材未出现、按钮/帮助区抢焦点、布局不像结构合同等问题，即使 E2E 通过，UI 状态仍是 `in_progress`。

## 真实页面完成口径

真实页面 E2E 只能证明流程可操作；视觉完成还必须证明布局、素材、状态和交互都符合合同。

不能收口为完成的情况：

- 真实页面仍有崩溃、保护页、遮挡、重叠、主结果不可读。
- 空态、等待态、终局态误导用户。
- 文案溢出、标题挤压、卡面/面板比例失真。
- 固定牌桌或棋盘类 PC live 需要页面级滚动才能看到完整主状态和主操作，且未被规则或设计批准。
- 关键操作存在但阅读顺序、可达性或可理解性失败。
- AI 或用户已指出截图问题但未重拍、复看和关闭。

最终汇报必须区分：

- `已完成`：真实页面主路径端到端通过，且无已知阻塞级 UI bug。
- `未完成`：真实页面仍有阻塞级 UI bug。
- `可选 polish`：不影响主路径验收的后续微调。

## 主流程截图定义

对外说“主流程已跑通”前，先写死开始点和结束点。若起点是首页真实入口，就从首页起跑；若只是 match 内 opening 代表态，必须明确说只证明对局内从 opening 到某节点。

截图链至少覆盖：

- 入口前 / 入口后。
- 首个核心决策前 / 后。
- 至少一个中段关键决策前 / 后。
- 终局前 / 后；若本轮范围不到终局，写清当前只证明到哪里。

每张触发前截图必须让人看出下一步主操作在哪里；每张关键图必须由 AI 实际打开并给肉眼 verdict。文件存在、断言通过或路径生成不等于截图证明成立。

资源、筹码、卡牌、棋子等发生拿走、支付、移动或消耗时，截图和 E2E 必须同时证明源区域变化和目标区域结果；不能只看内部数量、日志或目标区数量。

## 基础玩法截图链

当用户要求“最基本端到端 / 看懂怎么运作 / 每步操作截图 / 指出每步点哪里”，或本轮准备声称“基础可玩流程已具备”，必须产出基础玩法截图链。

默认落点：

- 截图：`test-results/evidence-screenshots/_shared/<gameId>-基础玩法流程/`
- 说明：`evidence/<gameId>/<gameId>-basic-flow-e2e-<date>.md`
- 现成格式见 [basic-flow-screenshot-template](basic-flow-screenshot-template.md)。

最低要求：

- 默认至少 5 步；更短时说明原因。
- 开始点和结束点先写死。
- 每步都有真实截图、玩家现在要做什么、下一步点击哪里、点击后结果、肉眼确认。
- `下一步点击哪里` 先写玩家看到的现实对象；代码 locator 只能作补充证据。
- 截图落点不明显时，可补同一真实截图的局部辅助图，但不能替代整图。
- 联机玩家视角链必须固定同一 viewer/seat；跨 seat 自动切换只能标成本地演示或多势力演示。

禁止：

- 为了截图链在正式 UI 常驻“这一步做什么 / 下一步点这里”等说明正文。
- 把右侧说明区、日志区或次级信息栏默认写成唯一主提示。
- 把中段链路冒充整局流程；未到终局必须写清只证明到哪里。

基础玩法链必须能让第一次看的人回答五件事：从哪里开始、现在轮到谁做什么、关键对象点哪里、点完发生什么、然后怎么进入下一步。

## 验收

- UI 前置包、素材账本、布局合同和风格合同可回查。
- 当前实现所需设计稿已获用户批准；没有用实现截图反推设计批准。
- 核心操作通过正式 UI 完成，阶段推进和结束界面正常。
- 主路径、空态、等待态、终局态已按真实页面复核。
- 桌面端已过真实页面和截图复看；移动端未反向污染桌面。
- 若声称基础流程可理解，基础玩法截图链已补齐。
- 没有仍阻塞完成口径的已知 UI bug；存在可本地推进的 UI 工作时继续推进，不把“下一步可以做”写成收尾。
