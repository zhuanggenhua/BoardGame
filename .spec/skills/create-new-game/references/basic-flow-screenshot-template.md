# 基础玩法截图链交付契约

本文件定义“让第一次看的人看懂游戏怎么运作”的截图链字段。它不是固定文案，也不提供可复制示例。

## 适用范围

- 用户要求最基本端到端、每步真实截图、指出每步点哪里、看懂怎么运作。
- 准备对外声称“基础可玩流程已具备”。

不适用于只验证单个 bug、单个控件、单个 prompt 或局部 UI。

## 交付物

- 截图目录：`test-results/evidence-screenshots/_shared/<gameId>-基础玩法流程/`
- 说明文档：`evidence/<gameId>/<gameId>-basic-flow-e2e-<date>.md`

如果当前只证明到中段，说明文档必须写清截止边界，不得包装成整局流程。

## 流程边界

说明文档开头必须写：

- 固定视角：同一 viewer / seat，或明确这是本地演示 / 多势力演示。
- 开始点。
- 结束点。
- 当前未覆盖的规则、分支或视口。

## 单步字段

每一步都必须包含：

| 字段 | 要求 |
| --- | --- |
| 步骤编号和标题 | 使用可读顺序号，标题写玩家看到的阶段和动作 |
| 截图 | 本轮真实截图路径；局部图只能辅助，不能替代整图 |
| 当前任务 | 玩家现在要做什么 |
| 下一步点击哪里 | 先写现实对象名，再可补 locator / test id |
| 点击后结果 | 玩家肉眼会看到的变化 |
| 肉眼确认 | 为什么第一次看的人也知道该怎么继续 |

## 最低链路

默认至少 5 步，除非规则天然更短并写明原因。链路至少覆盖：

- 进入第一次可操作状态。
- 第一个正式主行动入口。
- 第一次目标选择、资源支付或确认。
- 第一次结果反馈。
- 回到主流程、进入下一阶段或达到本轮定义的结束点。

## 写法约束

- `下一步点击哪里` 使用卡牌、按钮、地图目标、资源、骰盘、阶段入口等现实对象名；内部字段名只能作补充证据。
- `点击后结果` 写可见变化，不写“触发 command / 状态更新成功”这类内部结果。
- `肉眼确认` 必须回答“为什么第一次看的人也知道该怎么继续”。
- 截图文件名使用顺序号和现实动作 / 可见结果，不用 fixture、内部状态或 locator 命名。

## 交付前自查

- 开始点、结束点和未覆盖范围已写清。
- 步骤顺序可回放。
- 每步都有真实截图、当前任务、下一步点击哪里、点击后结果和肉眼确认。
- 至少一步展示游戏核心特色，不只是按钮可点。
- 局部辅助图已标明来源整图。
- 最终汇报至少给出说明文档路径和关键截图路径。
