# Tutorial Workflow

本 skill 处理“教程是否真的教会玩家玩”，不只看教程能不能跑通。通用层只保留跨游戏成立的教程判断方法；单个游戏的章节拆法、起手路线、案例和专有机制必须下沉到该游戏教程实现、覆盖矩阵或专项文档。

## 触发

- 用户提到教程、新手引导、onboarding。
- 用户指出教程像规则书、只教按钮、看不懂、不是真实游玩。
- 新增、重写、压缩或审查某个游戏的教程步骤、文案、测试或 E2E。
- 教程要证明“基础流程 / 首回合 / 端到端 / 这个游戏怎么运作”。

## 必读

- 当前游戏规则真相源：`src/games/<gameId>/rule/*.md`、`docs/games/<gameId>/**` 或对应来源资料。
- [`tutorial-design`](../../knowledge/standards/tutorial-design.md)。
- [`e2e-verification`](../../knowledge/standards/e2e-verification.md)。
- [`game-audit-workflow`](../game-audit-workflow/SKILL.md)。
- 当前 `tutorial.ts`、语言包、教程测试和教程 E2E。

## 通用层落点

准备修改本 skill 或 `tutorial-design` 前，先判四件事：

1. 这条规则放到第 100 个游戏里是否仍成立。
2. 它约束的是“怎么判断教程合格”，还是当前游戏这次怎么拆章。
3. 它是否偷带当前游戏的专有机制、章节名、起手路线、UI 壳层或地图结构。
4. 另一个游戏没有这套回合 / 资源 / 战斗结构时，它是否仍可执行。

任一答案是否定，就不得进入通用层；写到当前游戏教程实现、覆盖矩阵、`docs/games/<gameId>/**` 或专项 skill。

## 核心合同

### 1. 教程按玩家因果链组织

每个章节或截图链都必须让玩家回答：

- 刚才发生了什么。
- 现在为什么轮到这个动作。
- 做完会改变什么。

不得按代码模块、测试顺序、截图生成顺序或验收清单排序。注入态、预设局面或中段场景必须先解释前一步如何导致当前状态；不能让玩家从基础动作突然跳到终局、特殊结算或胜负页。

### 2. 先文案，后实现

- 文案方向未锁定前，不改 `tutorial.ts`、语言包、测试或 E2E。
- 用户正在审文案或要求“先给文案”时，先停在完整文案稿；只有用户认可后才实施。
- 文案来源和章节边界按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 执行：除必要 UI 操作句、当前局面指向和短过渡句外，玩法 / 机制 / 卡牌效果解释只能取规则书原文、卡面原文或已锁定规则真相源；没有原文就标缺口，不能自写解释补上。
- 玩家可见文案不得混入作者话术、实现关系、验收要求、测试结论或内部流程词。

### 3. 教程要教玩法，不只教按钮

基础教程至少要覆盖：

- 游戏目标、一个基础回合动作和结束 / 胜负条件。
- 首局必须会读的基础数据和常驻 UI，例如生命 / 伤害、资源、回合收入、行动可用性、准备槽、分数 / 战力或等价核心读数；教程要说明它们在哪里、怎么读、何时变化。
- 第一个正式决策入口，而不是低信息量外壳或中段题面。
- 至少一个真实选择、两个以上动作之间的可见因果，以及一个可见收益或结果。
- 当前游戏首次上手高频但不明显的读局操作，例如查看公开信息、牌堆 / 弃牌堆、状态来源、分数 / 战力 / 资源来源、只读规则入口或视角切换。
- 核心结算概念：结算前玩家知道系统会比较什么，结算后知道结果为什么成功或失败。
- 如果规则卖点是组合、连锁、派系 / 角色协同或资源转换，基础教程要出现一次玩家可感知的组合闭环。

只跑到第一个动作、第一张图、空桌或最终数字，不得称为端到端教程。

### 4. 正式 UI 缺口不能靠教程粉饰

教程文案点名某个动作、入口、状态或结果时，正式 UI 必须有清楚承接：

- “点击 / 选择 / 确认 / 结算”必须指向屏幕上真实可见的对象或按钮。
- 目标是卡牌、骰子、token、棋子、地图格、单位或区域时，主流程优先直选对象本体；代理列表或数字按钮只能作备用 / 无障碍入口。
- 状态、资源、进度、结果和风险若影响决策，必须在正式 UI 中可读；不能只靠教程说明句。
- 高亮必须命中当前真实承接物；不得高亮上一阶段对象、空容器、提示横幅、摘要条或被浮层遮住的底层。
- 教程卡片不得遮挡本步骤要点击或阅读的目标主体。

正式 UI 没有对应入口或承接物时，结论是实现缺口；不得只改教程文案。

## 覆盖矩阵

写教程正文前，先列覆盖矩阵。最低列：

- 规则条目。
- 玩家要学会的现实动作 / 判断。
- 教程章节 / 步骤 / 主教学时刻。
- 正式 UI 承接物。
- 截图或 E2E 证据。
- 当前状态：`已覆盖` / `待补证据` / `暂不处理并说明` / `正式 UI 缺口`。

若范围包含“基础回合 / 完整回合 / 首回合 / 所有交互审查”，矩阵还要列：

- 规则书同层一级行动全集。
- 每个一级入口当前是否正式局真实可用。
- 哪些只是后续目标、支付、确认或提示 UI。
- 首局所需的基础数据、常驻读数和状态标记是否已在教程或帮助入口中被真实画面承接。
- 教程是否用了注入态、低保真替代或隐藏续章。

矩阵中每个核心机制必须有唯一主教学时刻，但不要求唯一独立章节。多个机制能在同一条自然玩家流程里被顺带教清楚时，优先合并；合并时必须逐项证明每个机制都有玩家动作 / 读局判断、真实 UI 承接、结果反馈和截图或断言证据。只有合并会吞掉机制、造成玩家混淆、需要新前提或无法给出独立证据时，才拆成独立章节。章节数、机制数或截图数不得作为完成证据。

矩阵仍有 `正式 UI 缺口`、`教程注入专供`、`低保真替代` 或 `待补证据` 时，不得报教程或新游戏整体完成。

## 文案自检

教程文案至少过这些问题：

- 第一句是否说清目标、基础动作和结束 / 胜负条件。
- 是否只教常规对局；变体和扩展规则是否有用户要求。
- 是否从首次教学所需的第一个正式决策入口开始。
- 是否教会玩家读懂首局必须看的基础数据和常驻 UI，而不是只带玩家点击下一步。
- 是否重复讲前面已经教过的核心机制。
- 连续步骤是否只讲当前新增信息；如果相邻步骤删掉步骤名后仍像同一段说明，必须先改文案，不得用 E2E 通过或截图数量收口。
- 是否有空提示句、作者腔、教程目标标题或实现说明。
- 是否能为每条玩法解释指回规则书原文、卡面原文或已锁定规则真相源；不能指回时只能作为缺口，不能留在玩家可见文案。
- 是否为拆而拆，把本可在一次自然流程中讲完的基础操作、读数和机制硬拆成多个章节；是否为合并而合并，把需要独立证据的机制一句带过。
- 是否贴当前局面，点名当前对象、当前收益和当前动作。
- 是否把规则动作名、对象名和结果名写给玩家，而不是“这一步 / 这里 / 为了演示”。
- 是否覆盖随机、揭示、抽牌、投骰、摊牌、计分或等价结果的主信息承接。
- 是否有简短结语，不在结尾重讲规则。

语言包改动后要静态扫描中英文 tutorial 区块，拦住实现话术、作者话术和验收话术；E2E 通过不能替代文案扫描。

## 实现

文案和矩阵锁定后，同步更新：

- `src/games/<gameId>/tutorial.ts`
- `public/locales/**/game-<gameId>.json`
- 教程单测
- 教程 E2E

教程默认是“正常对局运行时 + 教程浮层”。不得用热座切玩家、测试专用命令、教程专用脚手架或隐藏技术入口替代正常玩家视角和正式按钮；确需脚手架时，在矩阵里标明差异和原因。

## E2E 与截图

真实教程验证至少覆盖：

- 开场目标 / 基础回合。
- 第一个主要交互入口。
- 第一条正式行动。
- 一个真实案例。
- 命中的非直觉 UI：计数确认、观察 / 聚焦 / 视角切换、只读入口、状态 / 进度读法、等待归属等。
- 计分、胜负、收益、结算或等价结果反馈。
- 结语 / 结束态。

若教程提到只读参考入口，E2E 必须真实打开、断言关键内容或素材、截图，再关闭回到牌桌。若教程提到攻击、投骰、翻牌、抽牌、改骰、重掷或特殊结算，截图链必须覆盖触发前、结果主体出现、可选择 / 可修改对象、选择后结果。

截图必须按玩家游玩顺序排序；debug、素材加载、测试辅助和审计截图不得混入教程阶段流。

## 收口分类

最终结论必须区分：

- `教程局部已通过`：某章节、某步骤或某条链路完成。
- `桌面教程端到端已通过`：教程 E2E 和关键截图覆盖完整玩家教程链。
- `新游戏整体完成`：正式进行页、素材、教程、测试、关键截图和未覆盖项都闭合。

前两者不能自动升级成第三者。若教程依赖注入态、正式 UI 缺口、低保真对象、素材未接线或覆盖矩阵未闭合，必须保留缺口。
章节数量不是收口分类。对外汇报教程完成时，必须说清玩家实际学会了哪些读局信息、哪些操作链和哪些结果反馈；不能用“已拆成 N 章 / N 条用例通过”替代覆盖结论。

## 回写

- 可复用教程问题回写 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 或本 skill。
- 单游戏章节、路线、案例、素材和截图证据写进对应游戏实现、覆盖矩阵、专项文档或 evidence。
- 用户要求“先更新 skill 再继续”时，skill 更新不是完成；更新后继续回到当前游戏的运行态审查、实现和验证。

## 最终回复门禁

- 不得只说“教程跑通了”。
- 必须说清这轮教的是哪条真实流程。
- 提到 E2E 通过时，必须说明关键截图和验证范围。
- 用户要求看图 / 打开图 / 每步截图时，先完成当前项目看图入口；不得只报路径。
- 补完教程时，必须写明属于上述哪一类收口状态，以及仍未覆盖的正式 UI 或教程缺口。
