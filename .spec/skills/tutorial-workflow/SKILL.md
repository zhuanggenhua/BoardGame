# Tutorial Workflow

本 skill 处理“教程是否真的教会玩家玩”，不只看教程能不能跑通。BoardGame 是多桌游平台，通用层只保留放到第 100 个游戏仍成立的教程判断方法；单个游戏的章节拆法、起手路线、案例、对象分类和专有机制必须下沉到该游戏教程实现、覆盖矩阵或专项文档。

## 触发

- 用户提到教程、新手引导、onboarding。
- 用户指出教程像规则书、只教按钮、看不懂、不是真实游玩。
- 新增、重写、压缩或审查某个游戏的教程步骤、文案、测试或 E2E。
- 教程要证明“基础流程 / 首回合 / 端到端 / 这个游戏怎么运作”。

## 必读

- 当前游戏规则真相源：`src/games/<gameId>/rule/*.md`、`docs/games/<gameId>/**` 或对应来源资料。
- [`tutorial-design`](../../knowledge/standards/tutorial-design.md)。
- [`e2e-verification`](../../knowledge/standards/e2e-verification.md)。
- [`game-audit-workflow`](../game-audit-workflow/SKILL.md)。
- 当前 `tutorial.ts`、语言包、教程测试和教程 E2E。

## 通用层落点

准备修改本 skill 或 `tutorial-design` 前，先判四件事：

1. 这条规则放到第 100 个游戏里是否仍成立。
2. 它约束的是“怎么判断教程合格”，还是当前游戏这次怎么拆章。
3. 它是否偷带当前游戏的专有机制、章节名、起手路线、UI 壳层或地图结构。
4. 另一个游戏没有这套回合 / 资源 / 战斗结构时，它是否仍可执行。

任一答案是否定，就不得进入通用层；写到当前游戏教程实现、覆盖矩阵、`docs/games/<gameId>/**` 或专项 skill。

## 核心合同

### 1. 教程按玩家因果链组织

执行时先按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 的“正确交付路线”走：锁定玩家要学会的流程，画出玩家因果链，把教学内容挂到第一次进入玩家视野的节点上，默认合并成一条自然主线，按交互族设计 UI 状态，文案只讲当前节点，最后用真实截图闭环。

每条教程主线按玩家自然因果链组织；只有自然链被视角、权限、规则前提、局面来源或控制者真实打断时，才拆章节或分段证据。每条自然链或必要分段都必须让玩家回答：

- 刚才发生了什么。
- 现在为什么轮到这个动作。
- 做完会改变什么。

不得按代码模块、测试顺序、截图生成顺序或验收清单排序。注入态、预设局面或中段场景必须先解释前一步如何导致当前状态；不能让玩家从基础动作突然跳到终局、特殊结算或胜负页。

教程证据交付必须先按 [`regression-closeout`](../../knowledge/standards/regression-closeout.md) 完成“证据与问题是否关联”的第一次验收，再进行“教程是否解决问题”的第二次验收；不同章节、不同入口、不同操作者或不同结算对象的截图不得互相冒充。最终汇报必须保留“问题原文 -> 我的理解 -> 关联验收 -> 当前方案 -> 解决验收”的链路。

开工时先执行 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 的正式流程同源审计：阶段顺序、自动推进条件、玩家决策、系统结算和对手行为必须与正式对局共用同一入口。只有明确标记为机制练习的步骤才能使用预设局面，不能用隐藏步骤或教程专属命令掩盖正式流程缺陷。

### 基础教程开局同源门禁

- “基础教程 / 首回合教程 / 正常游玩教程”的入口状态必须与规则真相源和正式开局一致：剧本、人数、起手资源、初始版图、当前阶段、当前玩家和第一个真实可决策入口都要能逐项对上。
- 教学顺序可以把自动检查、读局说明和紧邻的结算合并，但不得通过 `coreTransform`、测试注入或教程专属状态把本来可选、条件触发或起手不会发生的维护 / 清理 / 支付动作强行制造成首步。基础教程不能为了“展示一个机制”伪造超上限手牌、虚构待处理窗口或跳过正式开局。
- 手牌上限弃牌、维护、强制响应、额外支付等动作，只有在正式起手状态真实触发时才能进入基础教程主线；若要独立教学，必须单列为明确标注的“机制练习”章节，不能继续命名为正式开局或首回合教程。
- 基础教程的第一个交互步骤必须是正式开局自动处理结束后的第一个真实玩家决策。当前规则检查自动通过时，默认不把未触发的处理做成玩家可见教学卡；只有玩家不看这句就无法理解为什么直接进入下一真实节点时，才允许一条最短的当前局面说明，且不得把未发生的分支写成当前动作。不得让玩家点击一个因教程注入才出现的动作。
- 实施前必须写出“开局同源对照”：规则来源、正式起点、首个真实决策、教程为了教学做的最小差异及其理由。E2E 必须在进入第一个交互前断言起手状态没有被教程改造成另一条规则分支。

用户连续指出教程跳步骤、内容被移走、相邻步骤复读、确认语义反复出错或 UI 承接不一致时，先回到 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 的教程内容总账和 [`ui-change-gates`](../../knowledge/standards/ui-change-gates.md) 的玩家任务与元素职责总账，补齐覆盖和职责裁决后再继续改实现；不得继续按单个步骤、单个按钮或单张截图逐点补丁式推进。

用户指出“突然就到某状态 / 为什么要做这个 / 前后文没有关联”时，先按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 回查规则原文、流程原子账和截图过渡账。若规则原文没有支撑该交互，就标为规则缺口或删出主线；若只是前置缺失，就补自然流程前因；若必须用预设局面，就拆成独立专题起点。不得用一句过渡文案把代表态伪装成自然流程。

每个保留步骤必须能写清“上一画面状态 -> 规则原文触发/允许 -> 当前玩家输入或系统自动结算 -> 下一画面后果”。若同名对象可由不同主体或不同规则路径获得，教程标题、文案和截图名必须保真区分“谁执行了什么”和“谁只是结算后持有”；写不清时先修前置、删出主线或拆专题；不得只靠标题、桥接文案或 E2E 绿灯继续保留。

### 2. 先文案，后实现

- 文案方向未锁定前，不改 `tutorial.ts`、语言包、测试或 E2E。
- 用户正在审文案或要求“先给文案”时，先停在完整文案稿；只有用户认可后才实施。
- 文案来源和章节边界按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 执行：除必要 UI 操作句、当前局面指向和短过渡句外，玩法 / 机制 / 卡牌效果解释只能取规则书原文、卡面原文或已锁定规则真相源；仍要教学但没有原文时才标缺口，不能自写解释补上，也不能把对应教程步骤或整条教程报成完整通过。没有原文且当前教程非必要的内容，删除或不纳入，不给玩家写“暂不教”的提示。
- 玩家可见文案不得混入作者话术、实现关系、验收要求、测试结论或内部流程词。

### 2.0.1 规则解释不可被实现词替代

- 每张教程卡的正文必须按固定顺序组织：上一步发生了什么 → 规则为什么把流程带到这里 → 当前规则动作或自动结算是什么 → 局面会怎样变化 → 最后才说点击哪个真实 UI。
- 规则书已经写明的费用、顺序、目标主体、限制、数值和结果必须原样保留或忠实转述；没有规则原文支撑的解释不能靠作者推断补齐，当前局面未触发的分支不能伪装成当前动作。
- `正式效果`、`待结算`、`系统入口`、`按提示继续`、`调度`、`选择目标`、`候选 / 已选中` 等词不能单独作为教学内容。若这些词是正式 UI 的按钮或状态，必须同时写明它对应的现实规则动作和可见结果；否则从教程文案中删除。
- 文案审查与 E2E 断言必须同时覆盖规则解释和 UI 指令。只断言按钮存在、步骤推进或摘要出现，不能证明玩家已经理解规则；缺少规则前因、动作含义和结果解释时，教程只能判为未完成。

### 2.0.2 单步单焦点

- 每张可见教程卡只保留一个主教学对象、动作或结果。
- 教程正文提到什么，`highlightTarget` 就必须聚焦什么；焦点、文案、截图和正式承接物必须指向同一现实对象。
- 如果一张卡同时提到轮盘、结算摘要、地图区域、条件分支或下一入口，默认判定为内容过载，拆成相邻步骤；不要靠一段更长的过渡文案替代拆步。
- 未发生的条件分支不进入当前步骤；规则书中的完整条款只作为当前情景所需部分的依据，不作为整段照读。
- E2E 必须断言当前步骤的 `data-tutorial-highlight-target` 与文案主对象一致，并为每张可见教程卡保留对应截图。

### 2.1 选择、候选与已选状态必须同源

- 教程文案只有在当前正式局面确实存在两个或以上合法、可点击且会改变结果的玩家选项时，才能写“选择 / 可选”。教程不得用 `allowedTargets` 或其它教程白名单把正式规则本来允许的选项置灰、吞掉点击或改成不可提交；如果只想推荐一条教学路径，用高亮和短文案表达，不缩小正式合法集合。只有正式规则本身认定目标非法时，才允许由正式 UI 状态或正式命令校验阻拦。
- “可点击候选 / 预览落点 / 教程高亮”不等于“已选中 / 已确认 / 已提交”。玩家可见颜色、边框、标签和文案必须与正式状态字段同源；只有状态已经发生选择或提交时，才允许写“已选中”或使用对应选中态。
- 采用直接执行交互时，教程卡和正式提示必须明确“点击即执行”，并在点击前截图中证明目标仍未执行、点击后截图中证明正式状态已经改变。禁止只靠绿色、发光或教程外框让玩家猜状态含义。
- E2E 至少断言：当前步骤真正可点击的目标集合、正式规则对这些目标的合法性、点击前 / 点击后的状态语义，以及截图可见文案没有把候选写成已选中。若存在多个正式合法选项，必须抽查至少一个非推荐选项可以按正式路径点击并进入对应结果；教程不能用“为了保证主线”解释对合法选项的特殊锁定。

### 3. 教程要教玩法，不只教按钮

基础教程至少要覆盖：

- 游戏目标、一个基础回合动作和结束 / 胜负条件。
- 首局必须会读的基础数据和常驻 UI，例如生命 / 伤害、资源、回合收入、行动可用性、准备槽、分数 / 战力或等价核心读数；教程要说明它们在哪里、怎么读、何时变化。
- 首局必须会读的卡牌、角色卡、帮助卡、骰面、token 或图标字段；字段第一次进入玩家视野时就开始教费用、目标、类型、范围、等级、状态、攻击条、生命 / 护甲或等价读法。若当场还不使用，只教基础识别和当前状态；等第一次影响判断或即将使用时再补目标、限制、结算后果或例外。若已有规则书、官方页、帮助卡或用户确认截图能直接说明字段含义，首次教学优先用真实图例 / 截图加极短文案；若来源是一组图例 / 截图，先逐张判重，非重复且属于当前教程范围的特殊子结构或新增字段必须在对应对象出现时承接，或在作者矩阵登记暂不覆盖；并在 E2E 中断言关键图片真实渲染且绑定当前画面承接物；后续同字段不重复讲，只讲新增差异。
- 第一个正式决策入口，而不是低信息量外壳或中段题面。
- 至少一个真实选择、两个以上动作之间的可见因果，以及一个可见收益或结果。
- 当前游戏首次上手高频但不明显的读局操作，例如查看公开信息、牌堆 / 弃牌堆、状态来源、分数 / 战力 / 资源来源、只读规则入口或视角切换。
- 核心结算概念：结算前玩家知道系统会比较什么，结算后知道结果为什么成功或失败。
- 如果规则卖点是组合、连锁、派系 / 角色协同或资源转换，基础教程要出现一次玩家可感知的组合闭环。

只跑到第一个动作、第一张图、空桌或最终数字，不得称为端到端教程。

### 4. 正式 UI 缺口不能靠教程粉饰

教程文案点名某个动作、入口、状态或结果时，正式 UI 必须有清楚承接：

- “点击 / 选择 / 确认 / 结算”必须指向屏幕上真实可见的对象或按钮。
- 目标是卡牌、骰子、token、棋子、地图格、单位或区域时，主流程优先直选对象本体；代理列表或数字按钮只能作备用 / 无障碍入口。
- 状态、资源、进度、结果和风险若影响决策，必须在正式 UI 中可读；不能只靠教程说明句。
- 高亮必须命中当前真实承接物；不得高亮上一阶段对象、空容器、提示横幅、摘要条或被浮层遮住的底层。
- 教程卡片不得遮挡本步骤要点击或阅读的目标主体。
- 高亮目标短暂不可见、恢复态未重新绑定或正式承接物丢失时，不得把整张教程卡隐藏成无提示状态；运行时至少保留当前步骤说明，并把缺失目标作为实现 / E2E 失败暴露出来。
- 多人等待 / 确认步骤必须说清现实归属：玩家看到另一名玩家的待确认结果时，提示要写明谁在确认、当前玩家是否只能等待或点“下一步”触发正式自动推进；高亮落在实际等待 / 确认承接物，不能落到被遮住的旧状态。

正式 UI 没有对应入口或承接物时，结论是实现缺口；不得只改教程文案。

## 覆盖矩阵

写教程正文前，先列覆盖矩阵。最低列：

- 规则条目。
- 玩家要学会的现实动作 / 判断。
- 教程章节 / 步骤 / 主教学时刻。
- 正式 UI 承接物。
- 截图或 E2E 证据。
- 当前状态：`已覆盖` / `待补证据` / `暂不处理（作者矩阵说明）` / `正式 UI 缺口`。

若范围包含“基础回合 / 完整回合 / 首回合 / 所有交互审查”，矩阵还要列：

- 规则书同层一级行动全集。
- 每个一级入口当前是否正式局真实可用。
- 哪些只是后续目标、支付、确认或提示 UI。
- 首局所需的基础数据、常驻读数和状态标记是否已在教程或帮助入口中被真实画面承接。
- 首局所需的卡面 / 图标含义是否已在玩家可用元素矩阵中过账，并标明第一次真实进入玩家视野的画面、首次教学时刻、第一次使用 / 影响判断的画面与后续复用依据。
- 首次卡面 / 图标教学若使用图片，图片资源链、alt / 说明、截图证据是否都已闭合；成组图例是否已逐张判重，属于当前教程范围的非重复图是否在对应字段第一次出现时教学或有作者矩阵暂不覆盖落点；同一套字段是否没有被提前一股脑预讲、没有拖到使用时才第一次讲，也没有在后续步骤重复贴图或重讲。
- 教程是否用了注入态、低保真替代或隐藏续章。

矩阵中每个核心机制必须有唯一主教学时刻，但不要求唯一独立章节。多个机制能在同一条自然玩家流程里被顺带教清楚时，优先合并；合并时必须逐项证明每个机制都有玩家动作 / 读局判断、真实 UI 承接、结果反馈和截图或断言证据。只有合并会吞掉机制、造成玩家混淆、需要新前提或无法给出独立证据时，才拆成独立章节。章节数、机制数或截图数不得作为完成证据。

矩阵仍有 `正式 UI 缺口`、`教程注入专供`、`低保真替代` 或 `待补证据` 时，不得报教程或新游戏整体完成。

## 文案自检

教程文案至少过这些问题：

- 第一句是否说清目标、基础动作和结束 / 胜负条件。
- 是否只教常规对局；变体和扩展规则是否有用户要求。
- 是否从首次教学所需的第一个正式决策入口开始。
- 是否教会玩家读懂首局必须看的基础数据和常驻 UI，而不是只带玩家点击下一步。
- 是否教会玩家读懂首局必须看的卡面、角色卡、帮助卡、骰面、token 或图标字段；成组图例是否先判重并保留非重复特殊字段；同一套字段是否在第一次进入玩家视野时开始教学，使用时补完整判断，后续只讲新增差异；是否把后续才出现的字段提前一股脑塞进前置说明，或把已可见字段拖到使用时才第一次讲。
- 是否重复讲前面已经教过的核心机制。
- 连续步骤是否只讲当前新增信息；如果相邻步骤删掉步骤名后仍像同一段说明，必须先改文案，不得用 E2E 通过或截图数量收口。
- 单张教程卡是否只指向当前这一次真实输入或当前这一项结果；若一句里出现“再 / 然后 / 接着 / and then / then click”并指向不同可点击对象、不同权限或不同后续状态，必须按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 拆成独立教学时刻，除非已证明这些操作是完全等价的重复操作。
- 卡池、手牌、法术书、单位列表、弃牌堆、地图区域等动态集合步骤是否匹配当前真实页面：目标已可见时不得保留翻页 / 筛选 / 查找步骤；目标不可见时必须有点击后目标出现的断言或截图。
- 是否有空提示句、作者腔、教程目标标题、设计意图、后续复用策略、坐标判断口径或实现说明。
- 是否能为每条保留的玩法解释指回规则书原文、卡面原文或已锁定规则真相源；仍要教学却不能指回时只能作为缺口，不能留在玩家可见文案；非必要内容不提示，直接删出教程范围。
- 是否为拆而拆，把本可在一次自然流程中讲完的基础操作、读数和机制硬拆成多个章节；是否为合并而合并，把需要独立证据的机制一句带过。
- 是否贴当前局面，点名当前对象、当前收益和当前动作。
- 是否把规则动作名、对象名和结果名写给玩家，而不是“这一步 / 这里 / 为了演示”。
- 是否覆盖随机、揭示、抽牌、投骰、摊牌、计分或等价结果的主信息承接。
- 是否有简短结语，不在结尾重讲规则。

语言包改动后要静态扫描中英文 tutorial 区块，拦住实现话术、作者话术和验收话术；E2E 通过不能替代文案扫描。

## 实现

文案和矩阵锁定后，同步更新：

- `src/games/<gameId>/tutorial.ts`
- `public/locales/**/game-<gameId>.json`
- 教程单测
- 教程 E2E
- 教程权限、步骤目标、命令许可和本地草稿 / 选中态测试必须读取当前 `tutorial.ts` 里的真实清单；不得在测试里手造更宽松的步骤、目标或命令来证明教程能跑。

教程默认是“正常对局运行时 + 教程浮层”。不得用热座切玩家、测试专用命令、教程专用脚手架或隐藏技术入口替代正常玩家视角和正式按钮；确需脚手架时，在矩阵里标明差异和原因。

多人教程中由系统 / AI 代另一座位完成连续正式动作时，自动动作批次的运行时语义按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 的“自动动作批次必须完整消费”和“规则原文里的他人 / 系统动作必须教学”执行：默认同一步批次完整执行后再清理，只有步骤显式声明等待新的棋盘同步、候选、响应窗口、动画或可见结果时，才在两条动作之间等待并把超时暴露为卡死。自动批次只隐藏其它席位的代执行点击；规则原文或正式流程里的对手、队友、另一名玩家、怪物或系统动作本身仍是教程内容，必须在玩家可见卡教清主体、规则动作、公开结果、风险变化和轮序归属。不能用“等待别人结束”或“不出现队友 / 对手 / 另一名玩家”等粗暴口径代替规则源教学。

## E2E 与截图

真实教程验证至少覆盖下列职责；它们是覆盖项，不是默认章节清单：

- 起始目标 / 基础回合。
- 第一个主要交互入口。
- 第一条正式行动。
- 一个真实案例。
- 命中的非直觉 UI：计数确认、观察 / 聚焦 / 视角切换、只读入口、状态 / 进度读法、等待归属等。
- 计分、胜负、收益、结算或等价结果反馈。
- 结语 / 结束态。

若教程提到只读参考入口，E2E 必须真实打开、断言关键内容或素材、截图，再关闭回到牌桌。若教程提到攻击、投骰、翻牌、抽牌、改骰、重掷、移动、探索、交易、响应、放置、资源支付或特殊结算，截图链必须覆盖触发前、结果主体出现、可选择 / 可修改对象、选择后结果；选择态还必须按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 的“同屏非目标必须负向过账”和“教程叙述与正式流程必须同源”证明同屏非目标不会被当成当前操作目标，相邻正式意图不会互相污染。这里验收的是“当前正式意图与教程叙述一致”，不是把某个游戏的对象分组写成通用规则。

教程 E2E 涉及正式规则动作、对象本体点击、确认提交、阶段推进、草稿 / 选中态或恢复态时，按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 的“教程验收必须有正式对照”和 [`e2e-verification`](../../knowledge/standards/e2e-verification.md) 的“教程动作必须正式对照”执行；没有同视角、同阶段、同对象、同点击区域的正式入口对照证据时，只能收口为教程路径局部通过。

动态过程截图必须证明屏幕上真的在动：重掷、移动、转移、翻页、投射等步骤的 E2E 断言要读取玩家可见投影或连续关键帧变化，不能只读内部 motion、状态字段或最终结果。用户指出过程帧看不出动画时，先修动画幅度、采样点和断言，再重建截图证据。

截图必须按玩家游玩顺序排序；debug、素材加载、测试辅助和审计截图不得混入教程阶段流。用户要求逐步截图、逐句确认或教程截图收口时，按 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 的“玩家可见文案逐卡截图”执行：每张玩家可见教程卡都要有当前步骤截图。纯自动桥接步骤本身必须证明运行时不渲染“当前玩家代操作别人”的提示卡；但这些动作来自规则原文或正式流程时，玩家可见截图必须覆盖它们造成的公开结果、等待归属、风险或轮序变化，不能用后一张结果图倒算覆盖上一句操作文案。

单条可见基础教程必须在 E2E 中断言 `/tutorial` 直接进入牌桌且目录页不存在；多条真实可选教程才允许显示目录。对手、队友、另一名玩家、怪物或系统的自动动作不得截图成当前玩家代操作步骤；但规则源或正式流程写到的他人 / 系统动作不能从教程证据里消失，必须作为玩家可见教程内容和截图证据承接。测试可以禁止“当前玩家代替别人操作”的话术，不能禁止“队友 / 对手 / 另一名玩家 / 怪物做了什么”的规则原文内容。

## 收口分类

最终结论必须区分：

- `教程局部已通过`：某章节、某步骤或某条链路完成。
- `桌面教程端到端已通过`：教程 E2E 和关键截图覆盖完整玩家教程链。
- `新游戏整体完成`：正式进行页、素材、教程、测试、关键截图和未覆盖项都闭合。

前两者不能自动升级成第三者。若教程依赖注入态、正式 UI 缺口、低保真对象、素材未接线或覆盖矩阵未闭合，必须保留缺口。
章节数量不是收口分类。对外汇报教程完成时，必须说清玩家实际学会了哪些读局信息、哪些操作链和哪些结果反馈；不能用“已拆成 N 章 / N 条用例通过”替代覆盖结论。

## 回写

- 可复用教程问题回写 [`tutorial-design`](../../knowledge/standards/tutorial-design.md) 或本 skill。
- 单游戏章节、路线、案例、素材和截图证据写进对应游戏实现、覆盖矩阵、专项文档或 evidence。
- 用户要求“先更新 skill 再继续”时，skill 更新不是完成；更新后继续回到当前游戏的运行态审查、实现和验证。

## 最终回复门禁

- 不得只说“教程跑通了”。
- 必须说清这轮教的是哪条真实流程。
- 提到 E2E 通过时，必须说明关键截图和验证范围。
- 用户要求看图 / 打开图 / 每步截图时，必须先按 [`show-image-to-user`](../show-image-to-user/SKILL.md) 完成当前项目媒体交付入口；默认用 `--no-open` 注册目录，最终回复必须带该入口返回的 `VIEWER_URL`，不自动打开查看器。本 skill 只负责教程流程与证据范围，不在这里复制查看器网址、目录注册或 PASS 清单规则。
- 补完教程时，必须写明属于上述哪一类收口状态，以及仍未覆盖的正式 UI 或教程缺口。
