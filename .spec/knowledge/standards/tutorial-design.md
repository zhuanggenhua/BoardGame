# 教程与新手引导设计规范

> 适用于 `tutorial / onboarding / 新手引导 / 教学步骤`。本文件约束“教什么”，不是只约束“怎么点”。

## 适用边界

- 当本轮在做教程、重做教程、审核教程质量、补教程 E2E、或用户明确指出“教程看不懂/只是在教按钮”时，必须阅读本文。
- 动手改教程前，默认还必须先读该游戏自己的规则真相源，例如 `src/games/<gameId>/rule/*.md`、当前规则整理文档或用户当轮给出的规则原文；不得只看现有教程文案就顺着旧口径修。
- 教程正文不是规则提炼入口的替代品。动手写教程前，必须先把本教程要覆盖的基础规则拆成规则合同：对象、触发条件、玩家选择、状态变化、结果反馈、图标 / 标记 / 牌型映射。若规则合同缺字段，先补合同或标缺口，不得用“对应的牌 / 发现牌 / 这里会结算”这类泛化文案绕过基础规则。
- 若本轮准备新增或修改“通用教程规则”，默认先判断这条内容放到未来第 100 个游戏里是否仍成立；只有成立时才允许留在本文，离开当前游戏就不成立的内容必须下沉到单游戏专项文档或实现。
- “考虑未来 100 个游戏”在教程设计里是默认持续动作，不是只在准备写规范时才临时做一次检查；只要本轮已经开始讨论章节边界、案例编排、起手路线、教学顺序或教程命名，就必须先判断这些结论到底属于通用判断方法，还是当前游戏的专项答案。
- 只要准备输出教程章节方案、覆盖矩阵、专项大纲或通用层条款，默认必须先写一版最小判层结果：`跨游戏判断方法`、`当前单游戏答案`、`单游戏答案下沉位置`。这三项没先锁定，就不得开始写教程正文或通用规则正文。
- 用户明确要求“先更新 skill / 先更新规范，不要只考虑一个游戏”时，默认第一响应不是补当前游戏章节答案，而是先补三件事：`怎么判通用与专项`、`什么时候必须下沉`、`没做判层前不得开始写正文或实施`。
- 本文和 `.spec/knowledge/standards/e2e-verification.md`、`.spec/skills/game-audit-workflow/SKILL.md` 配合使用：
  - `tutorial-design.md` 约束教学目标与内容结构
  - `e2e-verification.md` 约束截图与真实流程证据
  - `game-audit-workflow` 约束教程交互必须和真实游玩一致

## 通用层前置自检

准备把某条教程经验写进通用规范前，先依次判断：

1. 这条内容在未来第 100 个游戏里是否仍成立。
2. 这条内容是在约束“怎么判断教程质量”，还是只是在复述“当前某个游戏最好的章节拆法”。
3. 这条内容是否夹带了当前游戏的专属机制名、专属地图区、专属起手路线、专属 UI 承载方式或专属章节标题。
4. 如果另一个游戏没有这套回合结构、资源结构或战斗结构，这条内容是否仍然可执行。

只要有一项不成立，就不得写进通用层，必须下沉到对应游戏的专项文档、覆盖矩阵或教程实现。

通用层默认只负责三件事：

1. 判断教程有没有真的教会玩家这款游戏。
2. 判断章节边界是不是重复、割裂或命名失真。
3. 判断哪些内容必须下沉到单游戏文档或教程实现。

通用层默认不负责替任何一个游戏预写“应该拆成哪几章、哪章先于哪章、哪条固定起手路线最适合教学”。

如果本轮争议已经落到了“当前这款游戏哪章该并到哪章”“先演示哪条路线更顺”“这一题示范局从哪步开始更合适”这种粒度，默认先判为单游戏答案；除非你能把它翻译成离开当前游戏仍成立的判断方法，否则不得写进通用规范。

如果连“当前哪些内容是通用判断方法、哪些已经是单游戏答案、单游戏答案要落去哪里”都还说不清，默认说明前提未锁定；此时只能继续判层，不得直接写章节设计、固定顺序或规范正文。

如果用户当前要求的是“先更通用层，再回头做单游戏实现”，那通用层这一步的合格交付应当是：

1. 新增或补强一个能拦很多游戏共性错误的判断门禁；
2. 明确写出这条门禁不会替单游戏预写哪些章节、顺序、案例或起手路线；
3. 明确当前单游戏答案会留在什么专项文档、覆盖矩阵或实现里。

如果交付物做不到这三点，而只是把当前游戏的教程结构换个地方重写一遍，就说明这次“更新规范”仍然写跑偏了。

## 核心不变量

1. **教程先教“为什么赢”，再教“怎么按”**
   - 玩家必须先知道这局游戏的目标是什么，例如比总分、抢基地、击倒对手、占区得分。
   - 如果教程结束后，玩家仍说不出“我到底在追求什么结果”，该教程直接判不合格。

2. **教程必须解释“为什么做这个动作有好处”**
   - 不允许把教程退化成“点这里 -> 再点那里 -> 下一步”。
   - 每个正式行动至少要说明它解决什么现实问题，例如补组合、抢公开资源、压缩损失、推进结算。

3. **教程必须用真实局面教一个最小得分/收益案例**
   - 至少有一个真实案例能让玩家看到：做出正确选择后，分数、战力、控制权、伤害或其它核心收益发生了清晰提升。
   - 这个案例必须来自真实牌桌/真实棋盘状态，不能只靠口头描述“理论上会更强”。

4. **教程必须覆盖“结果反馈”**
   - 玩家不只要知道动作执行了，还要知道动作带来了什么结果。
   - 至少要覆盖以下其一：
     - 分数提升
     - 伤害/控制权变化
     - 资源曲线改善
     - 组合成立后的明显收益

5. **基础教程必须先形成“最小乐趣闭环”**
   - 基础教程不能只是规则覆盖表或操作清单；它必须让玩家在第一段教学里看到“这样玩为什么有意思”。
   - 合格闭环至少包含：一个真实选择、两个或以上有因果关系的动作、一个可见收益。
   - 可见收益可以是分数、战力、控制权、资源、伤害、行动次数、位置优势或其它游戏自己的核心优势。
   - 如果当前案例只能证明“流程能走通”，但没有可见收益或爽点，优先判定为案例设计不合格，而不是继续补文案解释。

5.1 **教程必须按玩家因果链排序，而不是按实现或截图产物排序**
   - 玩家看到任意一张阶段图时，都应能说出：刚才发生了什么、为什么现在要做这个动作、做完会改变什么。
   - 如果阶段图单独看会出现“为什么突然到这里”，默认说明教程链断了；必须重构章节、文案、截图顺序和取图点，不得只给图片补标签。
   - 注入态、预设中局、章节直达和 E2E 分文件取图只能服务验证，不能决定用户看到的教学顺序。
   - 技术门禁、素材加载、失败截图、debug 图和 review 拼图必须从玩家教程链里分离；它们可以作为工程证据，但不能混成“全链路教程截图”。
   - 只要一个阶段暴露出玩家因果链不通，就按全链路重审处理，不得把它当作单张图问题。
   - 教程文案只要点名一个规则入口、参考入口或正式动作，就必须在覆盖矩阵里标清它是 `只读参考` 还是 `正式动作`。只读参考必须有真实打开/切页/关闭截图；正式动作必须有真实点击和结果截图。禁止用“介绍了这个规则”替代端到端证据。
   - 如果某个分支规则会改变玩家对当前目标的理解，例如英雄攻击、敌方攻击、怪物攻击、打开剧本看胜利条件、投骰判定或使用道具改结果，即使它不是当前主线的下一步，也不能默认省略；要么补独立分支截图链，要么在矩阵中写成未覆盖缺口。
   - 只读参考入口必须命中玩家文案的真实对象。文案写“剧本目标页 / 胜利条件 / 任务目标”时，证据必须打开对应目标内容；不能用玩家参考卡、规则摘要、帮助页或默认素材卡替代。
   - 同类战斗、检定、投骰和改骰流程必须复用同一类主流程 UI。若一个游戏已经有批准过的物理骰盘或主结算面板，后续同类教程不能临时换成角落小面板、纯文字结果或另一套壳层；除非覆盖矩阵写明设计裁决和差异原因。
   - 首场景 / 首剧本只要出现怪物、召唤物、敌方单位或等价非玩家敌人，覆盖矩阵必须逐项标清：已做端到端截图、明确不属于当前必要范围并说明原因、或待补。不能因为英雄主胜利链暂时不经过它，就省略会影响目标理解的怪物行动或攻击。

6. **组合型游戏必须出现一次“首个可感知组合”**
   - 如果游戏核心卖点是牌组混搭、派系组合、角色能力协同、连锁效果或构筑套路，基础教程必须让玩家实际看到一次组合成立。
   - 这个组合必须让至少两个系统、牌组、派系、角色能力或资源来源对同一个结果产生不同贡献。
   - 不合格示例：先打一张 A，再打一张 B，但 A 和 B 只是并排发生，没有互相提高价值。
   - 合格示例：A 先制造资源、目标、窗口或弱点，B 利用它造成分数、战力、控制权或节奏优势。
   - 通用规范只要求“必须有首个可感知组合”；具体选哪张牌、哪条路线、哪次计分，必须留在对应游戏的覆盖矩阵、专项文档或教程实现里。

7. **计分制游戏默认必须看到计分因果**
   - 如果游戏胜负核心是分数，教程默认至少要让玩家看到一次真实计分、准计分，或清晰的分数差案例。
   - 禁止只讲“终局会计分”，却不让玩家看到“哪张牌为什么加分/减分”。

8. **教程交互必须与正式游玩一致**
   - 正式游玩点按钮，教程就点按钮。
   - 正式游玩点卡牌，教程就点卡牌。
   - 正式游玩靠区域/棋盘/地图高亮指认可选对象，教程就修正式高亮的目标、边界、视角和样式；不得另造标牌、圆点、编号或按钮列表来替代。
   - 不得为了教学顺手改成交互壳层、说明壳、替代入口。
   - 如果正式操作允许从默认来源之外选择对象，例如除中央池、手牌或公共区外，还能选择别人面前、弃牌堆、地图边缘、临时区或上一轮遗留区里的对象，教程必须先解释这些额外来源也是合法对象，再要求玩家点击。
   - 非默认来源教学至少要说清：默认来源是什么、额外来源是什么、拿/选额外来源后原对象或原持有人会发生什么变化；E2E 必须实际点击该额外来源对象并验证状态变化。

9. **教程不能用长段台词替玩家做判断**
   - 教程文案可以点出“当前该看什么”，但不应把整套推理替玩家说完，更不能形成“老师命令你现在该丢哪张、该拿哪张”的口吻。
   - 更好的做法是：先把真实局面布到足够清楚，再用 1 到 2 句短提示提醒玩家去看“哪张在补线、哪张只是在占位、哪张会拖后腿”。
   - 如果离开长段解释后，玩家就看不出为什么这张更好，优先判定为案例设计不合格，而不是继续往文案里加说明。

10. **判断提示和操作提示必须拆开**
   - `infoStep` 的职责是提醒玩家“这一步该看哪里、为什么值得看”，不应顺手把按钮操作和标准答案一起说完。
   - `requireAction` 的职责是教真实点击对象和最小动作，例如“点击摸牌按钮”“点击中央这张牌”“点击手牌弃掉”，而不是在动作步里再次长篇解释整套推理。
   - 如果一个步骤同时承担“替玩家做判断”和“告诉玩家怎么点”，默认先拆成前一说明步 + 后一操作步，再决定文案是否还需要保留。

11. **教程开场第一句默认只讲“目标 + 一个最基本操作”**
   - 开场第一句默认只负责让玩家立刻知道：这游戏要赢什么、自己每回合最基本在做什么。
   - 不要一上来把全部规则、例外、术语、细节一起塞进第一句。
   - 更好的开场是：`目标 + 轮到你时最基本的回合动作 + 结束条件/胜负条件`，而且必须短。

12. **脚本化教程可以直接点名当前对象与动作**
   - 当教程已经把牌桌固定到真实预设局面时，文案可以直接说出当前牌名、组合对象和该执行的动作，例如“中央有钟塔，和你手里的蜡烛可以加分，现在选中钟塔来获取”。
   - 这种直接点名只在“当前真实局面就是这一手示范题”时成立，禁止脱离当前牌面空讲策略。
   - 优先使用“这张能加分 / 这张现在没用 / 选中这张牌”这类短句，不要再绕成抽象术语或长段分析。

11. **示范题教学也必须从首次教学所需的第一个正式决策入口进入**
   - 即使教程采用“摆好的示范题局面”，也必须先从该游戏里玩家第一次需要理解规则、做出真实判断的正式入口开始，例如首个正式卡牌选择、首个正式棋盘目标、首个正式行动选择或资源决定。
   - 不得把教程直接切到中段预设题面，再让玩家在没有经历这个正式决策入口的情况下突然执行支付、结算、计分或战斗收口。
   - 如果教程为了讲一个中段案例而必须预设局面，也要先让玩家经过一次与正式开局同源的正式决策入口，再进入这道示范题。
   - 如果角色选择、剧本选择、确认开始这类开局壳层在当前游戏里只承担低信息量前置，规则书也没有要求玩家在这里理解关键规则，那么它们可以保留为真实进入链路的一部分，但不应自动单独占一章。
   - 如果某个目标、地区、支付对象、弃牌对象只是“进入一级行动之后才需要选的二级对象”，教程不得把它提前教成首个正式决策入口。
   - 动手前必须先区分：`一级行动入口`、`后续目标选择`、`提示 UI`、`真实交互载体`；没分清前，不得写正文。
   - 如果规则顺序是“先支付费用/弃牌/消耗资源，再触发效果，再由效果要求选择目标或地区”，教程与正式 UI 必须按这个顺序实现和验收：费用支付完成前不得提前出现效果目标选择，也不得把支付后的目标写成“已经锁定”。
   - 这条是跨游戏通用的时机门禁，不替任何单游戏预写具体路线；单游戏只需要把自己的费用对象、效果目标和结果反馈落到对应教程实现、覆盖矩阵或审计文档。

12. **默认只教常规对局，不教变体或扩展**
   - 如果用户没有明确要求教程覆盖双人变体、扩展规则、额外模式或特殊结算，基础教程默认只讲常规对局。
   - 禁止一边用常规口吻讲目标，一边在动作步骤里偷偷塞变体规则，例如“双人局会多摸 1 张”“这个模式结束条件不同”。

13. **已经讲过的规则不得在后续步骤复读**
   - 开场已经交代过的基本回合结构、胜负条件、结束条件，后续步骤默认不再重复。
   - 后续文案只负责当前这一步的判断、动作或结果，不再回头重讲规则书。

14. **禁止空提示句和无信息量过渡句**
   - 像“先看当前手牌”“下面看另一种情况”“现在总分更高了”这类没有新增信息、没有局面判断、没有交互价值的句子，默认不合格。
   - 每一步文案必须至少承担一项职责：讲当前目标、指出当前收益、点名当前对象、或说明当前结果。

15. **能合并的判断和动作就直接合并**
   - 如果同一句话已经足够自然地同时说明“为什么这么做”与“现在点哪里”，就不要机械拆成一个说明步加一个重复动作步。
   - 只有当拆开后能明显降低理解负担，才允许分成 `infoStep` 和 `requireAction` 两步。

16. **教程必须覆盖真实隐性交互**
   - 除了显式规则，教程还应覆盖玩家第一次上手时不一定会自己发现、但真实游玩中会频繁用到的关键交互。
   - 例如：点击或悬浮查看单张牌得分、查看战力来源、查看奖励说明、确认当前控制权、读懂等待归属。
   - 还必须覆盖本游戏高频但不明显的“桌面读局操作”，例如切换或查看对手公开视角、打开自己的牌库/弃牌堆、查看牌堆数量、放大看单张牌、查看当前力量或分数来源。
   - 这些操作不能做成孤立界面导览，必须贴在真实局面里教：对手刚行动后教看对手公开区，抽牌/弃牌/回收后教打开牌库或弃牌堆，计分前教查看力量来源。
   - 如果某个桌面读局操作是玩家理解当前局势的必要能力，覆盖矩阵必须单列该操作的教程落点；没有落点时不得把基础教程判成完整。

16.1 **非直觉 UI 必须进入教程覆盖矩阵**
   - 只要某个玩家可见 UI 不能仅凭图标、短标签或常识一眼看懂，就必须在教程覆盖矩阵里单列，并标成 `流程中教学 / 帮助或提示中解释 / 明确不需要并说明 / 待补缺口`。
   - 典型对象包括：带次数的确认按钮（例如 `确认 1/2`、多次确认、分步确认）、聚焦到自己位置/房间/对象的按钮、切换观察视角、查看剧本/目标/帮助的只读入口、当前值轨道/进度条、状态色、可取消的选中态、等待归属、可重掷/可改骰入口、隐藏但可恢复的牌堆/弃牌堆/持有区。
   - 教程解释这类 UI 时，必须说现实含义和使用时机，例如“这个按钮把视角移回你的所在位置”“`确认 1/2` 表示这一步需要完成两次确认中的第一次”；不得只复读按钮名字、图标名、内部字段或测试标签。
   - 带计数的确认按钮必须按玩家实际看到的结果解释：同一次公开结果/发现/结算里还有几项需要阅读并确认、当前画面已经显示了什么、确认后会回到哪里或进入哪一步。不得用画面数量来描述确认次数，也不得暗示已经同屏显示的获得、判定、抽牌或检定是分开发生的结果；不得把 `阻塞结算`、`队列`、`pending`、`stepKind` 这类内部流程词写进教程正文。
   - 如果多个内部结果事实已经在同一个结果画面里由正式对象承载，且下一步都是“读完关闭 / 回到牌桌 / 进入同一个后续状态”，玩家 UI 只能给一次确认；不得因为领域层有两条记录、两条日志、两个 reducer 步骤或两个测试断言，就生成 `确认 1/2`、`确认 2/2` 这类多次玩家动作。
   - 观察视角、镜头聚焦和返回上下文必须分开解释：首次点击玩家/队友切到谁、镜头是否跟随、再次点击或关闭后恢复到进入观察前的上下文。不得默认写成固定回自己，也不得把“聚焦到自己位置/房间”的按钮写成通用返回按钮，除非该控件确实承担返回职责。
   - 这些 UI 的教学必须贴在真实会用到它的局面里：聚焦按钮要在玩家可能迷路或切观察视角后教，多次确认要在真实需要重复确认的流程中教，剧本/目标入口要在规则目标变化或需要回看时教。
   - 如果正式 UI 出现这类非直觉控件，而教程没有教、帮助入口没有解释、覆盖矩阵也没有明确豁免，则教程不得收口为完整。

16.2 **教程完整性按“玩家可用元素”过账**
   - 用户要求“教程包含所有元素”时，默认指所有会影响玩家决策、操作、状态读取、规则回看或结果理解的可见元素；不要求逐个讲装饰纹理、纯氛围材质、无交互背景或已由正式素材自解释的图面细节。
   - 教程收口前必须有一张 `玩家可用元素覆盖矩阵`，至少包含：元素名称、现实职责、所在正式 UI、是否高频/非直觉、教程或帮助落点、端到端截图证据、未覆盖原因。
   - 常驻 HUD、阶段/回合状态、资源/属性/生命/进度轨、牌堆/弃牌堆/持有区、主要动作入口、目标选择、确认/取消、只读规则入口、观察/聚焦/视角切换、随机/结算承接、结果反馈都必须逐项过账。
   - 若某个元素只在特定阶段出现，覆盖矩阵必须写清触发条件，并用端到端或代表态截图证明它在该阶段被教到或被解释到；不能因为主线第一轮没出现就默认省略。
   - 如果元素本身承载业务逻辑但 UI 看不懂，优先修正式 UI 表达，再把教程作为上手解释；不得用教程长文替代本应自解释的正式控件。

17. **计分制教程必须出现一次清晰的计分因果**
   - 不能只说“最后比总分”，也不能只展示一个结果数字。
   - 至少要让玩家看到一次：哪张牌的基础分是什么、哪两张或哪几张牌如何互相加分、最后总分在哪里看。

18. **结语必须短，并且只负责收口鼓励**
   - 结语默认只做两件事：宣布基础流程讲完了；鼓励玩家进入正式对局。
   - 禁止在结语里再讲一遍完整规则、再总结一遍操作顺序、再复述一遍案例推理。

19. **指定对象步骤必须命中单牌级高亮**
   - 当教程文案已经点名“这张牌”“这张卡”“中央这张”“弃掉这张”时，高亮必须落到对应单牌对象本身。
   - 不得继续只高亮整片手牌区、整片中央区、整条分数带，要求玩家自己猜哪一张才是当前目标。

20. **步骤完成后旧目标牌不得残留选中态**
   - 教程步骤完成并推进后，上一张目标牌的高亮框、选中描边、聚焦态必须及时退场。
   - 如果下一步还看到上一张牌保留蓝框、白边、抬升态或其它“仍是当前目标”的视觉，就视为教程状态管理不合格。
   - 允许保留的只有下一步真实仍在指向的对象，不允许把历史 `focus/selected` 态混进新步骤。

20.1 **选中后确认的对象必须有可逆选中态**
   - 如果正式流程是先点卡牌、棋子、骰子、地图对象或列表项进行选择，再点确认/使用/结算按钮才消耗或生效，第一次点击必须给出清楚的全对象选中反馈，例如抬起、描边、发光或等价状态。
   - 再次点击同一个已选对象应取消选中，除非规则明确要求单击即执行；如果单击会立即执行，教程文案必须直说“点击后立即打出/结算/消耗”，不能写成“选中”。
   - 教程 E2E 必须覆盖至少三帧：未选中、选中态可见且确认按钮出现、取消或确认后状态正确。只断言命令成功或对象从手牌/场上消失，不足以证明玩家知道自己选中了什么。

21. **基础教程必须覆盖该游戏自己的核心规则面**
   - 基础教程不是固定几步模板，也不是“能跑通一条最短链”就算合格。
   - 必须先识别这款游戏真正的核心规则面，再决定教程要覆盖哪些段落。
   - 至少要覆盖：
     - 怎么赢
     - 一个真实回合的首个正式决策入口
     - 主要资源或手牌怎么用
     - 至少一个核心结算要素
     - 至少一个明确结果反馈
   - 如果是战争、战斗、推图、区域控制类游戏，默认还要覆盖玩家第一次就会碰到的战斗关键概念，例如打牌时机、部队等级、士气、伤害吸收、控制权变化。
   - 如果教程结束后，玩家仍说不出“我这游戏主要靠什么资源运作”“打起来在比什么”，该教程直接判不合格。

22. **示范题前提只讲当前局面，不讲教学编排理由**
   - 如果这次教学为了演示某个案例，预先指定了起始区域、起始对象、起始牌组或起始目标，玩家文案只允许解释“当前局面为什么从这里开始有意义”，不允许出现“这道示范题”“为了教学”“这不是通用规则”之类作者口吻。
   - 正确写法应是“先从这里开始，这一步能立刻看到控制权变化”；错误写法是“这道示范题先从这里起手，这不是通用规则”。
   - 内部设计必须知道这是案例前提，但玩家看到的仍应只是游戏事实、当前收益和当前操作。

23. **动手前必须先列教程覆盖矩阵**
   - 重做或新建教程前，先把“规则条目 -> 对应章节/步骤 -> 预期截图证据”列成覆盖矩阵，再开始写文案或实现。
   - 禁止边做边想、想到哪补到哪；如果还说不清这款游戏有哪些核心规则面，就还没到能写教程的时候。
   - 只要教程会涉及回合顺序、一级行动、地区目标、支付步骤或横幅提示，还必须同步列一张“一级交互审查表”：
     - 先按规则书或权威真相源列出这一段**同层一级行动的完整全集**，不得只按当前案例经过、当前画面显眼或最容易截图的几个入口做抽样。
     - 规则书规定的回合骨架
     - 规则书同层一级行动全集
     - 当前正式 UI 的一级行动入口
     - 当前正式 UI 的后续目标/地区/支付入口
     - 哪些 UI 只是提示，不承接点击
     - 当前教程是否把一级入口与后续目标入口教反
   - 没有这张表，不得开始写教程正文，也不得动教程实现。
   - 覆盖矩阵不得只写“已介绍”。每个被教程文案点名的规则入口都必须有一行写清：入口类型、真实承接物、E2E 操作、截图证据。缺截图时状态只能是 `待补端到端证据`，不能写成 `已覆盖`。
   - 覆盖矩阵里的截图证据必须语义命中该行规则。若规则条目是“打开剧本目标页”，真实承接物必须是目标页本身；若证据只证明参考卡图片加载，只能写成参考卡已加载，不能写成剧本目标已覆盖。

24. **刷新会丢进度时，默认优先拆成多条短教程**
   - 如果教程状态不会持久化，基础方案默认优先使用多个短章节/子教程，而不是把所有内容塞进一条超长教程。
   - 章节可以分别从真实开局、真实战斗局面、真实阶段结算局面进入，但每章都必须明确自己在教哪段真实玩法。
   - 章节是控制长度的手段，不是固定模板；如果一条短链已经完整覆盖当前规则面，就不必为了“看起来像章节化”再硬拆。
   - 只有当章节化会破坏这款游戏的真实理解链时，才考虑先补持久化再做单条长教程。

25. **战争/区域控制类教程体系必须分开覆盖战斗与攻城差异**
   - 对战争、推图、区域控制类游戏，不能只做“资源 + 回合 + 点一个目标”就收口。
   - 教程体系至少要分别覆盖：
     - 资源或手牌如何驱动行动
     - 一个真实回合主入口与轮次节奏
     - 至少一次完整野战
     - 若城战/围城/占领与野战显著不同，必须单独做一章覆盖
   - 至少一次结果反馈，例如控制权变化、部队损失、威望/纪年卡/胜利条件推进
   - 如果教程结束后，玩家仍说不出“野战和攻城哪里不一样”，该教程体系直接判不合格。

26. **同一基础回合链里的系统默认合并教学，不按模块名硬拆章**
   - 如果资源使用、目标选择、主行动推进、行动结果反馈本来就属于同一条基础回合链，默认应合并在“基础回合”或等价主章节里一起教。
   - 不要因为代码里有多个面板、多个 reducer、多个子系统，就机械拆成三章或四章；那会把一条完整回合理解切碎成“系统说明书”。
   - 只有当某个系统已经脱离基础回合，能独立承载一种后续规则理解，例如战斗结算、区域占领、外交交涉、季节结算、建造收分，才适合单独成章。

27. **章节划分按玩家心智任务，不按程序结构命名**
   - 章节名和章节边界首先要回答“玩家这章学会了哪一段玩法”，而不是“这一章对应哪个面板、哪个 reducer、哪个子系统”。
   - 正确拆法应优先按玩法任务分章，例如基础回合、战斗、建造、外交、季节/回合结算、终局计分。
   - 错误拆法通常是把界面部件或程序模块各拆一章，导致玩家学到的是控件目录，而不是游戏怎么运作。

28. **通用教程规范不得夹带单游戏术语或固定机制名**
  - 写在 `.spec/knowledge/standards/` 或通用 skill 里的规则，默认要服务整个项目里的不同游戏，而不是当前这一个游戏。
  - 通用层只能写可复用的教学方法、验收口径和分层原则，不得把某个游戏的专有机制名、专有区域名、固定开局路线或固定章节结构写成默认模板。
  - 像具体地名、牌名、专有资源轮、专属地图区、单游戏特例章节这类只对某个游戏成立的内容，必须下沉到该游戏的专项文档、教程实现或覆盖矩阵。
  - 如果一条规则离开当前游戏就不成立，它就不属于通用教程规范。

29. **通用教程规范不得预设固定章节答案**
  - 通用层可以要求“先列覆盖矩阵、按玩家心智任务拆章、基础回合链尽量合并”，但不能预设“教程一定分成哪几章、一定要出现哪几个标题、一定按哪种顺序拆”。
  - 像“基础章 + 战斗章 + 结算章 + 特例章”这类只是一种常见骨架，不是整个仓库的固定交付模板。
  - 如果一条章节建议其实只是在描述当前某个游戏的最佳拆法，就必须下沉到该游戏的专项文档，不得留在通用规范里。

30. **用户未确认文案前，不得把教程直接实施到运行态**
  - 当用户当前要求“先给文案”“先看教程文案”“文案我先审”或语义等价时，默认只能先交文案稿、覆盖矩阵或章节结构，不得抢跑去改 `tutorial.ts`、语言包、教程测试或教程 E2E。
  - 只有用户明确认可当前文案方向，或明确授权“直接按这个稿实施”，才允许进入运行态实现。
  - 禁止用“我先顺手做一版再给你看”绕过这条门禁。

31. **通用教程规则默认按“未来很多游戏”成立自检**
  - 任何准备写进 `.spec/knowledge/standards/**`、项目通用 skill、项目 overlay 的教程规则，默认先问自己：这条规则放到第 100 个游戏里还成立吗。
  - 如果答案依赖某个当前游戏的专属回合结构、专属地图、专属资源轮、专属章节名、专属起手路线或专属教学顺序，这条内容就不该留在通用层。
  - 通用层只保留“如何判断该不该拆章、如何判断是否重复教学、如何验证真实规则覆盖”的抽象方法。

32. **被命名为“完整回合”的章节必须真的完整**
  - 只要某一章被命名为“完整回合”“基础回合”“首回合”“一个完整行动轮”或语义等价，它就必须覆盖从正式主入口进入，到这条主循环的主要公共推进节点结束的完整链路。
  - 不得把同一条基础回合链里的后半段公共机制再拆成下一章重教，否则这章不配叫“完整回合”。
  - 如果后续章节仍要出现同一机制，只能讲这一机制在别的分支、例外或进阶结果里的新内容，不能把基础用法再讲一遍。

33. **同一核心机制只允许一个主教学落点**
  - 教程体系里，每个核心机制默认只能有一个主章节承接第一次完整教学。
  - 后续章节只能复用该机制作为背景条件，或补它的分支、反例、特殊结算、进阶组合，不得重新把它当作平级核心主题再教。
  - 如果某章看起来只是“把前一章的后半截单独再讲一次”，默认先判定为章节边界错误，而不是文案问题。

34. **通用层只管判断方法，不替单游戏预写最佳答案**
  - 通用规范可以要求“先列覆盖矩阵”“完整回合必须真的完整”“同一机制不要重复教学”，但不能直接替每个游戏预写“该分几章、每章叫什么、先教哪一章”。
  - 如果某个结论已经落到了“某游戏的某个专属系统该并进首回合”“某款构筑游戏应该先教弃牌再教买牌”这种粒度，它就已经是单游戏答案，不属于通用层。
  - 通用层的职责是阻止明显错误的拆章方法，不是替所有游戏给出同一份章节设计。
  - 当用户要求“先更新 skill，不要只考虑一个游戏”时，默认优先回看这一条：先补能约束很多游戏的方法，再把当前游戏答案留在它自己的专项文档和实现里。

35. **通用层改动必须同时交代“拦什么错、不过度规定什么、专项答案落到哪里”**
  - 任何准备写进教程通用规范或教程通用 skill 的新增规则，默认至少要同时回答三件事：
    1. 这条规则会拦住哪类跨游戏都会出现的教程错误；
    2. 它明确不替单游戏预写哪些章节、顺序、案例或起手路线答案；
    3. 当前这次单游戏的专属结论最终下沉到哪个专项文档、覆盖矩阵或教程实现。
  - 如果一条规则说不清这三件事，默认说明它还停留在“当前游戏的局部经验”，不应进入通用层。
  - 这样做的目标不是减少规范，而是避免通用层被单游戏答案污染，导致第 100 个游戏接入时照抄一份错误模板。

36. **提示 UI 与真实交互载体不得混讲**
  - 顶部横幅、步骤卡、状态条、提示气泡默认只负责告诉玩家“现在在做什么/该看哪里”，不自动成为正式交互载体。
  - 只有当某个提示 UI 自己真的承接点击、确认或选择时，文案才可以把它写成“点这里”。
  - 如果真实操作发生在按钮、地图区域、卡牌本体、列表项或其它对象上，教程必须直接教那个对象；不得把“上方有一条提示”写成主要操作入口。

37. **教程文案不得空讲当前步骤里没有被明确承载的状态**
  - 如果当前步骤文案点名了某个实时状态，例如剩余行动、剩余移动、当前资源、当前回合玩家、已选对象、当前目标、控制权差值，那么这个状态必须满足至少一种条件：① 被当前高亮直接包含；② 在当前画面里已有单独、清楚、稳定的可见承载，并在本步被明确指到；③ 被拆成下一步单独讲。
  - 不得在同一步里同时要求玩家去看两个相距很远、且只有一个被高亮的状态块，然后把另一个状态留给玩家自己猜。
  - 如果发现教程文案要解释的状态在正式 UI 里其实没有清楚落点，先判为实现缺口；应先补真实表达，再继续写教程。

38. **默认预选与玩家已决策不得混写**
  - 如果正式流程进入某阶段时已经默认聚焦某个地区、卡牌、轮盘项、行动项或目标列表，这只代表系统给了一个初始焦点，不代表玩家已经正式做出该选择。
  - 教程文案不得把这种默认预选写成“第一步先选这里”“你现在已经选好了这里”，除非玩家刚刚真的点过或确认过它。
  - 若当前案例确实依赖默认预选，玩家文案最多只能把它当作“当前聚焦点”，不能把它提升成规则顺序本身。
  - 正式 UI 视觉也必须同步遵守这条边界：默认聚焦只能是弱聚焦，不得直接使用“已确认 / 已锁定 / 正在执行”的强确认视觉。

39. **基础教程的首个主操作必须落在当前玩家真正有选择权的动作层**
  - 如果流程前面还有强制公共推进、开局前置、纯进入壳层或自动过场，这些可以被介绍，但不能冒充“第一步正式决策”。
  - 一旦当前画面已经进入玩家真正有选择权的一级动作层，教程的第一个主操作步骤就必须直接教这一层的真实承接物。
  - 不得跳过这一层，直接去教后面的目标地区、支付对象、来源区、确认按钮或结果区。
  - 如果当前游戏的第一段真实选择同时包含公共推进里的分支选择，例如轮盘走法、抓牌方向、先后次序，这类选择本身就属于首个主操作，而不是背景说明。

40. **直点交互进入时必须立即给到可操作线索**
  - 如果当前阶段的真实主入口是直点地图、卡牌、轮盘格、列表项或棋盘对象，那么这些对象在该阶段一进入时就必须已经具备清晰可操作语义，例如单牌级高亮、可点击描边、发光候选或其它稳定信号。
  - 不得把“请看横幅/请看右侧说明/再点一个替代按钮”当成弥补主入口不可见的手段。
  - 如果教程文案需要用一句话才能让玩家知道该点哪里，优先判为正式 UI 表达不足，而不是继续给教程加说明。
  - 如果目标语义来自已支付后的效果选择，仍然必须遵守场景直选优先：费用支付只是进入效果目标阶段的前置条件，不允许把后续地图/棋盘目标降级成右侧文字按钮主路径。

40.1 **动作文案必须点名真实可见控件**
  - `requireAction` 文案只要写“点击 / 点 / 选择 / 确认 / 结算”，就必须使用当前屏幕真实可见的对象名或按钮文案；不得写一个概念性动作名让玩家去猜，例如屏幕上只有“断后 / 溃退”时，不能写“点战斗结算按钮”。
  - `highlightTarget` 必须命中这条文案要求点击的同一个真实承接物；解释区、摘要区、状态条、承伤说明和结果文字不能替代本步真正要点的按钮、卡牌、地图对象或确认控件。
  - E2E 至少断言三件事：教程文案包含真实可见控件名、对应 `data-tutorial-id` 或等价锚点存在、点击该锚点后进入预期结果。只断言步骤推进或结果出现，不能证明玩家知道点哪里。

41. **教程玩家文案不得用作者旁白腔代替规则概念**
  - 玩家可见文案默认优先使用规则动作名、对象名、结果名，例如“转动轮盘”“打出事件牌”“弃 3 张手牌”“选择战后处理”。
  - 不得主要依赖“这一步 / 下一步 / 这里 / 这次 / 现在先”这类作者旁白腔来串联步骤；这些词最多只能作为补语，不能成为句子的核心语义。
  - 如果一条文案去掉这些旁白后就失去意思，说明它还没有真正落到游戏规则本身。

42. **玩家可见教程文案不得混入验收口吻**
  - 玩家教程正文只负责告诉玩家当前目标、真实动作对象、动作理由和可见结果；不得把测试、审计、实现证明或防误报口径写给玩家看。
  - 禁止在玩家文案中出现类似“真实链路”“运行态”“不是动画”“不是说明图层”“不是假按钮”“E2E 已覆盖”“正式验证”这类面向开发者或验收者的说法。
  - 用户给助手的设计裁定、验收要求和防回归要求不得原句进入教程或玩家 UI，例如“不要常驻写公式”“放到悬浮提示”“卡图已有内容不要复写”。需要教给玩家时，必须翻译成玩家动作和规则因果，例如“高亮格表示当前预兆数量”“抽到预兆后用这个数量进行作祟检定”；需要防回归时，写进测试、审计文档或专项合同。
  - 如果需要证明某个动作不是演示动画，证明应落到 E2E、截图证据、审计文档或测试断言；玩家文案应改写成规则内结果，例如“房间会翻开，并抽取对应的发现牌”。
  - 这条规则只约束跨游戏都会出现的“把验收话术上屏”错误，不替任何单游戏预写章节、路线或固定案例。
  - 如果教程从预设中段局面开始，不能只写“已经学会 / 已经获得 / 已经完成”。玩家可见文案必须补清必要前因：前置动作是什么、成功条件是什么、现在为什么进入下一步；若没有真实演示该前置，覆盖矩阵必须诚实标成“前置说明 / 未实操演示”，不得把一句结果状态冒充完整教学链。

42.1 **随机结果过程不得被摘要替代**
  - 只要教程步骤涉及投骰、重掷、翻牌、抽牌亮相或结算型揭示，玩家必须看到对应的结果承载，例如骰面、牌面、抽到的对象名和效果区；不得只在日志、横幅或一行摘要里写“成功 / 无事发生 / 即时生效”。
  - 如果翻开的牌、发现牌、事件牌或效果文本会立即要求投骰/检定，阻塞展示必须同时呈现牌面和本次骰面；不得把牌面放主舞台、骰子留在角落 HUD、侧栏小条、日志或一行结果里。
  - 如果这个随机/揭示结果会阻塞当前流程，结果承载必须进入主视线区域，不能缩成角落 HUD、侧栏小条或教程气泡旁的一行说明。教程提示层只能告诉玩家为什么看这里，不能替代正式 UI 的主结果承接。
  - 阻塞式牌面、骰面或参考页已经成为当前主结果时，教程说明卡必须退让主视线：只保留底部/既有动作锚点的最小确认控件，或使用一句“看清后继续”的短提示；不得把长段教程总结并排贴在正式素材旁边。
  - 如果正式牌面或骰面本身已经包含标题、正文、点数或结果说明，教程 UI 不得在旁边再可见复读同一内容。教程提示层只负责引导玩家看正式承载，交互层只负责选择、确认或跳过；可读性不足时必须先查图集切片、裁切坐标、显示尺寸或放大承接，而不是另写一套正文盖过素材。
  - 教程投骰结果不得把内部骰值序列、加法公式或测试验收口径写给玩家看。玩家需要的是骰子本体、加值、总点数、结果和下一步动作；如果截图里只能靠公式看懂结果，先判为骰面可读性或信息布局问题。
  - 教程文案可以用短句提示“投骰”“翻开房间”“抽发现牌”，但正式 UI 必须有可见过程结果；如果 UI 只能给一行文字，先判为结果反馈实现缺口，而不是继续把文案写得更像规则书。
  - 这条规则只约束跨游戏都会出现的“随机过程被压缩成摘要”错误；具体使用骰子、卡牌、轮盘还是其它承载，留给对应游戏实现决定。
  - 判断“缺骰子 / 缺牌面 / 缺模型 / 缺素材”前，必须区分三种状态：素材包真不存在、素材已在来源包里但未接入运行时、运行时已有低保真等价承载。只能按证据说“未找到 / 已找到但未接入 / 已临时承载”，不得把“运行时没接”说成“素材没有”。
  - 用户可见教程注入态不得使用测试专用假对象，例如“测试事件”“测试牌”“中性占位结果”。如果教程要演示抽牌、翻牌、投骰或结算，预设状态也必须引用正式规则对象或明确标成开发测试；不得把测试假对象当作玩家教程内容。

42.2 **规则原文优先，禁止把实现关系翻译给玩家**
  - 只要规则书、剧本书、卡面或参考卡已经直接表达了当前要教的触发条件、动作、比较方式或结果，教程正文优先使用已锁定的原文或正式翻译原文；不要再把同一规则改写成实现说明。
  - 规则原文不足以说明当前操作时，只补最短的玩家动作和结果，例如“读完后点确认”“返回牌桌”；不得补充“同一画面”“同一次发现”“结果面板”“日志摘要”“行动槽”或其它渲染、容器、队列和代码关系。
  - 当多个规则事实已经由同一个正式结果承载时，玩家文案应说明规则本身和唯一的后续动作，不得说明这些事实“被放在一起显示”或因为内部记录数量而制造额外确认。
  - 审查文案时必须逐句标记来源：`规则原文 / 正式对象原文 / 必要 UI 动作 / 当前结果`。没有来源或只是在描述实现结构的句子，必须删除或改写。
  - 每次教程语言包变更后，必须对中英文 `tutorial` 区块做静态扫描，并在教程单测中拦截实现容器词、内部流程词和作者话术，例如“同一画面 / 结果面板 / 摘要 / 队列 / 为了演示 / 待放置状态 / 主视区”等；E2E 通过不能替代这项文案门禁。
  - 这条是跨游戏的文案来源与分层门禁，不替任何单游戏预写章节、路线或固定句子；当前游戏的规则原文、正式翻译和 UI 动作仍落在对应游戏规则源、语言包和教程实现中。

43. **教程收口前必须列出主要交互清单**
  - 只要这轮教程会覆盖基础回合、战斗、攻城、年度结算或其它多阶段主循环，除了覆盖矩阵，还必须单独列一张“主要交互清单”，至少写清：
    - 开局公共推进
    - 一级行动入口
    - 支付/弃牌
    - 二级目标选择
    - 地图目标选择
    - 待结算战斗
    - 战后/阶段收口
    - 年度或终局结算
  - 任一类目还没被列出或还没判断“它是教程问题还是正式流程问题”时，不得宣称教程结构已锁定。

44. **压教程结构前必须先做覆盖差异表**
  - 只要准备合并章节、删隐藏续章、删旧步骤、把多条流程并成一条，必须先列“覆盖差异表”，至少写清：
    - 旧结构原先覆盖了哪些规则点、真实交互链、截图证据
    - 新结构把这些内容落到哪里
    - 哪些仍有正式局真实入口支撑，哪些其实只剩教程注入态或抽象替代
    - 哪些内容若本轮拿不出等价替代证明，就必须显式降级成缺口
  - 没有这张表时，不得静默删除任何已存在的核心规则覆盖，更不得用“避免重复”“结构更紧凑”作为默认删减理由。

45. **教程重构导致覆盖退化时必须直说**
  - 如果新教程删掉了先前已经覆盖的一类核心规则、真实战斗、正式一级入口、关键结算或截图证据，而本轮没有提供等价或更强的新证明，结论必须直接写成“覆盖退化/待补回”。
  - 不得把这种情况包装成“只是实施中先移除”“后面再补一下”后仍继续使用“基础教程已完整”“新游戏已收工”口径。

46. **实施前映射不得充当运行态真相**
  - `implementation-map / 章节草案 / 覆盖矩阵 / 教程脚本草案 / 实施前映射` 只能说明“准备怎么改”，不能说明“当前正式局已经这样工作”。
  - 只要结论里出现“这一章已实现”“正式局已有这个一级入口”“新游戏可收工”，证据必须来自当前 `tutorial.ts`、当前正式进行页源码、当前 worktree 的真实截图或 E2E，不得拿计划文档顶交。

47. **新游戏收工前必须逐类回到正式进行页核一级入口**
  - 当用户目标已经升级为“新游戏收工”“端到端能看出怎么运作”“所有交互都要审查”时，除了教程覆盖矩阵、一级交互审查表和主要交互清单，还必须再列一张“正式进行页一级入口核对表”。
  - 这张表至少要逐项标出：规则书同层一级动作全集、当前正式局入口、真正承接点击的对象，以及当前属于 `真实可用 / 抽象替代 / 教程注入专供 / 尚未实现` 哪一类。
  - 缺这张表时，不得把教程示范链、隐藏技术续章或抽象按钮链直接包装成“正式流程已完整”。
  - 只要这张表里同层一级动作仍有 `抽象替代 / 教程注入专供 / 尚未实现`，就不得把某条单独示范链、某个默认选区、某个后续目标选择或某个隐藏续章，包装成“基础流程第一步”“正式主入口已完整”或“新游戏已收工”；这些缺口必须原样保留在当前教程结论与正式流程结论里。

48. **主要交互清单必须继续分流到执行**
  - “所有交互”不能从教程截图、示范链或几条 E2E 成功路径倒推；必须从规则书同层动作、当前状态字段、command/event、builder/reducer 和当前 E2E 入口共同列全集。
  - 每一行都必须分开写 `真实承接物` 和 `提示 UI`。横幅、步骤卡、摘要、状态条只能作为提示 UI；如果真实承接物还没锁定，就不得写成玩家应该点击的对象。
  - 每一步的高亮目标必须跟随当前真实承接物迁移。进入二级目标、支付、战后或结算选择后，不能继续高亮上一阶段入口、整区容器、提示层、空占位容器或被结算/弹窗遮住的旧底层容器；E2E 应同时断言教程步骤标记、真实承接物可见，以及高亮锚点有非空几何并落在当前可视层里，避免业务面板已出现但教程蓝框框空处。
  - 结果、结算、摊牌、战斗、掷骰或计分步骤的蓝框必须落到当前结果主体或被结算对象本体；不得落在 portal 外壳、fixed 子层外面的占位 div、提示气泡、纯逻辑锚点或只含 sr-only 文案的节点。若当前 UI 只有文字结果而没有对象本体，先补结果对象展示，再补教程。
  - 如果结果主体本质是卡牌、棋子、骰子、地图地区或单位，结算 UI 必须优先显示这些真实游戏对象；“一对 / 失败 / 成功 / +3 分”只能作为辅助标签，不能替代牌面、骰面、单位或地图对象。
  - 如果教程声称覆盖胜负、结算、摊牌或计分，主教程链必须证明正确操作能得到正向结果，同时记录反向结果的出现条件；只有失败结算截图不得称为完整结算教学。
  - 当目标语义是地图、棋盘、场景里的现实对象，且当前场景对象可命中时，正式 UI 与教程必须以场景直选为主；按钮列表只能作为备用、无障碍入口，或作为目标已锁定后的效果/数量/确认控件。若目标是“来源对象 → 目标对象”的组合选择，场景直选必须同时显示组合关系，不能用一组文字按钮替代主流程。只有对象命中、身份映射或消歧无法稳定时，才允许暂用按钮主入口，并必须把原因写成正式缺口。
  - 能场景直选却让 E2E 主路径继续点击文字按钮或右侧列表，默认判为交互验收失败；“按钮能点通”只能证明备用入口或后续确认控件存在，不能证明玩家主流程合格。教程步骤、高亮目标和截图验收都必须回到场景对象本身，除非该对象命中能力被明确记录为正式缺口。
  - 审计时必须先问“规则目标是什么”：如果目标是选择地区、地点、部队、基地、随从或牌面，主路径必须点场景对象；如果场景对象已经选定，按钮才可以承接建军数量、效果分支、战后处理或继续结算。审计表和 E2E 必须分别记录这两层，不得用后续按钮证明目标选择合格。
  - “所有交互都要审查”不是只产出一张表；表中每一行都必须继续分流为 `可立即真修 / 需要建模或真相源补齐 / 明确暂不处理且说明原因`。
  - `可立即真修` 包括上屏文案误导、提示 UI 冒充交互、默认聚焦写成已确认、候选列表被摘要复述等可以直接落到当前源码或语言包的问题；这类行必须继续实施并验证，不能只写入文档。
  - `需要建模或真相源补齐` 必须点名缺口，例如素材合同、规则级对象映射、状态字段拆分、真实交互承接物或阶段收口；如果这些缺口会阻止“新游戏收工”，最终结论必须保留，不得用“后续优化”带过。

49. **低保真或错素材对象不得被教程写成正式入口**
  - 如果正式局某个一级动作当前依赖的可见对象仍是 `低保真预览 / 错 atlas / 混入别类对象 / 没有规则级身份`，教程和正式流程结论都不得把它写成“正式一级入口已具备”。
  - “混入别类对象”包括但不限于：人物牌、纪年卡、剧本卡、牌背、帮助卡、占位壳，或其它不属于该动作对象集合的可见对象。
  - 命中这条时，当前状态只能写成 `低保真替代 / 局部真实可用 / 正式缺口`，不能因为眼前已经有局部 seam、教程注入态或抽象按钮链，就把它包装成“正式主流程已教完”。
  - 这条规则拦的是跨游戏都会出现的“错对象冒充正式入口”错误，不替任何单游戏预写该先教哪章、哪张牌或哪条路线；当前单游戏的素材裁切合同、对象真相表和专项裁决，必须继续下沉到对应游戏的专项审计文档或实现。

50. **命中对象真相缺口时先追素材合同，不准在错对象层硬补教程**
  - 如果一级动作的可见对象还没有稳定的 `cardDefId / cardKind / 规则级身份 / atlas 裁切合同 / 对象顺序表`，默认动作不是补一句文案、补一个高亮、或在这层再挂一条教程步骤。
  - 正确顺序是先锁：素材清单、atlas 裁切合同、对象顺序、规则级映射，再决定是否真的已经具备正式入口。
  - 在这些真相没锁定前，教程最多只能把该链路作为 `局部示范 / 注入态演示 / 正式缺口` 处理，不能当成“基础流程已具备”的证明。

51. **过时覆盖矩阵不得继续当现状真相**
  - `覆盖矩阵 / implementation-map / 教程脚本草案 / 章节重组草案` 只要和当前 `tutorial.ts`、当前目录显隐、当前 `nextTutorialId`、当前 E2E 截图链有任一项不一致，就必须先标成“过时计划态”并回写。
  - 在回写完成前，不得继续拿其中的旧章节数、旧隐藏关系、旧证据组或旧缺口结论，去指导当前教程设计、正式交互审计或“新游戏是否收工”的判断。
  - 如果同时存在“当前源码真相”和“旧矩阵结论”，冲突时一律以后者为待修订对象，而不是以后者覆盖当前源码。

52. **截图验收必须实际开图核对**
  - 只要本轮结论依赖“截图里是否仍有重复提示、错误高亮、错误交互载体、错误教程壳层”，就必须实际打开当前 worktree 下的关键截图逐张核图。
  - 只给截图绝对路径、只说“E2E 通过”、或沿用历史截图结论，都不算完成。
  - 用户明确说“打开图 / 看图 / 图呢”时，必须完成用户可见展示，不得只复述路径。

53. **章节目录必须继承当前游戏自己的视觉风格**
  - 只要一个游戏使用 `TutorialCollection` 或同等章节目录能力，章节目录页就属于该游戏教程体验的一部分，不是全站通用后台列表。
  - 目录页必须先读取该游戏的设计系统或专项 UI 文档，继承该游戏的主色、材质、边框、字体气质和交互语法；不得把另一款游戏的皮肤硬套过来。
  - 这条规则拦的是跨游戏都会出现的“统一目录组件变成无风格网页卡片 / 串用别的游戏皮肤”错误，不替单个游戏预写具体色板、章节名、教程顺序或案例。
  - 单游戏的专属视觉答案必须下沉到对应 `design-system/games/<gameId>.md`、游戏专项文档或代码主题变量里；通用层只规定“必须按 gameId 继承设计系统”这一方法。
  - 换风格不得只替换颜色 token。至少要同时调整结构语法中的两类：入口尺度、边框/材质、编号形态、进入控件形态、背景纹理、排布密度、字体语气。否则视为“换色”，不是风格化。
  - 章节入口是目录项，不是整块巨型 CTA。移动横屏下必须保证触控命中足够，但视觉上应像桌游部件、档案条目、地图签、卡牌索引等当前游戏对象；不得为了制造可滚动而把卡片硬拉高。
  - 禁止把验收口径、适配能力或实现说明写成玩家可见 UI，例如“横屏可滚动”“手机适配”“无横向溢出”“E2E 已通过”“真实链路”。这类内容只能进入测试、文档或证据，不得作为目录角标、徽章、提示条或装饰文案出现。
  - 伪元素只能补真实视觉材质或真实对象语法，不得凭空造一个非规则、非素材、非交互所需的标签来证明风格，例如“山屋档案”这类如果不是游戏内真实栏目，就不应常驻在玩家目录页。

## 默认结构

一个合格的基础教程，默认至少包含以下四段：

1. **目标段**
   - 讲清楚赢法、核心爽点、玩家这局在追求什么。

2. **决策段**
   - 讲清楚本回合/本轮有哪些正式行动，以及它们分别在什么情况下更划算。

3. **案例段**
   - 给出一个真实局面，让玩家做出一次“有理由的选择”，并看到收益变化。

4. **结果段**
   - 用计分、结算、伤害、控制权或其它核心反馈收口，让玩家知道自己刚刚“做成了什么”。

如果游戏机制更重，例如战斗、构筑、资源曲线或隐藏信息占比较高，教程必须在上述四段之上继续扩展；不得把“四段”误解成上限。

当项目已支持 `TutorialCollection` 之类多教程目录时，默认应优先用现成目录能力拆章，而不是另造一套教程路由或状态系统。

## 禁止行为

- 禁止把“教程能走通”当成“教程合格”。
- 禁止把“固定 4 段 / 固定 6 步 / 固定 8 步”当成通用教程模板，忽略当前游戏真正的核心规则面。
- 禁止在通用教程规范里夹带单个游戏的专有机制名、专有地名、固定起手路线或固定章节模板。
- 禁止只用抽象概念替代真实案例，例如只说“注意组合”“尽量协同”，却不给可见的收益结果。
- 禁止只教界面部件名称，不教它们和赢法的关系。
- 禁止把非直觉 UI 留给玩家猜，例如多次确认计数、聚焦/回到自己位置、观察视角切换、状态色和可回看入口；这些要么在真实流程教程中解释，要么在覆盖矩阵中明确豁免。
- 禁止用教程长文替代正式 UI 的基础表达；如果控件没有说明现实含义，先修控件或补短提示，再在教程里教使用时机。
- 禁止为了让截图更顺而把教程写成特判壳、假按钮链、伪结算态。
- 禁止把“示范题”理解成可以跳过首次教学所需的正式决策入口，直接从中段题面开始教。
- 禁止把低信息量前置壳层误当成基础教程必须单独详教的核心规则面。
- 禁止把“这题先点哪里”伪装成“正式规则一上来就必须这样走”。
- 禁止只讲失败门禁或按钮顺序，不讲玩家为什么要这么做。
- 禁止用 3 句以上的说明文去替玩家完成本应由牌面、棋盘、数值变化自己表达的判断。
- 禁止在“指定这张牌”的步骤里，让整区高亮去冒充单牌目标高亮。
- 禁止把上一步目标牌的残留描边、残留焦点态、残留选中态带进下一步。

## 最低验收口径

教程收口前，至少要能用玩家听得懂的话回答以下问题：

1. 这游戏要怎么赢？
2. 这一回合我为什么选这个动作，不选另一个？
3. 我刚刚这步具体赚到了什么？
4. 哪张牌/哪个对象让结果变好了？
5. 如果这是计分游戏，我有没有真正看到一次分数因果？
6. 所有玩家可用元素是否已在覆盖矩阵里过账，并且非直觉 UI 是否有教程/帮助落点？
7. 教程是否有完整端到端截图链，能证明玩家从入门目标、真实操作、特殊 UI、结果反馈到结束态都走过？

以上问题有任意一个答不出来，教程不得收口。新游戏和正在补完的现有游戏默认以教程完整性作为验收条件之一；没有完整教程覆盖矩阵、真实教程 E2E 和关键截图核图，只能称为游戏实现或教程局部已完成，不能称为新游戏整体完成。
