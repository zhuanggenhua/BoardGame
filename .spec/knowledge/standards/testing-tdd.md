# 游戏开发 TDD 决策规范

> **角色**：BoardGame 项目中“什么时候写 TDD / 回归测试 / 阻断测试，什么时候只做截图、smoke、playtest 或 evidence”的唯一项目正文。测试运行命令和工具 API 看 `docs/automated-testing.md`；E2E 与截图验收主源看 `.spec/knowledge/standards/e2e-verification.md`。

## 外部资料核对口径

本规范按 2026-08-14 外部资料复核后收敛：

- Unity 和 Unreal 官方测试文档都把游戏测试拆成多层：低层代码测试、运行时/玩法测试、功能测试、smoke、截图或内容压力测试；这说明游戏测试不是单一“每改都写单测”。
- Riot 的《League of Legends》自动化实践把自动化用于高频变更下的快速反馈，但测试本身尽量线性、可本地运行，目的是减少重复 QA，把人留给更有创造性的测试。
- GDC《Backwards Is Forward: Making Better Games with Test-Driven Development》给出的边界是：如果其它游戏代码会依赖这段能力，通常值得 TDD；一次性高层脚本和关卡触发不一定值得。随机性应拆出来或固定序列。
- 视频游戏测试研究综述指出：自动化能提高可复现性和稳定性，但“好不好玩”、平衡和复杂人类行为不能靠自动化测试完全捕获；测试方法不能打断开发 workflow。

参考链接：Unity Test Framework 的 Edit / Play Mode 测试、Unreal Automation Test Framework、Riot《Automated Testing for League of Legends》、GDC Vault《Backwards Is Forward: Making Better Games with Test-Driven Development》、arXiv《A Survey of Video Game Testing》。

## 先判定，不机械写测试

新增或修改测试前，先给本轮改动分类：

| 分类 | 默认动作 | 允许升级测试的条件 |
| --- | --- | --- |
| 稳定规则 / 引擎 / 状态 | 优先写行为测试或 GameTestRunner | 有规则真相源、稳定命令入口、确定性预期 |
| 保存 / 同步 / 资源索引 / 公开协议 | 写契约测试、集成测试或最窄 E2E | 其它代码、数据或用户入口长期依赖该边界 |
| 已复现高风险 bug | 写最窄回归测试 | 原始症状可复现，且复发会破坏玩家结果 |
| UI 视觉恢复 / 样式微调 / 槽位复原 | 默认不新增阻断测试 | 用户明确要求冻结视觉合同，或已批准设计稿定义了稳定外形 |
| 玩法探索 / 数值手感 / 文案 / 关卡摆放 | 默认用 playtest、截图、smoke 或 evidence | 玩法结果已被接受为长期规则或发布合同 |
| 资源接线 / 单个素材映射 | 默认用文件存在性、截图或现有资源审计 | 映射属于长期索引表、批量资源管线或公开契约 |
| 内部重构 | 跑现有测试；不因重构本身新增测试 | 发现原有 seam 缺失，且新增测试能保护公开行为 |

不得因为“这是 bug”“这是业务变更”“要严谨”就自动新增阻断测试。测试是长期维护合同；没有稳定合同就不能把它写进 CI 门禁。

## 适合 TDD 的游戏对象

以下对象适合严格 red-green-refactor，或至少适合新增长期行为测试：

- 回合阶段、合法动作、结算顺序、伤害/资源/token/区域归属、胜负判定。
- 卡牌 / 技能 / 场地 / 流程节点等已录入规则对象的确定性效果。
- 随机相关规则，但必须用固定随机源、可控骰面、固定牌序或可重放序列。
- 存档恢复、重连同步、多人视角、响应窗口、交互队列和跨阶段清理。
- 资源 manifest、配置解析、i18n key、生成器输出、公开 API 和共享 helper 契约。
- 已经由用户、规则书、设计合同、历史正常版本或线上反馈锁定的回归点。

这类测试要优先通过公开行为 seam 观察最终玩家结果；不要断言内部函数调用次数、CSS class、临时状态字段或实现顺序。

## 不适合严格 TDD 的游戏对象

以下对象默认不写新增阻断测试，除非用户当轮明确要求冻结合同：

- 游戏手感、趣味、平衡、节奏、动画时长、镜头感觉和视觉气质。
- 设计稿实现中的尺寸、坐标、层级微调、色值、阴影、边距和临时布局。
- 左右 HUD、面板位置、提示条文案、按钮外形、截图中待人工审的视觉质量。
- 还在频繁变更的角色选择、关卡摆放、素材命名、接入名单、排序位、灰度状态。
- 只修单个资源路径、删除错误提示、恢复旧 UI 外形、清掉临时壳层或改日志文案。

这些对象仍需验收：UI 改动走真实截图核验；玩法手感走 playtest 或人工裁定；资源改动走文件/manifest/截图证据；回归恢复优先用 git 历史、旧截图或旧实现证明“原来是什么样”。

## 新增阻断测试的最低门槛

新增会让后续提交失败的测试前，必须同时满足：

1. **长期合同已锁定**：真相源来自规则书、已批准设计稿、用户当轮明确裁定、历史正常版本、公开 API 或稳定数据合同。
2. **现有证据不够**：已有单测、E2E、截图、类型检查、资源审计、git 历史或人工证据不能覆盖本轮风险。
3. **测试 seam 稳定**：可以通过公开命令、GameTestRunner、状态注入、真实入口或契约 helper 观察结果；不会绑死内部实现。
4. **预期独立**：断言来自规则/样例/历史正确版本，不是把当前实现算法复制一遍。
5. **维护成本合理**：正常业务或 UI 迭代不应频繁改这个测试；若会频繁跟改，改用 evidence 或更稳定的行为 seam。

不满足任一项时，不新增阻断测试。需要留证时，写临时 evidence、截图、playtest 记录或跑现有最窄验证。

## 交互可操作性测试

“有按钮但玩家实际点不了 / 点了没生效”是合法的长期回归风险，可以新增阻断测试；它保护的是玩家可操作链，而不是内部交互字段形状。

这类测试的最低断言顺序：

1. **入口可达**：通过真实 UI、GameTestRunner 命令或游戏 prompt facade 进入目标提示。
2. **选项可发现**：通过 facade 或 E2E locator 读取玩家可见的选项、按钮或目标对象；不得在业务测试体里直读 `sys.interaction.current`、`prompt.data.options` 等内部结构。
3. **动作可提交**：通过 facade 的响应 helper、真实点击或公开命令提交选择；不得手写底层系统命令绕过玩家路径。
4. **结果落地**：断言最终玩家结果、状态变化、日志 / 反馈或交互关闭；不能只证明“内部有一个 prompt”或“按钮看起来可见”。

如果现有 facade 不能表达“当前提示来源、选项列表、按钮是否可提交、提交后的交互是否收口”，先扩展 facade 或把测试下沉到对应系统契约文件。业务测试不得为了方便直接读取内部字段；底层系统契约测试才允许直接断言系统存储结构。

## 全量领域测试的覆盖口径

共享规则、结算管线或重构造成同类规则失效时，可以要求“全量领域测试”，但这里的“全量”指覆盖所有必要的玩家结果形态，不是把每张卡、每个技能键或每个实现分支都列成测试。

项目通用测试规范只能写抽象裁决方法、覆盖矩阵和分层原则；不得写入具体游戏、角色、卡牌、技能或单次事故清单。单游戏答案、卡牌事实和一次性缺口必须下沉到该游戏事实资料、evidence、用户故事或专项文档。

先列覆盖矩阵，再选代表用例。矩阵至少按四类差异分组：中间结果从哪里来、它在流程里是否可被修改、最终由哪个玩家结果消费、以及哪些可见反馈会复用同一个结果。一个来源形态不能代表另一个来源形态；一个生命周期不能代表另一个生命周期；一个消费点也不能代表另一个消费点。

凡规则允许玩家或系统在结算前改写某个中间结果，测试必须成对覆盖：未改时按原结果生效；改后按最终结果生效。断言要落到玩家结果，例如“原始输入为 6 时产生 +3，改成 4 后必须变成 +2”，而不是只断言内部缓存、日志片段或展示字段被更新。

如果同一公式、同一生命周期、同一消费点已经由一个代表用例覆盖，不能为了“看起来全面”继续枚举对象名、处理器名或内部效果键。只有来源、生命周期、时机窗口、目标归属、计算公式、状态流、随机控制或消费点不同，才拆成独立领域测试。剩余对象清单交给配置 / 合同审计、代表性 E2E 或专项审计，不用领域测试逐个复制。

## 领域测试的商业写法

规则文本逐句核对不等于逐句模拟整条规则链。逐句录入、字段存在、翻译 key、资源引用和处理器挂接属于配置 / 合同审计；只有会改变玩家结果的计算、状态、合法动作、结算顺序或可见反馈，才进入领域行为测试。

写领域测试前先列行为覆盖矩阵：玩家结果是什么、预期来自哪里、走哪个稳定入口、选哪个代表场景、最终由谁消费。矩阵里同一公式、同一状态流、同一消费点的多张卡或多句规则，只保留代表测试；只有计算公式、状态生命周期、目标归属、时机窗口、随机控制或消费点不同，才拆成独立测试。

商业项目默认分层：领域行为测试覆盖规则形态；配置 / 合同审计覆盖卡牌与数据清单；少量 E2E 覆盖真实页面、按钮、日志和关键串线风险；截图、evidence 或 playtest 覆盖视觉、手感和体验。不要用慢而脆的端到端链路替代可稳定判断的领域测试，也不要用领域测试假装证明 UI 画面已经正确。

领域测试应走真实领域入口和真实代码路径，只 mock 随机数、时间、网络、文件系统、数据库等外部不可控边界。不要 mock 自己控制的 reducer、结算器、规则处理器或 UI 消费前的领域适配层；否则测试会变成“模拟结果是否等于模拟结果”，不能证明玩家结果。

## GameTestRunner 成功路径断言

GameTestRunner 的成功路径不能只看最终状态和业务断言错误。只要用例预期命令序列全部成功，测试必须显式断言没有失败步骤；只有刻意验证非法命令、拒绝路径或错误提示时，才用对应的预期错误断言。

这条规则保护的是“中途命令失败但 runner 继续执行，最终状态看起来碰巧满足”的漏测风险。特别是多步选择、重投、改骰、响应窗口、阶段推进和临时交互收口这类命令链，必须同时证明最终玩家结果正确，以及每一步命令没有被静默拒绝。

## 回合制战斗闭环

攻击、防御、响应、重投、减伤或反击只要会跨越一个以上阶段，测试不能停在骰面、按钮、临时交互或待结算状态。每条稳定的战斗规则链至少按风险覆盖以下闭环：

1. 用正式命令和可控随机源进入攻击与防御位置，并断言每一步成功。
2. 骰子类型会影响规则时，断言它是当前阶段的普通骰还是独立奖励骰；不得只因骰面相同而把两类流程混用。
3. 完成投掷、确认、防御或响应收口，断言攻击方和防御方的最终生命、资源、状态或其它玩家结果。
4. 断言攻击阶段已收口，以及本链拥有的待攻击、待伤害、待奖励骰或等价临时状态已清理；仍在规则规定的响应窗口时，先完成该窗口再判收口。

原始反馈经过真实按钮、动画或浏览器事件链时，领域测试之外还要有最窄真实入口 E2E：一次点击要产生一次普通投掷结果，确认和结束防御后必须回读最终玩家结果；确认后不应凭空再次生成同一阶段的投掷或确认步骤。

## TDD、回归测试和验收测试的命名边界

- **TDD**：先写一个最小失败测试，确认失败来自目标行为缺失，再实现，再重构。必须保留 RED 证据。
- **回归测试**：bug 已存在或已修复后补的保护。要写清原始症状、最后正常证据、失败入口和修复后的结果。
- **契约测试**：保护公开 API、资源索引、配置、协议或生成器输出。它验证边界，不验证临时 UI 外形。
- **验收 / evidence**：证明当前视觉、玩法体验、资源接线或人工裁定结果。它不是 TDD，也不必都进 CI。

先实现后补测不能倒称 TDD；只拍截图不能声称单元测试覆盖；测试通过也只能证明它直接覆盖的行为。

## 游戏测试层级选择

按风险从低成本到高真实性升级：

1. **领域行为测试 / GameTestRunner**：规则、状态、结算、命令流优先使用。适合大量边界和组合。
2. **契约 / 静态审计**：资源、配置、注册表、i18n、schema、handler 覆盖用数据驱动检查。
3. **状态注入 E2E**：验证真实页面消费状态、关键按钮、提示层和结果展示；避免长局自然链当主调试器。
4. **真实入口 E2E**：只给关键玩家路径、多人同步、保存恢复、真实 UI 点击链和发布门槛使用。
5. **截图验收 / AI 看图 / 用户看图**：视觉、布局、素材、角色板、token、地图和交互壳层必须回到整图判断。
6. **playtest / 人工裁定**：手感、趣味、平衡和节奏最终靠玩家体验，不用测试假装能证明。

测试层级要服务原始问题。能用低层稳定 seam 证明的，不升级成长链 E2E；只有真实入口或视觉本身是风险时，才升级到 E2E / 截图。

## 单游戏全量测试命名口径

本仓库里的 `npm run test:<gameId>` 只表示该游戏源码目录下的领域、组件、契约和局部行为测试全量；它不是浏览器端到端测试，也不能证明玩家真实入口、真实点击链、右侧骰盘、响应窗口、HUD 或截图画面已经正确。

当原始症状涉及玩家能不能点、按钮是否过早出现、响应窗口能否关闭、UI 代理按钮是否绕过当前交互、结算后画面是否显示正确，或任一规则结果必须经过 Board / HUD / 浏览器事件链消费时，最终汇报必须把两层证据分开写：

1. **单游戏全量测试**：证明底层规则、状态和局部组件合同是否通过。
2. **端到端测试 / 截图**：证明真实页面里玩家动作、按钮门控、结果落位和可见画面是否通过。

如果只跑了 `test:<gameId>`，不得写“端到端已验证”“真实入口已验证”或用“单游戏全量通过”回答玩家可见链路已经没问题；必须明确说端到端未跑，并按 [`e2e-verification.md`](e2e-verification.md) 补最窄真实入口 E2E，或说明为什么本轮不需要端到端。

## 回归恢复专条

用户说“之前是对的 / 现在又坏了 / 恢复原来样子”时，默认不是新需求 TDD，而是回归恢复：

- 先用 git 历史、旧截图、旧 evidence、旧实现或用户故事锁定“最后正常版本”。
- 修复优先恢复最后正常行为，不新造交互、不扩大重构、不把当前 bug 版本当基线。
- 只在回归点具有长期稳定 seam 且复发风险高时补回归测试；频繁变更 UI 外形不靠新增测试冻结。
- 最终验收回到原始位点：代码测试只证明行为，UI 回归必须补当前真实整图。
