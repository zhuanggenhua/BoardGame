# 生图设计稿到实现流程

> 触发条件：使用 AI 生成图、设计稿、参考图、截图或 mockup 作为 UI 实现目标时必读。本文补充 `.spec/knowledge/standards/ui-ux.md`，专门约束“先生成设计稿，再按设计稿实现”的交付流程。

## 核心原则

- **生成稿不是验收结论**：生成图只能作为目标稿，不能因为“方向看起来对”就默认实现也对。
- **真实产品内容优先**：生成 prompt 前必须读取真实组件、字段、按钮、状态、i18n 文案和交互入口，禁止把项目没有的控件画进目标稿。
- **正式视觉稿不自动包含交互合同**：位图设计稿、目标截图或效果稿默认只能证明视觉目标，不自动证明“点哪里 / 谁承接 / 是否确认 / 是否要提示”。
- **目标稿旁的纠正记录也是实现输入**：如果设计稿经历过用户标注、用户纠正、审计撤销、覆盖账本或版本裁定，实现前必须同时读取这些记录；不能只看最后一张图的大致布局。
- **交互模式必须先锁来源**：设计稿里每一种关键交互模式都必须先有来源表，明确来自正式设计稿、仓内既有真相、官方产品还是用户明确要求；没有来源的交互模式不得直接画进设计稿，更不得直接写进实现。
- **规则语义优先于美术发挥**：游戏 UI、生图设计稿和实现都必须先服从正式规则、隐藏信息合同和揭示时机；不得为了“画面完整”擅自补出规则未公开的信息。
- **真实素材承载优先于假 UI 复刻**：桌游 / 棋盘类界面里，卡牌、token、figure、房间 tile、角色板等承载物必须优先使用真实素材或同对象真实裁片；如果缺某个正式前脸素材，只能诚实降级为真实背面 / 真实空态 / 同对象代用，不能用不相关 marker 假装“差不多像”。
- **实现必须量化对齐**：按目标稿实现时，必须把关键视觉结构转成可复查的几何指标，再写代码和测试。
- **复刻失败必须降级，不得堆装饰硬凑**：如果当前前端能力无法稳定复刻参考图的材质、角饰或复杂实体感，必须显式降级为“形似/气质参考”，重新以信息层级、控件尺寸、牌桌密度和交互锚点为验收项；不得继续叠边框、伪木纹、多层渐变和大阴影制造“像参考图”的错觉。
- **分区关系不是默认盒子语法**：设计稿里的左区、右区、底区、摘要区、帮助区，默认先理解为同一载体上的阅读责任区与落位关系，不是“一块区域就配一张带边框底板”。除非目标稿本身明确把该区画成独立面板，否则实现时不得机械加外框、底板和阴影把每区切开。
- **棋盘主对象不能被摘要区夺权**：当目标稿是牌桌 / 棋盘 / 地图构图时，玩家位置、怪物位置、房间对象等主事实默认仍应落在棋盘 / tile 上；右侧摘要、底部队友、hover 卡片只负责补充，不得把本来属于棋盘的对象搬去边栏常驻承载。
- **目标稿和问题标注图必须分开**：当同时存在 `artifacts/**` 下的目标图/参考图与用户在 `ui参考`、问题收集图里做过红框标注的截图时，前者才是设计真相源，后者只用于指出问题位点。禁止把带红框的标注图反过来当成目标稿，更禁止用它替代比例、装饰或内容语义的来源。

## 标准流程

1. **真实内容盘点**
   - 读取真实页面/组件代码、i18n 文案、交互入口和状态分支。
   - 写清哪些字段/按钮/状态允许出现在设计稿里。
   - 额外写清哪些对象的**主承载**必须在棋盘 / 地图 / 房间 tile 上，哪些只是辅助摘要；禁止在没确认承载语义前，先按“边栏看起来更整齐”重排对象。
   - 明确禁止项，例如第三方登录、协议勾选、Logo、帮助说明、营销文案、额外入口等，除非用户当轮明确要求新增。
   - 如果用户提供了带红框/箭头/圈选的参考图，红框本身就是验收信号的一部分，必须优先逐框核对；不能把它当成“只是示意”。若标注指出某个角标、分割线或背景块有问题，必须把对应区域单独命名并验证，不能只看整张图的整体感觉。若同一轮同时存在 `artifacts/**` 目标稿与 `ui参考` 问题标注图，必须先锁定目标稿，再用标注图定位问题，不能反过来。
   - 如果目标稿目录存在用户纠正覆盖账本、AI 审计、几何审计或历史版本裁定，先列出“必须保留 / 必须删除 / 不得改名 / 不得省略 / 必须可读”的条目，再实现。缺这张清单，不得把代码改动称为按设计稿实现。
   - 先做信息层级分类：结构锚点、主要动作、辅助上下文、可省略/低价值控件。主次关系只能用于调整注意力顺序，不能打破原本的结构平衡，也不能把低价值信息放大成视觉主角。
   - 辅助区域不能被弱化成空白。所谓次级只表示动作优先级较低，不表示信息密度、排版节奏和视觉收口可以缺失；详情页、说明区、上下文区仍必须完整、均衡、可读。
   - 对当前主流程没有明确贡献的控件，即使真实代码里存在，也不得默认画进生成稿；必须先判断是否必要。典型低价值控件包括重复统计、非必要筛选胶囊、解释型底部摘要、过大的推荐人数块等。
   - 区分“内容契约”和“旧载体版式”。读取真实 UI 是为了确认有哪些字段、状态、动作和信息职责，不是要求在新载体里一比一复制旧版空间关系。载体变化（例如从普通页改成书本）时，可以重排空间，但不能改写内容职责或凭空增删入口。
   - 载体变化时必须先重构布局网格。不要把旧页的左右/上下切分机械搬到新载体；必须基于内容模型重新决定模块分组、阅读路径、密度分布和视觉收口。平衡是构图结果，不是左右 50/50 填充，也不是强行保留旧实现的空洞区域。
- 如果目标稿属于单一棋盘、牌桌、地图、书页或整页海报式载体，必须先判断哪些信息只是“贴靠该载体的悬浮对象”。这类对象默认通过距离、对齐、密度和轻量高亮建立分区，不通过给每个区再套一层容器建立分区。
- 若某个页面同时存在悬浮球、调试 FAB 或其他与主构图无关的占位元素，默认验收时忽略其占位，不得因为它们给右下角或边缘留洞；只有用户明确点名要把该元素纳入设计稿时才算作构图对象。
- `betrayal` 这类桌游运行态不要跨游戏抄持有区语法；例如别的游戏的扇形持有区、歪斜卡叠、强旋转扇叶都不能直接拿来当本游戏默认布局。
- `betrayal` 这类桌游运行态也不要把房间板块或探索者周边对象卡片化：房间牌默认是桌面拼接对象，不是现代圆角内容卡；右下队友常驻态默认只保留头像 + 用户名，详情只进 hover / focus。
   - 同级导航 / tab 必须识别为同一组件语义。active tab 只能通过色重、字重、下划线、标记、底色等状态差异表达，禁止把同级 tab 画成一大一小、一个标题一个普通链接这类不同组件语法。

2. **生成目标稿**
   - prompt 必须把真实内容和禁止项写成硬约束。
   - prompt 必须明确“保留既有结构平衡”和“主次不等于重排版式”。例如左右书页、上下工具区、列表列宽等结构锚点，不得因强调某一动作而被任意放大或压低。
   - prompt 必须明确“内容参考不是版式复刻”。如果载体发生变化，要求生成稿保留内容关系和操作层级，同时适配新载体的空间约束。
   - prompt 必须要求“为新载体重构布局网格”：说明新的模块分组、阅读动线、密度节奏和每个区域如何收口。禁止只说“保持平衡”而不说明如何解决空白、拥挤或错位。
   - prompt 必须声明同级 tab 的一致视觉语法，避免 active tab 被画成大标题、其他 tab 被画成小链接。
   - 若背景会生成假数据、假游戏名或假状态，必须要求压暗/虚化到不可读，或改用真实截图/真实资产作为背景。
   - 生成后必须复看目标稿本体；若出现无中生有内容，不能进入实现，必须重生或改目标。

3. **目标稿几何量测**
   - 实现前必须量出目标稿关键元素的占屏比例和相对位置。
   - 最低量测项：
     - 主容器宽高占比；
     - 主容器中心点；
     - 关键按钮/输入框/分割线/标记相对主容器的位置；
     - 关键内部间距，例如标题到表单、字段之间、辅助链接到主按钮、主按钮到底部切换入口；
     - 若是弹窗或浮层，还要量背景主体是否仍可见。
   - 量测结果必须写入 `task_plan.md`、`findings.md` 或对应 `evidence/` 文档。

4. **实现与测试**
   - 代码实现必须围绕量测值收敛，禁止只凭肉眼“大概像”调整。
   - 对经过多轮纠正的目标稿，实现必须逐项落地纠正记录：用户点名保留的对象不得省略，已撤销的旧方案不得恢复，已批准的控件样式不得顺手改，规则术语不得被通用概念替换。
   - E2E 或等价脚本必须读取真实 DOM / 截图的关键几何值。
   - 固定构图 UI（弹窗、浮层、书页目录、卡牌特写、棋盘主面板）中，主容器宽高占比偏离目标稿超过约 10%，不得宣称“符合设计稿”。
   - 若 fixed-composition 弹窗/浮层有目标稿或同场景已有通用 modal 壳层，必须先复用同一套边框、角饰、标题/分割线、输入框和主按钮语法，再处理当前内容；**禁止**每个弹窗各自发明一套“差不多像”的变体。
   - fixed-composition 弹窗/浮层里的装饰元素必须“可命名、可计数、不可重复堆叠”：装饰层只要能清楚说明自己在扮演什么角色就可以保留，常见角色示例包括 backdrop / shadow、surface、border、accent line、corner ornament、divider accent，但这些只是示例，不是固定菜单；如果某一层灰色块、半透明矩形、线条或角标无法明确归类为其中一种角色，就应视为多余装饰而不是“再保留看看”。同一边、同一轴向上不得同时出现两套意义相近的装饰层，尤其禁止再叠一层既不像遮罩也不像边框的灰框。
   - 角饰、分割线这类强识别装饰必须按目标稿做语法核对，而不是机械镜像：有些参考稿的角饰本身就可能非对称，允许左右或上下不完全一致，但必须属于同一视觉家族，并在位置、留白、线条重量、折角关系上与目标稿一致。若用户在一个角上标了红框，必须顺带检查同组对位元素是否也符合目标稿语法，不能只修被框住的一侧。
   - 若 fixed-composition 弹窗/浮层在低高度视口下出现字段缺失、按钮挤出或内容裁剪，默认修法先落在共享壳层内的内部节奏压缩、局部滚动、紧凑分支排版；“做成近乎全屏”只是常见错误症状，不是可复用规范本体。除非目标稿本来就是全屏弹层，或用户当轮明确要求改成全屏路线。
   - 弹窗/表单类 UI 还必须量内部节奏：不能只量外框。若辅助链接到主按钮、标题到输入区、按钮到底部切换入口等关键间距明显偏离目标稿，外框比例正确也不得收口。
   - 弹窗/表单类 UI 遇到受限视口时，还必须单独量“内容恢复”和“容器未异化”两类指标：前者包括关键字段、辅助链接、主按钮是否都在真实可视区；后者包括主容器中心点、边距和宽高占比是否仍保持原载体语义，而不是被放大成另一种近全屏组件。
     - 对于书页、左右分栏、详情页这类支持性区域，还必须量内容占位和空白占比；如果有效内容只压在一条窄带里，说明网格没重建好，不能靠“外框对了”收口。
     - 对于列表/表格区域，还必须量行高、缩略图尺寸、操作按钮尺寸、表格起始位置和列分割节奏；不能只因为行数据存在就接受“小而淡的列表”。
   - 对于主操作和导航入口，还必须量高度、宽度占比、字号、位置、装饰重量和可点击热区；“轻量”只能降低装饰重量，不能把返回、创建、加入、确认等真实动作压成小标签或页眉装饰。
   - 若目标稿、当前截图和实现运行在不同分辨率，主操作/导航入口必须按书页、弹窗或主容器比例归一化量测。禁止把目标稿里随载体放大的按钮实现成固定 px 小控件，再用“高度超过触控下限”或“字段存在”通过验收。
   - 动作控件门禁必须先区分动作类型再设目标区间：创建、确认、加入等主操作要验证可见按钮承载；返回、关闭、回目录等导航入口若目标稿是透明/文本式，就要验证背景透明、无误加边框、字号、热区和位置。高度、宽度占比、字号、装饰重量、与相邻内容的间距都要进入证据；只设一个很低的 `> min` 下限不够。

5. **截图复看与证据**
   - 必须打开最新截图本体，不能只看测试断言。
   - 必须制作同尺度并排图或局部裁图对照，且对照图必须覆盖本轮被指出的问题区域。只看记忆中的设计稿不算复看。
   - 若存在纠正账本或用户标注，视觉 verdict 必须逐项回答这些条目在实现截图中是否仍成立；不得只写“整体接近目标稿”。
   - 必须给出视觉 verdict：达到 / 未达到、具体差异、下一步修改项。若 verdict 未达标，必须继续迭代，不得用“比上一版好”收口。
   - 证据文档必须同时写：
     - 目标稿量测值；
     - 当前实现量测值；
     - 肉眼看到的具体差异；
     - 是否达到本轮验收标准。
   - 如果截图文件名被复用，必须记录 `LastWriteTime` 或重新生成带新后缀的截图，避免查看器缓存导致误判。

## 禁止行为

- 禁止只检查字段、按钮和文案正确，就宣称“符合设计稿”。
- 禁止只照最后一张设计图的大概布局实现，却漏掉用户纠正过的元素、规则命名、隐藏信息、骰子/token、公开归档、分页样式或已撤销旧方案。
- 禁止把“比上一版好”偷换成“已达标”。
- 禁止把目标稿里的主容器比例缩小后，用“移动端紧凑”解释，除非用户明确要求压缩。
- 禁止把“不要接近全屏”误写成规范本体。真正的不变量是：实现必须回到目标稿和同类通用壳层的几何与组件语法；若低高度视口出问题，就先在共享壳层内收口，而不是为单个弹窗另起一套风格。
- 禁止截图里看不到目标对象本体，还用它作为收口证据。
- 禁止把“主次”理解成打破既有左右/上下结构平衡，或把辅助信息做得比原版更大、更重。
- 禁止把主操作或导航入口缩成装饰。创建、加入、确认等主操作必须保留清晰按钮语义；返回、关闭、回目录等导航入口必须按目标稿语义处理，目标稿是透明轻量导航时不得强加按钮背景。所有动作都必须有可读字号和移动端可点热区，不能只因为页面是书本风格就把真实操作压到页眉角落的小块里。
- 禁止用固定像素按钮冒充“已按设计稿缩放”。如果书本/弹窗整体按横屏画布放大，主操作和返回入口也必须随主容器比例放大；否则即使满足 44px 触控底线，也仍然是视觉不达标。比例放大不等于一律加背景，必须保持参考稿里的主操作/轻量导航分工。
- 禁止把辅助区域做空、做散或缺少视觉收口；左右页/上下区都必须各自成立。
- 禁止把非必要控件画成默认内容，尤其是不会直接推动当前主流程的筛选按钮、重复统计、底部说明、推荐人数放大块。
- 禁止把“看实际内容”误解成“照搬旧版布局”。内容职责必须继承，空间组织必须适配当前载体。
- 禁止把“左右平衡”误解成机械 50/50 填充或保留旧版分区；新载体必须先重构布局网格，再谈平衡。
- 禁止把“区域划分”误解成“每个区域都要有独立边框、底板、圆角盒子和阴影”。若目标稿主要依靠同一画布内的落位关系成立，实现也必须优先用落位关系成立。
- 禁止同级 tab 一大一小、不同基线或不同组件语法；active 态不能破坏 tab 组的一致性。
- 禁止把“生图完成”当成“实现完成”。生图只负责产生目标稿；实现验收必须由本流程承担，至少包含真实截图、同尺度并排图或局部裁图、视觉 verdict 和未达标继续迭代。
