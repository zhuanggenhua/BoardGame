# 共享层重构与语义回退防护

> **触发条件**：修改共享工具、共享状态结构、共享 helper、共享门禁、共享 transport / watchdog / recovery / flow / interaction / response-window 逻辑，或用户明确质疑“重构为什么改坏功能”“为什么通用化后行为变了”时必读。

## “跨游戏公共领域”的定义与准入

- 本文所说的“跨游戏公共领域”，不是某个目录名称，而是满足以下任一条件的代码、配置或资源：被两个或以上游戏/页面实际消费；位于共享引擎或共享基础设施中；或会同时影响多个游戏的传输、布局、动画、交互、回合推进、恢复和测试桥链路。单个游戏目录内、且没有被其他消费者引用的实现，不自动属于公共领域。
- 单游戏反馈一旦准备修改跨游戏公共领域，动手前必须列出真实消费者矩阵：每个游戏/页面的入口、使用的默认或特化路径、用户可观察行为，以及本次改动不会改变的语义。只看当前改动文件、只跑一个游戏或只依赖 PR 合并成功，不能证明公共领域改动安全。
- 公共默认只有在输入、拒绝条件、中间状态、生命周期、时序、回退顺序和最终可观察结果都等价时才能修改；存在一项语义差异时，优先保留或迁移到游戏级/阶段级特化入口，不得把单游戏需求提升为共享默认。
- 公共领域改动必须绑定最窄跨消费者回归：至少覆盖一个共享默认消费者、一个特化/override 消费者、一个拒绝或异常路径，以及用户反馈对应的原始失败位点。没有这些证据时只能继续定位或记录风险，不能宣称“公共层已修复”。
- 合并 PR、改提交历史或看到公共测试通过，只能证明对应提交/测试覆盖的事实，不能证明未覆盖的跨游戏消费者行为等价。若发现公共领域改动来自误通用化或语义回退，应先恢复正确职责归属，再决定是否保留共享抽象。

---

## 先说清什么叫“回退”

这里的**回退**不是指 `git revert` 或代码回滚。

这里说的“语义回退”是指：

- 原来已经按某个游戏/某类流程的**真实业务语义**处理，后来被重构成“看起来更通用”的默认逻辑；
- 原来已经有一条专门兜底链路，后来被简化成更粗的共享 fallback；
- 原来已经明确区分了多类消费者，后来被合并成“一套通用 current player / 通用 response / 通用 helper”。

典型形态：

- 把“当前真实操作者”回退成“通用当前回合玩家”；
- 把“先收口隐藏交互，再决定是否跳过响应”回退成“先发通用跳过响应命令”；
- 把“游戏级 override”回退成“共享默认值”；
- 把“已验证成立的旧语义”回退成“我觉得更统一的写法”。

**一句话**：只要重构后用户可观察行为变了，而这次变更又没有被明确声明为需求变更，那就是这里说的“回退”。

---

## 核心不变量

- **重构默认不得改功能（强制）**：只要任务名、提交口径、用户授权里说的是“重构 / 收口 / 清理 / 通用化 / 对齐 / 抽象”，默认目标就是**保持既有行为不变**。除非用户明确批准改行为，或需求/规格明确要求变更，否则不得把行为变化夹带进重构。
- **共享默认值只能覆盖“真的相同”的消费者（强制）**：两个入口共用同一份数据结构，不等于它们共用同一套语义。只要当前操作者、响应顺序、隐藏交互、阶段推进、清理时机、fallback 命令有一项不同，就不得强行并成同一条默认逻辑。
- **游戏级特化不是代码味道本身（强制）**：如果某条游戏级 helper / override 承载的正是该游戏的真实语义，就不能为了“更通用”把它删掉。需要消灭的是重复，不是语义差异。
- **旧实现不是装饰品（强制）**：重构前必须先回答“旧实现到底在保护什么行为”。没回答这个问题前，不得删旧分支、并共享 helper、改 fallback 顺序。
- **共享状态不变量必须只有一个解析 helper（强制）**：同一个运行时不变量一旦被两个以上消费者读取或判断，例如 AI 决策、watchdog、手动恢复、UI 门禁、transport 兜底同时依赖同一组状态字段，就必须先抽成共享 selector/helper，返回带现实语义的结构化结果。各消费者只能消费该 helper 结果，禁止各自重复拆字段、重复推当前操作者、重复判断锁定关系、重复拼 fallback 条件。第二个消费者出现时就是抽 helper 的触发点，不能等第三处回归后再收口。

## 面向一百个游戏的执行口径

不是每次重构都去手工测 100 个游戏。

正确做法是：

1. **先列消费者全集**
   - 列出这段共享逻辑当前服务哪些游戏、哪些阶段、哪些交互家族、哪些服务端入口。
2. **再分语义家族**
   - 例如：`当前操作者判定`、`response-window 收口`、`隐藏交互优先级`、`通用 fallback advance`、`display-only 残留清理`。
3. **每个语义家族至少挑 1 条代表链**
   - 代表链必须能证明这一家族最关键的不变量。
4. **对有 override 的家族强制补专门断言**
   - 只要某游戏没有走共享默认，而是走了 override / 特化 helper，就必须有 1 条测试或等价证据证明这条 override 仍然生效。

**禁止行为**：

- 禁止因为“游戏太多测不过来”，就退化成只看改动文件是否能过。
- 禁止把“server.test.ts 很大、跑过了部分”当成“共享层安全”的证明。
- 禁止只测共享 happy path，不测 override 家族。

## 重构前必须锁定的四件事

### 1. 旧语义清单

至少写清：

- 当前这段逻辑在保护什么现实行为；
- 哪些行为是共享默认；
- 哪些行为是游戏级/阶段级/交互级特化；
- 哪些 fallback 顺序不能变。

### 2. 消费者矩阵

至少列出：

- 使用该共享逻辑的游戏/模块；
- 每个消费者是否走默认值；
- 是否存在 override / 特化 helper；
- 若 override 被删掉，会坏哪条真实链路。

### 3. 等价性判断

在把特化逻辑并回共享前，必须先证明：

- 输入条件等价；
- 中间态等价；
- 拒绝条件等价；
- fallback 顺序等价；
- 最终用户可观察结果等价。

五项缺任一项，不得宣称“可以收口到共享默认”。

### 4. 最窄保护测试

重构前必须先确认已有哪几条测试在锁这段语义；如果没有，就先补最窄测试，再动共享实现。

## 强制门禁

### A. 通用 helper 替换门禁

- **触发条件**：把特化 helper、override、分支判断替换成共享 helper / 默认逻辑。
- **禁止行为**：只因为名字更统一、调用点更少、看起来能复用，就删掉特化分支。
- **最低证据**：
  - 旧 helper 保护的真实语义说明；
  - 新 helper 如何覆盖该语义；
  - 至少 1 条代表性回归测试。

### B. fallback 顺序改写门禁

- **触发条件**：调整 hidden interaction、visible interaction、response window、force command、advance phase、cancel/skip/respond 的优先顺序。
- **禁止行为**：未经证明就把“先收口 A 再 fallback B”改成“直接走 B”。
- **最低证据**：
  - 旧顺序图；
  - 新顺序图；
  - 至少 1 条“旧顺序保护的异常场景”回归测试。

### C. 当前操作者语义门禁

- **触发条件**：修改 current player / active player / responder / defender / current operator 相关 helper。
- **禁止行为**：把“真实操作者”偷换成“通用当前回合玩家”，或把游戏级 resolve helper 绕回共享默认。
- **transport / provider 专项红线（强制）**：一旦涉及命令派发、socket payload、local provider 自动注入字段、教程 AI override、测试桥 payload 元字段，必须先锁定“谁是命令执行者”的唯一真相源。`当前本地视角玩家`、`教程指定执行者`、`socket 已认证玩家` 只能是不同来源的候选输入，不能在 `local/server/provider` 各写一份独立优先级，更不能让本地视角字段串进在线业务入口。
- **测试桥专项红线（强制）**：`TestHarness` / 调试桥如果已经有正式的 `command.playerId`、状态注入入口或服务端 `/test` 注入入口，就不得再额外借用 `__tutorialPlayerId`、`__internalPlayerId` 之类 payload 元字段表达“我要代哪个玩家发命令”。否则就是把“测试壳便捷字段”重新抬成业务候选真相。
- **最低证据**：
  - 哪些场景当前操作者不等于主动回合玩家；
  - 每类场景的代表测试；
  - 共享 helper 与游戏级 helper 的职责边界。
  - 若修改 transport / provider：必须额外写清 `本地视角玩家`、`命令执行者`、`教程指定执行者` 各自的现实含义、唯一解析入口，以及哪些字段只允许停留在本地壳层。

### D. 状态真相源迁移的玩家入口与工具消费者门禁

- **触发条件**：迁移、统一、替换或收口会被 UI、调试工具、测试夹具、AI 或命令处理读取的状态真相源，例如把旧字段迁入当前上下文、把多个状态合并为一个寄存器、保留兼容字段或新增内部恢复元数据。
- **先列消费者矩阵（强制）**：动手前必须逐项列出玩家可见入口、玩家可执行命令、调试/作弊写入入口、测试状态夹具、AI 读取入口和旧字段兼容读取。每项写清“旧读写源、迁移后的唯一读写源、是否仍允许保留兼容适配”。没有这张矩阵，不得宣称状态迁移完成。
- **玩家动作来源（强制）**：每个新增、保留或改名的玩家按钮、命令、确认入口和提示，都必须能追溯到规则、已验证旧行为、已批准设计或用户明确授权之一。内部恢复记录、迁移标记、快照、兼容字段、调试状态和审计数据只能服务实现；除非存在独立的规则来源，禁止把它们直接暴露为玩家按钮、玩家命令或流程文案。
- **唯一写入点（强制）**：调试工具、测试夹具和正式 UI 若都在改同一现实对象，必须写入迁移后的正式真相源；仍需同步旧字段时，旧字段只能是明确标注的兼容适配，不能成为第二套可观察状态。禁止只改旧字段，再假设新 UI 会自行同步。
- **禁止行为**：
  - 禁止因为内部状态“可恢复 / 可回退 / 可定位”就新增“恢复 / 回到 / 结算”玩家按钮；
  - 禁止把内部命令先注册到命令表、再由 UI 寻找使用场景；
  - 禁止调试面板只修改迁移前数组或旧字段，导致玩家当前看到的对象不变；
  - 禁止用“功能能走完”替代检查旧按钮、旧命令、旧文案、旧测试标识是否已从玩家流程退出。
- **最低证据**：
  - 一条迁移后真实玩家流程，证明规则允许的按钮、文案和取消/确认语义不变；
  - 一条负向断言，证明没有规则来源的按钮、命令和测试标识不存在；
  - 一条调试或测试写入流程，证明它立即改变玩家实际看到的当前对象；
  - 对兼容字段仍保留的，每条写清正式真相源、同步方向和删除条件。

### E. 传输命令送达与恢复同步门禁

- **触发条件**：修改共享 `transport / provider` 的命令派发、全量同步、同步去重、应用恢复可见、自动重试、命令确认或 AI 尝试占用逻辑。
- **先锁四段现实结果**：必须分别说明`调用方发起命令`、`传输层实际接受并发出命令`、`服务端权威状态确认命令结果`、`调用方占用/重试状态释放`各由谁负责。四段不是同一件事；前一段发生不代表后一段已经发生。
- **唯一结果合同（强制）**：凡调用方会据此锁定 AI 尝试、关闭手动选择入口、停止重试或推进流程，命令派发接口必须明确返回“本次是否已被传输层接受”。同步中、断线、销毁或其它拒绝情形不得伪装成成功；调用方收到未送达结果后必须在同一轮释放占用或走唯一的恢复入口，不能等待与实际未送达命令无关的确认超时。
- **恢复同步语义（强制）**：应用从后台恢复、页面重新可见等恢复触发，不能被一个无法证明仍会完成的旧同步静默吞掉。若旧同步仍在进行，恢复链必须明确选择并证明以下之一：复用旧请求一定会在有界时间内给出权威结果；取消并重发；或发起可区分的强制刷新。不得只因“已有同步中”就跳过恢复动作。
- **禁止行为**：
  - 禁止把“调用了 `sendCommand`”当成“命令已送达”，再据此占住 AI / UI / retry 状态；
  - 禁止在同步中丢弃命令却不把拒绝结果交回调用方；
  - 禁止让手动操作桥、AI 自动调度、命令确认计时器各自保留一套释放 / 重试所有权；
  - 禁止把恢复可见当成普通手动刷新，若两者对同步中的请求有不同语义，必须在接口和测试中显式表达。
- **最低证据**：
  - 一条正常已同步后的命令发送链，证明旧默认行为未变；
  - 一条同步中命令被拒绝且调用方立即解除占用的链；
  - 一条恢复可见时旧同步仍进行的链，证明最终会重新获得权威状态；
  - 用户反馈对应的自动流程链，证明未送达不会阻塞后续选项、准备或其它自动动作。

### F. 共享层重构提交门禁

- **触发条件**：提交消息含“重构 / 收口 / 通用化 / 对齐 / 抽象 / cleanup”等。
- **禁止行为**：提交消息写成重构，实际却夹带功能改动，但不在消息和测试里显式交代。
- **最低证据**：
  - 提交说明里明确写“本次是否改变用户可观察行为”；
  - 若改变，必须写明变更对象、原因、批准来源；
  - 若不改变，必须列出本次保护行为的关键测试。

---

## 最低测试矩阵

修改共享 transport / watchdog / recovery / interaction / response-window 时，至少覆盖：

- 1 条共享默认 happy path；
- 1 条 override 场景；
- 1 条拒绝路径；
- 1 条 fallback 顺序场景；
- 1 条用户真实反馈对应的原始失败位点。

如果用户反馈是“只坏一部分 / 只坏防御方 / 只坏 hidden interaction / 只坏某一步”，测试也必须保留这种“部分坏”的症状形状；禁止只测“全流程能走通”。

---

## 文档与汇报口径

- 汇报“这是重构，不改功能”时，必须能说出本次保护了哪些旧语义。
- 汇报“可以合并到共享层”时，必须附消费者矩阵或等价性结论。
- 如果事故根因是“重构时把特化语义退回共享默认”，必须在 evidence 或审计文档里直接写明“发生了语义回退”，不要只写“某测试漏了”。

---

## 这条规则要拦住什么错误动作

这份文档存在的目的，就是在事故发生前直接拦住以下动作：

- “我先把这几个判断并成一个通用 helper，应该没区别”
- “这个 override 看起来多余，删掉让 shared 统一处理”
- “hidden interaction 太绕了，先直接 pass response”
- “现在有一套默认 current player，游戏特化就先不用了”
- “这是重构提交，不用专门补行为测试”

只要这几句话还可能顺利发生，说明规范还不够硬，必须继续补强。
