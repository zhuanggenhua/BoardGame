# 回归收口与漏审复盘

> 适用：用户反馈“以前好的现在坏了 / 审计漏了 / 为什么回归 / 这怎么又回来了 / 改了不该改的东西”，或本轮修复后需要解释为什么旧测试、旧审计、旧规范没有拦住问题。

## 落点

- 本文档属于 BoardGame 项目通用层，只写跨游戏回归处理和漏审复盘方法。
- 单游戏事故细节、具体卡牌结论、单次截图或规则裁定，不写入本文档；应下沉到该游戏 evidence、用户故事、专项 bug 文档或 `docs/games/<gameId>/...`。
- 全面审计仍走 `.spec/knowledge/standards/testing-audit.md`；本文档只管“修完后如何证明回归已收口、漏审原因已回代”。

## 回归处理顺序

### 开工闸门

只要用户说“以前 / 之前 / 一个月前 / 最近改坏 / 又坏了 / 回归 / 恢复原来 / 不该变”，或本轮修复会改变既有可见 UI、流程、锚点、布局、规则、数据或测试合同，先进入回归闸门；即使任务同时命中 UI、移动端、E2E、看图或普通 bug 修复，也必须先完成本节，再进入对应专项规范。

闸门最低输出一张回归锁定卡：

- 用户原始症状，保留数量、时间、入口、设备和空间关系等限定词。
- 最后正常证据；若尚未找到，明确标为“最后正常未锁定”。
- 首次变坏查找方式，例如旧截图、旧 evidence、`git log -S/-G`、`git blame` 或引入提交 diff。
- 禁止改变的旧行为、旧信息量、旧交互入口和旧测试合同。
- UI / 移动端回归还必须锁定最后正常的视觉尺寸、相对比例、承载量和可读性；不能只锁“元素存在 / 不重叠 / 能点击”。
- 原始失败位点与验收矩阵；UI / 移动端回归必须列 PC 对照、目标移动视口、压力态截图和会竞争空间的保护槽位。
- 固定构图 / `board-shell` 回归必须先判定旧行为是不是 PC 同构等比缩放；若是，修复默认恢复旧构图和旧比例，不得把移动端重排、单项摘要、减少可见项、压缩密度或隐藏保护槽位写成新期望。
- 若使用满载 / 压力态证明“不会挡住”，必须同时补同入口无压力常态截图；压力态只能证明容量边界，不能单独代表正常视觉密度。

最后正常证据未锁定前，不得新增替代 UI、替代流程、替代测试期望或 PASS 清单来定义“新的正确行为”。测试只能先记录当前失败或保护已锁定的旧行为；禁止把未经旧实现证明的新方案写成期望后再据此宣称回归已修复。若回归点涉及响应式缩放、字号、密度或槽位，让位方案必须证明屏幕上实际渲染后的对象仍接近最后正常尺寸和比例；不得把“更小但不挡住”写成通过条件。

1. **锁原始症状与正常路径**：回归专属的第一步是锁定用户原话中的数量、入口、操作者、阶段、对象和失败位点，并按同一真实玩家路径复现。通用的目标锁定、原话保真和“问题对象 / 真相源 / 入口环境 / 验收口径”要求，统一执行 [`conversation-handoff-target-lock`](conversation-handoff-target-lock.md) 与 [`system.md`](../../rules/system.md)；本文不再复制词表或需求拆解流程。
1.1. **正常路径优先（强制）**：默认把用户反馈视为正规玩家流程中的真实问题。只有来自同一入口、同一状态、同一操作者、同一失败位点和同构动作的反证，才允许把它降级为异常操作、未走完流程或环境差异；单测、状态注入、相邻入口、修复后成功或“元素存在”截图都不能承担这项反证。
1.2. **相近现象不得冒充原症状（强制）**：只复现到部分、相近或中间态时，必须明确标为“尚未复现原症状”，不得把数量级、显示缺失、空间关系或过程顺序改写成更窄的问题。显示缺失、最终可见结果和截图资格按 [`e2e-verification`](e2e-verification.md) 的同源证据规则判断。
1.3. **因果链先于归因（强制）**：归因前必须用证据串起 `玩家动作 -> 状态写入 -> 消费者/分支 -> 玩家可见结果或权威状态`。任一环节缺证据，只能报告缺口并继续取证，不能用猜测、相邻现象或中间状态补齐。
1.4. **代码链不完整就回真实入口（强制）**：读代码仍无法建立完整因果链时，回到用户原始入口或最近真实入口，跑最窄的正常端到端复现，并按事实标为“已复现原症状 / 未复现原症状 / 只复现到中间态 / 被环境或入口阻塞”。不得用状态跳点、测试夹具或替代 UI 冒充原始复现。
2. **先判定是不是回归，再写回归处理记录**：一旦用户表达“以前能用现在不能用 / 又坏了 / 回归 / 怀疑回归”，第一步不是改代码，而是确认它是否能被历史行为、旧测试、旧截图、旧 evidence 或用户明确记忆定义为回归。必须在本轮 evidence / progress / 对话记录中写清当前症状、用户原话、初始复现方式、首跑结果、是否判定为回归；尚未复现或尚未找到历史行为时，必须标为“待复现 / 待定性”。
2.1. **回归定义包含未授权变化（强制）**：回归不只等于“旧 bug 重现”。只要满足任一条件就按回归处理：① 原来正常、用户认可或历史证据通过的行为现在坏了；② 本轮或近期改动触碰了用户没有授权改变的 UI、流程、锚点、布局、规则、数据或测试合同；③ 为修 A 问题引入了 B 分支可见行为变化。此时默认目标是恢复最后正常行为，不是把新行为解释成“也能用”。
2.2. **历史同样异常时停止回归路径（强制）**：如果用户把问题描述为“回归 / 以前不是这样”，但当前历史代码、旧测试、旧截图、旧 evidence 或可复跑旧版本证明“以前也是同样行为 / 同样错误 / 没有最后正常版本”，必须立即停止按回归修复继续实施。汇报时必须说清：① 用户原始回归断言是什么；② 哪份历史证据证明旧版本同样如此；③ 因此当前不能按“恢复旧行为”收口；④ 问题可能是规则合同、产品预期、长期漏实现、测试基线错误或其它链路缺口，需要重新锁定问题对象、真相来源、目标入口和验收口径。没有用户明确授权，不得继续用“回归修复”名义改成新方案，也不得把旧错误当作 last-known-good。
3. **找最后正常证据**：优先找历史测试、evidence、截图、提交 diff 或用户故事；不能只凭印象说“以前是好的”。如果找不到，必须明确写“尚未找到最后正常证据”，并把这条不确定性作为风险点记录。
3.1. **最后正常证据不能来自已知 bug 版本（强制）**：如果用户已经指出某个当前实现、截图、提交、测试或 evidence 是错误版本、失败候选、bug 复现图或“不是正常版本”，它只能作为坏例证据，不能再被当作 last-known-good。继续往前找更早的历史代码、截图、evidence、用户故事或提交；找到的候选必须同时满足两点：① 没有包含用户当前指出的错误现象；② 没有用另一个已知错误替代原问题。若只能找到“较早但仍有同类 bug”的版本，必须标为“已知坏版本 / first-bad 候选”，不得据此实施恢复。
4. **找首次变坏范围**：必须使用 `git blame`、`git log -S/-G`、`git show` 或必要时 `git bisect`，定位引入提交、改动批次、共享 helper、录入合同变化或测试断言变化，并记录具体把哪条历史行为改坏了。禁止只凭当前代码猜根因后直接改。
4.1. **先 diff 引入提交，再决定修复**：对比最后正常版本、引入提交与当前版本的具体文件（例如 `git show <commit>:<file>` 或 `git diff <good> <bad> -- <file>`），先列出引入提交的关键 hunk，再提出根因假设；禁止“先假设→重写→再找证据”。
5. **判根因类型**：至少在 `数据/录入缺陷`、`单点实现缺陷`、`共享抽象缺陷`、`架构/时序/系统边界缺陷` 中选一类。
6. **先判是否误改真相源**：若原始症状来自 UI、教程、截图、视觉高亮、视角聚焦、点击路径或 E2E 稳定性，必须先检查本轮是否把表现层 / 测试控制问题反向改成了数据、规则、素材、区域、录入合同、玩家可见状态或测试基线变化。没有独立真相源证据时，这类改动必须判为跑偏，不能继续作为修复方向；随机或骰子结果的稳定方式回到 [`e2e-verification`](e2e-verification.md) 的“状态注入与玩家可见真相源”。
7. **再判是否替换正式交互载体**：若最后正常行为是点击正式对象本体、复用正式高亮或场景直选，必须先恢复这条主路径；禁止用按钮、圆球、编号、标牌、临时图层或隐藏锚点替代正式对象本体，除非用户明确批准改成交互降级。
8. **检查当前选择是否被旧快照覆盖**：若正式对象直选后还需要点规则按钮确认分支，按钮响应必须消费当前对象直选产生的 live 选择；旧 interaction 快照只能作为同一等待态续建的兜底，不能覆盖刚刚点选的地区、棋子、卡牌、基地或 token。
9. **检查是否用渲染兜底掩盖注入错误**：若教程、E2E 或截图验收依赖玩家视角、座位权限、手牌归属、暗棋或私有信息，必须先确认入口显式注入了正确视角。缺视角是测试入口/注入数据错误，不能用当前行动方、默认玩家、保守隐藏或显示全部背面等渲染兜底说成修复。
10. **回归恢复优先**：回归问题的默认修复不是重新设计、重画 UI、重做交互或换一套实现，而是找到最后正确版本，并把用户原本认可的行为恢复回来。动手前必须优先回查最后正常代码、截图、测试或 evidence；如果最后正常版本尚未锁定，只能继续定位或补证据，不得先造一个“看起来也能用”的新交互顶替旧行为。
10.1. **回归成立时默认还原错误 hunk（强制）**：修复方式默认是只还原或等价恢复引入提交中造成回归的 hunk，不顺手回滚无关改动。受项目 git 规则约束，未经用户确认不得执行 `git revert` / `git reset` / 强制 `git checkout`；需要还原时优先用手工最小补丁恢复正确行为。
10.2. **职责修复不得夹带视觉重设计（强制）**：如果最后正常证据表明 UI 外形、槽位、顺序、尺寸或空间关系本身已经被用户接受，而本轮回归只是组件职责、数据源、缺失态、资源入口或语义标签串用错误，修复只能替换错误职责入口或恢复错误 hunk，不得顺手改布局、改结构、合并面板、迁移信息条、调整视觉主次或“顺便优化”。这类额外视觉变化即使看起来更完整，也属于未授权回归扩大。若确实认为旧外形也需要改，必须先把“恢复旧行为”和“新视觉改版”拆成两个目标，先恢复旧行为并截图证明，再等用户明确批准改版。
10.3. **用户说“之前是对的”时必须停止新方案（强制）**：只要用户指出“之前不是这样 / 之前是对的 / 为什么 UI 变了 / 恢复原来”，当前任何非最后正常外形的新实现都必须立即降级为失败候选；不得继续用 E2E 绿灯、DOM 断言或“职责拆开了”维持通过结论。下一步只能是回查最后正常证据、恢复被误改的可见外形、重跑原始位点截图，并在 evidence 里写清哪些视觉变化被撤销。
10.4. **回归修复不得改成新方案（强制）**：除非用户当轮明确要求“改版 / 重新设计 / 换交互 / 采用新方案”，回归修复必须且只能围绕最后正常行为做最小恢复；不得把测量新锚点、新布局、新弹窗、新按钮、新 helper、新截图口径或新测试基线当作默认解法。若执行中已经做了新方案，必须先把它标为失败候选并撤掉，再恢复最后正常版本。
11. **最小修复**：默认恢复最后正常行为或修掉直接根因；禁止自创一套新逻辑冒充回归还原。只有同时满足以下条件，才允许偏离还原路径：① 找到明确用户故事、规则文档、卡面/规则书、已合并需求或用户当轮指令证明最后正常行为已经被业务替换；② 写清为什么不能直接还原引入提交；③ 获得用户确认或用户当轮已经明确要求采用新口径。否则一律按引入提交还原修复。
11.1. **结构修复升级条件**：在“还原引入提交错误 hunk / 恢复最后正常行为”目标下，优先选择最小变更面；只有 diff 无法定位或根因属于共享抽象缺陷时，才升级为结构修复，并说明结构修复如何等价恢复最后正常行为。
12. **红测 / 首跑失败必须保留为证据**：回归修复的首个失败用例、失败截图、失败状态快照或失败断言必须写入 evidence；最终绿测不得覆盖或删除首跑失败事实。若首跑失败暴露出与用户问题不同的新异常，必须新增“新异常归因”小节，说明它是修复目标的一部分、测试构造问题，还是同链路残余风险。
12.1. **不得用换场景绕过失败**：如果修复中的 E2E 因额外 prompt、reaction session、重复触发、异步队列等同链路异常失败，默认先当作潜在回归调查。只有证明该异常来自测试场景无关干扰或已有独立覆盖，并在 evidence 写清理由，才允许收窄场景；收窄后仍必须保留一条能证明用户原始问题成功路径的真实入口 E2E。
13. **补回归验证**：验证必须回到用户原始失败位点，不能只证明辅助现象变好了。UI 回归必须有能代表真实入口的运行验证和截图证据；引擎/规则回归必须有 GameTestRunner、单测、既有回归用例或等价状态断言。若问题涉及“写入点 -> 候选/高亮 -> 用户选择 -> validator/handler -> reducer 最终状态”，验证必须覆盖整链，不能只断言中间额度、prompt 或候选存在。
13.1. **正向 / 反向结果必须成对验证**：共享规则执行器新增或修复一个派生结果时，至少同时验证“规则声明该结果时会生成”和“规则未声明该结果时不会生成”。随机消费次数、事件 payload、UI 结果层和最终状态都属于同一回归合同；只证明正向结果出现，不能证明无结果对象没有被错误投掷或渲染。
13.1. **视觉尺寸验收看最终屏幕效果（强制）**：UI / 移动端回归涉及字号、按钮、阶段提示、token、手牌、面板或 HUD 密度时，必须同时检查屏幕上的实际矩形、最终可见字号或等价截图审计结果。元素存在、未缩放的 CSS 值、`transform` 前尺寸、点击热区达标和不相交，只能证明工程约束，不能证明旧视觉尺寸已经恢复。
13.2. **原始位点 E2E 不得替代**：端到端验收必须覆盖用户原话里的阶段、操作者、目标对象、入口和失败位点；具体证据资格与截图组规则统一按 [`e2e-verification`](e2e-verification.md) 执行。禁止用普通投掷、相邻对象、结算后单帧或新造交互截图顶替原始位点。
13.3. **已验证 UI 入口的最小还原例外（强制）**：如果回归修复只是把被误删的既有 UI 入口、`data-testid`、state 同步或 payload 字段等价恢复到最后正常实现，且已有历史 E2E / evidence 证明该入口曾走通过，本轮没有改变布局、样式目标、选择器语义、点击路径、路由或跨系统链路，则不得机械套用“UI 回归必须 E2E”。此时优先使用能直接证明恢复点的最窄验证：相关单测 / 集成测试、`eslint`、`typecheck` 或提交 hook。若最窄验证无法证明用户可触达入口，或本轮改动实际触及视觉 / 路径 / 选择器 / 浏览器专属行为，才升级到 E2E + 截图。
13.4. **代理按钮不得绕过当前交互合同（强制）**：当中间壳层、等待层、快捷按钮、悬浮条或其它 UI 代理控件代表当前 `simple-choice / reaction session / prompt` 执行“让过 / 跳过 / 完成 / 确认”时，修复与验证必须同时锁两件事：① 真实承接者是谁（当前交互还是旧并行命令）；② 代理按钮最终发出的 payload 是否与当前 live 交互合同一致。禁止只验证“按钮显示了 / 可以点 / dispatch 被调用了”，却不验证它命中的仍是当前交互；也禁止沿用旧命令旁路当前 live prompt。至少补 1 条失败用例直接断言：点击该代理按钮后，发出的命令类型与 `interactionId / optionId` 命中当前真实交互，而不是历史兼容命令。
13.5. **回归验证不等于新增阻断测试（强制）**：新增测试前必须先判必要性。若原问题可由 git 历史对照、现有测试、类型检查、截图 / evidence 或最窄运行验证覆盖，不得再新增同义阻断测试。小 bug、资源路径/素材语义、缺失提示、UI 外形恢复和频繁变化业务默认只做必要验证与证据留存；只有长期公开行为、复发风险高、且存在稳定 seam 时，才补新的回归测试。
14. **同类扩审**：按根因关键词、事件、状态字段、共享 helper、生命周期和同族对象横向搜索。
15. **规范回代**：复盘为什么旧测试、旧审计或旧规范没拦住；若是方法失守，按 [`spec-steward`](../../skills/spec-steward/SKILL.md) 判断是否改项目主源；若是单游戏规则答案，回写单游戏文档。规范是否更新不在本文重复定义。

## 漏审归因默认口径

漏审不能默认归因于“测试不够多”。先按下面顺序判断：

1. **真相源没锁**：录入合同缺失、冲突、状态错误，或实现拿旧文案当规则。
2. **审计对象没建全集**：只看了用户点名对象，没列基础版、升级版、变体、同名分支、共享 helper。
3. **证据停在中间态**：只看到了 prompt、候选、pending、按钮、日志，没有验证最终血量、资源、token、区域归属或阶段收口。
4. **测试层级错配**：把单游戏领域测试、组件测试或局部行为测试当成真实入口端到端验收；原始问题经过 Board、HUD、浏览器点击、响应窗口或截图画面消费时，却没有补对应 E2E / 截图证据。
5. **测试断言过窄**：只测 happy path、只测单状态、没测已有状态叠加、并存来源、低伤害/低资源等边界。
6. **旧测试已经失效**：测试仍在断言旧规则、旧文案或旧错误语义。
7. **共享抽象没扩审**：根因在共享消费、清理、时序、队列或状态字段，却只修了单个对象。
8. **表现层误改真相源**：画面、教程、截图或 E2E 路径异常被误判成数据、规则、素材、区域、录入合同或测试基线错误，并把新值写成长期合同。
9. **正式交互载体被替换**：原本应点地图地区、棋盘格、卡牌、角色、基地、token 等对象本体，却被按钮、圆球、编号、标牌、临时图层或隐藏锚点抢成主路径，导致截图或 E2E 看似可走但真实教程退化。
10. **当前选择被旧快照覆盖**：用户已经通过正式对象本体更新了目标，但后续规则按钮仍读取旧 interaction 快照，导致画面看似点了新目标，实际结算或教程截图仍沿用上一轮地区、棋子、卡牌、基地或 token。
11. **注入视角缺失被渲染兜底掩盖**：教程、E2E 或截图验收需要明确玩家视角，却没有注入 `playerID`、座位或 viewer identity，后续又靠组件 fallback、默认视角、保守隐藏或背面显示把画面做成“看起来没泄露信息”，实际掩盖了错误测试数据。
12. **回归被误当新需求**：用户说“以前是对的 / 之前不是这样 / 恢复原来 / 改了不该改的东西”，但执行时没有先找最后正确版本，而是新造 UI、交互、流程或 helper，导致原本正确的行为被替换成另一套方案。
13. **视觉回归被几何通过掩盖**：阶段条、HUD、token、手牌、提示或主按钮被缩到低可读状态，但验收只看“不重叠 / 不出屏 / 只有一个高亮 / 能点”，没有对照旧尺寸、承载量和玩家第一眼可读性。
14. **代表态冒充自然流程**：对象来源由 fixture、测试预置或内部状态替换产生时，按 [`e2e-verification`](e2e-verification.md) 降级为代表态 / 分段合同，不能用于原始反馈收口。
15. **规范落点错误**：把单游戏答案写成通用规则，或把通用判断方法留在一次性对话里。

## 同类扩审最低要求

修复 bug 后必须说明横向搜了什么，而不是只说“已检查”：

- **先定根因，再扩审**：必须先确认 bug 是由哪个事件类型、状态字段、调用模式、共享 reducer/handler/hook/system、阶段时序或 UI 消费链路导致，再据此横向搜索；禁止只按表面文案或单个卡牌名做浅层搜索。
- 同游戏同族对象：基础版、升级版、同名变体、相同骰型/图标/触发条件。
- 同游戏共享实现：reducer、handler、hook、selector、validator、UI 消费点。
- 引擎共享层：同一事件类型、状态字段、helper、生命周期钩子。
- 测试和证据：旧测试断言、evidence 表格、截图描述、文案合同。
- **推荐搜索维度**：根因关键词、事件 kind、payload 字段名、状态字段名、生命周期钩子名（如 `onPhaseEnter` / `onPhaseExit` / `afterEvents`）、共享 helper 名、同类描述语义。必要时组合 `rg` 多轮搜索，而不是一次搜不到就结束。
- **可选触发 / 响应窗口扩审**：若漏审点是“只验证到响应窗口生成，没验证提交后的执行和最终状态”，同类范围优先按正式触发注册展开，例如同游戏所有 `optional: true` 触发；每个对象至少判定有没有提交响应后的最终权威状态证据。仅有静态录入、注册存在、卡名引用、按钮出现或队列存在，只能算候选证据，不能算同类重审收口。
- **命中后的处理原则**：命中同类问题时，默认继续修到共享根因被消除，或明确写出“该命中点为何不受影响”的判定依据；禁止只挑当前用户提到的那一处修复。
- **交付口径**：修复总结必须说明“搜索了什么、覆盖到哪里、命中了什么、哪些已一并修复、哪些确认不受影响”。没有这部分，视为扩审未完成。

若扩审未完成，最终口径只能写“当前点位已修复，仍有残余扩审范围”，不得写“已收口”。

## 回归收口输出模板

最终汇报或 evidence 至少包含：

- 用户原始症状。
- 我的理解，以及证据与原始问题的第一次关联验收结论。
- 是否判定为回归，以及最后正常证据。
- 引入范围或疑似根因范围。
- bug 判定：是 bug、不是 bug、还是证据不足；不是 bug 时必须说明哪条同源证据证明当前行为符合规则或产品合同，不能只写“未复现”。
- 根因类型与为什么不是其它类型；是 bug 时必须写清 `玩家动作 -> 状态写入 -> 消费者或分支 -> 玩家可见结果或最终权威状态` 的原因链，缺失环节要明说。
- 修复策略是否恢复最后正常行为；若不是，依据是什么。
- 最后正确版本证据；如果没恢复最后正确版本，必须说明用户是否明确批准新方案。
- 验证命令、截图或状态断言。
- 第二次解决验收结论；如果尚未进入解决验收，明确写“未进入 / 阻塞”。
- 同类扩审范围、命中结果和未完成范围。
- 漏审复盘：旧测试/旧审计/旧规范为什么没挡住。
- 是否存在“表现层问题反向改真相源”的误判；如果存在，说明已恢复或仍需恢复的真相源范围。
- 规范回代：新增或更新到哪里；若不需要更新，说明原因。
