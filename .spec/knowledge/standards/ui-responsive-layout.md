# UI 双端与响应式布局规范

> 来源：从 `.spec/knowledge/standards/ui-ux.md` 无损拆出。本文档承载多端布局、参考分辨率、双端架构分层和单位选择规则；`ui-ux.md` 只保留入口摘要。

## 多端布局策略 (Multi-Device Layout Strategy)

- **双端并行，不是双份 UI**：默认只有一套 React UI 架构，通过 `manifest + runtime viewport + 终端能力探测 + layout preset` 做条件化分支；**禁止**为同一游戏长期维护两套互相漂移的 `DesktopBoard` / `MobileBoard`。
- **移动端优先继承 PC 视觉语言（强制）**：桌面版是同一游戏的视觉真相源。移动端适配必须尽量保持 PC 的色彩、边框、卡牌/房间/骰盘质感、按钮语气、选中描边、教程提示样式、对象层级和主要视觉关系；只允许因为屏幕、触控、安全区和方向限制做密度压缩、尺寸缩放、次要信息收纳、滚动/抽屉化或位置让位。禁止把“移动端重构”理解成另起一套视觉主题、另换一组材质、另造一套按钮/面板风格。
- **移动端临时弹窗 / 阻塞层默认 PC 同构（强制）**：事件牌、发现结果、投骰、prompt、确认框、教程浮层这类临时 UI，在移动端默认沿用 PC 的承载结构、周边 HUD 可见性和信息层级；只能在出现真实重叠、裁切、触控尺寸不足或安全区遮挡时，对该弹窗自身做最小尺寸、间距、换行、滚动或局部避让。禁止因为进入手机横屏就把横排选项改成竖排、把开放桌面叠层改成另一套实心弹窗、把 PC 同源行动栏 / 阶段 / 牌堆 / 角色 HUD 整体隐藏，或用“移动端更清爽”作为改布局理由。若确实要隐藏某个常驻 UI，必须逐项证明它与当前弹窗发生现实遮挡，并给出等价入口或阶段内不需要的理由。
- **临时弹窗验收必须逐项对照 PC（强制）**：凡触碰事件牌、投骰、prompt、确认框、教程浮层、发现/结算面板，移动端验收必须同一状态提供 PC 基线截图或等价 DOM 证据，并逐项裁决：弹窗承载、牌面/内容区、选项方向、骰盘/结果区、确认/关闭按钮、底部行动栏、角色/HUD、地图/牌桌是否保留 PC 语义。任何一级 UI 没有明确去向、弹窗视觉家族换掉、主 HUD 被整体隐藏、或主交互承载被替换且无必要性证明，一律判为不合格；不得用“能点 / 没溢出 / E2E passed”替代 PC 同构结论。
- **PC 同构通过必须使用当前 PC 基线（强制）**：PC 基线必须来自当前工作区、当前代码、同一路由、同一交互状态；历史截图、旧 worktree、旧端口、旧 evidence 只能作为参考，不能作为本轮通过依据。缺当前 PC 同状态基线时，最多只能说“移动端局部可用”，不得说“PC 同构通过 / 视觉合格”。用户已经看图判不合格后，新的通过结论必须来自晚于修复的新移动图和当前 PC 对照图。
- **移动端是否需要改布局必须由失败证据决定（强制）**：手机横屏、窄屏、触控端默认不是“另做移动布局”的理由。动手前必须先证明 PC 同源布局或同源承载在目标移动视口出现了具体失败，例如不可读、不可点、被安全区挡住、遮住主对象、主要信息溢出或真实流程无法完成；如果只是觉得“移动端应该不一样 / 更像移动端 / 更清爽”，一律不得改布局，只允许在同源布局上做尺寸、间距、安全区、滚动和触控命中区适配。
- **移动端改造不得改写 PC 基线（强制）**：移动端重构只能新增或条件化移动端布局分支，不得改变 PC 端既有布局语义、视觉样式、元素存在性、断点显示阈值、选中/可用描边、主按钮样式、教程提示位置或截图输出。凡是为了手机横屏隐藏/压缩/重排的 rail、dock、手牌、角色区、牌堆区、教程卡、按钮区，必须用明确的移动端布局条件隔离；桌面分支要回到改动前同源截图可对照的 DOM 与样式。
- **移动端默认保留 PC 同一交互承载（强制）**：移动端适配不是默认新建一套 `mobile dock`、移动按钮栏、移动手牌栏或移动专用选择器。若 PC 原有按钮、手牌、卡牌、房间、骰盘或提示承载只需要调整尺寸、位置、间距、安全区、滚动或触控命中区，就必须继续使用同一承载做条件样式适配；不得因为进入手机横屏就把 PC 承载隐藏，再另造一个“看起来更移动端”的重复承载。只有已经用截图、DOM 尺寸或真实交互证明 PC 原承载在移动端不可读、不可点、遮挡主对象或破坏流程时，才允许替换为移动专用承载。
- **移动端分页不得牺牲候选本体尺寸（强制）**：`每页 N 个` 只约束同一页的数据数量，不等于必须把 N 个候选全部压进一屏。角色、卡牌、基地、目标对象这类候选本体必须优先保持可读可点尺寸；空间不足时应沿用 PC 同源滚动/下滑、分栏减少、页内滚动或抽屉化，而不是缩小到看不清。验收必须证明候选本体可读、触控目标足够大、页码/翻页只占辅助空间。
- **新增移动专用承载必须先证明必要性（强制）**：任何新增 `mobile-*` 主交互承载前，必须写清三项证据：① PC 原承载在目标移动视口的具体失败表现；② 为什么只调样式/位置/尺寸/安全区不能解决；③ 新承载和旧承载的唯一可见关系。缺任一项，不得实施。验收时必须同时证明旧承载没有被无理由替换、没有双份可见、PC 截图未变化。
- **移动端改造必须带 PC 回归截图（强制）**：只要本轮改动触碰共享 Board、教程层、HUD、手牌/持有区、主动作栏、事件/骰子面板或响应式断点，验收必须同时提供同源 PC 对照截图或 DOM 断言。PC 对照优先使用该功能已有 evidence 的同一分辨率、同一路由、同一步用户链路；不能只拿移动端截图、移动端 E2E 或“桌面分支理论不命中”当作 PC 未回归证据。
- **移动端对照 PC 必须盘点信息去向（强制）**：PC 截图里的一级可见信息不能在移动端无声消失。移动端截图验收必须给每个 PC 一级区块一个明确去向：继续同源显示、压缩显示、贴边显示、滚动可达、抽屉/按钮入口可达、阶段内明确不需要。尤其是 PC 右侧牌堆/弃牌/队友栏、左侧角色与属性、底部主动作、当前持有区、当前阶段提示，不得只因为手机横屏空间紧就直接隐藏。没有去向说明的缺失项一律按验收失败处理。
- **用户看图判不合格时必须重审裁决（强制）**：如果用户指出“弹窗不一致 / UI 看不到 / 明显不合格 / 和 PC 不一致”，先撤回当前“通过”结论，把截图重新放回 PC/移动对照矩阵逐项核查；不得继续引用原 E2E 绿灯、局部 DOM 断言或“AI 已看图”维持合格判定。只有重新证明每个缺失项的去向、必要裁剪理由和同构关系后，才能再次收口。
- **PC 回归失败先收回外溢，不得继续调移动端（强制）**：如果 PC 截图出现“东西没了、样式变了、按钮/rail 消失、卡牌描边变形、教程卡位置变化、主区域尺度变化”，默认先判断为移动端改动外溢。必须先恢复 PC 原样式或把新逻辑隔离到移动端条件内，再继续移动端验收；不得把 PC 变化解释成“响应式自然变化”或用新的 PC 截图直接覆盖旧 evidence。
- **移动端可改信息架构，不可改视觉家族（强制）**：`board-shell` 不是“必须缩小 PC 桌面”的许可证，也不是“移动端另做一套风格”的许可证。探索地图、房间棋盘、骰盘、事件牌在移动端可以把主棋盘/牌面/骰盘放大为唯一主舞台，把手牌/持有物/动作贴边，把日志、牌堆、角色详情收纳；但这些对象的材质、边框、色调、圆角、高亮和按钮语气必须来自 PC 同一组件家族。
- **开放式地图 / 棋盘必须分 Scene 与 HUD 验收（强制）**：开放式 UI 不是把整张 PC 舞台 `scale-to-fit` 后留下黑边，也不是把背景拉满后顺手裁掉可交互对象。底图、地图纹理、远景装饰属于 Scene，可以用 `cover` 思路铺满并裁掉非关键边缘；玩家状态、轮盘、牌堆、手牌、动作按钮、关闭按钮、放大查看内容、阶段提示属于 HUD / 交互层，必须单独进入安全区并完整可读可点。验收时必须分别说明：① Scene 是否铺满且没有黑边 / 遮罩条补比例；② HUD 是否没有被上沿、下沿、刘海区、圆角区或裁切容器吃掉；③ 玩家当前需要操作的信息是否都有 PC 对应去向。三项缺一，不得判通过。
- **开放式适配不得用单一缩放公式收口（强制）**：地图类、房间类、探索类棋盘在手机横屏下默认按“Scene 铺满 + HUD 安全区重排 / 贴边 / 收纳”处理；禁止只用一条 `min(width/designWidth, height/designHeight)` 或一条 `cover scale` 同时决定底图和全部 UI。若使用 `cover` 消除黑边，必须同时给交互层建立独立锚点、inset 或 portal；否则一旦底图被裁，顶部轮盘、底部手牌、关闭按钮等也会跟着被裁，属于适配失败。
- **固定设计画布不是视觉边界（强制）**：`1920x1080`、`designWidth/designHeight`、舞台 scale 只表示“设计稿多大、HUD 和棋盘内容如何按比例换算”，不是页面外框。开放式地图 / 棋盘 / 牌桌必须按现有成熟实现处理：先用一个 `h-full w-full overflow-hidden` 的真实底图 / 桌面层铺满 viewport，再在里面放可缩放 / 可拖拽的地图内容层和独立 HUD 层。不得把设计画布实现成真实页面的最大宽高、居中小岛或外层裁切框；禁止在设计画布外补纯色、黑条、半透明遮罩条、模糊补丁或明显拼接边。
- **移动端对比 PC 必须先查“是否需要换承载”，再查重（强制）**：移动端继承 PC 视觉语言时，第一判断不是“移动端有没有一套自己的按钮”，而是 PC 原承载能否通过样式适配继续使用。能继续使用时，移动端必须沿用 PC 同一组主按钮/主交互对象；不能新增移动专用动作栏替代。只有必要性已证明且确实替换承载时，才进入查重：同一类动作面、同一组主按钮、同一块状态信息只能保留一个可见承载。禁止出现“PC 动作栏 + 移动动作栏同时可见”，也禁止把“只剩一组移动动作栏”误当成通过；如果 PC 原动作栏本可适配却被替换，仍然判失败。桌面右侧牌堆/角色/日志常驻栏若被收纳，原右栏也必须不可见，且必须证明收纳有必要。
- **移动端不能用“无重复”掩盖“少信息”（强制）**：验收顺序必须是先查缺失，再查重复，再查样式。只证明移动端没有双份 UI、主按钮贴底、PC 没被改坏，不足以证明移动端合格；如果 PC 有玩家决策所需信息而移动端没有等价显示或入口，仍然判失败。
- **禁止 PC 压缩冒充移动端，也禁止移动端换皮（强制）**：手机横屏验收不得只证明“横屏、按钮可见、没有溢出”。如果截图里仍能看到桌面多栏常驻、左右 rail 挤压主视区、底栏压住棋盘、主对象不是第一视觉焦点，必须判失败；如果移动端虽然可用，但按钮、面板、提示、持有物轨道看起来像另一套游戏皮肤，也必须判失败。验收断言必须覆盖移动端专用布局标记、桌面 rail 不参与布局、主舞台有效尺寸、动作栏贴边高度、PC 风格继承和截图 AI 目测通过。
- **固定牌桌错向必须继续可看可滚动（强制）**：`board-shell` / 固定牌桌在手机错误方向下，仍按同一张牌桌渲染，并通过横向/纵向滚动、非阻断方向提示、缩放或安全区让位解决可达性；不得切成全屏方向阻断页，不得为了截图整齐隐藏真实牌桌。
- **移动端是一等输入终端**：移动端不再只是“能打开就行”。凡是共享组件、共享交互、共享布局，只要预计会出现在移动端，就必须在方案阶段同时考虑安全区、触控命中区、长按/armed 等替代入口和方向约束。
- **宽限度约束 (Constraints)**：平台/网页 UI 通过 `max-w-7xl` 等容器限制内容延展，确保视觉焦点集中。

### 默认参考分辨率（强制）

- **PC 默认主参考分辨率固定为 `1920x1080`**。
  - 这是桌面端唯一默认权威基线；未特别说明时，桌面截图、桌面布局对照、PC 同构验收都优先以此为准。
  - 这是验收视口和设计稿尺寸，不是页面最大宽度；宽于或窄于该尺寸的真实视口必须由 Scene 铺满、HUD 锚定或布局让位承接，不能露出固定舞台外框。
  - 不再默认混用 `1440x900`、`1600x900`、`1366x768` 作为并列基线；这些尺寸若要使用，必须说明只是补充排查，不是主裁决口径。
- **移动端默认主参考分辨率固定为 `375x812`**。
  - 这是移动端唯一默认权威基线；未特别说明时，移动端截图、适配验收、对照证据默认使用它。
  - 若某游戏主打手机横屏或老板明确指定横屏分辨率，再按当轮任务单独声明，不在项目全局规范里默认保留第二套移动端主基线。

### 参考分辨率使用规则（强制）

- 先看该界面的**主参考分辨率**结果，再决定布局是否成立。
- 当老板明确指定分辨率（如 `1920x1080`）时，以老板指定为准；未指定时，按本节默认值执行。
- 正式 E2E 的职责是验证行为，不是服务某次截图取证。**特定分辨率截图需求应走独立取证路径，不得为了出图把正式 E2E 改写成专用脚本。**
- **开放式移动横屏截图必须同时带 PC 主基线（强制）**：涉及开放式地图 / 棋盘的移动横屏适配，验收截图至少包含 PC `1920x1080` 主基线、移动横屏主状态、移动横屏关键 overlay / 放大态。PC 图用于盘点视觉语言和一级信息，移动图用于证明无黑边、无遮罩条补比例、Scene 铺满、HUD 完整。若只生成移动图，或 PC 图不是 `1920x1080` 且未说明只是补充排查，不得作为正式验收。

- **响应式策略指南 (Responsive Strategy Guidelines)**：
    - **信息交互层 (UI & HUD)**：
        - **场景**：大厅卡片、侧边栏、模态框、文字阅读区。
        - **建议**：**稳定性优先**。推荐使用标准 `rem`，必要时配合 `clamp()` 锁定物理最小值（12px/14px），保证全环境可读。**不要**用裸 `vw` 作为正文、按钮文案、常规表单控件的主字号来源。
    - **沉浸视效层 (Immersive & Board)**：
        - **场景**：游戏棋盘、全屏背景、核心对战区域。
        - **建议**：**比例优先**。优先使用 `aspect-ratio`、`%`、壳层统一 `scale(...)`、以及运行时 viewport 变量；`vw/vh` 只能作为局部比例辅助单位，**不再推荐**作为固定构图类界面的主适配手段。
    - **布局流动层 (Layout Flow)**：
        - **场景**：列表网格、工具栏排列。
        - **建议**：**内容驱动**。利用 Flex/Grid 的自然流特性（如自动填充、自动换行）来适配屏幕宽度，而非依赖硬编码的断点控制。

### 双端 UI 架构分层（强制）

- **L1 页面路由层**：负责路由、页面语义、`Suspense fallback`、错误兜底、方向提示、运行时环境门禁；不直接承担某个游戏的细部布局。
  - 对局页统一通过 `getGamePageDataAttributes()` / `syncGamePageDocumentAttributes()` 输出 `data-game-page`、`data-mobile-profile`、`data-mobile-layout-preset` 等属性。
- **L2 页面壳层 / 运行时层**：负责真实 viewport、安全区、键盘 inset、终端能力探测、根级 CSS 变量同步。
  - 统一使用 `useRuntimeViewport`、统一 runtime helper，禁止页面各自重算一套 viewport 和原生壳判断。
- **L3 游戏壳层（layout shell）**：负责 `MobileBoardShell`、top rail、side dock、bottom rail、缩放舞台、board-shell / portrait-simple / map-shell preset。
  - 这层解决“桌面结构如何映射到移动端”，不承载游戏规则。
- **L4 游戏画布层（scene / board）**：负责棋盘、卡牌、角色区、日志区、手牌区等游戏内容本身。
  - Board 组件默认只关心壳内内容区域，不再直接读取原始视口高度去自建第二套移动壳。
- **L5 交互适配层（interaction adapter）**：负责 hover 替代、long press、armed activation、drag fallback、触控命中区增强。
  - 这层只能改变“如何触发”，不能改变“是否可用”的业务真值。
- **L6 原生壳边界层**：负责 `Capacitor`/Android/iOS 专属能力、返回桥、更新检查、原生包逻辑。
  - 原生壳行为必须停留在统一 helper 与 App shell 层，不能泄漏到共享业务 UI。

### 双端设计裁决（强制）

- **先判断界面类型，再决定适配手法**：
  - 固定构图类：优先等比缩放 + 局部让位；同一牌桌内的顶栏、手牌、主按钮、分数和中央区不得被当成可自由重排的流式工具栏。
  - 流式信息类：优先响应式重排 + 抽屉/标签页/单列化。
- **允许设备差异，不允许语义分叉**：
  - 可以桌面 `hover`、移动 `long press`。
  - 可以桌面单击、移动 armed 后二击。
  - 不可以桌面和移动分别维护两份 `canUse / isSelectable / showUsed`。
- **缩放舞台只能有一层主真值**：如果页面已经位于 `board-shell` 统一缩放容器内，页面内部默认禁止再套第二层整页 scale-to-fit。
- **全屏底图层优先于缩放舞台（强制）**：召唤师战争、山屋惊魂这类成熟牌桌/地图页的有效模式是“全屏容器先铺底，内容层再缩放/拖拽”。缩放舞台只能管理棋盘内容、地图贴图、命中区和 HUD 的相对关系，不能承担页面背景边界。若需要暗角、左右渐隐或压场，只能作为覆盖在真实底图上的渐变效果，不能用纯色块替代底图外侧。
- **固定牌桌的中心轴与尺度链必须单一来源（强制）**：
  - 顶栏、中央牌河、手牌区、主动作等若属于同一套 live 牌桌，必须共享同一条几何中线与同一套缩放来源。
  - 禁止手牌区、中央牌区、按钮区分别使用互不相关的 `vw` 宽度公式、绝对定位魔数或额外 `transform scale` 去拼出“截图里像是居中”的结果。
  - 只要改动影响其中任一块的宽度、间距或锚点，就必须回到真实宽桌面与真实窄桌面同时验证中线、单卡宽高和主动作落点。
- **HUD 与 Scene 分治**：棋盘/地图/战区优先保持固定几何关系；日志、帮助、设置、按钮轨道可以让位、悬浮或抽屉化。
- **开放式 Scene 与主 HUD 不得共享裁切容器（强制）**：当 Scene 为消除黑边采用铺满裁切时，HUD / Overlay 不能继续作为同一被裁切节点的子元素参与裁边；必须提升到不被 Scene 裁切的层级，或用独立安全区变量修正位置。若图面出现上下横条、轮盘露半截、关闭按钮贴出屏幕、手牌被底边吃掉，默认先判为 Scene 与 HUD 没有分层，而不是继续微调背景比例。
- **开放式手机横屏主手牌必须贴底（强制）**：手牌、持有物栏、主动作 dock 这类底部主 HUD 默认贴住真实视口底边，不得用固定底部留白、黑边、遮罩条或“舒适余量”把主内容抬高。若目标设备存在刘海、圆角、系统手势区等真实安全区风险，只能用实际安全区变量或交互层 hit area 处理，并且必须同时证明没有重新制造底部黑条；禁止用统一固定 inset 代替开放式贴底。
- **主交互空间利用优先（强制）**：桌面和移动端的手牌、持有物栏、主动作 dock、底部 prompt、当前候选区都不允许留下无语义死空间。布局需要留边时必须能对应到真实安全区、可点击命中区、滚动边界、对象阴影/放大溢出或相邻 HUD 避让；否则应压缩 wrapper padding、贴近容器边界，把空间还给牌面、棋盘和当前操作对象。
- **贴底 HUD 优先覆盖，不优先占流（强制）**：固定牌桌里的手牌和主动作如果只是玩家当前操作层，默认不应作为普通 flex/grid 行占掉中央区高度；优先用覆盖层、绝对定位或独立 HUD 层贴底，让中央棋盘/牌河/筹码区的布局高度延伸到其背后。只有底部区域本身是独立信息面板、会滚动、会遮挡中央关键对象或有明确安全区冲突时，才允许作为正常流高度参与排版，并必须在截图里说明它占用高度的现实用途。
- **主 HUD 与次要 HUD 分治**：回合按钮、确认按钮、分数、阶段提示、手牌操作这类主 HUD 如果已经嵌在固定牌桌构图里，默认跟随牌桌统一缩放；只有日志、帮助、设置、聊天、反馈等次要 HUD 才默认允许移动端让位、悬浮或抽屉化。
- **端能力判断只进边界层**：`pointer: coarse`、`Capacitor.isNativePlatform()`、`window.androidBridge` 这类探测不应散落在业务组件中，必须先进入统一 helper 或 Hook。

### 单位选择规则（强制）

- **文本、按钮、表单、日志、常规 HUD**：
  - 优先 `rem`
  - 必要时 `clamp(minRem, preferred, maxRem)`
  - 原因：可读性稳定，桌面与移动不会随 viewport 宽度一起失真
- **固定构图类主布局**：
  - 主换算方案是 `px` 设计画布 + 外层统一等比 `scale`
  - 标准公式：`scale = min(availableWidth / designWidth, availableHeight / designHeight)`，只用于 HUD、固定栏位、命中区和棋盘内容的尺寸换算
  - 原因：保持几何关系，避免局部元素各自按 `vw/vh` 漂移；但它不是 Scene 层铺底公式，也不是页面外框宽高
  - 横屏常由高度约束、竖屏常由宽度约束，只能作为统一公式的计算结果，不得拆成“横屏 `vh`、竖屏 `vw`”两套主单位
- **壳层高度 / 移动端可视高度**：
  - 优先运行时同步的 viewport 变量
  - 在 `board-shell` 内禁止直接依赖裸 `100vh/100dvh`
- **局部比例型装饰尺寸**：
  - 可少量使用 `vw` / `vh`
  - 例如纯视觉徽章、背景装饰、局部舞台内的相对偏移
  - 前提：它不承担可读性和主布局稳定性的职责
- **触控命中区**：
  - 优先 `px/rem` 下限，例如 `44px`
  - 不要用 `vw` 让命中区跟着屏幕宽度忽大忽小
  - 图标按钮、关闭按钮、折叠按钮、页角返回这类小图标控件，验收看**真实可点热区**，不是只看图标本体大小；热区最低 `44px × 44px`，移动端优先按 `48px × 48px` 设计，图标本体可以更小但必须有 padding 扩大命中区。
  - 任何响应式压缩都不得把确认、关闭、返回、展开、菜单、页码、帮助这类可点击控件压到触控底线以下；如果视觉上需要轻量图标，必须用不可见热区或按钮盒子保留可点面积。
- **历史 `vw` 代码处理原则**：
  - 桌面固定构图下如果效果稳定，可暂时保留
  - 但新增代码不应再把裸 `vw` 当成默认主单位
  - 一旦该区域进入 `board-shell`、双端同构或移动端主链路，应优先迁移到“设计宽度 + 统一缩放”或 `clamp/rem`
