# E2E 与截图验收规范

本文件规定真实浏览器 E2E 和截图证据如何证明玩家可用合同。它不替代规则录入、素材 intake、UI 图面审计或用户开图；图面审计回到 [`ui-change-gates`](ui-change-gates.md) 与项目 [`ui-audit-loop`](../../skills/ui-audit-loop/SKILL.md)，用户开图回到 [`show-image-to-user`](../../skills/show-image-to-user/SKILL.md)。

## 适用边界

- 标准游戏 E2E 使用项目 Playwright runtime、fixture / 专用测试模式、最近真实入口和状态注入 / 代表态。
- 明确游戏目标的 `e2e/<gameId>/...` 目标，启动测试服务前必须按游戏补齐本地缺失运行时素材；`--list`、共享目录和无明确游戏目标不得自动拉全站素材。
- 真实开房链路只在要证明房间创建、加入、座位、权限、联机同步、`setupData -> runtime` 或多端同步时使用。
- `dev:lite` 只能证明快速本地体验，不证明 API、认证、社交、后台、持久化或浏览器级端到端。
- 外部数据库只在认证、保存恢复、排行榜、后台、真实持久化兼容性等目标里成为验收对象；标准游戏 E2E 默认内存游戏服即可。

## 入口分层

- **最近真实入口优先**：游戏内流程、牌桌交互、HUD、动画、结算、刷新恢复、终局或复盘，默认从 game route / match route / 代表态进入，不从主页、大厅、建房机械起跑。
- **主页/大厅和游戏内流程分开**：前者证明入口漏斗、房间、路由和权限；后者证明具体游戏可玩性。除非本轮目标就是整条漏斗，不得绑成一条大 E2E。
- **“开局”指当前合同最近起点**：在游戏流程语境里，开局通常是已完成配置后的开局牌桌、首轮代表态或当前机制最近真实位点，不默认包含首页到进房。
- **V1 首页是大厅类默认入口**：游戏详情、素材包入口、创建/加入房间、下载/更新浮层等首页/大厅问题，默认从当前正式用户入口起跑；候选 HomeV2 / 预览页只能在用户点名或线上入口确实分发时作为主证据。
- **刷新、spectator、near-end、review 是独立合同**：这些链路默认单独建用例，从最近可注入代表态起跑，不挂在主流程后半段顺手证明。
- **视角必须显式**：依赖座位、私有信息、手牌归属、暗棋、权限或视角聚焦时，入口必须显式注入 `playerID` / seat / viewer identity；缺视角是测试入口错误，不能靠 UI fallback 掩盖。
- **默认值要真实**：用户未指定开启实验、偏好、调试或可选功能时，E2E 和截图必须使用产品默认值。若同时展示关闭态/开启态，文件名、截图名和汇报必须分支标注。

## 诊断与验收

- 修复前的 E2E、截图、几何测量和历史对照只能叫诊断 / 复现 / 对照，不能叫验收或收口。
- 验收必须发生在实际修复之后，并回到原始问题位点和最近邻未改分支。
- 用户问“之前/原来/改前”时，必须先查旧提交、旧截图、旧 evidence、旧断言或用户提供的历史图；当前截图不能反推历史基线。
- 找错历史基线、错 worktree、错页面、旧 dev server 或候选图时，该证据作废，必须重锁入口和基线后再决定是否实施。

## 选择器与断言

- 选择器来自玩家可见语义、稳定 `data-testid` / `data-*`、ARIA、对象 id 或共享 helper；不得依赖临时 CSS、旧弹窗结构、测试占位文案或实现细节。
- UI 重构后同步审查操作路径、i18n 文案、断言和截图名；旧选择器仍能点到元素，不等于证明同一玩家动作。
- 断言必须直接命中用户目标。可滚动就要实际滚动并看见目标；按钮能用就要证明点击前权限态、点击后可见结果、源区/目标区变化；规则时序就要证明前后阶段。
- 测试语义不要写上屏。合法目标、来源、可移动、可攻击、己方/对手等语义通过隐藏测试锚点、ARIA、class、几何和截图核图验证，不在玩家 UI 里显示 debug 标签。
- 任何新交互或新 UI 都要进入覆盖矩阵：`新增项 -> 玩家动作/可见状态 -> 已有 E2E -> 需补 E2E -> 截图/断言证据`。已有 E2E 只有测试名、真实步骤、断言和截图明确命中该项时才可复用。

## 分支对照

- 同一组件、容器、hook、CSS 类或渲染路径服务多个模式时，目标分支和最近邻未改分支都要验证。
- 对照分支尽量复用同一测试文件、入口、视口族和代表态，只切换本轮相关参数。
- 目标分支要证明变化成立；对照分支要负向证明未被误伤，例如位置未漂移、按钮仍可点、保护槽位未被侵入。
- 缺对照时只能写“目标分支已验证，对照未完成”；不适用必须说明该分支不共享本轮改动路径或已有更窄合同覆盖。

## 黄金链

### 定义

- “全流程端到端 / 黄金端到端 / 黄金链 / golden flow”同义：一条同一真实浏览器会话里的连续主证据链，从当前合同最近真实起点推进到游戏结束、胜负收口或本合同收口点。
- 黄金链开局默认不含主页、游戏选择、大厅、建房、选派系/角色等前置漏斗；除非本轮目标是入口漏斗，否则只允许在第一步玩家动作前用一次正式 fixture / 代表态进入当前合同最近真实起点。
- 每个游戏、场景、角色包或同级可玩单元默认只有一条主黄金链。多条分段链、诊断链、代表态链或 current-scope 候选链相加，不能命名为主黄金链。

### 主链资格

- 主链必须在同一个真实浏览器用例里，从最近真实起点推进到收口点；玩家动作、页面控件、合法系统结算和规则状态自然承接必须按截图顺序可读。
- 第一笔玩家动作之后，主链不得再使用 `injectCore`、TestHarness 状态替换、fixture 换段、手工改状态、领域命令跳点或任何会把页面放到另一个合同位点的桥接手段。
- 如果链中需要桥接来跳过重复准备、长轮转、随机铺垫或未能自然推进的机制，该用例只能命名为 `桥接式综合候选链`、`组合验证链` 或 `分段合同链`，不能登记为主黄金链、黄金端到端或全流程端到端。
- 注入、代表态和 fixture 只能用于第一步玩家动作前，把页面放到当前合同最近真实起点；起点之后的核心机制必须由玩家动作、页面控件、合法系统结算和同一条命令链自然推进。
- 多条互不相连的分段链、诊断链或代表态链相加，仍只能命名为 `桥接式综合候选链`、`组合验证链` 或 `分段合同链`；只有同一个真实浏览器用例按顺序自然串起起点、核心机制和收口点，才能登记为主黄金链。
- 独立切片、代表态和注入先用于证明局部合同或分段风险；进入主黄金链时只能复用已打绿的玩家动作 helper、断言和截图口径，不能复用状态替换来补核心机制缺口。
- 核心机制包括但不限于：翻出场地 / 区域、抽取或亮出不同类型卡牌、同类型对象的不同交互形态、选择 / 投骰 / 目标指定、回合交接、阶段切换 / 阵营 / 私密信息 / 读本、战斗 / 敌对单位 / 特殊单位、胜负触发和终局朗读。
- 主黄金链必须交付**完整过程截图包**，不是挑几张代表图。每个核心机制和关键转场都要在玩家动作前后留下截图，能让未看过测试代码的人按截图顺序读出“发生了什么、玩家做了什么、系统怎么结算、下一步如何继续”。
- 过程截图必须随玩家流程顺序编号，并配套顺序索引或截图清单；缺少中间转场图、只保留起点 / 终点 / 结果图，或用单张代表图声称某段流程能走通时，只能算截图摘要，不满足主黄金链截图资格。
- 用户可见的主黄金链最终展示图组必须是完整过程截图组。摘要图、结果图、contact sheet、索引图或少数代表图只能作为辅助导航，不能替代过程图组，也不能作为“流程能走通”的完成证据。
- 每张过程截图落图前必须等待当前节点稳定：关键牌面 / 骰面 / token / 房间 / 单位 / 读本 / 响应窗口 / 结果面板已真实渲染，无空白牌、牌背占位、加载 shimmer、遮挡性临时浮层或未退场的过渡层。不能用“测试已通过”替代图面可读。
- 核心机制族未达到玩家可用合同时，不能进入 stable / pre-push 主黄金链，也不能用注入、代表态、截图数量或相邻机制外推为已覆盖。
- 玩家可用合同至少包括：规则状态与结算存在；合法目标 / 输入路径存在；正式 UI 可触发；可见结果能解释；非法或不可用分支有明确拒绝；低层测试或窄真实入口 E2E 已证明。
- 建设顺序必须是先独立、再综合：入口、核心回合、资源 / 手牌 / 骰子 / 目标、响应窗口、高风险分支和收口点先作为独立功能切片跑通；全部打绿并说明可外推边界后，才能把 helper、玩家动作、断言和截图复用进主黄金链。
- 未实现、未接 UI 或未证明的核心机制只能登记为 `deferred / 不在当前合同 / 分段或低层覆盖`。

### 覆盖矩阵

- 完整流程优先组合证明：入口合同、代表态合同、高风险分支合同和主黄金链；组合证明可以补风险覆盖，但不能把分段链合并命名为主黄金链。
- 主黄金链最低覆盖：开局牌桌、核心回合推进、对象生成/翻出/抽取、不同类型对象、同类型至少两种交互形态、回合交接、随机/选择/目标指定、私密/剧情/阵营或等价揭示、代表性冲突/战斗/特殊单位或等价高风险机制、胜负触发和终局收口。
- stable / pre-push 前必须有覆盖矩阵：机制族、玩家主路径、真实浏览器覆盖、分段/代表/低层覆盖、`deferred` 项和外推理由。
- 过程截图包是主黄金链证明玩家可读流程的必需证据；截图数量不能替代断言、玩家动作或覆盖矩阵，但没有过程截图包也不能把 E2E 通过升级成主黄金链通过。

### 预算

- 单条 E2E 目标 `3` 分钟内；超过 `5` 分钟要说明价值并优先拆分；单文件接近或超过 `10` 分钟先拆主题。
- 同一问题长链最多重跑两次，总定位预算 `15` 分钟；拉到 `45` 分钟仍未锁定，停止堆长链，退回代表态、低层或组合合同。
- pre-push 只跑发生增量的非实施中游戏已登记主黄金链；`skipped` 或未命中用例名按失败处理。

## 桥接式组合验证

当完整玩法既要证明入口，又要证明 match 内中后段语义时，默认分段：

1. **入口合同链**：建房/入房、首个可行动回合、座位/权限/同步。
2. **中段代表态链**：本轮关心的 draw/discard、waiting、live/stacked、spectator、reload 等位点。
3. **终局前代表态链**：near-end、最后动作、review 前一跳、终局切换和复盘。

三段可以说明“完整流程已分层证明”，但在没有同一主链用例、核心机制被桥接跳过或承接态无法对上时，不能叫主黄金链。若同一用例同时想证明入口、中段、near-end、review、reload 和 AI 决策，默认已经超出单链合同，应拆。

## 新游戏与流程节点

- 新游戏基本流程和首个场景 / 首个流程节点 / 终局默认分两段证明。
- **基本流程 E2E** 证明从最近真实入口完成角色/配置/开局确认，到达首个可操作运行时。
- **流程节点 / 终局 E2E** 从已确认运行时代表态或 near-end 起跑，证明关键交互、结算和终局可见结果；不重复已由基本流程证明的前置。
- 文件、用例和 evidence 分组必须写清 `basic-flow`、`first-scenario`、`near-end` 或 `endgame`，禁止一个“完整流程”承担全部合同。
- 命中保护页时，先回到真实页面：刷新重试或重新加载，等测试 harness 与真实游戏页挂载；保护页截图不能交付。

## 读本 / 私密信息 / 终局截图

证明规则读本、事件书、任务书、阶段切换、阵营/角色手册或结局朗读时，截图必须证明规则流程，不只证明“有文字”。

最低截图组：

1. 公开揭示：应知玩家共同看到入口或结果。
2. 秘密阅读：不同视角看到不同阅读入口或内容，并证明不该看到的视角看不到。
3. 开局叙事：叙事正文可读，且发生在目标承接前。
4. 目标承接：读完后，目标、任务、胜负条件或下一步行动入口进入可操作界面。
5. 结局朗读：胜负条件达成后出现对应结果正文；只显示胜利/失败不算。

叙事幕、手册页、目标承接和终局统计必须分开。开局/结局叙事若声明为电影字幕幕或朗读幕，必须是独占阅读时刻，不得像普通弹窗、书页、统计报告或目标摘要卡。每张截图说明必须写清节点、玩家视角、公开/秘密、承接到哪一步。

分阵营或分角色读本必须分别截图：公开揭示后，至少要有一个应看英雄书的视角截图和一个应看叛徒 / 敌对方书的视角截图，并证明双方看到的是各自该看的书名、正文入口和目标承接。只截其中一方，或只截“剧本已打开”的通用页面，不能证明私密信息流程完整。

## 素材门槛

- E2E 不是素材 intake 或规则对象矩阵的替代品。新增游戏、继续接入或宣称基础流程闭环前，先确认规则对象素材矩阵和实现任务没有可本地推进的前置缺口。
- 规则明确存在的牌面、牌背、token、棋子、骰子、地图、帮助卡等对象，要么使用真实素材并完成语义命名、落盘、压缩、manifest 和运行时引用，要么明确标为阻塞。
- 页面仍使用未批准程序化替代、mock 图片、纯文字壳或错素材时，E2E 最多证明代码链路通过，不能升级为基础版完整闭环。
- 素材阻塞必须写清现实对象、真相源、当前候选、为什么不能落盘、下一步动作；不能用“后续美术优化”吞掉。

## 流程截图

- 完整端到端默认覆盖六段：`触发前`、`亮相/翻出后`、`选择或随机前`、`选择/随机后`、`结算后`、`关闭/继续后`。
- 主黄金链截图必须覆盖完整过程，不是按机制族各挑一张代表图。每个关键动作至少要能看到动作前可操作态、动作后中间态 / 选择态 / 随机结果、结算结果、关闭或继续后的下一可操作态；连续机制之间要保留承接图。
- 证据文档或任务状态必须形成四列闭环：玩家实际动作、自动断言、截图文件、用户目标对应。缺列只能登记为 `待补完整链路`。
- 过程截图文件名要使用可读顺序号和玩家动作 / 可见结果，例如 `01-开局牌桌`、`02-卖牌换CP后`、`03-进入投骰阶段`；禁止用内部状态名、fixture 名或代表图名替代流程节点。
- 写链前先锁规则时序家族，例如先选择后随机、先随机后选择、随机后直接结算、可选是否触发、翻出后自动结算；不能用一个家族的链路证明另一个家族。
- 完整链路必须来自同一规则链和同一对象。自然链和代表态混用时只能登记为组合验证或分段合同；测试名、截图目录、截图名和 evidence 必须显式写断点，不得让截图看起来像自然连续剧情。
- 无弹层的流程也要有收口图，证明高亮、临时状态、阻塞层或选中态已退场，主界面可继续操作。
- 展开/详情 UI 必须截图入口可见态和展开态；只截最终展开面板，无法证明入口链路。

关键机制的过程图必须证明“入口从哪里来、玩家怎么选、结果落在哪里”，不能只截按钮或最终状态：

- **物品 / 能力使用**：至少包含使用前来源对象或持有区、选中后绿色合法目标高亮、玩家确认或提交、使用后结果落位。结果落位必须能看见状态变化，例如生命 / 属性恢复、资源变化、物品移除、日志反馈、目标状态变化或下一步入口恢复。
- **翻出后可选跳过 / 替代**：截图必须先证明玩家已经看见被翻出的房间、符号、牌型或将要结算的对象，再截图“是否跳过 / 是否替代”的选择。探索前声明、测试注入字段或只有跳过按钮的图，不能证明“知道类型后再决定是否跳过”。
- **攻击奖励 / 偷取 / 夺取**：截图必须同时证明奖励来源和奖励结果。最低过程是攻击前目标持有可偷对象、攻击或结算结果达到奖励阈值、奖励入口可见、选择奖励后对象归属变化；只截“偷取按钮”不能证明入口合法。
- **同类型不同交互**：黄金链声明覆盖某类对象时，至少两种不同交互形态要分别有过程图。例如同是房间或卡牌，一种自动结算、一种目标选择、一种可跳过 / 替代，不能互相用单张代表图外推。

## 随机、骰子与可介入结果

- 投骰、重掷、改骰、翻牌、抽牌、亮出事件、随机结果和阻塞式结算必须展示结果本体，不能只给日志、摘要、按钮或最终状态。
- 可介入阶段必须覆盖：结果出现、可介入对象可见/选中、目标对象可选、介入后结果变化、确认后现实结果落位、收口后主界面可继续。
- 可直接点击真实骰子、卡牌、token、场地/区域格、地图格、单位或目标区域时，主路径必须点对象本体或投影命中区；数字按钮、文字列表和编号选项只能作备用/无障碍入口。
- 物理骰或 3D 骰必须证明真实可见渲染面存在、尺寸非零、骰体可辨、专用骰面和规则值一致，并等稳定状态后截图。通用 d6 内部映射不得外露成玩家语义。
- 多颗骰子必须逐颗可辨，不得叠成一团后用 DOM 数量或业务数组通过。
- 若规则仍允许重掷、改骰或介入，阻塞结果不能空白关闭；介入机会结束后再允许关闭并推进。
- 只有失败提示、toast 或门禁图不能替代成功路径证据。

## 视觉与动态证据

- 看图必须直击问题位点，逐项核对用户指出的区域、现象和目标；不能只扫整页。
- 证明布局、弹窗、HUD 或游戏进行页时，主图优先整屏/整牌桌，局部裁切只作辅证并保留原图路径。
- 满载/压力态优先：截图应包含会竞争空间的手牌、牌堆、玩家面板、阶段/资源、主按钮、当前 prompt、侧边工具、浮层入口、安全区等；缺项要说明原因。
- 翻页、移动、飞行、伤害飘字、结算跳分、展开收起等时间维度需求，必须有真实过程帧、动态证据或连续关键帧；最终静态图不够。
- 过程帧必须来自同一真实页面链路的运行时动画，肉眼能看出来源、飞行/变化、命中/结果和稳定态。DOM 节点存在、canvas 存在或截图文件落盘不等于视觉通过。
- 高亮/描边/发光必须在整屏图里让第一次看图的人一眼认出目标；靠读测试字段、局部放大或口头解释才看得出，判未达标。
- 截图里若目标对象被裁切、遮挡、只露边角、关键牌面空白、仍有过渡 ghost/骨架、页面出现 Vite/Chunk/模块加载错误，该截图不能作为最终验收。
- 移动端/PC 同构要对照同状态当前截图，不能只给移动端局部图；PC 一级信息在移动端要有明确去向或合理收纳。

## 截图来源与证据文档

- 截图必须来自当前问题场景、当前 worktree、当前入口；大厅页、预览页、兄弟入口、资源诊断页或 mock 场景不能替代原问题位点。
- 证据说明必须写“我实际看到什么”和“是否达到本轮验收标准”；不要只复述断言、组件名、测试名或“正常”。
- 每张关键截图至少写 1-3 条肉眼观察结论，直接回应本轮需求点。
- 临时局部放大、标注图、流程图和 contact sheet 只能辅助；最终验收必须回到真实页面原图。
- 截图命名和汇报用玩家能懂的画面对象和动作，不用内部字段、测试夹具名或实现状态当画面名。
- 若最终回复写“E2E 通过 / 已验证成功”，必须给出至少 1 张已实际核对关键截图的完整绝对路径；否则不得用该口径收口。

## 用例拆分与命名

- 入口合同和游戏合同分文件优先：大厅/进房测试归入口主题；牌桌、终局、刷新恢复、spectator、AI roundtrip 归游戏主题。
- 每条用例只证明一个主合同。标题必须写清入口态、中间态、near-end、代表态、刷新恢复、分支对照或完整链路边界。
- 重复前置收成 helper、fixture 或代表态，不在每条用例里重复走长漏斗。
- 中文业务截图名优先；英文测试文件名可保留。面向用户的 evidence 目录和图片名不要默认用英文 slug，除非协议、工具或跨平台脚本硬性要求。

## 失败与收口

- E2E 用于收口，不作主调试器。先低层定位和修实现，再用最窄真实入口 E2E 收口。
- 环境不可用、入口打不开、目标状态无法构造、资源缺失或测试服务未启动时，停在该失败点，说明命令/步骤、现实后果、当前证据和最小补救动作。
- 测试输出 `passed`、trace 落盘、截图生成或断言变绿，只证明命令执行成功；最终结论必须回扣目标矩阵，逐项回答用户目标是否被证明。
- 看到不达标必须写不达标。E2E 绿灯不能覆盖手牌缺失、控件偏移、遮挡、只露边角、状态不完整、链路不真或截图无效。
