# 规则驱动交互设计

> 适用：新增游戏、迁移复杂卡牌 / 技能 / Token / 状态、设计响应窗口、阶段按钮、特殊行动、AI 合法动作或审计“为什么玩家能点不该点的按钮”。

## 核心原则

交互不能从“当前焦点玩家”“当前视角玩家”“当前回合玩家”这类实现便利概念直接推出。必须先从规则文本推导现实动作，再落到命令、验证、UI 和 AI。

需求涉及复杂触发、响应、替代、防止、长事务或 AI 阻塞时，先按 [`timing-opportunity-resolution`](timing-opportunity-resolution.md) 判断是否建立 `TimingPoint / Opportunity` 矩阵，再把需要输入的机会转成 Choice Request 或 response window。本文负责“机会如何被玩家、UI、AI 和验证消费”；不负责让 UI、按钮列表或 response window 自己发现机会。

必须分清四种身份：

| 身份 | 现实含义 | 能做什么 | 不能当成什么 |
| --- | --- | --- | --- |
| 视角玩家 | 当前屏幕正在看谁的牌桌 / 信息 | 决定显示角度、信息可见性、默认聚焦 | 不能决定规则权限 |
| 当前决策者 | 规则此刻要求谁做一个具体选择 | 只能完成该选择、跳过该响应或确认该交互 | 不能自动获得阶段推进权 |
| 动作所属者 | 这张牌、技能、Token、状态的来源玩家 | 决定来源归因、消耗、日志和效果归属 | 不能自动代表目标或响应者 |
| 阶段推进者 | 规则允许谁结束当前阶段或进入下一步 | 只能在所有阻塞窗口关闭后推进阶段 | 不能由响应窗口焦点推断 |

只要某个 UI 按钮、卡牌入口或 AI 动作会改变规则结果，就必须有一个从规则文本推导出来的授权条件；展示焦点、hover、高亮、镜头跟随、对手视角切换都只能影响显示，不能授予权限。

## 规则到交互的推导步骤

每个会让玩家操作的规则子句，都先拆成一行“交互原子”。不要先写按钮、状态字段或 helper，再反推规则。

| 字段 | 必填问题 |
| --- | --- |
| 规则子句 | 原文要求发生什么，关键限定词是什么 |
| 触发窗口 | 发生在阶段开始、打出时、结算前、响应时、防御后、回合结束后，还是延迟收口时 |
| 授权玩家 | 规则允许谁操作：攻击方、防御方、当前响应者、目标玩家、来源玩家、任意玩家、队友、所有人 |
| 第一入口 | 玩家第一下应该点什么：卡牌、角色、棋子、骰子、基地、地图格、目标玩家、确认按钮，还是无需玩家输入 |
| 合法动作 | 允许的命令集合是什么；是否包含跳过、取消、空选、继续、确认或阶段推进 |
| 禁止动作 | 当前窗口打开时明确不能做什么，例如不能结束阶段、不能打普通牌、不能操作非自己目标 |
| 目标与归属 | 效果作用到谁 / 什么对象；来源、目标、受益者、受害者是否不同 |
| 消耗与回滚 | 卡牌、资源、Token、次数在何时消耗；失败、取消、跳过时是否回滚 |
| 后续与清理 | 交互关闭后进入哪个阶段、继续哪个 pending、清理哪些临时状态 |
| 消费者 | UI、命令验证、resolver/reducer、AI 合法动作、自动推进 / watchdog 是否都读同一份授权真相 |

输出落点可以是 `rule/`、OpenSpec design、`evidence/<gameId>/...` 或新游戏阶段 1.5 的机制矩阵；但不能只停留在对话里。

多动作同屏时先做动作意图仲裁，不能由默认点击、拖拽、额度兜底、按钮高亮或旧测试习惯替玩家选路：

| 场景 | 第一入口 | 审计要求 |
| --- | --- | --- |
| 同一张手牌既可普通打出、又可发动自身手牌能力 | 该手牌本体 | 先让玩家选动作意图，再进入目标 / 确认 |
| 打出另一张牌时，手牌能力可替代 / 防止 / 改写原动作 | 原动作对象本体；替代能力作为同窗口合法动作 | 原动作和替代能力同时合法时必须可仲裁 |
| 响应牌、弃牌堆额外打出、牌库 / 对手手牌额外打出、纯场上 special、融合牌 play-as | 各自规则窗口定义的对象 | 按窗口、来源区域、第一入口和 command payload 分开，不因文案含“打出”混类 |

玩家 UI 只展示动作按钮和必要状态，不展示内部合法性解释；按钮复用当前游戏已有动作栏、浮动操作栏、触发按钮或等价正式槽位，不为单卡仲裁新造外壳。最小验证必须覆盖“多个动作同时合法”：每个合法动作可选、可取消 / 跳过、最终命令与所选动作一致，且没有多余解释文案上屏。

## 业务阻塞选择默认使用 Choice Request

如果存在业务阻塞选择，新游戏和已迁出旧选择弹窗的游戏默认不再用裸 `createSimpleChoice` 作为权威入口。规则选择应先建 `Choice Request`（选择请求），再由 UI、AI、服务端校验和自动恢复共同消费。

Choice Request 至少包含：

1. 当前决策者：谁被规则要求做这一步选择，不能从视角玩家或焦点玩家推断。
2. 选择语义：这是选玩家、选卡牌、选场上对象、选棋盘格、选来源、选目标、选数量、确认 / 跳过，还是响应窗口。
3. 稳定候选：每个候选必须有当前决策内稳定的业务 ID，例如 `playerId`、卡牌实例 ID、场上对象 ID、区域稳定 ID、位置 ID 或等价标识；禁止只用按钮文案、翻译文本、数组下标或 UI 顺序。
4. 提交命令：每个候选最终提交到哪个正式命令、payload 形状是什么、失败时如何拒绝。
5. 跳过与多选：是否可跳过、是否必须跳过、`min/max`、是否有顺序语义，必须显式声明。
6. AI 支持状态：`semantic`、`adapter` 或 `unsupported`，并说明 AI 生成合法动作的来源；正常 AI 对局不得把 `unsupported` 交互分配给 AI 座位。
7. UI 承载：UI 可以把同一份合同渲染为手牌高亮、棋盘高亮、场上对象高亮、弹窗或按钮，但 UI 展示形态不是规则真相源。

旧游戏中的既有 `simple-choice` 调用按兼容口径保留，不要求大爆炸迁移。修改旧游戏时，只有触碰到 AI 可控阻塞交互、响应窗口、场上来源-目标选择、多步选择或线上复发卡点，才必须按本节补 Choice Request 或迁移到专用 interaction kind；未触碰的历史交互继续遵守 [`engine-simple-choice.md`](engine-simple-choice.md) 的兼容规则。

## 特殊卡牌效果必须单独推导

“特殊”“响应”“打断”“替代”“防止”“结算后”“你可以”“至多”“任意数量”都不能归入普通回合动作。每一类特殊效果都必须单独回答授权玩家、窗口、可做动作和禁止动作。

规则语义要求玩家选择对象、分支、数量、顺序或是否执行时，系统必须保留玩家确认，不能因为当前只有一个合法候选、存在默认分支、旧 simple-choice 习惯、测试便利、AI fallback 或自动恢复逻辑就替玩家选择。`choose / 选择`、`discard a card / 弃掉一张牌`、`discard two cards / 弃掉两张牌`、`二选一 / 或`、`may / 可以`、`至多`、`任意数量` 等都默认属于玩家决策语义；只有规则明确写“随机 / random”、完全没有对象 / 模式 / 数量可选，或明确是强制自动结算，才允许系统自动结算。AI 座位需要完成这类决策时，必须走 AI 合法动作或策略选择，不能复用人类席位的自动提交语义。

| 效果类型 | 必查问题 |
| --- | --- |
| 响应 / 打断 | 谁能响应、响应者队列如何产生、每个响应者能打什么、能否跳过、响应期间哪些普通按钮必须禁用 |
| 特殊行动 / Special | 它是在普通行动阶段打出，还是在别人的动作窗口里打出；是否消耗普通行动额度 |
| 替代 / 防止 | 原事件是否被取消，替代事件何时写入，选择跳过时原事件是否恢复 |
| 可选 / 至多 / 任意数量 | 有合法候选时是否允许不执行，空候选时是否不创建卡死交互 |
| 多步选择 | 第一步选什么，后续步骤需要携带哪些稳定上下文，不能靠当前 UI 选中态猜 |
| 延迟 / finalize | 交互关闭后真正生效点在哪里，是否需要快照原始结果，是否会跨阶段或跨清场 |
| 私有 / 隐藏信息 | 谁能看见 prompt、谁只能等待，恢复态和重连后是否仍保持私有边界 |
| 额外行动 / 额外攻击 | 它授予的是额度还是立即消费；是否会打开新的响应 / 防御 / 收口窗口 |
| 自动推进 / AI | 有合法动作时 AI / watchdog 不能只看到“结束阶段”；无合法动作时才允许自动收口 |

“至多 N 个对象 / 任意数量对象”默认表示同一次确认前的一批多选，确认后应按这批选择结算并关闭该对象的当前效果；它不自动表示玩家可以跨多次确认分批累计到 N 个。只有规则原文明写“同一对象可重复选择 / 可重掷多次 / 每次尝试后仍可继续 / 可把次数分配给对象”等次数语义，才允许建模为跨确认的多步累计，并必须把同对象重复、剩余次数、取消后是否返还资源写入交互合同。

只要玩家在一个可见窗口里完成一次确认，这次确认就是一个玩家意图。若该意图会作用到多个目标、生成多条规则命令或同时包含“业务命令 + 关闭交互命令”，交互合同必须声明它们属于同一次确认批次；UI、AI、命令层和传输层不得把它拆成多次独立玩家动作，也不得让第一条命令的 pending、动画或回滚状态吞掉后续目标。实际传输和服务端原子性以 [`engine-transport`](engine-transport.md) 的批量命令合同为准。

禁止把“响应者当前可操作”扩大成“响应者可以推进阶段”。禁止把“当前回合玩家”扩大成“所有当前按钮都归他”。禁止把“焦点切到某玩家”当成权限变化。

## 卡牌型响应窗口职责顺序

当响应窗口允许玩家从手牌打出响应牌时，玩家语义固定为“先点手牌本体，再点合法目标 / 确认”：

| 职责 | 要求 |
| --- | --- |
| 响应窗口 | 开放时机、显示当前响应者、提供让过 / 跳过、承载最终提交命令；不是打出手牌的第一入口 |
| 手牌区 | 当前响应者的可响应手牌高亮或可点击；非响应手牌置灰或禁用 |
| 目标区 | 只在点选响应手牌后，高亮该牌允许的基地、随从、玩家或其它目标 |
| 按钮列表 | 只承载让过 / 跳过、非手牌触发、场上能力、强制排序、无障碍或兜底入口；不得代理“打出某张响应手牌” |

验证至少覆盖：非响应牌不可点或置灰、响应牌可从手牌本体发起、无关目标不可点、最终提交命中当前响应窗口的 live 交互。

## 场上对象可发动效果与自动效果分流

当场上卡牌、随从、角色、Token、基地或棋盘对象到达规则时机时，先分流强制自动效果和玩家可选 / 主动发动效果：

| 效果类型 | 第一入口 | UI 反馈 | 禁止 |
| --- | --- | --- | --- |
| 强制自动效果 | 系统直接结算；仅在规则要求玩家选择目标、顺序、数量时进入对应选择 | 可表现来源，但不要求点来源 | 为“表现来源”额外要求玩家点击来源本体 |
| 可选 / 主动发动效果 | 来源对象本体 | 窗口开放时只高亮可发动来源；文案用“可发动 / 是否发动 / 不发动 / 跳过” | 让目标在来源被点击前高亮、可提交或抢焦点 |
| 来源已点击后的目标选择 | 合法目标对象本体 | 保留来源选中态，并立即高亮合法目标 | 用一级按钮直接代点目标，除非规则完全没有对象、目标、支付、顺序、数量或可跳过分支 |
| 控制按钮 | 跳过、不发动、取消、排序确认、无障碍备用、纯分支或完成对象选择后的确认 | 降权为控制项 | 代理“发动来源对象效果”或“移动到目标对象” |

同一时机多个可发动来源可以同时高亮来源对象，但这不是目标提前高亮。验证至少覆盖：来源本体可发动、点击来源前目标未高亮且不可提交、点击来源后目标高亮、无关目标不可提交、旧代理按钮不能完成同一命令、最终提交命中当前 live 交互。目标高亮必须是整屏肉眼可见的本体反馈；隐藏锚点、DOM 属性或内部选择状态只能作辅证。

## 可选目标高亮

目标选择必须让玩家在正式对象本体上一眼看出“现在能点谁 / 什么”：

- 进入二级目标状态后，合法玩家、角色、棋子、房间、token、卡牌、区域或等价对象必须出现清楚贴合本体的可选高亮；无合法目标时明确说明无法选择。颜色和形态优先沿用同一游戏已验收的对象语法，绿色只是没有成熟语法时的默认合法目标色，不是跨游戏硬规则。
- 任何玩家主动交互一旦点击一级入口，例如交易、交换、使用、攻击、移动、观察、拾取、交付或等价动作，UI 必须进入可见交互模式：显示当前步骤、合法候选和下一步承接，不能只写内部选中态或等待玩家猜。
- 若同一游戏把绿色定义为合法可点目标，绿色只能给“当前点击会被正式命令接受”的对象；不可提交、条件不足、已用尽或只是可能相关的对象不得显示绿色合法高亮。需要解释不可用时，用隐藏、禁用、灰置或邻近原因承接，不能用合法色冒充可用。
- 黄色 / 琥珀色在多数游戏里只表示当前选中、警告、等待、候选提示、焦点或结算关注；只有同一游戏成熟语法明确把它定义为合法目标色，且能和选中态分清时，才可用于可点击合法目标。对象同时被选中且合法时，必须用主边界与内部选中态分层，避免玩家把选中误读成可点。
- 一级动作选中后，同级一级按钮退场或降权，合法目标本体高亮，非法目标保持普通 / 禁用；唯一合法目标也不能省掉可见选择，除非规则没有目标选择语义。
- 点击合法对象后必须立刻出现玩家能读懂的承接反馈，例如对象选中态、目标名进入流程提示、候选列表切换、提交按钮启用或结果反馈；不得只让日志、DOM 属性或隐藏测试锚点变化。
- 截图、E2E 和人工验收以肉眼图面为准；隐藏测试锚点、DOM 属性、日志、按钮可用态或内部选择状态只能辅助证明。整屏看不出可点目标，或高亮颜色 / 形态和同游戏语义冲突，必须判不达标并修 UI。

## 通用弹窗不是兜底入口

当一个交互无法收窄成手牌、基地、随从、玩家、按钮或明确的场上来源-目标类型时，才允许保留通用弹窗；通用弹窗必须说明它承载的真实语义，不能用单张牌名、单个 `sourceId` 或历史实现习惯证明自己合理。

允许保留通用弹窗的常见语义只有这些：

1. 牌池选择：候选来自牌库、弃牌堆、展示区、组合牌池或非主视图可见区域，玩家实际是在一组卡面里挑选。
2. 埋葬牌选择：候选是埋葬区、翻开区或类似隐藏 / 半隐藏区域里的牌，主棋盘对象不能直接代表完整候选。
3. 离场或快照对象：候选对象在交互解决时可能已经离开主视图，只能按创建交互时的快照继续选择。
4. 复合上下文：一个选项同时携带牌、基地、随从、区域、数量或来源关系，任何单一对象本体都不能独立表达这次选择。
5. 模式或定义选择：玩家选的是效果分支、处理方式、牌名 / 定义、排序或规则模式，不是在选择一个当前可见实体。
6. 卡牌与控制混合：同一窗口同时包含卡牌候选和跳过 / 完成 / 额外行动等控制项，且主视图对象直选不能覆盖完整动作集合。

实现和审计必须按选项形状或显式通用意图来放行通用弹窗，例如 `genericIntent` 表示牌池、埋葬牌、快照对象、复合上下文、模式、排序、卡牌与控制混合或定义选择。禁止维护“哪些 `sourceId` 可以 generic”的白名单；如果只能靠牌名解释，说明职责还没有抽象到可复用规则。

带有场上实体字段的通用弹窗必须额外审查：若它其实只是选择当前可见基地、随从、玩家或场上来源对象，就必须改成对应对象本体入口；只有能证明它属于上述通用语义时，才可保留。验证至少覆盖：通用意图声明或形状推导存在、UI 不把它误渲染成错误对象直选、提交 payload 仍来自当前 live 选项、非法场上对象不能被旧快照或弱字段伪造。

## 按时机窗口排查时的对象全集

当反馈指向某个时机窗口里的交互职责错误，例如计分、战斗结算、回合结束或响应窗口，不得只修第一个复现对象后宣称同类都正确。先建立该窗口的对象全集，再逐项分流职责：

1. 每个触发、响应、基地效果、场上 special、手牌 special 或等价入口都必须有独立行；未列行就是未审对象，不能被兄弟对象或代表样本覆盖。
2. 每行先判定现实职责：强制自动、手牌响应、场上可选来源、基地效果、纯确认 / 跳过、目标玩家、目标手牌、目标牌库或其它目标选择。
3. 每行再写第一入口：系统自动结算、手牌本体、来源对象本体、目标对象本体、确认按钮或跳过按钮。只有“场上可选来源对象 -> 可见目标对象”的效果适用“先点来源，再点目标”。
4. 代表性 E2E 只能覆盖已写清判等依据的共享合同；它不能外推到未列行、职责不同或目标类型不同的对象。
5. 对外汇报必须带证据层级：L1 对象清单、L2 行为断言、L3 真实 UI / 截图链、L4 生命周期和无残留。没有逐行证据时，只能称专项验证、代表验证或清单快照，不能称完整逐牌审查已经完成。

## 权限矩阵是实现前置产物

任何包含阶段、响应窗口、卡牌特殊效果或 AI 自动动作的游戏，在正式实现前必须建立最小权限矩阵：

```markdown
| 窗口 / 阶段 | 角色 | 可见入口 | 可提交命令 | 禁止入口 | 关闭条件 | 验证层级 |
| --- | --- | --- | --- | --- | --- | --- |
```

最低要求：

1. 至少覆盖每个阶段、每类响应窗口、每类特殊卡牌窗口和每个系统按钮。
2. 同一窗口里分别列攻击方、防御方、响应者、非响应者、旁观者、AI。
3. “结束阶段 / 结算攻击 / 结束防御 / 下一步”这类系统按钮必须单独列，不能挂在焦点玩家下。
4. UI、命令验证、AI 合法动作和自动推进必须引用同一个授权 helper 或同一份结构化合同；不能各自写近似条件。
5. 每个可见入口都要有一条正向证据；每个禁止入口至少有一条负向证据，证明它在不该出现或不该可点时不会出现 / 不会可用。

## 实现要求

- 先建立规则合同和权限矩阵，再写 Board 条件、按钮 enable、AI legal-actions 或 watchdog。
- “当前决策者”只能授予当前交互的命令；阶段推进、普通行动、响应、私有 prompt 必须有各自的 actor resolver。
- 若规则状态同时被 UI、validator、AI、自动推进消费，必须抽出唯一查询入口；后层校验只能做活体性和权限复核，不能引入另一套业务口径。
- 响应窗口、simple choice、deferred/finalize、attack/defense pipeline 并存时，先定义哪个系统拥有当前命令门控，避免一个系统抢掉另一个系统的合法命令。
- 内部非法状态应尽早断言或返回明确错误，不要为“理论上不该出现”的权限组合加沉默兜底。

## 验收

新增游戏、卡牌效果或特殊响应窗口要宣称可玩 / 已审计 / 可发布时，至少证明：

- 权限矩阵存在，且覆盖本轮所有玩家身份和特殊窗口。
- 每条规则子句能追到命令、验证、执行、UI 和 AI / 自动推进消费者。
- 每个特殊效果都有成功路径、拒绝 / 跳过路径和不该可用的负向路径。
- 响应 / 打断 / 延迟 / 私有窗口关闭后，没有残留 pending、错误阶段推进、错误按钮暴露或 AI 抢推进。
- 审计文档或测试说明里明确写清“视角变化不改变权限”的证据。
