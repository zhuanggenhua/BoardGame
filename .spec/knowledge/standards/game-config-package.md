# 游戏配置包规范

> 适用：新游戏静态配置、配置审查表、玩家字段级修正提案，以及旧游戏是否接入统一配置视图的裁定。
>
> 配置审查表的可执行流程以项目 [`config-review-workflow`](../../skills/config-review-workflow/SKILL.md) 为唯一执行入口；本文只记录本项目配置包边界和项目适配入口，不重复维护同一套表格 SOP。

## 默认口径

- `GameConfigPackage` 是项目内共享接口，不是第三方包。
- 配置包是数据驱动录入的正式真相层之一；检查“录入是否完成”时必须同时检查规则字段、素材 / atlas、运行时配置、setup、token / 骰子 / 区域、能力绑定和表格物化裁定，不能只检查卡牌字段或图片字段。
- 新游戏的静态事实默认先进入严格 JSON 配置包，再由运行时加载、校验和物化。
- 旧游戏默认不强制迁移；只有明确需要统一审查表、结构化修正提案或迁移配置真相源时，才建立单独接入任务。
- 表格是同源审查视图，不是运行时依赖；表格行必须来自配置包物化结果，禁止另维护一份展示专用数据。
- 配置审查页面只保留 adapter 输出、字段中文显示、编辑解析、筛选项和素材 / 音频扩展的接入；页面复用、真实入口、玩家可见字段、素材预览 / 试听、横向滚动、分页和提案流程不在本文重复定义。

## 录入复查口径

数据录入复查默认包含配置复查。若新游戏暂不使用 `GameConfigPackage`，仍必须把现有配置面逐项列入复查记录，并说明哪些只是当前运行时临时真相源，哪些需要后续迁入配置包。

| 配置面 | 必查内容 |
| --- | --- |
| 对象配置 | 卡牌、单位、法师 / 角色、token、骰子、区域、墙体、牌组构成、初始部署 |
| 资源配置 | 正式图片 / 图集、frame、牌背、manifest、压缩产物和运行时引用路径 |
| 规则配置 | `abilityId + params`、目标规则、触发条件、使用限制、需要代码支持的能力缺口 |
| 运行配置 | 游戏 manifest、玩家数、移动端能力、方向、资源包、首屏关键素材 |
| 审查配置 | schema 范围、表格物化范围、字段级修正提案路径和玩家可提交字段 |

如果这些配置面仍散落在 TypeScript、JSON、manifest、i18n 或文档合同里，复查结论只能写成“当前配置面已登记 / 可追溯，但配置包化 deferred”，不能写成“数据驱动录入已完整闭合”。

## 格式职责

| 格式 | 职责 | 禁止口径 |
| --- | --- | --- |
| 严格 JSON | 新游戏官方仓库真相源，便于 diff、review、自动校验和稳定解析 | 不得跳过 schema 校验直接运行 |
| JSONC / YAML / XLSX | 只允许作为未来导入、导出或编辑辅助；进入系统前必须转换成严格 JSON 配置包 | 不得作为官方仓库真相源，不得进入运行时默认解析链路 |
| TypeScript 配置 | 旧游戏可继续临时使用；可通过只读 adapter 暴露审查视图 | 新游戏不得默认把静态事实直接写进代码对象 |

## 特殊效果边界

- 配置包只声明 `abilityId + params`。
- 真正的特殊效果由代码里的能力 / 规则模块实现。
- 加载配置包时必须能报告：
  - 能力 ID 不存在；
  - 能力需要代码支持但未实现；
  - 参数缺失或类型不符合能力参数合同。
- 玩家提交的修正不能包含可执行代码；只能修改 schema 允许字段，或建议新增 / 调整能力绑定。

## 玩家修正提案

玩家从配置审查表提交的是结构化提案，不是直接改官方配置。提案至少保存：

- 游戏 ID、配置版本；
- 对象 ID、对象类型；
- 字段路径；
- 当前值、修改后值；
- 玩家可见对象名、玩家可见字段名、当前显示值、修改后显示值；
- 说明、证据；
- 来源页面、表格 ID、行 ID、单元格 key、语言环境；
- 审查状态。

AI 审查只做首轮建议，可输出：建议接受、建议拒绝、需要更多证据、需要人工确认、需要代码支持。AI 不得自动写入官方配置源；正式合入仍走代码变更、测试和发布流程。

## 维护者内部配置模式

配置表可以提供维护者内部配置模式，但它和玩家提案模式不是两份数据来源：

- 玩家提案模式：默认展示当前值；编辑后生成字段级配置修正提案，等待人工 / AI 审查。
- 维护者内部模式：允许查看字段路径、消费证据和内部状态，编辑草稿并生成待应用 patch；正式应用仍回到唯一官方配置源、代码变更和测试流程。
- 草稿、提案、patch、审计 evidence 都不是运行时真相；不得让浏览器运行时直接写仓库配置，也不得另存一份运行时配置副本。
- 旧游戏的 TypeScript 配置可以继续作为官方源；同源 adapter 负责生成表格、解析编辑值和生成提案 / patch，不要求立即迁移 JSON。

## 新游戏门禁

新游戏 OpenSpec 的 proposal 或 design 必须说明：

1. 是否使用 `GameConfigPackage` 承载静态事实；
2. 若使用，严格 JSON 文件位置、schema 范围、表格审查范围是什么；
3. 若暂不使用，跳过原因、影响范围和后续补齐项是什么；
4. 特殊效果哪些只需配置参数，哪些需要代码能力支持；
5. 玩家配置修正是否进入现有反馈式流程。

## 旧游戏裁定

旧游戏已有清晰 TypeScript 配置、注册表和测试覆盖时，不应为了统一格式立即重构。优先级顺序：

1. 保留现有运行时配置；
2. 如果需要审查或维护，先做同源可视化 adapter；玩家模式默认只读展示并提交提案，维护者模式可编辑草稿并生成待应用 patch；
3. 如果需要字段级修正提案，再让 adapter 输出配置包表格模型；
4. 只有当官方真相源本身要迁移时，才把旧配置逐步搬进配置包。

具体旧游戏属于哪一类，不在本标准维护；应由对应游戏专项文档或任务卡裁定。

## 旧游戏同源 adapter 模板

旧游戏需要配置审查表或内部维护入口时，默认先做同源 adapter，不迁移官方真相源：

1. 读取该游戏当前真实运行入口，例如卡牌注册表、阵营目录、牌组构建器或运行时 manifest；
2. 建立字段覆盖清单和审查行；素材可见性、入口验收和表格交互不在本文重复展开；
3. 将现有对象映射为配置包物化表格行，保留原对象 ID、中文名、类型、阵营、数量、数值、能力 ID、素材预览和内部来源上下文；
4. 字段覆盖清单必须从规则真相源和消费代码反推，至少覆盖运行时、牌组构建、起始部署、素材加载、能力绑定和特殊规则实际读取的静态字段；禁止只看 adapter 当前字段、UI 列名或历史实现印象来判断“已经上表”；
5. 表格字段必须能回指原配置对象，字段路径可采用 `legacy.<gameId>.<source>.<objectId>.<field>` 或项目内等价稳定路径；
6. 表格页面只能消费 adapter 暴露的字段清单生成列、字段值、字段适用性和编辑解析规则，并接入共享配置审查工作台；不得在页面里再维护一套独立列清单、字段类型清单、提案状态机或表格交互流程；
7. adapter 测试必须覆盖：玩家可录入 / 可修正的必审字段都在可见列中、内部定位 / 图集索引 / 运行时 debug 字段不在主表列中、每个必审字段都有证据来源、每个可编辑单元格有字段路径、字段值来自同一物化对象；
8. adapter 不得把旧游戏运行时切到配置包，不得在运行时直接改写现有配置对象，也不得额外维护展示专用副本；
9. 若玩家提交修正，提案保存 adapter 生成的字段路径、当前值、修改后值和证据；AI / 人工审查后再决定是否另建正式迁移或代码修改任务；
10. 若维护者编辑配置，adapter 只能生成待应用 patch；正式应用必须回到唯一 TypeScript 配置源并完成类型、领域和回归验证。

具体旧游戏的 adapter 来源、必审字段和字段名裁定，放对应游戏专项文档；本标准不维护单游戏字段清单。
