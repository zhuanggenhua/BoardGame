# 规则合同审计门禁

> 适用：用户反馈“规则不对 / 等级效果不一致 / 不是这个等级能做 / 审计漏了 / 回归了”，或本轮准备修复卡牌、技能、Token、状态、阶段结算等规则 bug。

## 落点

- 本文档属于 BoardGame 项目通用层，只写跨游戏都成立的判断方法。
- 单游戏规则答案、卡牌原文、技能等级差异、截图裁定结果，必须下沉到 `docs/games/<gameId>/...`、对应 evidence、用户故事或游戏专项 workflow。
- 数据录入全流程仍归 `.spec/skills/data-entry-workflow/SKILL.md`；本文档只规定规则 bug 修复前如何消费和校验已有录入合同。

## 规则提炼先行门禁

规则文本太长不是允许跳过基础规则的理由。只要本轮要实现、重构或审计一条规则链，必须先把规则源提炼成可消费合同，再写代码或教程：

1. **先列基础对象**：至少列出规则对象、触发条件、玩家选择、状态变化、抽牌 / 掷骰 / 移动 / 结算结果、结束条件。
2. **先拆符号和字段**：规则书里的图标、颜色、牌型、场地/区域标记、阵营可见性、次数限制等，都必须落成结构化字段；不得只把它们留在图片、长文或 UI 文案里。
3. **先定实现消费点**：每个合同字段必须写清由哪类数据、命令、事件、读模型或 UI 承接消费。若卡牌 / 状态 / 持续效果已存在结构化生命周期字段，到期、清理、返回、弃置等生命周期结算必须从该字段统一投影；不得在能力文件、handler、reducer 或 UI 里按对象 ID 另写同一时机的生命周期入口。确实存在同名基础版、POD 版或变体规则差异时，先把差异写回各自结构化字段或显式标成 separate，再让运行时按数据消费。
4. **先推导交互权限**：凡规则子句会让玩家、AI 或系统按钮操作，必须按 `.spec/knowledge/standards/rule-driven-interaction-design.md` 推导授权玩家、第一入口、允许命令、禁止命令、窗口关闭条件和消费者；不得从当前焦点玩家、当前视角玩家或当前回合玩家直接推出权限。
5. **缺字段先阻塞**：如果规则源明确存在某个字段，但当前 catalog / 静态数据 / 合同表没有对应字段，只能标 `needs-contract` 或 `implemented-needs-remodel`，不得用轮换顺序、默认值、旧实现习惯或“发现对象”这类泛化词替代。

图标、颜色、牌型、场地/区域标记、阵营可见性或次数限制只要会决定抽取类别、目标类型、结算分支或玩家权限，就必须成为合同字段；实现不能用运行时顺序、默认值或 UI 文案临时替代。

### 成本字段的否定语义

规则合同必须把“成本”作为独立原子字段核对：规则原文明确写出消耗、支付、弃置或次数限制时，必须在实现中填写对应成本；原文没有成本时，成本字段必须为空，不能因为对象属于 Token、能力或资源系统就默认扣除资源。测试必须根据原文断言资源确实扣除或保持不变，并断言消费事件与规则一致。

同样，规则没有写“每回合一次”时，不得从按钮习惯、旧角色实现、`oncePerTurn` 或测试夹具推导该限制；规则写出次数限制时，必须记录限制粒度和重置边界。规则写“每回合每个效果一次”时，不能错误建模成整组能力共用一个次数标记。

### 累计档位与复合能力

规则把同一资源对应到多个档位时，必须分别核对：每档使用门槛、每档实际成本、每档效果、每档次数限制、次数重置和资源扣除后的后续可用性。若门槛是递增资源数量，默认按累计门槛建模：持有更高数量时低档位同时满足门槛；除非原文明确“只能选择一个档位”或其它互斥语义，不能把档位当成互斥选项。

完整性测试至少覆盖：高资源时低档位可用、高档位可用、使用一档后剩余资源影响其它档位、同一档本回合重复使用被拒绝、不同档位按“每个效果”分别判断，以及回合 / 轮次重置后的再次可用性。

### 主真相源高于已锁合同

`locked` 只表示录入合同已经完成来源登记和字段锁定，不表示它可以推翻主真相源。只要完整规则图片、规则书或用户指定材料与合同不一致，必须以主真相源为准，将合同降级为 `disputed`，先修正录入合同，再审实现；代码、i18n、测试、旧 evidence 和审计摘要都不能反向成为规则来源。

## 批量规则实现的商业验收范围

当用户要求“整包 / 全牌库 / 全流程节点 / 全场地组件 / 全能力 / 所有组合”时，默认目标是可审计、可维护、可交付的批量规则闭合，不是无限组合穷举。批量审计先识别共享模块和代表链；共享模块深审一次后，重复对象只做引用 / 等价校验，除非出现不同触发时机、候选生成、流程态、清理或其它独有语义。

| 验收面 | 必须证明 | 禁止口径 |
| --- | --- | --- |
| 缺口分层 | 先分 `功能实现阻塞`、`当前范围验证缺口`、`审计留档缺口`、`非阻塞扩展`；只有会影响规则对象、合法动作、候选生成、资源消耗、流程态、共享消费者或最终权威状态的条目才算功能阻塞 | 把额外排列、额外截图或更宽覆盖拖成无限组合测试 |
| 对象全集 | 每张卡、场地/区域组件、流程节点、能力或状态都有独立行，写清规则真相源、结构化字段、实现状态、证据等级和残余风险 | 对象全集缺行却宣称已审 |
| 主链逐对象 | 每个对象的主触发、玩家选择、结算结果和最终权威状态至少有领域行为证据；有玩家入口的对象还要有真实页面或等价 Board 代表链证据 | 只凭一条代表 E2E 或几张截图宣称整包完成 |
| 关键组合 | 只覆盖会改变规则消费者的组合：伤害与减免 / 防护 / 死亡保护，随机与重掷 / 替代 / 固定值，场地目标与区域 / 已发现状态，特殊对象转移与阶段风险，流程节点与胜负 / 私密信息 / 阵营可见性等 | 对不会改变触发、候选、资源、流程态、共享消费者或最终状态的排列做全排列 |
| 代表链判等 | 触发时机、候选生成、交互入口、payload、resolver / handler、最终权威状态六项等价，差异仅限名称、文案、数值、图集、目标枚举或筛选参数；每个复用对象登记代表对象、判等依据、独有差异和残余风险 | 只因同名 helper、相似按钮、相似文案或同一 `sourceId` 家族免审 |
| 独立补证 | 新增或不同的触发时机、资源消耗、目标生成、可选 / 强制语义、流程态、清理、死亡保护、减免、重掷、保密 / 阵营可见性、阶段切换 / 终局、真实入口语义 | 借代表链完成独有语义 |
| E2E / 截图 | 用于关键玩家链、时序家族代表、高风险组合和用户点名链；用户点名“完整端到端”的对象才按 [`e2e-verification.md`](e2e-verification.md) 六段模板收口 | 默认全牌库逐牌逐组合跑六段截图 |
| 完成用语 | 只用可复查结论：`对象全集闭合`、`关键组合闭合`、`代表链判等矩阵无待补项`、`残余组合清单为空`；任一行 `partial / blocked / disputed / pending` 只能写进行中或局部闭合 | 写“所有组合完成”“差不多完成”“再补几个” |
| 证据分层 | 领域测试、Board 代表链、注入态 E2E、截图候选、规则书阅读 E2E 分属不同层；evidence 必须写清每层不能证明什么 | 把组件代表链外推成自然 Playwright 链、截图链、负向分支和所有消费者组合已完成 |
| 对外汇报 | 按 `对象全集录入`、`主链逐对象实现`、`关键消费者组合`、`真实入口 E2E / 截图`、`残余矩阵清零` 分层说明剩余和估时 | 用小切片时间冒充整包剩余时间 |

## 第一门禁：先判断录入合同是否被实现正确消费

规则 bug 的第一步不是直接重看图片，而是先找当前仓库里已经确认的规则合同：

- 录入核对表、规则原文矩阵、evidence 子句表、user story、游戏规则文档或已锁定 workflow 产物。
- 当前游戏内可见/静态规则描述，例如技能描述、卡牌描述、Token 描述、状态描述、基础版/升级版描述和对应中英文文案。
- 若合同状态是 `locked`，先判断当前实现是否正确消费这份合同。
- 旧单测、旧 E2E、旧实现、旧注释、旧 i18n 文案只能说明“系统现在怎么运行或怎么错”，不能单独证明规则正确。

如果实现与已锁合同冲突，默认这是实现 bug：先按合同修实现，并把旧测试或旧证据降级为失效证据。

### 规则流程不是可选 UI

当规则书、读本、任务卡或事件书要求“公开揭示、指定玩家秘密阅读、分阵营/分角色阅读、开局叙事、目标承接、阶段提示、结局朗读”时，这些不是装饰性文案，而是规则指定的信息流和流程节点。实现审计必须把它们拆成合同字段：谁能看到、何时出现、是否公开、是否保密、承接哪个目标或状态、读完后进入哪一步。

此类流程只要缺一段玩家应读的正文、把私密内容公开给了不该看的玩家、没有把开局叙事接到目标、或没有在结局阶段朗读对应结局，都按“规则流程未实现 / 合同未消费”处理，不得降级成小文案优化。涉及玩家以阅读原文为目的的正文时，还必须同时满足 `.spec/knowledge/standards/data-entry.md` 的原文展示门禁；没有逐字原文或正式翻译原文时只能标 `blocked / disputed`，不得用摘要冒充原文正文。

沉浸式原文阅读器不得承接机械 setup。setup、准备清单、标记放置、开局记录、目标摘要和胜负条件是规则承接信息，应落在目标卡、任务面板、规则提示或帮助页；它们可以与原文共享来源合同，但不能混入“开局叙事 / 私密阅读 / 结局朗读”的正文页。审计时只要发现 setup 被塞进沉浸式书页，就按“信息架构 / 流程承接错误”处理，而不是按普通文案命名问题处理。

规则流程审计必须输出“节点覆盖矩阵”，至少包含以下行：公开揭示、私密阅读、开局叙事、目标承接、结局朗读。每行必须写清：规则原文定位、当前实现入口、可见玩家、保密玩家、截图或测试证据、当前状态 `covered / missing / blocked / disputed`。任何一行缺证据时，整条流程不得写“已实现 / 已收口 / 已验收”。

截图只能作为这张矩阵的证据之一，不能反过来替代矩阵。只看到书页、弹窗、按钮或一段正文，最多证明“有阅读 UI”；如果截图没有同时表达可见对象、公开/秘密边界、对应流程节点和读完后的承接结果，就不能证明“公开揭示 / 私密阅读 / 开局 / 目标 / 结局”已经完成。

### 反馈断言与当前描述的分流门禁

处理规则 bug 反馈时，不得把反馈断言自动当成最终规则真相，也不得反过来直接否定反馈。这里的反馈断言包括对话描述、线上反馈记录、截图/红圈标注、日志解释、测试观察和交接摘要里的 bug 表述。必须先做三步分流：

1. **拆反馈断言**：把反馈里的触发条件、骰面/图标、阶段、目标、伤害、资源、状态、基础版/升级版差异拆成独立断言。
2. **对当前描述**：逐项比对当前技能/卡牌/Token/状态描述和已锁录入合同。
3. **决定下一步**：
   - 若反馈断言与当前描述/合同一致，默认先查实现是否正确消费合同；此时不要为了“谨慎”反复回图。
   - 若反馈断言与当前描述/合同不一致，默认先回图面、规则书、OCR、evidence 或用户故事复核，因为反馈来源可能记错、看错、混版本或被中间摘要改写；在合同未重新锁定前不得改正式规则逻辑。
   - 若用户当轮明确裁定要偏离图片或规则书，先按 `docs/user-stories/README.md` 留档为用户故事，再按该用户故事修实现。

## 外部脚本 / TTS 还原零猜测门禁

当本轮目标是从 TTS Lua、Workshop JSON、解包资产、旧平台脚本、规则插件或其它外部实现里还原规则、UI、自动提示、配置流程时，默认先建立证据矩阵，再进入实现。

### 核心不变量

| 不变量 | 强制要求 |
| --- | --- |
| 脚本扫描先行 | 用户提到 TTS、Workshop、中文 mod 或外部脚本“可能能补逻辑”时，先扫 Workshop JSON 顶层 `LuaScript / XmlUI / LuaScriptState`，再统计 `ObjectStates` 内对象脚本；最低汇报 `OBJECT_COUNT`、`SCRIPTED_OBJECT_COUNT`、全局脚本是否为空、对象脚本是否为空 |
| 空脚本降级 | `SCRIPTED_OBJECT_COUNT=0` 或只有默认空壳 `function onLoad() end / function onUpdate() end` 时，只能写“可参考资源、摆件、牌堆顺序、地图、setup 信息”，后续规则实现回到规则书、卡牌文本、领域测试和现有代码 |
| 证据落地 | 脚本扫描路径、统计结果和结论必须进最终汇报或 evidence；扫描失败则停在“脚本真相源未锁定” |
| 定位证据 | 脚本事实定位到函数、变量、分支、返回值或事件；资产事实定位到 GUID、JSON 对象、模型、贴图或截图；运行行为定位到真实入口、E2E 截图、日志或复现步骤 |
| 禁止猜测 | 函数名、变量名、对象名、贴图名只算线索；必须追到实际读写、返回值、显示文本、可见性或触发路径，不能用直觉、同类经验或旧实现背书 |
| 真实素材 | 已定位真实 token、筹码、棋子、牌、模型或贴图时，运行 UI 必须接入真实素材或可追溯派生产物；未经用户当轮批准，不能用文字按钮、CSS badge、自绘图标、几何图形或相似占位冒充还原 |
| token / marker / figure | 规则要求放置组件时，必须证明运行对象使用同一语义家族的正式资源，且代码引用命中源图、压缩产物和 manifest / 索引；E2E 通过或截图占位只能证明交互链存在 |
| 未锁定不实装 | 脚本复杂、资产缺失、UI 承载不唯一或可见性不清时，标为 `blocked` 或 `disputed`，写明最小证据缺口；不得先造“差不多”的正式规则 |
| 不派生新配置 | 外部脚本只有一个可见开关或配置项时，不因实现或测试方便拆出额外玩家设置；除非脚本、规则书或用户故事明确存在独立配置 |
| 临时近似标注 | 用户允许临时近似、占位或体验保护时，代码、测试和汇报都标“临时近似 / 非 TTS 还原 / 待脚本证据复核”，不得称为“规则已还原”或“脚本已对齐” |

### 最小证据矩阵

进入实现前，至少列出以下字段；任一关键字段缺失时，不得把该项标为完成：

| 字段 | 要求 |
| --- | --- |
| 规则 / UI 项 | 用户关心的现实对象，例如“牌型提示”“扩展开关”“工具牌效果”。 |
| 脚本锚点 | 具体文件、函数、变量、分支或返回值；不能只写“Lua 里有”。 |
| 资产 / UI 锚点 | 具体 GUID、JSON 对象、贴图、模型、截图或明确“脚本按钮无贴图”。 |
| 当前实现 | 当前 Web / 目标实现到底怎么做。 |
| 差异结论 | 已对齐、缺字段、冲突、未找到、只做临时近似。 |
| 状态 | `locked` / `blocked` / `disputed`，只有 `locked` 可以进入正式实现和完成口径。 |

### 写代码前最低门槛

准备修改实现前，必须能用中文说清四件事：

1. 现在处理的具体规则或 UI 对象是什么。
2. 哪个脚本 / 资产 / 运行证据直接命中了这个对象。
3. 当前准备修改的代码为什么直接作用于该对象。
4. 修完后回到哪个真实入口、截图或测试位点验证。

四项缺一，只能继续补证据或把缺口写入矩阵；不得继续实施。

## 术语拆字段门禁

规则对象不能只按口头简称归类。遇到卡牌、技能、Token、状态或阶段相关反馈时，必须先把用户描述拆成独立字段再判断：

- `卡牌颜色/外观分类`：例如红色、蓝色、橙色等。
- `卡牌类型/使用窗口`：例如即时牌、阶段牌、响应牌、防御技能等。
- `效果目标`：改自己的骰、改对方的骰、造成伤害、获得资源、授予状态等。
- `阶段与操作者`：当前是谁的回合、谁正在掷骰、谁是响应者、效果描述限定的是哪个阶段。
- `合法性 / 奖励 / 惩罚`：能不能做、做了给不给奖励、没做到会不会受罚，必须拆成三类字段分别判断。

禁止把这些字段互相替代。特别是“某颜色卡牌”不等于“某阶段牌”，“当前处于防御阶段”也不等于“这张牌属于防御阶段牌”。如果本轮结论依赖这些字段，必须在汇报里用听得懂的中文说清现实含义，再补代码符号或字段名作证据。

合法性、奖励条件和惩罚条件也不得互相反推。规则写“攻击敌方卡牌才获得奖励 / 才避免惩罚”，只能证明奖励或惩罚的触发口径，不能自动推出“攻击友方卡牌非法”；反过来，规则允许某动作，也不等于该动作满足所有奖励、任务或触发条件。遇到这类文本，必须分别落证据：① 动作是否合法；② 是否计入奖励；③ 是否计入惩罚豁免；④ 是否满足后续能力触发前提。

## 什么时候才回图面或规则源

只有满足以下任一条件，才回到卡图、规则图、规则书、OCR、重新裁图或其它规则源复核：

1. 没找到对应录入合同。
2. 合同状态不是 `locked`。
3. 合同字段缺失，无法支持本轮判断。
4. 合同内容与用户 bug 描述冲突。
5. 同一对象存在多个互相矛盾的合同来源。
6. 用户当轮明确质疑“看图 / 红圈 / 图标 / 是不是看错图”。

进入复核时，结论只能写“规则合同未锁定 / 需复核图面 / 存在来源冲突”。不得一边保持合同 `locked`，一边在实现审计里临时猜规则。

复核后必须先更新录入合同、evidence 子句表、user story 或游戏规则文档，再按新合同修代码。

## 修复必须回写合同入口

只要本轮确认以下内容与真实规则不一致，修复范围必须同时包含这些真相入口：

- 中文规则描述、英文规则描述、i18n 文案。
- 能力定义注释、静态数据、升级版描述。
- evidence 子句表、录入核对表、规则原文矩阵。
- 用户故事或游戏专项规则文档。

不得只改 handler、reducer、测试或注释后交付。收口前必须反查：

1. 对象中文描述是否仍保留旧错误语义。
2. 英文描述是否仍保留旧错误语义。
3. 基础版与升级版描述是否互相矛盾。
4. 相关 evidence、测试名、测试断言是否仍在传播旧规则。

只要旧错误描述还存在，就只能写“实现已临时修正，规则合同未收口”，不得写“规则 bug 已修复 / 回归已收口”。

## 最小输出

处理规则 bug 时，最终汇报或 evidence 至少写清：

- 用户原始症状是什么。
- 已找到的录入合同在哪里，状态是什么。
- 当前实现与合同是否一致。
- 是否需要回图面或规则源；若需要，冲突点是什么。
- 本轮同步更新了哪些合同入口。
- 仍有哪些旧描述、旧测试或旧 evidence 未收口。
