# 分支 / Worktree 目标锁定

## 触发场景

遇到以下任一情况，先执行本文档，不得直接改代码、合并、删除或清理：

- 用户要求删分支、删 worktree、清理分支、清理工作树、合并后删除、把某边内容放回正确位置。
- 同一任务同时出现多个近名分支或 worktree，例如 `<target-game>`、`<engine-candidate>`、`<old-experiment>`。
- 一个游戏的问题或修复落在另一个游戏的分支 / worktree 中。
- 用户质疑“为什么改到这个工作树 / 分支”“入口是不是找错了”“这个工作树不是早该删了吗”。

## 五项锁定

执行任何会改变仓库状态的动作前，必须先用证据写清这五项：

1. **用户点名对象**：用户原话里的目标是哪一个分支、worktree、游戏或问题。
2. **实际 branch/worktree**：`git branch --list` 和 `git worktree list --porcelain` 里命中的精确对象、近名对象和缺失对象分别是什么。
3. **当前执行现场**：当前 `cwd` 属于哪棵 worktree、哪个分支；当前目录已有改动是否命中本轮目标。
4. **游戏归属**：用户问题属于哪个 `gameId`；准备修改的文件属于哪个 `gameId`；当前分支名或 worktree 名是否服务同一个游戏。
5. **删改影响**：删除、合并、迁移或清理会影响哪些提交、未提交改动和文件范围；若有未合入内容，必须说明它的保留落点。

五项缺任一项，只能继续只读核对或停在“目标未锁定”，不能实施。

## 删除分支 / Worktree 门禁

- 用户说“删 X”时，只能把 `X` 作为候选目标；不得因为附近还有其他旧 worktree、相似分支或刚刚排查过的分支，就改删其他对象。
- 若 `X` 没有对应 worktree，只能报告“没有工作树可删”；不得转而删除另一个 worktree。
- 若 `X` 分支存在未被 `main` 包含的提交、未提交改动，或内容是否已被主分支语义吸收尚未证明，默认结论是“有东西，不能直接删”。
- “有东西就合并，没东西就删”必须先做内容级比对：哪些内容已在 `main`，哪些只在目标分支，哪些应迁移，哪些可明确废弃。未完成比对前，不得删除分支指针。
- 删除前必须说明将删除的精确引用或目录、为什么安全、删完用什么命令/证据验证；用户只授权删除 `X` 时，禁止触碰相邻候选 `Y`。

## 清理差异包

只要发现目标分支 / worktree “有东西”，不得只说“有改动”、贴一大片 diff，或把当前 `main` 比旧分支多的内容混进结论。用户首先需要判断的是：**目标侧相对保留侧到底多出来了什么**。

- **只报目标侧独有差异**：先列 `目标分支/worktree` 相对保留侧新增、修改或独有的内容；默认不要列保留侧比目标侧多了什么。
- **按现实含义分组**：只围绕“多出来的东西”分组，例如源码实现、测试、素材/清单、规则文档、OpenSpec、项目规范/脚本；每组列 1-3 个代表路径和一句现实含义。
- **先说是否值得合并**：直接给出 `应合并 / 只捞部分 / 可删除 / 暂停确认`，理由必须基于目标侧独有差异，而不是基于分支名、文件数量或历史印象。
- **覆盖情况只作判断，不喧宾夺主**：如果当前 `main` 已有同名后续实现，只用一句话说明“这些独有内容已被后续实现覆盖 / 仍缺某几项”；不要展开 `main` 的全量新增内容。
- **禁止反向差异污染**：禁止把 `main` 比目标分支多出的文件、后续重构、无关删除列表，当作“目标分支有什么”汇报给用户。
- **风险点只说删会丢什么**：删除风险只围绕目标侧独有内容；合并风险只说会把哪些旧内容带回或覆盖当前实现。

这个差异包必须先于删除、合并、迁移或清理动作出现。用户要的是判断依据时，先交“目标侧多出来什么”，不要让用户从内部文件名、大 diff 或反向差异里自己翻译。

## 跨游戏落点门禁

当用户问题属于游戏 A，而当前分支 / worktree 明显服务游戏 B 时：

- 若准备修改的是 `src/games/A/`、`docs/games/A/`、`e2e/A/` 或 A 的资源清单，默认判为“实施现场不匹配”，必须停止。
- 只有三种例外允许继续：用户明确要求在 B 分支修 A；当前任务是跨游戏共享基础设施且 A 是必要验证对象；或已有项目文档证明 B 分支本来承载 A 的收口。
- 错误落点已经发生时，先标记为“误改侧”，再回到正确实施现场读取真相；需要吸收时必须逐项迁移，不能手工重写一版冒充合并。
- 从错误分支移除误改内容也属于仓库状态改变，必须先说明删除/保留范围；禁止用 `git reset`、`git restore`、`git checkout --` 直接覆盖。

## 汇报模板

最低汇报格式：

```text
目标对象：用户点名的是 ...
实际对象：存在/不存在的 branch/worktree 是 ...
当前现场：我现在在 ... 分支 / ... worktree
游戏归属：问题属于 ...，当前分支服务 ...
目标侧多出来的内容：源码 / 测试 / 文档 / 素材 / 规范分别多了什么，代表路径是什么
当前覆盖一句话：这些独有内容是否已被保留侧覆盖，仍缺什么
结论：建议合并 / 迁移部分内容 / 删除 / 暂停确认；原因是 ...
下一步：只读比对 / 迁移到正确现场 / 等用户确认丢弃 / 删除精确对象 ...
```

如果结论是“规范事故”，必须同时回答：

- 入口问题：是否缺少文档入口或未按入口执行。
- 硬度问题：现有规则为什么没能在动手前直接拦住错误动作。
- 新规则是否能在事故发生前阻止同样动作。
