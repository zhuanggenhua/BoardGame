# 描述到实现全链路审查规范

## 主源定位

本文档是 BoardGame **规则 / 玩法 / 机制审计的项目级 canonical-source**。它只定义跨游戏都成立的审计方法：从权威描述出发，追到实现消费、玩家真实入口、最终权威状态和证据边界。

项目级审计回答的是抽象问题，不回答某个游戏的具体规则答案：

- 真实语义是什么。
- 实现有没有消费这份语义。
- 玩家入口、命令、状态、UI、AI / 自动推进和测试是否共享同一份业务真相。
- 缺口属于功能实现、语义一致性、验证范围、审计留档还是非阻塞扩展。
- 当前结论能否支撑“已审计 / 已收口”的对外口径。

本文档不承载单游戏答案、卡牌裁定、骰面公式、场地/区域效果、教程章节安排、截图结论、历史事故清单或某个批次的对象全集。这些内容只能落到对应游戏规则合同、`docs/games/<gameId>/...`、`evidence/<gameId>/...`、用户故事或游戏专项 workflow。

旧 `testing-audit-*` D 维度分卷只保留为历史链接兼容，不再作为新的项目级审计基准。新审计以本文档的“语义 -> 消费 -> 真实入口 -> 证据”链路为基准；证据文档格式看 [`audit-evidence-template.md`](audit-evidence-template.md)，规则 bug 合同裁定看 [`rule-contract-audit.md`](rule-contract-audit.md)，E2E 与截图看 [`e2e-verification.md`](e2e-verification.md)。

## 项目级审计最小维度

审计不是机械填表。除非用户或任务明确要求更细矩阵，项目级默认只按下面六个维度裁定：

| 维度 | 要回答的问题 | 常见结论 |
| --- | --- | --- |
| 语义一致性 | 权威描述拆出的原子断言是否被完整表达，没有多做、少做、错对象或错时机？ | `语义一致` / `语义不一致` / `合同未锁定` |
| 消费完整性 | 静态定义、注册、合法性、命令、执行、状态、UI、AI / 自动推进和测试是否消费同一份真相？ | `消费闭合` / `消费缺口` / `多重真相` |
| 功能结果 | 玩家动作或系统触发后，最终权威状态是否正确变化并完成必要清理？ | `功能已实现` / `功能实现阻塞` |
| 交互可用性 | 真实玩家入口是否可见、可点、可完成；可选、跳过、多步、私有或延迟交互是否能收口？ | `真实入口已证实` / `当前范围验证缺口` |
| 共享影响 | 缺口是否位于共享 helper、系统、状态字段、UI 组件或 AI 消费者；受影响对象是否能列出？ | `当前对象` / `最小受影响集` / `候选残余` |
| 证据状态 | 旧 evidence、旧测试、截图或总结是否仍传播旧结论；当前证据能否支撑对外口径？ | `可收口` / `需降级` / `审计留档缺口` |

编号、脚本、矩阵和截图都只是帮助回答这些现实问题的证据，不是审计本身。不得把“填完编号表”“跑过脚本”“截图存在”当作审计结论。

## 全量口径

当用户要求审计某个已经锁定的派系、角色、对象组、规则族或“全量 / 全面 / 全派系 / 全对象”时，默认结论口径是**锁定范围内全对象覆盖**，不是抽样、代表性验证或只查反馈对象。

全量审计必须先列出锁定范围内的完整对象清单，并为每个对象给出结论行。覆盖方式可写 `直接验证`、`共享流程引用`、`无玩家入口` 或 `残余范围`；无论哪种方式，都不能省略对象本身的语义审计行。

“全量”是覆盖口径，不等于每个对象都单独跑真实入口 E2E。共享流程资产、配置差异轻量复核和代表链判定分别只按本文件 4.5、4.6 和 6 执行；本节不重复定义这些证明项。

## 审计流程

### 0. 锁定本轮前提

开始前必须写清四件事：

- **问题对象**：本轮审的是哪个游戏、哪类对象、哪条规则子句、哪条共享链路或哪份旧 evidence。
- **真相来源**：规则合同、已锁录入表、用户当轮原文、规则书、图片合同或其它来源中，哪一份承担本轮裁定。
- **目标入口 / 环境**：审计对象最终由哪个玩家入口、命令、系统触发、AI / 自动推进或测试入口消费。
- **验收口径**：本轮要证明功能已实现、语义一致、验证补齐、旧结论失效，还是只做范围裁定。

缺任一项，只能继续定位或标为 `合同未锁定 / 当前范围验证缺口`；不得直接写“通过”。

### 1. 锁定权威描述

审计阶段默认消费当前项目已经存在的规则文档、配置、实现、测试、evidence、已建立的数据合同或用户当轮明确提供的材料；规则合同必须能回指完整主真相源。若规则图片 / 规则书已在合同中登记且用户指出语义冲突，不能只信合同摘要，必须回看完整主真相源并以规则原文为准。

如果现有材料缺规则原文、对象归属、版本差异或图片合同，先按 [`rule-contract-audit.md`](rule-contract-audit.md) 或数据录入 workflow 标成 `blocked / disputed`。审计不能临时把实现字段、i18n 文案、测试断言或代码注释补成权威规则。

### 2. 拆成原子语义

把自然语言描述拆成可验证断言，每条断言至少说明：

- 触发条件和时机。
- 执行主体。
- 作用对象。
- 玩家是否有选择权。
- 数值、资源、状态或区域变化。
- 持续时间、清理条件和不应发生的反向路径。

复杂描述按独立交互链拆分；不同触发时机、不同玩家选择、不同目标集合、替代 / 防止、额外行动、延迟收口和可选 / 强制分支不能混成一条。

规则句中的附加条件、阈值奖励、资源获得 / 消耗、状态施加 / 移除和持续效果，必须各自拆成独立原子语义。主效果已经结算，不代表这些附加结果也已实现；每个附加语义都必须单独写清触发条件、读取的输入快照、最终权威状态和必要清理。尤其是“相同结果达到数量”“达到某个点数 / 数量后获得奖励”这类阈值规则，必须证明阈值判断读取的是规定的那组结果，不能被后续防御投、共享上下文或 UI 派生值覆盖。

对包含多个资源档位或复合主动能力的规则，原子语义还必须显式包含：使用门槛、实际成本、效果结果、次数限制、次数重置、档位是否累计解锁、一次执行后对其它档位的影响。规则写“每个效果一次”时，次数粒度必须落到每个效果；规则写“拥有 N 个 / 花费 N 个”时，门槛与成本必须分别落字段，不能只保留一个资源数字或一条总效果摘要。

如果一个分支结果内部还会产生新的随机结果、二次骰、抽牌、随机目标或随机伤害，这个派生结果必须拆成独立原子语义，不能只审主检定或分支文案。最低要单独追清：

- 派生随机何时生成，由哪个规则结果触发，是否与主检定使用独立随机消费。
- 独立随机不是只把 UI 标题拆开；随机源消费必须发生在派生事件自己的命令 / 结算时机，并能从命令、事件、状态或日志边界上证明，不能在主检定命令里提前物化，也不能把一串固定随机队列写死成同一次投掷。
- 派生结果的具体值、合计值、待分配状态和最终承受 / 获得 / 移动 / 抽取结果是否对玩家可见。
- 玩家可介入或需要确认的派生结果必须有独立确认交互；不能把派生骰、抽牌、随机目标或随机伤害与后续分配 / 选择 / 最终扣减压到同一帧，也不能让后续面板盖住派生结果本体。
- 派生结果确认后是否写入最终权威状态，并且不应被当成固定数值、文案占位或主检定点数复用。
- 如果派生结果是伤害，必须继续追到伤害管线：物理伤害是否只能由力量 / 速度承担，精神伤害是否只能由知识 / 神志承担，玩家是否有选择分配权，最终扣减是否发生在分配确认之后，死亡保护 / 减伤 / 日志 / 撤回是否消费同一结果。
- 操作日志、反馈记录、撤回 / 回滚和截图 / E2E 证据是否记录派生结果本身，而不只是记录“发生了某个分支”。
- 全量审计时，同一个派生随机共享流程的每个引用对象都必须列入对象清单；只有骰子数量、伤害类型、文案或触发分支不同，且共享流程不变量都已判等时，才允许写 `共享流程引用`。

### 3. 追实现消费链

每条原子语义都要追到真实消费者。推荐按下面顺序记录证据，但不要求机械填固定表格：

| 消费层 | 要确认什么 |
| --- | --- |
| 静态定义 | 配置、规则数据、i18n 和资源引用没有把语义写偏 |
| 注册与合法性 | registry、validator、候选生成和权限判断能让正确玩家在正确时机行动 |
| 命令与执行 | command、handler、system、resolver 或 reducer 实际执行了该语义；若一次玩家确认、一次 AI 决策或一次规则机会会生成多条命令，必须审计这组命令是否保持同一业务事务边界，没有被 UI、乐观更新、网络合包或恢复链路拆成独立动作 |
| 最终权威状态 | HP、资源、Token、区域、阶段、队列、pending / deferred 状态或等价权威状态正确落地并清理 |
| 玩家真实入口 | 正式 UI 中可见、可点、可确认、可跳过；同一可见对象同时存在多个合法动作时必须先让玩家仲裁动作意图，不能由默认点击、拖拽或兜底逻辑吞掉其它合法动作；玩家看到的文案和状态没有把入口层级讲错 |
| AI / 自动推进 | AI、watchdog、auto-continue、阶段推进或服务端恢复消费同一合法动作真相 |
| 测试与证据 | 单测、GameTestRunner、E2E、截图或日志直接覆盖当前断言，而不是只证明相邻现象 |

遇到“打出时 / 可打出 / 改为打出 / 作为额外打出 / 从手牌发动”这类描述，审计不得只搜文案或只看单张反馈牌。最低对象全集必须合并四个来源：玩家可见描述、静态能力 / 卡牌元数据、命令合法性验证、正式 UI 消费点。扫出的每个候选都要分类为同牌动作仲裁、其它手牌替代 / 防止 / 改写、响应窗口手牌、外部区域额外打出、纯场上能力或非同类；只有分类后才允许说哪些是同类问题、哪些确认不受影响。

审计必须追到最终权威状态；`prompt / modal / pending / sourceAbilityId / 按钮可点` 只能证明流程中段，不能替代功能结果。

### 4. 判缺口类型

每个发现先分类，再决定是否阻塞当前口径：

| 分类 | 含义 | 默认处理 |
| --- | --- | --- |
| `功能实现阻塞` | 规则对象、玩家合法动作、候选生成、资源消耗、流程态、共享消费者或最终权威状态确实错误 | 修实现并补验证 |
| `语义不一致` | 实现多做、少做、错对象、错时机或把可选 / 强制 / 替代语义理解错 | 回权威描述与消费点修正 |
| `当前范围验证缺口` | 实现可能正确，但缺本范围必要证据、负向断言、真实入口或关键组合证明 | 补证据或降级口径 |
| `审计留档缺口` | 证据存在但没有被总账消费、旧结论未回写或截图目录未索引 | 回写 evidence；不得误报成功能未实现 |
| `非阻塞扩展` | 不改变当前范围规则正确性的额外排列、额外截图或更宽覆盖 | 记录为范围外扩展，不阻塞当前收口 |
| `合同未锁定` | 真相源缺失、冲突或对象归属不清 | 转入录入 / 合同裁定；不得写通过 |

### 4.5. 抽取共享流程审计资产

当两个以上对象确实消费同一个流程时，先审流程本身，再让对象引用流程。共享流程审计必须记录：

- `sharedFlowId`：稳定、可搜索，命名到流程职责而不是单张卡名。
- 一次性审计范围：流程入口、正式 UI / 命令入口、候选生成、权限、payload、命令组事务边界、执行入口、最终权威状态、清理语义、AI / 自动推进和测试证据。
- 流程不变量：哪些行为必须对所有引用对象一致。
- 可配置差异：哪些字段允许不同，例如数值、数量上限、目标基础集合、文案、图集 slot 或 sourceId。
- 禁止引用条件：新增目标类型、新响应窗口、新资源消耗、新状态生命周期、新 UI 控件、新 AI 合法动作、新最终权威状态，或任一不变量无法确认一致。
- 失效影响面：如果该流程出 bug，应重审哪些引用对象；如果只是某个对象语义错，只重审该对象和同语义族。

共享流程资产可以落在同一份 evidence 的“共享流程审计表”，也可以引用已有 evidence；但引用者必须写出本对象的一致性核对，不能只写“同样流程”“同类卡”“复用 shared helper”。

### 4.6. 配置差异的轻量复核

已经建立 `sharedFlowId` 后，数值、数量上限、费用、文案、图集 slot、sourceId 等只要被写进该共享流程的“允许配置差异”，后续变更不要求重审整条流程链路。它要证明的不是“流程重新跑了一遍”，而是“本次变更仍然只落在允许配置差异里，流程不变量没有变”。

配置差异复核的最低证据：

| 证明项 | 要写清什么 |
| --- | --- |
| 共享流程未变 | 本对象仍引用同一个 `sharedFlowId`，实现入口、handler / resolver / reducer 路径没有换 |
| 变更字段可配置 | 变更字段和旧值 / 新值是什么，并能对应到共享流程资产里的“允许配置差异” |
| 流程不变量未变 | 触发时机、候选生成、权限判断、交互入口、payload 结构、最终权威状态类型、清理语义、AI / 自动推进消费没有改变 |
| 最小验证 | 只补与该配置相关的边界或最终状态断言，或引用已有共享流程测试并说明它已覆盖执行链路 |

例子：

- `+2 power` 改成 `+3 power`：只复核数值字段落地到最终权威状态，必要时补一条 finalState 数值断言；不重审选择器、按钮、handler 和清理链。
- `最多 2 个目标` 改成 `最多 3 个目标`：复核数量上限和边界输入，确认候选生成、权限、payload shape 和清理语义未变；不重审 UI 外壳。
- `己方随从` 改成 `任意随从`：这改变候选生成 / 权限判断，不属于配置差异，必须直审该对象。
- 新增响应窗口、资源消耗、状态生命周期、新 UI 控件、新 AI 合法动作、新阈值奖励或新最终权威状态：不是轻量复核，必须重审受影响流程。

共享流程的“允许配置差异”只允许覆盖不变量已经定义的参数，不得用配置差异掩盖新增或遗漏的最终权威状态。若对象新增了资源获得 / 消耗、状态施加 / 移除、Token 变化、阶段 / 队列变化或其它玩家可观察的结算结果，即使命令入口和 UI 外壳与旧对象相同，也不能按代表链或轻量配置复核收口；必须为该对象补独立原子语义、消费链和最终状态证据。

### 5. 控制范围和扩审

审计默认只覆盖本轮已锁定范围。发现问题后是否扩审，取决于直接影响证据：

- 缺口位于共享消费者、共享状态字段、共享 UI 组件、共享 AI 合法动作或共享规则合同，扩到可列出的最小受影响对象集。
- 只是相似命名、同批次、同主题、同素材包，不能自动扩成整批审计；只能登记候选残余。
- 扩审前必须在 evidence 或任务记录里写清触发证据、纳入对象、排除对象和理由。

### 6. 复用共享流程 / 代表链

共享流程或代表链只能在以下事实都一致时复用：

- 触发时机等价。
- 候选生成和权限判断等价。
- 玩家真实入口等价。
- payload / command 结构等价。
- 多命令动作的事务边界等价。
- resolver / handler / reducer 消费路径等价。
- 最终权威状态和清理语义等价。
- AI、自动推进、恢复或跳过逻辑没有新增消费差异。

任一项不同或未确认，就只能复用较浅层证据，并把本对象剩余差异写成当前范围验证缺口或功能实现阻塞。禁止因为命名相似、描述相似、界面外壳相同、同属一个派系或同批实现，就省略一致性核对。

代表链复用的结论写法：

- `passed via shared flow` / `passed（共享流程引用）`：对象语义已经独立审计，流程差异只在配置或参数，且上方一致性核对都写清。它可以支撑全量审计收口。
- `representative_only`：只抽了样、只跑了代表对象、没有逐对象判等，或无法证明剩余对象只是配置差异。它不能支撑全量审计收口。
- `needs_direct_entry`：对象引入新交互、新 UI 消费、新权限窗口、新状态生命周期、新资源消耗、目标选择差异或新最终权威状态时，必须补本对象直接入口 / 测试证据，不能靠代表链外推。

## 输出最低要求

审计结果或 evidence 至少包含：

- 本轮范围和不在范围内的对象。
- 若口径是全量：锁定范围内完整对象清单，以及每个对象的直接验证、代表链复用、无玩家入口或残余范围分类。
- 若对象引用共享流程：写清 `sharedFlowId`、一次性流程审计证据、本对象逐项一致性核对、只剩哪些配置差异，以及为什么不需要逐对象真实入口 E2E。
- 权威描述或合同状态。
- 原子语义断言。
- 每条断言的实现消费点和最终权威状态。
- 玩家真实入口或说明为什么本轮不需要真实入口。
- 测试、E2E、截图、日志或人工核对证据各自证明了什么。
- 缺口分类、是否阻塞当前口径、最小补救动作。
- 旧 evidence / 旧测试 / 旧总结是否需要降级或回写。

对外口径必须和证据强度一致。只做抽样、代表链或局部对象时，不能说“全面审计完成”；只补留档时，不能说“功能已修复”；只看到入口时，不能说“玩法已收口”。
