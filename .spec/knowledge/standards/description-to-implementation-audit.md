# 描述到实现全链路审查规范

## 描述→实现全链路审查规范（强制）

> 用户说"审计/审查/审核/核对/对一下描述和代码"时按此执行，禁止凭印象回答。"检查"不算触发词，不自动启动全量审计流程；但只要本轮准备新增、修改或修复游戏机制代码，必须至少执行第零步与语义拆解门禁。

**适用**：① 新增技能/效果/被动/光环 ② 修"没效果"bug ③ 审查已有机制 ④ 重构消费链路 ⑤ 修卡牌/技能/Token 的触发次数、目标、资源、状态、阶段或自动结算异常

### 第零步：锁定权威描述

审计阶段默认只消费当前项目已经存在的规则文档、配置、实现、测试、evidence、已建立的数据合同或用户当轮明确提供的材料；不默认重新读取卡图、OCR、Wiki、网页资料或在线文本包。真相源优先级排序属于数据录入/合同建立阶段，不属于每次机制审计的前置动作。若审计发现现有证据不足、来源冲突或对象归属不清，只能登记 `blocked/disputed` 缺口；不得在审计里临时查新来源并把它写成权威结论或机制修复依据。**禁止用 i18n JSON、AbilityDef.description、代码注释作为权威输入**——这些是实现产物，可能带着错误理解。

**审计阶段来源边界（强制）**：审计第零步是确认“当前有哪些已存在证据可消费”，不是重新建立数据合同。不得在实现审计阶段临时查 Wiki、网页资料、在线文本包、旧脚本 bundle、第三方数据库、卡图或 OCR 来裁定卡面规则、对象归属。若现有证据不足，先把对象回写为 `blocked/disputed` 并说明缺口；是否进入录入复核，由用户当轮任务或数据录入 workflow 决定。

**录入合同承接门禁（强制）**：如果当前对象已经有数据录入合同状态，审计第零步必须先读取并沿用该状态，而不是重新从实现字段、旧测试或 OCR 反推规则。
- `locked`：合同中的主真相源、原子子句、索引/归属和对照差异就是本轮实现审计真相源；继续时进入定义→执行→状态→UI→测试→真实入口证据，不得无故重新读图或重录。
- `blocked`：只能登记缺少的真相源、高清图、官方原文、页码或索引；不得写机制修复、不得写规则断言测试、不得把 i18n、AbilityDef、旧测试、OCR 或实现字段补成规则结论。
- `disputed`：先裁定冲突，冲突未裁定前不得进入机制修复或通过结论。
- 无合同或待建合同：先补对象级合同表，至少写清对象、主真相源、对照源、原子子句、索引/atlas/归属、实现差异和状态；没有合同状态前，不得开始机制修复。

**录入质量与继续审计边界（强制）**：`locked` 不是跳过录入质量的口令，而是录入质量已经达标后的承接状态。数据录入阶段必须先把主真相源、可读裁图、对象归属、规则原文/原子子句、索引入口和对照差异做扎实；这样后续实现审计才不用反复重读图。若后续对照发现合同缺字段、来源冲突或对象归属不清，应先把对象回写为 `blocked` 或 `disputed` 并补合同；不得在实现审计里用实现字段、旧测试、OCR 或临时印象补规则结论。

**locked 合同续跑模板（强制）**：对象已经 `locked` 后，普通“继续”不再进入图片/OCR/录入循环。续跑只能先做合同完整性检查：对象、主真相源、原子子句、索引/归属、对照差异、状态六项都在且不冲突 → 直接消费合同做实现审计、测试补证、真实入口补证或最小修复；任一项缺失或冲突 → 先把该对象降级为 `blocked/disputed` 并回写 evidence，再补录入合同。禁止一边保持 `locked`，一边在实现审计里临时猜规则或重新录入。

**机制 bug 修复门禁（强制）**：用户反馈某个卡牌、技能、Token、状态或阶段行为异常时，改代码前必须先锁定权威描述，并把描述拆成原子断言。若当前只有截图现象、日志、旧实现、i18n 文案、AbilityDef 描述或代码字段，只能写成候选假设并继续找真相源，不得直接实施修复。像“每回合一次 / 攻击后 / 第一次 / 额外攻击 / 可以 / 必须 / 若如此”这类频率、时机、可选性和依赖词必须逐字对照权威描述；不得为了消除溢出、降噪或让测试变绿而把额外限制写进机制逻辑。

**玩家反馈修复顺序（强制）**：处理玩家反馈或用户当轮指出的卡牌/技能数值、图标、伤害类型、可用条件、升级差异时，默认顺序是 `当前描述 → 当前实现 → 原图/合同 → 用户裁定`。先把用户当轮描述拆成可验证断言，并对照当前实现；如果对象、症状、入口和验收口径都已锁定，且当前实现确实违背该描述，应直接做最小修复并补回归测试，不得为了拖延或逃避判断而无故重读图。只有当用户描述与已锁合同、旧录入、旧测试或当前实现证据不一致，或用户明确质疑“看原图 / 红圈 / 图标 / 你是不是看错图”时，才进入图片复核；复核必须按安全图片读取门禁使用轻量预览、OCR 或目标裁图。看图后如果仍与用户描述冲突、图面低置信度、不同图面互相打架或无法唯一裁定规则，只能停止在 `disputed`，把“用户描述是什么、当前实现是什么、图上实际看到什么、冲突点是什么、会影响哪些对象”交给用户裁定；不得自行选择一个最像的真相继续改代码。

**反馈原文锚点优先级（强制）**：玩家反馈里如果同时出现骰型、触发条件、技能名、伤害数值、状态图标或可点击症状，定位对象必须先按反馈原文的“最能唯一确定对象”的锚点找技能。像“12345 点不了大顺子技能”这种原文，首要对象是所有 `大顺子 / large straight / 12345` 对应技能，而不是同角色相邻技能、同卡邻近分支或最近刚改过的技能。若按技能名和按骰型得到两个不同候选，必须回到图面/合同列出候选和证据；没有证明前，禁止拿无问题的相邻技能顶替原 bug。

**同名基础/升级版本联查（强制）**：修复任一技能、卡牌或 Token 的基础版、升级版、变体版、同名分支、相同图标公式或相同 handler 时，必须同时列出并核对同族对象清单，至少覆盖 `基础版 ↔ 升级版`、`静态定义 ↔ 执行 handler`、`可用条件 ↔ 实际结算`、`测试断言 ↔ 用户反馈症状`。多数基础牌与升级牌的触发条件、骰面家族、主 handler 或公式骨架只做小幅差异；因此只要发现升级牌录入、触发条件、图标公式、伤害类型或 handler 映射错了，默认必须把同名基础版、其它升级版和共享 helper 标为高风险并同步核对。禁止只改用户点名的升级技能而不检查一级版本，或只改一级版本而不检查升级版本。若时间或证据不足，最终回复必须明确标注“已修 X，未核 Y”，不得把单点修复包装成同族全部收口。

**同族联查触发条件必须默认一致（强制）**：当一张升级牌或升级技能被证实触发条件录错时，一级版本、同名升级版、同一升级卡替换目标、同一奖励骰 handler 和同一 UI 槽位映射都必须进入联查；默认假设一级和升级后的触发条件属于同一骰型家族，只允许在图面/规则原文明确写出差异时例外。最终收口必须写明“一级版本现在是什么触发条件、升级后是什么触发条件、差异来源是什么”，避免只修升级版却漏掉基础版。

**规则术语必须查词汇表（强制）**：描述中出现专有术语（如"基础能力"、"建筑"、"士兵"等）时，必须在 `rule/*.md` 的词汇表/术语定义中查找其精确定义，不得从代码函数名推断含义。**典型错误**：函数名 `getUnitBaseAbilities` 返回 `card.abilities + tempAbilities`，但规则词汇表定义"基础能力 = 单位卡上印刷的能力，不包括其他卡牌添加的能力"——函数名暗示的语义与规则定义不一致。
### 第一步：拆分独立交互链

原子单位是**独立交互链**，不是"卡牌"或"技能"。拆分信号：
- 不同触发时机（"打出时" vs "之后每当…时"）
- 需要玩家做出新选择
- 独立的条件→结果对
- "可以/may" → 独立链，必须有确认/跳过 UI，禁止自动执行
- "代替 X 做 Y" → 拆为"消耗 X"+"执行 Y"两个原子操作

**语义边界锁定（强制）**：
- **无限定词 = 不区分**："士兵"/"单位"/"卡牌" = 所有，包括敌我双方
- **有限定词 = 严格过滤**："敌方士兵"/"友方单位" = 仅限定范围
- **禁止凭"游戏常识"自行添加描述中不存在的限定条件**
- 审查时：实现中每个 filter/条件表达式回溯到描述依据，无依据 = ❌

**自检**：交互链拼接后与原文逐句对照，每句必须被覆盖，否则禁止进入下一步。

### 第 1.5 步：语义拆解（所有描述都必须做）

将自然语言描述转化为无歧义的**原子断言列表**，每条只描述一个可独立验证的事实。

**拆解步骤**：
1. **提取动作谓词**：每个动词/动作短语是一个原子效果的起点
2. **锁定五要素**：
   - 主体（谁执行）
   - 动作（做什么）
   - 目标（作用于谁，按语义边界规则锁定。**注意**：同一技能可能有多个不同目标——自我增益目标=自己，伤害/debuff 目标=对手。实现层必须分别处理，禁止用同一个 targetId 变量覆盖两种目标）
   - 数值（固定值/动态公式，标注数据来源）
   - 条件（触发时机/前置条件/资源消耗）
3. **识别复杂语义模式**并按策略展开（见下方「复杂语义模式」）
4. **输出**：`[条件] → [主体] 对 [目标] 执行 [动作]，数值=[数值]`

### 第二步：逐链追踪八层

用原子断言列表作为对照基准：

| 层 | 要点 |
|----|------|
| 定义 | 字段值与原子断言一致 |
| 注册 | registry/白名单同步 |
| 执行 | 逻辑存在且语义一致。数据来源/计算方式/作用目标与断言匹配。**函数名不是证据（强制）**：不得因函数名"看起来对"就跳过实际返回值验证。必须追踪函数体确认返回值与权威描述一致。典型：`getUnitBaseAbilities` 名字暗示"基础能力"，但实际返回 `card.abilities + tempAbilities`，与规则定义的"基础能力"不一致 |
| 状态 | reduce 持久化正确。**事件副作用审计**：reduce handler 中除"持久化本事件状态变更"外的逻辑都是副作用嫌疑（如递增计数器、修改无关字段），须逐个确认合理性。同一事件类型在不同阶段（自动触发 vs 手动激活）是否需要不同处理？ |
| **消耗** | **（D11 新增层）reducer 中消耗该资源/额度的分支逻辑是否正确？条件优先级是否正确？多来源并存时消耗的是正确的来源？消耗后不影响其他来源的剩余量？** |
| 验证 | 影响其他命令合法性？**两阶段冲突**：自动触发阶段的计数/状态变更是否导致后续手动激活验证拒绝？ |
| UI | 反馈/入口/提示同步。角色反转上下文中角色字段与约定一致？**UI 读取的字段是否与 reducer 写入的字段一致？多来源聚合是否完整？** |
| i18n | 全语言有条目 |
| 测试 | 触发→生效→状态正确。**测试通过但语义错误 = 测试有 bug**，须同时修复实现和测试。**否定路径测试**：额外额度消耗后正常额度不变？基地限定额度不影响其他基地？ |

### 第三步：grep 消费点

ID 只出现在定义+注册 = 消费层缺失。

### 第四步：交叉影响

新增交互链是否触发已有机制连锁？列出路径并确认。

"交互链 × 八层"矩阵，每条链附权威描述原文，每格 ✅/❌ + 证据（文件名+函数名），❌ 立即修复或标 TODO。禁止模糊结论。

## 复杂语义模式参考

> 语义拆解（第 1.5 步）遇到以下模式时，按对应策略进一步展开。

| 模式 | 识别信号 | 拆解策略 |
|------|---------|---------|
| 条件分支 | "如果/若/当…则…否则…" | 拆为独立路径（含隐含的"否则无效果"），每条独立追踪八层 |
| 组合效果 | "造成 X 并获得 Y" | 拆为原子效果序列，标注顺序依赖 |
| 时序依赖 | "先…然后根据结果…" | 画因果链，验证前置结果正确传递 |
| 升级变体 | "Level 2: 从 3 变为 5" / 同名技能存在基础版与升级版 / 升级牌录入已证实错误 | 建 `字段×等级` 差异矩阵，逐字段验证定义层+执行层+i18n 层一致；修任一等级必须联查同名基础/升级版本；升级牌录入错时，同族基础牌与其它升级牌默认高风险，不得只改单边 |
| 条件累加 | "每有 1 层 X，额外 Y" | 验证动态公式、边界值（0/满） |
| 互斥选择 | "选择 A 或 B（不可同时）" | 验证互斥约束在验证层+UI层双重保障 |
| 触发条件组合 | "当 A 且 B 时" | 列条件真值表，验证条件真值组合；不等于对象/场景全排列 |
| 跨阶段效果 | "本回合…下回合开始时…" | 标注生命周期起止点，验证 tick/清理 |
| 跨机制交叉 | 效果涉及多个机制标签 | 列出标签的所有消费点，确认交叉场景正确处理 |
| 角色反转 | 防御阶段"攻击者"实际指防御者 | grep 角色反转上下文，验证角色字段与约定一致 |
| target 间接引用 | custom action 中框架自动设置的 target 与 handler 实际业务目标不同 | 列出 handler 所有伤害/状态变更事件的 targetId 来源，确认进攻伤害用显式对手 ID、自我增益用上下文目标。同一 handler 内两种目标必须分别处理 |

## 教训附录

> 审查时用 D1-D50 维度，此表仅供类似场景参考。

**核心教训**：
- 语义保真（D1）：实现必须忠实于权威描述，禁止添加/删除/修改描述中不存在的限定条件
- 句号不等于隐式条件（D1/D1.5）：没有 `if you do / 若如此` 等依赖词时，后句不能默认要求前句成功
- 边界完整（D2）：所有限定条件必须全程约束，不得只在入口检查
- 数据流闭环（D3）：定义→注册→执行→状态→验证→UI→i18n→测试 必须闭环
- 查询一致性（D4）：可被 buff/光环动态修改的属性必须走统一查询入口
- 交互完整（D5）：玩家决策点都有对应 UI，交互模式与描述语义匹配
- 时序正确（D8）：写入时机必须在消费窗口内，阶段结束交互必须 halt 推进
- Reducer 消耗路径（D11）：多来源并存时消耗优先级必须正确
- 写入-消耗对称（D12）：写入路径和消费路径的条件分支必须对称
- 事务状态唯一宿主（D12/D35/D36）：跨阶段 deferred 状态只能有一个权威宿主，镜像字段必须显式桥接
- 回合清理完整（D14）：临时状态必须在回合/阶段结束时正确清理
- UI 状态同步（D15）：UI 读取的字段必须与 reducer 写入的字段一致
- 审计必须通到 finalize（D35/D36）：不能只证明 prompt 创建/交互解决，必须证明最终收口消费了同一份 deferred 状态

详细案例见 git history 和 docs/bugs/ 目录。
