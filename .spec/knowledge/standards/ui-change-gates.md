# UI 改动门禁与验收入口

> 本文件只规定 BoardGame 特有的压力态、信息去向、主交互槽位和证据增量。AI 图面审计、`PASS` / `REVISE` 由项目 [`ui-audit-loop`](../../skills/ui-audit-loop/SKILL.md) 承担；最终用户开图由项目 [`show-image-to-user`](../../skills/show-image-to-user/SKILL.md) 承担；本文件不复制审计表、查看器步骤或开图失败回退。

## 0.0 既有正式高亮能力优先（强制）

- 当正式页面已经存在区域高亮、棋盘格高亮、卡牌高亮、可选对象描边、地图遮罩或等价的正式交互反馈能力时，教程、E2E 修复或视觉回归必须先修这套正式能力的目标、边界、过滤条件、视角聚焦和样式参数。
- 当正式对象本体已经可作为交互载体，例如地图地区、棋盘格、卡牌、角色、基地、token 或其它场景对象能直接点击/选择时，主路径必须优先点击对象本体；按钮、列表、圆球、编号、标牌、隐藏锚点只能作为无障碍、测试定位或已证明必要的备用入口，不能成为教程/E2E 的主要承接方式。
- 如果当前合法候选只有 1 个，但语义仍是选择目标、支付对象、骰子、卡牌、房间、角色、单位或玩家，仍然必须走“对象高亮 -> 点击对象 -> 结算”的真实对象选择流程。一级按钮只能进入/聚焦选择态，不能自动填入唯一候选后直接结算。只有完全没有对象选择、目标选择、支付、顺序、数量、可跳过/可接受分支时，才允许自动推进。
- 教程、E2E 和调试 harness 不得为了“跑通链路”预先写入唯一目标、自动进入已选目标态，或直接点击隐藏锚点代替玩家路径。正确验收必须覆盖：玩家点击一级动作、对象本体出现可见高亮、玩家点击该对象、系统再结算。
- 禁止新增标牌、气泡、圆点、编号、按钮列表、临时图层或说明壳层来替代正式高亮；这些东西只能作为已证明必要的辅助提示，不能掩盖正式高亮错位、缺失或难以辨认。
- 需要玩家继续操作的真实目标对象，除非图面本身已经极其明显，否则必须在对象本体上给出可见交互提示。可选目标应有邀请态（如绿色描边/发光/合法落点高亮），已选目标应有更强确认态；不得只在旁边按钮、面板文字或教程文案里说“请选择”，却让地图、棋子、卡牌、token 本体没有明显可操作状态。
- 如果正式高亮看起来落在错误对象上，最低排查顺序是：先核真相源数据与区域边界，再核渲染层 tone/描边/透明度，再核视角聚焦和点击命中区；这里的“核真相源”只允许读、对比、截图取证，不能直接改数据去迎合当前截图；不得先新造一套“看得见”的替代视觉。
- 如果用户反馈“能不能场景直选 / 为什么还要按钮 / 目标是选择地区吧 / 高亮区域对吗”，默认判定为交互载体或高亮消费问题，不得先新增另一套高亮模式；必须回到正式对象命中、正式高亮、视角聚焦和教程文案四项核对。
- 如果用户反馈“描边只有两边 / 左边和下边叠很多层 / 选中框不对称 / 高亮看不出完整对象”，默认判定为当前游戏的正式高亮几何失败，不得用解释文案、额外标签或更亮的单边阴影替代。动手前必须先重新绑定当前任务的游戏、真实入口、目标对象和验收截图；相邻上下文、上一次开图或兄弟游戏如果不是同一个游戏，只能当参考，不能成为修改对象。
- 如果当前游戏代码一眼看不出描边问题，必须找同类成熟端到端产物做视觉对照，例如大杀四方手牌/卡牌选中截图，再回到当前游戏截图验证四边是否均衡、是否只有一个宿主外框、是否被卡壳或附属角标叠边。兄弟游戏只提供“成熟效果长什么样”的截图证据，不得顺手修改兄弟游戏源码、测试或截图。
- 只有在证明正式高亮能力不存在、不适用于当前交互，且用户当轮明确同意新增辅助模式时，才允许新增替代提示；最终验收仍必须证明正式交互对象没有被替代提示抢焦点，且截图里玩家第一眼看到的是正式目标对象本体。

## 0.0A 表现层异常不得反向改真相源（强制）

- **触发条件**：用户反馈 UI、教程、截图、视觉高亮、视角聚焦、点击命中、提示层、选择路径或“以前看着对、现在不对”时，只要症状首先出现在画面或交互层，就触发本门禁。
- **核心不变量**：表现层异常默认先归因到消费链路：渲染、筛选、样式、视角、锚点、点击命中、教程承接、E2E 操作路径或截图入口。不得把“当前画面看起来不对”直接升级成数据、规则、素材、拓扑、真相表或录入合同错误。
- **禁止行为**：禁止为了让截图、教程、E2E 或某个视觉效果看起来对，直接修改正式数据、规则文本、素材索引、区域/棋盘/卡牌真相源、录入矩阵、测试基线或长期合同；也禁止把错误改动再写成测试预期，反向固化成“正确合同”。
- **允许改真相源的最低证据**：只有同时满足三项，才允许修改真相源：① 真相源自己的编辑器、预览器、官方素材、规则书或录入合同能独立复现错误；② 至少两个彼此独立的证据源互相矛盾，例如素材像素与 JSON 坐标、规则书与录入矩阵、编辑器选区与运行时数据；③ 已对比最后可信基线或用户确认的正确证据，证明旧真相源本身错，而不是当前 UI 没消费对。
- **默认修复方向**：若证据只能说明“画面没聚焦、没高亮、点击没落到对象、教程用了替代按钮、截图入口不对、E2E 点错路径”，只允许改表现层消费链路或测试操作路径；真相源保持不动。
- **测试口径**：测试可以防止表现层再次消费错对象，但不得把本轮未经证实的新数据值写成真相源断言。新增或改写测试前，必须说明该断言锁的是“表现层消费正确”，还是“真相源本体正确”。

## 0.0B 规则与素材驱动 UI 不得先画框后补证据（强制）

- **触发条件**：新增游戏主 UI、桌游牌桌 / 棋盘 / 战场、位图设计稿、Open Design brief、HTML/CSS 预览、imagegen prompt、主界面重做或任何规则对象、卡牌、token、骰子、棋盘、角色板、状态板会出现在画面里的 UI 改动。
- **核心不变量**：规则和正式素材是设计输入，不是设计完成后的装饰补丁。进入布局、风格、prompt、预览、截图核验或实现骨架前，必须先在本轮读取规则真相源和素材合同，并把它们写进同一份可复查的前置证据。
- **最低启动证据**：动手前至少同时具备四项：① 本轮实际读取的规则文件 / 页段；② 三条以上会改变画面主体、布局、隐藏信息或操作入口的规则结论；③ 可见主体素材账本，逐项写清正式路径、atlas/frame、状态、画面职责，以及是否属于 `approved-programmatic-runtime-ui`；④ 素材如何进入当前图像输入、reference sheet、atlas crop 或运行时渲染链。
- **禁止行为**：禁止先画一套容器、面板、文字壳、CSS 假卡、抽象 token 或临时裁图，再把规则路径和素材路径补到说明里；禁止把“prompt 里写了素材名 / 文档里列了路径 / 截图里有相似形状”称为已用素材。
- **素材职责判定**：只要正式棋盘、卡牌、牌背、token、骰子、角色板或状态板已经存在或本轮合理可查，画面主体必须由这些真实素材、正式 atlas crop 或已批准的程序化对象承担。素材优先不等于把所有运行态信息直接贴原物理素材；生命、资源、能量、冷却、进度、短状态等动态读数若原素材不适合实时显示，可在矩阵中标 `approved-programmatic-runtime-ui` 并使用清晰自制 UI。若第一眼主要看到的是外框分舱、玻璃板、说明框或后台面板，而不是这些桌游对象和贴近对象的运行态反馈，直接判 `REVISE`。
- **固定区域先于画面构图**：当规则把棋盘格、地图房间、战场区域、基地、路线节点或等价空间单位作为移动、射程、攻击、放置、控制或目标判断单位时，设计稿 / Open Design artifact / HTML 预览前必须先有 `区域 -> 对象锚点 -> 容量 / 堆叠 -> token 贴附 -> 高亮` 合同。场上对象必须有唯一所属区域；中心点不得落在区域边界、缝隙或格外；玩家一眼不能判断对象属于哪一格时，直接判 `REVISE`。可参考成熟游戏的“格子先行、对象在格内、点击对象本体”交互不变量，但不得复制其皮肤、牌区名称或规则语义。
- **核心交互不得被边缘化**：当前阻塞下一步的主决策 / 主结果对象，例如攻击掷骰、翻牌揭示、命中、伤害、治疗、支付成败、目标选择结果，必须锚在目标、来源、主棋盘上层或当前动作链路中。边栏、日志、右侧仪表盘、牌区旁角落只能承载已结算摘要、历史回看或可检视详情；若当前主结果放在这些位置，截图和设计稿直接判 `REVISE`。出稿前必须说明该核心对象为什么在这个位置，以及让位的是哪些低权重 UI。
- **用户指出失守时的处理**：用户指出“没看规则”“没用素材”“边框太多”“重新设计”或“明显不合适直接用素材的可以自己做 UI”时，当前候选稿先标 `rejected / failed-candidate`，不得继续沿旧稿调样式。后续只允许补规则读取、补素材输入链、补 `approved-programmatic-runtime-ui` 裁定、重写前置包或重新出图；AI 图面核验 `PASS` 前不得进入用户验收展示。

## 0.0C 设计稿批准与 PC 优先门禁（强制）

- **触发条件**：用户要求“设计稿 / 视觉稿 / 效果稿 / Open Design 稿 / 先看图”，或指出“PC 端没好为什么管移动端”“我通过之前你就开始实施了”等阶段越界问题时触发。
- **设计稿就是当前交付物**：本轮目标一旦锁定为设计稿，交付物只能是已过前置证据和 AI 图面核验的设计稿候选；不得改写成真实运行页、前端实现、E2E 截图或“能玩的页面”。
- **人工批准前禁止实现**：设计稿未获得用户明确人工批准前，禁止启动 dev server / 联机房间 / 真实运行页验证，禁止新增或扩展 Board/UI、运行时 HUD、动作条、PromptOverlay、页面骨架，禁止用运行页截图、E2E 通过或测试通过反推设计已经通过。
- **PC 基线优先**：棋盘、牌桌、战场、固定栏位等固定构图类游戏，PC 桌面稿 / 桌面真实页是主基线。PC 桌面被 AI 或用户判 `REVISE`、`failed-candidate`、未通过、未完成人工验收、或仍有明显规则 / 素材 / 少边框问题时，不得转入移动端适配、移动端截图、移动端 E2E 或移动端完成汇报。
- **移动端只能后适配**：移动端工作只允许在 PC 主基线已通过后作为适配阶段进入。手机截图最多证明“适配风险 / 局部适配状态”，不能抵消 PC 未过，也不能作为“整体 UI 已完成”的证据。
- **失败口径必须降级**：一旦用户指出 PC 没好或设计未获人工批准，此前的 `AI_PASS`、运行页截图、移动端截图和 E2E 绿灯必须降级为历史技术证据；当前状态写成 `REVISE / implementation-blocked / mobile-blocked-by-desktop`，并回到 PC 设计稿重构。

## 0.0D 布局与层级必须分开建模（强制）

- **触发条件**：游戏主 UI、桌游牌桌 / 棋盘 / 战场、牌区、持有物、主动作 dock、提示条、结算浮层、目标选择层、Open Design artifact、HTML/CSS 预览或设计稿改动，只要涉及“放哪里 / 会不会重叠 / 是否需要确认”就触发。
- **核心不变量**：UI 不是只分区，也必须分层。设计前置包必须先写出层级表：背景 / 底图、规则空间单位、实体对象、主交互 overlay、结算 overlay、辅助 HUD；再写允许重叠表和保护对象表。没有这三张表，不得开始布局、生成设计稿、截图核验或实现。
- **合理重叠允许**：主交互 overlay 可以压在背景、桌面、低权重底图或棋盘边缘上；结算 overlay 可以高于棋盘、卡牌和 HUD；牌区 / 持有物 / 已计划对象可以贴底、贴边或轻压桌面。前提是当前必须点击 / 阅读的区域、卡牌、token、骰子、角色、资源和印刷信息仍清楚可用，并且重叠对象有明确职责。
- **机械避让直接失败**：若为了避免和底图 / 棋盘 / 桌面重叠，把当前主动作、当前可支配对象、已计划对象、目标选择、骰盘或结果反馈挤到角落、边缘、无关空白区，导致玩家第一眼不知道点哪里、动作路径变远或右下 / 底边出现无职责空白，直接判 `REVISE / layer-model-failed`。
- **空白必须过账**：任何大块未使用空间必须写清承担的现实职责，例如安全区、临时结算层、未来展开区、对象溢出容量或明确留白。不能回答“右下为什么空着 / 空白保护了什么”的设计稿，不得送人工验收。
- **规则对象实体锚点按项目设计前置执行**：涉及卡牌、token、骰子、棋盘单位、计划区、持有区、目标摘要、放大检视或详情层时，先按项目 [`ui-design-pipeline`](../../skills/ui-design-pipeline/SKILL.md) 的“规则对象实体锚点守恒”建立 `规则对象 -> 唯一实体锚点 -> 状态 / 归属 / 详情引用` 表。公开规则对象首次出现时，玩家必须能从对象本体、稳定视觉身份和同一步结果反馈理解“这是什么、现在在哪里、谁持有、下一步能做什么”；不能只靠角落小标记、单字缩写或悬停 title 猜测。对象进入 `held / carried / attached` 状态后，实体锚点必须迁移到持有者或与持有者形成明确附着关系，不能继续以孤立房间标记表示；房间角落只承载真正属于房间的持久标记。项目验收只检查该表是否被当前稿落实；不得在审计、README 或临时证据里另写一套独立规则。
- **确认控件必须有授权**：确认 / 取消 / 提交 / 下一步类控件必须证明来自规则步骤或真实系统状态。最低要说明：确认前玩家还能改变什么；确认后系统发生什么；为什么不能通过点击当前对象、合法目标、高亮对象或来源卡直接完成。若规则或当前状态没有可撤销选择、多目标分配、费用选择、响应窗口、网络提交或不可逆危险动作，常驻确认按钮直接判为伪控件。
- **对象本体优先**：当前主动作能由真实对象本体承接时，优先让卡牌、区域、token、骰子或目标本体可点，并用高亮 / 短状态 / 费用提示反馈。按钮只负责进入模式、退出模式或处理确有依据的提交，不得替代对象本体。
- **目标/来源状态不得做成解释标签**：当玩家选择将要释放的卡牌、单位行动、攻击来源或移动来源后，合法对象必须由对象本体的高亮、描边、发光、抬升、可点击态或禁用态表达；不得在棋盘格、场上单位或目标旁常驻“可选目标 / 来源 / 对手 / 你”等解释标签来替代交互反馈。测试需要这些语义时，用不可见语义锚点和截图几何断言验证。
- **来源到目标到确认必须同组**：施法、攻击、使用行动卡、使用道具等来源对象驱动的动作，必须按 `选中来源 -> 选择目标 -> 同一工作台确认 / 取消 -> 结算反馈` 组织。确认 / 取消如果有授权，必须贴近来源对象与目标摘要；不得把来源卡、目标、确认按钮、费用摘要、骰子结果拆到两个以上无关视觉区域。确认后进入掷骰 / 伤害 / 状态结算时，确认 / 取消必须退场。
- **动作链通过要看玩家能否执行，不看字段是否齐全**：确认态截图必须能用一句玩家语言说明“我现在用哪个来源对象、目标是谁、点哪里确认、点哪里取消”。卡面已有费用 / 射程 / 目标 / 骰数时，截图不复写这些字段只能算底线；如果来源卡、目标和确认仍分散、距离过远、像三个无关入口，或法术书 / 弃牌堆抢成第二主焦点，直接判 `REVISE / player-workflow-failed`。

## 0.0E 主交互可读性与空间预算门禁（强制）

- **触发条件**：卡牌、棋盘、战场、库存、持有物、法术书、计划区、结算浮层、骰盘、token 或其它当前可支配对象同屏出现，且设计稿 / Open Design artifact / HTML 预览 / 真实页面截图用于证明 UI 是否可玩时触发。
- **核心不变量**：几何上不重叠不等于玩家看得懂。当前可执行对象必须在 100% 缩放下可读、可辨、可点；中央主舞台必须留给当前目标、来源、结算和场上对象；大块空白必须有职责。任何一项失守，截图和设计稿直接判 `REVISE`。
- **可读对象分级**：当前可执行卡 / 焦点卡 / 当前目标必须能读出名称、资源代价或核心状态；候选卡可以作为小缩略，但必须配套同屏焦点预览、hover / focus 放大、抽屉展开或分页工作台；弃牌堆、日志、完整库、历史摘要默认只做边缘入口。
- **卡面已有字段不得复写成标签墙**：当前可执行卡 / 焦点卡如果已经可读，费用、射程、目标栏、行动图标、骰数、类型、等级和效果正文默认由卡面本体承担；UI 只补运行态，例如选中态、已选目标、确认 / 取消、资源不足、等待响应和结算结果。若字段看不清，必须先放大、改裁切、加 hover/focus 或详情检视；不得用旁边一排 `费用 / 目标 / 射程` chip 替代读卡。
- **禁止小牌墙冒充主交互**：底部、侧边或角落不得把全库浏览、当前来源、已计划对象、弃牌堆和分页控制全部压成一排不可读小牌。空间不足时，优先保留当前来源 / 当前目标 / 焦点预览，把完整浏览降级到抽屉或分页。
- **阶段容量必须匹配规则任务**：规则里的大型集合、法术书、牌库、背包、市场或等价对象，在“选择 / 计划 / 浏览”阶段必须有足够可读的候选、分类、页码和焦点预览；在“执行 / 目标确认 / 结算”阶段默认退为入口或抽屉。不得把这两种状态混成一条小牌栏，也不得因为目标确认态收起法术书，就宣称计划态浏览已经友好。
- **重复预览不算解决可读性**：如果当前可执行对象已经在一处可见，再在远处放同一对象大图，只能算详情预览；它必须替代或整合原先不可读槽位，成为真实主工作台，才能证明可读性问题已解决。若底部 / 侧边仍保留不可读混合牌区，直接判 `current-object-workbench-failed`。
- **满载空间预算**：出稿前必须列出 `主棋盘 / 当前来源 / 当前目标 / 结算浮层 / 可浏览候选 / 归档入口 / 玩家资源 / 临时提示` 的最大可见对象数、最小可读尺寸、默认展开策略和让位顺序。没有这张表，不得把稿件标成 AI PASS 或送人工验收。
- **主舞台拥挤硬失败**：当前目标、场上卡、骰子、伤害 / 状态 token、路径线、候选牌、提示条和 HUD 同时聚在中央导致对象边界、归属或动作链难以分辨时，即使没有 DOM 重叠，也判 `center-stage-overcrowded`。
- **空白职责硬失败**：右下角、底边或侧边出现可承载焦点预览 / 抽屉 / 当前来源 / 结算详情的大块空白，同时主交互对象却缩小、拥挤或不可读时，判 `dead-space-failed`；不能用“留白更干净”抵消。
- **未用规则空间不得浪费主画布**：当规则只使用版图的一半、部分区域或局部战场时，设计稿应优先放大当前可交互区域；未用区域只能作为低权重背景、缩略参考或完全退场。若未用区域占据主画布，导致当前目标、来源或结算挤在一侧，直接判 `active-play-area-underallocated`。
- **范式复核硬失败**：当用户质疑“这能不能给人看 / 为什么这里空着 / 中间这么挤 / 要不要搜其它游戏 UI 范式”时，当前稿不得继续用本地几何表自证通过；必须至少补一份可回查外部范式或成熟同类来源，说明主游戏区、当前可执行对象、边缘归档、焦点预览和 HUD 的职责如何映射到本稿。缺这份复核，当前稿直接降为 `REVISE`。
- **范式复核必须落成五项空间裁决**：外部资料不能只写“已搜索”。下一稿前置包必须逐项回答：① 主游戏区是否居中且当前规则空间被放大；② 当前可执行对象是否达到读卡 / 读状态标准，缩略候选是否只作入口；③ 当前结算是否是目标附近的上层反馈，而不是侧栏或一团压在目标周围；④ 弃牌堆、日志、完整牌库等归档对象是否降为边缘入口；⑤ 右下、底边、侧边空白承担什么真实职责。任一项答不清，直接判 `external-pattern-not-consumed`。
- **玩家视角优先于几何通过**：DOM 不相交、bbox 不重叠、元素数量正确、截图尺寸正确，只能证明基础工程约束；不能证明玩家能看懂。若肉眼复核仍出现小牌不可读、中心结果团块、右下无职责、对象归属不清或下一步点击对象不明确，必须撤销 `AI_PASS` 并写成 `geometry-pass-player-failed`。
- **当前结算拥挤按注意力团块判定**：骰子、伤害、状态、目标框、路径线、短标签和 HUD 即使互不遮挡，只要在同一小区域形成多焦点团块，让玩家需要分辨“骰子属于谁、结果贴谁、还能点哪里”，就判 `center-pressure-failed`。修法优先减少、分层、贴附和退场低权重对象；不得把主结算丢到远侧栏换取干净。
- **审计必须用玩家语言**：最终审计必须回答“玩家第一眼看哪里、当前能用什么、该点哪个对象、点完反馈在哪里”。如果审计只能列几何数值、元素数量或内部 class，不足以证明玩家友好。

## 0.0F HUD / 动态提示不得挤压主布局（强制）

- 动态出现的提示 UI，例如交互提示、等待提示、状态通知、战斗短浮层和 viewport 锚点 Loading，必须使用 `absolute`、`fixed` 或 `HudPortal` 等脱离普通文档流的承载方式；禁止让它们以 `relative/static` 节点插入后挤压右侧栏、手牌区、技能区、主棋盘或其它核心槽位。
- `MobileBoardShell` 或其它整体缩放壳层内部不得直接渲染 viewport 语义的 `fixed/absolute` HUD。凡战斗提示、短浮层、悬浮 HUD、viewport Loading 等需要锚定真实视口的层，必须通过 `HudPortal` / `getHudPortalRoot` 进入 `#hud-root`。整页阶段 UI、页面级选择界面和本来就是页面主内容的全屏层不得因为“也是 overlay”就塞进 portal。
- `LoadingScreen`、`ConnectionLoadingScreen`、`CriticalImageGate` 在 board-shell 场景必须使用 viewport 锚点或 `HudPortal` 承载；根节点不得用 `relative` 覆盖 `fixed/absolute` 语义，避免跟随缩放容器偏移。
- 对已经内置居中、定位或安全区锚点的浮层组件，禁止用 `containerClassName` 完全替换默认定位类；扩展样式只能追加，或通过显式 props 调整。若必须替换定位，必须同步补截图或 DOM 几何证据证明居中、热区和周边槽位未被破坏。
- 动态提示的层级必须通过项目 z-index 常量、明确语义层或同源组件约定表达；不得用随手增大的裸 z-index 掩盖遮挡问题。提示默认 `pointer-events-none`，只有真实需要交互时才允许打开指针事件。
- 手机横屏主路径默认保留横屏桌面化构图；用户反馈“整体偏一点 / 不居中 / 像桌面端 / 不该变窄”时，优先修锚点、容器、比例、scale 与 transform-origin，不得未经证据擅自改成窄布局、双列手机竖稿或大留白路线。

## 0.1 样式修复不得擅自升级为布局修复（强制）

- 当用户只反馈 `样式 / 视觉反馈 / 描边 / 颜色 / 黑底 / 黑边框 / 阴影 / 挡板感 / 按钮质感` 这类视觉问题时，默认只允许在现有槽位内改装饰层、颜色、边框、透明度、阴影、文案短标签或选中态。
- 未经当前截图/测量证明，不得把“看起来像挡板 / 不够明显 / 有黑底”直接升级成改布局结构、区域顺序、宽高尺寸、滚动方式、锚点位置、主交互槽位或响应式断点。
- 一旦用户指出“你改布局了 / 我没让你改布局 / 只是修样式”，必须立刻暂停新增实现，先用 diff 精确列出本轮碰过的布局 hunk，并撤掉确认属于本轮越界的间距、尺寸、顺序、锚点、滚动和断点改动；撤干净后才能继续样式修复。
- 若确实判断布局本身是原始症状的直接根因，必须先停下说明：原始症状、布局根因证据、准备动的布局范围、修完回到哪个截图位点验证；没有这四项，不得实施布局改动。
- E2E 断言可以约束“不能出现黑底/黑边框/遮挡感”，但不能反向授权扩大布局范围；如果断言失败是因为测试阈值写得过宽或把样式问题误写成布局高度问题，先修断言口径，不能先改正式布局去迎合测试。
- **样式任务改变交互方式时必须升级门禁（强制）**：如果名义上只是修 bug、间距、字号、颜色或适配，但实际改变了用户发现候选、浏览/筛选、判断可操作对象、选择、确认提交或视图切换的方式，必须按新 UI / 交互模式变化执行真实入口 E2E 和截图验收，不能用“只是换展示/补入口/方便筛选”绕过门禁。

## 0.1A UI 回归问法不得当成改版授权（强制）

- 当用户问“我不是改过吗 / 原来不是这样吗 / 怎么又变了 / 是不是 PC 特殊处理 / 这是回归吗 / 为什么又坏了”这类问题时，默认目标是先定位历史基线、回归来源和当前分支差异，不是直接重排布局或设计新方案。
- 如果同一句里还带有“是不是放到某处更直观 / 要不要这样更好 / 这是不是应该在旁边”这类方案性尾句，只能标成候选建议；在回答清楚原来是什么、现在为什么变、最小还原点是什么之前，不得把该建议落成代码。
- 回归修复默认只还原被破坏的既有合同，例如删掉错误断点、恢复旧锚点、恢复旧交互载体；不得把“最小还原”升级成迁移到另一个槽位、重做主交互、合并两个按钮区或发明新空间语义。
- 准备动手前必须先写出三项证据：① 最后正常形态或历史合同来自哪里；② 当前错误由哪段实现或断点造成；③ 本轮只改哪一个最小点来恢复它。缺任一项，只能继续查证，不能实施。

## 0.0C 视觉、空间与主交互槽位细则（强制）

> 本节承载 UI 设计与布局判断；E2E 截图证据链细节回到 .spec/knowledge/standards/e2e-verification.md，默认 PC/移动参考分辨率与双端布局回到 .spec/knowledge/standards/ui-responsive-layout.md，避免三处重复维护。

- **动画/翻面/过场类 UI 必须补动态证据（强制）**：如果本轮主要变化依赖时间维度判断，例如翻面、转场、展开收起、逐帧揭示、滚动切页或其它连贯动效，单张静态图默认不够。至少还要补一份动态证据，例如 `webm/mp4/gif`，或在链路受限时提供能证明关键中间态的连续帧，并在回复中明确哪一份是主证据。
- **移动端优先**：默认至少提供 `375x812` 的移动端截图；如桌面也受影响或有额外风险，再补 `1920x1080` 桌面截图。
- **用户显式点名截图规格时，以用户指定为准（强制）**：此处默认截图策略让位给全局 `Acceptance Artifact Scope Freeze`，不得擅自补更多视口、尺寸或局部图。
- **验收截图默认先给整体构图（强制）**：只要目标是证明页面、弹窗、浮层、书页、HUD 或布局“整体是否对”，主截图必须优先给出包含周边上下文的整页/整屏/整容器视图，能同时看见目标元素与其所在构图关系。局部裁切、元素级截图只能作为补充排查材料，不能替代主验收图。
- **验收截图默认取尽量满元素状态（强制）**：当目标 UI 会与公共牌、筹码、手牌、玩家席位、按钮、提示条、资源栏等多个对象同屏共存时，主验收图必须优先选择真实链路里元素最多、空间最紧、最能暴露遮挡/漂移/挤压的状态。不能只截空态、首轮、少人数、未选择、未加载或最低元素状态来证明布局达标；若确实没有真实满载状态，必须在汇报中说明缺少哪些对象，并补一张能覆盖该对象的独立截图或几何证据。
- **满载空间预算失败直接判未通过（强制）**：当满载状态里公共牌、筹码/token、手牌、玩家席位、操作按钮同时出现时，验收必须先给这些对象划出互不侵入的空间预算，再截图和几何断言核对。任何“为了显示新增 token/角标/提示”而保留空席位、空 wrapper、高额 padding，或让本地玩家在上方重复占位、让底部手牌顶进中央牌河、让 token 外挂到公共牌/手牌之外的保护槽位，都直接判 `REVISE`；不得用“节点数量正确 / 图片加载成功 / E2E 能点”抵消。
- **贴附 token 不得覆盖对象本体（强制）**：筹码、状态、撤离 token、角标这类“贴附到卡牌/棋子/目标”的 UI，必须贴近所属对象并保持可读归属，但不得压住对象本体、牌面数字/花色、规则文字或可点击热区；多枚 token 默认按一排横向或等价清晰序列排在对象外侧。验收必须用截图或几何断言证明 token 与所属对象不相交，且玩家能一眼看出归属；禁止把“中心点贴右上角”当作合格，实际却把 token 盖在牌面上。
- **共享组件改定位必须列模式影响矩阵（强制）**：只要改动发生在共享渲染组件、共享 hook、共享样式类或同一组件被多种模式复用，例如单副/两副手牌、本地/对手、PC/移动、空态/满载、选筹/摊牌/调换阶段，动手前必须逐项写清每个模式的预期：跟随本轮一起改变、保持旧位置、隐藏、拆分分支或需要独立验收。不得因为当前 bug 只暴露在某一模式，就默认让共享组件的定位、标签、token、槽位或边距变化静默扩散到其它模式；若扩散是正确产品行为，必须明确说“也适用于这些模式”并补对应截图/几何断言。若不是正确行为，必须先拆分分支再改。该矩阵不能停留在文字判断，必须按 `.spec/knowledge/standards/e2e-verification.md` 的分支对照验证落成“目标分支 + 最近邻未改分支”的 E2E / 截图清单。
- **标签和值不得重复同一语义（强制）**：当同一行已经有独立对象标签，例如“上手 / 下手 / 玩家名 / 区域名”，相邻结果 pill 只显示结果值，例如“高牌 / 两对 / 已确认”；不得再写成“上手：高牌”，更不得形成“上手：上手：高牌”。若为了无标签状态需要自包含文案，必须按状态分支生成，不能让有标签和无标签状态共用同一重复文案。
- **截图前必须先锁真实入口与真实运行实例（强制）**：当仓库同时存在多 worktree、多 dev server、多路由入口、classic/book 并存页面、preview/draft/devtools 并存页面，或同一端口可能被旧进程占用时，截图前必须先同时确认：① 当前访问的是哪一个具体 URL / 路由；② 当前页面实际来自哪个工作区/文件路径；③ 当前端口对应的进程命令行是不是本轮要验的那份前端。任一项未锁定，不得把截图当作验收证据，更不得继续基于该图下结论。
- **看错入口/看错 worktree 的截图一律作废（强制）**：如果后续证据表明截图来自错误页面、错误样式分支、错误 worktree、旧 dev server、历史构建产物或与当前修改无关的运行实例，则该截图必须直接降级为无效证据；不得再拿它解释布局、对齐、显隐、交互是否达标。此时默认动作是回到正确入口重新取整套证据，而不是在错误图上继续讨论细节。
- **证据直指问题位点**：截图必须能直接证明“本轮重构的 UI 位点已达标”，不能用无关页或非真实链路截图代替。
- **主交互空间不得浪费（强制）**：手牌、持有物栏、主动作 dock、底部 prompt、骰盘/牌桌的当前操作区属于玩家持续盯着的主交互空间，默认必须贴近所属容器的真实边界并最大化留给对象本体。不得用固定大留白、装饰性安全垫、空的 wrapper padding 或“看起来舒服”的底部空区把主对象抬高；确有刘海、圆角、系统手势区或遮挡风险时，只能用真实安全区变量、命中区外扩或同源槽位让位处理，并在截图里证明没有形成新的死空间。
- **底部 HUD 不得抢中央流式高度（强制）**：如果手牌、持有物栏、主动作 dock 只是贴底 HUD，而不是需要占一整块版面参与上下排版的内容，默认应作为 overlay / absolute / portal 类承载贴在底边，让中央牌河、棋盘、筹码区继续使用背后的高度。禁止把底部 HUD 放进正常 flex/grid 文档流后，占掉一整条不可用高度，再让中央主区域被迫上移或缩小。
- **主交互贴边验收（强制）**：凡是改动手牌区、持有区、主动作栏、底部提示条、底部 rail 或游戏主 HUD，最终截图必须能看出主交互槽位与屏幕/牌桌/容器边界的关系。若图面下方还留有明显无语义空白，必须说明这块空间承载了什么真实信息或安全区；说不清就判为布局未达标，不得用“元素存在 / E2E 通过”收口。
- **原始 UI bug 不得用新 UI 旁路收口（强制）**：如果用户反馈的是现有 UI 的可读性、显隐、点击后状态、缩放、遮挡、位置或对齐问题，默认目标是修好并验收这个原始 UI 位点。未经用户明确要求“改成新的显示方式 / 新增提示 / 重做 UI”，不得新增 HUD、浮层、toast、辅助面板、旁路提示或另一套更显眼的组件来替代原位点；更不得用新 UI 截图宣称原始 bug 已修复。若新 UI 被提出为候选方案，必须先标注为“范围扩展方案”，并继续给出原 UI 位点仍未通过或已通过的独立证据。
- **同屏新旧 UI 并存时必须声明验收对象（强制）**：当截图里同时出现原 UI 与新增/既有的辅助 UI，最终结论必须明确本轮验收的是哪一个现实对象。原问题是卡牌内文字，就验卡牌内文字；原问题是按钮位置，就验原按钮；原问题是主交互壳层，就验原壳层。禁止因为同屏另一个更大的标签、更亮的提示或另一个入口可见，就把原对象未达标的问题说成已经解决。
- **改 UI 前必须扫描同屏旧 UI 影响（强制）**：只要本轮会新增、移动、折叠、隐藏或删除某个界面入口，动手前必须先列出同一整屏内已有的相邻入口、旧入口、同类入口，以及用户此前明确要求删除或保留的 UI，并说明本次会保留、删除、迁移还是避让。禁止只看新增 UI 自己能不能用；若同屏旧 UI 仍残留、重叠、抢焦点，或违反用户已确认的删除要求，即使新 UI 的 E2E 通过，也不得收口。
- **同屏保护槽位必须逐项过账（强制）**：游戏进行页里 `token / 状态标记 / 资源条 / 血量与属性 / 玩家面板 / 阶段条 / 骰盘 / 牌库与弃牌堆 / 手牌与持有物 / 当前 prompt / 主动作入口 / 日志或目标摘要` 都是保护槽位。凡是新增、移动或改定位一个 UI，动手前必须逐项写清这些槽位是保留、避让、迁移、折叠还是本轮不相关；截图和几何断言也必须覆盖受影响槽位。缺这张清单时，不得开始实现；缺截图证据时，不得收口。
- **对象内部保护槽位也必须逐项过账（强制）**：不要只检查整屏 HUD。凡是把新 UI 贴到卡牌、基地、棋盘格、单位、房间、玩家面板或其它主对象上，动手前必须先列出该对象自身已经承载的附属槽位，例如持续牌、大型常驻牌、附着牌、力量 / 状态 token、放大镜、短操作徽章、可选高亮和已展开浮层，并说明新对象是复用、避让、折叠还是另建同源附属行。对象边缘、上缘、角落和 hover 浮层不等于空位；若满载状态里新 UI 会覆盖或挤压既有附属槽位，直接判 `REVISE`。
- **新 UI 禁止抢占 token / 状态 / 资源槽位（强制）**：token、状态标记、资源、生命/属性、阶段、骰盘、牌堆、手牌这类玩家持续读取的槽位不是“空白位置”。未经用户明确批准迁移，任何浮层、特写、提示条、关闭按钮、阅读卡、toast 或辅助控件不得放进这些槽位、覆盖这些槽位、把这些槽位挤出视线，或让它们和新 UI 共用同一视觉焦点。若确需迁移，必须同时证明旧信息有等价新承载、玩家第一眼能找到、原槽位不会留下误导残影。
- **隐藏/删除 UI 不得造成父布局塌陷或主区域漂移（强制）**：当本轮按需求隐藏、折叠或删除某个可见块时，验收不能只证明该块消失或不占位；还必须回看同屏父容器内剩余主对象的位置关系，尤其是公共牌河、棋盘中心、主按钮、手牌区、筹码区、提示条等固定槽位。若删除对象后相邻主区域被吸到上方/下方/一侧，或原本中区对象失去中线锚点，即使没有重叠、DOM 数量正确、E2E 通过，也必须判为 UI 未达标并继续修布局。
- **微交互改动也必须扫描同屏影响（强制）**：不要把 `transform / scale / translate / z-index / opacity / ring / shadow / pointer-events / hover / selected` 这类“只改样式”的动作排除在影响审查之外。只要它会改变对象位置、层级、点击面、可读性、可见面积或视觉焦点，动手前就必须列出同屏相邻 UI、覆盖层、工具按钮、提示框、确认条、token/状态/资源槽位和主槽位，并说明它们是否跟随、避让、退场或保持不动。禁止只验目标对象“自己变明显了”，却不验它有没有压住、错位、抢焦点或脱离同一对象的其它 UI。
- **视觉/对齐类 bug 默认必须回到真实来源页取证（强制）**：当用户反馈的是图标与文字不居中、按钮/徽章/角标偏移、字号与图标关系不对、主 UI 某一处“看着不顺/没对上/以前不是这样”这类视觉 bug，验收主证据必须来自该 bug 的真实来源页、真实路由、真实组件挂载位或真实业务链路截图。禁止新造一个 playground/demo 页面，把类似元素摆出来后用那张图冒充“已证明来源问题”。若为了隔离变量临时做了最小对照页，它只能作为**辅证**帮助分析，不得替代来源页主截图。
- **真实来源与合成对照冲突时，以真实来源为准（强制）**：如果 synthetic demo、最小复现页、局部 HTML 对照看起来“已经居中/已经没问题”，但真实来源页截图仍不达标，结论必须判为**未修好**，继续回到真实来源查布局上下文、容器约束、缩放变量、字体、真实 SVG 或路由分支差异。禁止拿“在我造的页里是对的”覆盖来源页证据。
- **来源证据优先级高于静态断言与理论推断（强制）**：只要当前问题属于视觉呈现或布局达标，E2E 断言通过、组件静态 HTML 存在、CSS 理论正确、skill 搜索结论正确，都不能替代真实来源页截图。最低收口证据必须同时回答：① 哪个真实入口复现了原问题；② 修后回到同一入口的截图是否达标；③ 若临时用了 playground，它和真实来源分别证明了什么。
- **真实来源链路拿不到时不得用替代图收口（强制）**：如果当前环境拿不到用户点名的真实页面/真实链路截图，只允许继续修通该链路，或明确汇报卡住的具体步骤、阻塞原因与最小补救动作；不得改交自制页面截图、组件孤立图、示意图或局部 mock 图来冒充完成。
- **交互壳层改动前必须先写“主交互槽位五联单”（强制）**：只要本轮会改变用户如何点击、确认、取消、选目标、弃牌、支付、推进或等待，就必须先明确写出：① 当前主交互对象；② 固定槽位；③ 空间冲突时的让位顺序；④ 禁止侵入该槽位的临时 UI；⑤ 参考的来源家族。五项缺一时，不得先改布局，也不得用截图调参代替结构判断。
- **来源家族必须点名到真实文件或截图（强制）**：不得只写“参考成熟项目”或“参考大杀四方”这类抽象口径。最低要能回查到真实证据，例如 `src/games/smashup/ui/HandArea.tsx` 的底部常驻主交互槽位、`src/games/smashup/ui/PromptOverlay.tsx` 的底部非阻塞卡牌查看/选择面板、`src/games/smashup/ui/MeFirstOverlay.tsx` 的中央 ownership/waiting shell、`src/games/smashup/Board.tsx` 中 `activePromptSurface` 的单一承接面路由。说不出这类来源家族时，视为来源未锁定，不得开始实现。
- **主交互槽位验收必须证明“前中后都不漂移”（强制）**：凡是有手牌区、右侧 rail、中央 prompt、底部 prompt 条、步骤横幅或 waiting shell 的界面，验收时必须回到真实链路截图回答三件事：交互前主入口在哪，交互中是否仍在原槽位，交互后是否正常退场且没有留下占位残影。若瞬时 UI 通过插入正常流把主交互区顶走、压窄或下推，直接判失败。
- **临时 UI / waiting / hint / confirm strip 不得侵入主交互槽位（强制）**：说明条、等待条、短提示、确认条、日志块、帮助块只能附着在自己的槽位、overlay 或 modal 中；不得把底部手牌槽位、右侧动作槽位、中央主选择壳层占成第二块“也像主入口”的区域。若当前唯一下一步入口被这类临时 UI 挤掉或遮掉，直接判失败。
- **交互壳层验收必须证明没有双主焦点（强制）**：凡是右侧 rail、底部手牌区、中央 prompt、waiting shell、步骤横幅共存的界面，验收时必须回到真实截图回答：当前是否只有一组主操作焦点；如果同时出现两组并列“都像主入口”的可操作 UI，直接判失败。
- **可选候选验收必须检查“空侧选择是否被做成伪候选”（强制）**：当某步存在可选对象候选，例如交易里己方持有物、对方持有物、可追加支付或可额外选择目标，截图后必须判断“不选某一侧”到底是独立放弃动作还是默认空侧。若只是默认空侧，验收图里不得出现和真实对象同级的 `无 / 不选择 / 索要 / 换回 / 不换回` 按钮或模式标签；必须能从摘要和主确认按钮看出当前提交的是哪些真实对象。若是独立放弃动作，则必须有清楚按钮，且按钮不能被角落化。
- **请求确认验收必须检查“确认是否贴着摘要”（强制）**：当当前步骤会发送交易、交换、协商、邀请或其它需要对方回应的请求时，最终确认按钮必须与请求摘要、候选区处在同一视觉块里，且同屏只有一个最终确认。若确认还停在底部导航、右下角、侧栏或远离摘要的位置，即使按钮能点也判失败；若底部动作栏和流程条各有一个确认，也判失败。
- **五联单默认模板（强制照填）**：凡是命中以上门禁的 UI 改动，实施前至少先按下面模板写出当前判断，缺项就不能开改：

```text
主交互对象：
固定槽位：
让位顺序：
禁止侵入对象：
来源家族：

交互前主入口：
交互中主入口：
交互后收口状态：
双主焦点检查：
```
- **游戏类 UI 默认必须给整体整屏截图（强制）**：凡是游戏进行页、牌桌、棋盘、战场、书本双页、主 HUD、主选择层、横屏主态这类游戏 UI，主验收图默认必须是整屏/整页/整牌桌视图，能够同时看见主内容区、HUD、提示层、目标元素和周边构图关系。仅给一个局部按钮、局部徽章、局部卡角、局部浮层裁切图，对用户默认没有验收意义，不能单独交付。
- **过程动画必须给中间态截图（强制）**：计分动画、结算跳分、翻牌揭示、移动结算这类“过程本身是需求”的 UI，不能只用最终静态截图收口。最低证据必须包含同一真实链路的过程态整屏截图与最终态整屏截图，并说明两张图来自同一入口。
- **结算动画主体必须是被结算对象（强制）**：如果总分来源于牌、棋子、随从、骰子或其它已在场对象，过程动画默认应先让这些对象本体发生可感知结算，例如对象高亮、对象轻跳、对象附近弹出 `+N/-N`，再让总分同步累加。右侧榜单、终局排名、结果列表、总结面板默认只负责承载结果，不得反过来成为主要动画舞台。
- **结算结果必须以对象本体为主（强制）**：摊牌、掷骰、战斗、计分、交易、失败/成功判定这类结果界面，默认先展示真实对象本体，例如牌面、骰面、棋子、token、单位、目标区域或资源；牌型名、命中/失败、数值、排名和解释文案只能作为辅助标签。若核心结果只显示“一对 / 两对 / 成功 / 失败”等文字，或者遮罩只覆盖局部区域导致未结算背景继续干扰视线，直接判结算 UI 未达标。
- **局部截图在游戏场景里只能作辅证（强制）**：游戏类任务若需要说明某个图标、token、按钮、角标、数值或描边细节，可以附局部近景，但必须建立在至少一张同链路整屏主图之上，并明确标注“这张只是细节辅证”。禁止只交局部图让用户自己脑补它在整局画面里的位置、比例和上下文。
- **压缩预览不能冒充原图验收（强制）**：AI 为了上下文预算可以看 contact sheet、缩略图、裁图或低清预览，但这只能证明“预览里大致可见”。只要最终要对用户说“我看图确认了 / 图面合格”，必须同时明确本次肉眼判定依据是哪张原始 E2E 截图或哪张从原图裁出的目标区域；若只看了压缩预览，必须说“只看了预览，尚未对原图下结论”，不得把预览判断包装成原图验收。
- **横屏游戏必须覆盖横屏主链路**：若问题发生在游戏页手机横屏，截图与 E2E 必须至少覆盖“进入前/加载或选择态 → 游戏内主态”两段横屏链路，不能只给一个竖屏图或只给最终态。
- **缩放/偏移类问题必须单独写出视觉判定**：至少说明 ①有没有缩在左上角；②HUD/主内容是否仍同坐标系；③有没有被误修成窄布局/双列路线。禁止用“元素存在”代替视觉达标结论。

## 0. UI 改动分级流程（强制）

### 0.0 新 UI 端到端验收门禁（强制）

- **触发条件**：凡是新增用户可见 UI、入口按钮、悬浮按钮、浮层、菜单、卡片、状态分支、动作入口，或把原本隐藏/不可达入口改成可见，都必须触发；纯文案、纯颜色、已有控件同槽位微调可例外，但不得改变可见入口或交互状态。
- **核心不变量**：新 UI 不允许只靠 TypeScript、ESLint、单元测试、组件静态渲染、代码审查或单张静态截图收口；默认必须跑真实入口的端到端验证，例如 Playwright、项目既定 E2E、真机/模拟器流程，或等价的真实页面交互链路。
- **最低验收链路**：端到端必须覆盖 ① 从用户真实入口打开目标页面；② 新 UI 在目标状态下可见；③ 点击、展开、切换、关闭、确认等主交互可执行；④ 交互后的真实状态变化、副作用或下一步 UI 成立；⑤ 必要时留下截图、录像或命令输出路径。
- **剧本 / 作祟类 UI 验收补充（强制）**：如果新增或修复的是作祟、剧本、阵营目标、Boss/怪物登场、终局路线这类会改变玩家胜负目标的 UI，真实入口 E2E 不能只断言日志、内部状态、evidence 产物或“可打开剧本书”存在；必须在真实牌桌上断言阶段揭示、目标摘要、主动作入口、主动作点击后的执行态或对象选择态、可回看剧本入口、打开后的对应剧本内容，以及关闭后仍回到可操作牌桌。
- **作祟主动作 E2E 门槛（强制）**：作祟/剧本 UI 的完成门槛不是阅读浮层可见，而是不打开剧本书也能推进当前玩家的下一步。E2E 必须至少覆盖一条直接执行动作（例如寻找解药、搬尸体、献给大宅、砸毁相机）或一条对象选择动作（例如攻击邪教徒、交换疾病、拍照/攻击目标）：点击主动作后，合法目标必须在牌桌对象本体上高亮，并在目标对象附近出现局部短引导；目标所在区域必须聚光或提亮，非目标对象和无关 rail / 普通动作入口必须降噪或退场。打开剧本书只能作为辅助断言，不能单独作为主验收。
- **作祟目标选择态玩家视角验收（强制）**：目标选择态验收不能只说“截图里有高亮”。必须逐项回答玩家四问：① 我现在是要点牌桌对象，还是继续点顶部按钮；② 具体点哪个对象；③ 点了会发生什么；④ 点错/不想做时怎么退出。若顶部仍显示一个看起来可再次执行的主按钮、目标热区低于 44px、没有取消入口、或对象旁提示只写“目标/这里/点这个”而不说明行动后果，判为未通过。
- **作祟主动作截图门槛（强制）**：作祟/剧本 UI 的截图不能只证明侧栏目标卡或剧本书存在；必须用整屏真实牌桌证明主动作处于玩家主视线区，按钮满足常规触控尺寸，不被手牌/持有区/右侧 rail/左侧探索者板遮挡，且需要目标时目标本体高亮、目标旁短提示、目标区域聚光都能一眼识别。若玩家还需要先扫侧栏小字、先打开剧本书或在地图里猜目标在哪里，截图判为未通过。
- **截图/测试不是用户友好本身（强制）**：截图、录像、E2E 绿灯、DOM 属性和 evidence 文件只能作为证据，不能代替玩家体验结论。汇报前必须用玩家语言写出“玩家此刻第一眼会怎么行动”的判断；如果判断里还需要“看截图路径 / 看测试断言 / 我解释给你听才懂”，不得收口，必须继续改交互。
- **流程型 UI 不能由单图证据收口（强制）**：关键业务节点和状态覆盖回 [`e2e-verification`](e2e-verification.md)；本节只判断 BoardGame 布局和信息去向是否成立。
- **新增控件必须自解释动作语义（强制）**：新增按钮、tab、分段选择器、开关或目标槽位选择器时，截图后必须判断玩家不听解释能否知道“它会改变哪一个后续动作”。如果按钮只写对象名、方向、内部槽位或状态名，例如“上手 / 下手 / A / B / top / bottom”，而实际语义是“把下一枚筹码给哪一手 / 选择哪个目标槽 / 切换后续点击对象”，必须改成动作化短标签或等价图标语法，例如“给上手 / 给下手”。`aria-pressed`、内部字段、测试断言和口头解释都不能替代可见语义。
- **新增或修复动作控件不得做成小字入口（强制）**：凡是承担声明、跳过、确认、取消、下一步、筛选、模式切换、目标槽位选择的控件，真实截图里必须像按钮或可点对象，而不是透明背景小字、注脚或状态标签。最低验收包括：① 命中区不小于 44px 级；② 有可见边界/底色/形态；③ hover/focus/选中反馈可见；④ 同屏玩家不需要解释也能知道它可点。缺任一项，直接判 UI 未通过，不能用 DOM 点击成功或 E2E 绿灯抵消。
- **触控下限不是视觉尺寸合格（强制）**：`44px` 只能证明控件最低可点，不能证明它在画面里大小正确。贴在手牌、卡牌、棋子、角色、房间、token 或其它真实对象旁边的辅助按钮 / 分段选择器 / 模式开关，必须区分“可见按钮面”和“真实点击热区”，并量相对主体的宽度、面积或视觉权重；如果可见面接近或超过被控制对象本体，让玩家第一眼看到按钮而不是对象，直接判 `REVISE`。需要更大热区时用透明 hitbox / padding 外扩，不得把可见按钮面画成 44px 高的大主按钮。E2E 不能只断言热区达标，还必须覆盖“不会因触控下限而视觉放大成主对象”的比例断言；像手牌旁目标选择器这类三四个字的小辅助控件，默认可见面应低于主体宽度约一半，不能用接近半张手牌的高亮胶囊收口。
- **缩放壳内禁止真实断点二次缩小（强制）**：`board-shell` / 固定设计画布 / 运行时整体缩放这类布局里，核心牌桌对象必须先按设计画布尺寸排版，再统一缩放。不得让手牌、棋子、公共牌、主按钮等核心对象继续用真实 viewport 的 `sm/md/lg/xl` 断点决定主尺寸，否则会出现“移动端先变小、整桌再缩一次”，破坏 PC 等比效果。验收必须量核心对象的实际尺寸与 `设计基线 × shell scale` 是否匹配，不能只看整屏没有溢出。
- **禁止使用浏览器默认确认弹窗（强制）**：凡是会重开、删除、覆盖、退出、清空进度、应用高影响设置或改变多人状态的确认流程，必须使用项目内可截图、可本地化、可测试的自定义确认 UI；禁止用 `window.confirm` / `alert` / `prompt` 或浏览器原生对话框。设置类弹窗必须先在弹窗内维护草稿，只有点击明确的“应用/确认”按钮后才允许出现高影响确认；点选开关、模式卡、关闭或取消不得直接应用草稿或触发确认。
- **旧壳复用的新对象级交互链**：复用已有 prompt、simple-choice、response window、目标高亮或 Me First 壳层时，通常不算“新的 UI 类型”；但只要本对象让玩家在新的触发时机、候选过滤、特殊模式、是否执行或结算结果里完成选择，就仍算新的对象级交互链，必须补本对象真实入口 E2E 与截图，不能只借旧壳截图或代表对象 shared 证据。
- **端到端前置缺口不得被 UI 验收吞掉（强制）**：如果新 UI 属于新增游戏、游戏接入、规则驱动对象、素材驱动牌桌/棋盘/地图/HUD，且端到端前或端到端过程中发现缺规则对象、缺素材、缺正式运行时资源、缺交互承载或缺实现任务，必须先停止“完成”口径，回到 proposal/tasks/spec、规则对象素材矩阵和实现清单补齐缺口；不得继续缩小路径、删断言、跳过对象或用相似元素制造 E2E 绿灯。
- **缺关键素材必须转资源补齐，不得只改 UI 文案（强制）**：如果真实页面出现缺正面、缺图、空卡、错误牌背、无来源占位或素材未闭合状态，本轮默认目标首先是补素材来源、询问用户提供素材或回到资源 intake；UI 只能做临时降噪，不能把缺口藏成“可接受状态”后继续验收。
- **禁止用 HTML/CSS UI 冒充规则素材（强制）**：规则、物理配件、官方素材或用户素材目录已经指向的牌面、牌背、token、棋子、筹码、桌面、牌槽、帮助卡、地图格、角色/怪物/状态标记等对象，必须优先使用真实素材并完成语义命名、正式落盘、压缩/manifest 和运行时引用。只有规则对象素材矩阵明确裁定“不需要图片”，或用户明确批准程序化替代时，才允许用纯 HTML/CSS/文字/程序化图形承载；否则必须标为 `blocked`，不得继续实施或收口。
- **错误素材不得被程序化 UI 遮掉（强制）**：当用户反馈“显示了其他派系/错误阵营/错卡图/错素材/金牌不该出现”等素材归属问题时，默认问题对象是素材绑定、图集槽位、派系/牌组映射或运行时引用错误；修复顺序必须是先核真相源与素材目录，再找正确素材并接入。禁止把问题改写成“去掉图片、改成文字卡、结构化卡、占位卡、通用壳层”来制造截图或 E2E 通过。找不到正确素材时只能继续排查或标记 blocked；除非用户当轮明确批准临时无图/程序化占位。
- **状态分支必须逐态验证**：如果新 UI 会根据下载完成、已安装、未安装、可卸载、错误、禁用、加载中等状态改变文案、可见性或按钮动作，不能只验默认态；至少要覆盖用户点名的状态分支，以及本轮改动直接影响的前后状态。
- **App / Native 专属 UI 口径**：浏览器 E2E 覆盖不到的 App WebView、原生能力、安装/卸载、权限、文件系统、系统弹窗等链路，必须改用真机、模拟器、原生 E2E、调试桥或项目约定的 native 验收方式；如果本轮只能做到静态或 mock 验证，最终必须明确标注“端到端未完成”。
- **失败处理**：若 E2E 环境不可用、命令失败、入口打不开、目标状态无法构造，必须停在该失败点，说明卡住的具体命令/步骤和最小补救动作；不得把“类型通过/代码已改/截图能看到”汇报成新 UI 已完成。
- **禁止行为**：禁止新增 UI 后不走真实入口验证；禁止用 mock 页面、临时预览页、故事页、孤立组件截图冒充端到端；禁止只验证元素存在，不验证主交互和交互后的现实结果；禁止把“这次只是小按钮/小浮层”当作跳过 E2E 的理由。
- **最终回复门槛（强制）**：只要本轮新增或暴露用户可见 UI，最终汇报必须点名真实入口端到端用例、关键截图或真机证据；未跑通时只能写“端到端未完成 / blocked”，不得说“已完成”“已实装”“已收口”。
- **多状态截图门槛（强制）**：新 UI 涉及弹窗、菜单、开关、模式选择、状态分支、重设/关闭/确认等多态时，验收不能只交一张代表图；必须覆盖每个新增入口的可见态、至少一个主交互后态，以及本轮改动直接影响的重置/关闭/下一步状态。
- **交互模式变化按新 UI 处理（强制）**：即使只改一个现有组件，只要改变了用户发现候选、浏览/筛选候选、判断可操作对象、选择、确认提交或视图切换的方式，就按新 UI / 交互模式变化执行真实入口 E2E 和截图验收，不得用“只是补入口/换展示/方便筛选”降级。
- **新 UI 默认按交互类型统计（强制）**：新 UI 默认指新的交互壳层或操作模式，不把旧 prompt 只换文案/候选数据、旧 overlay 承载新对象、旧链路新增规则分支或旧面板出现新对象计为新 UI 类型。新交互类型至少需要一条 direct E2E 和一张正式证据图；复用旧壳但改变触发时机、候选过滤、是否执行或结算结果的，标为“旧壳复用的新对象级交互链”，不能拿代表对象证据充数。
- **新派系的展示页与交互 UI 分开统计（强制）**：派系选择页、详情预览、素材展示和进局展示默认不计入“新交互 UI 类型”；用户明确点名这些展示页时，另列展示型证据，不与交互型 UI 混表。

### 0.0A 大规模 UI 改动与参考来源门禁（强制）

- **触发条件**：涉及 3 个及以上组件文件的样式变更、新增整页/整区域布局、全局配色/字体/间距调整、新游戏 Board 搭建，或布局稳定性、视觉层级等跨组件 UI 优化时触发。
- **参考来源不等于视觉风格**：TTS、Workshop、BGG、DOM、HTML、截图或用户素材可以证明素材、布局、信息层级或交互参考，但不能直接决定最终视觉风格；新游戏 Board 必须回到 UI skill、design-system/styles/ 和游戏主题选择风格。
- **点名参考未命中不得收口**：用户明确指定的 DOM、电子版、截图或素材读取失败、为空或不覆盖目标时，必须停在 blocked/in_progress，说明缺口；不得换成相似参考后宣称完成。
- **读取顺序**：先读 .spec/skills/ui-ux-pro-max/SKILL.md，再读 design-system/game-ui/MASTER.md、对应 design-system/styles/<风格>.md 和存在时的 design-system/games/<gameId>.md；通用 skill 与项目设计系统冲突时，以项目设计系统为准。

### 0.0 UI 可复用性与组件化判断门禁（强制）

- **触发条件**：凡是新增或修改按钮、开关、滑块、输入框、选择器、tab、弹窗、toast、菜单、卡片、面板、列表项、状态徽章、浮层入口、HUD 控件等用户可见 UI 控件时触发；修复已有控件的交互或视觉回归也触发。
- **核心不变量**：UI 开工前必须先判断“这是一次性业务壳，还是可复用控件/交互 primitive”。不能因为本轮只改一个游戏、一个面板、一个小控件，就默认在业务组件里手写一套基础交互。
- **最低检索顺序**：动手前至少按顺序检查：① 同文件/同面板是否已有同类控件；② 同游戏 `ui/` 目录是否已有同类组件；③ `src/components/**`、`src/hooks/ui/**`、`design-system/**` 是否已有共享组件、共享 hook 或设计系统合同；④ 项目已使用的 headless primitive 是否能承接底层交互。
- **组件化判定**：只要满足任一条件，默认必须复用现有组件或沉淀共享组件，而不是继续手写：① 同类控件已经在两个以上页面/游戏/面板出现；② 控件包含状态切换、键盘操作、ARIA、focus、disabled、受控/非受控同步、拖拽、滑动、弹层定位等基础交互；③ 未来明显会继续出现；④ 这次 bug 暴露的是基础控件交互不可靠，而不是单一业务规则错误。
- **允许不抽组件的条件**：只有当控件语义只服务当前业务、视觉和交互都不可泛化，或抽象会把不同语义强行混成一套 API 时，才允许保留在业务组件内；最终汇报必须说明“不抽共享”的原因，而不是默认沉默。
- **组件库使用口径**：优先使用项目已经验证可用的 headless primitive 承接底层交互，再由项目共享组件封装视觉与业务命名。样式必须仍由项目控制；禁止为了省事引入未验证、会破坏打包或动态加载的大型 UI 库。
- **共享组件落点**：跨游戏、跨页面可复用的基础控件默认落到 `src/components/**` 或既有共享组件目录；只在单游戏内复用的控件落到该游戏 `ui/` 目录；通用交互行为优先落到 `src/hooks/ui/**`。不得把可复用基础控件继续埋在单个业务面板里。
- **验收要求**：共享控件首次落地必须至少覆盖一个真实调用点、一个窄单测或组件测试，以及能证明用户肉眼状态变化的真实截图/E2E；状态型控件不能只测文案、存储值或 DOM 属性，必须验证真实视觉变化，例如开关圆球位移、滑块 thumb 位移、tab active 态、弹层锚点。
- **禁止行为**：禁止每个游戏各写一套外观相似但底层不同的基础控件；禁止把 `div/button + className` 手写状态机当成默认实现；禁止在已有共享组件能扩展覆盖时另起重复组件；禁止为了“快一点”牺牲可访问性、键盘交互和后续复用。

### 0.0 截图后的 BoardGame 视觉增量门禁（强制）

> 本节只补 BoardGame 的布局、压力态、信息去向和双端证据增量。截图生成、Playwright 通过或元素存在，都不能替代图面审计结论。

- **触发条件**：只有本轮 UI 已形成稳定交付候选、完整重构准备收口、用户明确要求截图验收 / 玩家视角检查 / 打开图，或测试虽通过但界面仍有高风险可用性疑点时，才触发真实页面截图和系统图面审计。打开图片是稳定候选完成后的胜利号角，不是过程性 UI 修改的例行动作。过程性 UI 修改、流程跑通中的临时状态和后续还会继续重构的中间状态，不默认进入截图验收；这类阶段只做与风险匹配的功能验证和局部诊断，仍不能用测试通过冒充最终视觉通过。
- **双端截图必须做缺失项审计（强制）**：只要本轮涉及 PC/移动端对照、手机横屏、响应式布局或“像桌面端”的验收，截图判定不能只看是否不重叠、不重复、贴底、可点击。必须先拿同一步 PC 截图列出玩家可见的一级信息与一级交互，例如角色/属性、持有区、主动作、阶段提示、牌堆/弃牌、队友/对手、日志/提示、帮助/参考入口；再在移动截图中逐项标明：原位保留、同源样式适配、折叠/抽屉收纳、暂时隐藏、确认为本轮不需要。任何 PC 一级信息在移动端“看不见也没有收纳入口”，且没有写清必要性，都必须判为缺失，不得收口。
- **双端缺失项审计必须产出矩阵（强制）**：不能只在回复里笼统说“移动端都有去向”。每次涉及 PC/移动端对照、手机横屏或响应式布局验收时，必须产出一张可追溯矩阵，至少包含：`PC 一级信息/交互`、`PC 承载`、`移动端去向`、`是否同源`、`当前证据`、`判定`。如果移动端使用专用压缩条、抽屉、摘要、图标入口或隐藏策略，必须在矩阵里逐项说明它不是误删；没有矩阵时，不得宣称双端视觉验收完成。
- **缺失项审计必须区分“合理收纳”和“误删”（强制）**：移动端可以因为屏幕限制收纳次要栏，但收纳必须有可见入口、状态提示或可恢复路径；不能把 PC 右侧常驻栏、左侧角色信息、牌堆/弃牌、队友信息、当前持有区这类玩家决策信息直接消失后说成“移动端更清爽”。如果截图里少东西，默认先按误删/外溢处理，除非当前任务已证明该信息在该阶段无用、已有等价入口，或用户明确同意隐藏。
- **失败处理**：图面审计不通过时回到同一真实入口继续重构、重拍和复审；本项目门禁不能用 E2E 绿灯、脚本成功或截图落盘替代审计结论。

### 0.0 双端默认视角（强制）

- 现在项目默认按 **双端并行** 处理 UI：网页/PWA、App WebView、桌面、移动端都要在设计阶段被同时考虑；**禁止**把移动端当成“桌面做完再补”的尾项。
- **移动端适配不是可选项（强制）**：新增游戏、新增 Board、重做游戏主界面时，不需要询问用户“是否考虑移动端”；AI 必须默认纳入移动端方案。可以询问主使用姿态或验收优先级，但不能把移动端适配作为需要用户额外授权的工作。
- **双端并行不是验收并行（强制）**：本节只要求设计输入和架构可扩展时同步考虑移动端；不得覆盖 §0.0C 的 PC 优先批准门禁。固定构图类游戏 PC 基线未通过时，移动端只能记录风险和适配意图，不能进入验收、截图交付或完成口径。
- **manifest 决定的是能力边界，不是是否考虑移动**：某个游戏可以暂时声明 `mobileProfile: 'none'` 或 `tablet-only`，但共享页面、共享组件、布局壳层、交互语义仍必须避免写成只能桌面工作的死结构。
- 只要改动会进入共享层（路由页、加载页、通用组件、共享 Hook、样式 token、壳层容器），必须先问自己两件事：
  - 这套结构在桌面和移动端是否仍是同一套架构，只是条件化呈现不同？
  - 以后某个游戏从 `none` 升级到 `landscape-adapted` 时，这里是否还能直接复用，而不是推倒重来？
- **固定构图类界面** 仍以桌面版为权威基线；移动端默认做同构缩放、触控入口和局部让位，不默认重排成另一套手机稿。
- **固定构图类验收顺序不可倒置（强制）**：桌面基线没有 AI PASS 和用户明确人工通过前，不得以“移动端也考虑了 / 移动端也能打开 / 移动端没重叠”为理由继续推进或收口。
- **游戏页若主使用姿态是手机横屏，则横屏是第一验收基线（强制）**：当某个游戏长期按手机横屏使用时，移动端修复默认围绕“横屏下像桌面端那样的构图与密度”收敛；未经用户明确确认，禁止把问题擅自改造成“窄布局 / 双列手机稿 / 大量留白”的路线。
- **轻微偏移优先修锚点，不优先改版式（强制）**：用户反馈“整体偏一点 / 不居中 / 像桌面端 / 不该变窄”时，默认先排查锚点、坐标系、容器宽度、scale 与 transform-origin；禁止直接通过改列数、减卡片数量、压成双列等方式把原本的横屏主版式推翻。
- **固定构图的 `px` 只能是设计基线，不能直接锁死最终尺寸（强制）**：牌桌、棋盘、手牌区、中央牌河、主按钮等固定构图对象允许用 `px` 描述设计宽度、设计间距和设计偏移，但这些值进入真实运行时后，必须由壳层统一缩放、容器约束或等价适配层承接。禁止把“设计卡宽 176px / 设计牌河宽 1460px”直接实现成所有设备最终都按这组像素显示；这会把“固定构图”误做成“硬编码最终尺寸”。
- **手机横屏首屏必须完整容纳手牌区与主操作（强制）**：牌桌类游戏在手机横屏下，`手牌区`、`当前可点击对象`、`主动作按钮` 必须同时留在首屏可视区内；不得把手牌压到屏幕外、把主按钮挤出触达区，或靠用户滚动去找当前回合入口。若高度预算不足，默认先收掉 `当前焦点`、辅助面板、次级说明等常驻辅件，让位给手牌和主操作。
- **移动端已有长按预览时，不得再常驻重复放大镜按钮（强制）**：如果同一张牌在移动端已经支持 `长按预览`、`二次点击已选牌预览` 或其他明确的触控预览入口，就不得再在每张牌角上常驻一排放大镜按钮制造视觉噪音。桌面端可保留显式放大镜；移动端默认优先保留更直接的触控手势入口。

### 0.0 页面语义边界（强制）

- 首页/大厅、游戏页、App 壳层更新页、后台、开发工具页属于**不同语义域**。即使复用同一个 Loading/Fallback/Empty/Error 视觉容器，也必须由调用方显式传入当前页面语义，禁止沿用其他页面的默认文案。
- 文案 key 必须按页面域归属：大厅/首页优先放 `home.*` 或 `lobby.*`，游戏页放 `matchRoom.*`，App 更新相关放 `ota.*` / `nativeUpdate.*`，后台放 `admin.*`，开发工具放 `devTools.*`。**禁止**为了省事把一个页面族的 key 借给另一个页面族当默认值。
- `Suspense fallback`、路由兜底页、空状态、错误态、骨架屏是最容易串语义的区域。只要这些组件可能在多个页面复用，就必须满足二选一：
  - 默认文案是中性语义，例如“正在加载页面...”“正在准备内容...”
  - 或者组件 API 强制调用方传入 `title/description/progressText/namespace`
- 若默认值里已经包含明显场景词，如“对局”“房间”“安装新版 App”“更新后台数据”，则该组件只能在对应场景使用，不得继续作为通用 UI 容器扩散。
- **错误提示必须对应真实失败阶段（强制）**：涉及下载、发布、清单同步、校验、激活、权限、网络这类多阶段链路时，用户可见错误提示必须直接对应当前已确认的失败阶段。禁止把“清单拉取失败”“网络超时”“原生方法缺失”“权限被拒绝”统一写成“未发布/请先发布一版”之类的发布态文案，也禁止用发布态去兜底所有前置失败。若当前只能确认“失败了但阶段未锁定”，默认使用中性失败文案，不得脑补成更具体但错误的原因。
- 任何入口级 UI 改动后，必须反问自己：用户在“错误页面”里看到这句文案，会不会立刻误解自己已经进了另一条流程？如果会，这个设计就不合格。

### 0.0 样式任务边界（强制）

- 当任务表述是“改小一点、改大一点、调间距、修溢出、修遮挡、修错位、改视觉层级、改颜色、改圆角、改阴影”这类样式目标时，默认只允许动视觉呈现，不允许顺手改交互编排。
- 交互编排包括但不限于：入口顺序、主按钮是谁、默认展开哪一项、点击一次还是两次、弹窗从哪里触发、菜单项上下次序、常驻入口变抽屉、hover 改 click、click 改 long press。
- 如果视觉问题与交互编排耦合，必须先向用户显式确认“需要连交互一起改”，否则只能提交纯样式方案。
- **样式微调必须先锁不变量（强制）**：用户要求“调间距 / 改大改小 / 修左边距 / 修上下挤 / 修视觉密度”时，动手前必须先明确这轮哪些东西不能变。至少覆盖：滚动语义是否保留、列数是否保留、卡片/头像尺寸是否保留、主内容区宽度是否保留、主按钮和关键控件位置是否保留。没有先锁这些不变量，禁止直接试改样式参数。
- **样式/布局改动默认不得改变功能表面（强制）**：当任务目标是修视觉、布局、密度、间距、对齐、遮挡、尺寸或响应式表现时，默认只能改变呈现方式，不能改变功能表面。功能表面包括但不限于：某个功能/入口/控件是否存在、是否可见、是否可达、默认状态是什么、信息默认展示范围、交互顺序、触发条件、自动展开/自动收口、自动跳转等。**删除、隐藏、禁用、替换、改默认值、改触发路径** 都属于功能改动，不得伪装成“只是样式调整”。
- **小控件状态提示必须先匹配真实尺寸（强制）**：当按钮、角标、切换器、历史项重播键、表格内操作格这类控件本身尺寸很小或宽高被强约束时，状态反馈优先使用 `spinner / icon / 背景态 / ring / tooltip` 这类等尺寸提示；禁止把“加载中”“处理中”之类完整文字硬塞进原本只容纳单图标的小按钮里。若状态提示一加上去就破坏比例、挤压布局或明显变丑，视为 UI 方案不成立，必须先回到真实尺寸重做。
- **关闭 / 返回 / 浮层关闭控件必须测热区（强制）**：弹窗右上角叉号、返回箭头、关闭图标这类小控件，视觉图标可以保持精致，但真实点击/触控热区不得小于 44px × 44px。凡用户点名“叉号太小 / 点不到 / 关闭按钮难点”，验收必须同时有 DOM 几何或 E2E 断言证明热区尺寸、以及截图证明视觉不挤压其它内容；不能只把图标画大或只说按钮存在。
- **用户要求“布局不变”时不得重排（强制）**：当用户明确说“布局不变 / 位置不变 / 排名改回去 / 只要徽章 / 只要动画”时，本轮只能在现有槽位内部改视觉装饰、徽章、颜色、文本或数值动画；不得移动牌桌、中央牌区、手牌区、排名面板、主按钮或任何已有锚点。若实现确实需要移动锚点，必须先停下说明“这已经不是布局不变”，等待用户确认。
- **排名标记必须挂到名次而不是玩家名（强制）**：王冠、金银铜、奖杯、名次色块这类“排名结果”默认属于“第 1 名 / 第 2 名 / 第 3 名”这一行，不属于玩家名本身。用户说“第一名+icon / 王冠放上面 / 排名改回去”时，应实现为名次文本旁同轴图标，而不是把图标塞到玩家名后面。
- **悬浮面板不得压住牌桌主对象（强制）**：右上角排名、右侧 rail、终局摘要、提示层、确认层只要和卡牌、棋子、手牌或中央牌区处于同一垂直范围，就必须在截图里证明没有横向覆盖主对象。若主对象被面板盖住、裁掉或只剩部分可见，即使 E2E 文本断言通过，也判布局失败。
- **视觉修复若必须影响功能，必须显式升级口径（强制）**：如果视觉问题和功能表面确实耦合，必须先明确告诉用户“这不是纯样式修复，而是会连功能表面一起改”，并把两部分分别验收。禁止为了恢复某个布局/历史观感，顺手删入口、藏控件、收窄可见信息或改默认行为。
- **回归恢复默认先用历史实现，不得重画一版“像以前”的 UI（强制）**：当用户要求“恢复原来样式/原来逻辑/默认关闭时和以前完全一致”时，默认必须先锁 `last known good` 的真实代码与截图基线，并优先恢复那套实现；禁止只保留抽象语义后在当前实现里重写一版“味道差不多”的界面。若旧实现已与当前新增能力共用同一组件，默认优先做分支隔离或抽回旧分支，而不是继续让旧路径跟着新路径共享视觉逻辑漂移。
- **功能开关双分支不得混成一套共享视觉（强制）**：如果同一开关同时承载“默认关闭旧体验”和“开启后新体验”，则两边都属于正式产品面，默认必须能各自独立成立。关闭态不得依赖开启态的视觉补丁，开启态也不得靠关闭态的历史兜底拼起来；若两边视觉/交互语义不同，应明确拆成独立分支、独立样式或独立组件，并分别做截图与行为验收。
- **回归恢复的默认实施顺序（强制）**：处理 UI 回归时，默认顺序必须是 `先锁旧代码真相 -> 先恢复关闭态旧合同 -> 再接回开启态新合同 -> 最后分别验收`。禁止一上来就在当前新实现里“往回调一点”，也禁止把关闭态和开启态同时揉在一套新组件里边修边猜。
- **旧合同优先读取真实代码，不得只凭截图猜（强制）**：`last known good` 不是只看旧截图大概长什么样，而是必须实际打开当时承载该行为的真实代码、入口组件、关键样式或 helper。若用户要求“直接用原来的代码”，默认含义就是优先恢复那套代码路径或等价抽离，不是按旧图临摹一版。
- **删除可选 UI 不得误删默认态共用合同（强制）**：当用户要求删除、关闭或清理某个可选 UI、实验模式、偏好分支、3D/高级渲染、调试入口或类似开关时，动手前必须把“可选分支专属职责”和“默认态仍要保留的共用职责”分开列清。共用职责包括默认素材加载、旧动效、旧尺寸、旧命中区、旧锚点、旧截图/测试合同等。只能删除可选分支专属入口和实现；若旧文件同时承载默认态效果，必须先迁移/抽离默认态合同，再删除旧文件。禁止把“删除开启态 3D”扩展成“默认 2D 骰子的立体翻滚、骰图加载或可点击合同也一起删除”。
- **关闭态恢复完成前，不得拿新路径补丁临时托住（强制）**：只要本轮目标包含“默认关闭时必须和以前完全一致”，在关闭态旧合同未恢复前，不得继续往新路径加条件分支、样式补丁、参数兼容或视觉降级来凑结果。关闭态应先独立成立，再讨论开启态如何挂回。
- **双分支应优先做结构隔离，而不是视觉条件分支（强制）**：当关闭态与开启态的视觉语义、交互载体、布局锚点或动画机制明显不同，默认优先拆成独立组件、独立 render 分支、独立样式入口或独立策略层；不得继续依赖同一组 `if/else`、同一套 className 拼接或同一批共享 token 去同时服务两份合同，除非证据已证明这层共享语义完全一致。
- **用户明确要求“直接用原来的代码”时，默认先做 git 级旧实现回接（强制）**：实施顺序必须优先是 `定位旧提交/旧文件 -> 读取旧实现 -> 以当前接口做最小适配接回`，而不是先在现有新组件里反复调样式、调槽位、调参数去逼近旧观感。除非证据已经证明旧实现接不回来，否则不得跳过这一步。
- **用户要求“完全两套分支效果”时，只允许共享非视觉适配层（强制）**：旧合同与新合同可以共享数据来源、状态映射、命令分发、能力探测和开关判定；但默认不得共享最终 render、布局锚点、动画承载、视觉 token 或截图验收口径。只要共享到了这些层，就必须先证明这层在两边语义完全一致；否则一律拆开。
- **旧合同与新合同若已混在同一组件里，默认先拆回旧合同再继续（强制）**：当关闭态和开启态已经落在同一个 render 分支、同一组样式拼接或同一个视觉组件里时，默认第一步不是继续加条件分支修补，而是先把关闭态旧合同从历史实现中抽回成独立分支、独立组件或独立入口。只有关闭态先独立成立后，才允许把开启态新能力重新挂回开关。
- **关闭态仍落在新视觉组件里时，不得宣称“已恢复原版”（强制）**：如果当前所谓“默认关闭”仍然只是新组件换一组 props、换几条 className、关掉部分动画或隐藏部分新元素，而不是直接回到旧实现入口或其等价抽离版本，默认只能称为“视觉接近”或“临时兼容”，不得称为“恢复原来的代码”。
- **无法直接复用旧代码时，必须先说明断点在哪里（强制）**：如果旧实现因为数据结构、组件签名、运行时入口或依赖删除而无法直接接回，必须先明确说明是哪一层接口已断，准备怎样做最小适配把旧合同接回；不得跳过这一步，直接升级为“那我重写一个像以前的版本”。
- **回归恢复的最低汇报要素（强制）**：最终汇报这类回归时，至少要同时说清：① 旧合同基线来自哪笔提交/哪组文件；② 当前关闭态直接恢复了哪些旧实现；③ 开启态单独新增了哪些新实现；④ 两边现在通过哪一个开关或入口分流。缺任一项，不得表述为“已经恢复原样”。
- **局部修复不得擅自改变默认可见信息（强制）**：当用户点名修复某个入口、搜索、排序、间距或布局时，默认只能恢复该入口本身及其直接依赖。若实现方案会顺带改变“默认展示全部还是过滤一部分”“别人已选/已锁定/不可操作对象是否可见”“玩家状态卡/座位条/进度条是否常驻可见”这类信息范围，必须先停下询问用户。只有用户明确确认后，才允许把这类默认可见信息变化纳入同轮修改；否则只能提供低侵入入口，例如保留搜索/筛选按钮，但默认仍展示完整上下文。
- **移除入口必须同步释放布局占位（强制）**：当用户要求删掉设置、帮助、搜索、调试、筛选或其它工具入口时，验收对象不只是按钮本身消失，还包括它原先占用的 grid track、固定宽度、padding、空壳分栏和对齐占位是否同步释放。禁止出现“控件没了但空位还在”的假删除。
- **明显问题不得靠测试断言自我授权（强制）**：如果某个断言为了让当前修改变绿，要求隐藏玩家卡、隐藏对手已选信息、删除常驻状态、遮挡主交互区、或把用户未点名的功能面改成另一套默认行为，即使测试能通过，也必须视为需求升级点而不是修复细节。最低动作是先说明“这会改变用户看到的信息/状态入口”，等待用户确认；禁止用“减负、样式、旧布局兼容”包装后直接落代码。
- **滚动列表的间距问题先保留滚动语义（强制）**：用户反馈列表“上下太挤 / 太松 / 左边距怪 / 看起来不对”时，默认目标是修正列表项之间的视觉节奏，不是追求“首屏全部显示”或“多露几项”。禁止通过改整层 inset、缩卡片/头像、改列数、压缩主内容区等方式间接改变可视密度；优先只改目标列表自身的 `row-gap`、单项内边距或局部留白。
- **滚动列表样式验收必须先对照同场景 PC（强制）**：如果同一组件同时跑在 PC 和移动端，先锁定 PC 同场景作为结构真相源，再看移动端是否只是同构缩放下的局部节奏调整。若移动端为了“修间距”把列表项显著缩小、主区被挤窄、按钮位置跟着漂移，直接判失败。
- 只要任务涉及“PC 同构”“移动端等比缩放”“手机横屏像桌面端”“双端布局策略”“到底该缩放还是重排”，必须先读 `docs/mobile-adaptation.md`，不要只凭通用 UI 审美规则判断。
- **参考图驱动的局部优化必须先抽取视觉不变量（强制）**：用户给出参考图并要求“参考这里优化”时，动手前必须明确抽取目标对象的形状/轮廓、位置锚点、色彩材质、信息层级四类不变量。禁止只保留“有一个徽章/有一个 token/有一个面板”这种抽象功能，再用泛化几何体或常见组件替代参考图中的具体轮廓语言。若证据文档宣称“已参考”，必须写清楚截图里实际对应到哪些不变量；形状不一致时只能说“未达标”，不能用断言通过替代视觉判断。
- **草稿 / 手绘 / 标注图不得照抄成正式 UI（强制）**：用户给出的粗框、手绘线、箭头、圈注、临时色块、占位字或口头草图默认只用于提炼设计不变量，例如对象关系、分段数量、当前位置表达、锚点、信息取舍和交互语义。正式实现必须回到既有设计系统、正式素材、目标稿或同家族成熟实现；禁止把草稿里的线宽、颜色、粗糙边框、手绘笔触、临时红框或标注排版直接作为运行 UI 样式。若草稿与正式素材冲突，先按正式素材和规则真相源实现，再把草稿只当问题定位证据。
- **用户点名横向参考时必须真实打开来源（强制）**：当用户点名“看某个已完成游戏怎么做”“参考某个成熟 UI”“像某个游戏但做出自己风格”时，不得只口头说参考了。动手前必须实际打开对应代码、截图或设计系统条目，并写出四类可回查不变量：①对象形状/轮廓；②位置锚点；③状态语法；④信息层级。来源只提供不变量，不授权直接复制视觉皮肤；当前游戏必须结合自己的风格 token 和空间合同重新设计。
- **参考未命中不得宣称完成（强制）**：如果指定参考源不存在、打不开、没有覆盖目标对象，或只找到了不同 UI 家族的证据，任务必须停在“参考源未命中 / 证据不足”。不得换成相邻游戏、旧截图、个人判断或测试断言继续完成后说“已参考”。
- **完整对象描边必须截图判定（强制）**：当用户反馈手牌、卡牌、房间、头像、单位等选中态“左右有色块 / 只有两边亮 / 边缘像叠了条块”时，最低验收图必须能看见目标对象完整外圈。实现优先把 `border/ring/shadow` 放在同一外层对象容器；禁止用错位 wrapper、半透明侧条、伪元素叠层或被 `overflow-hidden` 裁切的内层阴影凑效果。截图里只要仍像左右色块，就判视觉失败。

### 0.0a 通用规范与单游戏专名分层（强制）

- `.spec/knowledge/standards/**`、项目通用 skill、项目 overlay 这类通用层，默认是给整仓长期会存在的大量游戏写的，不是给当前正在改的单个游戏写案例说明；写作时默认按“这条规则放到第 100 个游戏里还成立吗”自检。
- 通用层只能写抽象职责、分层原则、验收门禁和反模式，不得直接写某个游戏的专有机制名、专有地名、专有势力名、专有控件名。
- 即使只是举例，也不得拿单游戏机制名充当“通用例子”；示例必须抽象成职责，例如“共享行动指示器”“年份或回合卡位”“特殊区域”“主交互槽位”。
- 通用层允许引用仓内某个现成实现当“真相源”或“成熟来源”，但引用只用于证明这个交互家族在仓内真实存在；规则正文、家族命名和不变量本身仍必须保持跨游戏抽象，不得把该实现里的单游戏机制词带进通用合同。
- 某个游戏独有的主交互构件、地区、棋盘结构、流程术语、教程编排、截图口径，只能写进 `docs/games/<gameId>/**`、该游戏自己的 skill，或该游戏的 `design-system` 文档。
- 如果一条规则离开当前游戏就不成立，默认说明它落点错了；先下沉到单游戏文档，再继续写内容。

### 0.0b 交互与跨断点真相（强制）

- **同一游戏跨断点不得分裂成两套独立 UI 家族**：桌面、移动、live、stacked、compact 之间允许改排布、密度和尺寸，但不能把同一个游戏做成两套像“两个产品”的交互家族。回合信息、主操作、分数摘要、焦点区、终局复盘、等待态这几类对象在跨断点时必须保持同构职责。
- **同一游戏跨状态不得裂变成两套壳层家族（强制）**：开局、对局中、弃牌中、终局这些只是流程状态，不是新产品。除非用户明确要求或权威设计稿明确点名，状态切换时只允许做信息显隐、主次变化、动画和密度调整；不得把原本持续存在的顶栏、总分摘要、回合轴、主牌桌锚点、排名壳层整体换成另一套布局语言。若某个状态看起来像“另一个游戏”，直接判失败。
- **单对象 / 多对象分支不得分裂状态提示家族（强制）**：当功能从单对象扩展到多对象，例如单目标变多目标、单组资源变多组资源、单个结果变多个并列结果时，新增的当前状态提示不得只覆盖新分支。若多对象分支显示当前结果、状态徽章、选中态、可用态或确认反馈，必须回查旧单对象分支是否需要同一信息家族；除非有权威截图、设计合同或用户当轮明确裁定旧分支不显示，否则单对象和多对象都要各有截图或测试证明口径一致。
- **正式视觉稿不自动包含交互合同**：设计稿、效果稿、目标截图默认只能证明构图、材质、比例、对象摆放和信息层级；若图里没有明确画出“谁承接点击、是否分步确认、是否要提示”，不得自行脑补成交互设计。
- **交互模式必须有来源表**：只要本轮改动改变了“点哪里、怎么确认、谁承接、是否先选后确认”，就必须先写出最小来源表，至少说明当前动作来自正式设计稿、仓内既有真相、官方产品、用户明确要求中的哪一个。没有来源表时，不得凭个人偏好发明正式交互。
- **主推进交互不得隐式到不可见**：承担“继续流程 / 完成当前步骤”的主推进动作，不能同时满足“无明确承接对象”与“无明确提示”。对象本体可以承接，但必须自带清晰可点击语义，或同时给出明确短提示。
- **默认预选不得冒充玩家已决策（强制）**：如果页面进入某阶段时默认选中了某个地区、卡牌、轮盘项、行动项或候选目标，这只能算初始聚焦或便捷态，不等于玩家已经做出正式选择。文案、标题、状态词和教程都不得把它写成“你先选了这里”；若玩家确实还没点过，UI 也不得把这种默认态做成“已确认”的语气。
- **默认选项不得被可选 UI 覆盖（强制）**：当某个 UI 存在显示偏好、功能开关、实验开关或用户设置时，用户未明确指定开启该选项，就必须按产品默认值验收和交图。默认关闭的 3D 骰台、新版壳层、候选视觉模式、调试显示等只能作为“开启态/可选分支”单独展示，不能冒充默认体验。
- **可选 UI 验收必须双分支命名（强制）**：涉及功能开关或视觉偏好的 UI 回归，至少要把默认/关闭态和开启态在测试名、截图名、evidence 和汇报中分开。若用户只问“当前/默认/给我看”，优先交默认态；只有用户要求比较或查看可选分支时，才额外打开并展示开启态。
- **一级交互清单必须以规则全集为准（强制）**：只要在做教程、正式 UI、审计或截图验收时提到“一级动作 / 主入口 / 基础回合 / 所有交互”，都必须先按规则或权威真相源列出同层一级入口的完整全集，再映射到当前 UI。不得只因为某几个入口当前更显眼、当前案例刚好走到、或者当前测试更容易拍，就把其它同层入口漏掉。
- **主提示必须落在当前玩家这一层真正有决定权的对象上（强制）**：如果当前画面前面还有强制公共推进、开局前置或纯进入壳层，这些状态可以被提示，但不能冒充“当前主要操作”。一旦页面已经进入当前玩家真实有选择权的一级动作层，主提示、主高亮和主交互入口都必须回到这一层；不得跳过它，直接把后面的目标地区、支付对象或确认按钮说成“第一步”。
- **提示横幅不是交互入口，除非它自己真的能点（强制）**：顶部横幅、地图横幅、步骤卡、右侧说明卡默认只负责提示当前阶段，不得承担“唯一主入口”的语义。只要真实点击发生在地图、卡牌、轮盘格、列表项或按钮本体上，横幅文案就必须保持提示口吻，不能伪装成“点这里继续”。
- **直点交互进入即高亮（强制）**：若某阶段的真实入口是直点对象，本阶段一进入就必须让可操作对象处于清晰可见的候选态，例如描边、发光、箭头、单对象高亮或等价 affordance。禁止先让用户读一堆说明，再去猜哪个对象能点。
- **直点对象不得默认代选（强制）**：只要当前步骤要求玩家选择可见对象，唯一合法对象也必须走 `高亮候选 → 玩家点击对象 → 进入已选/可确认` 的流程。禁止因为候选只有 1 个，就在状态派生、payload 构造、确认按钮或 `使用` 按钮里默认塞入第一个候选。例外只限于完全没有对象/目标/支付/顺序/数量选择的固定推进步骤。
- **确认按钮必须跟真实选择同源（强制）**：确认/提交按钮只能提交玩家已经完成的真实选择，不能代替对象选择本身。若当前还要求玩家点房间、卡牌、角色、格子或其它可见对象，确认按钮必须保持不可提交或只提示缺项；对象本体必须先显示候选态，点击后进入已选态，确认才变为可用。PC 与移动端必须采用同一确认语义：PC 没有确认时，移动端不得独有确认；PC 有确认时，移动端也必须让玩家看见同样的“选对象后确认”流程。
- **玩家可见短提示不得用作者旁白腔代替规则语义（强制）**：主界面横幅、步骤标题、摘要卡、教程短句默认优先使用规则动作名、对象名、结果名，不得长期写成“这一步 / 下一步 / 这里 / 这次 / 现在先”这类作者旁白腔。旁白词最多做补语，不能成为主语义；若去掉这些词后句子失去含义，说明这条提示没有真正落到游戏规则本身。
- **牌堆 / 弃牌堆 / 棋盘对象不得承担唯一一级主动作（强制）**：像 `摸牌`、`结束回合`、`确认选择`、`确认弃置` 这类一级主推进动作，默认必须有**显式主按钮或等价主控件**承接；牌堆、弃牌堆、棋盘格、卡牌本体最多只能作为辅助直点入口，不能成为唯一入口。尤其 `从牌库摸牌` 默认禁止设计成“直接点牌堆摸牌”，因为它在桌面与移动端都会降低可发现性，并把可操作性退化成猜测。只有当用户当轮明确要求某个对象本体就是唯一合法承接物，并且该对象已具备成熟项目级的显式可点击语义时，才允许例外。
- **正规流程优先于临时收口**：当页面“规则合法但看起来像卡死”时，默认动作是回到正式 UI 流程，重新锁对象职责、交互来源和主操作锚点；不得为了先过图、先过测，就临时补一个小按钮、小提示条或小确认区，把补丁反写成正式合同。
- **固定牌桌类游戏的 PC live 默认禁止页面级滚动**：除非规则或用户当轮明确允许长桌/可滚动战场，桌面进行页必须在 `1920x1080` 首屏内看到完整主状态；放不下时先调内部比例、留白和非核心装饰，不得把 `body` 页面滚动当主布局方案。
- **固定牌桌截图验收必须单独检查最外侧对象完整性（强制）**：像公开牌河、手牌带、棋盘边缘格、最左最右基地、最外侧角色卡这类“靠边对象”，验收时不能只看“整体没重叠”。必须额外确认三件事：① 最外侧对象不是被相邻对象盖成半截；② 没有被父容器、遮罩、阴影或截图边界裁掉主体轮廓；③ 外缘没有异常透明框、灰边、假描边或只在边缘牌上出现的脏边。只要最外侧对象看起来像“少了一截”或“边缘发灰发白”，即使 DOM、矩形和主流程都通过，也不得收口。
- **固定牌桌边缘异常不得误判成截图裁切（强制）**：用户反馈“边上的牌像被裁了 / 只剩半张 / 有透明边框”时，默认必须同时核对真实截图和当前实现层级，区分到底是截图边界、容器裁切、对象互相遮挡，还是卡面外框/阴影/资源透明边导致的视觉假象。没有明确分清成因前，不得用“截图刚好截到这里”“只是重叠一点点”“看起来问题不大”收口。
- **固定牌桌移动端验收不得只盯中央牌河（强制）**：当用户正在反馈手机横屏 live 牌桌时，验收截图至少要同时检查三组对象：① 中央公开牌河的步长、错位、遮挡；② 左上/右上/左下/右下角锚点对象是否完整可见，例如牌库、计数、头像、角标；③ 主动作按钮是否离壳层边缘过近、是否像“贴边漂着”。只要其中任一组还存在“角落对象只露半截”或“按钮明显贴边”的现象，就不得用“中央牌河已经对了”来宣布通过。
- **截图验收不得用几何断言替代肉眼结论（强制）**：在固定牌桌、移动横屏、同构 PC 牌桌这类任务里，`不重叠 / 不越界 / 步长一致 / 左偏量正确` 只能证明几何约束成立，不能自动推出“图已经对了”。完成截图验收时，必须显式写出自己从图上看到的现实结论，例如“左上牌库完整可见”“右侧主按钮未贴边”“最外侧公开牌主体完整”；如果这些现实结论没有被逐项说清，就视为还没真正看图。
- **固定牌桌类游戏不得用禁用主按钮充当步骤提示**：`确认选择`、`结束回合`、`确认弃置` 这类主按钮，只应在已有真实可确认对象时出现。若当前步骤只是要求玩家先选对象，应由对象本体和最小短提示承接，不得常驻一个禁用大按钮来解释步骤。
- **常驻文案不得重复视觉已经表达的信息（强制）**：当高亮、箭头、连线、选中态、禁用态或按钮位置已经清楚表达“哪里可选、往哪里走、当前选中了谁”时，常驻 UI 文案只允许补动作意图、成本、结果或必要对象名。禁止再写“点击绿色目标 / 绿色区域都能点 / 沿箭头走 / 点右侧按钮”这类复述视觉信号的说明。具体交互原则见 `design-system/game-ui/MASTER.md` 的“文案不得复述视觉信号”。
- **按钮已摆出来时不得再写“可选”（强制）**：当按钮本体已经作为当前候选入口出现在主 UI，且视觉上已具备正常可点击语义时，不得再额外贴一个 `可选` 状态词。只有 `当前 / 处理中 / 已锁定 / 不可用原因` 这类按钮自身不能独立表达的信息，才允许再加状态标签。
- **联机前置选择默认不得只放在建房页或常驻 HUD（强制）**：只要前置项会影响某个 seat / 阵营 / 私有手牌 / 私有负载配置，默认必须在进入对局后的局内 setup 层完成。若剧本本体还需要介绍、候选对比、全员投票或同票裁定，剧本本体也默认属于局内 setup，不得继续在建房页预设最终结果。建房页只保留房间级公共参数或房间模式开关，不得用默认值替代玩家在 match 内本该完成的私有或共同决策。
- **联机局内 setup 不得压在正式棋盘 HUD 上（强制）**：剧本投票、阵营选择、人物/军备/loadout 这类进入正式对局前的共同或私有决策，必须是独立 setup 页或独立 setup 壳层。该阶段不得同时渲染正式棋盘的主行动控件、手牌、牌库、弃牌、动作栏等主 HUD；最多只能保留弱化背景或阶段装饰。否则用户会误判“已经进局但被面板挡住”，也会形成重复无效 UI。
- **在线房间不得按本地同屏视角实现（强制）**：联机页面的 UI 语义必须先绑定具体 viewer/seat。非本 seat 的手牌、私有 prompt、私有 setup、私有候选默认不得出现在当前页；也不得因为轮到别人行动，就把当前页面直接切成对方视角。若当前 viewer 解析不到对应 seat / faction，必须显示空态、等待态或明确错误提示，不能回退成“当前行动势力视角”。若当前实现没有 viewer 隔离，就不能宣称“联机 UI 已完成”。
- **联机 E2E 证据截图必须先锁“这是谁的页面”（强制）**：只要是联机流程截图，动手前必须先锁定当前截图到底来自 `房主页 / 玩家 A 页 / 玩家 B 页 / 玩家 C 页 / 观战页` 中哪一个 viewer 页面。若用户要看“我自己的完整流程”“固定某个玩家端从头看到尾”，则整条截图链必须固定在同一 viewer 页面，禁止为了让步骤继续推进而中途切去别的 seat 页面拍图，再把结果命名成单人连续流程。
- **跨席位截图不得冒充单玩家流程（强制）**：如果某张图确实来自别的 seat 页面，文件名和步骤名必须显式写出 `玩家 B 页 / 玩家 C 页 / 接收方页 / 发送方页` 这类视角归属；不得使用 `第3步-别人行动窗口`、`玩家 A 结束后-玩家 B 行动窗口` 这类会让读者误以为仍在同一用户页面里的命名。
- **联机流程通过不能只看测试绿，还要看截图视角口径是否一致（强制）**：当验收目标是“固定玩家视角连续体验”“别人行动时我仍只看自己的私有信息”“我被动等待时界面是否友好”时，E2E 即使断言全绿，只要证据截图链跨了 viewer 页面，也不得宣称该验收目标已经完成。必须回到正确 viewer 页面重拍真实链路。
- **非当前玩家行动不得自动抢走 viewer 视角（强制）**：多人牌桌、地图、棋盘或战场 UI 必须区分“规则上的当前行动者”和“当前页面 viewer 正在看的区域”。轮到其他玩家、AI、怪物或系统行动时，允许显示其行动摘要、日志、短暂动画或可手动定位入口，但不得无条件把地图楼层、缩放中心、手牌/角色面板、主提示或私有信息切成对方视角。只有 viewer 主动点击定位、当前查看区域已失效、或规则明确要求全员观看同一公共对象时，才允许自动校正视角；验收必须在固定 viewer 页面证明别人行动后原查看区域仍可控。
- **局内 setup 的 waiting 页不得泄露他人可操作卡片（强制）**：当当前页只是等待其他 seat 完成 setup 时，只允许展示紧凑 waiting 壳层和最小摘要；不得继续把别人的可点击人物/军备/阵营候选直接摊在当前页上，让等待页看起来也能操作。
- **一级行动与二级步骤必须有唯一主入口（强制）**：允许保留“一级行动 / 二级步骤”的语义分层，但这只是理解层级，不应默认再加一层选择交互。当流程是“先定一级行动，再选目标/支付/确认”时，首屏只能有一个当前主入口承担节奏推进。若当前规则与状态已经唯一确定一级行动，必须自动锁定并直接暴露对应二级行动；不得再要求用户额外点击一次“一级行动按钮”做重复确认。只有同一时点确实存在多个并列且都合法的一级行动、并且规则没有自动锁定时，才允许让用户先做一级选择；进入一级行动后，二级目标与提示才允许升到前景。
- **无目标决策的唯一强制动作不得让页面空掉（强制）**：当当前规则态只剩一个合法动作，且该动作不需要玩家选择目标、支付对象、顺序、数量或是否放弃时，可以自动推进，也可以按本游戏既定交互保留一个显式状态入口；但两种做法都必须让玩家一眼知道页面正在做什么。若自动推进会造成短时间或异常情况下没有任何主入口、只剩对象本体或空桌面，就必须保留可见主按钮、灰态状态按钮或明确 waiting 控件。像 Fantasy Realms 开局摸牌这类没有并列选择的固定推进步骤，应直接自动推进；进入弃牌阶段后即使实际弃牌由手牌承接，也必须保留灰态 `弃牌` 锚点。
- **一级动作进入前景后，同级一级按钮必须退场（强制）**：当用户已经选中某个一级动作，并开始暴露该动作的二级目标时，同级的其它一级动作按钮必须立即收口，不能继续和二级目标同屏并列。像 `拿公开牌` 已经进入选牌态时，`摸牌` 按钮必须退场；否则视觉上会退化成“三选一/多选一错觉”，把 `一级动作` 和 `二级目标` 混成同一层。
- **一级动作若只是在选目标，不得继续保留同名大按钮（强制）**：当某个一级动作已经进入前景，且当前真正需要点击的是它的二级目标集合时，这个一级动作本身不得再以同等级大按钮和目标并列出现。此时一级动作最多降级成轻量状态词或完全退场；例如 `拿公开牌` 进入选卡态后，只保留可选公开牌，不再并排保留一个同名大按钮。
- **一级动作不得代点唯一目标（强制）**：当某个一级动作已经进入前景，且二级目标集合只有 1 个时，也不得把该一级动作按钮继续做成“点一下直接选中唯一目标并结算”。它必须退场、降级为状态词，或只负责聚焦目标；真正结算必须由用户点击高亮对象本体完成。
- **动作入口数量必须服从当前真实公共信息（强制）**：动作栏不能按“这一阶段通常可能出现什么”预支入口，只能按当前真实公共区与当前规则态生成。若目标区为空、当前规则明示禁止、或当前真实公共信息还不成立，就不得提前渲染对应入口。像 Fantasy Realms 开局时 `弃牌区为空`，且首位玩家第一回合本就不能从弃牌区拿牌，此时只能出现 `摸牌`，不得提前画出 `拿公开牌`。
- **设计稿也必须服从当前规则态（强制）**：游戏 UI 草稿、效果稿、截图标注和正式实现都必须先从权威规则/领域状态推导“此刻同时合法的动作集合”。禁止为了表达完整流程，把不同时机的动作画成同屏并列选择；例如 `摸牌 / 拿公开牌` 属于摸牌阶段二选一，`弃牌` 属于后续弃牌阶段，不能在同一个当前玩家操作态里做成三选一。若当前状态只允许两个动作，设计稿和实现都只能出现这两个一级入口；若下一阶段才出现第三个动作，必须作为阶段切换后的另一张状态稿或另一种渲染态。
- **动作栏必须由规则态生成，禁止按钮条件散落（强制）**：游戏进行页的主动作栏必须先列出“当前阶段合法动作集合”，再渲染按钮；实现上不得把 `摸牌`、`拿公开牌`、`弃牌`、`结束回合` 等按钮用互不相干的布尔条件分别塞进同一动作栏。若规则规定 `draw` 阶段只有 `摸牌/拿公开牌`，动作栏最多两个按钮；进入 `discard` 阶段后动作栏只能换成弃牌确认相关入口，上一阶段按钮必须消失。截图验收必须核对按钮数量与阶段规则一致，而不是只看按钮文案存在。
- **当前步骤不得在视觉上像“卡死”（强制）**：只要当前页面仍需要用户继续完成某一步，或页面正在等待一个对用户重要的系统阶段结束，就必须给出**显式可见的状态化主入口**，不能让用户只能靠猜测对象本体去试点。允许的形式包括：可点击主按钮、灰态主按钮、明确 waiting 状态牌或等价主控件。像 `discard` 阶段如果真正的提交入口在手牌本体上，动作栏也仍必须保留一个显式 `弃牌` 状态按钮作为锚点；禁止把按钮区清空后只剩可点卡牌，让页面看起来像没有下一步。该规则不要求所有状态都可点击，但要求所有关键状态都**一眼能看出现在该做什么或在等什么**。
- **临时结果层必须让出主阅读对象（强制）**：事件牌、发现牌、技能牌、房间牌、目标选择和投骰结果同屏时，主阅读对象优先保持可读；投骰、加值、总点数、结算按钮只能作为自适应结果坞、侧向/底部信息区或同卡片内的次级区域。禁止用固定右上角骰盘、全屏居中大结果层、整块背景框、强阴影盒子或持续遮罩抢走牌面/地图/目标的主焦点。结果层必须有明确继续/关闭路径，关闭后阻塞层、选中态和最近结果都要退场；若流程还允许改骰或选择目标，合法对象必须仍能被看见和点击。
- **隐藏态控件不得残留为可发现入口（强制）**：弹窗、放大预览、菜单、临时层关闭后，不得把关闭按钮、确认按钮、隐藏菜单项继续留在可访问树、可 tab 聚焦范围、测试可发现的 role/name、或主 UI 文本流里。允许为了性能保留容器壳层，但关闭态必须 `aria-hidden`，且不渲染或禁用内部交互按钮。禁止让用户、测试或读屏工具在主界面里发现一个实际不可见的 `关闭预览`、`确认`、`继续` 等隐藏按钮。
- **唯一一级动作已锁定时，不得退回桌面对象猜入口（强制）**：如果当前合法一级动作只剩一个，但仍需要玩家选择目标、确认对象、支付或主动结束时，UI 必须把该动作做成显式主入口或直接暴露对应目标；不能因为桌面上“正好有个牌堆/牌河/按钮看起来也许能点”，就让玩家自己猜该点哪里。若该动作没有目标决策，应按“无目标决策的唯一强制动作不得让页面空掉”处理：可自动推进，也可保留显式状态入口，但不得让页面看起来没有下一步。
- **等待摘要必须按人能读懂的层级组织（强制）**：等待态可以提示“等谁、还差几项”，但不得把同阵营的多条待决项机械重复成一串字段样文本。默认应按阵营或角色归并，让用户一眼读懂当前阻塞来源。
- **非当前操作者视角不得显示“他人步骤提示”（强制）**：当当前 viewer 只是等待别人行动时，顶部/侧边状态区默认只允许表达“谁在行动、我在等谁、当前是否轮到我”。像 `摸牌`、`弃牌`、`确认选择`、`确认弃置` 这类只对当前操作者有直接操作意义的步骤提示，不得展示给等待方当作常驻 cue；否则会制造“我也该点这里”的假 affordance。若确需暴露流程阶段，也必须明确降级成只读总结，而不是伪装成可操作提示。
