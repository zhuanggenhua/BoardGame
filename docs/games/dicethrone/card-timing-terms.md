# DiceThrone 卡牌时机与术语裁定

> 适用：处理 DiceThrone 卡牌、阶段、骰子修改、响应窗口、手牌可用性相关 bug 或回归时。

## 强制拆分

DiceThrone 反馈里不能把“颜色”“类型”“使用时机”“效果目标”混成一个概念。动手前至少拆清：

- `卡牌颜色`：例如红色卡。
- `技能/伤害图面颜色`：例如能力框、伤害图标、伤害类型颜色或规则书颜色提示；这些是规则信号，必须进入录入合同，不能只看代码里的 `damage` 事件。
- `卡牌类型/使用窗口`：例如即时牌、阶段牌、响应窗口可用牌。
- `效果目标`：例如修改自己的骰子、修改对方的骰子、强制重掷、调整点数。
- `阶段归属`：进攻掷骰、防御掷骰、伤害结算前后、玩家主阶段等。
- `现实操作者`：当前回合玩家、当前掷骰者、防御者、响应者。

## 红色即时牌口径

- 红色即时牌默认按“即时牌 / 可在任意时机打出”理解，不得把红色即时牌称为“防御阶段牌”。
- “防御阶段能用来改骰子的牌”只描述效果发生的阶段和目标，不代表该牌本身的颜色或类型是防御阶段牌。
- 如果一张牌的描述限定“只能在其防御投掷阶段”或类似语义，默认按黄色防御阶段牌处理；必须同时满足：当前确实在防御掷骰阶段，并且操作者就是正在掷自己防御骰的人。
- 反过来，不能因为对方回合就一刀切禁用所有可用手牌；也不能因为当前是防御阶段就放开非当前防御掷骰者打防御骰牌。

## Token 直接使用与响应收口

- 主动 Token 的图标本体是玩家交互载体。响应阶段出现可用 Token 时，玩家直接点击自己面板上带可用高亮的 Token 图标即可使用；Token 响应不得先打开阻塞式 Token 弹窗，再让玩家去弹窗里找同一个 Token。
- 卡牌响应与 Token 响应共用同一个位于手牌上方的非阻塞提示框和跳过/确认入口；提示不能进入 Token 行的布局流、替换 Token 槽位、遮挡 Token 图标或把 Token 移到弹窗里。Token 本体必须在提示出现前后保持同一实体锚点。
- 一次直接点击按该 Token 的最小合法使用数量消费；允许重复使用时继续点击同一个 Token。领域层仍以 `getUsableTokenAmountForTiming` 和 `getTokenUseOptions` 为唯一合法性判断，UI 高亮不能绕过时机、响应者、攻击伤害范围或窗口次数限制。
- Token 使用后的伤害、闪避骰和当前响应状态必须继续显示在原牌桌/骰区附近；普通跳过仍使用手牌上方的共享响应提示框，闪避骰出现后的收口只使用右侧骰盘下方的普通“确认”按钮，不使用覆盖主棋盘的阻塞式弹窗，也不在 Token/骰区新增第二个操作条。
- 响应阶段的玩家流程固定为：`Token 本体高亮 → 点击 Token → 领域层使用并更新当前结果 → 继续点击其它合法 Token、点击共享提示框的跳过，或在闪避骰出现后点击右侧骰盘确认 → 响应关闭并回到原结算步骤`。同一次伤害里允许重复使用同一个可重复 Token 时，每次点击只能按该 Token 的最小合法数量消费一次，不能一次吃掉多个。
- 太极、闪避这类可直接使用的响应 Token 是该流程的代表验收路径：太极必须证明点击 Token 后当前伤害数值随之变化，跳过/确认后才正式结算血量；闪避必须证明点击 Token 后闪避骰进入右侧骰盘且仍可被合法改骰/重投，失败且仍有剩余闪避时可以继续点击 Token 重试，每次只消耗 1 个，最后通过右侧骰盘确认收口。两者都不得恢复 `TokenResponseModal`，也不得把提示条塞进骰盘或右栏。
- 如果主动效果还需要选择骰子或其它目标，Token 点击只进入选择态；之后必须高亮合法目标本体并由玩家点击目标，不能因 Token 已点击就自动填入唯一目标并结算。
- 只有确实需要从多个目标、状态或选项中继续选择的 Token 效果，才允许打开目标选择层；`rollToNegate`、伤害增减、不可防御等可直接结算的响应 Token 禁止使用默认弹窗。
- 被动 Token、规则上不属于当前响应窗口的 Token，以及卡牌效果内部的 Token 选项，不得因为共用 Token 图标就自动放行；它们必须分别走对应的阶段/选择合同。
- `TokenResponseModal` 不再是响应 Token 的职责入口；不得恢复其默认调用、测试断言或“有可用 Token 就弹窗”的注释。需要目标选择时使用对应的目标选择交互，不得把同一个可直接使用的 Token 复制到弹窗按钮。

## 响应、骰盘与弹窗的唯一归属

- 普通卡牌响应和 Token 响应共用手牌上方的共享提示框；它只承接“继续响应 / 跳过 / 确认收口”，不承接骰面本体。
- 普通攻击骰、闪避骰、奖励骰、决斗/摊牌等对掷骰，以及它们的改骰/重投，都由右侧 2D 骰盘承接。需要收口时只能使用骰盘下方的普通“确认”按钮；不得在响应框、奖励骰摘要层或独立弹窗里复制确认。
- `dt:bonus-dice` 是领域层的阻塞交互状态，不是玩家可见的弹窗类型。它不能被 `simple-choice` 或 `BonusDieOverlay` 接管；UI 必须读取当前骰上下文并渲染右侧骰盘。
- 只有比较结果、多个目标或其它确实需要继续选择的交互，才允许进入对应的选择层。选择层只承接结果文案、选项和等待状态；骰子本体仍留在右侧骰盘，不能在选择层里复制成中间骰子特写。
- 骰盘是骰面本体、选骰、改骰、重投和普通确认的输入区，不是结果选择弹窗容器。禁止把所有和骰有关的弹窗都塞进右侧骰盘；决斗 / 摊牌的对掷结果层必须作为主舞台上的结果 / 选择层展示，等待态和选项要能被人直接读懂，但不得复制骰子本体或恢复中间骰子特写。
- E2E 必须同时断言：目标状态下右侧 `dicethrone-2d-dice-tray` 可见、普通 `dice-confirm-button` 可用或按状态禁用，并且 `bonus-die-overlay`、`bonus-dice-confirm-button`、`token-response-modal` 与中间骰子特写 `roll-spotlight-dice-content` 不存在。涉及太极、闪避、决斗这类反馈时，最终截图必须是有序图组，至少覆盖使用/投骰前、使用/改骰后待收口、收口后结果三段。

## 官方伤害类型口径

- Rulepop 伤害表列的是伤害类型属性，不是给本地实现另造“大招特殊处理”规则。当前 bug 裁定只需要区分：`Undefendable Damage` 是否仍可被卡牌/状态效果响应，以及非攻击来源伤害是否能吃攻击修正。
- `Undefendable Damage` 官方口径：不可防御，但仍是 `Avoidable`；`Avoidable` 的官方定义包括被卡牌或状态效果降低、防止、闪避或打断。实现上不能把“不可防御”扩展成“不能用 Token 减伤/防止/闪避”。
- Rulepop 也列有 `Ultimate Damage` 条目：这是终极招式造成的一类特殊不可防御伤害，伤害表里标为不可 `Avoidable`。这只用于解释终极招式结算后的不可避免口径，不得反向扩大到普通不可防御伤害。
- 进攻骰确认并选中终极招式后，仍必须先开放正常的改骰、重掷响应窗口；对手可以通过合法卡牌改变骰面，使终极骰型不再成立。终极来源产生的任何未结算额外骰也沿用同一改骰规则，不能因来源或展示方式被锁定。
- 图面颜色、伤害类型和文字描述必须共同决定“是否进入防御投”。`DAMAGE_DEALT` 或 custom action `categories: ['damage']` 只能说明会造成伤害事件，不能单独证明这是可防御攻击伤害。像附属伤害、目标选择后直接伤害、非攻击来源伤害，必须在录入合同里显式写成“不触发防御投”或“需要防御投”，再由实现消费该合同。

## 不可防御伤害与可避免边界

- 官方 Rulepop / Dice Throne 规则索引口径：普通 `Undefendable Damage` 是不可防御但仍可被卡牌或状态效果响应。
- `不可防御` 在实现里只表示不能使用防御技能，不等于不能用受伤前卡牌、状态 Token 或其他合法避免效果减伤、免伤、闪避或打断。像忍者 `九字切` 这种普通不可防御直伤，应允许防御方用 `太极` 这类状态 Token 减伤。
- 非攻击来源伤害不属于攻击伤害：不能开放攻击方攻击修正或攻击加伤 Token，也不能使用防御技能；但只要不是终极伤害，仍可被防御方卡牌或状态效果避免。
- 终极招式的不可避免只按官方终极条目处理；不要把它扩展到普通不可防御伤害。

## 骰子重投统一执行合同

DiceThrone 的普通重投、卡牌重投和主动 Token 重投可以有不同的时机、目标、费用和交互命令，但“当前骰区指定一颗骰子并执行重投”的领域动作只有一个执行真相：

- `REROLL_DIE` 与 `USE_PASSIVE_ABILITY` 的 `rerollDie` 分支必须共用当前骰重投执行器，统一生成随机点数、`DIE_REROLLED` 事件、骰区目标归属和进攻技能重选事件。
- 主动 Token / 被动重投的 UI 可用性必须按“当前骰区是否允许被动重投、该骰是否仍可介入”判断；覆盖主进攻骰、防御骰、奖励骰、比较骰、闪避骰及其它临时骰。禁止只为 `defensiveRoll` 或 `afterRollConfirmed` 写特例后宣称重投链路收口。
- 是否要求重选攻击技能只由“当前骰区是否为主进攻骰”决定，不能只看当前阶段是 `offensiveRoll`：主进攻骰被改面或重投后才重选；奖励骰、比较骰、闪避骰及其它临时骰即使在进攻阶段出现，也只能更新自己的结果，必须保留原 `pendingAttack`、原伤害和后续防御/收口链。普通改骰与重投都消费这同一条判断，禁止各自按阶段猜测骰子身份。
- 右侧 2D 骰盘只是统一的玩家选择入口；不能因为 UI 入口相同，就在不同命令分支里重复写骰面生成和状态回写，也不能因为命令入口不同就复制一套重投实现。
- 奖励骰结算专用的 `REROLL_BONUS_DIE` 可以保留独立事件，因为它还要更新奖励骰结算次数、费用账本和奖励骰结算字段；但随机点数必须复用统一的骰子随机原语，不能再维护第二套随机实现。
- 新增任何“重投一颗当前骰”的卡牌、Token 或技能前，必须先复用该执行器；只有新增的状态生命周期确实不同，才允许增加新的外层命令或事件，并在测试中说明专属差异。

## 显示型奖励骰与主攻击生命周期

- `displayOnly` 只说明奖励骰本身不按默认“骰面总和伤害”结算；它不表示产生该奖励骰的主攻击已经结束，也不能据此把主攻击直接置为 `readyToResolve`。
- 奖励骰专属结算器若根据最终骰面把原本无伤害的技能转为攻击，必须在同一 `PENDING_ATTACK_UPDATED` 中明确写入伤害、`isDefendable` 与正确的结算阶段。战争贩子的军刀结果固定为基础版 5 点、II 6 点可防御攻击，并恢复到 `preDamage`，随后进入防御投掷。
- 同一类显示型奖励骰若规则结果是直伤、抽牌、Token 或额外进攻，则由其专属结算器明确收口或转入对应阶段；不得借用“显示型”这一 UI 属性猜测攻击是否应继续。
- 回归至少覆盖：真实技能槽选中、奖励骰最终面、右侧 2D 骰盘普通确认、确认后主攻击的阶段与可防御伤害；不能只注入已经构造好的 `pendingAttack` 作为证据。

## 回归验收门禁

修改 DiceThrone 卡牌时机、手牌可用性、视角自动切换、响应窗口或改骰牌逻辑时，不能只用截图或单条正向链路收口。至少补并跑通以下自动化断言：

- 用户点名卡牌正向：必须锁定用户点名的中文牌名、卡牌 ID 和普通触发入口；不能用另一张相似颜色或相似类型的牌替代。若用户点名“这玩意儿真棒！”，回归测试就必须覆盖 `card-artificer-perfectly-calibrated` 本体。
- 红色即时牌正向：非当前回合玩家在普通对方回合能打出红色即时牌，卡牌离开手牌、进入弃牌堆，并结算对应效果；测试必须经过真实出牌命令校验，不能只直调效果结算函数。
- 防御阶段牌负向：描述限定防御投掷阶段的牌，例如“就这？”，在非防御掷骰阶段不能打出；在防御掷骰阶段也只能由当前防御掷骰者打出。
- UI 入口正向：自己的手牌不应因为自动切到对手视角或不是当前回合玩家，就被整体禁止拖动打牌；真正能不能打由卡牌规则校验决定。
- UI 入口负向：观察者仍不能操作手牌；卖牌、弃牌等只属于当前回合或弃牌阶段的动作不得被红色即时牌规则顺手放开。
- 技能/卡牌使用时状态：如果效果会打开选择窗口、响应窗口、奖励骰面板或其他中间交互，必须验证使用时玩家能看见对应中间状态，不能只断言底层命令成功。
- 技能/卡牌使用后状态：必须至少验证一个用户能看见的最终变化，例如血量、资源、状态标记、Token、弃牌堆、阶段推进或交互关闭；截图只能作为可见性证据，不能替代最终状态断言。
- 多步改骰/重掷交互：凡是“选择至多 N 颗骰子”“修改 N 颗骰子”“复制一颗骰子的骰面到另一颗骰子”这类牌，必须同时验证正向、少选、超限和重复选择。`俺也一样！` 这类复制牌必须证明源骰和目标骰是两个独立步骤，重复点击同一颗源骰不能提前完成；`我又行了！`、`就这？`、`不愧是我！` 这类“至多 N 颗”重掷牌必须证明少选后可以手动确认，继续多选会被上限挡住；`意不意外？！` 这类多骰改面牌必须证明能一次修改多颗不同骰子，且不能用重复点击同一颗骰子冒充多步完成。
- 防御阶段改对方骰子：若用户原问题是“防御阶段改别人的骰子”，验收必须在 `defensiveRoll`、防御骰确认后的响应窗口、出牌者选择对方骰子的真实 UI 上完成。截图至少覆盖出牌后选择提示、目标骰被选中、结算后对方骰结算状态；不得用普通进攻投掷、自己骰子或只看最终骰面变化替代。DiceThrone 当前统一使用右侧 2D 骰盘，所有自己骰子和对方骰子的直接选择、改面、锁定和重掷都必须回到同一骰盘入口；不得再用棋盘内 3D 骰台或显示开关替代。重掷牌的验收要以真实重掷事件和动画入口为准，不能要求骰面必然变化；即使随机出相同骰面，也必须产生重掷事件并播放重掷动画。
- 2D 骰盘交互提示口径：复制骰面类牌必须分清“选择要复制的源骰子”和“选择要设为源骰面的目标骰子”；设置指定点数类牌才允许写“选择要设为 N 的骰子”。提示 UI 只能说明当前步骤，真实交互必须由右侧骰子本体和其紧邻的加减/确认控件承接；不得用棋盘内第二套骰子或透明物理命中层制造另一条选择路径。截图验收必须覆盖复制源骰、复制目标骰、任意改面加减、重掷选择这几类不同提示，防止把 `俺也一样！`、`再来一次`、`意不意外？！` 等牌混成同一个交互。
- 改骰/重掷响应时机：进攻骰确认后，若规则要求先选定攻击，测试夹具也必须走“确认骰面 → 选择攻击 → 响应窗口打牌”的真实链路；旧测试不能停在“只确认骰面”后直接打攻击修正牌。终极招式同理，发动前仍走普通改骰响应窗口，进入 `Ultimate Damage` 结算后才适用不可避免边界。
- 掷骰时机牌与当前骰区：当前骰区存在未结算的奖励骰，只说明该骰能否成为合法目标，不能改写卡牌自身的阶段时机。“来个六！”这类掷骰时机牌仍只能在进攻、防御或目标掷骰阶段使用；主要阶段即使因卡牌效果留下奖励骰或响应窗口，也不得打出。测试必须覆盖这条主要阶段负向断言，不能把“当前骰区允许改骰”写成主要阶段放行。
- 奖励骰与攻击骰分流：奖励骰不是攻击骰。所有奖励骰在投出后都必须先停在右侧当前骰盘，等待骰主点击骰盘下方的普通“确认”才结算；不得因为没有可响应、没有奖励骰内置重投资格或所有响应者让过，就自动按当前骰面结算。通用改骰牌、Token 和能力仍只由响应窗口承接；响应关闭后回到同一右侧骰盘。奖励骰结算自身允许重投时，骰主可先直接点击右侧骰子重投，再点击同一个普通“确认”收口；若该重投设置了 Token / 资源费用，点击骰子必须扣除对应费用；只有费用明确为 0 时，才可描述为不消耗 Token / 资源的重投，不得把所有奖励骰内置重投统称为“免费重投”。不得另造奖励骰专用确认入口。中央奖励骰特写、卡牌特写内嵌骰子和 `BonusDieOverlay` 都不是该流程的展示或交互入口。打出卡牌本体的可读特写由卡牌事件队列承接，不能因为奖励骰转入右侧骰盘而被清空或隐藏。
- 奖励骰影响面审计：修改奖励骰、临时骰、右侧骰盘确认、奖励骰重投或调试改骰入口时，必须把影响面至少扫到五类事实：生产渲染入口是否仍调用旧特写/专用按钮；共享 E2E 驱动器是否承接右侧骰盘普通确认；对象 E2E 是否仍断言自动结算、旧 `bonus-die-overlay` 或旧 `bonus-dice-confirm-button`；旧 evidence 是否仍把旧特写/自动结算当当前结论；奖励骰期间普通攻击技能候选是否被清空且来源技能只保留为来源感。未完成这五类扫描时，只能说“局部修复”，不得说奖励骰链路已审计或已收口。
- 奖励骰期间的技能槽候选：未确认的奖励骰只能驱动右侧骰盘、响应窗口和奖励骰结算处理器，不能重新计算或点亮普通攻击技能槽。玩家板可以保留本次来源技能的选中/来源感，但其它技能不得因为奖励骰面临时满足组合而高亮、可点或进入分支选择；例如死亡盛放 II 的奖励骰出现两个面具时，不得点亮烟雾阵。来源选中感只属于未结算奖励骰期间；点击普通“确认”完成奖励骰结算后，来源技能选中态应随 pending 清理，后续只保留骰盘最终骰面的只读回看。
- 响应 Token 的后续奖励骰：Token 点击只负责消费 Token 并建立奖励骰结算态；原伤害响应收口与奖励骰效果结算必须分成两个正式步骤。像武士背击这种“投骰后反伤”的效果，反伤只能由统一奖励骰结算处理器按最终骰面生成，不能在点击 Token 时提前塞进原伤害的延迟伤害队列，也不能让 E2E 在原伤害关闭前冒充反伤已经结算。
- 奖励骰结算后的右侧回看：点击普通“确认”只结束改骰资格，不删除投掷结果。右侧骰盘必须保留本次奖励骰的全部最终骰面为只读回看，直到下一次投掷或其它新骰区覆盖它；不得在确认结算后清空骰盘。
- 奖励骰确认的 UI、AI 合法动作和自动恢复必须同源：当前玩家看到右侧骰盘普通“确认”时，AI 也必须枚举同一条普通确认动作；旧“跳过奖励骰重投 / 奖励骰响应”只能作为历史兼容命令，不得作为玩家或 AI 的主交互语言。
- 调试改骰入口：调试面板和测试工具修改当前骰值时，也必须复用“惊不惊喜？！”这类任意时刻改骰牌的同一条当前骰区改骰语义。现实含义是只改玩家当前实际看到和后续会结算的那颗骰子；实现上应进入统一的骰子修改事件链（`DIE_MODIFIED`），让普通攻击骰、闪避骰、奖励骰/临时骰同步更新骰值、骰面和结算参数，不得在调试工具里直接再写一套奖励骰字段修改逻辑。
- 奖励骰 E2E 控制：技能或卡牌额外投出的奖励骰必须用奖励骰骰面 helper（`setDiceThroneBonusDiceValues(page, [1-6...])`）控制；底层 `random.setQueue` / `setDiceThroneRandomQueue` 接收的是 0-1 原始随机数，不是骰面值。不要用普通攻防骰池 helper（`setDiceThroneDiceValues`）伪造奖励骰，也不要把 `[4, 5]` 直接传给 `random.setQueue`；否则会把奖励骰回归遮住，出现“截图像走了流程但实际随机值不受控”的假证明。
- 在线主骰面权威性：真实在线 E2E 中，`setDiceThroneDiceValues` 只可作为客户端测试工具或随机准备，不得用它证明服务器已经接受主骰面。需要固定主骰面以进入技能或攻击链时，必须通过项目正式 `/test/inject-state` 状态注入入口更新服务端 `core.dice`，再回到真实命令和页面验证；客户端调试面板覆盖后被联机状态改回随机值时，必须判为测试夹具错误，不能放宽技能可用断言。
- 响应提示空间合同：当前 DiceThrone 响应提示使用历史固定 HUD 槽位，锚点为视口，位置为手牌抬起区上方；它不跟随手牌 hover 或卡面变形，也不进入骰盘/右栏/Token 行。E2E 截图验收至少同时证明响应条水平居中、处于固定手牌抬起槽位、hover 手牌时位置不漂移、手牌和右侧骰盘未被遮挡。若未来要改成对象几何锚点，必须作为新设计单独获得用户授权，不能作为回归修复默认方案。
- 流光与确认入口合同：响应条的流光必须是沿自身外轮廓连续旋转的单条亮线，不能用堆叠阴影、重复方框或额外背景面冒充；奖励骰摘要层不得再渲染“确认奖励骰”“结算奖励骰”或同义专用按钮，未结算奖励骰统一由右侧 2D 骰盘的普通“确认”收口。已有专用确认文案即使暂时没有出现在截图，也属于违规实现，必须从真实 render 分支删除。
- 链路截图最终帧：如果对外声称“造成伤害、获得资源、获得/移除 Token、弃牌成功”等结果，最终截图里必须让对应可见数字或标记入镜、已经更新且无遮挡可读；例如声称对手掉血 5 点时，截图里的对手血量必须清楚显示最终值 45，不能仍显示冻结前的 50，也不能被“-5”飘字、爆字、弹层或特效遮住。
- 动画冻结等待：如果存在飞行动画、受击动画、飘字特效或血量冻结缓冲，E2E 必须等用户可见 UI 解除冻结、遮挡层消失并显示最终值后再截图。内部状态断言只能证明结算逻辑，不能替代图面验收；图面看不到变化或变化被遮住时，不得向用户声称链路截图已证明变化落地。

## 汇报要求

向用户解释时必须使用清楚口径，例如：

- 正确：`“就这？”是黄色防御阶段牌，只能在自己防御掷骰阶段由当前防御掷骰者使用。`
- 正确：`红色即时牌是任意时机牌，不等于防御阶段牌。`
- 正确：`这次修的是“这玩意儿真棒！”本体的红色即时牌回归，不是用另一张红牌证明同类牌大体可用。`
- 错误：`防御阶段红卡可以用。`
- 错误：`红卡是防御牌。`
- 错误：`用“老大真慷慨”通过了，所以“这玩意儿真棒！”也修好了。`

如果涉及代码证据，先说现实含义，再写符号。例如：“当前掷骰者是防御方，代码里的 `rollerId` 等于该玩家”。
