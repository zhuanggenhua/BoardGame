## 规则结构摘要

- 游戏目标：两名法师在竞技场内决斗，击败对方法师获胜；多人规则为后续扩展，不建议纳入首轮本体。
- 空间模型：当前运行目标使用标准竞技场 12 格区域。学徒模式曾作为教程 / 早期素材理解中的 2x3 半场参考，但不再是当前实现目标。距离按上下左右相邻区域计算，不走斜线；墙体占区域边界，并可阻挡移动、造成通行伤害或阻挡视线。
- 回合结构：准备环节包含起始、重置、聚魔、维持、计划、部署；行动环节包含优先快速施法、生物行动、最终快速施法。
- 行动结构：生物行动通常是“移动 + 快速行动”或“停留 + 标准行动”；快速行动含快速攻击、快速法术、守卫、第二次移动、特殊快速行动。
- 法术结构：攻击、咒语、生物、魔物、结界、装备六大类型；法术书每回合计划最多 2 张，未施放返回法术书。
- 隐藏信息：结界正面朝下附属，展示时支付展示费用；强制结界和陷阱有严格触发时机，不能用 UI 简化成普通公开状态。
- 战斗结构：攻击按 8 步结算：宣告攻击、回避攻击、投掷骰子、伤害和效果、额外打击、反伤屏障、反击、攻击结束。
- 状态/特性：飞行、守卫、束缚、瘫痪、眩晕、燃烧、腐化、重生、免疫、近战/远程/伤害类型修正等需要统一建模；FAQ 还补充了时间戳、强制行动、目标移动导致攻击/法术取消等边界。

## 技术选型结论

首轮不建议把 Phaser 作为法师战争主实现技术。推荐仍走项目现有自研引擎 + React UI + 自研 FX/Canvas/Shader 的路线。

这里的结论不是“法术没有特效”。相反，法术释放特效应作为法师战争首轮体验的硬需求：玩家施放法术时，画面必须能看出施法来源、目标区域/对象、法术运动或扩散路径，以及命中/结算结果。

理由：

- 法师战争的主要复杂度是规则状态机，而不是实时物理或自由场景渲染：计划法术、隐藏结界、触发时机、攻击八步、状态时间戳、法术绑定和法术书才是实现风险。
- 项目现有架构已经提供 DomainCore、Pipeline、InteractionSystem、ResponseWindowSystem、UndoSystem、ActionLog、SpriteAtlas、FxSystem、Canvas/Shader 动效入口；这些正好覆盖格区桌游和卡牌/状态交互。
- Phaser 会新增一套 Scene 生命周期、输入事件、坐标/缩放、对象销毁与 React 同步桥。对本游戏首轮而言，这会增加状态同步复杂度，但不能降低规则建模复杂度；法术特效可以先由现有 `engine/fx`、Canvas 2D、ShaderCanvas 和 framer-motion 承载。
- 当前主线 `package.json` 没有 Phaser 依赖；已有 `.worktrees/phaser-doudizhu` 是斗地主/特效方向 POC，可作为参考，但不应直接作为法师战争默认架构。
- 项目动画规范要求复杂特效必须评估 Phaser，但该规则的触发点是大量粒子、真实对象运动、镜头震动、连环命中、时间线编排或多目标排序。法师战争首轮必须做法术释放特效，但可以先用现有 FX/Canvas/Shader；若后续做“法术释放电影感”、密集连锁闪电、召唤风暴或多目标连续结算，再单独评估 Phaser 特效层。

## Phaser UI 口径

- Phaser 的主游戏对象渲染走 Canvas/WebGL renderer；这很适合连续动画、粒子、镜头、场景对象和统一输入坐标。
- Phaser 也支持 DOM Element：需要在 game config 中启用 `dom.createContainer`，再用 `this.add.dom(...)` 创建由 Phaser 管理的 HTML 元素。这说明 Phaser 不是“所有 UI 只能画进 canvas”。
- 但 Phaser DOM Element 仍然要跟 Phaser Scene 生命周期、坐标、缩放、销毁和输入系统同步；它不能自然替代本项目已有的 React 组件树、i18n、通用 HUD、InteractionSystem、ResponseWindowSystem 和联机状态展示。
- 所以本轮不选 Phaser，不是因为 React 更适合表达“游戏对象结构”本身；游戏对象结构仍应放在 DomainCore / 数据模型里。真正原因是法师战争的常驻 UI 是大量状态、私密信息、附件、计划区和玩家选择控件，React 更适合表达这些可组合 DOM UI；Phaser 更适合在需要复杂连续特效时作为渲染层候选。

## 法术特效基线

首轮所有可见法术至少需要满足以下表现合同：

- 施法来源：法师、魔宠或再生点必须有清晰的起手反馈，例如发光、抬起、符文圈或能量聚集。
- 目标定位：目标生物、魔物、区域或墙体边界必须被明确点亮，不能只靠日志说明。
- 运动路径：远程攻击、推斥、传送、治疗、召唤、结界展示等要有可见路径或扩散形态。
- 命中结果：伤害、治疗、状态、召唤、装备、结界展示、陷阱触发要在目标上有冲击帧或落地反馈。
- 规则同步：特效必须由规则事件驱动；命令未验证成功前不能先播正式结算特效。

推荐实现分层：

- 轻量 UI 反馈：framer-motion / CSS transition，用于按钮、计划法术、结界翻开、状态标签切换。
- 标准法术反馈：`engine/fx` + Canvas 2D，用于火球、闪电、治疗、召唤光、推斥冲击等。
- 流体/元素大特效：ShaderCanvas，用于旋涡、火焰、能量护盾、传送门。
- Phaser 候选场景：连锁闪电多目标跳转、召唤大量粒子、镜头震动、复杂时间线、多人同屏大量对象特效。

## 推荐实现路线

1. 先建 OpenSpec：`add-mage-wars-foundation`，至少包含本体范围和附加能力矩阵。
2. 先做领域建模文档：术语 -> 事件映射、决策点表、引擎能力缺口表。
3. 当前首轮运行范围已改为标准竞技场两派系流程：2 名玩家、默认兽王 / 女祭司、配置包首批预设法术书、12 格竞技场、基础回合/行动/攻击/守卫/常见状态。
4. 隐藏结界、陷阱、法术绑定、完整法术书构筑、多人局作为明确分层：能进首轮底层模型，但 UI 交付可拆后续。
5. UI 采用 React 固定构图：竞技场格区、法师状态 HUD、法术书 / 已计划法术 / 弃牌堆区、结界 / 装备 / 状态附件层；等待玩家选择全部走 `sys.interaction`，不要在 core 上放 pending UI 状态。
6. 动效首轮必须交付法术释放特效，采用现有 `engine/fx`、Canvas 2D、ShaderCanvas、framer-motion。Phaser 只作为后续“复杂特效层”候选，不作为首轮 Board 主渲染器。
