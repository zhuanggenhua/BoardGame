## 本轮修正裁定

| 用户指出的问题 | 设计裁定 |
| --- | --- |
| 规则里没有“手牌”却把卡牌区画成手牌 | Mage Wars 主牌区必须按规则叫法建模：`法术书 -> 已计划法术（最多 2 张） -> 施放 / 摧毁后弃牌堆；未施放计划法术回到法术书`。UI、artifact class / aria、审计文本和汇报不得再写“手牌”或“对手手牌”。 |
| 法师 / 召唤者对象有自己的卡图 | 法师必须使用 Mage Wars 自己的法师牌素材和法术牌 atlas；禁止借用其它游戏卡图、通用头像、召唤师战争式卡牌家族或文字壳替代。 |
| DiceThrone 骰子贴图用法没看透 | Mage Wars 攻击骰不得只写“参考 DiceThrone”。必须沿用其分层不变量：物理/随机/点击层可以程序化，正式骰面必须来自 `attack-die-texture.png` 或由它派生的骰面 canvas / sprite；效果骰是来源锁定的蓝色 12 面程序化骰。 |
| UI 风格没有从 Mage Wars 核心素材重新设计 | 视觉语法从竞技场石面、卡牌金属/羊皮纸边、红蓝行动标记、黑色快速施法标记、法术卡背和状态 token 推导；不继承 DiceThrone 皮肤，也不套通用暗色玻璃 dashboard。 |
| 玩家血量/蓝量不该继续贴状态板素材 | 法师状态板降为 `reference-only`：只用于规则/setup、轨道坐标来源和详情检视。Step 1 运行时主界面不得出现整张状态板或状态板裁切作为玩家面板；常驻生命、伤害、法力、聚魔全部用自制运行态 UI。 |
| 饱和不是乱炖 | 饱和必须表现完整游戏界面压力态：多对象、多附件、多状态、隐藏信息、费用预扣、目标选择和反制等待都有组织；不允许把素材堆成样本墙、联系表或无主次拼贴。 |
| v37 仍不能证明玩家友好 | v37 只能证明没有手牌词、没有复写卡面字段、没有几何重叠；它没有证明法术书 / 已计划法术 / 弃牌堆按当前阶段给足容量，也没有证明来源卡、目标和执行反馈形成玩家一眼可执行的单一动作链。v37 降级为 `REVISE / player-workflow-insufficient`，不得送人工验收。 |
| 攻击 / 施法必须同构 | Mage Wars 的攻击、施法、使用装备攻击条或当前行动对象，统一按 `选中来源对象 -> 选择合法目标 -> 目标点击即提交 -> 反制 / 结算浮层` 设计。来源可以是已计划法术卡、生物攻击条、法师装备攻击或特殊行动；目标未提交前允许撤选 / 更换来源，但主桌面不得常驻确认 / 执行 / 取消按钮。 |
| 卡面字段不需要 UI 代抄 | 91 张学徒卡字段合同只是运行时规则与核对真相源；设计稿里的可读卡面已经承担费用、射程、目标、骰数、类型和效果正文。UI 只补当前运行态：来源已选、合法目标、资源是否足够、直接执行反馈、等待响应和结算反馈。 |
| “容量友好”必须按规则阶段判断 | 计划阶段需要给法术书分类、分页、候选和焦点卡足够空间；攻击 / 施法执行阶段不需要把法术书、已计划法术和弃牌堆压成一排小牌。完整法术书此时只能是边缘检视入口；弃牌堆是公开归档入口，默认用紧凑顶牌正面 / 半露正面 + 数量表达可检视内容，但不能抢当前来源、目标、执行链。 |
| 对手计划必须按席位镜像 | 对手已计划法术是规则对象，但只允许显示卡背 / 数量 / 控制归属。PC 对局稿中对手计划默认放左上，和己方底部 / 右下的计划槽形成桌面镜像；不得挂在对方法师状态 HUD 右侧，也不得放进右下己方计划 / 行动区。 |
| 问号区只保留规则职责 | 用户标问号的区域必须先裁定规则身份。左下独立“玩家区”、底部重复“当前来源”大卡、右下大计划框、常驻关系箭头都不是独立规则区域；只有其中承载的法师状态、行动 / 快速施法 token、当前来源对象、已计划法术、目标摘要和普通命令可能必要。没有规则身份的外框、空白和常驻箭头必须收缩、合并或退为阶段性提示。 |
| 分页样式继承用户标注 | 法术书分页是必要入口，但分页控件必须贴在法术书浏览 / 书页边缘，使用用户标注的紧凑翻页 / 页角语法；不得再做成漂在底部或离开法术书主体的圆形小按钮。 |

## 阶段容量裁定

| 阶段 | 玩家问题 | 必须展开 | 必须收起 / 降权 |
| --- | --- | --- | --- |
| 计划 / 浏览态 | 我要从法术书准备哪两张？ | 法术书分类、分页、候选卡、焦点预览、两个已计划槽 | 棋盘结算骰、伤害结果、弃牌堆详情 |
| 目标选择 / 执行态 | 我现在用哪张已计划法术 / 行动对象，可以点谁，点下去会不会付得起？ | 当前来源大卡或当前行动对象、棋盘合法目标高亮、法力预扣 / 不足短反馈、撤选入口 | 完整法术书候选、弃牌堆详情、结算骰和伤害结果、常驻确认 / 执行 / 取消按钮 |
| 结算态 | 这次攻击 / 法术对谁造成什么结果？ | 骰子 / 效果骰、伤害 / 治疗 / 状态 token、目标本体反馈 | 常驻确认 / 执行 / 取消按钮、法术书浏览、无关候选和长说明 |

v38 之后默认拆成两个独立稿：`计划 / 浏览态` 与 `目标选择 / 执行态`。目标选择 / 执行态中法术书只允许作为明确入口，不能把 30+ 张法术书浏览能力塞成小牌墙；当前来源必须是可读对象，不能缩成底部候选后靠旁边文字解释。攻击态、施法态和装备攻击态复用同一动作结构，只更换来源对象、合法目标反馈和结算表现。

## 统一动作工作台硬规则

| 项 | 硬规则 |
| --- | --- |
| 来源 | 来源可以是场上生物、已计划法术、法师装备或特殊行动，但必须有一张可读来源卡 / 来源对象；不能只在棋盘高亮后让玩家不知道当前动作从哪里来。 |
| 目标 | 目标选择必须发生在竞技场对象本体或区域本体上；已选目标摘要只写对象名和区域，不复写卡面字段。 |
| 直接执行 / 撤选 | 目标未提交前允许撤选、更换来源或返回法术书；目标本体点击即提交并进入反制 / 骰子 / 伤害结算层。主界面不得常驻确认 / 执行 / 取消按钮来重复占空间。 |
| 法术书 / 弃牌堆 | 在执行态只做边缘检视入口；不得和当前来源卡并列成小牌墙，也不得让玩家误读为当前主候选。弃牌堆不是隐藏信息，默认可显示顶牌正面 / 半露正面和数量；卡背只用于对手已计划、未公开法术书、隐性结界等隐藏信息。 |
| 卡面字段 | 当前来源卡足够大时，费用、射程、目标、骰数、效果正文由卡面承担；若看不清，修放大 / hover / focus，不在 UI 旁边另写一套字段。 |
| 空间预算 | 工作台不得遮挡任何场上卡牌；场上卡必须保留唯一 `zoneId` 和可见区域归属。右下 / 底部空白如果出现，必须承担来源卡、目标摘要、撤选 / 返回或临时结算层，不得只是装饰留白。 |

## 规则到界面结论

| 规则结论 | 画面主体 | UI 决策 / 禁止项 |
| --- | --- | --- |
| 学徒模式只使用标准竞技场一半 | 中央竞技场 | 使用正式 `standard-arena.jpg`，在其上表达 `2x3` 可用半场候选；禁止单独画六格抽象棋盘 |
| 距离只算水平 / 垂直 | 区域高亮 | 合法目标高亮必须按区域邻接计算；非法斜向目标必须可见但禁用，不能消失 |
| 每回合从法术书准备最多 2 个计划法术且对手保密 | 法术书 / 已计划法术区 | 本人从法术书选择并看到正面计划卡；对手只看到卡背 / 数量 / 控制归属。己方计划槽跟随己方工作台；对手计划槽放左上，和己方计划槽形成镜像，不并入对方法师状态 HUD 或右侧 rail。未施放计划法术回到法术书，施放或摧毁后进入公开弃牌堆 |
| 快速施法可在三个时机插入 | 当前行动槽 + 快速施法标记 | 主动作区必须能表达“现在可快速施法 / 可跳过 / 已用”；不能把快速施法做成普通结束回合按钮 |
| 生物行动是移动 + 快速行动或停留 + 标准行动 | 棋盘对象和行动 dock | 当前生物本体是第一点击对象；行动列表只服务当前生物，不列全局动作墙 |
| 施法有宣告、反制、结算三步 | 统一动作结构 | 支付前只表达已选来源卡、合法目标和法力条预扣；费用、射程、目标栏等卡面字段由可读卡面承担。目标点击即提交，进入反制 / 等待态；成功后才播命中 FX |
| 攻击 / 治疗需要骰子结算 | 骰盘 + 目标对象 | 攻击骰必须按 DiceThrone 的成熟分层方式处理：物理 / 交互可以程序化，正式视觉必须用 Mage Wars 攻击骰贴图或等价皮肤；蓝色 12 面效果骰按来源锁定程序化对象渲染；禁止用纯数字公式、默认 D6、黑色方块或封闭骰盒替代骰面 |
| 结界隐藏且附着在对象或区域 | 附件堆叠 | 隐性结界用卡背贴在宿主附近；本人可检视，对手只看卡背和控制归属 |
| 强制结界满足条件必须展示 | 响应窗口 | 触发时 UI 必须给拥有者强制展示动作和费用反馈；不能让玩家继续隐藏 |
| 状态板用方块记录聚魔、法力池、生命和伤害 | 玩家状态读数 | 主界面不展示整张状态板或状态板裁切。状态板只作为 `reference-only` 规则来源；常驻生命、伤害、法力、聚魔用贴近法师牌的自制血条 / 蓝条 / 短读数表达，并可在帮助/设置/详情层回看状态板来源 |
| 行动标记、快速施法标记有正反面 | 法师 / 生物 token | 用正式 token 或来源锁定语义表达已用 / 可用；禁止普通灰色 chip 顶替 |
| 状态如守卫、燃烧、腐化、眩晕、昏迷、沉睡影响行动 | 对象本体 token | token 必须贴近对象，层数/短 tooltip 可程序化；禁止只在日志里写状态 |
| 法术牌文字优先于标准规则 | 卡牌详情层 | 主界面不常驻长规则正文；详情层可放大正式卡牌，必要时提供结构化字段 |

| 对方法师状态 HUD | 顶部靠对方起始角，贴近法师牌 | 公开生命条 / 伤害读数、公开装备/显性结界、对方行动/快速施法状态 | 攻击 / 施法目标、公开信息读取；不得出现整张状态板或状态板裁切 |
| 对手已计划法术区 | 左上，贴近对手侧但不塞入对方法师 HUD | 最多 2 张卡背、数量和控制归属 | 只表达对手已计划的隐藏信息边界，与己方计划槽形成桌面镜像；不得公开牌名、不得与己方行动区混组 |
| 法术书 / 已计划法术 / 弃牌堆区 | 底部横向槽 | 本人最多两张已计划法术、法术书入口、公开弃牌堆入口、当前计划详情 | 从法术书计划法术、放大卡牌、选择施法来源；禁止出现手牌区 |
| 当前行动槽 | 右侧中下 | 当前阶段、当前可操作对象、主动作按钮、跳过 / 撤选、费用预览 | 单一主焦点；不承载常驻确认 / 执行 / 取消按钮 |
| 响应 / 等待层 | 棋盘上方轻 overlay | 等待对手计划、等待反制、结界展示窗口、非法操作短错误 | 不占正常布局，不遮挡目标本体 |
| 骰盘 / 结算层 | 棋盘下方或目标附近 overlay | 攻击骰、效果骰、伤害 / 治疗 / 状态结果、受击飘字 | 结算可读，完成后退场，不抢长期槽位 |

### 移动 / 平板

- 桌面构图是权威基线；移动端后续按 `landscape-adapted + board-shell` 同构缩放。
- 不能为了手机端把桌面棋盘压成面板网格。
- 竖屏或错向只给非阻断提示；主界面仍可滚动/缩放访问。

## 必须交互元素

| 元素 | 设计要求 |
| --- | --- |
| 主动作入口 | 只显示当前玩家当前阶段可做的 1 组主动作：计划法术、使用快速施法、激活生物、移动、快速攻击、快速法术、守卫、标准攻击、标准法术、特殊行动、跳过或结束当前行动。 |
| 对象选择态 | 可选择对象必须在真实对象本体上高亮：区域、法师、生物、魔物、装备、显性结界、隐性结界卡背。列表只能辅助检索，不能替代对象本体点击。 |
| 合法 / 非法目标 | 合法目标用稳定高亮和可点光标；非法目标保留可见但降噪，并在 hover / tap 后给短原因，例如“范围外”“目标类型不符”“快速施法已用”。 |
| 直接执行 / 撤选 | 支付前必须能撤选或更换来源；支付后撤选入口退场，进入反制或结算。目标本体点击即提交，主界面不常驻确认 / 执行 / 取消按钮。 |
| 资源 / 代价反馈 | 卡面已写费用、行动图标、射程、目标和骰数时，主 UI 不复写这些卡面字段。提交前只在法力条 / 行动标记上给轻量预扣或不足反馈；提交后自制状态读数和 token 立即给出事件驱动反馈，状态板只作为非主屏规则来源。 |
| 结果反馈 | 成功法术必须有来源、目标、路径 / 扩散、命中或治疗结果；攻击必须显示骰子和受影响对象；失败只播撤选 / 反制，不播成功 FX。 |
| 隐藏信息边界 | 本人计划法术和隐性结界可正面检视；对手只见卡背、位置、数量和控制归属；旁观者默认不越权。 |
| 响应 / 等待态 | 对手反制、结界展示、双方同时计划、非当前玩家等待必须有明确短状态；非 owner 不显示可操作壳层。 |
| 溢出 / 展开 | 多结界、多装备、多状态、多生物同区时，主桌面只给堆叠摘要，点击展开详情抽屉；详情不能挡住当前目标选择态。 |

## 饱和交互状态模拟

| 项目 | 饱和状态 |
| --- | --- |
| 当前阶段 | 行动环节 / 生物行动阶段；邪术师可在激活火烙魔婴前插入快速施法窗口 |
| 当前玩家 | 邪术师对女祭司；邪术师快速施法标记仍为活动面，法师行动标记仍活动 |
| 棋盘对象 | 邪术师、女祭司、火烙魔婴、烈焰狱鬼、灰衣天使、西锁骑士、皇家箭手、缠绕藤蔓至少 8 个对象分布在 `2x3` 半场 |
| 附件 / 状态 | 邪术师有狱火长鞭和隐性结界；女祭司有风龙皮甲、偏移护腕和 2 张隐性结界；灰衣天使带守卫，火烙魔婴带燃烧，西锁骑士带伤害 token |
| 法术书 / 计划 / 弃牌堆 | 邪术师本人从法术书准备 `火球术` 与 `法师祸咒` 两张正面计划卡；女祭司计划区在左上只显示 2 张卡背 / 数量 / 控制归属，和己方计划槽形成镜像；双方弃牌堆可检视公开内容，因此紧凑入口显示顶牌正面 / 半露正面 + 数量；未施放计划法术回到法术书 |
| 当前操作 | 邪术师已选中 `火球术`；B2 的西锁骑士作为合法目标高亮，点击目标即提交施法。卡面自己承担费用、射程、目标栏和骰数读取；主界面不显示常驻确认 / 执行 / 取消按钮 |

| 非法目标 | 己方火烙魔婴、范围外对象、目标类型不符对象、被墙体阻断候选降噪并给短原因 |

| 资源读数 | 邪术师常驻自制生命条、法力蓝条、聚魔短读数和当前伤害；提交前只在法力条或目标可点状态上给预扣反馈，不另写卡面费用字段。状态板不进入 Step 1 主界面，只保留为 setup / 规则参考 |

| 溢出策略 | 同区多生物用扇形 / 小堆叠保留卡牌主体；多附件按宿主方向叠卡背，点击展开；状态 token 超过 3 个时压成 token 串 + 数量 |

## 视觉稿继承约束

- 后续 Open Design v38 及以后必须继承本文件重构后的对象、交互、隐藏信息、阶段容量和饱和状态，不得重新发明主交互。
- 后续 Open Design artifact、导出 PNG 和 AI 图面核验必须先逐项消费 `user-correction-traceability-ledger.md`。该账本只作纠正覆盖 / drift-check；若发现新规则缺口，先回本文件、`.spec/skills/mage-wars-ui-design-memory/SKILL.md` 或 `.spec/skills/ui-design-pipeline/SKILL.md` 补 canonical-source，再重新审图。
- 后续 Open Design v38 及以后必须做字符串审查：可见文案、aria、class、审计文本中不得出现 `手牌`、`hand`、`opponent-hand`；只允许法术书、已计划法术、弃牌堆、隐性结界等规则真实名称。
- 设计稿必须用正式素材或来源锁定程序化对象作为主体；边框、玻璃面板、文字壳只能做轻量组织，不得抢走棋盘 / 卡牌 / token 主语。
- 玩家生命、伤害、法力、聚魔的常驻读数必须使用自制运行态 UI；不得把整张法师状态板素材、状态板裁切或状态板轨道当血量 / 蓝量面板铺在主界面。
- 骰盘必须按 DiceThrone 的分层不变量处理：物理 / 随机 / 点击层可以程序化，正式骰面贴图层必须来自 Mage Wars 自己的攻击骰贴图或来源锁定的蓝色 12 面效果骰视觉；不得交付默认数字骰、普通 D6、黑色方块、封闭黑盒骰盘或纯文本公式。
- 设计稿必须模拟上述饱和状态；如果图面只展示空竞技场、少量对象或单张卡牌，不能进入 AI 图面 `PASS`。
- 对手计划法术必须按本文件的左上镜像槽位出现；若被放到对方法师侧栏、右下己方计划区、日志区或无关空白区，即使卡背数量正确也直接判 `REVISE / opponent-plan-symmetry-failed`。
- 用户标注的问号区域必须按“规则职责 / UI 辅助 / 可删装饰”裁定后再画；若验收文档需要写下一版要求，必须回到本文件补设计规范，审计只引用本文件，不得另写规则。
- 法术书分页必须按本文件的用户标注页角 / 贴边样式出现；若继续使用孤立圆形按钮或漂浮控件，直接判 `REVISE / pagination-style-mismatch`。
- AI 验收只能采用“本文件条款 / 设计合同条款 -> 图面证据 -> 结论”的引用矩阵；不得在审计、截图说明或失败报告里新增独立 PASS/FAIL 规则。若发现新要求，先补回本文件或对应设计合同，再重新验收。
- 视觉候选必须先由 AI 按本文件和 `board-ui-preflight-matrix.md` 自检；AI 自检不通过时不得打开给用户人工验收。
