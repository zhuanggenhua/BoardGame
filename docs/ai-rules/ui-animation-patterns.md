# UI 动画设计规范

> 来源：从 `docs/ai-rules/ui-ux.md` 无损拆出。本文档承载 UI 动画触发、结果揭示和表现层事件身份规则；`ui-ux.md` 只保留入口摘要。

## UI 动画设计原则（强制）

> **核心原则：动画应由数据/状态变化驱动，而非由 UI 事件直接触发**。尤其是涉及命令验证的操作，必须等待验证成功后再启动动画。

### 玩法因果动效必须由画面本身表达（强制）

当动画用于表达技能触发、攻击命中、卡牌效果、结算奖励、对象移动、对象离场或状态变化时，动效本体必须回答三件事：**谁是来源、影响打到哪里、目标发生了什么变化**。

- **对象优先**：来源卡牌、目标卡牌、棋子、骰子、token、基地或区域必须是第一视觉主体；禁止用一段说明文字、结果面板、toast、徽章或日志替代真实对象动效。
- **动作优先**：玩家不读文字也应能看出因果链，例如来源对象抬起/蓄力 → 能量/牌/刀光/粒子到达目标 → 目标震动、碎裂、离场、增益、得分或改变状态。
- **文字只做辅助**：允许保留对象名、数字（如 `+1`、`VP`）和极短状态标签；禁止把规则解释、效果句、验收说明、结果描述常驻在动效层里当主要信息。
- **预览页同样按实战验收**：特效预览不能只证明“有一个说明 UI 出现”；必须用 start / impact / end 关键帧或录屏证明运动路径、冲击帧和目标结果都可见。
- **预览按钮不等于动效表达**：预览页上的按钮、标题、场景名只负责选择案例，不得承担“谁触发、触发了什么、触发到哪里”的主要说明职责；进入预览画面后，来源对象发光/抬起、飞行轨迹、目标冲击和最终状态必须自己讲清楚这条因果链。
- **禁止说明面板顶替 SNAP 式触发反馈**：类似卡牌触发、被动触发、反应触发这类需求，默认验收对象是镜头节奏、对象高亮、轨迹、打击帧和目标变化；不得把一块“触发效果 → 结果”的文字面板、toast、日志或大段说明当成动效优化成果。
- **失败判定**：如果截图里主要信息来自“触发效果：X → 结果：Y”这类文字，而对象运动或目标变化看不出 X/Y，则该动效失败，必须重做表现层。
- **真实对象承载门槛**：Snap 式卡牌 / 能力触发预览必须让真实来源对象和真实目标对象参与动画；禁止额外渲染一张空白卡壳、灰色替身、结果说明卡、日志条或 toast 来替代源卡发光、飞行路径和目标受击 / 增益 / 离场变化。若来源卡本体仍静止、目标本体无反应，只是旁边出现了说明或替身动效，直接判失败。
- **用户看不懂触发链时先改动效本体**：当反馈是“看不出谁触发、触发了什么、触发到哪里”时，禁止先补大段说明、图例、日志、toast、结果面板或文字步骤来解释。必须先增强来源对象启动、路径方向、命中帧和目标状态变化；文字隐藏后仍看不懂，就判为未完成。
- **边框不是动效主体**：来源、目标、选中态、命中态不能同时叠多层亮边、ring、outline、发光框和装饰框。截图第一眼若看到的是边框系统而不是卡牌/随从本体，判 `REVISE`；优先用抬起、缩放、受击形变、材质变暗、碎裂、粒子或离场动作表达。
- **结果符号不能承担飞行路径**：叉号、骷髅、对勾、加减号、伤害章这类符号只属于命中帧或最终状态，不能在命中前沿路径飞过去。飞行段必须使用刀光、能量束、粒子、卡牌残影、投射物或对象移动；结果符号只能锚在目标上，并且不得遮住目标本体。
- **选择线只能表达目标选择，不表达死亡**：当需求收敛为“卡牌缩放代表生效、连线代表选择目标、分裂代表销毁”时，连线只承担来源到目标的选择关系；销毁结果必须由目标卡牌分裂/离场表达。禁止把线条本身、飞行叉号或飞行骷髅当成死亡结果。
- **两块裂开不能退化成裂缝线**：当死亡效果选择“卡牌分成两块”时，验收主体必须是两块真实卡面的大块位移、旋转、离场和断面烧蚀；裂缝高光只能是附属断面细节，不能作为唯一或最醒目的结果。若截图第一眼只看到一根切线、斜线或亮缝，而看不出两块卡面分离，直接判 `REVISE`。
- **分裂不能保留完整原图**：当销毁用“两块真实卡面分裂”表达时，分裂层必须接管原目标卡牌：先用同一张卡面快照画出两块可拼回完整卡但已出现可见裂开间距的起始帧，然后同帧隐藏真实原卡，后续画面只能看见两块卡面分离。禁止完整原卡继续作为底图留在两块碎片后面；若截图看起来像“完整卡还在，前面叠了两块碎片”，或起始帧第一眼仍像一张完整卡，判 `REVISE`。
- **动效颜色必须有语义来源**：能力触发、选择线、命中帧和销毁效果的颜色不得凭空选用。颜色必须来自动态参考里能说明的动作语法，或来自项目既有语义色（例如选中/行动/危险/增益）。若参考搜索只拿到静态图或失败，必须明说“没有拿到动态颜色依据”，并改用项目语义色，不得用青色、紫色等随机科技感色替代。
- **禁止简单 DOM 几何冒充主特效**：能力触发、攻击、消灭、增益、离场这类主特效不得主要由 `div` 矩形、圆角框、CSS 线条、border/ring、box-shadow 光条、伪元素叉号或多个绝对定位块拼出来。DOM 可以保留真实卡牌/随从本体、按钮和轻量状态；主运动、路径、冲击和粒子应优先使用 canvas/WebGL、sprite、遮罩、粒子系统或 Phaser 这类游戏特效层。
- **Phaser 方案必须纳入复杂特效评估**：如果能力触发需要大量粒子、卡牌/随从真实运动、镜头震动、连环命中、时间线编排或多目标排序，不得默认继续堆 React DOM/CSS。应明确评估 Phaser canvas 特效层：React 负责预览工具、按钮、游戏状态和事件输入；Phaser 负责特效对象、tween、粒子、镜头和渲染顺序。只有在效果很轻、对象少、无连环时间线时，才优先保留纯 React/CSS 实现。
- **语义 stage 只做性能门控，不等同于 Phaser**：若继续使用 React/CSS，推荐把能力触发生命周期拆成 `source-wake / travel / impact / resolve / settle` 等 animation stage，但 React 状态只在阶段边界变化，不能逐帧 setState。stage 的性能收益来自“只挂载当前阶段必要图层”：飞行阶段不常驻大结果符号，命中后卸载路径层，收尾阶段卸载高成本 blur / filter / 多层 shadow。
- **连环效果必须走队列或时间线**：大杀四方存在触发链、反应、消灭后再触发等连环效果；表现层不得用一个全局 `activeKey`、单个 timer 或单个 source/target 覆盖全部。每个可见效果实例至少要有 `effectId`、来源快照、目标快照、animation stage、开始时间和完成回调；后续效果可以排队、短重叠或被合并，但必须是显式策略，不能互相抢占或把前一个目标状态抹掉。
- **连环效果验收要看顺序关系**：验证时不能只抓单个命中帧。至少检查第一段触发的 settle 与第二段触发的 source-wake/travel 是否衔接清楚；若多个目标连续受击，玩家必须看得出 A 触发后导致 B，再由 B 导致 C，而不是一堆光效同时爆开。
- **关键帧验收口径**：至少检查 start / travel / impact / end 四段：start 看得出哪张卡触发；travel 看得出从来源打向目标；impact 看得出命中帧；end 看得出目标状态变化。四段缺任一段，不得用按钮名、标题、效果文案或口头解释补足。

### 页面翻转与转场的真实过程门禁（强制）

- **动画必须由可观察的运行时过程构成**：翻页、翻卡、折叠、展开和其它需要表达“从 A 到 B”的转场，必须在真实页面中保留来源态、过渡态和目标态，并由 CSS 动画、Web Animations API、Canvas/WebGL 时间线或等价的逐帧运行时机制驱动。点击后直接替换内容，再用延迟、透明度、位移或一张预先制作的中间图营造“正在翻页”，一律视为伪动画。
- **过渡帧必须有真实几何变化**：翻页类动画至少应有可复查的旋转、折叠、裁切、透视或等价几何进度；不能只有两张静态图交替显示。过渡期间来源页和目标页的内容身份必须可追溯，不能用空白页、占位壳或与真实内容无关的截图替代。
- **截图不得反向制造动画**：为了通过截图或视觉验收，禁止在测试脚本、截图后处理、联系图脚本或演示壳层里手工拼接、合成、绘制中间帧，也禁止只截“点击前”和“点击后”两张图后声称存在翻页过程。中间帧必须来自真实运行时动画正在执行的那一刻。
- **自动化验收必须覆盖三态**：E2E 至少断言触发前的来源页、动画中的可见过渡层（含实现身份或运行时进度）和动画结束后的目标页；目标页最终内容必须与真实下一页一致。只断言点击后文本换了、按钮可再次点击或动画 class 出现，不足以证明真实翻页。
- **动画状态不可抢先于业务结果**：涉及命令验证或状态同步的转场，必须在对应状态/事件确认后启动；验证失败、回滚或阶段切换时要清理过渡层，不能出现画面已经翻到下一页而业务仍停在原页的视觉欺骗。

### 直接操控动效生命周期（强制）

拖拽、长按、滑动、投放、飞行转移、筹码/卡牌/棋子移动这类直接操控动效，不只要“动起来”，还要证明整段生命周期不断流。

- **生命周期 owner 先行**：实现前必须写清开始、持续移动、命中高亮、取消、松手和退场分别由谁接管。源对象可能会隐藏、重渲染、移出命中区域或被占位替换时，后续移动与结束事件必须交给稳定控制器、全局指针生命周期或等价输入 owner。
- **源对象隐藏不能切断输入**：源卡、源筹码或源棋子隐藏占位后，只能停止承担视觉本体职责，不能继续作为后续 `pointermove` / 松手链路的唯一事件来源。
- **ghost 与源对象职责互斥**：直接操控中源对象负责占位和归属，ghost 负责当前运动；禁止源对象和 ghost 双显，也禁止为了避免双显而把源对象移除到导致事件断流。
- **持续态验收是必需项**：验收必须覆盖第一次启动、中途持续按住后继续移动、指针离开源对象后仍跟手、取消/松手清理和最终结果。不能只用“刚拖起时 ghost 可见”或“松手后结果正确”替代。
- **并发动效互不抢占**：多人或多对象同时动效时，每个实例必须有独立身份；一个实例完成/取消只能清理自己，不能清掉其它仍在运动的实例。

### 两种动画触发模式

**数据驱动动画（Data-Driven Animation）**：
- **定义**：通过 `useEffect` 监听状态字段变化，状态变化时启动动画
- **适用场景**：所有需要命令验证的操作（投掷骰子、打出卡牌、激活技能等）
- **优势**：动画只在操作真正成功后播放，验证失败时不会出现"动画已播放但操作未生效"的不一致

**事件驱动动画（Event-Driven Animation）**：
- **定义**：在 `onClick` 等事件处理器中直接设置动画状态
- **适用场景**：纯 UI 交互，不涉及命令验证（如展开/折叠面板、切换标签页、hover 效果）
- **风险**：若用于需要验证的操作，验证失败时动画已播放，造成视觉欺骗

### 正确模式（数据驱动）

```typescript
// ✅ 正确：监听 rollCount 变化启动动画
const [isRolling, setIsRolling] = React.useState(false);
const prevRollCountRef = React.useRef(rollCount);

React.useEffect(() => {
    if (rollCount !== prevRollCountRef.current) {
        const prevCount = prevRollCountRef.current;
        prevRollCountRef.current = rollCount;
        
        // rollCount 增加 → 投掷成功，开始动画
        if (rollCount > prevCount) {
            setIsRolling(true);
            // 安全超时：防止服务器长时间无响应
            const timer = setTimeout(() => setIsRolling(false), 5000);
            return () => clearTimeout(timer);
        }
    }
}, [rollCount, isRolling]);

const handleRollClick = () => {
    if (!canInteract) return;
    // 不在这里设置 isRolling，而是在 rollCount 变化时设置
    // 这样可以避免命令验证失败时动画已经开始播放
    dispatch(COMMANDS.ROLL_DICE, {});
};
```

### 反模式（事件驱动）

```typescript
// ❌ 错误：onClick 中直接设置动画状态
const handleRollClick = () => {
    if (!canInteract) return;
    setIsRolling(true);  // ← 动画立即开始
    dispatch(COMMANDS.ROLL_DICE, {});  // ← 命令可能验证失败
    // 问题：验证失败时动画已播放，但骰子值未变化
};
```

### 与乐观更新引擎的关系

项目使用乐观更新引擎（`OptimisticEngine`），客户端会立即预测状态变化。但预测可能失败（如命令验证失败、随机数不一致），此时会回滚到服务端确认的状态。

- **乐观更新成功**：`rollCount` 立即增加 → `useEffect` 检测到变化 → 启动动画
- **乐观更新失败**：`rollCount` 不变或回滚 → `useEffect` 不触发动画 → 视觉与状态一致
- **关键**：动画依赖最终状态（`rollCount`），而非用户操作（`onClick`），确保动画只在操作真正生效时播放

### 阶段转换清理（强制）

当游戏阶段转换时（如从进攻阶段进入防御阶段），必须立即清理上一阶段的动画状态，防止动画残留。

```typescript
// ✅ 正确：阶段转换时清理动画状态
React.useEffect(() => {
    if (currentPhase === 'defensiveRoll' || currentPhase === 'offensiveRoll') {
        // 进入新阶段时立即清除投掷动画状态
        if (isRolling) {
            setIsRolling(false);
        }
    }
}, [currentPhase, isRolling, setIsRolling]);
```

### 最短播放时间保护（可选）

乐观更新会瞬间产生新状态，但动画需要一定时间才能完整播放。可以记录动画开始时刻，在状态变化时检查是否已过最短时间，未过则延迟停止。

```typescript
const MIN_ROLL_ANIMATION_MS = 800;
const rollStartTimeRef = React.useRef<number>(0);

React.useEffect(() => {
    if (rollCount > prevCount) {
        setIsRolling(true);
        rollStartTimeRef.current = Date.now();
    } else if (isRolling) {
        const elapsed = Date.now() - rollStartTimeRef.current;
        const remaining = MIN_ROLL_ANIMATION_MS - elapsed;
        if (remaining <= 0) {
            setIsRolling(false);
        } else {
            const timer = setTimeout(() => setIsRolling(false), remaining);
            return () => clearTimeout(timer);
        }
    }
}, [rollCount, isRolling]);
```

### 新增 UI 交互检查清单

开发新的 UI 交互时，必须回答以下问题：

1. **这个操作需要命令验证吗？**
   - 是 → 使用数据驱动动画（监听状态变化）
   - 否 → 可以使用事件驱动动画（onClick 直接设置）

2. **动画状态的唯一真实来源是什么？**
   - 必须是引擎层状态字段（如 `rollCount`、`G.core.xxx`）
   - 禁止依赖 UI 层临时状态（如 `isButtonClicked`）

3. **阶段转换时需要清理动画状态吗？**
   - 是 → 在 `useEffect` 中监听 `currentPhase` 并清理
   - 否 → 确认动画不会跨阶段残留

4. **动画是否需要最短播放时间保护？**
   - 是 → 记录开始时刻，延迟停止
   - 否 → 状态变化时立即停止

5. **这个动效是否会让源对象隐藏、重渲染或离开命中区域？**
   - 是 → 后续移动和结束必须由稳定生命周期 owner 接管，不能依赖源元素继续派发事件
   - 否 → 仍需证明持续态、取消和清理链路正常

6. **验收是否覆盖了中途持续态？**
   - 是 → 至少验证启动、中途按住后继续移动、离开源对象后仍响应、松手/取消清理
   - 否 → 不得判定拖拽、长按、滑动、投放或转移动效完成

### 可重播结果动画的事件身份规则（强制）

> 适用于“同一个结果值也可能需要再次播放完整动画”的场景，如掷骰特写、翻牌揭示、抽牌亮相、结算浮层中的单次结果展示。

- **随机结果揭示交互不得静默跳过（强制）**：凡是规则层刚刚产生了一次需要玩家感知的随机结果，例如额外投骰、重掷结果、翻牌揭示、抽牌亮相、结算型 reveal，这类都属于**结果揭示交互**，不是普通背景状态刷新。只要结果已经发生，UI 就必须给出可感知的特写/揭示承载；禁止因为同批次又弹了 choice、prompt、response-window、after-event follow-up 或其它 overlay，就把这次结果直接静默结算掉。唯一允许压住前台特写的情况，是该结果已经被另一条更高优先级、同语义的专用承载完整接管，例如阻塞式奖励骰重掷 modal 已经展示了同一批骰子。
- **不要用结果值本身推断“是否发生了新事件”**：如果动画的语义是“系统刚刚产生了一次新结果”，则 `value` / `face` / `amount` 只代表**最终停留结果**，不能作为“要不要重播动画”的唯一依据。
- **必须区分两类信号**：
  - **结果状态**：最后展示什么，例如骰子最后停在 `4`。
  - **事件身份**：这是第几次展示/第几次重掷/哪一次结算，例如 `settlementId + rerollCount`、`eventStream entry id`、`timestamp`、`nonce`。
- **判定标准（强制）**：若以下任一条件成立，组件必须消费独立的事件身份信号，而不能只监听结果值变化：
  - 组件可能在父层复用，不会因新事件自动卸载重挂载；
  - 新事件的结果可能与上一次完全相同；
  - 用户看到的是“一次性结果揭示过程”，而不是稳定状态持续展示。
- **优先级顺序（强制）**：
  1. 优先复用领域层或 EventStream 已有的稳定事件 ID；
  2. 其次使用结算对象自带的序号/重掷 key；
  3. 最后才允许在展示聚合层生成局部 `presentationKey` / `nonce`。
- **禁止反模式**：
  - 仅凭 `value !== prevValue` 决定是否重播掷骰/翻牌/揭示动画；
  - 依赖 React “通常会重挂载”这种偶然行为；
  - 在多个父组件里各自手搓一套“如果没动就不播/强制 setTimeout 重播”的分叉逻辑。
- **推荐模式**：
  - 组件 API 显式区分 `value` 与 `presentationKey`（或等价命名）；
  - `value` 决定落点，`presentationKey` 决定是否开始一轮新的表现生命周期；
  - 若动画只允许针对局部目标重播（如多骰中只重掷一颗），则用“目标索引 + 事件身份”组合成局部 key，而不是重播全部对象。

### 结果动画的架构落点（强制）

- **这是表现层模式，不是业务补丁**：`presentationKey` 的职责是表达“新的可见事件已经发生”，不应被视为临时兜底字段；业务状态里不得为了 UI 动画额外保存 `animationKey` 这类纯表现字段。
- **统一 seam**：React 结果揭示动画优先复用 `src/hooks/ui/useResultRevealAnimation.ts`，不要在组件里重复维护 `previousValueRef + setTimeout + isRolling` 组合。
- **长期方向**：同一类结果展示组件应收敛到统一触发契约。对于跨游戏可复用的“结果揭示型”组件，优先定义通用 props 语义，而不是每个游戏自行发明一套布尔开关或局部 timer。
- **审查门禁**：当用户反馈“只有结果没有过程”“同样结果第二次不动了”“重掷后直接跳最终值”时，必须先检查该组件是否缺少事件身份信号，再决定是否改动画样式或时长。
