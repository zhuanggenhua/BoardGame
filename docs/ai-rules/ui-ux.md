# UI/UX 完整规范

> 本文档是 `AGENTS.md` 的补充，包含 UI/UX 设计范式、布局策略、游戏 UI 特化规范。
> **触发条件**：开发/修改 UI 组件、布局、样式、游戏界面时阅读。

## 0. UI 改动门禁入口（强制）

> 详细门禁已拆到 `docs/ai-rules/ui-change-gates.md`。凡是修改 UI、样式、布局、交互壳层、截图验收、回归恢复或主交互槽位，先读该文档；本文从 §1 起只保留审美准则、组件单一来源和游戏 UI 特化范式。

最小执行口径：
- 样式修复不得擅自升级为布局、交互或功能表面改动。
- UI 改动必须先锁真实入口、真实运行实例、截图证据和视觉判定口径。
- 用户要求 UI 审计、玩家视角或“没过继续改”时，必须执行 `ui-change-gates.md` 的 `UI 审计闭环`；任一审计项失败就保持 `in_progress` 并继续重构同一真实入口。
- 游戏主交互壳层改动必须先写 `主交互槽位五联单`。
- UI 回归恢复必须先锁旧代码和旧截图基线，再分开验收关闭态与开启态。
- 双端/移动端布局细则继续读 `docs/ai-rules/ui-responsive-layout.md`。

### 0.1 UI 同类交互统一门禁（强制）

- 凡是本轮修改选择、目标、鉴定、可达对象、高亮、候选列表或卡牌/房间/角色交互，动手前必须主动搜索当前游戏内同类实现，至少覆盖 `selected`、`target`、`highlight`、`rounded-full`、`ring`、`choice`、`room`、`card` 等关键词。
- 可直选对象必须直选：如果真实对象已经在画面上可见，点击区域必须落在该对象本体或其贴合描边上；不得新增一排文字按钮、黑框按钮或悬浮列表来替代本体点击。
- **组合目标必须拆成真实步骤**：如果一次效果同时要求选择对象、传送门/区域、落点或数量，不能把所有组合排列提前展开成按钮墙。应按规则顺序创建由引擎交互持有的分步选择：先点当前可见对象本体，再点下一类对象或位置；按钮只保留数量、确认、跳过、取消等对象本体无法表达的语义分支。
- **适配层不得把对象选择统一降级为按钮**：领域选项已经携带单位、建筑、棋盘格等真实目标时，UI 适配器必须把它们映射到对应的本体点击与高亮入口；`targetType: 'button'` 只适用于确实没有可见业务对象的语义选择，不得作为“方便统一渲染”的默认路由。
- **重复跳过入口必须消除**：同一步如果已有横幅的跳过/取消入口，选项列表不得再生成同义的“跳过”按钮；需要由引擎交互保留可取消语义，并由一个前台入口承接。
- 非骰子对象禁止用圆形命中/高亮作为默认选择态。若确实要用圆形，必须先说明对象现实形态就是圆形，或这是头像/状态点而不是选择高亮。
- 同一游戏内同类交互只能有一套主视觉语法。新增“鉴定”“选择目标”“选择房间”“选择物品”时，必须复用已验证的候选/选中/确认样式，并在截图里检查没有混入另一套黑框、圆圈或文字下划线风格。
- 同一游戏内同类数值、徽章、候选、选中态和确认入口必须主动统一。只要发现一处“选择页是方形、局内是椭圆”这类同类 UI 不一致，不能只修眼前一个点；必须扩审当前游戏内同类元素，并说明哪些已统一、哪些因现实对象形态不同而保留差异。
- 一处 UI 被用户指出“不像本游戏风格 / 不起眼 / 丑 / 位置离谱”时，默认触发同类交互扩审。至少回查同游戏的角色选择、局内 HUD、卡牌/房间检视、阻塞式发现、确认/取消按钮和目标高亮，不能把单点修补当成全面收口。

## 1. 核心审美准则 (Visual Excellence)

- **深度感 (Depth)**：通过渐变、阴影、毛玻璃构建视觉层级，但需按场景分级使用：
  - **重点区域**（游戏结算、核心面板）：可使用毛玻璃 + 软阴影增强层级感
  - **一般区域**（确认弹窗、列表项）：使用纯色/简单渐变 + 轻阴影即可
  - **高频更新区域**（动画中元素、拖拽对象）：**禁止毛玻璃**，仅用 `opacity`/`transform`
- **动效反馈 (Motion)**：状态变更应有动效反馈，但需区分场景：
  - **关键交互**（确认/提交/阶段转换）：使用物理动效（弹簧/惯性）
  - **常规交互**（Hover/Focus）：使用简单 `transition`（150-200ms）
  - **高频交互**（快速点击/连续操作）：仅用颜色/透明度变化，禁止复杂动画
- **布局稳定性 (Layout)**：动态内容通过 `absolute` 或预留空间实现。**辅助按钮严禁占据核心业务流空间，必须以悬浮 (Overlay) 方式贴边/贴底显示。**
- **空间让渡必须兑现到主内容（强制）**：当用户要求“压缩左栏 / 收窄侧栏 / 减少辅助区 / 节省空间”时，真实目标通常不是辅助区数字变小，而是把省出来的空间交还给当前主内容。验收必须证明主内容因此获得更完整的展示，例如候选角色从两列变三列、原本露半截的候选完整进入首屏、当前决策对象更大或更少被裁切；禁止只把侧栏改窄，却让主内容仍沿用旧列数、旧宽度或旧裁切状态。
- **空间压缩必须守视觉比例（强制）**：节省空间不是把辅助区压到失去分量。双栏选择、角色详情 + 候选墙、属性栏 + 主对象这类界面，默认先按黄金比例附近审查主次关系：信息侧栏约 38%，主候选/主舞台约 62%；只有当候选数量、触控尺寸或安全区证据要求时，才允许偏离。验收必须同时看“主内容是否完整”和“辅助信息是否仍像一个有重量的面板”，禁止从一个极端（左侧过宽）直接调到另一个极端（左侧瘦成条）。
- **牌桌/棋盘主视图优先开放式设计（强制）**：真实对局主界面默认让牌面、棋盘、骰盘、手牌和当前可操作对象直接成为画面主体，不要先套一层“围栏式 UI”。除非规则本身需要窗口化承接，禁止把桌面切成厚边框卡片、硬容器、栅栏面板、居中说明盒或多层边线框；需要分区时优先使用留白、尺度、光照、轻量分割线和对象自身边界。
- **开放式主舞台不得再套硬背景框（强制）**：一旦本轮判断为开放式牌桌、开放式棋盘或开放式阻塞结果主舞台，就不能在主对象和选项外再套一整块深色背景板、厚边框、封闭卡片壳或“看起来像弹窗”的框。允许保留的是对象本体阴影、局部光晕、按钮自己的可点边界和必要的轻量压场；若截图里第一眼看到的是一个大背景框而不是牌面/棋盘/选项本体，直接判为未达标。
- **事件牌 / 发现结果开放叠层必须 PC/移动同构（强制）**：事件翻牌、属性检定、投骰结果和发现结算若在 PC 上属于开放桌面叠层，移动端默认也必须保留同一承载结构、周边 HUD 和透明骰盘；不得因为移动端空间紧张就隐藏行动栏、阶段、牌堆、探索者面板，或给事件面板、投骰区、结果条另套整块黑底。`牌面 → 骰盘 → 结果 → 选项 → 提交/返回` 这条主链路必须在两端保持同一相邻关系和同一语义锚点；其中“提交”可以是确认按钮，也可以是玩家点击最终真实目标对象本体。若规则还要求放置/移动到房间、卡牌、角色或棋盘目标，目标对象本体必须在地图/牌桌上以候选态承接点击；当该对象点击已经是最终决策时，点击本体必须直接提交结算，不得再额外要求一次同义确认。只有显式接受/放弃二选一、多选未完成、危险性二次确认或规则文本明确要求“确认”时，才允许保留确认按钮。双端同构指顺序、语义锚点、提交语义和周边信息保留一致，不是同尺寸、同列宽或同紧凑；移动端因触控和安全区做的紧凑化不得反向压缩 PC 的牌面、骰盘和结果区，PC 的桌面宽高阈值也不得硬套到移动端导致横屏布局被误判失败。移动端必须用真实横屏截图、触控尺寸、牌面/骰子可读性和周边 HUD 去向单独验收。只有真实截图或几何证据证明发生重叠、裁切、不可读、不可点或安全区遮挡时，才允许做最小避让，并必须在 E2E 里覆盖该避让原因。
- **地图/牌桌目标选择态必须让目标本体成为前景（强制）**：当流程已经从事件牌、骰盘、结果或属性按钮推进到地图/牌桌目标本体选择时，上一阶段的牌面特写、骰盘、结果条和选项组必须退场，或缩到不遮挡目标的辅助区；不得让玩家顶着前景特写、骰盘或结果面板去点被遮挡/半遮挡的真实目标，也不得只靠 `pointer-events` 穿透证明“能点”。E2E 必须覆盖目标选择态截图和几何断言：目标本体可见、无遮挡、中心点命中真实对象，上一阶段特写不再占据目标选择前景；若点击目标本体就是最终决策，还必须反向断言不存在额外确认按钮。
- **事件目标选择不得加代理文字标签或目标块（强制）**：当事件要求选择房间、卡牌、角色或棋盘目标时，真实目标必须由对象本体的候选/选中高亮承接；不得在地图房间、token、卡牌上额外叠 `点{{对象}}`、`已选{{对象}}`、`目标`、`请点这里` 这类可见标签，也不得在事件面板里新增 `地图 / {{房间名}}` 这类代理目标块，更不得靠一行说明正文替代对象高亮。E2E 必须同时覆盖 `目标本体可见可点 → 玩家点击真实对象 → 按规则直接提交或同源确认`，并反向断言这些代理标签、代理目标块和说明正文不存在。若流程是最终对象点击即提交，测试必须反向断言不存在额外确认按钮；没有改骰、后续选择、确认、可撤销或必须阻塞阅读的信息时，还必须反向断言不存在只用于点“返回牌桌”的结果特写，点击目标后应直接回到牌桌并让位置/属性/日志落位。截图和汇报必须把点击目标前称为“效果处理中选择目标”，不能误写成“先选择再结算”。
- **开放式棋盘禁止黑边/遮罩条补比例（强制）**：地图、棋盘、牌桌底图比例与屏幕比例不一致时，只能通过裁切、缩放、局部重排、贴边悬浮控件或轻量信息浮层解决；禁止在上下左右加黑边、暗色横条、半透明遮罩条、深色信息栏或伪 letterbox 来“补满”画面。验收截图里只要出现无规则意义的黑条/暗条压住棋盘，就必须判为未通过，不能用 E2E 断言通过替代视觉验收。
- **开放式裁切不得裁掉可交互 UI（强制）**：开放式棋盘允许裁掉无交互意义的底图边缘，但不得裁掉轮盘、玩家状态、牌堆、手牌、动作按钮、关闭按钮、放大查看内容等可读或可点对象。移动横屏验收必须同时证明“没有黑边/遮罩条”和“所有常驻可交互 UI 完整可见”；如果截图里控件只露半截、标题/数字被切掉、按钮不可读，即使地图铺满也必须判为未通过。
- **阻塞式结果承接不得角落化（强制）**：翻牌、抽牌亮相、投骰结果、事件选择、战斗结算这类会阻塞当前流程、要求玩家先阅读或处理的对象，属于当前主内容，不是日志、角落 HUD 或轻提示。默认必须放在主视线区域（通常居中或等价主舞台位），并让真实牌面、骰面或结果本体清楚可见；后续 `继续 / 确认 / 跳过` 按钮可以继续使用既有主动作锚点，但不得用右上角小条、侧栏摘要或一行文字替代主结果承接。事件、属性、伤害、目标这类当前必须选择的选项不得做成小号 chip；必须至少满足常规触控命中区并在整屏截图里肉眼可读。
- **即时检定的牌面和骰面必须同屏主承接（强制）**：如果翻开的牌、发现牌、事件牌或效果文本会立即触发投骰/检定，牌面与本次骰面属于同一个阻塞结果；不得把牌面放中央、骰子放角落，也不得用日志、小字或摘要替代骰面。
- **物理骰承接默认用透明虚拟骰盘（强制）**：当骰子像 DiceThrone 一样在桌面上物理滚动时，骰区默认是透明/开放式的虚拟承接面，不得额外套实体黑盒、厚边框骰盅或封闭面板来抢走桌面感。需要承载总点数、加值、结果时，把这些信息放到底部或侧边信息带；骰子本体仍应浮在桌面主舞台上。截图必须等骰子停稳后再截，不能用滚动中、半悬空、残影或过渡态冒充最终验收图。
- **玩家可见投骰信息不得展示内部公式（强制）**：正式对局和教程里的投骰结果默认只展示玩家能理解和需要决策的信息，例如骰子本体、加值来源、总点数、成功/失败和可选改骰入口；不得把内部骰值序列、`2 + 1 + 0` 这类计算式、测试用公式或规则引擎中间值直接写到玩家可见 UI。若玩家肉眼看不清某颗骰子的点数，应先修骰面可读性、尺寸、角度或专用皮肤，而不是用一行公式替代骰面。
- **投掷与终局不得混名（强制）**：如果规则流程是“先投掷/检定，结算后才进入终局”，截图、测试名和汇报必须按真实时序命名，例如 `驱魔神志检定投掷`、`驱魔成功后的终局页`。禁止把前一步投掷叫成“终局投掷结果”或“终局物理骰”；若终局页保留最近一次投掷回看，也必须说成“终局页保留的最近一次驱魔检定骰盘”，不能把它当成终局阶段本体。
- **正式素材已含信息时不得复读（强制）**：当正式牌面、房间板块、参考卡、剧本页、骰面或 token 图本身已经清楚包含标题、类型、规则正文、点数或结果说明，运行时 UI 默认只能补充交互控件、状态归属、无障碍文本和必要选择入口；不得在素材旁再可见重复同一标题、同一规则正文、同一“已翻开/已抽取”说明，把正式素材降级成装饰图。若素材文字小到不可读，正确动作是先检查图集切片、裁切坐标、压缩产物、显示尺寸和放大承接；没有这些证据前，不得另写一套可见正文替代素材。
- **素材已说明的可改骰对象不得再贴文字标签（强制）**：如果物品/手牌自身牌面已经写明能改骰或影响结果，运行时只允许用全边描边、发光、脉冲、可点击态等无文字方式强调它可介入；禁止再叠“改骰”“可用”“点击改骰”这类可见文字徽章。高亮必须覆盖完整对象边界，不能只露右边/下边，截图验收要能一眼看出整张牌可点。
- **禁止无意义重复信息填充（强制）**：当前上下文已经明确的信息（例如当前 tab、页面标题、区块标题、卡片标题）默认不应在子内容区机械重复，除非该重复能明显提升理解效率。允许重复的场景包括：消歧、跨区块跳读、无障碍提示、风险提示、需要脱离上下文单独成立的卡片/弹窗标题。禁止的场景包括：仅为了“看起来信息更满”而重复标题、在空状态里重复当前 tab 名称、同一视窗内对同一事实做无新增价值的二次强调。示例：tab 已叫“更新”时，空状态写“暂无日志”即可；若是从外部入口打开的独立弹窗，标题写“更新”则是合理重复。
- **长文阅读界面内容优先（强制）**：剧本、规则书、故事档案、帮助文档等以阅读为主的弹窗或书本界面，默认必须把主空间留给正文/原始内容。上一页、下一页、关闭、页码等控件只能做贴边悬浮、页角页码或轻量热区，不得额外占用整条顶部栏、底部栏或左右大框来挤压阅读区。书本式长文阅读如果用户预期是“点击左右翻页”，左右热区必须透明，不得再显示左右箭头按钮、上下翻页框或占位控件；页面里只保留必要退出入口和页角页码。按钮文案不应复读为“阅读模式 / 沉浸阅读 / 完整阅读”这类自我描述；界面已经由入口和标题说明用途时，正文区不得再显示无信息增量的模式说明。章节页只允许一个可见章节标题，章节序号可做小号页眉或装饰，不得写成“01 / 标题”后再用大标题重复同一个标题。验收截图必须证明首屏正文面积优先、翻页可点、页码可见但不抢占内容。
- **生图设计稿到实现必须走专项流程（强制）**：用 AI 生成设计稿、参考图或 UI mockup，并继续按该图实现时，必须先读 `docs/ai-rules/generated-design-implementation.md`。`ui-ux.md` 负责通用审美与布局原则；生成稿到实现的内容盘点、目标稿复看、几何量测、E2E 证据链以该专项流程为准。若同时存在目标稿和用户标注的错误截图，目标稿永远是语义与比例真相源，标注图只负责定位问题，不能反向替代目标稿。
- **Home V2 移动横屏必须读专项规范（强制）**：修改 Home V2 首页、详情页、纸面弹窗或相关 E2E 时，必须先读 `docs/ai-rules/home-v2-design.md`。该页面当前按移动横屏书本界面验收，PC 端通过结果不能替代移动 CSS 视口截图。
- **方向偏好不等于阻断许可（强制）**：`preferredOrientation`、`landscape-adapted`、`portrait-adapted` 或移动布局 preset 只能说明首选构图，不能自动升级成 wrong-orientation gate。没有用户当轮明确要求“错误方向不可继续操作”时，错误方向必须保留真实页面、允许滚动/缩放/非阻断提示，不能为了规整截图而拦住玩家。
- **固定牌桌错向禁止全屏阻断（强制）**：`board-shell` / 固定牌桌在手机竖屏或横屏错向时，默认仍按同一张牌桌渲染，只能通过横向/纵向滚动、缩放、安全区让位或非阻断提示解决可达性；不得隐藏主界面，不得用整屏方向页替代游戏本体。
- **入口/首页方向建议默认不得替代可操作入口（强制）**：若用户明确要求首页、入口页、模式选择页仍可继续操作，方向提示只能作为非阻断 banner / hint 呈现，不得复用游戏页 wrong-orientation gate 去遮挡创建、加入、继续对局等主入口。验收必须证明主入口在错向提示存在时仍可见、可点、不会被全屏遮罩捕获。
- **方向敏感页面验收必须同时证明错向态与正向态（强制）**：凡需求里出现“横屏版 / 竖屏版 / 一种强制横屏一种竖屏 / 旋转后继续”，验收至少要给两类证据：① 错误方向下真实页面仍可见、可滚动、可继续操作，且没有全屏阻断页遮住游戏本体；② 正确方向下主内容占位、比例与交互入口正常。禁止拿“切换成功了”“出现了提示条”“DOM 还在”当作方向适配达标。
- **方向/壳层受 UI 状态控制时，Web 与 Native 必须共享同一真相源（强制）**：只要某个页面样式、首页模式、运行态开关会影响原生方向锁、沉浸式状态、状态栏/导航栏模式或 App 壳层布局，就不能只把状态存在 React state、context、localStorage 或单端路由分支里。必须把该状态同步到 native 可直接读取的载体，例如 URL/query、hash、bridge、SharedPreferences、原生可读配置或等价单一真相源，并在验收时证明“切换后原生判定已同步变化”。禁止出现 Web 已切样式、但 native 仍按旧模式锁方向/开沉浸式的分叉状态。
- **移动端方向锁和系统返回必须归属全局壳层（强制）**：游戏只声明 `preferredOrientation`、移动布局 preset 和可运行 shell target；横屏/竖屏锁定、沉浸式窗口、Android 返回键和边缘侧滑返回必须优先接在 App 壳层、路由守卫或通用棋盘壳层。禁止为了某个游戏“先能用”就在单个 Board 里私接方向锁或侧滑返回；若某个游戏阻断了系统手势，应修通用手势让路或全局返回桥，而不是每个游戏复制一份。
- **游戏教程路由必须继承游戏方向配置（强制）**：`/play/:gameId/tutorial` 和 `/play/:gameId/tutorial/:tutorialId` 属于该游戏的游戏页，不是独立竖屏教程页；移动端方向、`MobileBoardShell` preset、沉浸式系统栏和截图验收默认全部继承该游戏 manifest 的 `preferredOrientation / mobileLayoutPreset`。对横屏游戏，教程移动 E2E 主视口必须使用项目横屏基线（`MOBILE_LANDSCAPE_REFERENCE_VIEWPORT` 或同等 13:6 横屏比例），并断言页面根节点确实带有该游戏的横屏配置。禁止教程入口单独写竖屏视口、单独接方向锁，或用竖屏截图替代横屏游戏教程验收。
- **动作控件不能按最低触控线糊弄设计稿（强制）**：创建、加入、确认、返回等真实动作必须跟随当前载体比例形成清晰交互语义；44px 只是不失效的触控底线，不是“符合设计稿”的尺寸标准。按参考图实现时必须按主容器比例量宽高、字号、位置、热区和装饰重量。创建/确认/加入这类主操作通常需要可见按钮承载；返回这类导航入口若参考图是轻量透明样式，禁止强加按钮背景，只能保留透明导航并证明热区、字号和可读性达标。
- **关键控件可读性不足直接判视觉失败（强制）**：按钮、tab、输入框、搜索图标、切换项、标题、副标题、分页/排序入口这类承担识别或决策职责的控件，只要在真实截图或真机画面里出现低对比、字色贴底色、图标歪斜、状态不清、点击态与未选态难区分，就必须直接判定为未达标并继续重做。禁止用“断言通过”“控件存在”“热区够大”替代可读性验收；高频控件的可读性是收口门槛，不是可选优化项。
- **高亮/描边承担主决策提示时，必须强到“一眼认出对象”（强制）**：如果用户当前该点哪里、当前选中了谁、当前哪个槽位可落点，主要依赖描边、发光、外圈、底色或脉冲来表达，那么该高亮必须在整屏真实画面里直接把目标对象从周边元素里拉出来。禁止出现“代码里确实高亮了，但第一眼看不出高亮的是谁”的状态；这类情况一律按视觉失败处理。默认最低要求是同时拉开 `边界厚度/亮度`、`与非目标的色相对比`、以及 `目标周边局部压场或底色对比`，而不是只把原来的细浅描边再轻微加粗一点。
- **教程引导框不得伪装成对象选中态（强制）**：教程蓝色目标框/聚焦框属于“提示定位层”，负责告诉用户当前看哪里或点哪里；它不是卡牌、骰子、房间等游戏对象本体的选中/可选状态。即使被提示目标本体使用圆形圈、旋转描边或随对象几何的命中区，教程引导框也默认保持原有矩形/目标框语法，除非用户明确要求重做教程聚焦框样式。禁止把“选中态改圆形”泛化成“教程蓝框也改圆形”。
- **唯一目标仍然必须点选（强制）**：只要当前步骤的语义是选择某个可见对象，例如卡牌、骰子、房间、角色、目标、支付对象、重投骰或可用道具，即使合法候选只剩 1 个，也不得默认选中、默认写入 payload、或点击“使用/确认/攻击/移动/重投/驱魔”后自动代点该对象。正确流程必须是：一级动作进入选择态 → 合法对象在桌面/棋盘/手牌/骰盘里以绿色或同场景可操作色完整高亮 → 用户点击/点按对象本体或投影命中区 → 才结算。教程、E2E 和调试 harness 也必须走这条链路，不得通过预置状态、默认目标或隐藏锚点替玩家完成选择。只有完全没有对象/目标/支付/顺序/数量/放弃语义、且没有玩家会期待亲自选择的可见对象时，才允许自动收口。
- **主按钮不得替代目标点击（强制）**：当按钮点击后仍然需要目标、费用对象、骰子、卡牌、房间、单位或玩家时，按钮只能打开或聚焦选择态，不能携带唯一候选直接结算。像 `使用道具`、`选择骰子`、`重投`、`攻击英雄`、`移动到房间`、`驱魔检定` 这类链路，只要后面还有一个可见对象要决定，就必须保留对象高亮和对象点击，不得把按钮做成代点器。
- **完整对象描边必须四边均衡（强制）**：可选/选中描边必须像一个完整对象外圈，而不是左边、下边或两条边更重。默认参考大杀四方成熟做法：`src/games/smashup/ui/HandArea.tsx` 对手牌选中使用 `ring-4 ring-green-400 shadow-[0_0_20px_rgba(74,222,128,0.5)]`，`src/games/smashup/ui/BaseZone.tsx` 对基地/随从候选使用 `border + ring + shadow` 同层组合。实现时优先把 border/ring/glow 施加在同一个外层对象容器上，避免被 `overflow-hidden`、内层缩放、伪元素、叠多层阴影或错位 wrapper 裁掉；截图里只要看起来只有两边有描边，就直接判视觉失败。
- **固定构图弹窗/浮层必须以“目标稿 + 同类通用壳层”作为真相源（强制）**：当 modal、overlay、表单浮层、书页内面板有明确设计稿或同场景已有通用 UI 时，默认先复用同一套共享壳层、边框、角饰、标题/分割线、输入框和主按钮语法，再做当前内容编排；禁止一边声称“同风格”，一边为登录、创建、加入、确认各写一套不同的组件语法。受限视口下若出现裁剪、挤压或字段缺失，先修共享壳层内的节奏、局部滚动和紧凑分支；“做成接近全屏”只是可能暴露的失败症状，不是规范本体。验收时至少同时证明四件事：①主容器宽高占比和中心点仍符合目标稿；②标题、分割线、角饰、输入框、主按钮属于同一视觉语法；③键盘/聚焦不会把弹窗整体顶走；④关键字段和下一步主操作都在真实可视区。若同一轮同时存在目标稿和 `ui参考` 问题标注图，前者优先，后者仅用于问题定位。
- **装饰层必须可命名、可计数、不可重复堆叠（强制）**：在固定构图弹窗、卡片、面板里，装饰层必须能清楚说出自己在扮演什么角色。常见角色可以是 backdrop / shadow、surface、border、accent line、corner ornament、divider accent，但这些只是例子，不是固定清单；若某个灰色框、半透明矩形、阴影带、细线、角标无法明确归类，就应优先视为多余层而不是“看着差不多就留着”。同一边同一轴向上不得同时出现两套意义相近的装饰层，也不得为了“更满”额外叠一层不解释的灰块；背景里出现既不像遮罩、也不像边框或投影的灰色框时，默认判为无意义装饰，必须删除或重做成明确角色。
- **标注图红框是验收信号，不是示意图（强制）**：当用户提供带红框、箭头或圈选的参考图时，标注区域必须优先作为问题位点核对；如果红框圈的是角标、分割线或背景框，就必须把对应元素命名并逐项检查位置、重量、留白和语法一致性。角饰不要求机械镜像，但必须保持同一视觉家族，不能只看整体观感就提前收口。
- **参考图几何语义必须先命名再实现（强制）**：对照设计稿时，必须先判断每个视觉元素的几何归属，再落代码和测试命名。像“分类选中线”这类元素，如果实际落在页眉分割线上，就应按“页眉选中线 / rule / divider accent”处理；只有贴近文字基线、属于文字装饰时，才允许称为“文本下划线”。禁止用模糊命名掩盖还原错误，也禁止只量宽度/中心点而不量相对参照线、文字和容器的位置关系。
- **同级 tab / 导航必须保持同一视觉语法（强制）**：同一 tab 组里的项目必须共用一致的字号基线、间距节奏和组件形态；active 态只能通过颜色、字重、下划线、标记、底色等状态差异表达。禁止把 active tab 画成大标题、其它 tab 画成小链接，或用一大一小破坏同级关系。若需要页面标题，必须和 tab 组分离，不得混在同一行冒充 tab。
- **空状态禁止“操作教学式说明”（强制）**：首页/大厅/详情等主路径的空状态默认只允许“状态标题 + 必要主操作”，禁止再追加“先做什么就会出现什么”的解释型文案（如“先开一局就会出现记录”）。若确需说明，必须有用户明确要求或可用性证据，并优先放到帮助页而非主界面。
- **主界面只展示有直接用途的元素（强制）**：主入口、总控页、工作台首页、首页首屏默认只允许展示“当前用户马上能用到”的内容。内部模块编排图、调试按钮、编辑器工具栏、背景/吸附切换、实现分层示意、纯技术态流程图等，如果不能直接帮助用户决策、执行或理解当前结果，就必须隐藏、下沉到调试态，或彻底删除。禁止把“这能说明系统内部怎么做”当成留在主界面的充分理由。
- **牌桌类 Board 首屏必须让位给当前决策对象（强制）**：当页面属于真实对局 Board，而不是大厅、详情页、教程页或独立品牌页时，首屏主视觉必须优先给当前决策对象，例如公共牌列、手牌、当前目标、焦点卡、棋盘落点和当前可执行动作。禁止把游戏标题、品牌名、连接状态、局外说明、大块总结面板或装饰性章节标题做成首屏第一视觉，除非它们本身就是这一回合必须操作的对象。
- **Board 内不得重复壳层已拥有的全局状态（强制）**：如果游戏页壳层、悬浮 HUD、系统状态球或共享框架已经稳定显示“已连接/未连接”“房间名”“游戏名”“玩家身份”这类全局状态，具体游戏 Board 默认不得再机械重复一遍。只有当该状态直接参与当前回合决策，或脱离壳层后会失去语义时，才允许在 Board 内保留轻量副本；否则必须删除或降级。
- **终局/总结信息不得在常规对局态抢主区域（强制）**：计分册、排行榜、终局结算摘要、胜负条件说明这类主要服务于收尾、复盘或阶段切换的信息，在常规对局态默认只能做成紧凑徽记、折叠入口或次级角落信息。除非“当前分数本身就是玩家此刻主要决策对象”，否则禁止用大面板、居中纸张、整列侧栏等形式长期占据主交互区。
- **组合爆炸类交互禁止枚举成按钮墙（强制）**：当交互本质是“同一组对象的排序、分组、分配、顶/底拆分、先后次序编辑”时，禁止把所有排列、组合或分割结果直接展开成按钮列表、卡片墙或长菜单。只要候选数量会随对象数呈阶乘级、指数级或明显超线性膨胀，就必须改成线性复杂度的编辑方式，例如分步选择、双列表分配、局部移动、拖拽排序或显式确认流。验收时必须提供真实链路截图，证明用户面对的是有限工具条/编辑器，而不是爆炸式选项清单。**其中用于检视/预览的对象卡面不计入“按钮数量”**；只有真实可执行的动作控件、确认控件和跳过控件才算交互负担。
- **交互模式成立性优先于减负入口（强制）**：用户觉得“难选、难扫、步骤多、选项墙、总在弹 prompt”时，第一检查项不是先补搜索、筛选或折叠，而是先判断**交互模式本身是否成立**。至少先回答四件事：① 这一步是否本来就该自动收口；② 是否错误地把单候选/必选步骤做成了确认层；③ 是否把组合爆炸问题错误实现成按钮墙；④ 当前 ownership、时机、`may/skip` 语义是否正确。只要其中任一项不成立，就必须先修交互模式，禁止用“减负入口”掩盖错误模式。
- **多候选/多状态界面在模式成立后仍须提供减负机制（强制）**：只有在确认交互模式本身成立之后，才讨论“怎么让用户更容易扫和选”。当一个界面需要同时展示较多候选对象，且对象混有多种状态时，禁止只靠全量平铺让用户自己扫。必须提供至少一种能明显降低扫描和决策成本的机制，例如分步流、状态分层、聚焦当前可操作对象、搜索、筛选或等价手段。移动端受限视口下默认优先聚焦当前可操作对象，而不是先把全部状态混排给用户。
- **减负机制不得反向挤爆主交互区（强制）**：补搜索、筛选、状态条、分组器、辅助说明或其他减负机制时，不能只满足“多了个入口”就算完成。若页面本身已经处在紧预算场景，减负机制必须优先做成单行、可折叠、渐进展开或其他低侵入形式，避免为了增加工具而压缩、遮挡或裁切真正的主交互对象。验收时必须同时看两件事：① 用户是否真的更容易理解和操作；② 主交互区是否仍保持完整可见、可读、可点。
- **空间预算必须先于文案分层（强制）**：在角色选择、局内 HUD、移动横屏、侧栏、底栏等紧预算 UI 中，新增标题、说明、状态或能力描述前，必须先判断能否与现有标签合并成 `标签：内容` 同行表达。短能力、短状态、短说明默认用一个信息框直显，例如 `特性：大胆，攻击投骰 +1`，禁止拆成“能力名一个框 / 完整说明另一个 tooltip 或另一行”。只有正文长到单框会明显挤压主对象时，才允许用 `title` / tooltip / 折叠详情承载完整说明，此时常驻触发器只能显示标签、名称或短摘要，禁止复读完整正文。验收时必须证明新增信息没有额外挤掉一排关键空间，且主交互对象仍可读、可点、可滚动到；涉及 tooltip 的改动必须有断言证明触发器没有复读 tooltip 完整正文。
- **常驻辅助 UI 不得遮挡主交互区（强制）**：座位条、玩家状态卡、草稿顺序条、阶段提示条、底部信息栏这类**常驻辅助 UI**，不得再用绝对定位压在当前主交互区上，尤其不能盖住底排卡牌、底部按钮、确认区或当前可点对象。若页面需要同时展示“主交互对象 + 常驻状态摘要”，必须二选一：① 让辅助区进入正常布局流，占据独立高度；② 对主交互区显式预留等量安全区，并在真实截图里证明没有任何关键对象被遮挡。禁止通过放大当前玩家卡、加悬浮卡片或叠加半透明面板来挤占主交互空间。
- **固定牌桌类游戏的桌面进行页默认极简（强制）**：对于 Fantasy Realms、麻将、卡牌牌桌、棋盘战区这类“主交互对象本身就是牌桌/棋盘”的桌面进行中页面，官方规则以外的辅助信息默认不得常驻成独立大面板。默认只保留：`当前行动/主操作`、`公共区`、`自己的可操作区`、`牌库或资源剩余量`、`当前总分或必要计数`。像 `当前焦点`、长段策略解释、分数拆解、复盘提示、终局排名、辅助推演这类内容，只允许进入以下三类场景之一：① 终局复盘 ② 窄视口/堆叠态 ③ 用户显式展开。若没有这三类前提，就不得在桌面进行页常驻。
- **样式修复不得升级成布局或交互载体替换（强制）**：当用户只点名 `黑底 / 黑边框 / 描边 / 阴影 / 选中效果 / 挡板感 / 按钮质感` 这类视觉样式问题时，默认只允许修改现有槽位内的颜色、边框、阴影、透明度和状态反馈。禁止把底部按钮、手牌、队友卡、目标卡、确认按钮等既有交互载体替换成横幅、文字链、弹窗、步骤条或另一套布局；如果确实判断必须改布局，必须先说明“这是从样式修复升级为布局修复”并等确认。验收必须证明原交互对象仍在原槽位，只是目标样式被修正。
- **可点击不等于必须有实体按钮框（强制）**：固定牌桌、棋盘或地图上方/下方的主动作按钮，若用户要求去掉黑底、边框、挡板或容器感，默认应做成低容器化按钮：保留图标、文字、点击区域、键盘焦点和当前态颜色即可。禁止为了证明“这是 UI”而重新套黑底、渐变底、边框、内线、厚阴影或胶囊框；需要强调当前动作时优先用文字颜色、透明度、轻量下划线或图标状态，而不是再造一个实体底板。
- **主按钮已自解释时，提示横幅不得重复说明动作（强制）**：如果当前一级动作已经通过显式主按钮写清楚了，例如 `摸牌`、`弃牌`、`结束回合`、`确认选择`，那同一屏上的提示横幅只能承担状态或归属说明，不能再重复写成“下一步：摸一张牌”这类同义复述。提示横幅只在以下情况才允许升格：① 当前合法动作不明显、需要额外解释；② 当前处于等待别人或系统推进的强状态；③ 当前存在多个并列合法动作，且需要用一句短提示说明分流。否则横幅必须退成更短的状态词或直接隐藏。
- **阶段、剧本状态和日志不得重复抢主 HUD（强制）**：阶段或当前剧本状态在顶栏、HUD、日志、房间焦点里只能有一个主可见入口。像“恶兆前”“首剧本开始”“当前阶段”这类信息已经由顶栏表达时，不得再在主牌桌上方常驻一条同义日志或第二个阶段条。日志默认只作为刚发生的反馈、可展开记录或读屏辅助，不得和阶段 HUD 并列成第二主提示。
- **牌桌短提示不得侵入手牌安全区（强制）**：固定牌桌进行页里的“你的回合 / 摸牌 / 弃一张牌 / 等待某玩家”这类短提示，只能作为上方或桌面中上部的轻量状态条；不得横跨主牌桌做成大块横幅，也不得压在底部手牌上方、遮挡手牌、贴着手牌顶边或挤占手牌槽位。若主按钮或卡牌本体已经表达动作，提示条必须降级为短状态词；真实截图里提示条底边与手牌顶边没有明确空隙时，直接判失败。
- **牌桌布局必须按区域独立预算（强制）**：顶部 HUD、中央公共区、底部手牌区、侧边主操作区、短提示条必须先划分独立区域预算，再各自布局。辅助提示条、状态条、等待条不得参与中央区或手牌区的尺寸分配；中央区卡牌数量变化也不得把手牌区卡尺寸突然压小。若某个辅助元素一出现就导致别的区域缩放、跳位、压缩或改密度，直接判为布局分区失败。
- **绝对定位 UI 必须是独立 overlay 层（强制）**：牌桌里的横幅、短提示、浮动按钮、倒计时、动效飘字这类 `absolute/fixed` UI，只能挂在明确的 overlay/rail 层上；不得放进手牌行、公共牌行、棋盘格、单位列等主内容区域里参与 `grid` / `flex` / `row` 高宽计算。验收不能只看“元素存在”，必须量矩形证明：① overlay 出现前后主区域卡牌/棋子尺寸不变；② overlay 不遮挡当前可点对象；③ 主按钮位于独立操作带，不压住手牌或底部按钮。缺任一项，判为布局失败。
- **当前行动者必须主 HUD 强可读（强制）**：固定牌桌进行页必须让玩家一眼看出当前是谁的回合，尤其是 `你的回合`。它不能退化成小号淡色标签、角落装饰字或需要放大截图才能识别的弱提示；等待别人时也必须明确显示当前行动对象，而不是展示玩家此刻无法操作的动作说明。
- **卡牌附属工具只在悬浮/键盘焦点时出现（强制）**：放大镜、查看详情、小角标按钮这类“检视工具”不是主动作入口，桌面端默认必须隐藏，只能在鼠标悬浮卡牌或键盘可见焦点时出现；`可操作/actionable`、`已选中/selected`、`当前阶段可点击` 都不能让这类工具常驻。若真实截图里未悬浮卡牌也能看到放大镜，直接判失败。
- **触屏卡牌预览与执行必须二段式（强制）**：移动端没有可靠 hover。若同一张卡既能预览又能执行关键动作，例如拿中央牌、弃手牌、使用牌，默认必须采用“第一次点击聚焦/抬起/预览意图，第二次点击才执行”的二段式；长按只允许作为打开大图的辅助入口，不得代替主操作确认。除非另有独立明文主按钮承接执行，否则禁止首点直接提交不可逆或阶段推进动作。
- **进行中手牌尺寸必须稳定（强制）**：成熟卡牌游戏通常把手牌视为玩家的固定操作带，进行中不得因为阶段、提示条、公共区卡牌数或临时多 1 张手牌而整体缩放。默认做法是预留最大临时手牌槽、稳定重叠/扇形排布或固定轨道；禁止用 `7 张正常、8 张压缩` 这类中途密度切换。验收必须覆盖从常规手牌到临时多一张的代表态，并量卡牌宽高证明未变化。
- **固定牌桌类游戏的 PC live 基线固定为 `1920x1080`（强制）**：除非用户当轮明确指定其他分辨率，桌面进行页的结构验收、截图复看和参考图对齐都必须以 `1920x1080` 为权威基线。这里的基线是验收视口和设计稿尺寸，不是页面最大宽度或固定外框。禁止继续用 `1440px` 最大宽度、窄屏截图或局部裁图判断“已经铺满”；若真实页在 `1920x1080` 下主牌桌没有吃满首屏可用空间，直接判失败。
- **固定牌桌类游戏的 PC live 必须铺满首屏（强制）**：牌桌/棋盘本体应占据首屏绝大部分宽高，辅助 HUD 只能贴边服务主交互对象。禁止让主牌桌停留在页面中央小岛、四周留出大块空黑边、或只靠 `max-width` 居中导致 1920 桌面大量空置。验收截图必须能同时看到：主牌桌铺满、公共区有明确秩序、自己的操作区靠近底边且尺寸充足。
- **固定牌桌类游戏的 PC live 极简不得等于低对比（强制）**：极简只表示去掉非必要容器、正文和装饰噪音，不表示把必要 HUD、计数、当前玩家和分数做得很淡很小。`弃牌阈值`、`手牌槽数`、`当前行动`、`当前玩家分数` 必须一眼可读；若用户需要放大截图才能看清这些数值，直接判失败。
- **固定牌桌类游戏的计数优先级必须服从对局语义（强制）**：不是所有计数都同权。直接决定阶段推进、结束阈值、公共资源耗尽或胜负触发的计数，必须贴近对应主交互区并保持强可读；只是重复表达固定槽位、小数量手牌或低风险辅助状态的计数，默认不得常驻抢 HUD 权重。像 Fantasy Realms 的公开弃牌 `9/10` 属于结束进度，应放在中央公共区上方；手牌固定 7 槽且可直接数清时，不应再常驻 `7/7`。
- **固定牌桌类游戏的桌面进行页禁止描述性正文常驻（强制）**：PC 进行页中的常驻文字默认只能承担 `名字`、`数值`、`回合/阶段短标签`、`必要动作标签` 四类职责；禁止出现整句解释、策略建议、规则摘要、观察者说明、复盘提示或任何“告诉用户现在该怎么理解画面”的描述性正文。若某段文字去掉后不影响用户识别谁在行动、哪里能点、当前资源还剩多少，就说明它不该常驻在桌面进行页。
- **进行页容器数量必须服从主交互对象（强制）**：当主内容已经是牌桌、棋盘、手牌带、弃牌河这类强视觉对象时，不得再为每组辅助信息各套一层同等级“方框/面板/卡片”来争夺注意力。若某个信息块不是当前操作必需，也不是独立流程容器，就应优先并入角标、短标签或计数，而不是再加一个完整框体。验收时必须反问：用户第一眼看到的是否仍然是主交互对象，而不是一圈解释面板；如果后者更抢眼，直接判失败。
- **固定牌桌类游戏的桌面进行页禁止并列厚容器（强制）**：在 PC live 牌桌里，`中央公共区`、`底部手牌区`、`顶部/侧边 HUD` 的层级必须明显区分。允许存在桌面底色、边缘 HUD、必要的局部承托，但禁止把弃牌区、手牌区、分数区、回合区都做成同厚度、同底色、同圆角的并列大框，否则视觉上会退化成后台表单页而不是牌桌。只要用户第一眼先看到的是几块大色块而不是牌本身，直接判失败。
- **固定牌桌类游戏的 PC 进行页默认要验“近终盘代表态”（强制）**：桌面进行页若存在明显的阶段密度变化，默认不能只用开局或空场景截图验收。至少要再补 1 张“临近结束但仍在进行中”的代表态，优先选最能暴露信息密度问题的时刻，例如高弃牌数、多人局、手牌已满、公开区接近阈值。允许使用 `TestHarness`、场景注入或等价状态构造直接到达该代表态；禁止把“真实手打到那一步太慢”当成不补这张图的理由。
- **单一合法结果且无显式放弃语义时禁止继续弹选择层（强制）**：这条只适用于已经没有可见对象选择、目标选择、支付对象、顺序或数量决策的固定结果收口。如果当前仍需要玩家选择一个卡牌、骰子、房间、角色、目标或其它实体，即使候选只有 1 个，也按“唯一目标仍然必须点选”处理，不能自动代选。若规则文本明确允许放弃、跳过或在唯一候选与“不做”之间二选一，也必须保留该选择入口。验收时至少证明：① 权威文本里是否存在显式放弃语义；② 单候选入口到底是固定结果收口，还是仍有对象/目标选择。
- **`skip / 让过` 不等于整条链必须立即无 prompt（强制）**：若规则语义只是“放弃当前这一步机会”，但当前状态后面仍有合法 follow-up reaction / response / afterScoring 触发，那么 UI 在 `skip / 让过` 后可以合法切到下一层 prompt。此时验收不能机械要求 `interaction.current == null`；真正要看的，是旧 prompt 的标题、按钮、计数和辅助条是否已经从 DOM 与视觉上退场，只留下新的那一层交互。
- **私有/owner-only prompt 必须在恢复态保持同一归属（强制）**：凡交互只应由单一玩家看到或操作（如私有检索、顶牌重排、owner-only extra action、只属于某一玩家的 reaction/response），验收不能只证明“首次出现时归属正确”。至少还要补一条真实 `hidden -> visible -> manual-resync` 或等价恢复态链，证明：① 拥有者页恢复后 prompt 仍在或仍可继续；② 非拥有者页不会接管控制权、不会被错误拉进 waiting/prompt；③ 收口后两页都无残留 overlay。禁止把这类恢复态串页问题留到 transport 层再模糊兜底。

- **后台与工作台文案默认中文（强制）**：后台管理界面、Flowise 工作流页、AI Repo Workbench、菜单项、按钮、空状态、提示语、对话框标题等面向终端用户的 UI 文案，默认使用自然中文。禁止用英文名、英文按钮、英文空状态临时占位后长期保留；若确需保留英文术语，必须确认该词没有稳定中文译法，或用户明确要求保留原文。
- **禁止把实现细节直接写进用户 UI（强制）**：用户可见文案只能表达当前产品状态与下一步动作，不能暴露“真实进度 / 伪进度 / 等待原生返回 / 接口尚未返回 / 本地缓存 / 降级逻辑 / 技术限制”这类实现层解释。若当前阶段没有准确百分比，就保持中性状态文案或纯视觉 loading，禁止再补一段工程说明来自我辩解。
- **扫光只给图片加载用，不给骨架占位用（强制）**：`shimmer / sweep / atlas-shimmer / 扫光` 的唯一默认语义，是“当前画面里这个正式图片对象已经存在，但图片/图集/媒体资源还在加载”。它不是通用骨架皮肤，更不是流程占位装饰。
- **正式图片加载态默认必须用扫光（强制）**：当界面已经进入正式布局，但卡牌、头像、棋盘块、图集切片或其它正式图片资源尚未完成加载时，默认必须显示与目标轮廓一致的扫光加载态；禁止直接裸露纯色底块、纯色贴片、深色占位面或静态空框来冒充“加载中”。只有两类例外：① 权威视觉稿明确要求静态占位；② 当前对象本身就是不可见背景预热，用户不会把它当成正式对象。若加载态是图片型对象，就必须先看到对象轮廓，再看到扫光通过，而不是先看到一块纯色板。
- **未来对象 / 空槽位 / 流程预留位禁止套扫光（强制）**：不得把 `未来可能出现的弃牌位`、`尚未打出的卡槽`、`接下来也许会有的候选项`、`为了发牌/入场做气氛的预留位置`、`当前规则语义上仍为空的区域` 伪装成 `atlas-shimmer`。这些对象如果现在并不是真实图片加载中，就只能表现为空态、留白、静态装饰或明确的正式空槽，不得叫“加载中”。
- **Toast 文案最小化（强制）**：Toast 默认只允许一句结果/错误信息，禁止“原因 + 过程 + 后续说明”三段式解释。除非用户明确要求，否则不要在 toast 里追加“系统会继续观察”“建议通过反馈入口提交问题”这类说明性文案；需要详细解释时应放到日志页、帮助页或可展开详情中，而不是 toast 正文。
- **临时/瞬态 UI 不得挤压已有布局（强制）**：攻击修正徽章、buff 提示、倒计时标签等"出现/消失"的临时 UI 元素，必须使用 `absolute`/`fixed` 定位，禁止插入 flex/grid 正常流导致其他元素位移。若需占位，必须在初始布局中预留固定空间（如 `invisible` 占位符）。
- **Flex 容器可滚动子元素必须加 `min-h-0`（强制）**：在 `flex-col` 容器中，使用 `flex-1 overflow-y-auto` 的子元素**必须同时加 `min-h-0`**。原因：flex 子元素默认 `min-height: auto`（内容撑开），导致 `overflow-y-auto` 不生效，内容被父级 `overflow-hidden` 裁剪而非滚动。同理，`flex-row` 容器中横向滚动的子元素需加 `min-w-0`。

  - ✅ `<div className="flex-1 min-h-0 overflow-y-auto">` — 正确，可滚动
  - ❌ `<div className="flex-1 overflow-y-auto">` — 错误，内容溢出时被裁剪而非滚动
- **数据/逻辑/UI 分离（强制）**：UI 只负责展示与交互，业务逻辑放在引擎/系统/领域层，数据定义与配置（manifest、常量表、资源清单、文案 key）用纯数据文件维护。
- **派生 UI 状态同步必须幂等（强制）**：当 UI Context / React state 只是从权威游戏状态、路由、配置或服务端快照派生出来的展示态时，默认优先直接派生，不要复制保存；确需同步到 Context 时，写入入口必须先比较内容签名，内容不变不得调用 setter，setter 自身也必须保持幂等。禁止把 `useEffect + new Set/new Array/new Object` 当作无条件同步模板，否则联机刷新、重连或父级新对象引用会把同一现实状态反复写入，引发级联刷新或 React 最大更新深度问题。
- **交互语义单一真值（强制）**：`可用 / 已用 / 不可用 / 可选目标 / armed` 这类视觉反馈必须绑定真实业务语义，不能在 UI 层复制一套近似判断。若领域层已有 `validate(...)`、统一可用集合或查询函数，组件只能消费这些结果，不能再凭 `isMyTurn && !used && owner===me` 之类局部条件单独推导一套描边/发光/徽记。
- **视觉态与触发方式分离（强制）**：`能不能做` 与 `怎么触发` 是两件事。可以因设备差异改变触发方式（例如 touch 端先 armed 再激活），但不能因为触发方式变化而改写“当前是否可用”的视觉态来源。前者属于交互层，后者属于语义层，必须分离。
- **视觉报障不得先归结为“用户看错”（强制）**：当用户反馈“看起来像另一张牌 / 看起来进了弃牌堆 / 看起来没贴回面板”时，不能直接把用户判断当最终根因，也不能直接降级成“看错了”。必须同时看稳定态截图、DOM 标识与权威状态字段，明确区分“视觉误导”与“状态错误”。
- **Inspect / 放大镜按钮状态层隔离（强制）**：卡牌、随从、基地、弃牌堆等实体上的 `inspect` / 放大镜按钮，禁止挂在承载 `ring`、`shadow`、`opacity`、`grayscale`、`scale`、`rotate` 等状态视觉的同一 DOM 层内。放大镜按钮必须是该状态层外的独立悬浮兄弟节点，默认只拥有自己的固定底色与 hover 态，不得跟随实体的“可选/已选/不可用/高亮/武装”视觉态一起变色、变描边、变透明、变灰。只要用户反馈“按钮也跟着描边/变色”，默认先检查 DOM 层级，而不是先调颜色值。
- **共享 FAB / HUD 面板锚点按面板类型分流（强制）**：`undo`、确认提示、短说明这类短面板，默认使用“当前按钮自身”作为垂直锚点；`action-log`、长列表、滚动日志这类长面板，默认使用“展开列 / 按钮列 referenceRect”作为垂直锚点。**禁止**把所有弹出面板统一绑到同一套垂直对齐算法，否则很容易出现“修好短面板后把长面板改歪”或“为恢复长面板又把短面板拖到兄弟按钮层级”的回归。只要改动共享 FAB / HUD 锚点逻辑，必须同时检查至少一个短面板场景和一个长滚动面板场景。
- **操作日志和撤回统一归悬浮球承载（强制）**：本项目的行为记录、操作日志、撤回入口已经由通用 `GameHUD` / FAB 悬浮球统一承载。具体游戏 Board 默认只接入 `ActionLogSystem`、`UndoProvider` 和必要状态，不得在牌桌主界面、侧栏或底部区域重复实现日志面板、撤回面板或“最近操作”列表。只有当某条日志本身就是当前规则结算的主结果承接时，才允许在主视线区域展示对应结果本体；这不等于复制悬浮球里的完整日志。
- **按钮文案短且尺寸稳定（强制）**：按钮不是标题栏，也不是规则说明容器。右侧 rail、横幅、工具按钮、页角按钮、小型 CTA 这类小槽位默认只写 2-5 个中文字符的动作名或对象名，例如 `剧本`、`关闭`、`确认`；剧本编号、章节名、长标题、验收语义和说明句只能放在内容标题、邻近状态、tooltip、aria-label 或阅读页正文里，不得拼成 `剧本1查阅` 这类长按钮。只要真实截图里按钮因文字换行、撑宽、挤压相邻控件或改变固定槽位，就按 UI 失败处理，不能用“热区仍可点”放过。
- **业务逻辑不得当作玩家 UI 正文（强制）**：领域状态、规则流程、测试裁决、实现原因、验收结论、系统决策、素材来源、OCR / 转写状态、真相源可信度、翻译状态、测试 evidence 状态和文件路径都只能先被提炼成玩家此刻需要看的对象名、数值、短状态、动作入口或阅读器内容；不得原句搬到牌桌、阶段横幅、剧情幕、按钮、状态条、标题副行或常驻 HUD。像“英雄和叛徒分别阅读自己的剧本书正文”“按已发现预兆数掷骰，5+ 作祟”“系统已锁定某剧本”“setup 队列已准备”“本地规则源正文 / 正式中文转写”“官方 If You Win 原文 / 正式翻译”这类规则/业务/来源句，只能进入录入合同、剧本书正文来源审计、规则书、帮助层、tooltip/aria、后台调试或测试断言；主 UI 应改成 `作祟开始`、`剧本已切换`、`预兆 3`、`剧本` 这类短承载。若规则句描述的是阶段变化，先实现一次性流程承接；若描述的是长期可查信息，放进阅读器/帮助层；若只是开发来源或录入状态，默认不上屏。每次新增玩家可见文案前必须先问：这是玩家当前要读的状态/动作，还是业务逻辑/开发来源解释；后者默认不上屏。
- **剧情幕 / 阅读承接可见文字不得小于 12px（强制）**：开局电影字幕、作祟剧本阅读承接、终局朗读、重大阶段横幅和主 HUD 里，只要是玩家能看见的中文/英文文字，最低字号就是 `12px`；眉标、章标、页脚、装饰性短字、状态标签和按钮副文案都算可见文字，不能用 `8px/9px/10px/11px` 当“氛围小字”。如果某段字只是装饰而不需要玩家读，就改成非文字装饰或移除，不要把可读文字缩到注脚级别。

### 1.1 游戏内 UI 组件单一来源（强制）

> **同一类 UI 功能在每个游戏中只允许有一个组件实现**，所有场景必须复用该组件，禁止新建功能重叠的组件。

- **卡牌展示/选择 UI**：每个游戏只允许一个卡牌展示组件，所有卡牌展示场景（弃牌堆查看、弃牌堆出牌、reveal、卡牌选择交互）必须通过该组件实现。
  - SmashUp：`PromptOverlay.tsx`（通过 `displayCards` prop 支持纯查看和选择两种模式）
  - 新增卡牌展示场景时，必须扩展现有组件的 props/模式，禁止新建 `CardStrip`/`CardList`/`CardReveal` 等重复组件。
- **卡牌放大/详情 UI**：统一使用 `CardMagnifyOverlay`，禁止新建放大弹窗。
- **参考卡/帮助卡的大图查看也归入放大详情 UI（强制）**：玩家参考卡、帮助卡、规则卡、提示卡这类运行时放大查看，必须沿用 `MagnifyOverlay` / `CardMagnifyOverlay` 一致风格，禁止再套一层厚边框、大圆角说明盒或额外解释壳。
- **运行时持有区不得为过门禁发明伪常驻焦点牌（强制）**：当用户实际持有的是一组真实卡牌/道具/预兆时，默认应直接展示这组真实对象本体，并通过分排、分组、尺寸、滚动方式解决可读性问题；禁止为了“至少有一张看得清”发明规则里不存在的常驻主卡位、焦点卡、当前选中主牌或等价的伪状态容器。只有当规则本身真的存在“当前装备 / 当前武器 / 当前激活卡”这类正式主对象时，才允许常驻单独主卡位。
- **运行时持有区/手牌区的卡牌尺寸在同一状态下必须稳定（强制）**：同一运行态里，同一持有区/手牌区的真实卡牌，默认必须共用稳定尺寸；不得因为某一排、某一列、某一类别当前数量不同，就把那一组牌单独放大或缩小。若当前总量上升，只允许整块持有区统一降一个尺寸档位，不允许出现 `上排大、下排小`、`物品牌大、预兆牌小` 这类跳变。
- **分排本身已表达类型时，不得再叠加重复类型说明（强制）**：如果运行时持有区已经用稳定的上下排、左右栏或其它固定空间分区表达了“这一排就是物品 / 这一排就是预兆 / 这一列就是装备”，默认不得再在每一排前重复加 `物品 / 预兆 / 装备` 这类说明标签，也不要再补数量徽记、解释字样或二级标题去重复讲同一件事。类型语义应优先由位置分区承担，文字只留给对象本体。
- **“成熟游戏做法”默认指商业成品，而不是解释性原型（强制）**：当用户要求“参考成熟游戏”“像成熟游戏一点”“商业游戏那样”，默认应理解为参考已经上线或正式发行的商业游戏成品里对同类对象的摆放、露边、重叠、点选和放大处理方式，而不是参考管理后台、教学原型、演示样机或为了讲清逻辑而额外加的说明块。若某个 UI 方案主要靠解释字样、类型标签、焦点主卡位或额外壳层才成立，默认判为不符合这条要求。
- **真实持有物优先吃空间（强制）**：如果运行时左栏/底栏里同时存在“真实持有物”与“位置摘要 / 属性壳层 / 帮助入口 / 次级工具按钮”等辅助对象，当两者争空间时，默认先收辅助壳层的宽度、padding、标题高度和按钮占位，再决定是否继续压缩真实持有物。禁止把真实持有物先缩成难辨识的小片，再保留一组更完整但次级的辅助壳层。
- **教程中的对象选择必须高亮对象本体（强制）**：教程要求玩家选择卡牌、房间、骰子、棋子、地图区块或其它可见游戏对象时，必须给该对象本体一个完整、对称、可读的选中/可选高亮；不得用动作按钮、整片容器、角落圆点、小徽记、右侧列表或文本说明替代对象本体高亮。若后续还要点“使用 / 确认 / 继续”，文案必须明确写成“先点对象本体，再点后续动作”。
- **详情预览不继承禁用弱化（强制）**：卡牌、物品、预兆、帮助卡等对象即使在持有区里因已用/不可用被弱化，放大预览或详情 overlay 也必须保持可读；禁止把 `opacity / grayscale / blur / disabled overlay` 这类状态层继承到预览卡面，导致玩家看不清正式素材。
- **阻塞式发现/投骰/改骰必须按步骤截图验收（强制）**：发现牌、事件牌、投骰、重投、改骰这类会阻塞流程的 UI，不得只用最终摘要或单张结果图验收。最低截图链应覆盖：触发对象高亮、阻塞结果主体、可改/可选对象高亮、对象本体选择、落定后的结果；缺任一关键阶段，只能称为局部通过。
- **重大阶段揭示采用商业游戏式渐进披露（强制）**：作祟开始、终局触发、阵营目标改变、Boss/怪物登场这类会改写胜负目标或行动规则的阶段切换，先判断信息职责。如果玩家只是需要知道“阶段已变、详情在既有剧本/规则入口”，默认使用**可关闭的非模态阶段横幅（stage-change banner）**：短条/徽章级强阶段信号 + 一句事实状态 + `关闭`，例如 `作祟开始，剧本已切换`。如果游戏已经有常驻剧本书/规则书入口，横幅不得再放第二个“打开剧本书”按钮，也不得伪装成流程面板、action panel、步骤清单或规则摘要墙；如果流程已经在状态变化发生时承接过剧本/规则页，横幅也不得再写 `可以打开` / `可查阅` 这类动作提示。只有规则明确要求“当前必须读完/确认某个阻塞内容才能继续”时，才使用阻塞式 overlay 或手动继续按钮；否则关闭横幅即可回到牌桌后续动作。
- **重大阶段横幅不得承载规则细节（强制）**：规则步骤清单、公开/私密边界、阵营目标分读、隐藏身份说明、设置队列、秘密目标和胜负条件不得进入阶段横幅或常驻主 HUD。详细规则、目标、秘密边界和设置流程进入剧本书、规则书、帮助层或后续专门的目标/动作 UI。端到端截图必须覆盖 `阶段横幅出现 -> 既有剧本/规则入口仍可手动打开 -> 关闭阅读层后横幅仍在 -> 玩家关闭横幅后才进入牌桌后续动作`；只有一张弹窗图，或把规则流程写成主屏面板，都不得称为流程验收。
- **连续操作文案必须有中间态截图（强制）**：教程或提示文案只要写了“先点 A，再点 B”，验收就必须证明 A 被选中后的中间状态和 B 的可用状态。只给 A 点击前与 B 执行后的截图，不能证明玩家知道“选中后下一步在哪里”。如果测试里实际使用了某个可选能力、道具、重投或确认链，而画面教程文案没有教这一步，测试通过也不得算教程截图验收通过。
- **首帧素材门禁优先于默认样式（强制）**：游戏页若依赖正式图集、牌背、房间牌、骰子皮肤或阻塞式发现牌，首帧必须等关键素材就绪，或显示明确 loading/扫光/转圈。禁止先显示默认样式、错图、纯色占位或布局跳位，再在玩家眼前闪成正确样式。
- **判定标准**：新增 UI 组件前，必须先搜索同游戏 `ui/` 目录下是否已有功能相似的组件。如果已有，必须通过扩展 props 复用，不得新建。

#### 1.1.1 选择型 Prompt 可用性门禁（强制）

- **多对象动作必须展示完整操作链（强制）**：交易、支付、交换、治疗、定向攻击这类需要同时选择 `对象/资源 + 目标 + 确认` 的动作，必须在真实交互槽位展示短流程，例如 `交易：绳索 -> 某玩家` + `点交易确认`。端到端验收必须真实点击对象、目标和确认按钮；只证明确认按钮能靠默认选中直接提交，不算覆盖了这个交互。若对象或目标还没选齐，首次确认只能显性化选择流程或提示缺项，不能静默用系统默认项提交不可逆结果。
- **多对象动作只能有一个可见流程提示（强制）**：当交易、支付、交换、治疗、定向攻击已经用横幅或主交互槽位展示 `对象 -> 目标 -> 确认` 时，状态区、房间焦点、快捷按钮和移动端摘要不得再写另一套“请选择 / 先选 / 再选 / 确认”流程文案。其它区域只允许表达归属、可用对象数量或结果反馈；若截图里同一动作同时出现两套流程提示，判为未达标。
- **少量候选禁止堆辅助按钮**：当多选 prompt 的真实候选只有 1-2 个时，默认不得再显示 `全选`、`取消全选`、重复说明文案或其他不会降低操作成本的辅助按钮。此时主界面只保留标题、候选本体、必要的确认/跳过入口。只有候选数足以让批量操作明显省步骤时，才允许显示 `全选/清空` 一类工具按钮。
- **标题 / 候选区 / 确认区必须分层**：卡牌/基地/随从选择 prompt 必须把标题、候选内容、确认动作做成可一眼区分的独立区域；禁止把标题压在棋盘本体上、把确认按钮悬在候选区之外、或让用户在一张图里难以判断“当前在选什么”和“下一步该点哪里”。
- **紧凑 prompt 必须压住背景焦点**：当 prompt 已收成 1-2 个候选的紧凑模态后，背景棋盘高亮、HUD、浮动按钮和其它远景元素不得继续与候选本体抢第一视觉焦点。最低要求是：主遮罩足以压暗背景，模态背后要有独立的局部压场层或等价手段，让用户第一眼先看到标题、候选和确认区，而不是先被基地描边或角落控件吸走注意力。
- **owner prompt 激活时不得继续暴露外围壳层噪音控件（强制）**：当当前玩家自己正在处理 prompt（无论是 overlay、棋盘直选还是手牌直选），主视觉必须只服务当前这一步选择。最低门禁不是“结束回合按钮先藏掉”就算完成，而是**所有会被误读成另一组并列入口的外围壳层都要一起退场或降到只读背景**。至少包括：① 右下 `结束回合` 大按钮、额度徽章、显隐切换；② 当前 owner prompt 不再需要的牌库/弃牌/rail 工具入口；③ 会被读成控制入口的记分板、调试浮球、设置浮球或其它全局工具。允许保留的只有与当前 prompt 语义直接相关的对象本体、最小必要状态提示，以及不会抢主焦点的弱背景信息。禁止把“当前该先做出的选择”和“别的可点控件”同时留成两组主焦点。
- **棋盘直选高亮必须等于真实可落点**：当界面不走 prompt、而是直接进入棋盘直选时，基地/随从/目标的高亮范围必须与命令校验的合法落点完全一致。禁止 UI 先把更多对象亮成可选、点击后再靠 toast 或 validator 拒绝；若存在基地限定额度、同名额度或力量限制，前端高亮必须先按这些约束收窄，再让用户点击。
- **热切换 prompt 禁止旧内容残留**：同一 overlay 容器承载多步交互时，第二步内容出现前，第一步标题、按钮、勾选数、等待态必须先从 DOM 和视觉上消失。禁止因为动画退场、本地状态复用或同 id 重渲染，把上一层 prompt 的文案/计数残留到下一层截图里。
- **同批 reveal 与 prompt 不能双层同屏**：当当前玩家的 prompt 已经直接承接同一批 reveal / deck-top 卡牌时，非阻塞 reveal 浮层必须退场或被抑制，不能继续与 prompt 重复展示同一批卡面与标题。否则截图会把单一流程拍成两层候选，直接伤害可用性。
- **展示型 overlay 不得伪装成整屏可操作层**：若 reveal / spotlight / 说明浮层的语义是“展示型、非阻塞、可继续操作”，整屏根容器默认必须 `pointer-events-none`，只允许最小必要交互区（例如关闭按钮、卡牌本体放大入口）恢复 `pointer-events-auto`。禁止再用整屏 `onClick`、整屏 backdrop 点击关闭或其它会抢走底层主操作点击的实现；否则用户会把展示层误读成新的 prompt/按钮墙。
- **特写生命周期必须按语义分流（强制）**：① 瞬时反馈，例如普通出牌动效、飞牌、飘字、分数飞行和大杀四方行动卡打出展示，继续走 FX / animation 自动退场，不得升级成“看清后可关闭”；② 短暂展示，例如 DiceThrone 自建卡牌展示，按游戏既有合同保留短 timer 自动关闭，除非具体规则或用户故事把它改成阻塞阅读；③ 阻塞阅读 / 复盘 / 确认型特写，例如小黑屋发现牌展示队列、发现牌同屏骰盘结算、必须读懂后才能继续的揭示或技能结算，必须让玩家用明确关闭按钮或继续按钮收口，且 E2E 要覆盖连续多个特写逐个读完后再继续。剧本书 / 规则书 reader 属于长文阅读界面，不能拿“状态变化承接剧本书、翻到末页、关闭”冒充卡牌/发现特写队列验收。
- **特写提示不得使用 AI 过程话术（强制）**：这条只约束玩家可见文案，不改变特写生命周期。需要明确关闭时，按钮只能写玩家动作短语，例如“关闭特写”“继续”“返回牌桌”；“看清后可关闭”“阅读后关闭”“确认是否受影响”这类给 AI 或测试人员的验收话术不得进入按钮、提示条、队列状态或截图标签。
- **审查结论不得作为玩家文案（强制）**：测试、规则改造或截图审计里可以讨论“上屏 / 不上屏 / 前景 / 不暴露 / setup 队列”，但这些词只能出现在反例或禁词清单里，不能原样进入玩家 UI。写入玩家 UI 前必须先问“商业成品会不会把这句话放在主屏”：主屏通常只能改成玩家动作短语，例如“打开剧本书”“继续牌桌”“关闭特写”；“公开读……”“不要公开谁是叛徒”“各自阅读目标 / 秘密规则”这类规则执行细节只能放在规则书、剧本书、帮助层或测试断言里，不能作为常驻牌桌 UI。本地化文件要作为玩家文案源接受禁词扫描，而不是把内部结论藏到 i18n 里。
- **缺素材不是玩家状态（强制）**：正式对局缺少正面图、裁片或图集映射时，不得在牌面、按钮、状态条、sr-only 或截图标签里显示 `缺正面`、`front missing`、`缺图` 这类排障词。玩家 UI 最多用牌背、对象名和类别做临时可玩承接；资源缺口必须进入 intake、manifest、审计 evidence 或开发日志，并向用户索要素材或锁定补源路径。只改 UI 降低存在感不能称为素材问题修复。
- **规则能力按钮写玩家动作（强制）**：规则允许某角色“忽略 / 跳过 / 免疫”某效果时，按钮和结果摘要必须从玩家视角命名，例如 `跳过事件`、`不触发房间效果`；禁止把规则分析句或内部摘要压缩成 `叛徒忽略事件` 这类主 UI 小字。
- **小字不能承担交互（强制）**：声明、跳过、确认、取消、下一步、模式选择、筛选这类真实动作控件，不能做成透明背景小字、注脚、弱标签或普通状态文本。最低门槛是 44px 级命中区、可见按钮边界/底色、hover/focus/选中反馈，并在整屏截图里能被玩家一眼识别为可点控件。若想保留小字，它只能是提示，不得绑定主流程点击。
- **批量重排类交互禁止枚举结果墙**：当交互本质是“排序/分堆/放顶放底/任意顺序”时，不得把所有排列结果直接铺成按钮墙。应优先提供可编辑的线性工具面板，让用户操作对象本体，再通过确认提交最终顺序。
- **线性重排编辑器按“动作数”审可用性，不按“展示卡数”误判**：当 prompt 的主体是被 inspect/reveal 的卡面本体，而真正可执行操作被收敛为少量工具按钮（例如 `前移/后移/移到底/确认`）时，审查“选项太多”必须按显式动作控件数量与层级来判断，不能把 3-5 张被编辑对象本体误算成 3-5 个独立候选按钮。只有当编辑器把每种结果、每张卡、每个位置都额外展开成一堵可点按钮墙时，才算违背可用性门禁。
- **`skip / 让过` 后允许合法切到下一层 prompt，但旧层必须退干净**：若规则语义只是“放弃当前这一步机会”，而后面仍存在合法 follow-up reaction / response / afterScoring 交互，那么 UI 在 `skip / 让过` 后可以直接切到下一层 prompt；这不算 UX 错误。真正的错误是旧 prompt 的标题、按钮、计数、浮动操作栏或 overlay 还和新 prompt 同屏残留。验收时必须同时看两点：① 下一层 prompt 是否确属合法链路；② 旧层内容是否已经从 DOM 与视觉上退场。
- **`skip-only` 的手牌直选 prompt 不得继续暴露伪候选（强制）**：当 `targetType='hand'` 的 owner prompt 最终只剩 `skip / 放弃 / 让过` 一类辅助动作、已经没有任何合法手牌或泰坦候选时，手牌区必须一并退场，只保留标题与最小必要的 skip 按钮。禁止把普通手牌继续留在屏幕上，让用户误读成“这里还有一张可以点的牌”。若仍有至少一个真实候选，才允许保留手牌区承接点击。
- **手牌直选 prompt 只允许展示真实候选卡，不得把无关手牌一起摆成“额外选项”**：当 owner prompt 的 `targetType='hand'` 仍有 1..N 个真实 `cardUid` 候选时，手牌区只能展示这批 prompt option 对应的候选卡本体；与本次 prompt 无关的普通手牌必须隐藏或退成不可见背景，不能继续与 skip/确认按钮并列出现。否则用户会把“当前只是在这几个候选里选一张”误读成“整手牌都还能点”。
- **setaside 泰坦反应 prompt 必须保留真实本体（强制）**：当 owner prompt 的目标是 `setaside` 泰坦反应 / 进场选择时，外围壳层可以退场，但当前可触发的泰坦本体必须继续留在主视觉里，并且只能保留与该 prompt 直接相关的 rail / skip / 确认动作。禁止把 prompt 文案保留下来却把实际可点击泰坦一起藏掉，也禁止把 deck / discard / 结束回合 / turn notice 重新拉回到同屏里制造第二焦点。
- **非 owner 等待页只能保留单一等待语义**：当当前页面并不拥有该 prompt，只允许展示一处明确的等待状态（例如 `等待调整` / `正在等待 {{player}}`）。禁止同时保留重复等待文案、禁用版编辑工具、禁用确认按钮，或任何会把等待页误读成“我也能操作”的控件噪音。
- **非 owner waiting prompt 不得继续保留原 prompt 标题/候选壳层**：如果当前页只是等待别人处理，默认不再显示该 prompt 的原始标题、候选卡带、候选列表容器或其它“正在选什么”的主内容骨架；否则用户会把等待页误读成“我也在这一步里”。唯一例外是 deck reorder 这类明确需要展示 inspect 对象本体但不暴露操作工具的场景，此时必须显式标注为只读等待态。
- **响应窗口 waiting family 同样按单一等待壳层处理**：像 `Me First! / 计分后响应` 这类 response-window overlay，若当前页不是 active responder，也不得继续显示原始标题、让过按钮、响应进度点阵或任何“大卡片式操作面板”。非响应者页面只能保留一条等待文案或等价的紧凑 waiting shell；同时右下 `GameHUD/FAB`、设置/聊天/反馈这类全局工具入口也必须退场，避免等待页出现第二视觉焦点。否则用户会把合法等待态误读成自己也能参与的响应界面。
- **棋盘 blocked waiting 不得继续暴露结束回合配套控件**：当 `Board` 只是因为别人拥有当前交互而进入 blocked waiting 时，结束回合区只能保留一个被动状态牌（如 `等待对方操作`）。禁止继续同时显示额度徽章、显隐切换、禁用版结束回合配套控件，避免把“当前只是等待”误读成“这里还有一组可操作入口”。若用户此前手动隐藏了结束回合 UI，blocked waiting 仍必须保留状态牌，不能把等待语义一起隐藏掉。

### 1.2 通用 UI 交互 Hooks（强制复用）

> 位于 `src/hooks/ui/`，跨游戏复用。新增交互行为前必须先搜索此目录。

| Hook | 用途 | 说明 |
|------|------|------|
| `useHorizontalDragScroll` | 横向卡牌 / 对象横排浏览增强 | 滚轮纵向→横向转换 + 鼠标拖拽左右滑动。所有横向卡牌列表/弃牌堆浏览必须使用，禁止手写 wheel 事件监听。不要用于同时需要上下滚动的数据表、审查表或日志表；这类表格必须保留普通滚轮上下、横向滚动条 / 触控板横向手势 / `Shift + 滚轮` 左右浏览。返回 `{ ref, dragProps }`，`dragProps` 需展开到容器元素。 |
| `useTouchLongPress` | mobile long-press interaction | Provides touch long-press trigger, move-cancel, and post-long-press click suppression. Returns pointer handlers, `clearLongPressState`, and `shouldBlockClick`. |
| `useTouchInspectGesture` | coarse-pointer inspect gesture | Combines coarse-pointer detection with long-press inspect behavior. Use when touch devices need long-press preview while keeping tap for the primary action. |
| `useArmedActivation` | armed tap-to-activate interaction | Provides "first tap arms, second tap activates" state for touch-first UIs. Use when coarse-pointer devices need explicit selection before firing a primary action. |
| `useDeferredRender` | 延迟渲染 | 避免首帧闪烁 |
| `useDelayedBackdropBlur` | 延迟毛玻璃 | 毛玻璃效果延迟启用，避免动画期间性能问题 |

### 1.3 UI 动画设计入口（强制）

> 完整规范已拆到 `docs/ai-rules/ui-animation-patterns.md`。本文档只保留入口，避免 UI 总览继续承载动画实现百科。

- 涉及命令验证的动画必须由数据/状态变化驱动，不能在 `onClick` 里先播动画再等命令结果。
- 涉及掷骰、翻牌、抽牌亮相、奖励骰、结算浮层等“结果揭示”时，必须使用独立事件身份信号，不得只靠结果值判断是否重播。

## 2. 多端布局策略入口 (Multi-Device Layout Strategy)

> 完整规范已拆到 `docs/ai-rules/ui-responsive-layout.md`。本文档只保留入口，避免 UI 总览继续承载双端布局百科。

- 双端并行不是双份 UI；默认一套 React UI 架构，通过 manifest、runtime viewport、终端能力和 layout preset 做条件化分支。
- 固定构图类牌桌的 HUD、固定栏位、命中区和棋盘内容可以按 `px` 设计画布 + 外层统一等比 `scale` 换算；开放式地图 / 棋盘 / 牌桌必须先铺满真实 viewport，不能把 `1920x1080` 设计稿尺寸当成页面外框；文本/按钮/表单/常规 HUD 优先 `rem/clamp`。
- 默认参考分辨率、双端架构分层、单位选择规则和固定牌桌裁决见 `ui-responsive-layout.md`。

## 3. 游戏 UI 特化范式 (Game-Centric Design)

> **⚠️ 游戏内 UI 必须遵循设计系统规范**
> 
> - **交互原则**：`design-system/game-ui/MASTER.md`（所有游戏通用）
> - **视觉风格**：`design-system/styles/` 下选择合适风格
>   - `arcade-3d.md` - 街机立体风（休闲、派对、骰子类）
>   - `tactical-clean.md` - 战术简洁风（策略、卡牌对战）
>   - `classic-parchment.md` - 经典羊皮纸风（复古、桌游模拟）
> 
> **核心要求**：游戏感 = 即时反馈 + 状态清晰 + 操作愉悦
> - 所有可交互元素必须有 hover/press 反馈
> - 禁用状态必须视觉明显
> - 动画只用 transform/opacity，时长 150-300ms

- **阶段语义先于遮挡判断（强制）**：
    - 判定“遮挡 / 压住 / 抢位 / 干扰”是否是 UI bug 前，必须先锁定当前真实游戏阶段、当前可操作对象、当前不可操作区域，以及该遮挡是否发生在玩家此刻需要操作或读取的主区域。
    - 投掷、重投、碰撞、结算等待、强制动画等阶段里，若技能区、手牌区、右侧 rail 等区域按规则暂时不可操作，短时间视觉覆盖不得直接判为“挡住可操作入口”；必须先证明它确实遮挡了当前阶段的主操作或关键反馈。
    - 禁止因为静态截图里某个 UI 元素压到非当前操作区，就擅自改容器锚点、重排主布局或迁移视觉载体；若问题本体是动画未落定、物理未停止、截图时机过早或状态判断错误，应优先修原始链路。
    - 验收截图必须说明所处阶段及当时真实可操作区域；否则不得用“看起来挡住了某区”作为修改布局的依据。

- **动态提示 UI（强制）**：
    - 必须使用 `absolute`/`fixed`，禁止占用布局空间（如 `relative/static`）。
    - 出现/消失不得挤压或移动其他 UI；新增前必须验证布局稳定性（尤其右侧栏/手牌区/技能区等核心区）。
    - **层级统一**：使用 `UI_Z_INDEX` 常量（如提示用 `UI_Z_INDEX.hint/overlayRaised`，模态用 `UI_Z_INDEX.modalOverlay/modalContent`），禁止硬编码 `z-[...]`。
    - 常用位置：顶部中央（交互选择）、正中央（等待）、手牌上方（弃牌）；默认 `pointer-events-none`（除非需要交互）。
    - 棋盘/牌桌上的阶段提示默认属于整体 HUD，而不是局部组件装饰。若提示服务整局操作流程，应挂在 HUD 层并按整体布局找锚点（如对手信息区下方、主视线中心），不得塞进骰台、单个对象、透明命中区或局部容器里造成视觉脱节。
    - **重大阶段切换必须有一次性可感知事件（强制）**：进入作祟、阵营揭示、终局触发、Boss/怪物登场、全局目标改变这类会改写玩家目标的阶段切换，必须在真实牌桌上给出短促但强烈的画面事件，例如闪烁、冲击、斜切、标题短卡、角色点名或对象本体动效；不得只靠日志新增、按钮变化、角落小字、内部状态或普通阶段标签让玩家自己猜“已经进入新阶段”。该提示必须使用短标签或短状态，不得在常驻主 UI 写整段规则说明。
    - **作祟 / 剧本目标必须落到真实玩家 UI（强制）**：翻开作祟剧本、阵营目标改变、胜负路线改变这类状态不能只存在于日志、测试 evidence、流程图、调试脚本或截图目录里。作祟刚触发的开场揭示期，主屏只需要可关闭的非模态阶段横幅、既有剧本书入口和极短暂停状态；横幅只提示“作祟开始 / 剧本已切换”这类事实状态，不解释目标、不公开秘密、不要求先读书。若作祟流程已经在状态变化发生时承接过剧本书，横幅不得再写“可以打开 / 可查阅 / 阅读开局”这类动作提示。玩家关闭横幅后，真实牌桌必须提供常驻但短的当前目标摘要、当前关键进度、当前主动作入口和可回看的剧本书 / 规则入口。完整规则正文只能放在剧本书、帮助层或临时说明层；不得把 evidence 图、调试图、流程图或“可以打开剧本书”当成玩家已经理解下一步的证据。
    - **作祟主动作必须先于剧本书（强制）**：这条只适用于作祟开场揭示已经完成、牌桌进入具体作祟行动后。作祟目标卡、剧本目标条或等价常驻 UI 的第一操作职责，是告诉玩家“现在点什么、点了会发生什么”。主动作必须直接进入或执行当前合法作祟动作；若还需要选择探索者、怪物、房间、尸体、相机等可见对象，主按钮只能进入/聚焦选择态，真正结算必须由玩家点击对象本体高亮完成。剧本书入口只能作为次级参考，不得成为作祟行动期的唯一继续路径。
    - **作祟目标选择态必须落在对象附近（强制）**：主动作点击后若进入目标选择态，真实目标对象附近必须出现短促局部引导，目标所在房间/区域必须被聚光或提亮，非目标对象和无关 rail / 普通动作入口必须降噪或退场；不得只在顶部按钮、侧栏目标卡或剧本摘要里写“点目标”，却让玩家在地图里自己找。
    - **作祟目标选择态必须有玩家退路（强制）**：进入目标选择后，顶部主动作不得继续表现成另一个可执行按钮；它必须转成“点牌桌高亮目标”这类状态提示，旁边提供明确取消入口。取消必须清空本次临时目标/武器/交换选择并回到正常牌桌，不能要求玩家猜“再点一次主按钮就是取消”。
    - **对象旁提示必须说明后果（强制）**：目标旁短提示至少要同时表达动作和对象，例如“选择邪教徒发起攻击”“点丽贝卡交换疾病”；不得只写“点这里”“目标”“选择”“开始”或只显示内部目标名。若提示需要覆盖小 token，必须优先扩大热区和外圈，不得遮住目标本体。
    - **作祟主动作不得藏在侧栏详情里（强制）**：如果作祟阶段已经改变当前胜负目标，下一步主动作必须位于牌桌主视线区或等价中央指挥槽位，不能只藏在左侧目标卡、侧栏详情、底部手牌旁的小按钮、右侧 rail 或日志旁。侧栏目标卡可以保留摘要，剧本书可以保留回看，但玩家第一眼必须先看到“现在该做什么”的主动作。
    - **作祟指挥条不得遮挡手牌/持有区/目标本体（强制）**：作祟主动作进入主视线后，仍不得压住底部手牌、持有物、右侧牌堆、左侧探索者板或当前要点的房间/怪物/相机本体。截图验收必须同时证明主动作显眼、主对象高亮可见、辅助剧本入口不抢主焦点。
    - **作祟无动作态必须解释现实缺口（强制）**：如果当前玩家暂时没有可执行作祟动作，常驻 UI 必须用短提示说明缺的是位置、目标、道具、尸体、标记、回合限制还是等待别人，不能只显示目标摘要或让玩家自行阅读长规则。提示必须是玩家语言，禁止暴露内部字段或测试口径。
    - **受击 / 伤害反馈必须绑定受影响对象本体（强制）**：攻击命中、属性损失、生命/耐久下降、精神/物理伤害这类会改变角色状态的结算，必须在受影响的角色、卡牌、棋子或 token 本体上给出短促视觉反馈；不得只靠日志、骰台结果、行动按钮、侧栏数字变化或攻击者动效让玩家推断“谁挨打了”。默认可沿用山屋口径：斜切 + 抖动 + 闪红，并用对应属性颜色显示飘字；实现层必须优先复用 `docs/ai-rules/animation-effects.md` 的通用受击组件 / FX 系统，不得在单个 Board 里临时手写一套平行 CSS 受击特效。若某游戏采用不同主题表现，必须等价覆盖“谁受影响、影响类型、数值/属性、发生时机”四件事。花费、成本、消耗、准备动作不得误触发受击反馈；它们应使用资源消耗提示，而不是伤害反馈。
    - 受击 / 伤害反馈必须是临时 overlay，不得占用正常布局空间；默认 `pointer-events-none`，不抢主交互焦点，并遵守 `prefers-reduced-motion` 降级。验收必须回到真实结算位点，证明反馈出现在受影响对象本体上，而不是只证明日志或内部状态已更新。
- **动态效果视觉提示实施规范（强制）**：
    > 当全链路审查（见 `docs/ai-rules/description-to-implementation-audit.md`）发现动态赋予效果缺少 UI 提示时，按以下规范实施。
    - **力量修正**：修正后的力量值必须与基础值有视觉区分。正向修正用绿色/上箭头，负向修正用红色/下箭头，显示格式为 `基础值 → 当前值` 或 `当前值(±N)`。
    - **持续保护/限制**：在受影响实体上显示小图标（盾牌=不可消灭、锁=不可移动、禁止=不可打出），hover 显示效果来源。
    - **基地持续效果**：基地卡下方显示当前生效的效果摘要文字（从 i18n 获取），多个效果竖向堆叠。
    - **临时 buff/debuff**：使用 `absolute` 定位的徽章/标签，附带淡入淡出动画（150-200ms），效果结束时自动消失。禁止插入正常流。
    - **条件触发效果**：条件满足时在实体上显示发光边框或脉冲动画，条件不满足时无视觉标记。
    - **附着行动卡**：随从/基地上附着的 ongoing 行动卡必须有视觉标记（如卡牌角标或堆叠指示器），hover/点击可查看附着卡详情。
    - **不确定时必须询问用户**：如果效果的 UI 展示方式不明确（图标样式、放置位置、颜色选择、文字 vs 图标），**必须先询问用户确认再实现**，禁止自行猜测。
- **视角解耦 (Scene vs. HUD)**：
    - **场景层 (Scene)**：棋盘、卡片等核心实体，需通过 `anchorPoint` 处理坐标缩放，确保跨平台逻辑一致性。
    - **UI 层 (HUD)**：状态信息、控制面板，执行 Overlay 挂载逻辑。
- **高度稳定性**：核心游戏区（棋盘/面板）**必须**使用明确高度约束（如 `h-[35vw]`）代替 `h-full`，彻底解耦父级 Flex 依赖。
- **`MobileBoardShell` 容器约束（强制）**：凡是 manifest 声明 `mobileLayoutPreset: 'board-shell'` 的游戏，Board 根容器必须跟随壳内画布高度，使用 `h-full` / `absolute inset-0` 等容器高度方案；**禁止**在 Board 根容器上写 `h-screen`、`min-h-screen`、`100vh`、`100dvh`。原因：`board-shell` 会在移动横屏下先做整体缩放，若子树继续读取原始视口高度，会导致内容实际渲染高度小于壳高度，出现底部黑边、下半截空白或布局漂移。
- **board-shell 内 HUD/Overlay 固定定位禁令（强制）**：在 `MobileBoardShell` 内部渲染的 HUD/Overlay **不得直接使用 `fixed/absolute` 作为最终定位**；必须通过 HUD portal（`HudPortal` / `getHudPortalRoot`）渲染到 `#hud-root`，脱离缩放容器。历史实现可保留，但新增/修复必须遵守该规则。
- **board-shell 下全屏 Loading/门禁锚点（强制）**：凡是覆盖全屏的 Loading（`LoadingScreen`/`ConnectionLoadingScreen`/`CriticalImageGate`）在 `board-shell` 场景必须使用 `anchor="viewport"` 并挂载到 `#hud-root`；**禁止**用 `anchor="container"` 或在 Loading 根节点强行追加 `relative`，否则会让 `fixed` 退化为容器相对定位，出现整体偏移。
- **相位敏感性**：UI 必须清晰反馈当前"游戏相位"与"操作权限"，通过高亮合规动作 (Valid Actions) 降低认知负荷。
