# UI/UX 完整规范

> 本文档是 `AGENTS.md` 的补充，包含 UI/UX 设计范式、布局策略、游戏 UI 特化规范。
> **触发条件**：开发/修改 UI 组件、布局、样式、游戏界面时阅读。

---

## 0. UI 改动分级流程（强制）

### 0.0 双端默认视角（强制）

- 现在项目默认按 **双端并行** 处理 UI：网页/PWA、App WebView、桌面、移动端都要在设计阶段被同时考虑；**禁止**把移动端当成“桌面做完再补”的尾项。
- **移动端适配不是可选项（强制）**：新增游戏、新增 Board、重做游戏主界面时，不需要询问用户“是否考虑移动端”；AI 必须默认纳入移动端方案。可以询问主使用姿态或验收优先级，但不能把移动端适配作为需要用户额外授权的工作。
- **manifest 决定的是能力边界，不是是否考虑移动**：某个游戏可以暂时声明 `mobileProfile: 'none'` 或 `tablet-only`，但共享页面、共享组件、布局壳层、交互语义仍必须避免写成只能桌面工作的死结构。
- 只要改动会进入共享层（路由页、加载页、通用组件、共享 Hook、样式 token、壳层容器），必须先问自己两件事：
  - 这套结构在桌面和移动端是否仍是同一套架构，只是条件化呈现不同？
  - 以后某个游戏从 `none` 升级到 `landscape-adapted` 时，这里是否还能直接复用，而不是推倒重来？
- **固定构图类界面** 仍以桌面版为权威基线；移动端默认做同构缩放、触控入口和局部让位，不默认重排成另一套手机稿。
- **游戏页若主使用姿态是手机横屏，则横屏是第一验收基线（强制）**：当某个游戏长期按手机横屏使用时，移动端修复默认围绕“横屏下像桌面端那样的构图与密度”收敛；未经用户明确确认，禁止把问题擅自改造成“窄布局 / 双列手机稿 / 大量留白”的路线。
- **轻微偏移优先修锚点，不优先改版式（强制）**：用户反馈“整体偏一点 / 不居中 / 像桌面端 / 不该变窄”时，默认先排查锚点、坐标系、容器宽度、scale 与 transform-origin；禁止直接通过改列数、减卡片数量、压成双列等方式把原本的横屏主版式推翻。

### 0.0 页面语义边界（强制）

- 首页/大厅、游戏页、App 壳层更新页、后台、开发工具页属于**不同语义域**。即使复用同一个 Loading/Fallback/Empty/Error 视觉容器，也必须由调用方显式传入当前页面语义，禁止沿用其他页面的默认文案。
- 文案 key 必须按页面域归属：大厅/首页优先放 `home.*` 或 `lobby.*`，游戏页放 `matchRoom.*`，App 更新相关放 `ota.*` / `nativeUpdate.*`，后台放 `admin.*`，开发工具放 `devTools.*`。**禁止**为了省事把一个页面族的 key 借给另一个页面族当默认值。
- `Suspense fallback`、路由兜底页、空状态、错误态、骨架屏是最容易串语义的区域。只要这些组件可能在多个页面复用，就必须满足二选一：
  - 默认文案是中性语义，例如“正在加载页面...”“正在准备内容...”
  - 或者组件 API 强制调用方传入 `title/description/progressText/namespace`
- 若默认值里已经包含明显场景词，如“对局”“房间”“安装新版 App”“更新后台数据”，则该组件只能在对应场景使用，不得继续作为通用 UI 容器扩散。
- 任何入口级 UI 改动后，必须反问自己：用户在“错误页面”里看到这句文案，会不会立刻误解自己已经进了另一条流程？如果会，这个设计就不合格。

### 0.0 样式任务边界（强制）

- 当任务表述是“改小一点、改大一点、调间距、修溢出、修遮挡、修错位、改视觉层级、改颜色、改圆角、改阴影”这类样式目标时，默认只允许动视觉呈现，不允许顺手改交互编排。
- 交互编排包括但不限于：入口顺序、主按钮是谁、默认展开哪一项、点击一次还是两次、弹窗从哪里触发、菜单项上下次序、常驻入口变抽屉、hover 改 click、click 改 long press。
- 如果视觉问题与交互编排耦合，必须先向用户显式确认“需要连交互一起改”，否则只能提交纯样式方案。
- **样式微调必须先锁不变量（强制）**：用户要求“调间距 / 改大改小 / 修左边距 / 修上下挤 / 修视觉密度”时，动手前必须先明确这轮哪些东西不能变。至少覆盖：滚动语义是否保留、列数是否保留、卡片/头像尺寸是否保留、主内容区宽度是否保留、主按钮和关键控件位置是否保留。没有先锁这些不变量，禁止直接试改样式参数。
- **样式/布局改动默认不得改变功能表面（强制）**：当任务目标是修视觉、布局、密度、间距、对齐、遮挡、尺寸或响应式表现时，默认只能改变呈现方式，不能改变功能表面。功能表面包括但不限于：某个功能/入口/控件是否存在、是否可见、是否可达、默认状态是什么、信息默认展示范围、交互顺序、触发条件、自动展开/自动收口、自动跳转等。**删除、隐藏、禁用、替换、改默认值、改触发路径** 都属于功能改动，不得伪装成“只是样式调整”。
- **视觉修复若必须影响功能，必须显式升级口径（强制）**：如果视觉问题和功能表面确实耦合，必须先明确告诉用户“这不是纯样式修复，而是会连功能表面一起改”，并把两部分分别验收。禁止为了恢复某个布局/历史观感，顺手删入口、藏控件、收窄可见信息或改默认行为。
- **局部修复不得擅自改变默认可见信息（强制）**：当用户点名修复某个入口、搜索、排序、间距或布局时，默认只能恢复该入口本身及其直接依赖。若实现方案会顺带改变“默认展示全部还是过滤一部分”“别人已选/已锁定/不可操作对象是否可见”“玩家状态卡/座位条/进度条是否常驻可见”这类信息范围，必须先停下询问用户。只有用户明确确认后，才允许把这类默认可见信息变化纳入同轮修改；否则只能提供低侵入入口，例如保留搜索/筛选按钮，但默认仍展示完整上下文。
- **明显问题不得靠测试断言自我授权（强制）**：如果某个断言为了让当前修改变绿，要求隐藏玩家卡、隐藏对手已选信息、删除常驻状态、遮挡主交互区、或把用户未点名的功能面改成另一套默认行为，即使测试能通过，也必须视为需求升级点而不是修复细节。最低动作是先说明“这会改变用户看到的信息/状态入口”，等待用户确认；禁止用“减负、样式、旧布局兼容”包装后直接落代码。
- **滚动列表的间距问题先保留滚动语义（强制）**：用户反馈列表“上下太挤 / 太松 / 左边距怪 / 看起来不对”时，默认目标是修正列表项之间的视觉节奏，不是追求“首屏全部显示”或“多露几项”。禁止通过改整层 inset、缩卡片/头像、改列数、压缩主内容区等方式间接改变可视密度；优先只改目标列表自身的 `row-gap`、单项内边距或局部留白。
- **滚动列表样式验收必须先对照同场景 PC（强制）**：如果同一组件同时跑在 PC 和移动端，先锁定 PC 同场景作为结构真相源，再看移动端是否只是同构缩放下的局部节奏调整。若移动端为了“修间距”把列表项显著缩小、主区被挤窄、按钮位置跟着漂移，直接判失败。
- 只要任务涉及“PC 同构”“移动端等比缩放”“手机横屏像桌面端”“双端布局策略”“到底该缩放还是重排”，必须先读 `docs/mobile-adaptation.md`，不要只凭通用 UI 审美规则判断。
- **参考图驱动的局部优化必须先抽取视觉不变量（强制）**：用户给出参考图并要求“参考这里优化”时，动手前必须明确抽取目标对象的形状/轮廓、位置锚点、色彩材质、信息层级四类不变量。禁止只保留“有一个徽章/有一个 token/有一个面板”这种抽象功能，再用泛化几何体或常见组件替代参考图中的具体轮廓语言。若证据文档宣称“已参考”，必须写清楚截图里实际对应到哪些不变量；形状不一致时只能说“未达标”，不能用断言通过替代视觉判断。

> ### 0.1 修 bug / 微调（无需额外流程）
> 修复布局错位、调整间距/字号/颜色微调、修复交互 bug 等。直接改即可。
> - **例外门禁（强制）**：只要本轮改动虽然名义上是“修 bug / 微调”，但实际上改变了用户完成这一步交互的方式，就不再按 0.1 处理，必须升级到“新增 UI / 交互模式变化”口径，并执行端到端验证与截图验收。这里的“交互模式变化”包括但不限于：用户如何发现候选、浏览候选、筛选候选、判断可操作对象、做出选择、确认提交、在多种视图间切换。禁止把“只是补了一个入口”“只是换了一种展示方式”“只是让筛选更方便”包装成普通微调以绕过 E2E。
>
> ### 0.2 新增 UI 元素（必须配合现有风格，无需读设计系统文档）
> 新增按钮、面板、提示、弹窗等 UI 元素，即使只改一个文件：
> - **必须复用同模块已有组件**（如 `GameButton`、`SpotlightContainer`），禁止手写原生 `<button>` / `<div>` 替代已有封装
> - **必须参考同文件/同模块的现有样式**（配色、圆角、间距、字号），保持视觉一致
> - **禁止引入与当前风格不一致的颜色/样式**（如现有模块用 amber 主色调，不得引入紫色）
> - **响应式适配必须保持默认视觉基线**：如果任务目标是“适配/防裁剪/防溢出/多端自适应”，默认桌面尺寸、信息层级、视觉比例必须与原版保持一致；只能在受限视口条件下做降级或压缩，禁止把原本正常视口下的卡牌、字号、间距整体改小后当作“适配完成”
> - **新增 UI 默认必须交付 E2E 截图（强制）**：只要本轮新增了用户可见的新按钮、新面板、新弹窗、新卡组/列表展示、新视觉层级，就必须附至少 1 张本轮实际核对过的端到端截图绝对路径；不能只用断言通过、DOM 存在或局部组件截图代替真实交付证据。
> - **现有组件内发生交互模式变化也算新增 UI（强制）**：新增 UI 不要求必须新建组件文件。只要在现有组件、现有弹窗、现有 overlay、现有卡牌选择器、现有列表里改变了用户的交互模式，例如新增候选发现入口、改变候选展示载体、加入筛选/搜索/排序、改变确认区结构、加入视图切换或新的可操作状态层，就按“新增 UI”处理，同样必须跑 E2E、看截图、给证据。
> - **新增 UI 的默认验证级别就是端到端（强制）**：除非用户当轮明确说“无校验 / 跳过验证 / 不跑测试 / 直接提交”，否则新增 UI 不得只停在单测、快照、组件测试或本地静态阅读。最低交付证据必须是：真实链路 E2E + 至少 1 张实际复看的端到端截图绝对路径。
> - **“新 UI”默认指新的交互 UI 类型（强制）**：当用户要求核对“新 UI”“最近新 UI”“新派系的新 UI”时，默认优先指**新的交互 UI 类型**，不是任意新内容，也不是任意新派系接入页。判定标准看的是：这一步是否引入了新的用户交互壳层/模式，例如新的卡牌选择面板、新的搜索/筛选式候选浏览、新的排序编辑器、新的多视图切换、新的 owner-only 等待壳、或新的确认/提交结构。**不算新 UI 类型**的情况包括：旧 prompt 只换了文案或候选数据、旧 overlay 仅承载了新卡牌/新派系内容、旧交互链路里新增一条规则分支、旧面板里只出现新的对象或新的能力名。若一条链路只是“新交互内容复用旧 UI 壳”，汇报时必须明确标为“旧壳复用”，不得冒充“新 UI 类型”。
> - **“新派系的新 UI”默认不含展示页（强制）**：除非用户明确点名“派系选择页 / 详情预览 / 资源展示 / 进局展示”，否则“新派系的新 UI”默认不包含派系选择页、详情页、素材预览、资源渲染图这类展示型页面；默认只统计新派系实际引入的**新的交互 UI 类型**。如果用户要看展示页证据，必须单独按展示型 UI 口径列出，不能和交互型新 UI 混表。
> - **“旧壳复用”不得拿来充数（强制）**：像旧 prompt / 旧 reaction / 旧 extra-action / 旧 reorder 壳层里，哪怕承载了新派系、新能力或更复杂的数据，只要用户完成任务的交互外形、操作节奏、可见壳层结构没有升级成一种新的 UI 类型，就只能记为“旧壳复用”或“旧 UI 承载新内容”。这类链路可以作为玩法 E2E 证据，但不能在“新 UI 截图台账”里冒充新的交互 UI。
>
> ### 0.3 大规模 UI 改动（必须先读设计系统）
> **判定条件**：涉及 ≥3 个组件文件的样式变更、新增整页/整区域布局、全局配色/字体/间距调整、新游戏 Board 搭建。
> **UI 优化任务**（布局稳定性修复、字号/间距层级调整、视觉层级重构等）也须走此流程。
>
> 必须按以下顺序执行：
> 1. **先读 Skill**：先读 `.windsurf/skills/ui-ux-pro-max/SKILL.md`。它在本项目里是 **overlay 入口**：先路由到全局 `ui-ux-pro-max` 获取通用设计建议（配色/字体/风格/反模式），再回到项目设计系统与本项目验收口径。
> 2. **再读项目自定义设计系统**：
>    - `design-system/game-ui/MASTER.md` — 游戏 UI 交互通用原则
>    - `design-system/styles/<风格>.md` — 对应视觉风格规范
>    - `design-system/games/<gameId>.md` — 游戏专属覆盖配置（若存在）
> 3. **冲突时以项目自定义设计系统为准**：Skill 提供的是通用建议，项目 `design-system/` 是权威来源；两者冲突时，以后者为准。
>
> ### 0.4 UI 重构必须端到端验证 + 端到端截图（强制）
> **触发条件**：UI 重构、全局/共享布局改动、HUD/Overlay 分层重排、壳层/缩放逻辑调整、跨页面共享 UI 组件改造。
> - **触发扩展（强制）**：凡是修改现有 UI 组件却改变了用户如何发现、理解、筛选、浏览、选择、确认当前候选或目标的方式，也按本节处理；不要因为“没重构整页”“只改了一个 overlay”“只是优化现有面板”就降级跳过 E2E。
>
> **强制要求**：
> - **必须跑 E2E**：覆盖本次改动影响的真实流程与关键 UI 交互，不得只做静态检查就收口。
> - **必须出端到端截图**：使用 E2E 产物截图作为验收证据。
> - **最终回复门禁（强制）**：只要对外说“新 UI 已完成 / UI 已验收 / E2E 已通过”，就必须同时给出至少 1 张本轮实际核对过的 E2E 截图绝对路径；没有截图路径时，不得按“已完成 UI 交付”口径收口。
> - **移动端优先**：默认至少提供 `375x812` 的移动端截图；如桌面也受影响或有额外风险，再补 `1920x1080` 桌面截图。
> - **用户显式点名截图规格时，以用户指定为准（强制）**：此处默认截图策略让位给全局 `Acceptance Artifact Scope Freeze`，不得擅自补更多视口、尺寸或局部图。
> - **验收截图默认先给整体构图（强制）**：只要目标是证明页面、弹窗、浮层、书页、HUD 或布局“整体是否对”，主截图必须优先给出包含周边上下文的整页/整屏/整容器视图，能同时看见目标元素与其所在构图关系。局部裁切、元素级截图只能作为补充排查材料，不能替代主验收图。
> - **证据直指问题位点**：截图必须能直接证明“本轮重构的 UI 位点已达标”，不能用无关页或非真实链路截图代替。
> - **横屏游戏必须覆盖横屏主链路**：若问题发生在游戏页手机横屏，截图与 E2E 必须至少覆盖“进入前/加载或选择态 → 游戏内主态”两段横屏链路，不能只给一个竖屏图或只给最终态。
> - **缩放/偏移类问题必须单独写出视觉判定**：至少说明 ①有没有缩在左上角；②HUD/主内容是否仍同坐标系；③有没有被误修成窄布局/双列路线。禁止用“元素存在”代替视觉达标结论。

## 1. 核心审美准则 (Visual Excellence)

- **深度感 (Depth)**：通过渐变、阴影、毛玻璃构建视觉层级，但需按场景分级使用：
  - **重点区域**（游戏结算、核心面板）：可使用毛玻璃 + 软阴影增强层级感
  - **一般区域**（确认弹窗、列表项）：使用纯色/简单渐变 + 轻阴影即可
  - **高频更新区域**（动画中元素、拖拽对象）：**禁止毛玻璃**，仅用 `opacity`/`transform`
- **动效反馈 (Motion)**：状态变更应有动效反馈，但需区分场景：
  - **关键交互**（确认/提交/阶段转换）：使用物理动效（弹簧/惯性）
  - **常规交互**（Hover/Focus）：使用简单 `transition`（150-200ms）
  - **高频交互**（快速点击/连续操作）：仅用颜色/透明度变化，禁止复杂动画
- **布局稳定性 (Layout)**：动态内容通过 `absolute` 或预留空间实现。**辅助按钮严禁占据核心业务流空间，必须以悬浮 (Overlay) 方式贴边/贴底显示。**
- **禁止无意义重复信息填充（强制）**：当前上下文已经明确的信息（例如当前 tab、页面标题、区块标题、卡片标题）默认不应在子内容区机械重复，除非该重复能明显提升理解效率。允许重复的场景包括：消歧、跨区块跳读、无障碍提示、风险提示、需要脱离上下文单独成立的卡片/弹窗标题。禁止的场景包括：仅为了“看起来信息更满”而重复标题、在空状态里重复当前 tab 名称、同一视窗内对同一事实做无新增价值的二次强调。示例：tab 已叫“更新”时，空状态写“暂无日志”即可；若是从外部入口打开的独立弹窗，标题写“更新”则是合理重复。
- **生图设计稿到实现必须走专项流程（强制）**：用 AI 生成设计稿、参考图或 UI mockup，并继续按该图实现时，必须先读 `docs/ai-rules/generated-design-implementation.md`。`ui-ux.md` 负责通用审美与布局原则；生成稿到实现的内容盘点、目标稿复看、几何量测、E2E 证据链以该专项流程为准。若同时存在目标稿和用户标注的错误截图，目标稿永远是语义与比例真相源，标注图只负责定位问题，不能反向替代目标稿。
- **Home V2 移动横屏必须读专项规范（强制）**：修改 Home V2 首页、详情页、纸面弹窗或相关 E2E 时，必须先读 `docs/ai-rules/home-v2-design.md`。该页面当前按移动横屏书本界面验收，PC 端通过结果不能替代移动 CSS 视口截图。
- **方向提示不等于方向约束（强制）**：当页面、模式或首页样式被定义为“强制横屏 / 强制竖屏”时，错误方向下不能只加一条“建议旋转”提示后继续完整渲染原页面。必须在路由级或页面守卫级进入明确的 wrong-orientation gate / blocker / fallback，使用户看到的是独立的方向切换界面，而不是被缩成小卡片、小舞台或带巨大空边的错误构图。只有用户明确说“推荐即可、不必强制”时，才允许保留 banner 而不阻断主内容。
- **入口/首页方向建议默认不得替代可操作入口（强制）**：若用户明确要求首页、入口页、模式选择页仍可继续操作，方向提示只能作为非阻断 banner / hint 呈现，不得复用游戏页 wrong-orientation gate 去遮挡创建、加入、继续对局等主入口。验收必须证明主入口在错向提示存在时仍可见、可点、不会被全屏遮罩捕获。
- **方向敏感页面验收必须同时证明错向态与正向态（强制）**：凡需求里出现“横屏版 / 竖屏版 / 一种强制横屏一种竖屏 / 旋转后继续”，验收至少要给两类证据：① 错误方向下看到的是独立 gate，而不是缩小后的真实页面；② 正确方向下主内容占位、比例与交互入口正常。禁止拿“切换成功了”“出现了提示条”“DOM 还在”当作方向约束达标。
- **方向/壳层受 UI 状态控制时，Web 与 Native 必须共享同一真相源（强制）**：只要某个页面样式、首页模式、运行态开关会影响原生方向锁、沉浸式状态、状态栏/导航栏模式或 App 壳层布局，就不能只把状态存在 React state、context、localStorage 或单端路由分支里。必须把该状态同步到 native 可直接读取的载体，例如 URL/query、hash、bridge、SharedPreferences、原生可读配置或等价单一真相源，并在验收时证明“切换后原生判定已同步变化”。禁止出现 Web 已切样式、但 native 仍按旧模式锁方向/开沉浸式的分叉状态。
- **动作控件不能按最低触控线糊弄设计稿（强制）**：创建、加入、确认、返回等真实动作必须跟随当前载体比例形成清晰交互语义；44px 只是不失效的触控底线，不是“符合设计稿”的尺寸标准。按参考图实现时必须按主容器比例量宽高、字号、位置、热区和装饰重量。创建/确认/加入这类主操作通常需要可见按钮承载；返回这类导航入口若参考图是轻量透明样式，禁止强加按钮背景，只能保留透明导航并证明热区、字号和可读性达标。
- **关键控件可读性不足直接判视觉失败（强制）**：按钮、tab、输入框、搜索图标、切换项、标题、副标题、分页/排序入口这类承担识别或决策职责的控件，只要在真实截图或真机画面里出现低对比、字色贴底色、图标歪斜、状态不清、点击态与未选态难区分，就必须直接判定为未达标并继续重做。禁止用“断言通过”“控件存在”“热区够大”替代可读性验收；高频控件的可读性是收口门槛，不是可选优化项。
- **固定构图弹窗/浮层必须以“目标稿 + 同类通用壳层”作为真相源（强制）**：当 modal、overlay、表单浮层、书页内面板有明确设计稿或同场景已有通用 UI 时，默认先复用同一套共享壳层、边框、角饰、标题/分割线、输入框和主按钮语法，再做当前内容编排；禁止一边声称“同风格”，一边为登录、创建、加入、确认各写一套不同的组件语法。受限视口下若出现裁剪、挤压或字段缺失，先修共享壳层内的节奏、局部滚动和紧凑分支；“做成接近全屏”只是可能暴露的失败症状，不是规范本体。验收时至少同时证明四件事：①主容器宽高占比和中心点仍符合目标稿；②标题、分割线、角饰、输入框、主按钮属于同一视觉语法；③键盘/聚焦不会把弹窗整体顶走；④关键字段和下一步主操作都在真实可视区。若同一轮同时存在目标稿和 `ui参考` 问题标注图，前者优先，后者仅用于问题定位。
- **装饰层必须可命名、可计数、不可重复堆叠（强制）**：在固定构图弹窗、卡片、面板里，装饰层必须能清楚说出自己在扮演什么角色。常见角色可以是 backdrop / shadow、surface、border、accent line、corner ornament、divider accent，但这些只是例子，不是固定清单；若某个灰色框、半透明矩形、阴影带、细线、角标无法明确归类，就应优先视为多余层而不是“看着差不多就留着”。同一边同一轴向上不得同时出现两套意义相近的装饰层，也不得为了“更满”额外叠一层不解释的灰块；背景里出现既不像遮罩、也不像边框或投影的灰色框时，默认判为无意义装饰，必须删除或重做成明确角色。
- **标注图红框是验收信号，不是示意图（强制）**：当用户提供带红框、箭头或圈选的参考图时，标注区域必须优先作为问题位点核对；如果红框圈的是角标、分割线或背景框，就必须把对应元素命名并逐项检查位置、重量、留白和语法一致性。角饰不要求机械镜像，但必须保持同一视觉家族，不能只看整体观感就提前收口。
- **参考图几何语义必须先命名再实现（强制）**：对照设计稿时，必须先判断每个视觉元素的几何归属，再落代码和测试命名。像“分类选中线”这类元素，如果实际落在页眉分割线上，就应按“页眉选中线 / rule / divider accent”处理；只有贴近文字基线、属于文字装饰时，才允许称为“文本下划线”。禁止用模糊命名掩盖还原错误，也禁止只量宽度/中心点而不量相对参照线、文字和容器的位置关系。
- **同级 tab / 导航必须保持同一视觉语法（强制）**：同一 tab 组里的项目必须共用一致的字号基线、间距节奏和组件形态；active 态只能通过颜色、字重、下划线、标记、底色等状态差异表达。禁止把 active tab 画成大标题、其它 tab 画成小链接，或用一大一小破坏同级关系。若需要页面标题，必须和 tab 组分离，不得混在同一行冒充 tab。
- **空状态禁止“操作教学式说明”（强制）**：首页/大厅/详情等主路径的空状态默认只允许“状态标题 + 必要主操作”，禁止再追加“先做什么就会出现什么”的解释型文案（如“先开一局就会出现记录”）。若确需说明，必须有用户明确要求或可用性证据，并优先放到帮助页而非主界面。
- **主界面只展示有直接用途的元素（强制）**：主入口、总控页、工作台首页、首页首屏默认只允许展示“当前用户马上能用到”的内容。内部模块编排图、调试按钮、编辑器工具栏、背景/吸附切换、实现分层示意、纯技术态流程图等，如果不能直接帮助用户决策、执行或理解当前结果，就必须隐藏、下沉到调试态，或彻底删除。禁止把“这能说明系统内部怎么做”当成留在主界面的充分理由。
- **组合爆炸类交互禁止枚举成按钮墙（强制）**：当交互本质是“同一组对象的排序、分组、分配、顶/底拆分、先后次序编辑”时，禁止把所有排列、组合或分割结果直接展开成按钮列表、卡片墙或长菜单。只要候选数量会随对象数呈阶乘级、指数级或明显超线性膨胀，就必须改成线性复杂度的编辑方式，例如分步选择、双列表分配、局部移动、拖拽排序或显式确认流。验收时必须提供真实链路截图，证明用户面对的是有限工具条/编辑器，而不是爆炸式选项清单。**其中用于检视/预览的对象卡面不计入“按钮数量”**；只有真实可执行的动作控件、确认控件和跳过控件才算交互负担。
- **交互模式成立性优先于减负入口（强制）**：用户觉得“难选、难扫、步骤多、选项墙、总在弹 prompt”时，第一检查项不是先补搜索、筛选或折叠，而是先判断**交互模式本身是否成立**。至少先回答四件事：① 这一步是否本来就该自动收口；② 是否错误地把单候选/必选步骤做成了确认层；③ 是否把组合爆炸问题错误实现成按钮墙；④ 当前 ownership、时机、`may/skip` 语义是否正确。只要其中任一项不成立，就必须先修交互模式，禁止用“减负入口”掩盖错误模式。
- **多候选/多状态界面在模式成立后仍须提供减负机制（强制）**：只有在确认交互模式本身成立之后，才讨论“怎么让用户更容易扫和选”。当一个界面需要同时展示较多候选对象，且对象混有多种状态时，禁止只靠全量平铺让用户自己扫。必须提供至少一种能明显降低扫描和决策成本的机制，例如分步流、状态分层、聚焦当前可操作对象、搜索、筛选或等价手段。移动端受限视口下默认优先聚焦当前可操作对象，而不是先把全部状态混排给用户。
- **减负机制不得反向挤爆主交互区（强制）**：补搜索、筛选、状态条、分组器、辅助说明或其他减负机制时，不能只满足“多了个入口”就算完成。若页面本身已经处在紧预算场景，减负机制必须优先做成单行、可折叠、渐进展开或其他低侵入形式，避免为了增加工具而压缩、遮挡或裁切真正的主交互对象。验收时必须同时看两件事：① 用户是否真的更容易理解和操作；② 主交互区是否仍保持完整可见、可读、可点。
- **常驻辅助 UI 不得遮挡主交互区（强制）**：座位条、玩家状态卡、草稿顺序条、阶段提示条、底部信息栏这类**常驻辅助 UI**，不得再用绝对定位压在当前主交互区上，尤其不能盖住底排卡牌、底部按钮、确认区或当前可点对象。若页面需要同时展示“主交互对象 + 常驻状态摘要”，必须二选一：① 让辅助区进入正常布局流，占据独立高度；② 对主交互区显式预留等量安全区，并在真实截图里证明没有任何关键对象被遮挡。禁止通过放大当前玩家卡、加悬浮卡片或叠加半透明面板来挤占主交互空间。
- **单一合法结果且无显式放弃语义时禁止继续弹选择层（强制）**：如果当前交互在规则语义上没有 `may` / `可以放弃` / `skip` / `二选一` 之类显式分支，而运行时又只剩 1 个合法候选，则必须直接自动收口，禁止再额外弹一层“确认这唯一候选”的 prompt、按钮或卡片墙。相反，如果规则文本明确允许放弃、跳过或在唯一候选与“不做”之间二选一，则仍必须保留该选择入口。验收时至少要同时证明两点：① 权威文本里是否存在显式放弃语义；② 单候选真实入口下页面是否没有多余 overlay / prompt，并已直接到达最终权威状态。
- **`skip / 让过` 不等于整条链必须立即无 prompt（强制）**：若规则语义只是“放弃当前这一步机会”，但当前状态后面仍有合法 follow-up reaction / response / afterScoring 触发，那么 UI 在 `skip / 让过` 后可以合法切到下一层 prompt。此时验收不能机械要求 `interaction.current == null`；真正要看的，是旧 prompt 的标题、按钮、计数和辅助条是否已经从 DOM 与视觉上退场，只留下新的那一层交互。
- **私有/owner-only prompt 必须在恢复态保持同一归属（强制）**：凡交互只应由单一玩家看到或操作（如私有检索、顶牌重排、owner-only extra action、只属于某一玩家的 reaction/response），验收不能只证明“首次出现时归属正确”。至少还要补一条真实 `hidden -> visible -> manual-resync` 或等价恢复态链，证明：① 拥有者页恢复后 prompt 仍在或仍可继续；② 非拥有者页不会接管控制权、不会被错误拉进 waiting/prompt；③ 收口后两页都无残留 overlay。禁止把这类恢复态串页问题留到 transport 层再模糊兜底。
- **后台与工作台文案默认中文（强制）**：后台管理界面、Flowise 工作流页、AI Repo Workbench、菜单项、按钮、空状态、提示语、对话框标题等面向终端用户的 UI 文案，默认使用自然中文。禁止用英文名、英文按钮、英文空状态临时占位后长期保留；若确需保留英文术语，必须确认该词没有稳定中文译法，或用户明确要求保留原文。
- **禁止把实现细节直接写进用户 UI（强制）**：用户可见文案只能表达当前产品状态与下一步动作，不能暴露“真实进度 / 伪进度 / 等待原生返回 / 接口尚未返回 / 本地缓存 / 降级逻辑 / 技术限制”这类实现层解释。若当前阶段没有准确百分比，就保持中性状态文案或纯视觉 loading，禁止再补一段工程说明来自我辩解。
- **Toast 文案最小化（强制）**：Toast 默认只允许一句结果/错误信息，禁止“原因 + 过程 + 后续说明”三段式解释。除非用户明确要求，否则不要在 toast 里追加“系统会继续观察”“建议通过反馈入口提交问题”这类说明性文案；需要详细解释时应放到日志页、帮助页或可展开详情中，而不是 toast 正文。
- **临时/瞬态 UI 不得挤压已有布局（强制）**：攻击修正徽章、buff 提示、倒计时标签等"出现/消失"的临时 UI 元素，必须使用 `absolute`/`fixed` 定位，禁止插入 flex/grid 正常流导致其他元素位移。若需占位，必须在初始布局中预留固定空间（如 `invisible` 占位符）。
- **Flex 容器可滚动子元素必须加 `min-h-0`（强制）**：在 `flex-col` 容器中，使用 `flex-1 overflow-y-auto` 的子元素**必须同时加 `min-h-0`**。原因：flex 子元素默认 `min-height: auto`（内容撑开），导致 `overflow-y-auto` 不生效，内容被父级 `overflow-hidden` 裁剪而非滚动。同理，`flex-row` 容器中横向滚动的子元素需加 `min-w-0`。

  - ✅ `<div className="flex-1 min-h-0 overflow-y-auto">` — 正确，可滚动
  - ❌ `<div className="flex-1 overflow-y-auto">` — 错误，内容溢出时被裁剪而非滚动
- **数据/逻辑/UI 分离（强制）**：UI 只负责展示与交互，业务逻辑放在引擎/系统/领域层，数据定义与配置（manifest、常量表、资源清单、文案 key）用纯数据文件维护。
- **交互语义单一真值（强制）**：`可用 / 已用 / 不可用 / 可选目标 / armed` 这类视觉反馈必须绑定真实业务语义，不能在 UI 层复制一套近似判断。若领域层已有 `validate(...)`、统一可用集合或查询函数，组件只能消费这些结果，不能再凭 `isMyTurn && !used && owner===me` 之类局部条件单独推导一套描边/发光/徽记。
- **视觉态与触发方式分离（强制）**：`能不能做` 与 `怎么触发` 是两件事。可以因设备差异改变触发方式（例如 touch 端先 armed 再激活），但不能因为触发方式变化而改写“当前是否可用”的视觉态来源。前者属于交互层，后者属于语义层，必须分离。
- **视觉报障不得先归结为“用户看错”（强制）**：当用户反馈“看起来像另一张牌 / 看起来进了弃牌堆 / 看起来没贴回面板”时，不能直接把用户判断当最终根因，也不能直接降级成“看错了”。必须同时看稳定态截图、DOM 标识与权威状态字段，明确区分“视觉误导”与“状态错误”。
- **Inspect / 放大镜按钮状态层隔离（强制）**：卡牌、随从、基地、弃牌堆等实体上的 `inspect` / 放大镜按钮，禁止挂在承载 `ring`、`shadow`、`opacity`、`grayscale`、`scale`、`rotate` 等状态视觉的同一 DOM 层内。放大镜按钮必须是该状态层外的独立悬浮兄弟节点，默认只拥有自己的固定底色与 hover 态，不得跟随实体的“可选/已选/不可用/高亮/武装”视觉态一起变色、变描边、变透明、变灰。只要用户反馈“按钮也跟着描边/变色”，默认先检查 DOM 层级，而不是先调颜色值。
- **共享 FAB / HUD 面板锚点按面板类型分流（强制）**：`undo`、确认提示、短说明这类短面板，默认使用“当前按钮自身”作为垂直锚点；`action-log`、长列表、滚动日志这类长面板，默认使用“展开列 / 按钮列 referenceRect”作为垂直锚点。**禁止**把所有弹出面板统一绑到同一套垂直对齐算法，否则很容易出现“修好短面板后把长面板改歪”或“为恢复长面板又把短面板拖到兄弟按钮层级”的回归。只要改动共享 FAB / HUD 锚点逻辑，必须同时检查至少一个短面板场景和一个长滚动面板场景。

### 1.1 游戏内 UI 组件单一来源（强制）

> **同一类 UI 功能在每个游戏中只允许有一个组件实现**，所有场景必须复用该组件，禁止新建功能重叠的组件。

- **卡牌展示/选择 UI**：每个游戏只允许一个卡牌展示组件，所有卡牌展示场景（弃牌堆查看、弃牌堆出牌、reveal、卡牌选择交互）必须通过该组件实现。
  - SmashUp：`PromptOverlay.tsx`（通过 `displayCards` prop 支持纯查看和选择两种模式）
  - 新增卡牌展示场景时，必须扩展现有组件的 props/模式，禁止新建 `CardStrip`/`CardList`/`CardReveal` 等重复组件。
- **卡牌放大/详情 UI**：统一使用 `CardMagnifyOverlay`，禁止新建放大弹窗。
- **判定标准**：新增 UI 组件前，必须先搜索同游戏 `ui/` 目录下是否已有功能相似的组件。如果已有，必须通过扩展 props 复用，不得新建。

#### 1.1.1 选择型 Prompt 可用性门禁（强制）

- **少量候选禁止堆辅助按钮**：当多选 prompt 的真实候选只有 1-2 个时，默认不得再显示 `全选`、`取消全选`、重复说明文案或其他不会降低操作成本的辅助按钮。此时主界面只保留标题、候选本体、必要的确认/跳过入口。只有候选数足以让批量操作明显省步骤时，才允许显示 `全选/清空` 一类工具按钮。
- **标题 / 候选区 / 确认区必须分层**：卡牌/基地/随从选择 prompt 必须把标题、候选内容、确认动作做成可一眼区分的独立区域；禁止把标题压在棋盘本体上、把确认按钮悬在候选区之外、或让用户在一张图里难以判断“当前在选什么”和“下一步该点哪里”。
- **紧凑 prompt 必须压住背景焦点**：当 prompt 已收成 1-2 个候选的紧凑模态后，背景棋盘高亮、HUD、浮动按钮和其它远景元素不得继续与候选本体抢第一视觉焦点。最低要求是：主遮罩足以压暗背景，模态背后要有独立的局部压场层或等价手段，让用户第一眼先看到标题、候选和确认区，而不是先被基地描边或角落控件吸走注意力。
- **owner prompt 激活时不得继续暴露外围壳层噪音控件（强制）**：当当前玩家自己正在处理 prompt（无论是 overlay、棋盘直选还是手牌直选），主视觉必须只服务当前这一步选择。最低门禁不是“结束回合按钮先藏掉”就算完成，而是**所有会被误读成另一组并列入口的外围壳层都要一起退场或降到只读背景**。至少包括：① 右下 `结束回合` 大按钮、额度徽章、显隐切换；② 当前 owner prompt 不再需要的牌库/弃牌/rail 工具入口；③ 会被读成控制入口的记分板、调试浮球、设置浮球或其它全局工具。允许保留的只有与当前 prompt 语义直接相关的对象本体、最小必要状态提示，以及不会抢主焦点的弱背景信息。禁止把“当前该先做出的选择”和“别的可点控件”同时留成两组主焦点。
- **棋盘直选高亮必须等于真实可落点**：当界面不走 prompt、而是直接进入棋盘直选时，基地/随从/目标的高亮范围必须与命令校验的合法落点完全一致。禁止 UI 先把更多对象亮成可选、点击后再靠 toast 或 validator 拒绝；若存在基地限定额度、同名额度或力量限制，前端高亮必须先按这些约束收窄，再让用户点击。
- **热切换 prompt 禁止旧内容残留**：同一 overlay 容器承载多步交互时，第二步内容出现前，第一步标题、按钮、勾选数、等待态必须先从 DOM 和视觉上消失。禁止因为动画退场、本地状态复用或同 id 重渲染，把上一层 prompt 的文案/计数残留到下一层截图里。
- **同批 reveal 与 prompt 不能双层同屏**：当当前玩家的 prompt 已经直接承接同一批 reveal / deck-top 卡牌时，非阻塞 reveal 浮层必须退场或被抑制，不能继续与 prompt 重复展示同一批卡面与标题。否则截图会把单一流程拍成两层候选，直接伤害可用性。
- **展示型 overlay 不得伪装成整屏可操作层**：若 reveal / spotlight / 说明浮层的语义是“展示型、非阻塞、可继续操作”，整屏根容器默认必须 `pointer-events-none`，只允许最小必要交互区（例如关闭按钮、卡牌本体放大入口）恢复 `pointer-events-auto`。禁止再用整屏 `onClick`、整屏 backdrop 点击关闭或其它会抢走底层主操作点击的实现；否则用户会把展示层误读成新的 prompt/按钮墙。
- **批量重排类交互禁止枚举结果墙**：当交互本质是“排序/分堆/放顶放底/任意顺序”时，不得把所有排列结果直接铺成按钮墙。应优先提供可编辑的线性工具面板，让用户操作对象本体，再通过确认提交最终顺序。
- **线性重排编辑器按“动作数”审可用性，不按“展示卡数”误判**：当 prompt 的主体是被 inspect/reveal 的卡面本体，而真正可执行操作被收敛为少量工具按钮（例如 `前移/后移/移到底/确认`）时，审查“选项太多”必须按显式动作控件数量与层级来判断，不能把 3-5 张被编辑对象本体误算成 3-5 个独立候选按钮。只有当编辑器把每种结果、每张卡、每个位置都额外展开成一堵可点按钮墙时，才算违背可用性门禁。
- **`skip / 让过` 后允许合法切到下一层 prompt，但旧层必须退干净**：若规则语义只是“放弃当前这一步机会”，而后面仍存在合法 follow-up reaction / response / afterScoring 交互，那么 UI 在 `skip / 让过` 后可以直接切到下一层 prompt；这不算 UX 错误。真正的错误是旧 prompt 的标题、按钮、计数、浮动操作栏或 overlay 还和新 prompt 同屏残留。验收时必须同时看两点：① 下一层 prompt 是否确属合法链路；② 旧层内容是否已经从 DOM 与视觉上退场。
- **`skip-only` 的手牌直选 prompt 不得继续暴露伪候选（强制）**：当 `targetType='hand'` 的 owner prompt 最终只剩 `skip / 放弃 / 让过` 一类辅助动作、已经没有任何合法手牌或泰坦候选时，手牌区必须一并退场，只保留标题与最小必要的 skip 按钮。禁止把普通手牌继续留在屏幕上，让用户误读成“这里还有一张可以点的牌”。若仍有至少一个真实候选，才允许保留手牌区承接点击。
- **手牌直选 prompt 只允许展示真实候选卡，不得把无关手牌一起摆成“额外选项”**：当 owner prompt 的 `targetType='hand'` 仍有 1..N 个真实 `cardUid` 候选时，手牌区只能展示这批 prompt option 对应的候选卡本体；与本次 prompt 无关的普通手牌必须隐藏或退成不可见背景，不能继续与 skip/确认按钮并列出现。否则用户会把“当前只是在这几个候选里选一张”误读成“整手牌都还能点”。
- **setaside 泰坦反应 prompt 必须保留真实本体（强制）**：当 owner prompt 的目标是 `setaside` 泰坦反应 / 进场选择时，外围壳层可以退场，但当前可触发的泰坦本体必须继续留在主视觉里，并且只能保留与该 prompt 直接相关的 rail / skip / 确认动作。禁止把 prompt 文案保留下来却把实际可点击泰坦一起藏掉，也禁止把 deck / discard / 结束回合 / turn notice 重新拉回到同屏里制造第二焦点。
- **非 owner 等待页只能保留单一等待语义**：当当前页面并不拥有该 prompt，只允许展示一处明确的等待状态（例如 `等待调整` / `正在等待 {{player}}`）。禁止同时保留重复等待文案、禁用版编辑工具、禁用确认按钮，或任何会把等待页误读成“我也能操作”的控件噪音。
- **非 owner waiting prompt 不得继续保留原 prompt 标题/候选壳层**：如果当前页只是等待别人处理，默认不再显示该 prompt 的原始标题、候选卡带、候选列表容器或其它“正在选什么”的主内容骨架；否则用户会把等待页误读成“我也在这一步里”。唯一例外是 deck reorder 这类明确需要展示 inspect 对象本体但不暴露操作工具的场景，此时必须显式标注为只读等待态。
- **响应窗口 waiting family 同样按单一等待壳层处理**：像 `Me First! / 计分后响应` 这类 response-window overlay，若当前页不是 active responder，也不得继续显示原始标题、让过按钮、响应进度点阵或任何“大卡片式操作面板”。非响应者页面只能保留一条等待文案或等价的紧凑 waiting shell；同时右下 `GameHUD/FAB`、设置/聊天/反馈这类全局工具入口也必须退场，避免等待页出现第二视觉焦点。否则用户会把合法等待态误读成自己也能参与的响应界面。
- **棋盘 blocked waiting 不得继续暴露结束回合配套控件**：当 `Board` 只是因为别人拥有当前交互而进入 blocked waiting 时，结束回合区只能保留一个被动状态牌（如 `等待对方操作`）。禁止继续同时显示额度徽章、显隐切换、禁用版结束回合配套控件，避免把“当前只是等待”误读成“这里还有一组可操作入口”。若用户此前手动隐藏了结束回合 UI，blocked waiting 仍必须保留状态牌，不能把等待语义一起隐藏掉。

### 1.3 UI 动画设计原则（强制）

> **核心原则：动画应由数据/状态变化驱动，而非由 UI 事件直接触发**。尤其是涉及命令验证的操作，必须等待验证成功后再启动动画。

#### 两种动画触发模式

**数据驱动动画（Data-Driven Animation）**：
- **定义**：通过 `useEffect` 监听状态字段变化，状态变化时启动动画
- **适用场景**：所有需要命令验证的操作（投掷骰子、打出卡牌、激活技能等）
- **优势**：动画只在操作真正成功后播放，验证失败时不会出现"动画已播放但操作未生效"的不一致

**事件驱动动画（Event-Driven Animation）**：
- **定义**：在 `onClick` 等事件处理器中直接设置动画状态
- **适用场景**：纯 UI 交互，不涉及命令验证（如展开/折叠面板、切换标签页、hover 效果）
- **风险**：若用于需要验证的操作，验证失败时动画已播放，造成视觉欺骗

#### 正确模式（数据驱动）

```typescript
// ✅ 正确：监听 rollCount 变化启动动画
const [isRolling, setIsRolling] = React.useState(false);
const prevRollCountRef = React.useRef(rollCount);

React.useEffect(() => {
    if (rollCount !== prevRollCountRef.current) {
        const prevCount = prevRollCountRef.current;
        prevRollCountRef.current = rollCount;
        
        // rollCount 增加 → 投掷成功，开始动画
        if (rollCount > prevCount) {
            setIsRolling(true);
            // 安全超时：防止服务器长时间无响应
            const timer = setTimeout(() => setIsRolling(false), 5000);
            return () => clearTimeout(timer);
        }
    }
}, [rollCount, isRolling]);

const handleRollClick = () => {
    if (!canInteract) return;
    // 不在这里设置 isRolling，而是在 rollCount 变化时设置
    // 这样可以避免命令验证失败时动画已经开始播放
    dispatch(COMMANDS.ROLL_DICE, {});
};
```

#### 反模式（事件驱动）

```typescript
// ❌ 错误：onClick 中直接设置动画状态
const handleRollClick = () => {
    if (!canInteract) return;
    setIsRolling(true);  // ← 动画立即开始
    dispatch(COMMANDS.ROLL_DICE, {});  // ← 命令可能验证失败
    // 问题：验证失败时动画已播放，但骰子值未变化
};
```

#### 与乐观更新引擎的关系

项目使用乐观更新引擎（`OptimisticEngine`），客户端会立即预测状态变化。但预测可能失败（如命令验证失败、随机数不一致），此时会回滚到服务端确认的状态。

- **乐观更新成功**：`rollCount` 立即增加 → `useEffect` 检测到变化 → 启动动画
- **乐观更新失败**：`rollCount` 不变或回滚 → `useEffect` 不触发动画 → 视觉与状态一致
- **关键**：动画依赖最终状态（`rollCount`），而非用户操作（`onClick`），确保动画只在操作真正生效时播放

#### 阶段转换清理（强制）

当游戏阶段转换时（如从进攻阶段进入防御阶段），必须立即清理上一阶段的动画状态，防止动画残留。

```typescript
// ✅ 正确：阶段转换时清理动画状态
React.useEffect(() => {
    if (currentPhase === 'defensiveRoll' || currentPhase === 'offensiveRoll') {
        // 进入新阶段时立即清除投掷动画状态
        if (isRolling) {
            setIsRolling(false);
        }
    }
}, [currentPhase, isRolling, setIsRolling]);
```

#### 最短播放时间保护（可选）

乐观更新会瞬间产生新状态，但动画需要一定时间才能完整播放。可以记录动画开始时刻，在状态变化时检查是否已过最短时间，未过则延迟停止。

```typescript
const MIN_ROLL_ANIMATION_MS = 800;
const rollStartTimeRef = React.useRef<number>(0);

React.useEffect(() => {
    if (rollCount > prevCount) {
        setIsRolling(true);
        rollStartTimeRef.current = Date.now();
    } else if (isRolling) {
        const elapsed = Date.now() - rollStartTimeRef.current;
        const remaining = MIN_ROLL_ANIMATION_MS - elapsed;
        if (remaining <= 0) {
            setIsRolling(false);
        } else {
            const timer = setTimeout(() => setIsRolling(false), remaining);
            return () => clearTimeout(timer);
        }
    }
}, [rollCount, isRolling]);
```

#### 新增 UI 交互检查清单

开发新的 UI 交互时，必须回答以下问题：

1. **这个操作需要命令验证吗？**
   - 是 → 使用数据驱动动画（监听状态变化）
   - 否 → 可以使用事件驱动动画（onClick 直接设置）

2. **动画状态的唯一真实来源是什么？**
   - 必须是引擎层状态字段（如 `rollCount`、`G.core.xxx`）
   - 禁止依赖 UI 层临时状态（如 `isButtonClicked`）

3. **阶段转换时需要清理动画状态吗？**
   - 是 → 在 `useEffect` 中监听 `currentPhase` 并清理
   - 否 → 确认动画不会跨阶段残留

4. **动画是否需要最短播放时间保护？**
   - 是 → 记录开始时刻，延迟停止
   - 否 → 状态变化时立即停止

#### 可重播结果动画的事件身份规则（强制）

> 适用于“同一个结果值也可能需要再次播放完整动画”的场景，如掷骰特写、翻牌揭示、抽牌亮相、结算浮层中的单次结果展示。

- **不要用结果值本身推断“是否发生了新事件”**：如果动画的语义是“系统刚刚产生了一次新结果”，则 `value` / `face` / `amount` 只代表**最终停留结果**，不能作为“要不要重播动画”的唯一依据。
- **必须区分两类信号**：
  - **结果状态**：最后展示什么，例如骰子最后停在 `4`。
  - **事件身份**：这是第几次展示/第几次重掷/哪一次结算，例如 `settlementId + rerollCount`、`eventStream entry id`、`timestamp`、`nonce`。
- **判定标准（强制）**：若以下任一条件成立，组件必须消费独立的事件身份信号，而不能只监听结果值变化：
  - 组件可能在父层复用，不会因新事件自动卸载重挂载；
  - 新事件的结果可能与上一次完全相同；
  - 用户看到的是“一次性结果揭示过程”，而不是稳定状态持续展示。
- **优先级顺序（强制）**：
  1. 优先复用领域层或 EventStream 已有的稳定事件 ID；
  2. 其次使用结算对象自带的序号/重掷 key；
  3. 最后才允许在展示聚合层生成局部 `presentationKey` / `nonce`。
- **禁止反模式**：
  - 仅凭 `value !== prevValue` 决定是否重播掷骰/翻牌/揭示动画；
  - 依赖 React “通常会重挂载”这种偶然行为；
  - 在多个父组件里各自手搓一套“如果没动就不播/强制 setTimeout 重播”的分叉逻辑。
- **推荐模式**：
  - 组件 API 显式区分 `value` 与 `presentationKey`（或等价命名）；
  - `value` 决定落点，`presentationKey` 决定是否开始一轮新的表现生命周期；
  - 若动画只允许针对局部目标重播（如多骰中只重掷一颗），则用“目标索引 + 事件身份”组合成局部 key，而不是重播全部对象。

#### 结果动画的架构落点（强制）

- **这是表现层模式，不是业务补丁**：`presentationKey` 的职责是表达“新的可见事件已经发生”，不应被视为临时兜底字段；业务状态里不得为了 UI 动画额外保存 `animationKey` 这类纯表现字段。
- **统一 seam**：React 结果揭示动画优先复用 `src/hooks/ui/useResultRevealAnimation.ts`，不要在组件里重复维护 `previousValueRef + setTimeout + isRolling` 组合。
- **长期方向**：同一类结果展示组件应收敛到统一触发契约。对于跨游戏可复用的“结果揭示型”组件，优先定义通用 props 语义，而不是每个游戏自行发明一套布尔开关或局部 timer。
- **审查门禁**：当用户反馈“只有结果没有过程”“同样结果第二次不动了”“重掷后直接跳最终值”时，必须先检查该组件是否缺少事件身份信号，再决定是否改动画样式或时长。

- **阶段转换清理**：`src/games/dicethrone/Board.tsx`（`useEffect` 监听 `currentPhase`）

## 2. 多端布局策略 (Multi-Device Layout Strategy)

- **双端并行，不是双份 UI**：默认只有一套 React UI 架构，通过 `manifest + runtime viewport + 终端能力探测 + layout preset` 做条件化分支；**禁止**为同一游戏长期维护两套互相漂移的 `DesktopBoard` / `MobileBoard`。
- **PC 仍是固定构图类基线**：棋盘、战区、固定多栏面板、角色布局等几何关系明确的界面，仍以桌面版为结构真相源；移动端优先同构缩放，再处理 rail、dock、overlay、触控入口。
- **移动端是一等输入终端**：移动端不再只是“能打开就行”。凡是共享组件、共享交互、共享布局，只要预计会出现在移动端，就必须在方案阶段同时考虑安全区、触控命中区、长按/armed 等替代入口和方向约束。
- **宽限度约束 (Constraints)**：平台/网页 UI 通过 `max-w-7xl` 等容器限制内容延展，确保视觉焦点集中。

### 2.0 默认参考分辨率（强制）

- **PC 默认主参考分辨率固定为 `1920x1080`**。
  - 这是桌面端唯一默认权威基线；未特别说明时，桌面截图、桌面布局对照、PC 同构验收都优先以此为准。
  - 不再默认混用 `1440x900`、`1600x900`、`1366x768` 作为并列基线；这些尺寸若要使用，必须说明只是补充排查，不是主裁决口径。
- **移动端默认主参考分辨率固定为 `375x812`**。
  - 这是移动端唯一默认权威基线；未特别说明时，移动端截图、适配验收、对照证据默认使用它。
  - 若某游戏主打手机横屏或老板明确指定横屏分辨率，再按当轮任务单独声明，不在全局规范里默认保留第二套移动端主基线。

### 2.1 参考分辨率使用规则（强制）

- 先看该界面的**主参考分辨率**结果，再决定布局是否成立。
- 当老板明确指定分辨率（如 `1920x1080`）时，以老板指定为准；未指定时，按本节默认值执行。
- 正式 E2E 的职责是验证行为，不是服务某次截图取证。**特定分辨率截图需求应走独立取证路径，不得为了出图把正式 E2E 改写成专用脚本。**

- **响应式策略指南 (Responsive Strategy Guidelines)**：
    - **信息交互层 (UI & HUD)**：
        - **场景**：大厅卡片、侧边栏、模态框、文字阅读区。
        - **建议**：**稳定性优先**。推荐使用标准 `rem`，必要时配合 `clamp()` 锁定物理最小值（12px/14px），保证全环境可读。**不要**用裸 `vw` 作为正文、按钮文案、常规表单控件的主字号来源。
    - **沉浸视效层 (Immersive & Board)**：
        - **场景**：游戏棋盘、全屏背景、核心对战区域。
        - **建议**：**比例优先**。优先使用 `aspect-ratio`、`%`、壳层统一 `scale(...)`、以及运行时 viewport 变量；`vw/vh` 只能作为局部比例辅助单位，**不再推荐**作为固定构图类界面的主适配手段。
    - **布局流动层 (Layout Flow)**：
        - **场景**：列表网格、工具栏排列。
        - **建议**：**内容驱动**。利用 Flex/Grid 的自然流特性（如自动填充、自动换行）来适配屏幕宽度，而非依赖硬编码的断点控制。

### 2.1 双端 UI 架构分层（强制）

- **L1 页面路由层**：负责路由、页面语义、`Suspense fallback`、错误兜底、方向提示、运行时环境门禁；不直接承担某个游戏的细部布局。
  - 对局页统一通过 `getGamePageDataAttributes()` / `syncGamePageDocumentAttributes()` 输出 `data-game-page`、`data-mobile-profile`、`data-mobile-layout-preset` 等属性。
- **L2 页面壳层 / 运行时层**：负责真实 viewport、安全区、键盘 inset、终端能力探测、根级 CSS 变量同步。
  - 统一使用 `useRuntimeViewport`、统一 runtime helper，禁止页面各自重算一套 viewport 和原生壳判断。
- **L3 游戏壳层（layout shell）**：负责 `MobileBoardShell`、top rail、side dock、bottom rail、缩放舞台、board-shell / portrait-simple / map-shell preset。
  - 这层解决“桌面结构如何映射到移动端”，不承载游戏规则。
- **L4 游戏画布层（scene / board）**：负责棋盘、卡牌、角色区、日志区、手牌区等游戏内容本身。
  - Board 组件默认只关心壳内内容区域，不再直接读取原始视口高度去自建第二套移动壳。
- **L5 交互适配层（interaction adapter）**：负责 hover 替代、long press、armed activation、drag fallback、触控命中区增强。
  - 这层只能改变“如何触发”，不能改变“是否可用”的业务真值。
- **L6 原生壳边界层**：负责 `Capacitor`/Android/iOS 专属能力、返回桥、更新检查、原生包逻辑。
  - 原生壳行为必须停留在统一 helper 与 App shell 层，不能泄漏到共享业务 UI。

### 2.2 双端设计裁决（强制）

- **先判断界面类型，再决定适配手法**：
  - 固定构图类：优先等比缩放 + 局部让位。
  - 流式信息类：优先响应式重排 + 抽屉/标签页/单列化。
- **允许设备差异，不允许语义分叉**：
  - 可以桌面 `hover`、移动 `long press`。
  - 可以桌面单击、移动 armed 后二击。
  - 不可以桌面和移动分别维护两份 `canUse / isSelectable / showUsed`。
- **缩放舞台只能有一层主真值**：如果页面已经位于 `board-shell` 统一缩放容器内，页面内部默认禁止再套第二层整页 scale-to-fit。
- **HUD 与 Scene 分治**：棋盘/地图/战区优先保持固定几何关系；日志、帮助、设置、按钮轨道可以让位、悬浮或抽屉化。
- **端能力判断只进边界层**：`pointer: coarse`、`Capacitor.isNativePlatform()`、`window.androidBridge` 这类探测不应散落在业务组件中，必须先进入统一 helper 或 Hook。

### 2.3 单位选择规则（强制）

- **文本、按钮、表单、日志、常规 HUD**：
  - 优先 `rem`
  - 必要时 `clamp(minRem, preferred, maxRem)`
  - 原因：可读性稳定，桌面与移动不会随 viewport 宽度一起失真
- **固定构图类主布局**：
  - 优先 `px` 设计宽度 + 外层统一 `scale`
  - 或 `aspect-ratio` + `%`
  - 原因：保持几何关系，避免局部元素各自按 `vw` 漂移
- **壳层高度 / 移动端可视高度**：
  - 优先运行时同步的 viewport 变量
  - 在 `board-shell` 内禁止直接依赖裸 `100vh/100dvh`
- **局部比例型装饰尺寸**：
  - 可少量使用 `vw` / `vh`
  - 例如纯视觉徽章、背景装饰、局部舞台内的相对偏移
  - 前提：它不承担可读性和主布局稳定性的职责
- **触控命中区**：
  - 优先 `px/rem` 下限，例如 `44px`
  - 不要用 `vw` 让命中区跟着屏幕宽度忽大忽小
- **历史 `vw` 代码处理原则**：
  - 桌面固定构图下如果效果稳定，可暂时保留
  - 但新增代码不应再把裸 `vw` 当成默认主单位
  - 一旦该区域进入 `board-shell`、双端同构或移动端主链路，应优先迁移到“设计宽度 + 统一缩放”或 `clamp/rem`

## 3. 游戏 UI 特化范式 (Game-Centric Design)

> **⚠️ 游戏内 UI 必须遵循设计系统规范**
> 
> - **交互原则**：`design-system/game-ui/MASTER.md`（所有游戏通用）
> - **视觉风格**：`design-system/styles/` 下选择合适风格
>   - `arcade-3d.md` - 街机立体风（休闲、派对、骰子类）
>   - `tactical-clean.md` - 战术简洁风（策略、卡牌对战）
>   - `classic-parchment.md` - 经典羊皮纸风（复古、桌游模拟）
> 
> **核心要求**：游戏感 = 即时反馈 + 状态清晰 + 操作愉悦
> - 所有可交互元素必须有 hover/press 反馈
> - 禁用状态必须视觉明显
> - 动画只用 transform/opacity，时长 150-300ms

- **动态提示 UI（强制）**：
    - 必须使用 `absolute`/`fixed`，禁止占用布局空间（如 `relative/static`）。
    - 出现/消失不得挤压或移动其他 UI；新增前必须验证布局稳定性（尤其右侧栏/手牌区/技能区等核心区）。
    - **层级统一**：使用 `UI_Z_INDEX` 常量（如提示用 `UI_Z_INDEX.hint/overlayRaised`，模态用 `UI_Z_INDEX.modalOverlay/modalContent`），禁止硬编码 `z-[...]`。
    - 常用位置：顶部中央（交互选择）、正中央（等待）、手牌上方（弃牌）；默认 `pointer-events-none`（除非需要交互）。
- **动态效果视觉提示实施规范（强制）**：
    > 当全链路审查（见 `engine-systems.md`「描述→实现全链路审查规范」）发现动态赋予效果缺少 UI 提示时，按以下规范实施。
    - **力量修正**：修正后的力量值必须与基础值有视觉区分。正向修正用绿色/上箭头，负向修正用红色/下箭头，显示格式为 `基础值 → 当前值` 或 `当前值(±N)`。
    - **持续保护/限制**：在受影响实体上显示小图标（盾牌=不可消灭、锁=不可移动、禁止=不可打出），hover 显示效果来源。
    - **基地持续效果**：基地卡下方显示当前生效的效果摘要文字（从 i18n 获取），多个效果竖向堆叠。
    - **临时 buff/debuff**：使用 `absolute` 定位的徽章/标签，附带淡入淡出动画（150-200ms），效果结束时自动消失。禁止插入正常流。
    - **条件触发效果**：条件满足时在实体上显示发光边框或脉冲动画，条件不满足时无视觉标记。
    - **附着行动卡**：随从/基地上附着的 ongoing 行动卡必须有视觉标记（如卡牌角标或堆叠指示器），hover/点击可查看附着卡详情。
    - **不确定时必须询问用户**：如果效果的 UI 展示方式不明确（图标样式、放置位置、颜色选择、文字 vs 图标），**必须先询问用户确认再实现**，禁止自行猜测。
- **视角解耦 (Scene vs. HUD)**：
    - **场景层 (Scene)**：棋盘、卡片等核心实体，需通过 `anchorPoint` 处理坐标缩放，确保跨平台逻辑一致性。
    - **UI 层 (HUD)**：状态信息、控制面板，执行 Overlay 挂载逻辑。
- **高度稳定性**：核心游戏区（棋盘/面板）**必须**使用明确高度约束（如 `h-[35vw]`）代替 `h-full`，彻底解耦父级 Flex 依赖。
- **`MobileBoardShell` 容器约束（强制）**：凡是 manifest 声明 `mobileLayoutPreset: 'board-shell'` 的游戏，Board 根容器必须跟随壳内画布高度，使用 `h-full` / `absolute inset-0` 等容器高度方案；**禁止**在 Board 根容器上写 `h-screen`、`min-h-screen`、`100vh`、`100dvh`。原因：`board-shell` 会在移动横屏下先做整体缩放，若子树继续读取原始视口高度，会导致内容实际渲染高度小于壳高度，出现底部黑边、下半截空白或布局漂移。
- **board-shell 内 HUD/Overlay 固定定位禁令（强制）**：在 `MobileBoardShell` 内部渲染的 HUD/Overlay **不得直接使用 `fixed/absolute` 作为最终定位**；必须通过 HUD portal（`HudPortal` / `getHudPortalRoot`）渲染到 `#hud-root`，脱离缩放容器。历史实现可保留，但新增/修复必须遵守该规则。
- **board-shell 下全屏 Loading/门禁锚点（强制）**：凡是覆盖全屏的 Loading（`LoadingScreen`/`ConnectionLoadingScreen`/`CriticalImageGate`）在 `board-shell` 场景必须使用 `anchor="viewport"` 并挂载到 `#hud-root`；**禁止**用 `anchor="container"` 或在 Loading 根节点强行追加 `relative`，否则会让 `fixed` 退化为容器相对定位，出现整体偏移。
- **相位敏感性**：UI 必须清晰反馈当前"游戏相位"与"操作权限"，通过高亮合规动作 (Valid Actions) 降低认知负荷。
