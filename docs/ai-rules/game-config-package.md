# 游戏配置包规范

> 适用：新游戏静态配置、配置审查表、玩家字段级修正提案，以及旧游戏是否接入统一配置视图的裁定。

## 默认口径

- `GameConfigPackage` 是项目内共享接口，不是第三方包。
- 新游戏的静态事实默认先进入严格 JSON 配置包，再由运行时加载、校验和物化。
- 旧游戏默认不强制迁移；只有明确需要统一审查表、结构化修正提案或迁移配置真相源时，才建立单独接入任务。
- 表格是同源审查视图，不是运行时依赖；表格行必须来自配置包物化结果，禁止另维护一份展示专用数据。
- 配置审查表的顶部只承载标题、筛选、统计和批量提交入口；分页、每页数量、上一页 / 下一页等翻页控件必须放在表格下方或表格底部工具条，不得放进页面标题区抢占审查首屏。
- 宽配置审查表必须保留原生数据表滚动语义：普通鼠标滚轮控制上下滚动；左右浏览依赖底部横向滚动条、触控板横向手势或 `Shift + 滚轮`，不得复用会把纵向滚轮转换成横向滚动的卡牌横排浏览增强。

## 格式职责

| 格式 | 职责 | 禁止口径 |
| --- | --- | --- |
| 严格 JSON | 新游戏官方仓库真相源，便于 diff、review、自动校验和稳定解析 | 不得跳过 schema 校验直接运行 |
| JSONC / YAML / XLSX | 只允许作为未来导入、导出或编辑辅助；进入系统前必须转换成严格 JSON 配置包 | 不得作为官方仓库真相源，不得进入运行时默认解析链路 |
| TypeScript 配置 | 旧游戏可继续临时使用；可通过只读 adapter 暴露审查视图 | 新游戏不得默认把静态事实直接写进代码对象 |

## 特殊效果边界

- 配置包只声明 `abilityId + params`。
- 真正的特殊效果由代码里的能力 / 规则模块实现。
- 加载配置包时必须能报告：
  - 能力 ID 不存在；
  - 能力需要代码支持但未实现；
  - 参数缺失或类型不符合能力参数合同。
- 玩家提交的修正不能包含可执行代码；只能修改 schema 允许字段，或建议新增 / 调整能力绑定。

## 玩家修正提案

玩家从配置审查表提交的是结构化提案，不是直接改官方配置。提案至少保存：

- 游戏 ID、配置版本；
- 对象 ID、对象类型；
- 字段路径；
- 当前值、建议值；
- 说明、证据；
- 来源页面、表格 ID、行 ID、单元格 key、语言环境；
- 审查状态。

AI 审查只做首轮建议，可输出：建议接受、建议拒绝、需要更多证据、需要人工确认、需要代码支持。AI 不得自动写入官方配置源；正式合入仍走代码变更、测试和发布流程。

## 新游戏门禁

新游戏 OpenSpec 的 proposal 或 design 必须说明：

1. 是否使用 `GameConfigPackage` 承载静态事实；
2. 若使用，严格 JSON 文件位置、schema 范围、表格审查范围是什么；
3. 若暂不使用，跳过原因、影响范围和后续补齐项是什么；
4. 特殊效果哪些只需配置参数，哪些需要代码能力支持；
5. 玩家配置修正是否进入现有反馈式流程。

## 旧游戏裁定

旧游戏已有清晰 TypeScript 配置、注册表和测试覆盖时，不应为了统一格式立即重构。优先级顺序：

1. 保留现有运行时配置；
2. 如果玩家需要审查，先做只读可视化 adapter；
3. 如果需要字段级修正提案，再让 adapter 输出配置包表格模型；
4. 只有当官方真相源本身要迁移时，才把旧配置逐步搬进配置包。

召唤师战争当前属于第 1-2 类：配置技术债务不大，不建议立即重构；若要给玩家审查，优先基于现有卡牌注册表和牌组构建结果生成只读审查表。

## 旧游戏只读 adapter 模板

旧游戏需要配置审查表时，默认先做只读 adapter，不迁移官方真相源：

1. 读取该游戏当前真实运行入口，例如卡牌注册表、阵营目录、牌组构建器或运行时 manifest；
2. 将现有对象映射为配置包物化表格行，保留原对象 ID、中文名、类型、阵营、数量、数值、能力 ID、素材引用和来源上下文；
3. 先建立字段覆盖清单，再写表格 UI。字段清单必须逐项记录：玩家可理解的现实含义、字段 key、值类型、适用对象、字段路径、值读取方式、是否必审、规则/运行时消费证据；
4. 字段覆盖清单必须从规则真相源和消费代码反推，至少覆盖运行时、牌组构建、起始部署、素材加载、能力绑定和特殊规则实际读取的静态字段。禁止只看 adapter 当前字段、UI 列名或历史实现印象来判断“已经上表”；
5. 表格字段必须能回指原配置对象，字段路径可采用 `legacy.<gameId>.<source>.<objectId>.<field>` 或项目内等价稳定路径；
6. 表格页面只能消费 adapter 暴露的字段清单生成列、字段值、字段适用性和编辑解析规则；不得在页面里再维护一套独立列清单或字段类型清单；
7. adapter 测试必须覆盖：必审字段都在可见列中、每个必审字段都有证据来源、每个可编辑单元格有字段路径、字段值来自同一物化对象；
8. adapter 不得把旧游戏运行时切到配置包，不得改写现有配置对象，也不得额外维护展示专用副本；
9. 若玩家提交修正，提案保存 adapter 生成的字段路径、当前值、建议值和证据；AI / 人工审查后再决定是否另建正式迁移或代码修改任务。

召唤师战争的推荐 adapter 来源是 `src/games/summonerwars/config/cardRegistry.ts`、`src/games/summonerwars/config/factions/index.ts` 与 `src/games/summonerwars/config/deckBuilder.ts`。这些入口已经能聚合阵营、唯一卡牌池和牌组构建结果，适合先生成只读审查表，而不是立即把 `config/factions/*` 全部搬到 JSON。

## 召唤师战争字段审计裁定

- “牌组构筑用标记”的规则术语是“牌组符号”，代码字段为 `deckSymbols`；它和阵营视觉标识不是同一字段。
- `deckSymbols` 必须作为必审字段进入字段覆盖清单和表格可见列，因为规则书的牌组限制、`deckValidation.ts` 的符号匹配、组牌器更换召唤师过滤都实际消费它。
- 起始部署坐标必须作为 `setupPositions` 一类正式字段进入表格，不能只藏在“来源上下文”字符串里。
- 后续如果发现规则书、构筑验证、起始部署、素材或能力代码新增静态消费字段，必须先更新字段覆盖清单和测试，再更新 UI 展示。
