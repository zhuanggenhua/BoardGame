# 测试与审计规范

> **触发条件**：新增功能/技能/API、修复 bug、审查实现完整性时阅读。

---

## 核心原则入口

> fail-close 审计速查、全面审计完成定义、录入/图片/旧 evidence 边界、交互入口语义矩阵和技能完整流程矩阵，已拆到 `docs/ai-rules/testing-audit-core-principles.md`。
>
> 本文档只保留审计总入口、证据分层和流程路由。凡要对外写“已审计 / 已收口 / 全面审计完成”，必须先读核心原则文档并按其中矩阵落证据。

### 审计结论等级与证据分层（强制）

#### 结论等级

对外汇报时，必须使用下列结论等级之一，禁止再把所有情况都压成一句“已收口”：

- **结构审计通过**：只证明定义、注册、targetType、defId、handler 覆盖、静态契约或审计测试通过。
- **代表性玩法已验证**：已经有行为级证据证明至少一条真实规则链路成立，但覆盖范围仍有限。
- **当前发布口径已收口**：当前计划发布的范围内，结构、行为、真实入口玩法与残余范围声明都已满足门禁。
- **仍有残余范围**：已经修掉部分问题，但仍有未审家族、未覆盖交互链、共享根因或待补验证。
- **旧结论失效**：旧 evidence / rollout 文档里的完成结论已被后续证据推翻，必须降级并回写原因。

#### 证据分层

审计文档必须显式区分证据层级，禁止把低层证据偷换成高层结论：

- **L1 结构证据**：`interactionTargetTypeAudit`、`interactionDefIdAudit`、`abilityBehaviorAudit`、`interactionCompletenessAudit`、注册覆盖、静态契约测试。
- **L2 领域行为证据**：Vitest、GameTestRunner、smoke、能证明 reducer/trigger/阶段流转真实生效的行为测试。
- **L3 真实玩法证据**：从真实入口触发的 E2E、手工复现截图、完整业务链观察；入口必须来自打牌、响应窗口、真实规则触发，而不是直接把 prompt 或 interaction 注进状态。
- **L4 系统时序与治理证据**：beforeScoring / afterScoring / response window / trigger queue / reaction session / deferred event / base replace / once-per-turn / 自动推进 / 跨阶段交互等系统时序链路的真实入口验证；同时包括残余范围、共享根因归类、旧结论失效回写、汇总文档降级、替代旧 claim 的新回归证据。
- **跨层通用能力必须拆层证明（强制）**：日志、撤回、聊天、反馈、换位、HUD/FAB、AI、调试面板等通用能力，不能只用系统层配置、allowlist、管线测试或底层状态证明“已接入”。必须分别写清：① 系统层是否存在；② 当前游戏 Board/页面是否挂了必要 Provider、HUD/按钮/入口；③ 玩家从真实页面能否看到并触发该入口；④ 对应测试覆盖的是系统层、页面入口层还是完整用户链。缺少第 ②/③ 项时，只能写“系统层已接入，用户入口未证明/未接入”。
- **deferred/finalize 型交互一律按 L4 处理（强制）**：只要当前交互不会立刻直接改最终权威状态，而是先写入 deferred 队列、改写待补发事件、等待 frame 收口、等待 response/interaction 关闭后再 finalize，就不能停在“prompt 能出现 / 交互能点 / 中间 state 被改了”。必须补真实入口或等价代表链证据，证明收口后的最终权威状态和后续时序都正确。
- **时序类 UI 异常的额外门禁（强制）**：若用户症状包含“弹窗半开后重开 / 一闪而过 / 动画没播 / 伤害已结算但浮字没出 / 同一交互像执行了两次”，L3 截图只能证明某一帧画面，不能单独证明生命周期正确；此时至少还要补 1 份机器可复查的时序证据（交互 id 轨迹、overlay 挂载/可见段统计、事件流到 DOM 消费日志、关键样式采样等）后，才可下“未复现 / 已修复 / 当前链路健康”的结论。

#### 门禁关系

- **只有 L1**：最多只能写“结构审计通过”，不能写“玩法完成”或“已收口”。
- **L1 + L2**：最多只能写“代表性玩法已验证”，除非再补 L3 与 L4。
- **通用能力只有系统层证据**：最多只能写“系统层已启用 / 领域行为已验证”，不得写“玩家可用 / 已完成接入”。只有 Board/页面入口和真实可见入口也被验证后，才能写“用户可见接入完成”。
- **要写“全面审计完成 / 当前发布口径已收口”**：必须同时具备目标全集清单、逐对象 D 维度结论、适用 L1/L2/L3/L4 证据、旧结论回写与残余范围说明；缺任一项都要降级表述。
- **发现共享根因或未审家族**：结论必须至少降到“仍有残余范围”，直到共享路径与残余范围被明确清掉。

### 深度审计流程（强制）

> 适用场景：用户要求“审计 / 全面核对 / 这批都看完 / 为什么审计没发现”，或当前问题已暴露出共享根因、链式交互、跨系统状态推进风险。

**核心目标**：禁止把“看过代码 / 跑过单测 / prompt 弹出来了”误报成“已经深入审计”。深审必须把**对象清单、完整链路、真实入口、共享根因、失效回写**五件事一次打穿。

#### Step 0：先建对象清单，再开始审

- 审计前必须先列出本轮对象清单；对象可以是卡牌、能力、交互链、系统函数、事件家族或反馈簇。
- 每个对象都要显式标记当前层级：
  - `L0`：只建立了对象名，还没完成结构核对。
  - `L1`：结构层已核对。
  - `L2`：行为层已核对。
  - `L3`：真实入口玩法已核对。
  - `L4`：治理层已核对，能支撑收口。
- 没有对象清单时，禁止使用“这一批已经审过 / 基本都没问题 / 还剩个别尾巴”这类汇报口径。

#### Step 1：每个对象必须串完整链路

- 每个对象至少要按下面顺序过一遍，缺一段都不能叫“深入审计”：
  - 规则/描述语义
  - 静态定义与注册入口
  - validator / canActivate / legality check
  - command / reducer / trigger / handler
  - afterEvents / postProcess / pipeline 后处理
  - UI 消费链或可见交互出口
  - 真实入口验证
- 交付文档里必须写清“本对象链路具体落在哪些文件/函数”，不能只写一个总入口文件名。
- 若读静态定义无法独立解释运行时为何会触发，即使运行时暂时能跑，也只能记为 finding，不能写“实现完整”。

#### Step 2：高风险对象必须强制打到真实入口

- 命中下列任一风险时，L3 真实入口证据为强制项，不能只靠 L1/L2：
  - response window / `smashup_reaction_choose` / 中间反应态
  - `afterScoring` / `onDestroy` / `onPlay` / `onTurnEnd` 等链式触发
  - 动态候选刷新、基地替换、位置变更、宿主离场、`setaside` / `discard` / `buried` / `attached` 等区域依赖
  - 多系统协作、watchdog、恢复态、隐藏交互、可见交互恢复
  - 同批事件结算、循环后处理、批内副作用串行推进
- 命中这些风险时，至少要证明：
  - 候选/交互从真实入口出现，而不是注入状态造出来。
  - 真实用户动作后，最终权威状态确实变化。
  - 中间态没有被单测观察面或 prompt 存在性偷换掉。

#### Step 3：共享根因必须自动扩审，不能只修当前 case

- 一旦根因落在共享 reducer / handler / hook / system / pipeline / transport，上报时必须同时给出扩审范围。
- 扩审至少覆盖：
  - 同游戏同类能力或卡牌家族
  - 同游戏共享函数/共享状态字段
  - 引擎或框架层同类调用点
  - 使用同一事件 kind / payload 字段 / helper 的其他路径
- 典型高风险专项必须单独勾选：
  - `D37`：动态刷新只说明候选会跟 live state 走，不代表 `zone/location/可打出形态` 前置条件已经完整。
  - `D40`：同批输入事件的副作用必须串行吃到最新状态，不得反复基于批次入口旧 state/core。
- 如果扩审还没做完，结论只能写“仍有残余范围”，不能抢跑成“已收口”。

#### Step 4：旧审计结论失效时，必须原地降级并回写

- 发现旧 evidence 的完成结论被新 bug、新共享根因或新链路证据推翻时，必须直接回写原文档。
- 回写至少包含：
  - 哪条旧结论失效
  - 失效原因属于哪类根因
  - 新命中的审计维度
  - 新增修复/回归/证据路径
  - 旧结论降级后的当前状态
- 禁止另写一份新文档假装“现在这份才算真相”，而让旧文档继续顶着“已审计”状态存在。

#### Step 5：退出条件必须按层级核销

- 对单个对象宣称“当前发布口径已收口”前，必须同时满足：
  - `L1`：结构入口、defId、注册、handler 覆盖已核对。
  - `L2`：代表性行为测试已证明语义生效。
  - `L3`：真实入口玩法证据已证明完整链路成立。
  - `L4`：共享根因、残余范围、旧结论失效回写已完成。
- 对整批对象宣称“这一批审完了”前，必须同时满足：
  - 清单中的每一项都有当前层级。
  - 没有对象停留在未声明的灰区。
  - 所有“仍有残余范围”的对象都已写明残余点和后续入口。

#### 深审禁区（强制）

- 只看 `validator` / 只看 `canActivate` 就结束。
- 只跑结构审计或单测，就把交互/玩法写成“已验证”。
- 只看某一张卡当前 case，不追共享函数和同类调用点。
- 发现旧审计被推翻，但不回写旧 evidence。
- 用“动态刷新有了”“E2E 打开了 prompt”“日志里发了事件”来替代最终权威状态证明。

### 禁止假阳性收口（强制）

以下证据只能证明“展示存在 / 结构有接入 / prompt 能出现”，不能单独作为玩法收口依据：

- 只证明 faction selection、横幅、房间 UI、资源展示、静态素材存在的 E2E。
- 只证明测试文件包含某个 id、`registerAbility` 出现在回归文件里、静态覆盖为零。
- 只证明 prompt / modal / interaction 被打开，未证明玩家从真实入口走到该交互。
- 通过状态注入、直接改 `sys.interaction.current`、进入 prompt 后再接管流程的注入型交互 E2E。
- 只证明按钮可点、toast 出现、日志打印，未证明最终权威状态或后续流程真的变化。
- 只证明 `prompt/modal` 打开、`pendingAttack.sourceAbilityId` 命中、`pendingDamage` 存在、`pendingBonusDiceSettlement` 出现，但未继续证明最终权威状态与临时态清理。

出现上述情况时，文档必须明确标注为“展示证据 / 结构证据 / 注入型交互证据”，不得偷换成“完整玩法验证”。

### 回归问题处理流程（强制）

> 适用场景：用户明确说“之前正常现在不行”、或怀疑回归、或本轮修改后出现旧功能异常。

1. **先判定是不是回归，再写“回归处理记录”**：一旦用户表达“以前能用现在不能用 / 又坏了 / 回归 / 怀疑回归”，第一步不是改代码，而是确认它是否能被历史行为、旧测试、旧截图、旧 evidence 或用户明确记忆定义为回归。必须在本轮 evidence / progress / 对话记录中先写清“当前症状、用户原话、初始复现方式、首跑结果、是否判定为回归”。如果尚未复现或尚未找到历史行为，必须标为“待复现 / 待定性”，不得先把实现改到自己预期的状态。
1.1. **不得改写用户症状（强制）**：用户说“两次从小到大”，就只能按“两次从小到大”去复现、记录和汇报；禁止在没有证据的情况下把它改写成“像重开”“像二段动画”“像先小后大再稳定”这类相近但不同的表述。若当前证据只支持相近现象，必须明确写“复现到了相近现象，但尚未复现用户原话中的完整症状”。
1.1.1. **数量级描述不得降级（强制）**：用户明确说“全部消失 / 全部没了 / 所有都错 / 整个区域乱了”时，必须按“全量对象/整块区域”建立复现和断言；禁止在未复现全量症状时，把目标降级成“单个对象消失 / 部分元素被过滤 / 某个按钮不见”。如果当前证据只证明了单个或部分对象异常，必须直说“只复现到部分异常，尚未复现用户说的全部消失”，不得据此直接宣称命中原 bug 并开改。
1.2. **未复现就直说未复现（强制）**：如果当前测试、截图、日志或探针只复现到部分现象、相近现象或另一条链路的异常，结论必须直写“未复现用户描述的原症状 / 仅复现到相近现象”，不得用推测性语言把未复现包装成已复现。
2. **先定义“最后正常证据”**：必须给出至少一个可复查证据来源（`git log` / `git show` / 历史截图 / 旧 E2E 产物 / evidence 文档）。如果找不到，必须明确写“尚未找到最后正常证据”，并把这条不确定性作为风险点记录。
3. **先找导致回归的提交，再做实现归因**：必须使用 `git blame`、`git log -S/-G`、`git show` 或必要时 `git bisect` 找到疑似引入提交/提交范围，并记录该提交具体把哪条历史行为改坏了。禁止只凭当前代码猜根因后直接改。
4. **先 diff 引入提交，再决定修复**：对比最后正常版本、引入提交与当前版本的具体文件（`git show <commit>:<file>` 或 `git diff <good> <bad> -- <file>`），先列出引入提交的关键 hunk，再提出根因假设。禁止“先假设→重写→再找证据”的顺序。
5. **回归成立时默认还原引入提交的错误 hunk（强制）**：回归修复默认目标是恢复最后正常版本的行为/表现，修复方式默认是对导致回归的提交做最小范围还原修复：只还原或等价恢复造成回归的 hunk，不顺手回滚该提交的无关改动。受项目 git 规则约束，未经用户确认不得执行 `git revert` / `git reset` / 强制 `git checkout`；需要还原时优先用手工最小补丁恢复正确行为。
6. **禁止自创替代逻辑绕过回归还原**：回归成立后，禁止在没有权威依据的情况下重新设计一套“看起来更合理”的新逻辑替代历史行为。只有同时满足以下条件，才允许偏离还原路径：① 找到明确的用户故事、规则文档、卡面/规则书、已合并需求或用户当轮指令证明最后正常行为已经被业务上替换；② 写清为什么不能直接还原引入提交；③ 获得用户确认或用户当轮已经明确要求采用新口径。否则一律按引入提交还原修复。
7. **最小改动优先**：在“还原引入提交错误 hunk / 恢复最后正常行为”目标下，优先选择最小变更面；只有当 diff 无法定位或根因属于共享抽象缺陷时，才升级为结构修复，并且必须说明结构修复如何等价恢复最后正常行为。
8. **根因归类**：必须标注根因类型（数据/录入、单点实现、共享抽象、架构/时序），并说明为何不是其它类型。
9. **红测/首跑失败必须保留为证据**：回归修复的首个失败用例、失败截图、失败状态快照或失败断言必须写入 evidence；最终绿测不得覆盖或删除首跑失败事实。若首跑失败暴露出与用户问题不同的新异常，必须新增“新异常归因”小节，说明它是修复目标的一部分、测试构造问题，还是同链路残余风险。
10. **不得用换场景绕过失败**：如果修复中的 E2E 因额外 prompt、reaction session、重复触发、异步队列等同链路异常失败，默认先当作潜在回归调查。只有证明该异常来自测试场景无关干扰或已有独立覆盖，并在 evidence 写清理由，才允许收窄场景；收窄后仍必须保留一条能证明用户原始问题成功路径的真实入口 E2E。
11. **验证与证据**：至少补 1 条与回归直接相关的验证路径。UI 回归必须有 E2E + 截图证据；引擎/规则回归必须有 GameTestRunner 或单测断言。若问题涉及“写入点 -> 候选/高亮 -> 用户选择 -> validator/handler -> reducer 最终状态”，验证必须覆盖整链，不能只断言中间额度、prompt 或候选存在。
11.1. **已验证 UI 入口的最小还原例外（强制）**：如果回归修复只是把被误删的既有 UI 入口、`data-testid`、state 同步或 payload 字段等价恢复到最后正常实现，且已有历史 E2E / evidence 证明该入口曾走通过，本轮没有改变布局、样式目标、选择器语义、点击路径、路由或跨系统链路，则不得机械套用“UI 回归必须 E2E”。此时应优先使用能直接证明恢复点的最窄验证：相关单测/集成测试、`eslint`、`typecheck`、或提交 hook。若最窄验证无法证明用户可触达入口，或本轮改动实际触及视觉/路径/选择器/浏览器专属行为，才升级到 E2E + 截图。
11.2. **代理按钮不得绕过当前交互合同（强制）**：当中间壳层、等待层、快捷按钮、悬浮条或其他 UI 代理控件代表当前 `simple-choice / reaction session / prompt` 执行“让过 / 跳过 / 完成 / 确认”时，修复与验证必须同时锁两件事：① 真实承接者是谁（当前交互还是旧并行命令）；② 代理按钮最终发出的 payload 是否与当前 live 交互合同一致（如 `optionId: pass / skip / __emergency_skip__`）。禁止只验证“按钮显示了 / 可以点 / dispatch 被调用了”，却不验证它命中的仍是当前交互；也禁止继续沿用旧命令去旁路当前 live prompt。至少补 1 条失败用例直接断言：点击该代理按钮后，发出的命令类型与 `interactionId / optionId` 命中当前真实交互，而不是历史兼容命令。
12. **回归扩审**：完成修复后按“同类扩审”规则扫同类入口，记录命中点与未命中理由。若暂未扩审完，最终口径只能写“当前点位已修复，仍有残余扩审范围”，不得写“已收口”。若旧证据曾写“有测试 / 测试覆盖 / 可玩 handler + 测试”，还必须回查旧测试是否真的断言了正确语义；旧测试断言旧规则、旧文案或错误语义时，必须标成旧测试失效。

**回归处理输出必须包含**：
- 用户原始问题、首跑复现结果与“是否判定为回归”（含失败断言/截图/状态快照路径）
- 最后正常证据来源与日期
- 疑似引入提交/提交范围与归因依据
- 引入提交 diff 命中的关键 hunk
- 根因说明与修复策略
- 是否采用“还原引入提交错误 hunk”的修复；如未采用，必须写明权威依据、不能还原的原因和用户确认来源
- 修复中出现的新异常及处理结论（如无则写“无”）
- 验证命令与证据路径
- 扩审范围与结果

### 指定“最近合并 PRxx”为权威基线时的红测归因（强制）

> 适用场景：Owner/用户明确要求“全都以最近合并（例如 PR63）为准”，或明确指定某个 merge commit 作为权威口径。

**核心约束**：必须严格对照 PR 基线实现 / 当前实现 / 测试断言，**不得默认判定“测试过时”或“实现回归”**。若该 PR 为主动修改，且与权威描述一致、确实解决问题，则直接按合并口径更新测试/证据；否则必须先询问用户后再裁决。

1. **锁定权威基线提交**：用 `git log --merges -n 20 --oneline` 找到对应 PR 的 merge commit（记录完整 commit id）。
2. **对每个失败用例列三份事实**（必须写清楚）：
   - **PR 基线实现**：`git show <mergeCommit>:<file>`（实现当时到底做了什么）
   - **当前实现**：`git show HEAD:<file>` / 工作区实际文件（现在做了什么）
   - **当前测试断言**：测试到底在断言什么（交互结构、字段、事件、错误文案等）
3. **先判定 PR 主动修改是否成立**：
   - **成立且与描述一致、确实解决问题** → 直接按合并口径更新测试/证据（必要时同步实现对齐）。
   - **不成立或无法确认** → **必须先询问用户**，再进入下方裁决。
4. **裁决类型（必须三选一）**：
   - **测试过时**：测试断言与 PR 基线实现不一致 → **优先改测试**（把测试更新到权威口径）
   - **实现回归**：当前实现偏离 PR 基线实现，且无明确业务变更理由 → **优先改实现**（恢复到权威口径）
   - **业务变更**：PR 基线后存在明确的业务变更（merge 说明、evidence、规则更新）→ **改测试 + 补证据**（不能只改实现硬凑）
5. **最小验证要求**：
   - 至少跑到“失败的那个测试文件/用例”并通过（给出命令）。
   - 若失败用例涉及交互链/结算链，除单测外还应补 1 条更贴近真实链路的验证（smoke / GameTestRunner / E2E 任选其一，按改动层级决定）。

### Bug 修复后的同类扩审（强制）

- **先定根因，再扩审**：必须先确认 bug 是由哪个事件类型、状态字段、调用模式、共享 reducer/handler/hook/system、阶段时序或 UI 消费链路导致，再据此横向搜索；禁止只按表面文案或单个卡牌名做浅层搜索。
- **扩审范围必须覆盖共享层**：至少检查四层中的相关命中项：① 同游戏同类能力/组件 ② 同游戏共享 reducer/handler/hook/system ③ 引擎/框架层共享流程 ④ 复用同一事件类型、状态字段或 helper 的其他调用点。
- **推荐搜索维度**：根因关键词、事件 kind、payload 字段名、状态字段名、生命周期钩子名（如 `onPhaseEnter`/`onPhaseExit`/`afterEvents`）、共享 helper 名、同类描述语义。必要时组合 `rg` 多轮搜索，而不是一次搜不到就结束。
- **命中后的处理原则**：命中同类问题时，默认继续修到共享根因被消除，或明确写出“该命中点为何不受影响”的判定依据；禁止只挑当前用户提到的那一处修复。
- **交付口径**：修复总结必须说明“搜索了什么、覆盖到哪里、命中了什么、哪些已一并修复、哪些确认不受影响”。没有这部分，视为扩审未完成。
- **测试覆盖声明必须对账**：凡 evidence 或对外汇报写“有测试 / 测试覆盖 / 可玩 handler + 测试”，且对象语义包含选择、然后、可以、至多、任意数量、抽弃、prompt 或 simple-choice，必须写清测试断言覆盖的最终权威状态、玩家选择路径、负向路径或边界输入。只写 tests passed、测试文件名、用例数量或 handler 名，不能支撑语义正确。

### 根因分级与处置（强制）

- **根因分级**：每次修 bug 都必须先判定属于以下哪类：① 数据/录入缺陷 ② 单点实现缺陷 ③ 共享抽象缺陷 ④ 架构/时序/系统边界缺陷。
- **处置原则**：前两类可局部修复，但仍要检查是否已经外溢成共享问题；后两类默认必须优先修改共享抽象、统一 reducer/handler、流程时序或系统职责边界，不能仅在单个调用点打补丁。
- **设计问题优先重构**：如果根因是共享抽象错误、职责重叠、时序窗口错误、隐式依赖或架构假设不成立，应直接按 D8、D17、D23、D41、D43、D45 等维度审查，并以重构消除根因，禁止为了“先过当前 case”继续累积技术债。
- **同类语义分叉建模必须记为 finding（强制）**：如果同一类语义在同一游戏里同时落在两条或更多抽象路径上（例如一部分走数据驱动注册，另一部分靠 `flowHooks` / `if (abilityId === ...)` 特判），即使当前运行时看起来正确，也必须按 `D3/D23/D33` 记为结构性 finding，不能因为测试通过就忽略。
- **定义层与执行层必须双向自洽（强制）**：审计同类能力时，不能只验证“运行时能触发”，还必须反查“静态定义能否独立说明自己为什么会触发”。如果读定义层无法推导出真实执行链，就算测试通过，也不能写成“实现完整”。
- **临时方案约束**：只有在范围失控、风险过高或用户明确要求先止血时，才允许临时方案。采用临时方案时，必须同时记录残留问题、未修范围、回填方案与触发条件，不能把临时补丁伪装成最终修复。
- **重构完成定义**：当你判断需要重构时，完成标准不是“当前 case 通过”，而是“共享缺陷入口被消除、遗留分支已清理或已明确登记、同类场景已有回归验证”。

### 审计文档最低模板（强制）

审计文档建议命名为 `evidence/<game-or-module>-<scope>-audit-YYYY-MM-DD.md`，推荐直接套用 `docs/ai-rules/audit-evidence-template.md`，至少包含以下内容：

1. **审计范围**
   - 本轮覆盖哪些文件、哪些卡牌/模块、哪些共享链路。
2. **结论等级**
   - 必须从“结构审计通过 / 代表性玩法已验证 / 当前发布口径已收口 / 仍有残余范围 / 旧结论失效”中明确选择，禁止写含糊总评。
3. **权威来源**
   - 规则书、官方 FAQ、Wiki、设计文档、接口文档等。
4. **逐项结论**
   - 每张卡/每个能力/每个模块一条，禁止只写总评。
   - 每条至少写清：描述语义、实现入口、命中维度、判定结论、对应证据层级（L1/L2/L3/L4）。
5. **验证证据**
   - 已运行的测试、日志、截图、命令、人工观察结论。
   - 需要注明哪些是结构证据，哪些是注入型证据，哪些是真实入口玩法证据。
6. **共享根因与残余范围**
   - 明确哪些问题属于共享路径，哪些家族/交互链仍未覆盖，禁止把局部修复写成整体完成。
7. **修订记录**
   - 若本对象曾被标记为“已审计”，本轮又发现漏项，必须追加“失效结论/修订原因/新增回归/替代旧 claim 的新证据”。
8. **测试语义对账与同类扩审**
   - 只要文档使用“有测试 / 测试覆盖 / 可玩 handler + 测试”作为正向证据，必须写清测试断言的语义覆盖范围；只要文档记录漏审、回归或用户反馈修复，必须写同类扩审关键词、搜索范围、命中项和未完成扩审范围。

### 审计后自检（强制，不接发布门禁）

凡 evidence 或审计汇报要使用以下任一口径：

- “全面审计完成”
- “当前发布口径已收口”
- “当前代码验证口径已收口”
- “已审计”
- “已收口”
- “已审计完成”
- “对象级审计已收口”
- `full_audit` / `full_audit_e2e_verified`

必须先运行：

```text
npm run audit:evidence:selfcheck -- <evidence 文件>
```

并把命令与结果写回 evidence。该命令是**审计完成后的自检**，不默认接入 release、deploy、pre-push 或提交钩子；发布流程是否放行仍由发布门禁自己决定。该脚本默认只检查已跟踪或已暂存变更中的 `evidence/**/*.md`，避免无关未跟踪草稿互相阻塞；未跟踪新 evidence 必须显式传文件路径，或使用 `--include-untracked`。也可以用 `npm run audit:evidence:all` 做全量历史债务扫描。脚本检查的是**留档是否具备资格**，不是规则本身是否正确；脚本通过后仍必须按 D 维度和 L0-L4 证据人工审计。

脚本会强制检查“全面审计自检表”。凡声称“当前发布口径已收口 / 当前代码验证口径已收口 / 全面审计完成 / 已审计 / 已收口”的 evidence，前部必须有该表，并逐项列出 `对象全集`、`规则子句表`、`完整技能流程矩阵`、`L0-L4 证据层级`、`命中 D 维度`、`真实入口 E2E 与截图核验`、`测试语义对账 / 旧测试失效检查`、`同类扩审记录`、`残余范围声明`、`旧 evidence / 旧结论对账回写`。这些项必须是 `passed`；只要仍有 `representative_only`、`blocked` 或 `scoped_debt`，结论必须降级，不能继续写“已审计 / 已收口”。若 evidence 声称“当前发布口径已收口 / 全面审计完成”，正文里不得残留 `待补`、`pending`、`needs_l3_l4`、`仍未收口` 或等价未完成标记；这类矛盾必须先补证据或降级结论。脚本还会对较轻量的 evidence 做两类硬检查：① 声称“有测试 / 测试覆盖 / 可玩 handler + 测试”且命中选择、然后、可选或抽弃等语义时，必须写测试语义对账或旧测试失效检查；② 记录漏审、回归或用户反馈修复时，必须写同类扩审记录和漏审归因。

脚本失败时只能做三件事：

1. 补齐 evidence 必填结构和证据；
2. 把结论降级成“结构审计通过 / 代表性玩法已验证 / 仍有残余范围”；
3. 若旧结论被推翻，原地回写“旧结论失效”。

提交 / push / 发布口径：`audit:evidence:selfcheck` 只限制审计文档继续声称“已审计 / 已收口 / 全面审计完成”，不是默认 git 提交、push、release 或 deploy 硬门禁。脚本失败时可以继续走发布流程，但审计结论、汇报和相关 evidence 必须降级或保留残余范围，不能继续写“全面审计完成 / 已审计 / 已收口”。

禁止把脚本失败解释成“脚本太严格”，然后继续对外说“已全面审计 / 已收口”。如果本轮漏审暴露出脚本还拦不住的结构缺口，必须同步补 `scripts/verify/audit-evidence-completeness.mjs` 或本规范。

## 二、测试工具选型（辅助手段）

> **核心原则**：GameTestRunner 行为测试最优先，审计工具是补充。

### 效果数据契约测试（强制）

新增游戏/英雄/卡牌/Token 定义时必须同步编写。职责：结构完整性 + 语义正确性。数据定义必须包含所有执行所需字段，禁止执行层"猜测"。

## 三、E2E 测试选择器一致性检查（强制）

> **重构 UI 交互模式后必须执行**。UI 组件的渲染方式变更（如从弹窗改为内联横幅）时，所有引用旧选择器的 E2E 测试必须同步更新。

**检查清单**：

1. **选择器来源验证**：E2E 测试中的 `data-testid`/CSS 选择器/文本匹配，必须对应实际渲染的组件。重构后用 `grep` 搜索旧选择器，确认所有 E2E 文件已更新。
2. **交互路径验证**：测试中的点击/输入序列必须与实际 UI 交互路径一致。例如：手牌选择在 HandArea 中直接点击 vs 在弹窗 overlay 中选择，两者选择器完全不同。
3. **按钮文本验证**：按钮文本来自 i18n，测试中的正则匹配必须覆盖中英文两种 locale（`/Confirm Discard|确认弃牌/i`）。
4. **状态验证**：测试必须验证 UI 状态变更（如 `data-selected="true"`），不能只验证"点击了按钮"。

**典型反模式**：

- ❌ 重构了交互模式（弹窗→横幅），E2E 测试仍查找旧弹窗选择器 → 测试超时/skip，从未真正执行
- ❌ 测试中硬编码了组件内部 CSS 类名（如 `.card-selector-overlay`）→ 样式重构后测试失效
- ✅ 使用 `data-testid` + 按钮文本匹配，与实际渲染组件对齐
