# E2E 与截图验收规范

> 本文从根 `AGENTS.md` 迁出 E2E 和截图验收细则。根文件只保留入口，详细规则以本文为准。

## 适用边界

- 默认 E2E：使用专用测试模式和状态注入，验证 UI 交互、可见结果和用户操作链路。
- 真实开房链路：仅当本轮要证明房间创建、联机同步、`setupData -> runtime`、权限/座位/多端同步等跨入口合同时使用。
- 如果状态注入已经覆盖用户症状，不能把真实开房当成默认升级；如果真实房间链路能证明更多，必须在测试名、evidence 和汇报中写明它额外证明了什么。

## 三板斧与入口分层

1. **三板斧默认口径（强制）**：本项目的 E2E 默认按三板斧执行：① 使用现有 Playwright fixture / 专用测试模式；② 从离目标语义最近的真实入口起跑；③ 用状态注入或代表态把场景直接推进到问题位点。缺任一斧，都不能算“已经按默认 E2E 方式验证”。
2. **默认不从主页起跑（强制）**：如果本轮目标是验证游戏内流程、牌桌交互、阶段流转、HUD、动画、结算或刷新恢复，默认直接从 game route / match route / 代表态起跑；不得机械先走主页、大厅、进房这段前置漏斗。
3. **“开局”默认指当前合同的最近起点（强制）**：在游戏流程语境里，说“从开局验证”默认不是指“从主页点到进房再打一整局”，而是指“从当前要证明的游戏合同最近的起点开始”。例如验证抓牌、弃牌、近终局、刷新恢复时，最近起点通常是 `match route`、首轮代表态或近终局代表态，而不是首页。
4. **主页/大厅进房 与 游戏内流程分层（强制）**：`从主页进入` 和 `进入 match 后的游戏流程` 是两个不同合同。前者证明入口漏斗、房间创建、加入、路由或权限；后者证明具体游戏可玩性。除非本轮目标是整条漏斗都要收口，否则不得绑成同一条大 E2E。
5. **刷新恢复 / 终局复盘 / spectator 也属于独立合同（强制）**：这些链路默认单独建用例，从其最近的可注入代表态起跑；不要附着在主流程后半段顺手验证。

## 组合式验证与长链预算

1. **组合式验证优先（强制）**：完整流程优先拆成“入口合同 + 代表态合同 + 高风险分支合同 + 黄金链”组合证明，而不是把所有风险塞进一条超长 E2E。证明完整流程成立，靠组合覆盖矩阵，不靠重复从头跑到底。
2. **长链默认只保留少量黄金链（强制）**：需要自然完整对局、多人长轮转、真实 AI 串行托管时，只保留少量黄金链证明“整局能跑通”；其它回归优先收成注入态、单轮 roundtrip、近终局、刷新恢复、分支选择等窄合同。
3. **单条用例时长必须受预算约束（强制）**：默认目标是单条 E2E 尽量控制在 `3` 分钟内；超过 `5` 分钟的单条用例必须有明确理由，并优先评估能否拆成组合式验证。若某条链已经长到“比正常一局还久”或容易因时间累积放大环境噪声，默认视为设计异味。
4. **单文件总时长也要受预算约束（强制）**：默认优先把单个 E2E 文件控制在可快速回归的量级；当单文件逐步逼近或明显超过 `10` 分钟时，必须优先评估拆文件、拆主题、拆黄金链，而不是继续往同一文件里堆。
5. **长链例外必须写明价值（强制）**：如果保留一条超过预算的完整自然链，测试名、evidence 与汇报里必须显式写清它独有证明点，例如“只这条能证明多人自然终局”“只这条能证明高人数 repeated-refresh”。没有独有证明点的长链应拆掉。
6. **同一目标不得把长链重跑当默认调试循环（强制）**：同一个问题若第一次长链失败后仍未锁定根因，最多只允许在有明确新假设或新改动的前提下再重跑一次；若第二次仍未锁定，就必须退回代表态注入、局部合同或更低层测试，禁止继续无差别重复自然开局。
7. **单次问题定位必须有总时长预算（强制）**：默认把“为定位同一个问题反复跑长链验证”的总预算控制在 `15` 分钟内。超过该预算仍未拿到直接证据时，必须暂停继续堆长链，改做合同拆分、状态注入、日志/快照补证或更低层验证。
8. **实现推进与收口验证必须分阶段（强制）**：E2E 的职责是证明真实入口和可见结果，不是主调试器。默认节奏应是：先用状态注入或低层验证锁定实现缺口，再改代码，再用最窄 E2E 收口；禁止长时间停留在“反复跑 E2E 看哪里又不对”的循环里。
9. **45 分钟级单问题测试循环默认视为失守（强制）**：如果围绕同一个问题的测试与重跑已经明显拉到 `45` 分钟量级，却仍主要停留在到达目标位点之前、或还在反复确认同一条长链能不能走通，默认应判定为“三板斧失守”；必须立即拆成状态注入、组合式合同或更低层验证，不能继续把长链时间堆高。

## 定位顺序与停线动作

1. **游戏内问题默认先打到问题位点（强制）**：当目标是牌桌进行时、单回合交互、HUD、终局、复盘、刷新恢复或单个动画问题，默认先直达 `game route / match route / 代表态`，而不是先从主页起跑再自然打到那里。
2. **真实开局只证明它独有的合同（强制）**：如果当前要验证的是“从主页进入”“创建房间”“加入房间”“claim seat”“setupData -> runtime”这类漏斗合同，可以跑真实开局；否则它不能作为默认起点，更不能因为“更真实”就吞掉后续游戏内合同。
3. **停线条件必须明确（强制）**：一旦出现以下任一情况，必须立刻停止继续拉长链路，并改走拆分验证：
   - 同一目标已经重复跑了两次自然链；
   - 单条链路明显比正常一局还久；
   - 当前失败点仍停留在“没到问题位点前就先挂了”；
   - 这条链路证明的主要是前置漏斗，而不是本轮真正要改的游戏逻辑或 UI。
4. **重新起跑前必须先说清这次多证明了什么（强制）**：准备再跑一条长链前，必须能明确回答“这次与上一条相比，新增证明点是什么”。如果回答不出来，默认不该再跑。

## 桥接式组合验证（强制）

当一条完整玩法既要证明入口，又要证明 `match` 内多个中后段语义时，默认拆成下面三段，而不是硬跑一条自然终局长链：

1. **入口黄金链**：只证明真实入口、建房/入房、首个可行动回合、座位/权限/同步语义成立。
2. **中段代表态链**：直接注入到本轮真正关心的 `match` 内位点，例如 `draw/discard`、waiting、stacked/live、spectator、reload。
3. **终局前代表态链**：直接注入到 near-end、最后一弃、review 前一跳等位点，证明终局切换与复盘语义。

- 三段组合起来，才是“完整流程已被分层证明”；禁止把“没有单条从主页自然打到终局”偷换成“没有证明完整流程”。
- 入口黄金链只需要跑到它负责的合同 seam，不需要天然承担 review、spectator、终局前最后一弃等所有后段证明。
- 如果一条测试已经同时想证明入口、第二轮身份、AI 中段决策、near-end、review、reload，它默认已经超出单链应承担的合同数量，必须拆。

## E2E 测试强制要求

1. **UI 交互必须用 E2E**：必须使用三板斧（fixture / 专用测试模式 + 最近入口 + 状态注入/代表态）；UI 交互、多玩家协作、动画特效都不能用单元测试代替。
2. **必须实际运行并通过**：AI 编写后立即运行 E2E；单文件/单用例优先用 `npm run test:e2e:ci:file -- <测试文件名> "<用例名>"`，整文件复跑用 `npm run test:e2e:ci -- <测试文件名>`，禁止交给用户。
3. **必须实际打开截图验收**：优先看 `test-results/evidence-screenshots/_shared/`，失败用例再补看 `test-results/playwright-artifacts/`；验收标准不是“页面出现了”，而是“本轮问题位点已按要求修好”。
4. **最终达标截图必须主动打开，未达标候选图不得打开（强制）**：凡是靠截图收口 UI 结果，必须真的把关键图打开后再下结论。若当前会话提供 `view_image`，先用 `view_image` 核图；只有当你已经确认“这张图本身满足本轮需求、可作为最终收口证据”时，才执行 `npm run verify:open-image -- <截图绝对路径>`，或在需要一次打开多张时执行 `npm run verify:open-image -- <截图绝对路径1> <截图绝对路径2>` 主动打开同一批关键图作为 closeout 动作。不得把它理解成“每跑完一次 E2E 都顺手开一次图”；中间失败图、排查候选图、尚未达标图一律不打开。
5. **只要最终回复里提到“已跑 E2E / E2E 通过”就必须附截图绝对路径**：至少提供 1 张本轮实际核对过的关键截图完整绝对路径；没有路径不得以 E2E 结果作为收口口径。
6. **用户明确要求“端到端截图 / 实机截图 / 页面截图”时，禁止用替代图冒充交付（强制）**：不得用本地静态 HTML harness、局部渲染拼图、组件孤立页、Storybook 式沙盒、手工 clone DOM、设计稿复刻图或任何脱离真实页面链路的截图替代真实截图。若真实链路截图被环境、构建或服务 blocker 卡住，只能停下并汇报 blocker 与最小补救动作；禁止先交一张“辅助理解图”再把它说成端到端证据。
7. **用户直接要“截图 / 图 / 看图”时，默认也只允许交真实截图（强制）**：这里的“真实截图”包括真实页面截图、真实开发工具页面截图、真实运行时截图、真实设备截图；不包括手工叠加图、临时合成图、脚本后画标签图、辅助示意图、局部拼接图、裁完再重排的讲解图。除非用户明确说“先给辅助图理解一下”，否则不得把这类图片当成默认交付。
8. **辅助图只能显式降级为“排查辅助”，不得混称为截图证据（强制）**：如果为了定位问题确实临时生成了叠加点位图、手工标注图、裁切放大图、合成对照图，必须在同一条回复里直接标明“这不是截图真相，只是排查辅助图”，并且不得用它替代用户原本要求的真实截图。真实截图一旦拿不到，只能承认“当前没有真实截图证据”，不能继续拿辅助图收口。
9. **新 UI / 改 UI 默认必须先补真实页面截图再收口（强制）**：凡本轮新增或修改了页面、弹窗、菜单、浮层、toast、徽标、列表、表单、布局或其它用户可见 UI，即使用户没有单独追问截图，也必须至少补 1 张真实页面链路截图；若改动包含多个关键态（例如入口态、展开态、成功态），则必须按关键态分别截图。没有真实页面截图时，只能汇报“代码已改/测试已过”，不得表述成“UI 已确认”或“可以收口”。
10. **局部 UI 改动不得被“只改了一小块”豁免（强制）**：像登录态切换、名字入口、头像、积分徽标、通知红点、下拉菜单、账户面板、按钮文案、tab、角标、空态、单个弹窗壳层这类看似局部的可见改动，只要用户肉眼能直接看到变化，就仍然属于截图验收范围。不得因为“没改路由/没改主布局/只是复用现有组件/已有单测”就跳过真实页面截图。
11. **用户可见状态切换至少覆盖前后两态（强制）**：当本轮修复的是“点击前后不一致”“已登录/未登录态不同步”“展开前后内容不一致”“弹错弹窗/菜单”等状态切换问题时，截图至少要覆盖 `触发前` 和 `触发后` 两张；若只给其中一态，视为未证明问题已闭环。
12. **“流程跑通”默认按关键决策对截图（强制）**：当汇报口径包含“流程已跑通”“从开始到结束可完成”“端到端链路已收口”时，证据不得只给终点图或零散成功图。至少要按真实主流程列出每个核心决策位的 `触发前 -> 触发后` 截图对，例如创建前/创建后、摸牌前/摸牌后、确认前/确认后、结算前/结算后。若某一步没有截图对，只能说该局部链路已验证，不能上升为“整条流程已跑通”。
13. **关键决策前图必须自带下一步可操作性（强制）**：凡是拿来证明“流程仍可继续”的 `触发前` 截图，画面里必须让人一眼看出下一步主操作落在哪里。允许形式包括：真实主按钮、真实候选对象、本体可点击卡牌/牌堆/格子、明确的 owner prompt 或等待归属提示；但不允许出现“合法状态存在、却像页面卡死/没东西可点/不知道点哪里”的前图。若当前规则只剩单一合法动作，UI 必须把这一步做成显式可发现的下一步入口或短提示；否则该图直接判为不合格证据。
14. **用户要“基本流程端到端截图”时，必须逐步写清“点哪里继续”（强制）**：如果用户要的是“看懂一款游戏怎么运作”的基础流程，而不只是证明某条 bug 已修好，那么最终交付不能只是一串截图路径。必须按步骤列出：当前这张图在做什么、下一步要点击哪个现实对象、点击后会进入什么结果。`点哪里` 必须先说玩家看得到的对象名，例如“点击手牌中的这张牌”“点击地图上高亮的地区”“点击右侧确认按钮”；不得只给代码字段、locator 或内部 test id。若这条流程本身是教程/新手引导，首个正式牌桌截图还必须先把本轮正式行动讲清，并直接对应玩家真实可执行的动作；不得只讲“来源”“节奏”“先看哪一排”这类抽象概念。若教程对外口径写的是“基础教程会覆盖完整引导流程”“教程结束”“已经学会核心行动”，则截图和步骤至少要覆盖每一种正式行动各一次，并覆盖其后的必要收口动作；若只演示局部来源、只跑其中一种行动路线、或只有两步示意，只能表述为“局部教学片段”，不得上升为“完整教程已覆盖”。
14. **几何居中/对齐问题必须验证真实几何中心，不能拿固定槽位冒充（强制）**：当本轮问题是“居中是否为真”“宽度改了后会不会漂”“对象是不是仍然对齐到承载区中线/轴线”，E2E 断言必须直接测量目标对象组的几何中心（例如一组牌的 `group center`）与承载容器中心或目标轴线的偏差，并写明允许阈值。禁止继续用“前两张还落在历史第 1/2 槽”“和旧截图某几个 x 坐标差不多”“少牌时看起来没有更歪”来替代真实居中验证。
15. **几何稳定性至少覆盖两种数量或尺寸状态（强制）**：只在单一牌数、单一宽度、单一视口下量一次，不能证明“改宽度也不漂”。像牌河、弃牌区、头像列、按钮组、导航居中这类会随数量或尺寸变化的对象，默认至少比较 `低数量/窄状态` 与 `高数量/宽状态` 两态，并同时确认：对象组中心对齐、单体宽高未被偷偷改大、上下排或前后态仍共用同一中线/锚线。
16. **用户质疑“真实窗口里的大小/占比”和 E2E 不一致时，必须补多宽度桌面证据（强制）**：只要问题点涉及“真实浏览器里更大/更小”“窗口一变就不像同一套 UI”“E2E 截图比例不真”，默认至少补 `宽桌面` 与 `较窄真实桌面` 两档浏览器级证据，并同时记录真实视口宽度、目标对象宽高或关键容器宽度。禁止继续只拿单一 `1920x1080` 理想桌面截图，或只凭一句“CSS 没变所以应该一样”收口。
17. **尺寸争议必须优先取同一真实浏览器会话的运行时视口与元素读数（强制）**：只要用户明确说“看我浏览器真实截图”“这和我实际 Chrome 不一样”“我要你读元素尺寸而不是只看图”，就不能再用独立 Playwright 新开窗口或另一套固定 viewport 代替当前会话。默认必须先从同一真实浏览器会话读取 `运行时视口宽高`、`devicePixelRatio`、页面根上的运行时 viewport 变量，以及目标元素的 `getBoundingClientRect()` 结果，再拿这些读数和 E2E 结果对照。禁止把“E2E 里 1920 截图正常”当成“用户当前 Chrome 也正常”的证据。
18. **固定牌桌的共享中线与尺度链必须在同一真实会话里同时验证（强制）**：当桌面牌桌声称“中央牌区、手牌区、顶栏仍是同一套正式 UI”时，断言必须同时量出这些区域的几何中心线与关键卡牌尺寸，并确认它们共用同一条中线/同一套缩放结果。禁止一块区域靠 `calc(100vw - Npx)`，另一块靠独立 `right/bottom` 魔数，第三块再靠额外 `transform: scale(...)`，最后只凭截图“看起来差不多”就收口。
19. **真实浏览器旧 tab 若仍挂旧 bundle / 旧尺寸链，不得直接拿来否定当前代码（强制）**：当真实 Chrome / Edge / 原生 WebView 里已经存在历史打开的房间页、旧对局页或长时间未刷新的 tab 时，必须先读取该页当前运行时 CSS 变量、关键元素尺寸或其它版本指纹，确认它确实对应当前代码现场；若读到的运行时公式、关键变量或关键几何仍是旧值，就只能把它归类为“历史现场/过期 bundle 证据”，不得继续拿它和当前工作树代码、当前 E2E 结果做一对一归因。此时默认动作是：在同一真实浏览器会话里新开一个当前开发环境房间或强制进入当前页，再复测同状态尺寸。
20. **尺寸争议的最终裁决必须补“新真实房间 + 同状态复测”（强制）**：当用户指出“真实浏览器里的牌大小和当前 E2E 不一致”，并且已发现旧 tab 可能挂着历史 bundle 时，最终不能停在“旧 tab 是旧的”这句解释上。默认必须再在同一真实浏览器会话里创建一个新的当前开发环境房间，把它推进到与 E2E 同类的牌桌状态（至少相同视口档、相同牌数档），然后重新读取关键卡牌宽高和容器宽度。只有这份“新真实房间同状态复测”结果，才可作为当前代码是否仍分叉的最终依据。
21. **死端口旧页 / 浏览器错误页不得当真实现场证据（强制）**：如果所谓“真实 Chrome 页面”已经掉成 `chrome-error://chromewebdata/`、正文出现 `ERR_CONNECTION_REFUSED`，或它指向的本地开发端口与 `.tmp/dev-runtime-ports.json` 里的当前前端端口不一致且目标端口未监听，那么这页只能归类为“失活开发页/浏览器错误页”，不得继续当成当前 UI 现场、真实页面截图证据，或拿来否定当前代码。默认先核当前活跃开发端口、该页目标端口是否仍可访问，再决定是否新开当前真实页复测。
22. **真实浏览器验收前必须先判活当前开发端口（强制）**：凡是要用真实 Chrome / Edge 当前会话做本地开发页验收，至少先确认三件事：① `.tmp/dev-runtime-ports.json` 记录的当前前端端口；② 目标 tab 实际指向哪个本地端口；③ 该端口当前是否还能返回开发前端资源（例如 `/@vite/client`）。三者未对齐前，只能继续诊断“页是不是旧的/端口是不是死的”，不得直接把截图或页面表现上升为当前实现结论。
23. **活端口旧 tab 也可能挂过期运行时，不能只凭端口存活就当当前实现（强制）**：即使目标页仍指向当前活跃开发端口、`/@vite/client` 也能返回 `200`，该 tab 仍可能在长时间不刷新后保留旧布局、旧模块状态或旧几何链。只要刷新同一页后 `slotCount`、关键元素宽高、关键对象组中心偏差、运行时类名或其它核心几何指纹发生明显变化，就必须把这页归类为“活端口旧运行时页”，不得继续拿刷新前画面当当前实现证据。
24. **真实浏览器几何争议默认补同页刷新前后对比（强制）**：当用户质疑“我眼前这个活页和你现在代码不一致”，且该页并非死端口错误页时，默认至少补一次“同一页刷新前 -> 刷新后”的运行时对比，记录刷新前后的 `data-slot-count`、关键卡牌宽高、对象组中心偏差或等价几何指纹。若刷新后这些关键值翻正，结论只能写成“刷新前是旧运行时现场，刷新后才是当前实现”，不得继续把刷新前截图当当前 UI 真相。
25. **禁止为通过截图验收写牌数/视口特判布局（强制）**：当用户验收口径是“少牌态应与满牌态共用同一套位置语义/尺寸语义”时，修法必须优先落在统一布局结构上，例如固定槽位、稳定锚点、空槽位占位、同一套容器与坐标系；禁止为了让某几张截图过关，单独对 `1 张/2 张/某个阈值/某个视口` 写条件分支、临时偏移、魔数回中或只服务单张图的特殊排布。验收时必须证明：同一实现同时覆盖空态、低张数、中张数和满态，而不是靠每档数量单独调出来。
26. **固定槽位类布局优先用“空槽位占位 + 同一套坐标”实现（强制）**：像牌河、弃牌区、底座列这类用户要求“1 张也要落在满铺第一个位置”的对象，默认实现应是固定槽位或等价占位结构：无牌时保留空槽位，有牌时只替换对应槽位内容；不得靠“少牌时重新算起点”“某张数单独回中”“为了少牌图好看临时换一套步长”去模拟。若用户进一步要求“第二排横向错位、同排间距固定、改宽度后位置语义不变”，就必须把这些规则做成统一几何常量，并让 `1 张 / 2 张 / 9 张 / 10 张` 共用同一套常量，而不是按数量分支特殊处理。
27. **尺寸/位置争议除了截图还必须落运行时几何 JSON（强制）**：当用户明确质疑“真实浏览器里的牌大小、间距、居中和 E2E 图不一致”时，除了关键截图，还必须同步保存可回查的运行时几何数据，例如视口宽高、`devicePixelRatio`、容器 `getBoundingClientRect()`、目标元素 `width/height/x/y`、关键 CSS 变量。没有这类 JSON 或等价数据，只凭截图肉眼和口头描述，不得宣称已经证明“真实大小和位置一致”。
28. **用户反馈“什么都不做也一直闪 / 一直平移 / 感觉在反复重排”时，禁止只靠单帧截图收口（强制）**：这类问题本质是动态稳定性问题，不是静态布局存在性问题。默认必须先建立“静置窗口内不再重复进入动画态/重排态”的验证环，再谈收口。至少要覆盖：① 进入用户原始问题位点；② 在不进行任何操作的前提下等待一段静置窗口；③ 再次采样动画态、几何矩形或等价运行时指纹；④ 证明前后稳定，而不是继续变化。
29. **静置重排类问题默认先补受控调试日志（强制）**：当用户明确提出“要不要先加日志复现”，或当前症状肉眼像 `重复进场 / 重复动画 / 上层重挂 / 状态机抖动` 时，默认允许先加带唯一前缀的受控日志，并把日志范围收窄到能区分根因的边界，例如 `Board mount/unmount`、动画 cue 设置、预加载门禁切换、关键 runtime key 变化。禁止直接上“全量 console.log 一切”；也禁止在没有静置复现环时只凭猜测继续调样式。
30. **静置稳定性门禁优先于普通截图门禁（强制）**：只要本轮主症状是“静置仍在动”，最终验收除了关键截图，还必须至少有一条自动化或等价可复查证据证明：在同一状态下，连续两次采样之间关键对象的 `data-motion`、`transform`、`rect`、`key`、`mount 状态` 或等价指纹没有继续变化。若只能证明“某一帧看起来正常”，仍视为未证明原始问题修复。

## 用例拆分与命名

1. **入口合同和游戏合同分文件优先（强制）**：主页/大厅/进房类测试，优先放在入口或房间主题文件；牌桌进行时、终局、刷新恢复、spectator、AI roundtrip 等优先放在游戏主题文件。不要把“从主页开始”和“完整对局”机械混在同一文件里。
2. **同一用例只证明一个主合同（强制）**：每条 E2E 必须能用一句话说清自己主要证明什么，例如“可从大厅进入房间”“可在近终局代表态完成最后一弃”“spectator refresh 后仍不泄露”。若一条用例同时承担多个主合同，优先拆分。
3. **标题必须反映覆盖边界（强制）**：如果只证明中间态、入口态、近终局态、单轮 roundtrip、代表分支、刷新恢复，就必须把这些边界写进标题；禁止用“完整可玩”“可结算”“已完成”这类完成态措辞夸大覆盖。
4. **重复前置一律抽掉（强制）**：当多条测试反复从同一前置漏斗起跑，只为验证后面不同合同，应优先把共同前置收成 helper、fixture 或代表态注入，而不是在每条用例里重复走一遍。

## 特写与延迟结算

1. **涉及“骰子特写/奖励骰/重掷/改骰盘”的交互必须提供成功路径证据链**：最少 2 张连续截图：**触发/特写出现** -> **执行关键操作后 UI/结果发生变化**（例如重掷后骰面变化、改投后数值/徽章变化）。
2. 若交互包含“关闭/确认/收口”，则必须再补 1 张**收口后**截图证明流程已回到可继续推进的状态（例如特写关闭、pending 状态清空、阶段可继续推进）。
3. **禁止**只提供“失败提示 / 门禁 toast / 不可用提示”的截图就宣告完成；失败截图只能作为否定路径补充证据。
4. **攻击修正徽章（Active Modifier Badge）属于“效果提示”，不是“结果证明”**：徽章出现只代表“攻击修正已打出/已激活”，不代表加伤数值已经提前计入。
5. 若攻击修正包含“延迟结算/分段生效”（例如依赖奖励骰特写收口后再追加加伤），E2E 必须同时证明：徽章可在打牌后出现；伤害/加伤数值只在实际生效时写入权威状态（例如 `bonusDamage/attackModifierBonusDamage` 不会在特写阶段提前变化）。

## 看图验收

1. **看图必须直击问题位点**：不能只扫整页，必须逐项核对用户这轮指出的具体区域、具体现象和具体目标；如果是展开类/浮层类问题，主截图必须同时包含触发控件、展开内容完整边界、关键参照物。主截图收不全或看不清边界细节时，默认“未证明修复”，必须补局部放大图。
2. **缩放/偏移类问题必须显式判断“有没有缩在左上角/是否被误修成窄布局”**：用户反馈的是“整体偏了、缩在左上角、横屏不该变窄、像桌面端”这类问题时，看图结论必须单独写清：主内容是否仍只占左上角一块；HUD 与主内容是否仍在同一视觉坐标系；是否被错误改成窄布局/双列路线。不能只写“页面出现了/元素都在”。
3. **证据截图必须看得到“对应物”本体**：凡是宣称“某对象/某特写/某控件/某奖励骰/某弹窗/某表情已经出现、位置正确或视觉达标”的截图，肉眼必须能直接看到该对象本体、完整主体轮廓或足以识别的关键内容；如果截图里只有外围布局、遮罩、容器边界、背景、文案或其它无关元素，看不到被宣称对象本体，则该截图一律视为无效证据，不得用于收口。
4. **对象被裁切时不得判定视觉通过**：凡截图用于证明浮层、表情、popover、HUD overlay、特写或控件的视觉结果时，如果目标对象被视口边界、截图边界、容器裁剪、遮挡层或固定定位截断到只露边角/只露局部，最多只能证明“事件触发 / DOM 存在 / 局部进入视口”，不得证明“视觉达标 / 用户看得清 / 可收口”。
5. **高亮/可落点/选中反馈类问题必须按顺序排查**：当用户反馈“高亮没了、可选格看不见、选中反馈不明显、落点不亮”时，必须先确认实现里是否真的存在对应高亮/反馈逻辑；再确认触发链是否真的产出高亮状态/候选数据；只有在确认已触发后，才能用 E2E 和截图证明实际效果。
6. **高亮若不能让第一次看图的人一眼认出目标，直接判不合格（强制）**：凡是靠描边、发光、遮罩、外圈、脉冲或底色来表示“这里可点 / 当前选中 / 当前焦点”的 UI，在整体主截图里必须让第一次看图的人不需要猜就能说出“高亮的是谁”。如果仍要靠局部裁切、口头解释、读 `data-testid`、数边框厚度或对照 DOM 才分辨得出目标，就只能判为“高亮存在但不可辨识”，不得收口。此时默认动作不是补一句说明，而是回到实现里继续拉开高亮对象与周边非目标的对比。
7. **用户要求“恢复原来的效果”时先锁 git 基线**：必须先通过 `git log` / `git show` / `git blame` 给出 `last known good` 与 `first known bad` 候选，再决定是恢复历史行为还是在历史行为上做增量修复；必须实际打开并阅读对应旧实现、旧截图或旧 evidence，明确旧版本当时怎么实现、怎么显示、怎么验收。
8. **流程关键截图必须可继续操作**：凡是用于证明“流程可继续/可完成”的截图（如创建房间、确认弹窗、支付/提交、加入房间、密码输入），画面里必须同时可见下一步主操作控件（如“确认/创建/提交”按钮）且控件不被裁切、不在可视区外。若截图里看不到下一步主按钮或无法判断点哪里继续，该截图一律判定为无效证据，不得收口。
9. **合法等待态必须显式说明“谁在等谁”（强制）**：如果当前截图不是你操作，而是等待别人、等待 AI、等待服务器推进，则画面里必须直接可见等待归属或当前控制权信息，例如“等待玩家 X”“AI 正在行动”“对手处理中”。禁止让“合法等待态”和“页面没反应/流程挂起”在截图上长得一样。
10. **临时浏览器排查必须保持 snapshot 纪律**：使用 Playwright CLI、Browser snapshot 或等价浏览器自动化做临时排查时，必须先获取当前 snapshot 再按元素引用操作；导航、弹窗开关、菜单展开/关闭、阶段推进、DOM 大幅变化后必须重新获取 snapshot。旧元素引用只能作为历史线索，不得继续当作当前页面真相。
11. **战斗/进攻/掷骰证据必须拍到“掷骰结果本体”**：如果本轮汇报里声称已经证明了进攻、战斗或掷骰流程，关键截图里必须肉眼可见骰子本体、骰面结果或明确的掷骰结果文本；不能只给“已经进入战后选择”或“日志里提到掷骰”来顶替。
12. **地图引导截图必须同时证明“箭头存在”与“所有可点目标被点亮”**：涉及地图直选、移动、调度、进攻目标选择时，截图至少要让人一眼看出方向箭头头部在哪里，以及当前所有合法目标是否都被高亮。只有路线、只有目标、只有编号圆点、只有虚线，任一种单独存在都不算完整证据。
13. **用户文案验收必须按“第一次玩的人看不看得懂”判断**：截图里如果还保留 `一级/二级`、`待结算`、`fallback`、`pending`、`source/target` 这类程序员口径，只能判为文案未收口；不得用“代码里就是这么叫的”或“测试方便检索”作为例外。

## 截图来源与证据文档

1. **截图必须来自当前问题场景**：游戏内问题优先保留从能覆盖本轮风险的入口进入后的截图；禁止用大厅页、独立预览页、资源诊断页、兄弟入口截图或自造代理场景，代替问题本身已修复的证据。
2. **截图必须做合理性审查**：看截图时不仅要确认“元素存在”，还必须判断该截图是否能代表真实用户看到的画面。
   - **参考图未唯一锁定前必须先打开核对（强制）**：当用户只说“那张参考图”“之前正常那版”“摸牌（或弃牌）那一版”之类口头描述，但还不能唯一指出具体文件、具体帧或具体截图组时，必须先把候选图真实打开给用户逐张确认；在确认前，禁止据此调整 UI、回写证据、收口结论，或把任何候选图直接升级为正式真相源。
3. **关键截图文件名必须用中文直说交互含义（强制）**：最终用于验收、evidence、回归对照或用户查看的关键截图，文件名本身必须让人不打开图片也能看懂“这是哪一步、哪个交互、处于什么阶段”。允许保留 `gameId`、日期、编号等机器前缀，但真正文件名不得只写 `current`、`flow`、`pending`、`shot-1`、`board` 这类抽象词；至少要包含 `场景/动作对象` + `交互阶段/结果`，例如 `01-征召军队-弃牌选择交互.png`、`04-战后处理-围城选择后.png`。如果用户只看目录仍分不清哪张是“弃牌选择”“确认前”“确认后”，该命名视为不合格。
4. **同一流程截图必须成组编号，前后态命名要能直接对读（强制）**：同一链路里的多张关键图，默认按 `01/02/03...` 编号，并在中文名里显式写出 `触发前 / 选择中 / 确认后 / 结算后 / 回到行动窗口` 这类阶段语义。禁止同一目录下混用一组抽象名和一组语义名，导致人无法只靠文件名还原流程。
5. **截图目录里已经有用例标题时，文件名不得再重复同一标题（强制）**：`test-results/evidence-screenshots/<game>/<测试文件>/<用例标题>/` 这类目录结构里，目录已经承担了用例定位职责，默认截图文件名只保留本次步骤名或编号，不要再把整句用例标题重复拼进文件名。若同一用例内确实需要多个同名步骤，必须显式加步骤编号或传 `filename`。
6. 允许直接对当前页面/当前弹窗截图（`page.screenshot` / 对真实 locator `screenshot`）。
7. **真实页面主截图优先，辅助图不得替代主证据（强制）**：局部放大图、裁切图、locator 单元素截图、手工标注图只能在已经拥有真实页面整页/整屏/整容器主截图后作为补充材料使用，不能反客为主替代主证据。只要用户本轮点名要“截图”且语境指向真实页面，默认主证据必须来自真实页面链路。
8. **对用户交付截图时默认先给整体图，再决定是否补局部（强制）**：当用户说“给我图”“看截图”“给我对比图”“整体看一下”或语义等价表达时，最终回复默认必须先给能看见完整页面上下文的整体真实截图；局部裁切图只允许作为第二层辅助材料，且必须明确标注“这是局部辅助图”。禁止把局部放大图、单槽位截图、单元素截图当成默认第一交付物，也禁止在用户未要求时只给局部图让用户自己脑补上下文。
9. **截图交付现场必须排除当前工作树里的无关视觉实验（强制）**：即使代码真相源已经锁定在某棵专项 worktree，给用户看的整体截图仍必须再判断是否被该 worktree 里的旁支视觉改动、实验 UI、临时布局、独立动画方案或与本轮问题无关的可见元素污染。只要截图里存在这些无关视觉噪音，就不得把它当成用户验收图；必须先换到无污染的等价真实现场、收敛场景，或明确说明“这张图只用于排查，不是最终交付图”。
10. **禁止把脚本后画图或人工叠加图冒充截图（强制）**：凡是通过脚本额外叠点、补框、重排标签、拼接多张图、覆盖说明层、或重新渲染一张“更好懂”的图，都不再属于截图真相；最多只能作为辅助分析图。只要用户要的是“截图”，最终默认交付物里不得只剩这类后处理图片。
11. **临时裁切/局部放大也必须从真实截图原图派生并保留原图路径（强制）**：若为了看清问题位点需要放大或裁切，可以补局部图；但必须同时保留对应原始真实截图路径，并在证据文档里明确“这是从哪张真实截图裁出来的局部”。禁止只交裁切图，让读者无法回到原始页面上下文。
12. **本地默认路由受环境开关限制时，必须写明截图入口为什么仍能代表目标 UI**：如果某个 UI 只在 Android 壳、灰度开关、预览路由、特定 runtime 或特定 query 下启用，截图可以走该项目约定的真实组件入口，但 evidence 和最终汇报里必须显式写清：默认入口为什么在本地不可达、当前截图入口与目标 UI 的对应关系是什么。禁止静默换入口后把替代路由说成默认首页已验收。
13. 为了稳定出图而“克隆 DOM 再固定定位截图”（cloneNode + 手动 `position: fixed` + 强行置顶）不能作为唯一收口证据；如必须使用，证据文档必须明确标注“该截图为快照克隆”，并至少补 1 张真实页面原位截图或给出等价的可复查指标（真实元素 `getBoundingClientRect` + 可视区高度对比）。
14. 禁止通过隐藏关键遮罩、强行改 z-index、强行改 transform 来“把问题遮起来”的截图，或与真实布局关系不一致的“摆拍图”。
15. **资源缺失不等于跳过验收**：外部 R2/CDN 资源未稳定渲染时，必须明确写出“资源未渲染”，并继续检查布局、相对大小、层级、遮挡、溢出、对齐，不能把白卡面直接当成布局失败，也不能借此跳过看图。
16. **必须先看图再写证据结论**：必须创建 `evidence/<功能名>-e2e-test.md`；每张关键截图至少写 1-3 条肉眼观察结论，直接回应本轮需求点和用户指出的问题，禁止只写“正常 / UI 正确 / 看起来没问题”。
17. **证据文档必须显式写“我实际看到什么”和“是否达到验收标准”**：每张关键截图都必须单独写明肉眼看到的具体现象，以及该截图对应的问题位点是否已经达到本轮验收标准；禁止只复述断言、组件名、阶段名或“理论上应该如此”。
18. **必须区分“AI 已核图”和“图片已展示给用户”（强制）**：`view_image`、本地图片查看器、`verify:open-image`、仓库脚本或其他开图动作，只能证明 AI 已实际核对过图片；不能自动等同于“用户已经在当前会话里看到这张图”。当用户说“打开图”“给我看图”“1图呢”“把图打开”或语义等价表达时，默认目标是把图片真正展示给用户，而不只是完成内部核图。若当前回复里没有实际展示图片，或工具结果无法证明图片已展示到用户界面，就不得使用“已经打开给你看了”的口径；只能明确写成“我已核图，当前附绝对路径/当前继续尝试展示”。
19. **只有主收口图确认通过后才打开关键图（强制）**：触发 `npm run verify:open-image -- <截图绝对路径>` 的前提，不是“本轮刚跑完一条 E2E”，而是“这张图已经被实际核对，并确认可作为本轮主收口证据”。一旦最终要以该图收口，则默认必须主动执行开图动作，不能只在回复里贴路径。在此之前，允许继续补图、换图、重跑或直接判定“不达标”，不要求每次 E2E 产物都打开一次。若当前会话支持 `view_image`，默认顺序固定为：`view_image` 核图 → 确认该图满足本轮需求 → 仓库脚本打开同图 → 最终回复附路径与看图结论。
20. **开图失败或无法证明已打开时，必须降级回完整绝对路径（强制）**：如果 `verify:open-image` 没有返回明确成功，或用户反馈“并未打开”，则不得继续使用“已打开图片”的口径。最终回复必须直接附这张截图的完整绝对路径，并明确说明“请按此路径打开/定位”；禁止只贴脚本日志键值、相对路径或省略路径。
21. **看到不达标就必须写“不达标”**：如果截图里出现手牌缺失、控件偏移、被遮挡、只剩边角、主元素跑到一侧、状态不完整等现象，即使 E2E 断言通过，也必须在证据文档里明确写“未达到验收标准 / 不能据此收口”，并继续修图、修实现或修测试。
22. **禁止把“没缩在左上角”偷换成“整体已正常”**：对于移动端 UI 重构/布局修复，截图结论必须区分“已摆脱极端故障”和“布局已完全达标”。若截图只能证明“不再缩在角上/不再整屏错位”，就只能这样写，不能顺势宣称“整体完全正常”。
23. **出现新异常或链路不真都不得收口**：即使断言通过，只要截图里还有新的视觉异常、遮挡、空白块、层级错误、异常位移，或 E2E 没覆盖本轮风险，就不能宣称完成；先加日志定位，再审查调用链，最后修实现或修测试。
24. **trace / console / network 只能作为辅助定位证据**：当截图异常但断言通过、流程卡住、点击无效、资源或接口疑似异常时，可以补抓 trace、console、network 记录辅助定位；但这些记录不能替代关键截图、肉眼验收结论和本轮问题位点的可见证据。
