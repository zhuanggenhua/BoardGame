# E2E 与截图验收规范

> 本文从根 `AGENTS.md` 迁出 E2E 和截图验收细则。根文件只保留入口，详细规则以本文为准。

## 适用边界

- 默认 E2E：使用专用测试模式和状态注入，验证 UI 交互、可见结果和用户操作链路。
- 真实开房链路：仅当本轮要证明房间创建、联机同步、`setupData -> runtime`、权限/座位/多端同步等跨入口合同时使用。
- 如果状态注入已经覆盖用户症状，不能把真实开房当成默认升级；如果真实房间链路能证明更多，必须在测试名、evidence 和汇报中写明它额外证明了什么。

## 三板斧与入口分层

1. **三板斧默认口径（强制）**：本项目的 E2E 默认按三板斧执行：① 使用现有 Playwright fixture / 专用测试模式；② 从离目标语义最近的真实入口起跑；③ 用状态注入或代表态把场景直接推进到问题位点。缺任一斧，都不能算“已经按默认 E2E 方式验证”。
2. **默认不从主页起跑（强制）**：如果本轮目标是验证游戏内流程、牌桌交互、阶段流转、HUD、动画、结算或刷新恢复，默认直接从 game route / match route / 代表态起跑；不得机械先走主页、大厅、进房这段前置漏斗。
3. **首页/大厅类 UI 默认优先 V1 首页（旧大厅）起跑（强制）**：当本轮问题发生在游戏详情、素材包入口、创建/加入房间、房间列表、下载/更新浮层、发布中心入口等“首页/大厅壳层”语义上，默认先使用当前正式用户入口的 V1 首页 / 旧大厅做测试与截图。只有用户当轮明确点名 HomeV2、任务对象就是 HomeV2 书本界面，或代码证据证明线上入口实际分发到 HomeV2 时，才允许把 `/dev/home-v2-preview`、`home-v2-*` 组件或 HomeV2 历史截图作为主验证入口。
4. **不要用 HomeV2 候选图替代 V1 正式入口证据（强制）**：若本轮原始症状未明确属于 HomeV2，HomeV2 截图最多只能作为候选/辅助排查材料；最终截图必须回到 V1 首页/旧大厅真实入口，且图里必须能看见本轮业务对象和修复结果。只有书页背景、齿轮、空白壳层、未进入问题位点的图，一律视为无效截图，不能作为“已看图验收”。
5. **“开局”默认指当前合同的最近起点（强制）**：在游戏流程语境里，说“从开局验证”默认不是指“从主页点到进房再打一整局”，而是指“从当前要证明的游戏合同最近的起点开始”。例如验证抓牌、弃牌、近终局、刷新恢复时，最近起点通常是 `match route`、首轮代表态或近终局代表态，而不是首页。
6. **主页/大厅进房 与 游戏内流程分层（强制）**：`从主页进入` 和 `进入 match 后的游戏流程` 是两个不同合同。前者证明入口漏斗、房间创建、加入、路由或权限；后者证明具体游戏可玩性。除非本轮目标是整条漏斗都要收口，否则不得绑成同一条大 E2E。
7. **刷新恢复 / 终局复盘 / spectator 也属于独立合同（强制）**：这些链路默认单独建用例，从其最近的可注入代表态起跑；不要附着在主流程后半段顺手验证。
8. **依赖玩家视角的注入必须显式给视角（强制）**：当教程、状态注入、E2E 或截图验收依赖玩家座位、手牌归属、暗棋、私有信息、可见范围、权限或视角聚焦时，入口必须显式注入 `playerID`、座位或 viewer identity。缺少视角要判为测试入口/注入数据错误，必须修 URL、夹具或状态数据；禁止用组件 fallback 到当前行动方、默认玩家、保守隐藏、显示全部背面或其它渲染兜底来掩盖错误注入。
9. **直接开局配置不得被显式测试参数掩盖（强制）**：当用户反馈“我直接开局卡住 / AI 不动 / 默认人数或座位不对”时，至少补一条不传 `seatN` 覆盖参数的真实 game route / match route 用例，证明默认 seat controller、默认人数、默认 setup 确实能走通。显式 `seat1=local-ai`、`seat2=local-ai` 只能证明该参数组合能跑，不能证明用户直接开局没问题。
10. **实体拿走 / 消耗 / 移动必须验证源区和目标区（强制）**：如果交互语义是“拿走筹码、拿牌、支付资源、移动棋子、弃牌、消耗 token”，E2E 不能只断言状态字段或目标区数量。最低断言必须同时覆盖：源区域对应实体消失或变成明确空位、目标区域出现对应实体、下一步按钮状态与现实动作一致。否则即使真实按钮点击过，也不能证明玩家看到的链路已跑通。
11. **场景对象直选必须测主路径（强制）**：当玩家目标是房间、基地、棋盘格、角色、玩家 token、怪物、物品、卡牌或场上单位，且该对象在主视图可见时，E2E 主点击必须落在真实对象本体或贴合高亮层上；旁路列表、文字按钮、编号标签、顶部/底部代理按钮通过，只能证明备用入口可用，不能证明正式交互达标。截图也必须看得到目标对象本体和贴合高亮。
12. **可直点对象不得保留代理命令断言（强制）**：如果角色/玩家 token、物品牌、房间板块等本体已经承接正式命令，E2E 里必须断言旧代理入口不存在或不会直接完成目标命令；否则测试会继续鼓励 UI 退化。允许保留的旁路只能定位、展开详情、筛选或打开帮助，不得发送同一个目标命令。
13. **未说明开关/偏好时必须使用产品默认值（强制）**：当用户要求“给我看图 / 端到端截图 / 当前 UI / 默认样子 / 真实页面”但没有明确指定开启某个可选功能、实验开关、视觉偏好、调试模式或用户设置时，E2E 和截图必须按产品默认值运行。禁止为了展示新体验、覆盖更多分支或复用现有用例，主动打开默认关闭的可选项后把截图当作默认画面交付。
14. **功能开关双分支截图必须显式标注分支（强制）**：如果确实需要同时展示关闭态和开启态，测试名、截图名、汇报文案必须分别写清“默认/关闭态”和“开启态”。默认/关闭态是默认验收主证据；开启态只能证明可选分支成立，不能替代默认态。
15. **用户明确已开启时不得反向怀疑开关（强制）**：当用户明确说某个开关、偏好、模式或实验项已经开启，并反馈该开启态异常时，排查默认必须以“开启态成立”为前提构造 E2E、现场脚本或状态注入，直接验证开启态的真实渲染、交互、资源和运行时结果。检查本地存储或设置面板只能作为证据采集项，不得先把“用户没开启 / 没点开 / 走默认关闭态”当成主要结论，也不得用默认关闭态截图否定用户反馈。

## 组合式验证与长链预算

1. **组合式验证优先（强制）**：完整流程优先拆成“入口合同 + 代表态合同 + 高风险分支合同 + 黄金链”组合证明，而不是把所有风险塞进一条超长 E2E。证明完整流程成立，靠组合覆盖矩阵，不靠重复从头跑到底。
2. **长链默认只保留少量黄金链（强制）**：需要自然完整对局、多人长轮转、真实 AI 串行托管时，只保留少量黄金链证明“整局能跑通”；其它回归优先收成注入态、单轮 roundtrip、近终局、刷新恢复、分支选择等窄合同。
3. **单条用例时长必须受预算约束（强制）**：默认目标是单条 E2E 尽量控制在 `3` 分钟内；超过 `5` 分钟的单条用例必须有明确理由，并优先评估能否拆成组合式验证。若某条链已经长到“比正常一局还久”或容易因时间累积放大环境噪声，默认视为设计异味。
4. **单文件总时长也要受预算约束（强制）**：默认优先把单个 E2E 文件控制在可快速回归的量级；当单文件逐步逼近或明显超过 `10` 分钟时，必须优先评估拆文件、拆主题、拆黄金链，而不是继续往同一文件里堆。
5. **长链例外必须写明价值（强制）**：如果保留一条超过预算的完整自然链，测试名、evidence 与汇报里必须显式写清它独有证明点，例如“只这条能证明多人自然终局”“只这条能证明高人数 repeated-refresh”。没有独有证明点的长链应拆掉。
6. **同一目标不得把长链重跑当默认调试循环（强制）**：同一个问题若第一次长链失败后仍未锁定根因，最多只允许在有明确新假设或新改动的前提下再重跑一次；若第二次仍未锁定，就必须退回代表态注入、局部合同或更低层测试，禁止继续无差别重复自然开局。
7. **单次问题定位必须有总时长预算（强制）**：默认把“为定位同一个问题反复跑长链验证”的总预算控制在 `15` 分钟内。超过该预算仍未拿到直接证据时，必须暂停继续堆长链，改做合同拆分、状态注入、日志/快照补证或更低层验证。
8. **实现推进与收口验证必须分阶段（强制）**：E2E 的职责是证明真实入口和可见结果，不是主调试器。默认节奏应是：先用状态注入或低层验证锁定实现缺口，再改代码，再用最窄 E2E 收口；禁止长时间停留在“反复跑 E2E 看哪里又不对”的循环里。
9. **45 分钟级单问题测试循环默认视为失守（强制）**：如果围绕同一个问题的测试与重跑已经明显拉到 `45` 分钟量级，却仍主要停留在到达目标位点之前、或还在反复确认同一条长链能不能走通，默认应判定为“三板斧失守”；必须立即拆成状态注入、组合式合同或更低层验证，不能继续把长链时间堆高。

## 定位顺序与停线动作

1. **游戏内问题默认先打到问题位点（强制）**：当目标是牌桌进行时、单回合交互、HUD、终局、复盘、刷新恢复或单个动画问题，默认先直达 `game route / match route / 代表态`，而不是先从主页起跑再自然打到那里。
2. **真实开局只证明它独有的合同（强制）**：如果当前要验证的是“从主页进入”“创建房间”“加入房间”“claim seat”“setupData -> runtime”这类漏斗合同，可以跑真实开局；否则它不能作为默认起点，更不能因为“更真实”就吞掉后续游戏内合同。
3. **停线条件必须明确（强制）**：一旦出现以下任一情况，必须立刻停止继续拉长链路，并改走拆分验证：
   - 同一目标已经重复跑了两次自然链；
   - 单条链路明显比正常一局还久；
   - 当前失败点仍停留在“没到问题位点前就先挂了”；
   - 这条链路证明的主要是前置漏斗，而不是本轮真正要改的游戏逻辑或 UI。
4. **重新起跑前必须先说清这次多证明了什么（强制）**：准备再跑一条长链前，必须能明确回答“这次与上一条相比，新增证明点是什么”。如果回答不出来，默认不该再跑。

## 桥接式组合验证（强制）

当一条完整玩法既要证明入口，又要证明 `match` 内多个中后段语义时，默认拆成下面三段，而不是硬跑一条自然终局长链：

1. **入口黄金链**：只证明真实入口、建房/入房、首个可行动回合、座位/权限/同步语义成立。
2. **中段代表态链**：直接注入到本轮真正关心的 `match` 内位点，例如 `draw/discard`、waiting、stacked/live、spectator、reload。
3. **终局前代表态链**：直接注入到 near-end、最后一弃、review 前一跳等位点，证明终局切换与复盘语义。

- 三段组合起来，才是“完整流程已被分层证明”；禁止把“没有单条从主页自然打到终局”偷换成“没有证明完整流程”。
- 入口黄金链只需要跑到它负责的合同 seam，不需要天然承担 review、spectator、终局前最后一弃等所有后段证明。
- 如果一条测试已经同时想证明入口、第二轮身份、AI 中段决策、near-end、review、reload，它默认已经超出单链应承担的合同数量，必须拆。

## 新游戏基本流程与剧本流程分段（强制）

当新增或继续实施一个游戏，且本轮目标同时包含“基本流程”和“第一剧本 / 首个场景 / 终局”时，默认按两段端到端证明，不把它们绑成一条重复长链：

1. **基本流程 E2E**：只证明从最近真实游戏入口进入、完成角色/配置/开局确认，并到达首个可操作运行时。截图应覆盖 `确认前` 与 `运行时已可操作`。
2. **剧本 / 终局 E2E**：从已确认可用的运行时代表态或 near-end 代表态起跑，只证明该剧本的关键交互、结算和终局可见结果。不得重复跑角色选择、建房、配置等已经由基本流程证明过的前置。
3. **命名必须暴露边界**：文件和用例标题必须能看出是 `basic-flow`、`first-scenario`、`near-end` 还是 `endgame`，禁止继续用一个“完整流程”用例同时承担全部合同。
4. **证据文档按段记录**：每段 E2E 应有自己的 evidence 目录或清晰分组；最终汇报只能说“基本流程 + 第一剧本已分段证明”，不要偷换成“自然整局从头到尾已跑完”。
5. **Codex Windows 复用现服特例（强制）**：当本地处于 Codex Windows 受管环境，且已确认 `dev:file` 是当前允许的官方 fallback 时，运行 `scripts/infra/run-e2e-dev-single.js` 可显式带上 `CODEX_MANAGED_BY_NPM=1` 与足够的 `--max-old-space-size`，避免 `child_process` 预检误报与包装进程先 OOM。
6. **命中“页面没有正常显示”保护层时要先回到真实页面（强制）**：若真实 game route 先落到保护页，不得把保护页截图当交付，也不得直接判业务失败；应优先点击“刷新重试”或重新加载，再继续等待 `__BG_TEST_HARNESS__` 与真实游戏页挂载。

## 新游戏端到端素材门禁（强制）

E2E 的职责是验证真实入口和用户可见流程，不是替代规则录入、素材 intake、OpenSpec 任务矩阵或资源接线。执行 E2E 前，必须先确认本轮范围内的规则对象素材矩阵和实现任务没有可本地推进的前置缺口；否则 E2E 只能作为失败证据或排查证据，不能作为完成证据。

1. **缺素材先补提案，不准硬跑端到端**：新增游戏、继续接入游戏、或准备宣称基础流程闭环时，若发现规则明确提到的素材、数据、交互入口或实现对象仍缺失，必须先更新 proposal / tasks / 规则对象素材矩阵，把缺口写成待实施或阻塞项，再继续实现；不得直接跑 E2E 寻找“看起来可玩”的绿灯。
2. **禁止 HTML/CSS/文字壳冒充正式素材**：规则里明确存在的牌面、牌背、token、棋子、金条、警报、桌面、牌槽、帮助卡等对象，要么使用真实素材并完成语义命名、落盘、压缩、manifest 和运行时引用，要么明确标为阻塞；不得用 HTML 元素、CSS 图形、纯文字牌面、程序化图形、mock 图片或相似图标制造“端到端已通过”。
3. **E2E 只能验证真实运行时链路**：E2E 截图和断言只能证明当前运行时真实加载的资源与真实页面交互；如果当前页面仍使用程序化替代，且没有规则矩阵或用户批准说明该对象可程序化表达，则 E2E 只能标记为代码链路通过，不能升级为基础版完整闭环。
4. **素材阻塞不允许被“后续美术优化”吞掉**：只要规则对象素材矩阵里仍有基础版必需对象处于 `blocked`、`missing`、`needs-visual-confirmation`、`base-runtime-candidate` 或无明确替代批准，整体状态必须保持 `in_progress`；最终汇报必须点名阻塞对象，不得用“扩展不纳入本轮”“已有截图”“核心流程可玩”绕过。
5. **发现缺口后的下一步必须可执行**：阻塞记录必须同时写清现实对象、真相源、当前候选素材、为什么不能落盘、下一步是继续查找、裁切、OCR、开图确认，还是等待用户补素材。只写“后续处理”不算完成阻塞登记。

## 图片上下文预算门禁

1. **AI 核图必须先过图片上下文预算门禁（强制）**：需要模型自己读取截图/裁图时，先检查文件大小、尺寸和数量。禁止连续 `view_image` 多张 JPG/PNG/WebP 大图、atlas 裁图或高清整页截图；默认先生成低分辨率预览、局部 OCR 文本或单张小 contact sheet，再读取。
2. **用户开图不走 AI 读图（强制）**：若用户只是要“打开给我看”，直接用仓库开图脚本或系统查看器打开原图，不走 AI 读图，也不把压缩预览冒充原图。
3. **图片卡死按官方已知问题处理（强制）**：若读取图片后出现上下文暴涨、响应卡死、模型提示空间耗尽，先对照 `openai/codex#28316` 处理为“图片/base64 工具输出污染后续上下文”的规避问题；在官方修复合入前，不得继续反复读取原图。后续只能说“已改走轻量预览/OCR/外部开图规避”，不得宣称官方根因已修复。
4. **用户验收图不得默认压缩缩略（强制）**：运行时素材压缩、AI 核图轻量预览、用户最终验收图是三个不同场景。最终打开给用户看的端到端产物图必须保留高清可读版本；压缩图、缩略联系图、低清 contact sheet 只能作为 AI 自检或排查辅助，不能冒充交付图。
5. **流程产物图必须能脱离对话读懂（强制）**：如果交付物不是原始截图，而是脚本后处理的流程图、剧本说明图或收口图，图内必须同时包含大尺寸关键截图、玩家可读的规则/剧本摘要、流程边界、验证结论和“不外推”的范围说明。只拼截图、箭头和短标签，不足以作为规则链路收口图。

## E2E 测试强制要求

1. **UI 交互必须用 E2E**：必须使用三板斧（fixture / 专用测试模式 + 最近入口 + 状态注入/代表态）；UI 交互、多玩家协作、动画特效都不能用单元测试代替。
2. **展开/详情 UI 必须留下入口链路证据（强制）**：当验收对象是详情弹窗、展开面板、二级抽屉、悬浮提示、放大查看或任何需要先点击入口再进入的 UI 时，E2E 不能只截展开后的最终状态。最低要求是：先断言并截图入口按钮/触发控件可见，再点击入口并截图展开态；截图名和汇报文案必须区分“入口可见态”和“详情展开态”。如果只给展开后截图，让用户看不出从哪里点进去，视为证据不完整。
3. **核心新交互必须执行到真实结果（强制）**：当本轮新增、翻正或准备对外宣称某个核心玩家操作可玩时，E2E 不能只断言按钮存在、入口可见或领域单测通过；必须通过真实页面点击该交互，并断言玩家可见的结果态。像移动、探索、翻开未知房间、摸牌/拿牌、交易/搜尸、攻击、结算、结束回合这类主操作，至少要覆盖 `触发前 -> 选择/执行中 -> 触发后` 的真实页面证据；若没有这条 E2E，只能说“底层逻辑已测”或“入口已出现”，不得说“该交互已可玩 / 可上线给玩家”。
   3A. **按钮必须验现实后果和后续选择（强制）**：当用户反馈“点了没用 / 不能点 / 不知道点完发生了什么”，或按钮语义是 `发放 / 抽取 / 保存 / 重设 / 使用 / 选择 / 确认` 时，E2E 不能只点按钮或只看 dispatch。最低断言必须同时覆盖：① 点击前按钮可见且处于正确权限态；② 点击后玩家可见状态、文案或承载区发生变化；③ 源区和目标区的现实对象数量或内容变化；④ 若该动作会进入后续选择 UI，必须继续选择一个代表目标并断言最终结果。没有这些后果断言，不得说“按钮功能已做”。
   3B. **E2E 断言必须直接命中用户目标（强制）**：测试名、断言和截图必须证明用户点名的现实结果，而不是证明相邻实现细节存在。例如“可滚动”必须真的滚动目标容器并断言滚动后目标内容可见；“选项太小”必须量可点控件尺寸或截图肉眼判定；“不要背景框”必须断言目标主舞台没有整块背景/边框并配截图。只断言 `overflow-y-auto`、元素存在、`data-layout` 或按钮文字，不能替代目标结果。
   3C. **规则时序目标必须验前后阶段（强制）**：当用户质疑的是“先投骰后选择 / 先选择后投骰 / 先付费再结算 / 先选目标再确认”这类规则时序时，E2E 不得只注入最终 `pending` 或已结算状态。最低断言必须从同一规则链生成目标位点，并同时证明前置阶段已经发生或尚未发生、当前可见 UI 属于哪个阶段、后续点击后进入正确下一阶段。例如“已有骰子才有选项”必须在选择前截图里同时看到本次投骰结果和选项；“先选择后投骰”必须断言选择前没有投骰面板，选择确认后才出现投骰或结算结果。若测试直接注入 `pending`，只能叫“阶段承接 / 布局验证”，不得叫完整端到端。
   3C.1 **阶段系统交互必须补未处理负向链（强制）**：当阶段开始或阶段结束会产生确认、跳过、选择目标等系统交互时，E2E 除了确认/跳过后的正向结果外，至少补 1 条“交互未处理时继续推进阶段被阻止”的负向断言。最低证据必须同时覆盖：① 当前画面处于正确阶段；② 系统交互提示、按钮或目标选择仍可见；③ 再次点击结束阶段/继续阶段等推进入口不会进入下一阶段；④ 截图文件名直接写清“未确认仍停在哪个阶段”。禁止只用领域测试或按钮存在断言替代这条链，否则无法防止提示残留到下一阶段。
   3C.2 **强制自动效果不得做选择交互（强制）**：当规则文本、能力定义或已锁合同没有“可以 / may / 选择 / 任选 / 跳过 / 可不执行”等选择语义，而是“造成 / 获得 / 消耗 / 每个 / 所有 / 攻击阶段开始时”等强制结算语义时，实现不得新增确认、跳过、二选一或“是否执行”UI。E2E 必须同时证明：① 从真实规则链进入目标阶段或触发点；② 没有该效果的选择提示、确认按钮或跳过按钮；③ 现实结果已经落到玩家能看懂的位置，例如伤害、资源消耗、对象移动、状态变化或阶段停留。禁止把“提示出现”“按钮可点”“系统记录了待处理状态”当作强制效果的结果；若结果不可见或未断言，只能称为阶段承接，不能称为规则效果已收口。3C.1 只适用于规则确实需要确认、跳过或目标选择的系统交互，不适用于这类强制自动效果。
   3C.3 **自动阶段效果截图必须覆盖前后流程（强制）**：当阶段开始或阶段结束的强制自动效果被称为“端到端 / 完整链路 / 已收口”时，截图证据不得只保留最终结果图。最低截图组必须来自同一个 Playwright 用例、同一次真实页面链路，并至少包含两类前后态：① `触发前`，能看见当前阶段、触发对象或触发条件、结算前关键数值；② `结算后`，能看见已经进入正确阶段、没有多余选择 UI，并能看见或能被同一步断言对应到伤害、资源消耗、移动、状态变化等现实结果。如果一张结算后截图无法同时证明“阶段已到”和“结果已落位”，必须拆成 `推进阶段后` 与 `结算结果后` 两张；若画面无法直观看清数值，必须在 evidence 中把该截图对应的机器断言写清楚，说明“这张图证明画面阶段，断言证明哪项数值变化”。单张最终图、旧提示图、只截 pending/interaction、只截日志或只截状态字段，都只能叫局部证据，不得叫完整端到端。
   3D. **完整端到端必须覆盖触发到关闭（强制）**：当用户要的是“整个链路 / 端到端 / 流程跑通 / 牌翻出来再处理”时，同一条主证据必须从玩家可见的真实触发入口起跑，并至少覆盖 `触发前可操作 -> 牌或对象翻出/亮相 -> 选择或投骰前 -> 选择/投骰后 -> 结算结果可见 -> 关闭/继续后回到牌桌`。像事件牌、发现牌、抽牌亮相、结算浮层这类阻塞流程，不能只截 `pending` 选择态或最终结果态；必须证明翻出的牌面和后续选择属于同一张牌、同一次规则链，且关闭后遮罩/面板已退场、下一步主界面可继续操作。
   3D.1 **卡牌翻出类流程必须按六段模板收口（强制）**：凡流程以“翻牌 / 抽牌 / 亮出发现 / 亮出预兆 / 亮出事件 / 打出物品或技能卡”开始，正确 E2E 必须在同一用例、同一规则链里依次证明：① `翻出前` 玩家可见触发入口和当前牌桌；② `翻出后` 牌面或正式替代牌面可见，且能关联到本次触发对象；③ `选择或投骰前` UI 与规则时序一致，不能提前出现后续结果；④ `选择/投骰后` 玩家可见结算依据，例如骰面、目标、属性或资源变化；⑤ `结算后` 现实结果已经落到玩家能理解的位置；⑥ `关闭后` 阻塞层消失、临时状态清空、牌桌恢复可操作。缺任一段时，只能写“局部链路通过”或“阶段承接通过”，不得写“完整端到端通过”。
   3D.2 **卡牌翻出类 E2E 必须让测试结果对应目标（强制）**：这类用例的测试名、步骤截图名、断言和 evidence 结论必须同时点名同一张牌/同一对象、同一条规则时序和同一项用户目标。每一段截图都必须有对应断言：`翻出前` 断触发入口与当前对象，`翻出后` 断牌面/标题/正式图面，`选择或投骰前` 断本阶段应该有或不该有的 UI，`选择/投骰后` 断选择值/骰面/目标，`结算后` 断现实结果落位，`关闭后` 断阻塞层清空和主界面继续可操作。若用户目标是“选项太小 / 要滚动 / 不要背景框 / 骰子重叠 / 物品本体可点”，还必须加入尺寸、滚动后可见、无背景框、骰子几何或真实对象点击断言；只用最终状态、日志、DOM 存在或截图文件落盘，不能算目标相关的完整端到端。
   3D.3 **缺段必须降级登记（强制）**：六段链里任一阶段没有真实页面截图、没有对应断言、或截图/断言不是同一张牌和同一次规则链，当前对象就必须登记为`待补完整链路`。领域测试、组件测试、阶段承接 E2E、单张结果截图、按钮可见、日志无错都只能写成对应层级证据；evidence、任务状态和最终汇报必须同步说明缺的是哪一段，不得用“已修 / 已跑通 / 已可玩”覆盖缺口。
   3D.4 **完整端到端必须写成“步骤-断言-截图-用户目标”四列闭环（强制）**：凡对外宣称“完整端到端 / 整个链路 / 已跑通”，用例实现、evidence 或任务状态里必须能逐步对应四件事：① 本步骤玩家实际做了什么；② 自动断言证明了什么现实结果；③ 对应截图文件是哪一张；④ 这一步回应了用户点名的哪个目标。正确链路不是“进入某个 `pending` 状态后截一张图”，而是按真实顺序证明 `牌或对象翻出来 -> 玩家做选择或投骰 -> 系统结算 -> 玩家关闭或继续 -> 回到可操作牌桌`。如果某一步只是为了铺路但不回应用户目标，也必须写清它是前置，不得冒充目标验收。
   3D.4A **牌翻出类完整链路固定执行表（强制）**：事件牌、预兆牌、物品牌、发现牌、房间牌、技能牌或等价“亮相后再处理”的流程，完整 E2E 必须在 evidence 中逐行填写下表；不能只在测试代码里隐含步骤，也不能只贴截图目录。

   | 阶段            | 玩家实际动作                               | 自动断言必须证明                                                                         | 截图必须看见                                         | 用户目标对应                         |
   | :-------------- | :----------------------------------------- | :--------------------------------------------------------------------------------------- | :--------------------------------------------------- | :----------------------------------- |
   | 1. 触发前       | 玩家能在真实牌桌上执行触发动作             | 触发入口可见、可点、权限正确，牌桌处于可操作状态                                         | 当前牌桌、触发对象或按钮、相关玩家/房间/物品         | 证明不是直接注入中间态               |
   | 2. 翻出/亮相    | 玩家触发翻牌、探索、抽牌、使用或打出       | 本次翻出的牌/对象标题、牌面或正式替代面与触发链一致                                      | 翻出的牌面/对象、来源位置、当前阻塞层或展示区        | 证明“牌真的翻出来”                   |
   | 3. 选择或投骰前 | 玩家还没有完成选择/投骰                    | 当前 UI 属于正确时序，未提前出现结算；需要先投骰的必须已有骰子，需要先选择的必须尚无骰子 | 选择项、骰盘、目标高亮、属性/资源提示等本阶段真实 UI | 证明“先选择还是先投骰”没跑错         |
   | 4. 选择/投骰后  | 玩家完成目标选择、点击真实对象、投骰或确认 | 选择值、目标、骰面、属性、资源消耗或对象移动已经形成结算依据                             | 选中的对象/骰子/属性、投骰结果、可见依据             | 证明选择不是假按钮、投骰不是隐藏数据 |
   | 5. 结算结果     | 系统完成本次规则结算                       | 血量、属性、位置、物品、日志、房间、牌堆或胜负等现实结果已经落位                         | 结算面板或牌桌结果，玩家能理解发生了什么             | 证明效果真的生效，不只是点通         |
   | 6. 关闭/继续    | 玩家关闭结果、继续或确认收口               | 阻塞层、临时选择、目标锁定、高亮、`pending` 均清空，主牌桌恢复下一步操作                 | 关闭后的完整牌桌、可继续操作入口                     | 证明流程已收口，不残留半截状态       |

   若某个用户目标是视觉/交互反馈，例如选项过小、左侧滚动、背景框、属性颜色、开放式骰盘、骰子重叠、蜘蛛效果、物品本体可点，必须把该目标填入对应阶段的“用户目标对应”列，并在同一阶段加入机器断言或截图肉眼结论；不得另用孤立视觉截图替代这条主链。

   3D.4B **正确端到端的最小产物包（强制）**：每条被称为“完整端到端”的牌翻出/选择/投骰/结算流程，最低产物必须同时包含：① 锁定规则时序和触发对象的证据；② 一个从真实可见触发入口起跑的 Playwright 用例；③ 按 `01-触发前` 到 `06-关闭后` 命名的同链路截图组；④ evidence 里的六段四列表；⑤ 用户目标矩阵，逐项写明已证明、待补或不适用；⑥ 对最终截图的肉眼核图结论。缺任一项时，测试即使 `passed`，也只能登记为“局部链路 / 阶段承接”，不得写成完整端到端。

   3D.5 **规则时序分支必须各自有完整代表链（强制）**：先选择后投骰、先投骰后选择、投骰后直接结算、翻出后立即作祟/检定、物品本体点击后选择目标等，属于不同链路家族，不能互相替代。每个家族的代表 E2E 必须从该家族真实触发入口起跑，并证明“上一阶段尚未越权出现、下一阶段按规则出现”。例如先选择后投骰的链路必须证明选择前没有投骰结果；先投骰后选择的链路必须证明选项出现前已有本次投骰依据；直接结算链路必须证明没有多余选择 UI。若只测了其中一个家族，汇报只能说该家族通过，不能说整批卡牌/事件/物品都已核对。
   3D.6 **视觉反馈问题必须进入同一条端到端主链（强制）**：用户指出选项太小、关闭按钮/叉号太小、选中效果看不见、开启/关闭没有 UI 变化、左侧是否可滚动、背景框不该出现、属性颜色要统一、骰子不应重叠、开放式骰盘、蜘蛛/特性效果等问题时，不得另写一个孤立视觉用例代替主链。最低要求是在对应步骤里直接量或截：选项/图标按钮/关闭按钮的真实可点热区尺寸、开关/卡牌/目标的已选态与未选态视觉差异、滚动前后可见特性、主舞台是否无多余背景框、同类属性颜色是否一致且不同属性不全同色、骰子数量与互相遮挡风险、效果触发前后画面变化。端到端结论必须说明这些目标在哪一步被证明；没有证明的目标必须保持`待补`。图标本体变大不等于热区达标，必须用 bounding box 或等价 DOM 几何断言证明真实热区不小于项目触控底线；选中态不能只验 `aria-pressed`、`data-state`、文案或配置值，必须同时证明整屏截图里存在可见外框、底色/亮度/饱和度差异、徽标或等价视觉信号，且这些信号比未选态明显；若状态差异只靠颜色或亮度，必须额外补形状、外框、图标、文案徽标或等价非颜色信号。
   3D.7 **无弹层流程也必须证明收口清理（强制）**：交易、移动、攻击目标选择、物品本体使用、地图直选等流程即使没有“关闭”按钮，也不能停在结算日志或状态字段。最后一段必须证明临时选择、高亮、目标锁定、确认提示或 pending 状态已经清空，并且主牌桌回到可继续操作状态；如果只是物品转移、伤害数字或日志出现，但选中态仍残留，只能写“结算结果可见”，不得写“完整端到端通过”。
   3D.8 **测试通过必须回扣目标矩阵（强制）**：E2E 输出 `passed`、截图落盘、trace 生成或自动断言通过，只能说明命令执行成功；对外结论必须另写目标矩阵，逐项回答用户点名的对象是否被证明，例如“牌是否真实翻出”“是否先选择后投骰”“滚动后是否看到特性”“关闭后是否回到可操作牌桌”。若某个用户目标没有对应步骤、断言和截图，必须继续记为`待补`，不得被同一条测试的其它绿灯顺带覆盖。
   3D.9 **移动端可玩性必须用同一条主链证明（强制）**：当用户反馈“移动端无法游玩 / 手机端不好用 / 手机横屏不行”时，不能只补一个移动端入口截图或断言元素可见。最低 E2E 必须在目标移动视口里完成本轮主流程的真实操作链，例如移动、探索、翻牌、选择或投骰、结算、关闭回牌桌；若某一步需要滚动、抽屉、楼层切换或收纳入口，必须实际执行该操作并断言滚动/切换后目标内容可见。移动端结论还必须回扣 PC/移动一级信息去向矩阵，说明关键角色信息、行动入口、地图目标、牌面、投骰、结算和继续入口分别在移动端哪里承载。
   3D.10 **牌面、投骰和结算同屏时必须验证让位和退场（强制）**：当流程同时出现事件牌/发现牌/技能牌、投骰结果和结算按钮时，E2E 不能只证明三个元素都存在。必须断言牌面在选择/投骰后持续可读，投骰区不固定占据右上角或整块中央空间，结果区不会遮住牌面主阅读区，结算/继续按钮点击后相关阻塞层和最近投骰结果都退场。若骰子尺寸、背景框、顶部/右上角残留或事件牌一闪即消失是用户点名问题，这些必须进入同一步的几何断言或截图核图结论。
   3D.11 **需求-产物对照必须先于完成结论（强制）**：当用户连续提出多个验收点，或质疑“测试结果和目标没关联 / 产物在哪里 / 是不是规范要更新”时，最终收口前必须写一张需求-产物对照表，先逐条保留用户原话或保真改写，再为每条列出对应产物、证据路径、当前判定。状态只能是`已证明`、`部分证明`、`证据不足`或`不适用`；不得把多个用户需求折叠成一个笼统验收项，也不得只列已经通过的项。只要表里仍有`部分证明`或`证据不足`，任务状态不得标为`complete`，除非用户明确同意缩小范围或将该项移出本轮。
   3D.12 **方法性要求也必须进入对照表（强制）**：如果用户要求参考某个软件/旧实现/截图、要求打开原图而非降采样图、要求按某个交付通道看图、要求验证对象全集或规则时序家族，这些虽然不一定是代码功能，也必须作为需求行登记。没有外部参考记录、对象全集清单、原图打开记录或交付证据时，只能标`证据不足`，不得因为核心 E2E 通过就省略。
   3E. **先列对象全集和时序家族（强制）**：当本轮对象是一批卡牌、事件、技能、物品或同类交互时，写 E2E 前必须先从规则真相源或当前数据合同列出对象全集，并按真实时序分组，例如 `先选择后投骰`、`先投骰后选择`、`可选是否触发作祟`、`投骰后直接结算`。每个家族至少要有代表性完整链路证据；若用户点名的是某个家族的“全部/同类/还有哪些”，则该家族每个对象都必须有明确状态：`完整链路通过`、`阶段承接通过`、`待补完整链路` 或 `不适用`。禁止只命中一张代表牌后，把整批写成“已核对”。

4. **必须实际运行并通过**：AI 编写后立即运行 E2E；单文件/单用例优先用 `npm run test:e2e:ci:file -- <测试文件名> "<用例名>"`，整文件复跑用 `npm run test:e2e:ci -- <测试文件名>`，禁止交给用户。
5. **必须实际打开截图验收**：优先看 `test-results/evidence-screenshots/_shared/`，失败用例再补看 `test-results/playwright-artifacts/`；验收标准不是“页面出现了”，而是“本轮问题位点已按要求修好”。
6. **原始 UI 问题不得换验收对象（强制）**：当用户反馈的是现有界面上的某个具体显示、点击、字号、显隐、位置或交互问题时，E2E 必须回到同一个现实 UI 对象、同一条用户操作链和同一显示层验收。禁止新增或依赖另一套 HUD、浮层、toast、提示条、说明面板、旁路按钮、调试层或替代组件来证明原问题已解决；这类旁路 UI 只能算范围扩展或候选方案，必须先获得用户明确授权。若确实需要设计新 UI，应先停止原 bug 收口，说明“原问题尚未证明修复，新 UI 是另一个方案”，不得把新 UI 截图当作原 bug 通过证据。
7. **截图证据必须点名原始显示链路（强制）**：视觉类 bug 的截图脚本和汇报必须同时说明：① 注入或进入了什么真实状态；② 触发的是哪个用户可见对象；③ 截图里用于验收的是原始问题对象本身；④ 若页面上同时存在新旧两套相似 UI，哪一套才是本轮验收对象。只断言 DOM 里有文字、旁边另有大字提示、或另一个浮层能看清，不能证明原始文字/原始交互已修好。
8. **最终达标截图必须主动打开，未达标候选图不得打开（强制）**：凡是靠截图收口 UI 结果，必须真的把关键图打开后再下结论。若当前会话提供 `view_image`，先用 `view_image` 核图；只有当你已经确认“这张图本身满足本轮需求、可作为最终收口证据”时，才执行 `npm run verify:open-image -- <截图绝对路径>`，或在需要一次打开多张时执行 `npm run verify:open-image -- <截图绝对路径1> <截图绝对路径2>` 主动打开同一批关键图作为 closeout 动作。不得把它理解成“每跑完一次 E2E 都顺手开一次图”；中间失败图、排查候选图、尚未达标图一律不打开。
9. **只要最终回复里提到“已跑 E2E / E2E 通过”就必须附截图绝对路径**：至少提供 1 张本轮实际核对过的关键截图完整绝对路径；没有路径不得以 E2E 结果作为收口口径。
10. **用户明确要求“端到端截图 / 实机截图 / 页面截图”时，禁止用替代图冒充交付（强制）**：不得用本地静态 HTML harness、局部渲染拼图、组件孤立页、Storybook 式沙盒、手工 clone DOM、设计稿复刻图或任何脱离真实页面链路的截图替代真实截图。若真实链路截图被环境、构建或服务 blocker 卡住，只能停下并汇报 blocker 与最小补救动作；禁止先交一张“辅助理解图”再把它说成端到端证据。
11. **用户直接要“截图 / 图 / 看图”时，默认也只允许交真实截图（强制）**：这里的“真实截图”包括真实页面截图、真实开发工具页面截图、真实运行时截图、真实设备截图；不包括手工叠加图、临时合成图、脚本后画标签图、辅助示意图、局部拼接图、裁完再重排的讲解图。除非用户明确说“先给辅助图理解一下”，否则不得把这类图片当成默认交付。
12. **辅助图只能显式降级为“排查辅助”，不得混称为截图证据（强制）**：如果为了定位问题确实临时生成了叠加点位图、手工标注图、裁切放大图、合成对照图，必须在同一条回复里直接标明“这不是截图真相，只是排查辅助图”，并且不得用它替代用户原本要求的真实截图。真实截图一旦拿不到，只能承认“当前没有真实截图证据”，不能继续拿辅助图收口。
    12A. **最终联系图/拼图的可见标签必须中文且无乱码（强制）**：如果最终验收需要把多张真实截图汇总成联系图、拼图或对照图，图内标签必须使用中文业务语义，并且生成脚本必须使用可渲染中文的字体。禁止为了绕开乱码把标签改成英文、拼音、内部缩写或测试 slug；只要图内中文标签出现乱码、方块、问号替代或被英文替换，该联系图不得作为用户验收图打开或收口。
13. **用户要“整体图 / 整体图片 / 整体截图 / 端到端截图”时，主证据只能是整屏真实页面图（强制）**：默认截图范围必须覆盖当前真实页面的整个可见视口，用 `page.screenshot({ fullPage: false })` 这类整屏截图作为主收口图；禁止把 `locator.screenshot()`、`clip` 裁图、局部放大图、overlay-only 图、局部拼接图或 contact sheet 当成主证据。局部图只允许作为排查辅助，文件名必须显式包含“局部”“裁图”或“排查辅助”，最终汇报也必须标注它不是主截图真相。
14. **截图目录与截图文件默认使用中文业务命名（强制）**：新增或修改 E2E 证据截图时，用例标题、`getEvidenceScreenshotPath` 的截图名、必要的 `subdir/filename` 必须优先使用中文业务语义，例如“万箭齐发五骰-整屏结果图”“一掷千金-滚动中”。英文测试文件名可以保留；面向用户的证据目录和图片名不得继续默认使用英文 slug。只有第三方协议、框架固定产物、历史兼容清理路径或跨平台脚本硬性要求 ASCII 时，才允许英文命名，并且最终汇报必须补充中文说明。
15. **新 UI / 改 UI 默认必须先补真实页面截图再收口（强制）**：凡本轮新增或修改了页面、弹窗、菜单、浮层、toast、徽标、列表、表单、布局或其它用户可见 UI，即使用户没有单独追问截图，也必须至少补 1 张真实页面链路截图；若改动包含多个关键态（例如入口态、展开态、成功态），则必须按关键态分别截图。没有真实页面截图时，只能汇报“代码已改/测试已过”，不得表述成“UI 已确认”或“可以收口”。
16. **局部 UI 改动不得被“只改了一小块”豁免（强制）**：像登录态切换、名字入口、头像、积分徽标、通知红点、下拉菜单、账户面板、按钮文案、tab、角标、空态、单个弹窗壳层这类看似局部的可见改动，只要用户肉眼能直接看到变化，就仍然属于截图验收范围。不得因为“没改路由/没改主布局/只是复用现有组件/已有单测”就跳过真实页面截图。
17. **用户可见状态切换至少覆盖前后两态（强制）**：当本轮修复的是“点击前后不一致”“已登录/未登录态不同步”“展开前后内容不一致”“弹错弹窗/菜单”等状态切换问题时，截图至少要覆盖 `触发前` 和 `触发后` 两张；若只给其中一态，视为未证明问题已闭环。
18. **截图必须命中用户点名的现实控件（强制）**：当用户已经点名某个具体 UI 对象或交互，例如 `3D 骰子开关 toggle`、某个按钮、某个滑块、某张卡、某个菜单项时，E2E 截图和断言必须直接围绕这个对象本身的 `触发前 -> 触发后` 状态展开。禁止用同一面板、同一区域或相邻控件的截图替代；像把“3D 骰子开关”误验成“音量滑块”这种情况，必须直接判为验收对象未锁定，不能收口。
    18A. **目的改点必须可被标出（强制）**：当本轮改动是新增/修改某个用户可见控件、入口、开关、按钮、状态标记或视觉位置时，AI 核图结论必须能直接指出它在截图中的现实位置；用户质疑“图里在哪里 / 是否通过 / 能不能圈出来”时，必须提供红圈、箭头或等价标注图作为辅助图，并明确标注对应原始真实截图路径。若无法在截图里准确指出本轮目的改点，不得判定视觉验收通过。
    18B. **截图通过必须按验收项逐张归属（强制）**：一张截图只能证明它直接覆盖的现实画面和状态，不能因为属于同一条 E2E、同一文件夹或同一流程，就外推成其它验收项通过。证据文档、任务状态和用户汇报必须给关键截图标注用途，例如“入口可见通过”“选择态通过”“等待确认通过”“阶段推进辅证”；后续阶段截图、结果页截图、等待页截图不能反向证明前一阶段的选择 UI 合格。若某张图只能证明辅助状态，必须写“辅证 / 不可作为主验收图”，不得混称为最终通过图。
19. **“流程跑通”默认按关键决策对截图（强制）**：当汇报口径包含“流程已跑通”“从开始到结束可完成”“端到端链路已收口”时，证据不得只给终点图或零散成功图。至少要按真实主流程列出每个核心决策位的 `触发前 -> 触发后` 截图对，例如创建前/创建后、摸牌前/摸牌后、确认前/确认后、结算前/结算后。若某一步没有截图对，只能说该局部链路已验证，不能上升为“整条流程已跑通”。
20. **关键决策前图必须自带下一步可操作性（强制）**：凡是拿来证明“流程仍可继续”的 `触发前` 截图，画面里必须让人一眼看出下一步主操作落在哪里。允许形式包括：真实主按钮、真实候选对象、本体可点击卡牌/牌堆/格子、明确的 owner prompt 或等待归属提示；但不允许出现“合法状态存在、却像页面卡死/没东西可点/不知道点哪里”的前图。若当前规则只剩单一合法动作，UI 必须把这一步做成显式可发现的下一步入口或短提示；否则该图直接判为不合格证据。
21. **用户要“基本流程端到端截图”时，必须逐步写清“点哪里继续”（强制）**：如果用户要的是“看懂一款游戏怎么运作”的基础流程，而不只是证明某条 bug 已修好，那么最终交付不能只是一串截图路径。必须按步骤列出：当前这张图在做什么、下一步要点击哪个现实对象、点击后会进入什么结果。`点哪里` 必须先说玩家看得到的对象名，例如“点击手牌中的这张牌”“点击地图上高亮的地区”“点击右侧确认按钮”；不得只给代码字段、locator 或内部 test id。若这条流程本身是教程/新手引导，首个正式牌桌截图还必须先把本轮正式行动讲清，并直接对应玩家真实可执行的动作；不得只讲“来源”“节奏”“先看哪一排”这类抽象概念。若教程对外口径写的是“基础教程会覆盖完整引导流程”“教程结束”“已经学会核心行动”，则截图和步骤至少要覆盖每一种正式行动各一次，并覆盖其后的必要收口动作；若只演示局部来源、只跑其中一种行动路线、或只有两步示意，只能表述为“局部教学片段”，不得上升为“完整教程已覆盖”。
22. **教程步骤的点击对象必须与真实游玩同一步一致（强制）**：只要截图、文案或引导气泡里写了“点击哪里继续”，教程这一步所高亮、所指向、所要求点击的现实对象，必须和正式游玩里真正承接该命令的对象一致。若正式游玩是点按钮，教程就不能高亮牌库；若正式游玩是点中央牌，教程就不能改成点旁边说明壳。即使底层最终发出的命令相同，只要教程教玩家点错了现实对象，也应直接判为教程验收失败。
23. **几何居中/对齐问题必须验证真实几何中心，不能拿固定槽位冒充（强制）**：当本轮问题是“居中是否为真”“宽度改了后会不会漂”“对象是不是仍然对齐到承载区中线/轴线”，E2E 断言必须直接测量目标对象组的几何中心（例如一组牌的 `group center`）与承载容器中心或目标轴线的偏差，并写明允许阈值。禁止继续用“前两张还落在历史第 1/2 槽”“和旧截图某几个 x 坐标差不多”“少牌时看起来没有更歪”来替代真实居中验证。
    23A. **用户点名的视口和状态必须进入几何验收（强制）**：如果用户从某张真实截图、某个具体窗口大小、某个展开/关闭态或某个移动姿态指出“没居中 / 漂了 / 太小 / 挡住了”，最终几何断言和截图必须覆盖这个同源状态或最近等价状态。禁止只拿更宽桌面、另一种展开态、另一条主流程或单元几何通过，替代用户点名画面本身。
    23B. **多对象组合布局不能只验合并中心（强制）**：当中央牌桌、地图区、骰盘区或 HUD 同时包含两排或多类对象（例如筹码排 + 公共牌排、骰子 + 结果牌、地图目标 + 指示物）时，E2E 必须同时验证组合整体中心和内部关系。最低断言包括：① 各对象本体都真实存在且尺寸非零；② 上下/左右顺序正确；③ 对象间距在合理阈值内；④ 各子对象围绕同一中线或锚点分布，而不是只把最外层合并盒子凑到中间。禁止用“外包围盒居中”冒充多对象组合视觉达标。
24. **几何稳定性至少覆盖两种数量或尺寸状态（强制）**：只在单一牌数、单一宽度、单一视口下量一次，不能证明“改宽度也不漂”。像牌河、弃牌区、头像列、按钮组、导航居中这类会随数量或尺寸变化的对象，默认至少比较 `低数量/窄状态` 与 `高数量/宽状态` 两态，并同时确认：对象组中心对齐、单体宽高未被偷偷改大、上下排或前后态仍共用同一中线/锚线。
25. **用户质疑“真实窗口里的大小/占比”和 E2E 不一致时，必须补多宽度桌面证据（强制）**：只要问题点涉及“真实浏览器里更大/更小”“窗口一变就不像同一套 UI”“E2E 截图比例不真”，默认至少补 `宽桌面` 与 `较窄真实桌面` 两档浏览器级证据，并同时记录真实视口宽度、目标对象宽高或关键容器宽度。禁止继续只拿单一 `1920x1080` 理想桌面截图，或只凭一句“CSS 没变所以应该一样”收口。
26. **尺寸争议必须优先取同一真实浏览器会话的运行时视口与元素读数（强制）**：只要用户明确说“看我浏览器真实截图”“这和我实际 Chrome 不一样”“我要你读元素尺寸而不是只看图”，就不能再用独立 Playwright 新开窗口或另一套固定 viewport 代替当前会话。默认必须先从同一真实浏览器会话读取 `运行时视口宽高`、`devicePixelRatio`、页面根上的运行时 viewport 变量，以及目标元素的 `getBoundingClientRect()` 结果，再拿这些读数和 E2E 结果对照。禁止把“E2E 里 1920 截图正常”当成“用户当前 Chrome 也正常”的证据。
27. **固定牌桌的共享中线与尺度链必须在同一真实会话里同时验证（强制）**：当桌面牌桌声称“中央牌区、手牌区、顶栏仍是同一套正式 UI”时，断言必须同时量出这些区域的几何中心线与关键卡牌尺寸，并确认它们共用同一条中线/同一套缩放结果。禁止一块区域靠 `calc(100vw - Npx)`，另一块靠独立 `right/bottom` 魔数，第三块再靠额外 `transform: scale(...)`，最后只凭截图“看起来差不多”就收口。
28. **真实浏览器旧 tab 若仍挂旧 bundle / 旧尺寸链，不得直接拿来否定当前代码（强制）**：当真实 Chrome / Edge / 原生 WebView 里已经存在历史打开的房间页、旧对局页或长时间未刷新的 tab 时，必须先读取该页当前运行时 CSS 变量、关键元素尺寸或其它版本指纹，确认它确实对应当前代码现场；若读到的运行时公式、关键变量或关键几何仍是旧值，就只能把它归类为“历史现场/过期 bundle 证据”，不得继续拿它和当前工作树代码、当前 E2E 结果做一对一归因。此时默认动作是：在同一真实浏览器会话里新开一个当前开发环境房间或强制进入当前页，再复测同状态尺寸。
29. **尺寸争议的最终裁决必须补“新真实房间 + 同状态复测”（强制）**：当用户指出“真实浏览器里的牌大小和当前 E2E 不一致”，并且已发现旧 tab 可能挂着历史 bundle 时，最终不能停在“旧 tab 是旧的”这句解释上。默认必须再在同一真实浏览器会话里创建一个新的当前开发环境房间，把它推进到与 E2E 同类的牌桌状态（至少相同视口档、相同牌数档），然后重新读取关键卡牌宽高和容器宽度。只有这份“新真实房间同状态复测”结果，才可作为当前代码是否仍分叉的最终依据。
30. **死端口旧页 / 浏览器错误页不得当真实现场证据（强制）**：如果所谓“真实 Chrome 页面”已经掉成 `chrome-error://chromewebdata/`、正文出现 `ERR_CONNECTION_REFUSED`，或它指向的本地开发端口与 `.tmp/dev-runtime-ports.json` 里的当前前端端口不一致且目标端口未监听，那么这页只能归类为“失活开发页/浏览器错误页”，不得继续当成当前 UI 现场、真实页面截图证据，或拿来否定当前代码。默认先核当前活跃开发端口、该页目标端口是否仍可访问，再决定是否新开当前真实页复测。
31. **真实浏览器验收前必须先判活当前开发端口（强制）**：凡是要用真实 Chrome / Edge 当前会话做本地开发页验收，至少先确认三件事：① `.tmp/dev-runtime-ports.json` 记录的当前前端端口；② 目标 tab 实际指向哪个本地端口；③ 该端口当前是否还能返回开发前端资源（例如 `/@vite/client`）。三者未对齐前，只能继续诊断“页是不是旧的/端口是不是死的”，不得直接把截图或页面表现上升为当前实现结论。
32. **活端口旧 tab 也可能挂过期运行时，不能只凭端口存活就当当前实现（强制）**：即使目标页仍指向当前活跃开发端口、`/@vite/client` 也能返回 `200`，该 tab 仍可能在长时间不刷新后保留旧布局、旧模块状态或旧几何链。只要刷新同一页后 `slotCount`、关键元素宽高、关键对象组中心偏差、运行时类名或其它核心几何指纹发生明显变化，就必须把这页归类为“活端口旧运行时页”，不得继续拿刷新前画面当当前实现证据。
33. **真实浏览器几何争议默认补同页刷新前后对比（强制）**：当用户质疑“我眼前这个活页和你现在代码不一致”，且该页并非死端口错误页时，默认至少补一次“同一页刷新前 -> 刷新后”的运行时对比，记录刷新前后的 `data-slot-count`、关键卡牌宽高、对象组中心偏差或等价几何指纹。若刷新后这些关键值翻正，结论只能写成“刷新前是旧运行时现场，刷新后才是当前实现”，不得继续把刷新前截图当当前 UI 真相。
34. **禁止为通过截图验收写牌数/视口特判布局（强制）**：当用户验收口径是“少牌态应与满牌态共用同一套位置语义/尺寸语义”时，修法必须优先落在统一布局结构上，例如固定槽位、稳定锚点、空槽位占位、同一套容器与坐标系；禁止为了让某几张截图过关，单独对 `1 张/2 张/某个阈值/某个视口` 写条件分支、临时偏移、魔数回中或只服务单张图的特殊排布。验收时必须证明：同一实现同时覆盖空态、低张数、中张数和满态，而不是靠每档数量单独调出来。
35. **固定槽位类布局优先用“空槽位占位 + 同一套坐标”实现（强制）**：像牌河、弃牌区、底座列这类用户要求“1 张也要落在满铺第一个位置”的对象，默认实现应是固定槽位或等价占位结构：无牌时保留空槽位，有牌时只替换对应槽位内容；不得靠“少牌时重新算起点”“某张数单独回中”“为了少牌图好看临时换一套步长”去模拟。若用户进一步要求“第二排横向错位、同排间距固定、改宽度后位置语义不变”，就必须把这些规则做成统一几何常量，并让 `1 张 / 2 张 / 9 张 / 10 张` 共用同一套常量，而不是按数量分支特殊处理。
36. **尺寸/位置争议除了截图还必须落运行时几何 JSON（强制）**：当用户明确质疑“真实浏览器里的牌大小、间距、居中和 E2E 图不一致”时，除了关键截图，还必须同步保存可回查的运行时几何数据，例如视口宽高、`devicePixelRatio`、容器 `getBoundingClientRect()`、目标元素 `width/height/x/y`、关键 CSS 变量。没有这类 JSON 或等价数据，只凭截图肉眼和口头描述，不得宣称已经证明“真实大小和位置一致”。
37. **用户反馈“什么都不做也一直闪 / 一直平移 / 感觉在反复重排”时，禁止只靠单帧截图收口（强制）**：这类问题本质是动态稳定性问题，不是静态布局存在性问题。默认必须先建立“静置窗口内不再重复进入动画态/重排态”的验证环，再谈收口。至少要覆盖：① 进入用户原始问题位点；② 在不进行任何操作的前提下等待一段静置窗口；③ 再次采样动画态、几何矩形或等价运行时指纹；④ 证明前后稳定，而不是继续变化。
38. **静置重排类问题默认先补受控调试日志（强制）**：当用户明确提出“要不要先加日志复现”，或当前症状肉眼像 `重复进场 / 重复动画 / 上层重挂 / 状态机抖动` 时，默认允许先加带唯一前缀的受控日志，并把日志范围收窄到能区分根因的边界，例如 `Board mount/unmount`、动画 cue 设置、预加载门禁切换、关键 runtime key 变化。禁止直接上“全量 console.log 一切”；也禁止在没有静置复现环时只凭猜测继续调样式。
39. **静置稳定性门禁优先于普通截图门禁（强制）**：只要本轮主症状是“静置仍在动”，最终验收除了关键截图，还必须至少有一条自动化或等价可复查证据证明：在同一状态下，连续两次采样之间关键对象的 `data-motion`、`transform`、`rect`、`key`、`mount 状态` 或等价指纹没有继续变化。若只能证明“某一帧看起来正常”，仍视为未证明原始问题修复。

## 流程截图证据链

1. **流程截图必须通链路**：凡涉及“翻牌/抽牌/改投/重掷/分步确认/选择/结算/关闭/阶段推进”的交互，必须提供连续截图链；完整端到端默认至少覆盖 `触发前`、`翻出或亮相后`、`选择或投骰前`、`选择/投骰后`、`结算后`、`关闭后` 六段，且每张都写清观察结论。只有两段、四段或直接注入中间态时，只能证明局部前后态或阶段承接，不得宣称整条流程已跑通。
2. **完整链路必须登记四列闭环（强制）**：证据文档、任务状态或验收汇报里必须按六段逐项登记 `玩家实际动作 / 自动断言 / 截图文件 / 用户目标对应`。其中“用户目标对应”要写现实结果，例如“证明牌已翻出”“证明先选择后投骰”“证明结算伤害落位”“证明关闭后回牌桌可继续操作”；不能写成内部状态、组件名或截图编号。缺少任一列时，该对象只能登记为 `待补完整链路`，不得写“完整端到端通过”。
   2A. **写链前必须先锁规则时序家族（强制）**：用例开始前必须从规则真相源或当前数据合同确认该对象属于哪类时序，例如 `先选择后投骰`、`先投骰后选择`、`投骰后直接结算`、`可选是否触发`、`翻出后自动结算`。E2E 只能按该家族的真实顺序截图和断言；不能用“已有骰子才出现选项”的链路去证明“先选择后投骰”，也不能用直接结算链路去替代需要选择目标或属性的链路。
   2B. **端到端结果必须回扣本轮问题（强制）**：写 E2E 前先把用户点名目标拆成可观察结果，例如“牌确实翻出”“先选属性再投骰”“投骰后才出现选项”“跳过后哪项属性 +1”“关闭后是否回牌桌”。测试名、断言、截图和 evidence 必须逐项命中这些结果；只证明“有选项”“有骰盘”“按钮能点”或“最后状态看似正确”，不能替代整条链路。
3. **阶段结果必须和目标直接相关（强制）**：如果用户目标是“选项太小”“左侧能否滚动”“背景框不该出现”“属性颜色别全一样”“骰子是否重叠”“蜘蛛效果是什么”，对应阶段必须有自动断言或截图观察直接证明这个目标；不能用“测试通过”“按钮存在”“页面没有报错”替代。滚动类问题必须真的滚动并证明滚动后目标内容可见；选择类问题必须点真实选项或真实对象；结算类问题必须证明玩家能看见最终后果。
4. **无弹层收口也算一段（强制）**：如果流程没有关闭按钮，最后一张截图和断言必须证明“结算后的清理状态”，例如已选物品/目标消失、目标高亮回到候选态、确认提示回到初始态、主操作区仍可用。不能因为没有弹层就把六段缩成四段。
5. **奖励骰/骰子特写要求**：若交互会出现奖励骰特写或骰子特写，证据必须包含：
   - 特写出现的截图（可见骰面/提示/重掷入口）
   - 重掷/改投后的特写更新截图
   - 若规则要求“主攻击骰盘不改动”，截图中必须能看出主骰盘保持原值

   **奖励骰重掷/改投证据链 Checklist（建议按此顺序组织截图）**：
   1. **触发前/刚触发**：若存在攻击修正徽章/提示，截图应能看见其已出现；若结果需延迟生效，此时不应提前出现“已加伤”的结果展示。
   2. **特写出现**：overlay 可见，能关联到本次来源（卡牌/技能/token 的 effect 文案或等价提示）。
   3. **改投/重掷后**：overlay 仍可见，骰值/骰面发生变化（或有等价状态证据）；若有重掷上限，应能区分“达到上限”与“资源不足”。
   4. **关闭**：overlay 隐藏。
   5. **收口（settled）**：对应 pending/临时状态已清空，且流程可继续推进。
   6. **最终态**：伤害/状态/指示物/攻击修正等关键结果处于期望最终态（成功路径）。

   **生效时机判定（强制）**：特写/奖励骰只是 UI 展示形态，不等价于“数值必须等到关闭才生效”。一切以**卡牌/技能/token 自身描述**为准：
   - 若描述是“掷 1/5 颗骰子并获得该骰面的效果”（例如 Righteousness / Zanshin）：掷骰发生时效果即已确定，数值/状态**允许在特写打开期间写入权威状态**（随后再展示、再关闭）。
   - 若描述是“当你花费 X 时…然后…”或明确写了“结算后/关闭后/花费后才追加”（例如 Wild West 挂载到 Loaded 的 postSettle 加伤）：必须证明数值**不会在特写阶段提前写入**，只能在实际触发点/收口点写入。
   - **攻击修正徽章仅是效果提示，不是结果证明**：徽章出现不代表伤害已提前计入，需结合状态断言或收口后结果截图验证。

6. **无证据链不得收口**：未提供完整截图链路时，只能标记“待补/未达标”，**禁止宣告完成**。
7. **必须覆盖成功路径（强制）**：若交互存在“成功/失败”两类结果（如改投成功 vs 改投失败提示），证据链截图**必须包含成功路径**；仅有失败提示截图只能标记“未达标/待补”，不得作为收口证据。
8. **失败提示不得替代成功证据（强制）**：失败提示（toast/modal/红字提示）截图可作为补充证据，但**不能**替代“成功后状态已改变”的截图。
9. **必须覆盖收口清理（强制）**：凡涉及“弹层/特写/分步交互关闭后继续结算”的链路，证据必须包含“关闭后已收口”的证明：
   - UI 层：弹层/特写已关闭，且关键展示（如攻击修正/骰盘值）处于期望最终态；
   - 状态层：对应 pending/临时标记已清空（命中 D14/D15），避免“只关 UI 不清状态”的假修复。
10. **对外口径门禁（强制）**：如果你在对用户的最终回复中提到“已跑 E2E / E2E 通过 / 已验证成功”，则必须给出至少 1 张你实际核对过的关键截图的**完整绝对路径**；否则不得使用该口径收口。

## 用例拆分与命名

1. **入口合同和游戏合同分文件优先（强制）**：主页/大厅/进房类测试，优先放在入口或房间主题文件；牌桌进行时、终局、刷新恢复、spectator、AI roundtrip 等优先放在游戏主题文件。不要把“从主页开始”和“完整对局”机械混在同一文件里。
2. **同一用例只证明一个主合同（强制）**：每条 E2E 必须能用一句话说清自己主要证明什么，例如“可从大厅进入房间”“可在近终局代表态完成最后一弃”“spectator refresh 后仍不泄露”。若一条用例同时承担多个主合同，优先拆分。
3. **标题必须反映覆盖边界（强制）**：如果只证明中间态、入口态、近终局态、单轮 roundtrip、代表分支、刷新恢复，就必须把这些边界写进标题；禁止用“完整可玩”“可结算”“已完成”这类完成态措辞夸大覆盖。
4. **重复前置一律抽掉（强制）**：当多条测试反复从同一前置漏斗起跑，只为验证后面不同合同，应优先把共同前置收成 helper、fixture 或代表态注入，而不是在每条用例里重复走一遍。

## 特写与延迟结算

1. **涉及“骰子特写/奖励骰/重掷/改骰盘”的交互必须提供成功路径证据链**：最少 2 张连续截图：**触发/特写出现** -> **执行关键操作后 UI/结果发生变化**（例如重掷后骰面变化、改投后数值/徽章变化）。
2. 若交互包含“关闭/确认/收口”，则必须再补 1 张**收口后**截图证明流程已回到可继续推进的状态（例如特写关闭、pending 状态清空、阶段可继续推进）。
3. **禁止**只提供“失败提示 / 门禁 toast / 不可用提示”的截图就宣告完成；失败截图只能作为否定路径补充证据。
4. **攻击修正徽章（Active Modifier Badge）属于“效果提示”，不是“结果证明”**：徽章出现只代表“攻击修正已打出/已激活”，不代表加伤数值已经提前计入。
5. 若攻击修正包含“延迟结算/分段生效”（例如依赖奖励骰特写收口后再追加加伤），E2E 必须同时证明：徽章可在打牌后出现；伤害/加伤数值只在实际生效时写入权威状态（例如 `bonusDamage/attackModifierBonusDamage` 不会在特写阶段提前变化）。

## 看图验收

1. **看图必须直击问题位点**：不能只扫整页，必须逐项核对用户这轮指出的具体区域、具体现象和具体目标；如果是展开类/浮层类问题，主截图必须同时包含触发控件、展开内容完整边界、关键参照物。主截图收不全或看不清边界细节时，默认“未证明修复”，必须补局部放大图。
2. **缩放/偏移类问题必须显式判断“有没有缩在左上角/是否被误修成窄布局”**：用户反馈的是“整体偏了、缩在左上角、横屏不该变窄、像桌面端”这类问题时，看图结论必须单独写清：主内容是否仍只占左上角一块；HUD 与主内容是否仍在同一视觉坐标系；是否被错误改成窄布局/双列路线。不能只写“页面出现了/元素都在”。
3. **证据截图必须看得到“对应物”本体**：凡是宣称“某对象/某特写/某控件/某奖励骰/某弹窗/某表情已经出现、位置正确或视觉达标”的截图，肉眼必须能直接看到该对象本体、完整主体轮廓或足以识别的关键内容；如果截图里只有外围布局、遮罩、容器边界、背景、文案或其它无关元素，看不到被宣称对象本体，则该截图一律视为无效证据，不得用于收口。
4. **对象被裁切时不得判定视觉通过**：凡截图用于证明浮层、表情、popover、HUD overlay、特写或控件的视觉结果时，如果目标对象被视口边界、截图边界、容器裁剪、遮挡层或固定定位截断到只露边角/只露局部，最多只能证明“事件触发 / DOM 存在 / 局部进入视口”，不得证明“视觉达标 / 用户看得清 / 可收口”。
   4A. **移动端牌桌关键对象不得用局部可见偷过（强制）**：移动端整屏验收里，手牌区、牌堆、弃牌堆、行动按钮、玩家面板、地图目标等本轮关键对象必须逐项检查主体完整可辨；禁止只因为中间某一张牌、某一个按钮或某个局部元素完整，就宣称整组 UI 通过。若左右牌堆、边缘手牌或关键操作对象只显示半截、被下沿/侧边裁掉、或需要用户靠猜才能识别，一律判为截图未达标，并必须修布局或收紧 E2E 断言。
5. **高亮/可落点/选中反馈类问题必须按顺序排查**：当用户反馈“高亮没了、可选格看不见、选中反馈不明显、落点不亮”时，必须先确认实现里是否真的存在对应高亮/反馈逻辑；再确认触发链是否真的产出高亮状态/候选数据；只有在确认已触发后，才能用 E2E 和截图证明实际效果。
6. **高亮若不能让第一次看图的人一眼认出目标，直接判不合格（强制）**：凡是靠描边、发光、遮罩、外圈、脉冲或底色来表示“这里可点 / 当前选中 / 当前焦点”的 UI，在整体主截图里必须让第一次看图的人不需要猜就能说出“高亮的是谁”。如果仍要靠局部裁切、口头解释、读 `data-testid`、数边框厚度或对照 DOM 才分辨得出目标，就只能判为“高亮存在但不可辨识”，不得收口。此时默认动作不是补一句说明，而是回到实现里继续拉开高亮对象与周边非目标的对比。
   6A. **用户点名颜色框/描边/发光时必须肉眼可见完整标识（强制）**：凡用户明确要求“黄色框、橙色框、红色框、描边、颜色框、发光框、高亮框”等视觉标识，最终整屏截图里必须能直接看见对应对象的完整颜色边界，并且颜色顺序、数量和用户描述一致。若目标被面板、浮层、视口边缘或其它对象遮挡，边框太细太淡、只靠 DOM 属性/测试字段能证明、或必须局部放大后才能看出框在哪里，一律判为“截图未达标”；不得打开给用户当最终验收图，也不得宣告完成。
7. **用户要求“恢复原来的效果”时先锁 git 基线**：必须先通过 `git log` / `git show` / `git blame` 给出 `last known good` 与 `first known bad` 候选，再决定是恢复历史行为还是在历史行为上做增量修复；必须实际打开并阅读对应旧实现、旧截图或旧 evidence，明确旧版本当时怎么实现、怎么显示、怎么验收。
8. **回归恢复默认先还原历史实现，不得重写“像以前”的近似版（强制）**：当用户明确要求“改回原来”“恢复旧样式”“默认关闭时和以前完全一样”时，默认动作必须是基于 `last known good` 的真实代码做恢复或分支抽离，而不是在当前实现上凭印象重写一版“看起来差不多”的 UI。只有在证据已经证明旧实现本身不可直接复用，或用户明确授权“允许重新设计/重写”时，才允许偏离历史实现。最终汇报必须说清：恢复基线是哪一笔提交、哪些文件直接参考了旧实现、哪些部分仍是当前增量逻辑。
9. **功能开关双分支必须按两份正式合同收口（强制）**：当同一开关同时承载“默认关闭旧路径”和“开启后新路径”两种 UI/交互时，必须把它们视为两份并列正式合同，而不是“一个主路径 + 一个临时例外”。默认要求同时满足：① 关闭态回到旧实现或旧合同；② 开启态只承载新能力；③ 两边各自有独立截图证据与断言；④ 关闭态不得继续消费开启态的共享视觉逻辑，除非证据已证明该共享层在两边语义完全一致。若当前实现仍处于“旧路径套着新组件 / 新路径又继承旧补丁”的混用状态，不得宣称回归已收口。
10. **用户要求“直接用原来的代码”时，验收先看代码回接证据，再看截图（强制）**：关闭态不能只靠“截图看起来像以前”过关，还必须给出它当前确实回到了哪笔旧提交、哪组旧组件或旧样式入口的证据。截图负责证明用户可见结果，代码回接证据负责证明这不是在新实现里临摹出来的近似版。
11. **若关闭态仍跑在开启态视觉入口里，默认验收失败（强制）**：当用户要的是“完全旧实现 + 完全新实现”两条并列合同，只要关闭态仍然主要依赖开启态的 render 分支、样式入口或新视觉容器，哪怕截图暂时接近历史效果，也只能算“新路径兼容旧观感”，不能算“旧合同已恢复”。除非证据已证明该入口本身就是历史旧实现的直接延续，否则默认判失败。
12. **双分支回归必须先证明“拆开了”，再证明“都好了”（强制）**：除了旧合同来源图、关闭态图、开启态图之外，还必须能说明当前开关是如何把两条实现明确分流的，例如独立组件、独立 render 分支、独立样式入口或独立策略层。若实现仍然混在一套最终视觉 JSX 里，只是条件不同，则不能宣称“双分支回归完成”。
13. **双分支回归默认要有三段证据链（强制）**：至少同时具备 `旧合同来源证据`、`当前关闭态证据`、`当前开启态证据`。如果只给当前截图，不给旧合同来源，最多只能证明“现在长这样”，不能证明“这是恢复了原实现”。
14. **双分支回归的默认验收顺序（强制）**：涉及“默认关闭旧体验 + 开启后新体验”的回归时，验收顺序必须固定为：① 先证明关闭态已回到历史合同；② 再证明开启态单独成立；③ 最后证明开关切换不会串态。禁止只截开启态新图，或只证明“切换后能看到变化”，就反推关闭态也没问题。
15. **关闭态验收必须直接对旧合同，不得对“当前感觉差不多”**：关闭态截图、断言和人工核图必须明确对应 `last known good` 的历史行为，例如旧骰盘位置、旧按钮样式、旧交互承接物、旧可见信息范围。若当前只是“肉眼上类似”“没有明显坏掉”，但没有对到旧合同证据，不能算关闭态通过。
16. **双分支必须各自有独立证据组（强制）**：默认至少要分成 `关闭态证据` 与 `开启态证据` 两组截图/断言；若本轮还验证切换链路，则再补 `切换前 -> 切换后` 一组。禁止把两边混在同一组抽象截图里，让人无法判断每张图到底代表哪个正式合同。
17. **关闭态必须显式排除新分支污染（强制）**：当本轮目标是“默认关闭时完全旧实现”，关闭态验证不能只证明旧对象出现了，还必须证明新路径专属对象、样式或交互没有偷偷介入。像新骰台、新动画承载层、新布局占位、新特写容器这类开启态专属可见物，只要关闭态还能看到或还能影响布局，就应直接判失败。
18. **最终回归结论必须同时回答“旧的回来了”和“新的没丢”（强制）**：这类任务的最终结论不能只说“回归修了”或“3D 还能用”。必须同时说明：关闭态已恢复哪一份旧合同，开启态保留了哪一份新合同，以及两边现在如何被开关明确分流。三者缺一，不得收口。
19. **流程关键截图必须可继续操作**：凡是用于证明“流程可继续/可完成”的截图（如创建房间、确认弹窗、支付/提交、加入房间、密码输入），画面里必须同时可见下一步主操作控件（如“确认/创建/提交”按钮）且控件不被裁切、不在可视区外。若截图里看不到下一步主按钮或无法判断点哪里继续，该截图一律判定为无效证据，不得收口。
20. **合法等待态必须显式说明“谁在等谁”（强制）**：如果当前截图不是你操作，而是等待别人、等待 AI、等待服务器推进，则画面里必须直接可见等待归属或当前控制权信息，例如“等待玩家 X”“AI 正在行动”“对手处理中”。禁止让“合法等待态”和“页面没反应/流程挂起”在截图上长得一样。
21. **临时浏览器排查必须保持 snapshot 纪律**：使用 Playwright CLI、Browser snapshot 或等价浏览器自动化做临时排查时，必须先获取当前 snapshot 再按元素引用操作；导航、弹窗开关、菜单展开/关闭、阶段推进、DOM 大幅变化后必须重新获取 snapshot。旧元素引用只能作为历史线索，不得继续当作当前页面真相。
22. **战斗/进攻/掷骰证据必须拍到“掷骰结果本体”**：如果本轮汇报里声称已经证明了进攻、战斗或掷骰流程，关键截图里必须肉眼可见骰子本体、骰面结果或明确的掷骰结果文本；不能只给“已经进入战后选择”或“日志里提到掷骰”来顶替。
23. **技能/卡牌效果链路截图必须覆盖使用时和使用后状态（强制）**：凡用户质疑某个技能、卡牌、Token 或骰面结算“到底有没有生效 / 中途资源能不能用 / 最终血量对不对”，E2E 截图不能只截最终图。至少要覆盖 `使用前或触发前`、`使用时或响应窗口中`、`使用后或最终结算后` 三类状态；若中途会获得资源并立刻影响本次结算，还必须截图证明“资源获得后可用”和“资源使用后结果变化”。只靠一张最终截图，或只靠内部断言，没有资格说端到端证明完成。
24. **多人同意 / 可跳过分支必须截等待态和收口态（强制）**：凡流程需要本地确认后等待其他玩家、AI、服务器或全员同意，例如下一阶段投票、交易同意、手牌调换、可跳过/不执行分支，E2E 不能只截“选择中”或最终态。最低截图链必须包含：`本地确认后等待其他人`、`其他人/全员同意后进入下一阶段`；如果该动作既可执行也可跳过，还必须至少覆盖一个跳过或空 payload 路径，证明不是被强制执行。
25. **掷骰截图不得用“存在”替代“可读”（强制）**：骰子结果验收必须同时判断布局和可读性：骰子盘应占结果区主要空间，骰面不能侧成线、糊成不可辨纹理、被裁切、过小或被信息文字挤压；加值、检定条件、总点数、成功/失败结果应放在独立信息区。若只证明 DOM 节点存在、贴图加载、物理源接入或日志有总点数，一律不能宣称骰子视觉通过。
    13A. **掷骰与改骰流程必须逐步核 UI 表现（强制）**：当用户质疑骰面、点数、重掷、改骰、使用道具或选中效果时，端到端验收不能只看测试通过。截图链至少覆盖 `投掷结果出现`、`可介入对象选中`、`选择要改/重掷的骰子`、`改/重掷后结果` 四类关键态；每一态都必须肉眼核对 UI 是否友好、主对象是否在主视线、合法对象是否高亮、按钮是否抢焦点、信息区是否与可见结果一致。缺任一关键态，只能说“局部链路通过”，不能说端到端 UI 已收口。
    13A.0 **能直接选中画面对象就不要加代理按钮（强制）**：当玩家要选择的对象已经在画面里可见，例如卡牌、骰子、Token、房间、地图格、单位或目标区域，主流程必须直接选中该对象本体或其投影命中区。数字按钮、文字列表、编号选项和重复说明按钮只能作为无障碍/备用入口，不得替代玩家对真实对象的选择；E2E 必须优先断言真实对象被选中，而不是只断言代理按钮可点。

27. **专用骰面必须按规则值验收（强制）**：如果游戏骰不是普通 1-6 点骰，例如山屋骰为 0/1/2 点，验收不能把规则值映射成普通 d6 的 1/3/5 面后仍称为“游戏骰”。必须证明骰面视觉和规则值一致；若使用第三方物理骰引擎，也要接入专用骰面皮肤或专用模型，不能只证明通用 d6 在滚动。
    26A. **第三方物理骰引擎的通用面映射不能外露成玩家语义（强制）**：如果底层 dice-box / Three.js 仍需要用普通 d6 的 `1-6` 数字驱动物理结果，玩家看到的骰面必须由游戏专用材质、贴图、皮肤或模型本体承载成真实规则值。不得用 DOM 数字、额外小骰面列、浮层标签或结果说明去盖住/补救通用 d6；这类做法只能算临时止血，不能作为验收通过。验收截图和汇报只能说玩家实际看到的 0/1/2、符号或自定义面，不能把内部 d6 映射当成玩家规则解释。
    26B. **自定义骰不得只贴目标面（强制）**：当物理骰使用通用 d6 模型承载 0/1/2、符号或其它专用规则值时，不能只给“理论朝上面”贴正确图案、把其它面留成纯色/空白/无意义材质；最终截图里任何可见大面都必须是玩家能理解的有效规则面。像“纯色无点其实代表 2”这类解释直接判为骰面素材或面序映射失败，必须修贴图、材质分布、模型面序或落定姿态，不能靠说明文字收口。
    26C. **可见骰面诊断不得抄业务结果（强制）**：E2E 若断言“可见骰面等于结算骰”，诊断值必须来自物理引擎当前朝上面、材质面、贴图面或截图可核验结果；不得直接把业务投掷数组、规则 subtotal、测试预期值复制成 `visible` 字段。否则测试只能证明状态链有值，不能证明玩家看见的骰子本体正确。
28. **物理骰最终截图必须等骰子停稳（强制）**：如果物理骰组件提供 `settled`、`finished`、`animationEnd` 或等价状态，E2E 截图必须先等该状态为真，并额外留出一小段稳定时间再截；禁止在滚动中、刚落地残影、半悬空或过渡帧截最终验收图。截图断言必须覆盖真实可见 canvas、专用骰面、透明/开放式骰区，以及骰盘不被玩家面板、牌库栏、HUD 或教程层遮挡。
    27A. **多颗物理骰必须逐颗完整可辨认，禁止叠成一团仍通过（强制）**：当规则态应显示多颗骰子时，最终整屏图必须能按期望数量逐颗辨认出独立骰体和主要骰面；任何两颗不得大面积互相覆盖，也不得因全部中心塌缩到同一区域而只剩少数可见骰面。E2E 必须同时验证期望骰子数量、真实物理投影尺寸、按每对骰子尺寸归一化的中心距离、交叠风险和整体散布范围；只断言 DOM 节点数量、画布存在、总像素量、横纵像素桶或固定像素中心距均不足以证明逐颗可见。骰子存在明显旋转或透视时，优先使用旋转感知轮廓、归一化中心距和整屏肉眼结论；轴对齐外接矩形的交叠只能作为“接近完全覆盖”的粗门禁，禁止把外接框空白角相交误判成骰体重叠。若机器几何断言与整屏截图肉眼结果冲突，一律回看真实截图并修正实现或错误门禁，禁止用绿灯覆盖“全叠在一起”的图面事实，也禁止用错误几何指标否定截图中已经逐颗完整可见的骰子。
29. **可改骰阶段不得遮蔽或复读可介入对象（强制）**：如果投骰结果仍可被物品、手牌、Token 或技能修改，结果展示不能把这些可介入对象模糊、压暗或当成背景。E2E 必须验证合法介入对象仍可见、可点击，并有完整对象边界的无文字高亮；如果牌面/素材已经写明效果，不得额外叠“改骰”这类可见文字标签。截图结论也要说明“当前是否还能改骰”。只有不可再介入的最终结果，才允许作为纯阻塞结算展示。
    29A. **改骰目标选择必须落在真实对象上（强制）**：可改骰阶段的交互顺序应是 `选择可介入物品/技能` → `直接点选要被影响的骰子本体` → `显示改后结果`。除非真实骰子元素无法稳定命中，否则不得把“选骰子”降级成旁边一排数字按钮；E2E 必须断言主路径命中的是真实骰子元素或其投影命中区，并断言替代数字按钮没有出现在玩家主流程里。若截图里玩家看起来是在按数字而不是选骰子，该交互不得收口。
    29B. **投骰结果关闭合同必须统一（强制）**：所有投骰结果、骰子特写、发现/事件即时检定、攻击复盘、驱魔复盘等阻塞式骰盘，默认都必须支持点击空白 / backdrop 关闭，并在关闭后证明骰盘、阻塞层和临时选中态退场。唯一例外是当前仍存在可改骰、可重掷、可锁定骰子或其它合法介入对象时：空白关闭必须禁用，界面必须保留明确的交互按钮或完成改骰所需的对象选择入口；完成改骰、消耗介入机会或不再允许改骰后，才恢复空白关闭。E2E 不能只测按钮，必须分别断言空白关闭 `enabled` 与可改骰时 `disabled` 两种状态，并实际点击空白证明对应结果。
    29C. **阻塞式投骰未收口前不得推进行动权（强制）**：回合结束、房间效果、攻击、事件或作祟结算只要仍显示阻塞式骰盘、骰子特写、backdrop、可改骰入口、重掷入口或必须点击的确认/关闭入口，就表示当前行动链尚未完成；此时当前行动者必须仍是投骰/结算玩家，下一位玩家不得获得行动入口。凡 E2E 涉及“投骰后轮转 / 别人行动 / 多玩家回合交接”，必须断言投骰者与当前行动者一致、下一位行动入口不可用，并实际点击确认/关闭或完成改骰后再断言行动权切到下一位。若当前仍可改骰、重掷或锁骰，空白关闭必须禁用，且界面必须保留明确按钮或对象入口；只有骰盘收口后，才允许隐藏阻塞层并进入下一位行动。移动端验收也必须覆盖同一合同，不能只证明元素缩放或按钮可见。
30. **截图命名和汇报必须说真实画面对象（强制）**：对用户汇报截图时，必须使用玩家能看懂的画面对象和动作，例如“驱魔神志检定骰盘”“驱魔成功后的终局页”“发现牌《外星几何》的知识检定骰盘”“兔脚改骰高亮”。如果截图在终局页里保留了上一步投掷，只能说“终局页保留的最近一次驱魔检定骰盘”，禁止造“终局物理骰”“终局投掷结果”“结果物理源”“canvas 状态”这类不对应现实规则时序或现实画面的名称；如需提代码证据，先说现实含义，再补内部字段或测试名。
31. **看到不达标就必须写“不达标”**：如果截图里出现手牌缺失、控件偏移、被遮挡、只剩边角、主元素跑到一侧、状态不完整等现象，即使 E2E 断言通过，也必须在证据文档里明确写“未达到验收标准 / 不能据此收口”，并继续修图、修实现或修测试。
32. **禁止把“没缩在左上角”偷换成“整体已正常”**：对于移动端 UI 重构/布局修复，截图结论必须区分“已摆脱极端故障”和“布局已完全达标”。若截图只能证明“不再缩在角上/不再整屏错位”，就只能这样写，不能顺势宣称“整体完全正常”。
33. **出现新异常或链路不真都不得收口**：即使断言通过，只要截图里还有新的视觉异常、遮挡、空白块、层级错误、异常位移，或 E2E 没覆盖本轮风险，就不能宣称完成；先加日志定位，再审查调用链，最后修实现或修测试。
34. **trace / console / network 只能作为辅助定位证据**：当截图异常但断言通过、流程卡住、点击无效、资源或接口疑似异常时，可以补抓 trace、console、network 记录辅助定位；但这些记录不能替代关键截图、肉眼验收结论和本轮问题位点的可见证据。
35. **最终验收图里不得残留过渡占位/ghost/临时骨架（强制）**：凡是已经被表述为 `静置态`、`最终态`、`正式可操作态`、`已收口截图` 的证据图，画面里不得继续保留只服务过渡阶段的半透明占位、ghost 卡槽、残影、过渡骨架、旧动画壳残留或任何“只是为了发牌/加载/入场提示存在一瞬间”的对象。只要最终验收图里还看得到这类残留，即使 E2E 文本断言、DOM 数量断言或矩形稳定性断言全部通过，也必须直接判为未达标，不得宣称成功。
36. **截图落盘不等于前端链路通过（强制）**：只要真实页面在同一轮里出现 `vite-error-overlay`、`Failed to fetch dynamically imported module`、`ChunkLoadError`、`Importing a module script failed`、模块脚本 MIME 错误或等价的前端编译/懒加载阻塞错误，就必须把这轮 E2E / 截图链判为失败；即使图片文件已经落盘，也只能算“拿到了排查产物”，不能算“页面通过”或“可收口证据”。默认动作应是先修通同一条真实页面链路，再重新产出截图。
