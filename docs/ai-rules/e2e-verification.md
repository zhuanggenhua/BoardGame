# E2E 与截图验收规范

> 本文从根 `AGENTS.md` 迁出 E2E 和截图验收细则。根文件只保留入口，详细规则以本文为准。

## 适用边界

- 默认 E2E：使用专用测试模式和状态注入，验证 UI 交互、可见结果和用户操作链路。
- 真实开房链路：仅当本轮要证明房间创建、联机同步、`setupData -> runtime`、权限/座位/多端同步等跨入口合同时使用。
- 如果状态注入已经覆盖用户症状，不能把真实开房当成默认升级；如果真实房间链路能证明更多，必须在测试名、evidence 和汇报中写明它额外证明了什么。

## 三板斧与入口分层

1. **三板斧默认口径（强制）**：本项目的 E2E 默认按三板斧执行：① 使用现有 Playwright fixture / 专用测试模式；② 从离目标语义最近的真实入口起跑；③ 用状态注入或代表态把场景直接推进到问题位点。缺任一斧，都不能算“已经按默认 E2E 方式验证”。
2. **默认不从主页起跑（强制）**：如果本轮目标是验证游戏内流程、牌桌交互、阶段流转、HUD、动画、结算或刷新恢复，默认直接从 game route / match route / 代表态起跑；不得机械先走主页、大厅、进房这段前置漏斗。
3. **“开局”默认指当前合同的最近起点（强制）**：在游戏流程语境里，说“从开局验证”默认不是指“从主页点到进房再打一整局”，而是指“从当前要证明的游戏合同最近的起点开始”。例如验证抓牌、弃牌、近终局、刷新恢复时，最近起点通常是 `match route`、首轮代表态或近终局代表态，而不是首页。
4. **主页/大厅进房 与 游戏内流程分层（强制）**：`从主页进入` 和 `进入 match 后的游戏流程` 是两个不同合同。前者证明入口漏斗、房间创建、加入、路由或权限；后者证明具体游戏可玩性。除非本轮目标是整条漏斗都要收口，否则不得绑成同一条大 E2E。
5. **刷新恢复 / 终局复盘 / spectator 也属于独立合同（强制）**：这些链路默认单独建用例，从其最近的可注入代表态起跑；不要附着在主流程后半段顺手验证。

## 组合式验证与长链预算

1. **组合式验证优先（强制）**：完整流程优先拆成“入口合同 + 代表态合同 + 高风险分支合同 + 黄金链”组合证明，而不是把所有风险塞进一条超长 E2E。证明完整流程成立，靠组合覆盖矩阵，不靠重复从头跑到底。
2. **长链默认只保留少量黄金链（强制）**：需要自然完整对局、多人长轮转、真实 AI 串行托管时，只保留少量黄金链证明“整局能跑通”；其它回归优先收成注入态、单轮 roundtrip、近终局、刷新恢复、分支选择等窄合同。
3. **单条用例时长必须受预算约束（强制）**：默认目标是单条 E2E 尽量控制在 `3` 分钟内；超过 `5` 分钟的单条用例必须有明确理由，并优先评估能否拆成组合式验证。若某条链已经长到“比正常一局还久”或容易因时间累积放大环境噪声，默认视为设计异味。
4. **单文件总时长也要受预算约束（强制）**：默认优先把单个 E2E 文件控制在可快速回归的量级；当单文件逐步逼近或明显超过 `10` 分钟时，必须优先评估拆文件、拆主题、拆黄金链，而不是继续往同一文件里堆。
5. **长链例外必须写明价值（强制）**：如果保留一条超过预算的完整自然链，测试名、evidence 与汇报里必须显式写清它独有证明点，例如“只这条能证明多人自然终局”“只这条能证明高人数 repeated-refresh”。没有独有证明点的长链应拆掉。
6. **同一目标不得把长链重跑当默认调试循环（强制）**：同一个问题若第一次长链失败后仍未锁定根因，最多只允许在有明确新假设或新改动的前提下再重跑一次；若第二次仍未锁定，就必须退回代表态注入、局部合同或更低层测试，禁止继续无差别重复自然开局。
7. **单次问题定位必须有总时长预算（强制）**：默认把“为定位同一个问题反复跑长链验证”的总预算控制在 `15` 分钟内。超过该预算仍未拿到直接证据时，必须暂停继续堆长链，改做合同拆分、状态注入、日志/快照补证或更低层验证。
8. **实现推进与收口验证必须分阶段（强制）**：E2E 的职责是证明真实入口和可见结果，不是主调试器。默认节奏应是：先用状态注入或低层验证锁定实现缺口，再改代码，再用最窄 E2E 收口；禁止长时间停留在“反复跑 E2E 看哪里又不对”的循环里。
9. **45 分钟级单问题测试循环默认视为失守（强制）**：如果围绕同一个问题的测试与重跑已经明显拉到 `45` 分钟量级，却仍主要停留在到达目标位点之前、或还在反复确认同一条长链能不能走通，默认应判定为“三板斧失守”；必须立即拆成状态注入、组合式合同或更低层验证，不能继续把长链时间堆高。

## 定位顺序与停线动作

1. **游戏内问题默认先打到问题位点（强制）**：当目标是牌桌进行时、单回合交互、HUD、终局、复盘、刷新恢复或单个动画问题，默认先直达 `game route / match route / 代表态`，而不是先从主页起跑再自然打到那里。
2. **真实开局只证明它独有的合同（强制）**：如果当前要验证的是“从主页进入”“创建房间”“加入房间”“claim seat”“setupData -> runtime”这类漏斗合同，可以跑真实开局；否则它不能作为默认起点，更不能因为“更真实”就吞掉后续游戏内合同。
3. **停线条件必须明确（强制）**：一旦出现以下任一情况，必须立刻停止继续拉长链路，并改走拆分验证：
   - 同一目标已经重复跑了两次自然链；
   - 单条链路明显比正常一局还久；
   - 当前失败点仍停留在“没到问题位点前就先挂了”；
   - 这条链路证明的主要是前置漏斗，而不是本轮真正要改的游戏逻辑或 UI。
4. **重新起跑前必须先说清这次多证明了什么（强制）**：准备再跑一条长链前，必须能明确回答“这次与上一条相比，新增证明点是什么”。如果回答不出来，默认不该再跑。

## 桥接式组合验证（强制）

当一条完整玩法既要证明入口，又要证明 `match` 内多个中后段语义时，默认拆成下面三段，而不是硬跑一条自然终局长链：

1. **入口黄金链**：只证明真实入口、建房/入房、首个可行动回合、座位/权限/同步语义成立。
2. **中段代表态链**：直接注入到本轮真正关心的 `match` 内位点，例如 `draw/discard`、waiting、stacked/live、spectator、reload。
3. **终局前代表态链**：直接注入到 near-end、最后一弃、review 前一跳等位点，证明终局切换与复盘语义。

- 三段组合起来，才是“完整流程已被分层证明”；禁止把“没有单条从主页自然打到终局”偷换成“没有证明完整流程”。
- 入口黄金链只需要跑到它负责的合同 seam，不需要天然承担 review、spectator、终局前最后一弃等所有后段证明。
- 如果一条测试已经同时想证明入口、第二轮身份、AI 中段决策、near-end、review、reload，它默认已经超出单链应承担的合同数量，必须拆。

## E2E 测试强制要求

1. **UI 交互必须用 E2E**：必须使用三板斧（fixture / 专用测试模式 + 最近入口 + 状态注入/代表态）；UI 交互、多玩家协作、动画特效都不能用单元测试代替。
2. **必须实际运行并通过**：AI 编写后立即运行 E2E；单文件/单用例优先用 `npm run test:e2e:ci:file -- <测试文件名> "<用例名>"`，整文件复跑用 `npm run test:e2e:ci -- <测试文件名>`，禁止交给用户。
3. **必须实际打开截图验收**：优先看 `test-results/evidence-screenshots/_shared/`，失败用例再补看 `test-results/playwright-artifacts/`；验收标准不是“页面出现了”，而是“本轮问题位点已按要求修好”。
4. **看图验收必须调用真实图片工具，不得只报路径（强制）**：凡是靠截图收口 UI 结果，必须真的把关键图打开后再下结论。若当前会话提供 `view_image`，先用 `view_image` 核图；核图通过后，再立即执行 `npm run verify:open-image -- <截图绝对路径>` 打开同一张关键图，作为默认 closeout 动作。
5. **只要最终回复里提到“已跑 E2E / E2E 通过”就必须附截图绝对路径**：至少提供 1 张本轮实际核对过的关键截图完整绝对路径；没有路径不得以 E2E 结果作为收口口径。
6. **用户明确要求“端到端截图 / 实机截图 / 页面截图”时，禁止用替代图冒充交付（强制）**：不得用本地静态 HTML harness、局部渲染拼图、组件孤立页、Storybook 式沙盒、手工 clone DOM、设计稿复刻图或任何脱离真实页面链路的截图替代真实截图。若真实链路截图被环境、构建或服务 blocker 卡住，只能停下并汇报 blocker 与最小补救动作；禁止先交一张“辅助理解图”再把它说成端到端证据。
7. **新 UI / 改 UI 默认必须先补真实页面截图再收口（强制）**：凡本轮新增或修改了页面、弹窗、菜单、浮层、toast、徽标、列表、表单、布局或其它用户可见 UI，即使用户没有单独追问截图，也必须至少补 1 张真实页面链路截图；若改动包含多个关键态（例如入口态、展开态、成功态），则必须按关键态分别截图。没有真实页面截图时，只能汇报“代码已改/测试已过”，不得表述成“UI 已确认”或“可以收口”。
8. **局部 UI 改动不得被“只改了一小块”豁免（强制）**：像登录态切换、名字入口、头像、积分徽标、通知红点、下拉菜单、账户面板、按钮文案、tab、角标、空态、单个弹窗壳层这类看似局部的可见改动，只要用户肉眼能直接看到变化，就仍然属于截图验收范围。不得因为“没改路由/没改主布局/只是复用现有组件/已有单测”就跳过真实页面截图。
9. **用户可见状态切换至少覆盖前后两态（强制）**：当本轮修复的是“点击前后不一致”“已登录/未登录态不同步”“展开前后内容不一致”“弹错弹窗/菜单”等状态切换问题时，截图至少要覆盖 `触发前` 和 `触发后` 两张；若只给其中一态，视为未证明问题已闭环。
10. **“流程跑通”默认按关键决策对截图（强制）**：当汇报口径包含“流程已跑通”“从开始到结束可完成”“端到端链路已收口”时，证据不得只给终点图或零散成功图。至少要按真实主流程列出每个核心决策位的 `触发前 -> 触发后` 截图对，例如创建前/创建后、摸牌前/摸牌后、确认前/确认后、结算前/结算后。若某一步没有截图对，只能说该局部链路已验证，不能上升为“整条流程已跑通”。
11. **关键决策前图必须自带下一步可操作性（强制）**：凡是拿来证明“流程仍可继续”的 `触发前` 截图，画面里必须让人一眼看出下一步主操作落在哪里。允许形式包括：真实主按钮、真实候选对象、本体可点击卡牌/牌堆/格子、明确的 owner prompt 或等待归属提示；但不允许出现“合法状态存在、却像页面卡死/没东西可点/不知道点哪里”的前图。若当前规则只剩单一合法动作，UI 必须把这一步做成显式可发现的下一步入口或短提示；否则该图直接判为不合格证据。

## 用例拆分与命名

1. **入口合同和游戏合同分文件优先（强制）**：主页/大厅/进房类测试，优先放在入口或房间主题文件；牌桌进行时、终局、刷新恢复、spectator、AI roundtrip 等优先放在游戏主题文件。不要把“从主页开始”和“完整对局”机械混在同一文件里。
2. **同一用例只证明一个主合同（强制）**：每条 E2E 必须能用一句话说清自己主要证明什么，例如“可从大厅进入房间”“可在近终局代表态完成最后一弃”“spectator refresh 后仍不泄露”。若一条用例同时承担多个主合同，优先拆分。
3. **标题必须反映覆盖边界（强制）**：如果只证明中间态、入口态、近终局态、单轮 roundtrip、代表分支、刷新恢复，就必须把这些边界写进标题；禁止用“完整可玩”“可结算”“已完成”这类完成态措辞夸大覆盖。
4. **重复前置一律抽掉（强制）**：当多条测试反复从同一前置漏斗起跑，只为验证后面不同合同，应优先把共同前置收成 helper、fixture 或代表态注入，而不是在每条用例里重复走一遍。

## 特写与延迟结算

1. **涉及“骰子特写/奖励骰/重掷/改骰盘”的交互必须提供成功路径证据链**：最少 2 张连续截图：**触发/特写出现** -> **执行关键操作后 UI/结果发生变化**（例如重掷后骰面变化、改投后数值/徽章变化）。
2. 若交互包含“关闭/确认/收口”，则必须再补 1 张**收口后**截图证明流程已回到可继续推进的状态（例如特写关闭、pending 状态清空、阶段可继续推进）。
3. **禁止**只提供“失败提示 / 门禁 toast / 不可用提示”的截图就宣告完成；失败截图只能作为否定路径补充证据。
4. **攻击修正徽章（Active Modifier Badge）属于“效果提示”，不是“结果证明”**：徽章出现只代表“攻击修正已打出/已激活”，不代表加伤数值已经提前计入。
5. 若攻击修正包含“延迟结算/分段生效”（例如依赖奖励骰特写收口后再追加加伤），E2E 必须同时证明：徽章可在打牌后出现；伤害/加伤数值只在实际生效时写入权威状态（例如 `bonusDamage/attackModifierBonusDamage` 不会在特写阶段提前变化）。

## 看图验收

1. **看图必须直击问题位点**：不能只扫整页，必须逐项核对用户这轮指出的具体区域、具体现象和具体目标；如果是展开类/浮层类问题，主截图必须同时包含触发控件、展开内容完整边界、关键参照物。主截图收不全或看不清边界细节时，默认“未证明修复”，必须补局部放大图。
2. **缩放/偏移类问题必须显式判断“有没有缩在左上角/是否被误修成窄布局”**：用户反馈的是“整体偏了、缩在左上角、横屏不该变窄、像桌面端”这类问题时，看图结论必须单独写清：主内容是否仍只占左上角一块；HUD 与主内容是否仍在同一视觉坐标系；是否被错误改成窄布局/双列路线。不能只写“页面出现了/元素都在”。
3. **证据截图必须看得到“对应物”本体**：凡是宣称“某对象/某特写/某控件/某奖励骰/某弹窗/某表情已经出现、位置正确或视觉达标”的截图，肉眼必须能直接看到该对象本体、完整主体轮廓或足以识别的关键内容；如果截图里只有外围布局、遮罩、容器边界、背景、文案或其它无关元素，看不到被宣称对象本体，则该截图一律视为无效证据，不得用于收口。
4. **对象被裁切时不得判定视觉通过**：凡截图用于证明浮层、表情、popover、HUD overlay、特写或控件的视觉结果时，如果目标对象被视口边界、截图边界、容器裁剪、遮挡层或固定定位截断到只露边角/只露局部，最多只能证明“事件触发 / DOM 存在 / 局部进入视口”，不得证明“视觉达标 / 用户看得清 / 可收口”。
5. **高亮/可落点/选中反馈类问题必须按顺序排查**：当用户反馈“高亮没了、可选格看不见、选中反馈不明显、落点不亮”时，必须先确认实现里是否真的存在对应高亮/反馈逻辑；再确认触发链是否真的产出高亮状态/候选数据；只有在确认已触发后，才能用 E2E 和截图证明实际效果。
6. **用户要求“恢复原来的效果”时先锁 git 基线**：必须先通过 `git log` / `git show` / `git blame` 给出 `last known good` 与 `first known bad` 候选，再决定是恢复历史行为还是在历史行为上做增量修复；必须实际打开并阅读对应旧实现、旧截图或旧 evidence，明确旧版本当时怎么实现、怎么显示、怎么验收。
7. **流程关键截图必须可继续操作**：凡是用于证明“流程可继续/可完成”的截图（如创建房间、确认弹窗、支付/提交、加入房间、密码输入），画面里必须同时可见下一步主操作控件（如“确认/创建/提交”按钮）且控件不被裁切、不在可视区外。若截图里看不到下一步主按钮或无法判断点哪里继续，该截图一律判定为无效证据，不得收口。
8. **合法等待态必须显式说明“谁在等谁”（强制）**：如果当前截图不是你操作，而是等待别人、等待 AI、等待服务器推进，则画面里必须直接可见等待归属或当前控制权信息，例如“等待玩家 X”“AI 正在行动”“对手处理中”。禁止让“合法等待态”和“页面没反应/流程挂起”在截图上长得一样。
9. **临时浏览器排查必须保持 snapshot 纪律**：使用 Playwright CLI、Browser snapshot 或等价浏览器自动化做临时排查时，必须先获取当前 snapshot 再按元素引用操作；导航、弹窗开关、菜单展开/关闭、阶段推进、DOM 大幅变化后必须重新获取 snapshot。旧元素引用只能作为历史线索，不得继续当作当前页面真相。

## 截图来源与证据文档

1. **截图必须来自当前问题场景**：游戏内问题优先保留从能覆盖本轮风险的入口进入后的截图；禁止用大厅页、独立预览页、资源诊断页、兄弟入口截图或自造代理场景，代替问题本身已修复的证据。
2. **截图必须做合理性审查**：看截图时不仅要确认“元素存在”，还必须判断该截图是否能代表真实用户看到的画面。
3. 允许直接对当前页面/当前弹窗截图（`page.screenshot` / 对真实 locator `screenshot`）。
4. **真实页面主截图优先，辅助图不得替代主证据（强制）**：局部放大图、裁切图、locator 单元素截图、手工标注图只能在已经拥有真实页面整页/整屏/整容器主截图后作为补充材料使用，不能反客为主替代主证据。只要用户本轮点名要“截图”且语境指向真实页面，默认主证据必须来自真实页面链路。
5. **本地默认路由受环境开关限制时，必须写明截图入口为什么仍能代表目标 UI**：如果某个 UI 只在 Android 壳、灰度开关、预览路由、特定 runtime 或特定 query 下启用，截图可以走该项目约定的真实组件入口，但 evidence 和最终汇报里必须显式写清：默认入口为什么在本地不可达、当前截图入口与目标 UI 的对应关系是什么。禁止静默换入口后把替代路由说成默认首页已验收。
6. 为了稳定出图而“克隆 DOM 再固定定位截图”（cloneNode + 手动 `position: fixed` + 强行置顶）不能作为唯一收口证据；如必须使用，证据文档必须明确标注“该截图为快照克隆”，并至少补 1 张真实页面原位截图或给出等价的可复查指标（真实元素 `getBoundingClientRect` + 可视区高度对比）。
7. 禁止通过隐藏关键遮罩、强行改 z-index、强行改 transform 来“把问题遮起来”的截图，或与真实布局关系不一致的“摆拍图”。
8. **资源缺失不等于跳过验收**：外部 R2/CDN 资源未稳定渲染时，必须明确写出“资源未渲染”，并继续检查布局、相对大小、层级、遮挡、溢出、对齐，不能把白卡面直接当成布局失败，也不能借此跳过看图。
9. **必须先看图再写证据结论**：必须创建 `evidence/<功能名>-e2e-test.md`；每张关键截图至少写 1-3 条肉眼观察结论，直接回应本轮需求点和用户指出的问题，禁止只写“正常 / UI 正确 / 看起来没问题”。
10. **证据文档必须显式写“我实际看到什么”和“是否达到验收标准”**：每张关键截图都必须单独写明肉眼看到的具体现象，以及该截图对应的问题位点是否已经达到本轮验收标准；禁止只复述断言、组件名、阶段名或“理论上应该如此”。
11. **看图通过后必须立即打开关键图（强制）**：确认某张图能作为本轮主收口证据后，不得只把路径写进回复就结束；默认还要执行 `npm run verify:open-image -- <截图绝对路径>` 打开这张图。若当前会话支持 `view_image`，则顺序固定为：`view_image` 核图 → 仓库脚本打开同图 → 最终回复附路径与看图结论。
12. **开图失败或无法证明已打开时，必须降级回完整绝对路径（强制）**：如果 `verify:open-image` 没有返回明确成功，或用户反馈“并未打开”，则不得继续使用“已打开图片”的口径。最终回复必须直接附这张截图的完整绝对路径，并明确说明“请按此路径打开/定位”；禁止只贴脚本日志键值、相对路径或省略路径。
12. **看到不达标就必须写“不达标”**：如果截图里出现手牌缺失、控件偏移、被遮挡、只剩边角、主元素跑到一侧、状态不完整等现象，即使 E2E 断言通过，也必须在证据文档里明确写“未达到验收标准 / 不能据此收口”，并继续修图、修实现或修测试。
13. **禁止把“没缩在左上角”偷换成“整体已正常”**：对于移动端 UI 重构/布局修复，截图结论必须区分“已摆脱极端故障”和“布局已完全达标”。若截图只能证明“不再缩在角上/不再整屏错位”，就只能这样写，不能顺势宣称“整体完全正常”。
14. **出现新异常或链路不真都不得收口**：即使断言通过，只要截图里还有新的视觉异常、遮挡、空白块、层级错误、异常位移，或 E2E 没覆盖本轮风险，就不能宣称完成；先加日志定位，再审查调用链，最后修实现或修测试。
15. **trace / console / network 只能作为辅助定位证据**：当截图异常但断言通过、流程卡住、点击无效、资源或接口疑似异常时，可以补抓 trace、console、network 记录辅助定位；但这些记录不能替代关键截图、肉眼验收结论和本轮问题位点的可见证据。
