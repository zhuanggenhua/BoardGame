# 数据录入规范

> **适用范围**：所有基于图片、规则书、Wiki、官方 PDF、截图或用户提供素材的业务数据录入任务。
>
> **边界**：本文件只定义全游戏通用的录入流程、来源优先级、核对契约和零猜测原则；任何游戏专属字段、卡牌结构、抓取站点、脚本、索引口径，都必须写到对应游戏自己的 `rule/` 文档或专项规范中。

## 项目内调用方式

- 项目内默认优先通过 `.codex/skill/data-entry-workflow/SKILL.md` 进入录入流程。
- 这个 skill 只负责通用门禁和 workflow 路由，不替代本文件。
- 目前已接入的专用 workflow：
  - `docs/games/dicethrone/workflows/dicethrone-hero-intake.md`
  - `docs/games/smashup/workflows/smashup-faction-intake.md`

## 一、通用原则

- 先建契约，后写代码：录入前必须先产出 Markdown 核对契约，再落运行时代码。
- 先锁正式原图/正式图集，再按需裁图录入：原始整图、正式单图、正式图集才是主真相源；录入工作面可以基于这些正式来源切出单对象裁图，以便看清文字、建立核对合同和复查定位。
- **整卡先于局部裁图（强制）**：凡是卡牌、技能牌、升级牌、提示牌这类物理卡面对象，必须先裁出**完整单卡**作为主核对图，再视需要补局部放大图；禁止直接拿半张卡、上半区、下半区或只含局部文字的裁图充当正式录入依据。
- **缩略图不得定稿字段（强制）**：低分辨率 contact sheet、整页缩略图、降采样合图、模糊预览图只能用于定位对象、槽位和需要重切的区域；费用、阶段、类型、生命、战力、数量、限定词、触发时机、目标范围和效果数值必须基于完整单卡主裁图或同一正式来源的高清局部裁图逐项锁定，不得从缩略图猜读后直接落代码或标 `locked`。
- **录入可看切图，但冲突裁定必须回正式原图/正式图集（强制）**：只要裁图是从当前对象的正式原图、正式压缩图或正式图集直接切出，录入时可以直接使用这些单对象裁图提高可读性；但一旦玩家反馈、旧录入、测试结果与裁图读法发生冲突，最终裁定必须回到正式原图/图集，必要时基于同一正式来源重切高清裁片，不能让低清旧裁片单独压过正式真相源。
- 单一权威来源：每个字段都必须能追溯到当前任务约定的主真相源。
- **图片优先于 Wiki（强制）**：只要本地正式图片、用户提供图片、截图或扫描件清晰覆盖当前字段，该图片就是当前字段的主真相源；Wiki、社区资料、脚本抓取结果只能作为对照源，不能覆盖图片。
- **卡图疑义先回原图（强制）**：当用户反馈“卡图不对”“贴图和效果不一致”“怀疑录入错误”“怀疑索引用错”时，必须先直接打开当前对象的主真相源图片（完整单卡、玩家板、提示板或原始图集），逐项对照图上文字、图上槽位、图上顺序与运行时对象。代码、旧录入文档、测试结果、旧截图只能辅助排查，不能替代原图裁定“是否录错”。如果这轮还没看图，只能给出“代码/测试层暂未发现分叉”的辅助结论，不能下“不是录入错误”的最终结论。
- **技能/规则反馈先分实现错误还是录入疑义（强制）**：当用户反馈某张卡、技能、升级、状态或骰面效果“不对 / 少选项 / 多选项 / 数值不对 / 时机不对 / 消耗不对 / 是否可重掷不对”时，必须先对照当前已录入数据（代码静态数据、i18n 文案、规则文档、现有合同）判断反馈描述是否已经和录入口径一致。若一致且问题发生在 UI、命令校验、结算、交互入口或状态消费链上，就按实现 bug 直接定位和修复，不得用“需要重新看图”拖住已明确的实现错误。
- **反馈与录入不符或看起来无 bug 时才回主真相源（强制）**：只有当反馈描述与当前已录入数据不一致、当前实现看起来已经符合录入但用户仍说不对、现有录入口径内部冲突、或需要裁定“录入到底对不对”时，才必须重新打开主真相源图片/规则书页/用户指定来源逐项核对。此时代码、旧录入文档、测试结果、旧截图只能辅助排查，不能替代主真相源裁定。
- **图片处理方只消费需求，不接管任务（强制）**：当图片读取、OCR、截图核对或子代理被用于读取图片时，传给它的是当前业务需求下的图片判定问题，而不是重新包装一份代理任务。录入类需求应返回可落表字段（原文、字段值、子句、索引、状态）；验收/对比类需求只返回是否满足当前预期、失败点和最小证据；不得要求图片处理方产出泛泛的读图缺口报告，除非当前需求本身就是缺口清单。
- **未锁定分类的修复只能叫候选补丁（强制）**：如果还没有明确区分“实现错误”与“录入疑义”，就不得把基于经验、文案或代码推断的改动称为最终修复；只能标为候选补丁，并继续补证据。若已证明是实现错误，允许直接修复并按原始 bug 位点验证；若落入录入疑义，必须先回主真相源，缺图或规则页时停在“前提未锁定”。
- **录入切图只能落 `temp/`（强制）**：凡是为了录入、核对、OCR、看清局部版式、比对 atlas 单格、人工复查而生成的裁图，不论是否做过锐化、放大、拼接、归一化，只要它不是正式运行时素材，就必须也只能写到 `temp/**` 或等价临时目录。禁止把这类录入切图写进 `public/assets/**`、`public/assets/**/crops/**` 或任何会进入正式资源树、manifest、服务器资源主源发布链的位置。
- **可视/图面合同归数据录入（强制）**：只要图片、玩家板、棋盘、卡图、图集、布局图本身足以直接判定“对象在哪个槽位/区域、顺序如何、哪格故意留空、哪格是 display-only、哪格可交互”，这些结论就必须在录入阶段写成正式合同，落到真相源表/录入核对表里。**这不是审计阶段临时补发现的工作**；没有这张合同表，录入就不能算完成。
- **禁止借共享旧语义猜图面合同（强制）**：当新对象复用旧系统、旧组件、旧 `slotId`、旧 atlas 语义或旧布局 helper 时，只要当前图片本身能直接看出槽位/区域/顺序，就必须以当前图片逐槽重建合同；**不得**因为“旧英雄同名槽位大多如此”“共享槽位名看起来像”“历史实现一直这么放”就直接沿用旧映射。凡 `slot -> object`、`frame -> object`、`region -> object` 来自这种外推，都视为猜测，不得进入正式录入结论。
- **用户故事显式覆盖（强制）**：只有当用户故事、需求单或本轮用户明确说明“为了体验/教学/本项目改动而不同于图片”时，才允许偏离图片真相源；偏离项必须在需求留档和对应游戏 `rule/` 或 evidence 文档中写明覆盖原因、影响范围和验收口径。
- **默认真相源**：如无明确指定，本项目以“**已录入的现有数据**”（代码中的静态数据 + i18n 文案 + 规则文档）作为默认真相源。
- 真相源与对照源分离：真相源负责正式录入，对照源只负责辅助核对与发现冲突。
- **录入合同状态必须显式标记（强制）**：每个对象完成录入核对后，必须标成 `locked / blocked / disputed` 三种状态之一。
  - `locked`：主真相源、裁图、字段、子句、索引、对照差异都已登记，可作为后续实现审计依据。
  - `blocked`：主真相源不可读、缺图、缺页、缺索引或无法定位，只能登记缺口，不能凭实现文案补规则。
  - `disputed`：主真相源与现有数据、规则书、Wiki、旧实现或用户故事冲突，必须先裁定冲突。
- **锁定后不得无故回到录入层（强制）**：对象已经在本轮合同里标为 `locked` 后，后续“继续”默认进入实现对照、测试补证或缺口登记；只有合同缺字段、证据冲突或用户明确要求复核时，才允许重新读图、重新 OCR 或重新录入。
- **录入质量门禁前置（强制）**：`locked` 不是“看过图”的口头结论，而是合同字段全部可复查后的状态。标 `locked` 前必须确认主真相源、完整单对象图/可读裁图、对象归属、规则原文、原子子句、索引入口、对照差异和未决项都已落表；标 `locked` 后继续任务时，不得再用“录入要做好”作为普通理由重跑图片/OCR，只能先消费合同做实现对照。若消费合同途中发现字段缺失或互相冲突，先把对象降级为 `blocked/disputed` 并回写 evidence，再补录入合同。
- **已锁合同的质量复查只查字段，不重读来源（强制）**：当批次已经有 `locked` 合同和实现对照矩阵时，续跑的第一步是核对合同字段是否齐全，而不是重新读取图片、OCR、裁图或重新抄录。字段齐全就继续实现审计；字段缺失才回写 `blocked`，来源/归属冲突才回写 `disputed`。禁止把“数据录入要做好”泛化成对已锁对象的普通重录入口。
- **locked 最小字段清单（强制）**：进入实现审计、机制修复或测试补证前，合同至少要能逐项回答：对象/实体标识是什么；主真相源定位在哪里；完整单对象图或可读裁图是什么；对象归属是什么；规则原文是什么；原子子句是什么；索引/atlas/槽位入口是什么；对照源差异是什么；未决项是否为空或已登记；合同状态为什么是 `locked / blocked / disputed`。缺任一项不得标 `locked`，后续续跑也不得用实现字段、旧测试或 OCR 临时补规则结论。
- **外部来源静态快照必须可回访（强制）**：凡是把 Wiki、官网页面、PDF、规则页、数据库页面或第三方站点内容抄录成项目内静态数据、测试 fixture、对照表、JSON、TS 常量时，必须同时记录：`来源链接`、`获取日期`、`对应对象/页面定位`、`采集方式（人工抄录 / 脚本抓取 / OCR）`。缺任何一项，都不得把该静态快照称为“权威来源”“官方快照”或“Wiki 基线”；只能标为“历史对照数据 / 待回填来源”。
- **外部图片素材来源必须留档（强制）**：凡是用户提供的本地素材目录、下载素材、TTS/Mod 图片、临时搬运图或非项目内原生资源，被用于录入、裁图、OCR、manifest、运行时资源或审计结论时，必须记录：原始绝对路径或来源链接、原始文件名、文件大小、尺寸、hash、发现/获取时间、覆盖对象、采集方式、运行时落点、压缩产物和远端回查结果。缺这些字段时，只能标为 `source-found / source-pending-ingest / partial`，不得标为 `locked`，也不得说“数据已录入 / 已审计完成”。
- **无可访问来源的数据不得覆盖图片真相源（强制）**：只要某条静态快照、旧表格、测试 fixture 没有可访问来源链接或本地证据路径，即使它在仓库里存在、甚至已被测试消费，也不能覆盖清晰卡图、官方 PDF、规则书或用户指定主真相源。
- 零猜测：任何文字、数字、关键词、限定词、索引，只要不确定就必须停下。
- **复合单卡先判语义，不得先拆对象（强制）**：当同一张卡面里出现多个标题、上下子区、分支名、副标题、相关技能名或多个效果块时，必须先判断它们是“同一张卡内的多个分支/variants/子效果”，还是“多个独立运行时对象”；在结论明确前，禁止先新增多个 `id`、多个 `previewRef.index`、多个 atlas frame，或把一张卡硬拆成两张。
- **同类实现先对照，后裁定结构（强制）**：一卡多能力、升级附带子分支、同槽多变体这类复合语义，必须先对照同系统里已成熟对象的实现合同（如同类英雄的 `variants`、共享 handler、升级替换链）；没有完成这步对照前，不得自创结构、更不得靠猜测把卡面拆散。
- 原文与结构化结果并存：禁止只保留最终代码值，不保留原始文本。
- **玩家可见长文必须用原文（强制）**：剧本书、规则书正文、事件书、任务卡、作祟开局、分阵营秘密阅读、结局朗读等“玩家以阅读原文为目的”的长文展示，默认必须来自已锁定主真相源里的逐字原文，或已锁定的正式翻译原文。摘要、规则书口吻整理、AI 改写、教学解释和目标摘要只能用于辅助 UI、目标卡、教程提示或按钮短文案，不能替代剧本书正文、开局朗读或结局朗读。
- **原文未锁不得冒充完成（强制）**：如果官方原文、用户授权原文、OCR 结果或正式翻译尚未锁定，相关录入合同必须标为 `blocked / disputed`，不得标 `locked`；实现层不得写入“看起来像官方文本”的正式剧本文案。因版权、素材缺失或用户授权限制只能使用摘要时，玩家 UI 和文档必须明确标注“非原文摘要 / 临时整理”，不得称为“剧本原文”“完整剧本”或“官方剧本书”。
- **原文展示与摘要用途必须分列（强制）**：录入合同里必须区分“进入原文阅读器 / 开局朗读 / 结局朗读”的逐字原文，以及“进入目标摘要 / 状态提示 / 教程提示 / 按钮”的摘要文本；禁止用同一段整理稿同时充当原文正文和目标提示。
- **剧本流程合同必须分节点（强制）**：只要素材含有剧本书、事件书、任务卡、阵营手册或结局段落，录入合同必须把“公开揭示 / 分阵营秘密阅读 / 开局叙事 / 目标承接 / 结局朗读”分别登记为独立节点，逐项写清触发时机、可见玩家、保密范围、承接目标或状态、原文来源定位和未决项。只记录“有剧本正文”或“有书本 UI”不能标 `locked`。
- 先文档后实现：影响规则、机制、描述、展示或资源映射的录入，必须先更新文档，再改代码。
- 根规范只管方法论：某个游戏的专用抓取脚本、字段命名、卡牌结构，不得写成全局默认。

## 二、录入对象范围

录入任务默认要覆盖素材承载的全部对象，至少检查：

- 能力类：技能、被动、防御技、升级差异、时机标签、伤害类型。
- 状态类：token、堆叠上限、施加/移除条件、持续时间、例外条件。
- 提示类：说明板、帮助板、关键词提示、骰面说明、流程提示。
- 资源类：atlas 图、atlas json、frame 命名、独立 icon、资源引用路径、复用关系。
- 索引类：原图路径、裁图路径、顺序依据、运行时索引字段、图块编号、显示映射。

强制要求：

- 每个条目都必须同时记录触发条件/时机、原始文本、结构化结论。
- 不得只写“效果摘要”而省略触发条件。
- 不得只录技能而漏掉提示板、图集索引或资源复用说明。

## 三、权威来源优先级

**默认真相源口径（本项目基线）**：

- 若当前字段能从清晰图片、截图或扫描件直接读出，则图片优先于一切 Wiki / 社区资料 / 既有实现。
- 对于没有图片覆盖的字段，**已录入的现有数据**（代码中的静态数据 + i18n 文案 + 规则文档）为默认真相源。
- 若用户明确指定新的真相源（如规则书/PDF/图片/Wiki），才允许切换真相源并以其为准。
- 未获得明确指定前，外部资料一律视为**对照源**。

外部资料优先级（作为对照源或在用户明确指定为真相源时的优先级）如下：

1. 用户提供或项目本地正式图片、截图、扫描件（清晰覆盖当前字段时）
2. 官方勘误、官方规则书、官方 PDF
3. 官方数据库、官方页面、官方 API
4. 项目约定的专用抓取源或游戏专属爬虫
5. 项目内既有规则文档
6. Wiki、社区资料、论坛整理

补充规则：

- 若用户明确要求“以这批汉化图片为准”，这些图片在当前任务里就是主真相源；英文原版、Wiki、社区资料只能作为对照源。
- 若用户故事明确要求偏离图片，用户故事只覆盖被点名的字段和场景；未点名字段仍按图片真相源执行。
- 若某个游戏要求必须走专用爬虫或专用比对脚本，应写在该游戏专属规范中。
- Wiki 不是默认真相源；除非用户明确指定，否则只能作为对照来源。

## 四、强制交付物

一次完整的数据录入任务，至少要有以下文档产物：

1. 真相源表
2. 切图表
3. 核对合同表
4. 对照表
5. 冲突待裁定表

### 1. 真相源表

必须记录：

- 真相源类型
- 真相源路径或链接
- 获取时间
- 覆盖对象
- 录入口径说明
- 若引用的是“项目内静态快照 / fixture / 对照 JSON / TS 常量”，还必须额外记录：
  - 该静态文件路径
  - 原始外部来源链接
  - 采集方式
  - 当前状态：`已回访` / `待回访` / `来源失效`

### 2. 切图表

必须记录：

- 原图路径
- 裁图路径
- 裁图坐标或裁图规则
- 对应对象
- 当前可读性结论

### 3. 核对合同表

至少包含：

| 字段 | 含义 |
| --- | --- |
| 合同状态 | `locked / blocked / disputed`，以及进入下一阶段的理由 |
| 实体标识 | `defId`、`id`、变体 ID |
| 类别 | 技能 / 状态 / 提示 / 图集 / 索引 |
| 真相源定位 | 图片路径、裁图路径、页码、URL |
| 原始名称 | 原图或原文中的名称 |
| 触发条件 / 时机 | 图标组合、阶段、前置条件、次数限制 |
| 原始文本 | 原图或原文中的完整描述 |
| 展示用途 | 原文阅读器 / 开局朗读 / 结局朗读 / 目标摘要 / 按钮短提示 / 教程提示；必须区分逐字原文和摘要文本 |
| 可见范围 / 保密范围 | 公开给所有玩家 / 仅求生者 / 仅叛徒 / 仅指定座位；必须说明不该看到的人 |
| 流程承接 | 公开揭示 / 秘密阅读 / 开局叙事 / 目标承接 / 结局朗读，以及读完后进入哪一步 |
| 结构化字段 | `type`、`cost`、`power`、`tags`、`index`、`faction` 等 |
| 不确定项 | 不可读字段、冲突字段、待确认字段 |
| 结论状态 | `已确认`、`待确认`、`冲突待裁定` |

若当前对象可由图片直接判定槽位/区域/atlas/布局，还必须额外补一张**可视合同表**，至少包含：

| 字段 | 含义 |
| --- | --- |
| `visualRegion / slotId` | 图面区域或槽位标识 |
| 图上对象 | 图上肉眼直接看到的对象/空槽/说明区 |
| 运行时对象 | 代码中应绑定的 `defId/id/frame` |
| 允许状态 | `active/passive/defense/display-only/empty` |
| 是否可交互 | 玩家是否应能点/选/高亮 |
| 备注 | 共享旧语义是否不适用、是否存在故意留空 |

强制补充：

- 只要当前对象历史上存在共享实现或旧对象同构参考，可视合同表必须显式写出“共享旧语义是否适用”；默认值不是“适用”，而是“待当前图片逐槽证实”。
- 若当前图片里存在被动槽、防御槽、展示槽、空槽或故意留白，必须独立成行；禁止只登记可执行对象，把其它槽位留给实现层自行猜。

### 4. 对照表

必须记录：

- 对照源链接或路径
- 对照源语言或版本
- 对照字段
- 对照结果：`一致`、`补充说明`、`疑似冲突`

### 5. 冲突待裁定表

一旦主真相源与对照源冲突，必须单独建表，至少包含：

- 冲突对象
- 真相源结论
- 对照源结论
- 冲突类型：文字 / 数值 / 时机 / 范围 / 索引 / 资源引用
- 当前处理状态：`待用户裁定`

禁止行为：

- 发现与“已录入现有数据”冲突后直接改写代码或文案。
- 在主表中偷偷用对照源覆盖真相源。
- 未经明确指定就擅自切换真相源。
- 把“我觉得更合理”写成裁决结论。

## 五、标准流程

### 1. 锁定主真相源与对照源

必须先记录：

- 真相源类型
- 真相源路径或链接
- 对照源类型
- 对照源路径或链接
- 获取时间
- 字段适用范围

### 2. 先裁图到可读粒度

必须先锁定正式原图/正式图集，再把它们按需切到“单个对象能完整看清”的粒度，之后才开始录入：

- 单张物理卡牌先裁成一张完整单卡
- 单个技能一张裁图
- 单个状态说明一张裁图
- 单个提示板块一张裁图
- 单个 atlas frame 或复用说明单独登记

强制要求：

- 裁图必须覆盖完整标题、触发条件、正文、图标和关键限定词。
- 卡牌类对象的主核对图必须覆盖整张卡；局部放大图只允许作为辅助，不得替代完整单卡主图。
- 若一张卡存在上下两个能力块或副标题，完整单卡主图必须与局部放大图同时保留，禁止只留下其中半张就进入录入。
- 如果整图上多个对象混在一起，必须拆开，不能依赖放大整页查看。
- 如果裁图后字段仍不可读，必须继续细分或更换更清晰来源；只阻塞对应字段，不把读图过程本身写成报告。

补充强制分类：

- `原始真相源`：原始整图、规则书页、官方 PDF 页、未改写的正式运行时图
- `几何裁图`：按固定坐标从真相源切出的单对象图，只服务录入核对
- `后处理核对图`：为了看清文字再做的放大、锐化、上下拆分、拼接、归一化预览
- `正式运行时资源`：代码真实引用、已进 manifest、会被客户端请求的资源

判定规则：

- `几何裁图` 和 `后处理核对图` 默认都是中间产物，必须放 `temp/` 或等价临时目录
- 只要裁图的目的仍是“录入核对”，即使它只是从正式图集做了最普通的单格几何裁切、没有任何后处理，也仍然属于中间产物，不能写入正式资源树、manifest 或服务器资源主源发布链
- 只要某张图是“为了录入时看清文字”额外生成出来的，就不能放进 `public/assets/` 正式资源树
- 禁止因为文件名像 `slot-24.webp` 或 `deadeye-2.webp`，就把中间产物误判成正式资源或主真相源
- 禁止把“半张卡裁图 / 子区放大图”误当成“这张卡的完整正式语义”；局部裁图只能辅助读字，不能单独决定对象拆分结构
- 如果某个游戏历史上把核对图留在了 `public/assets/.../crops/**`，后续排查时必须先把它当作可疑中间产物，而不是默认相信它代表正式 atlas 语义

### 3. 建立 Markdown 核对契约

- 表格必须按素材顺序、逻辑顺序或官方顺序排列。
- 原始文本必须和结构化字段并排出现。
- 同一字段如果存在多个来源，必须显式写出对照结论。
- 若图片可直接判定图面合同，必须在这里同时建立可视合同表；禁止把“等审计时再看图面落点”当成默认流程。

### 4. 全口径核对

至少逐项核对：

- 名称
- 类型
- 数值
- 关键词
- 限定词
- 作用对象
- 作用范围
- 触发条件
- 触发时机
- 次数限制
- 例外条件
- 图片索引、图集索引、资源路径、复用来源

### 5. 结构化映射

必须明确区分：

- 哪些字段进入静态数据层
- 哪些字段进入 i18n
- 哪些字段进入规则文档
- 哪些字段进入资源注册或 atlas/json
- 哪些字段只作为后续实现依据

补充强制项：

- 可视/图面合同必须明确哪些区域进入 `slot mapping / atlas frame / overlay metadata / display-only metadata / empty`。
- 如果图片已经证明“这里是空槽/说明区/被动区/非交互区”，录入阶段就必须写死，禁止把这类空白留给运行时用“最像的共享语义”自动补位。

### 6. 文档同步

录入影响玩法、机制、文案或资源展示时，必须同步更新：

- 对应游戏的 `rule/*.md`
- 对应 i18n 文案
- 必要时的开发规范文档
- 资源索引说明或素材登记

### 7. 资源上传收口

只要本轮录入新增、替换或移动了运行时会访问的资源，就必须在交付前完成：

- manifest 重建
- 发布到服务器资源主源
- 公开资源域名代表性 URL 回查

默认要求：

- AI 主动执行发布，不等待用户单独提醒
- 没有发布到服务器资源主源不算完整交付
- 若因环境、配置、脚本报错或用户明确要求而暂时无法发布，必须在最终汇报中明确说明：
  - 哪些资源未发布
  - 为什么未发布
  - 当前运行态会出现什么影响

### 8. 再进入代码实现

只有在以下条件满足后，才允许开始实现：

- 来源已锁定
- Markdown 核对契约已写
- 不确定项已清零或显式挂起
- 对应规则/说明文档已同步
- 本批次要进入实现的对象均已标为 `locked`；`blocked/disputed` 对象只能作为缺口或待裁定项保留，不能被实现层猜补。

进入实现后，`locked` 合同就是后续审计真相源。实现审计发现问题时，先判断是“实现未遵守合同”还是“合同本身缺失/冲突”：前者直接进入实现修复和测试补证，后者才退回录入层补合同。

续跑规则：如果当前批次已经有 `locked` 合同和实现对照矩阵，下一步必须从矩阵里的 `proof-needed / suspected-gap / match-with-proof` 等实现审计状态继续推进；不得把已 locked 对象重新放回录入队列。录入层只在合同缺字段、来源冲突、对象归属不清或用户明确要求复核时重新打开。

## 六、零猜测原则

以下任一情况都必须停止录入并向用户说明：

- 名称字段不可读
- 数值模糊
- “可 / 必须 / 直到 / 改为 / 额外 / 其他 / 另一个”等限定词不确定
- 图片索引、图集位置、裁片对应关系不确定
- 素材外观与运行时语义的对应关系不确定，例如看到了空白格、黑边、角落装饰、额外立绘或疑似复合排版，但无法证明它在运行时到底代表什么
- 看到了“升级标题 + 下方子区/副标题/相关技能名/说明块”这类复合升级排版，但尚未证明这些子区在运行时到底是同一张卡的组成部分、同类最高级语义，还是独立手牌对象

禁止行为：

- 根据英文原版猜中文
- 根据上下文补完整句子
- 根据相邻条目推断索引
- 在没有直接打开主真相源图片的前提下，只看 `cards.ts`、`abilities.ts`、旧录入文档、测试通过或旧 evidence，就下“不是录入错误 / 不是索引用错”的结论
- 根据半张卡或局部放大图，直接推断整张卡的对象结构
- 根据 atlas / crop 的视觉外观猜“这不是正式卡”“这一格其实是两张”“需要 split/topCrop”“可以直接改 rows/cols”
- 根据一张升级牌里出现多个标题、多个技能名或上下子区，就直接推断“要拆成两张正式手牌图”或“每个子区都要占一个新索引”
- 先录进去，等以后再核对

### 卡图与效果不一致专项门禁

触发词示例：

- “卡图不对”
- “贴图和效果不一致”
- “怀疑录入错误”
- “怀疑索引用错”

触发后强制动作：

1. 先回到当前对象的主真相源图片，优先看完整单卡；若问题涉及玩家板/提示板/整张图集，再补看对应原图。
2. 把图上可直接读取的名称、正文、费用、槽位、顺序，与运行时对象、索引、日志表现逐项对照。
3. 再用代码、测试、旧录入文档、旧 evidence 判断“错在录入、错在索引、还是错在运行时消费链”。

禁止行为：

- 先看代码或测试，再倒推“图大概率没错”
- 没看原图就把问题定性成“纯 AI 逻辑问题”或“纯 UI 显示问题”
- 仅凭旧裁图、后处理核对图、历史截图，替代当前主真相源图片

输出口径：

- 若已完成原图对照，才允许裁定“录入正确 / 录入错误 / 索引用错 / 运行时消费错”。
- 若还没看图，必须明确说“尚未完成录入真相核对”；此时最多只能汇报代码层、测试层或运行时层的暂时发现。

### 复合升级补充规则

- 如果老派系已经证明某类升级是“同一基础技能 + 多个 `variants` / 档位 / 子效果，且同类取最高”，新录入角色默认先沿用这条执行合同，不能重新发明成多张手牌对象。
- 图面上出现多个子区、多个标题或升级后附带的相关技能名时，必须先区分：
  - 这是能力执行层的复合语义
  - 还是图片源里的复合排版
  - 还是正式运行时真的存在多张独立手牌
- 上述三者未区分前，禁止把图片子区直接写成新的 `card.id`、新的 `previewRef.index`、新的 atlas frame。
- 一旦证据已经指向“同一张物理牌里的复合子区”，必须立刻停止继续改运行时实现，先完成：
  - 老派系同类升级逐张对照
  - 真相源 / 核对图 / 正式运行时资源三层拆分登记
  - 复合语义裁定文档
- 在这三步完成前，禁止继续推进：
  - `cards.ts` 新增或保留“两个子区 = 两张独立手牌”的录入
  - atlas / frame / `previewRef.index` 接线
  - 以 E2E 通过为由宣称素材语义已收口
- E2E、截图、真实 UI 行为只能证明“当前实现表现如何”，不能反向证明素材语义正确；只要素材语义仍未裁定，测试结果一律视为现象记录，不得作为录入正确性的最终证据。

## 七、图片与索引补充规范

当素材涉及 atlas / index / crop 时，必须额外记录：

- 原始大图路径
- 原始文件名、文件大小、尺寸、hash、发现/获取时间
- 裁片路径
- 裁片顺序依据（从上到下、从左到右或官方编号）
- 最终运行时索引字段
- 该素材是“真相源裁图”“正式运行时资源”还是“中间产物”
- 若进入正式资源链：运行时落点、压缩产物、manifest key、远端 URL、远端回查状态
- 本轮采用的旧实现 / 旧角色 / 旧资源接线对照依据

如果图片索引尚未确认：

- 可以先录 `defId` 和文案
- 但必须把 `previewRef` 或索引字段标为未完成
- 不得伪造正式索引占位

额外强制规则：

- 不得从后处理核对图直接反推“这一格其实是两张”“这个 slot 不是正式卡位”“运行时必须改成单卡图”
- atlas 语义、slot 语义、运行时 `previewRef` 合同，必须回到原始真相源、旧角色基线和真实 UI 消费链一起裁定
- 如果核对图与原始真相源、旧角色基线冲突，优先怀疑核对图生成链路有问题，而不是先改运行时代码

当 `previewRef`、atlas frame、手牌图集接线方式无法从现有文档唯一推出时：

- 先对照同游戏旧实现、现有运行时代码和专项规范
- 若仍有多种合理解释，必须先问用户，不得自行裁决
- 允许“一张正式图片对应多个运行时对象”，但这类复用关系必须显式登记，不能靠肉眼猜

## 八、游戏专属补充

- 某个游戏若要求特定爬虫、比对脚本、裁图规则、索引结构或字段命名，必须写到该游戏自己的 `rule/` 文档或专项规范中。
- 例如大杀四方若要求使用项目内爬虫核对 Wiki，应在大杀四方规则/专项文档中明确，而不是提升成全局默认。
