# 数据录入规范

> **适用范围**：所有基于图片、规则书、Wiki、官方 PDF、截图或用户提供素材的业务数据录入任务。
>
> **边界**：本文件只定义全游戏通用的录入流程、来源优先级、核对契约和零猜测原则；任何游戏专属字段、卡牌结构、抓取站点、脚本、索引口径，都必须写到对应游戏自己的 `rule/` 文档或专项规范中。

## 项目内调用方式

- 项目内默认优先通过 `.windsurf/skills/data-entry-workflow/SKILL.md` 进入录入流程。
- 这个 skill 只负责通用门禁和 workflow 路由，不替代本文件。
- 目前已接入的专用 workflow：
  - `docs/games/dicethrone/workflows/dicethrone-hero-intake.md`
  - `docs/games/smashup/workflows/smashup-faction-intake.md`

## 一、通用原则

- 先建契约，后写代码：录入前必须先产出 Markdown 核对契约，再落运行时代码。
- 先裁图，后录入：原始整图只用于定位；正式录入必须基于“单个对象可完整看清”的裁图。
- 单一权威来源：每个字段都必须能追溯到当前任务约定的主真相源。
- **默认真相源**：如无明确指定，本项目以“**已录入的现有数据**”（代码中的静态数据 + i18n 文案 + 规则文档）作为默认真相源。
- 真相源与对照源分离：真相源负责正式录入，对照源只负责辅助核对与发现冲突。
- 零猜测：任何文字、数字、关键词、限定词、索引，只要不确定就必须停下。
- 原文与结构化结果并存：禁止只保留最终代码值，不保留原始文本。
- 先文档后实现：影响规则、机制、描述、展示或资源映射的录入，必须先更新文档，再改代码。
- 根规范只管方法论：某个游戏的专用抓取脚本、字段命名、卡牌结构，不得写成全局默认。

## 二、录入对象范围

录入任务默认要覆盖素材承载的全部对象，至少检查：

- 能力类：技能、被动、防御技、升级差异、时机标签、伤害类型。
- 状态类：token、堆叠上限、施加/移除条件、持续时间、例外条件。
- 提示类：说明板、帮助板、关键词提示、骰面说明、流程提示。
- 资源类：atlas 图、atlas json、frame 命名、独立 icon、资源引用路径、复用关系。
- 索引类：原图路径、裁图路径、顺序依据、运行时索引字段、图块编号、显示映射。

强制要求：

- 每个条目都必须同时记录触发条件/时机、原始文本、结构化结论。
- 不得只写“效果摘要”而省略触发条件。
- 不得只录技能而漏掉提示板、图集索引或资源复用说明。

## 三、权威来源优先级

**默认真相源口径（本项目基线）**：

- **已录入的现有数据**（代码中的静态数据 + i18n 文案 + 规则文档）为默认真相源。
- 若用户明确指定新的真相源（如规则书/PDF/图片/Wiki），才允许切换真相源并以其为准。
- 未获得明确指定前，外部资料一律视为**对照源**。

外部资料优先级（作为对照源或在用户明确指定为真相源时的优先级）如下：

1. 官方勘误、官方规则书、官方 PDF
2. 官方数据库、官方页面、官方 API
3. 项目约定的专用抓取源或游戏专属爬虫
4. 用户明确指定为本轮真相源的清晰图片、截图、扫描件
5. 项目内既有规则文档
6. Wiki、社区资料、论坛整理

补充规则：

- 若用户明确要求“以这批汉化图片为准”，这些图片在当前任务里就是主真相源；英文原版、Wiki、社区资料只能作为对照源。
- 若某个游戏要求必须走专用爬虫或专用比对脚本，应写在该游戏专属规范中。
- Wiki 不是默认真相源；除非用户明确指定，否则只能作为对照来源。

## 四、强制交付物

一次完整的数据录入任务，至少要有以下文档产物：

1. 真相源表
2. 切图表
3. 核对合同表
4. 对照表
5. 冲突待裁定表

### 1. 真相源表

必须记录：

- 真相源类型
- 真相源路径或链接
- 获取时间
- 覆盖对象
- 录入口径说明

### 2. 切图表

必须记录：

- 原图路径
- 裁图路径
- 裁图坐标或裁图规则
- 对应对象
- 当前可读性结论

### 3. 核对合同表

至少包含：

| 字段 | 含义 |
| --- | --- |
| 实体标识 | `defId`、`id`、变体 ID |
| 类别 | 技能 / 状态 / 提示 / 图集 / 索引 |
| 真相源定位 | 图片路径、裁图路径、页码、URL |
| 原始名称 | 原图或原文中的名称 |
| 触发条件 / 时机 | 图标组合、阶段、前置条件、次数限制 |
| 原始文本 | 原图或原文中的完整描述 |
| 结构化字段 | `type`、`cost`、`power`、`tags`、`index`、`faction` 等 |
| 不确定项 | 看不清、冲突、待确认字段 |
| 结论状态 | `已确认`、`待确认`、`冲突待裁定` |

### 4. 对照表

必须记录：

- 对照源链接或路径
- 对照源语言或版本
- 对照字段
- 对照结果：`一致`、`补充说明`、`疑似冲突`

### 5. 冲突待裁定表

一旦主真相源与对照源冲突，必须单独建表，至少包含：

- 冲突对象
- 真相源结论
- 对照源结论
- 冲突类型：文字 / 数值 / 时机 / 范围 / 索引 / 资源引用
- 当前处理状态：`待用户裁定`

禁止行为：

- 发现与“已录入现有数据”冲突后直接改写代码或文案。
- 在主表中偷偷用对照源覆盖真相源。
- 未经明确指定就擅自切换真相源。
- 把“我觉得更合理”写成裁决结论。

## 五、标准流程

### 1. 锁定主真相源与对照源

必须先记录：

- 真相源类型
- 真相源路径或链接
- 对照源类型
- 对照源路径或链接
- 获取时间
- 字段适用范围

### 2. 先裁图到可读粒度

必须先把整图切到“单个对象能完整看清”的粒度，再开始录入：

- 单个技能一张裁图
- 单个状态说明一张裁图
- 单个提示板块一张裁图
- 单个 atlas frame 或复用说明单独登记

强制要求：

- 裁图必须覆盖完整标题、触发条件、正文、图标和关键限定词。
- 如果整图上多个对象混在一起，必须拆开，不能依赖放大整页查看。
- 如果裁图后仍看不清，必须继续细分或更换更清晰来源。

补充强制分类：

- `原始真相源`：原始整图、规则书页、官方 PDF 页、未改写的正式运行时图
- `几何裁图`：按固定坐标从真相源切出的单对象图，只服务录入核对
- `后处理核对图`：为了看清文字再做的放大、锐化、上下拆分、拼接、归一化预览
- `正式运行时资源`：代码真实引用、已进 manifest、会被客户端请求的资源

判定规则：

- `几何裁图` 和 `后处理核对图` 默认都是中间产物，必须放 `temp/` 或等价临时目录
- 只要某张图是“为了录入时看清文字”额外生成出来的，就不能放进 `public/assets/` 正式资源树
- 禁止因为文件名像 `slot-24.webp` 或 `deadeye-2.webp`，就把中间产物误判成正式资源或主真相源
- 如果某个游戏历史上把核对图留在了 `public/assets/.../crops/**`，后续排查时必须先把它当作可疑中间产物，而不是默认相信它代表正式 atlas 语义

### 3. 建立 Markdown 核对契约

- 表格必须按素材顺序、逻辑顺序或官方顺序排列。
- 原始文本必须和结构化字段并排出现。
- 同一字段如果存在多个来源，必须显式写出对照结论。

### 4. 全口径核对

至少逐项核对：

- 名称
- 类型
- 数值
- 关键词
- 限定词
- 作用对象
- 作用范围
- 触发条件
- 触发时机
- 次数限制
- 例外条件
- 图片索引、图集索引、资源路径、复用来源

### 5. 结构化映射

必须明确区分：

- 哪些字段进入静态数据层
- 哪些字段进入 i18n
- 哪些字段进入规则文档
- 哪些字段进入资源注册或 atlas/json
- 哪些字段只作为后续实现依据

### 6. 文档同步

录入影响玩法、机制、文案或资源展示时，必须同步更新：

- 对应游戏的 `rule/*.md`
- 对应 i18n 文案
- 必要时的开发规范文档
- 资源索引说明或素材登记

### 7. 资源上传收口

只要本轮录入新增、替换或移动了运行时会访问的资源，就必须在交付前完成：

- manifest 重建
- R2 / CDN 上传
- 远端代表性 URL 回查

默认要求：

- AI 主动执行上传，不等待用户单独提醒
- 没有上传不算完整交付
- 若因环境、配置、脚本报错或用户明确要求而暂时无法上传，必须在最终汇报中明确说明：
  - 哪些资源未上传
  - 为什么未上传
  - 当前运行态会出现什么影响

### 8. 再进入代码实现

只有在以下条件满足后，才允许开始实现：

- 来源已锁定
- Markdown 核对契约已写
- 不确定项已清零或显式挂起
- 对应规则/说明文档已同步

## 六、零猜测原则

以下任一情况都必须停止录入并向用户说明：

- 名称有字看不清
- 数值模糊
- “可 / 必须 / 直到 / 改为 / 额外 / 其他 / 另一个”等限定词不确定
- 图片索引、图集位置、裁片对应关系不确定
- 素材外观与运行时语义的对应关系不确定，例如看到了空白格、黑边、角落装饰、额外立绘或疑似复合排版，但无法证明它在运行时到底代表什么
- 看到了“升级标题 + 下方子区/副标题/相关技能名/说明块”这类复合升级排版，但尚未证明这些子区在运行时到底是同一张卡的组成部分、同类最高级语义，还是独立手牌对象

禁止行为：

- 根据英文原版猜中文
- 根据上下文补完整句子
- 根据相邻条目推断索引
- 根据 atlas / crop 的视觉外观猜“这不是正式卡”“这一格其实是两张”“需要 split/topCrop”“可以直接改 rows/cols”
- 根据一张升级牌里出现多个标题、多个技能名或上下子区，就直接推断“要拆成两张正式手牌图”或“每个子区都要占一个新索引”
- 先录进去，等以后再核对

### 复合升级补充规则

- 如果老派系已经证明某类升级是“同一基础技能 + 多个 `variants` / 档位 / 子效果，且同类取最高”，新录入角色默认先沿用这条执行合同，不能重新发明成多张手牌对象。
- 图面上出现多个子区、多个标题或升级后附带的相关技能名时，必须先区分：
  - 这是能力执行层的复合语义
  - 还是图片源里的复合排版
  - 还是正式运行时真的存在多张独立手牌
- 上述三者未区分前，禁止把图片子区直接写成新的 `card.id`、新的 `previewRef.index`、新的 atlas frame。
- 一旦证据已经指向“同一张物理牌里的复合子区”，必须立刻停止继续改运行时实现，先完成：
  - 老派系同类升级逐张对照
  - 真相源 / 核对图 / 正式运行时资源三层拆分登记
  - 复合语义裁定文档
- 在这三步完成前，禁止继续推进：
  - `cards.ts` 新增或保留“两个子区 = 两张独立手牌”的录入
  - atlas / frame / `previewRef.index` 接线
  - 以 E2E 通过为由宣称素材语义已收口
- E2E、截图、真实 UI 行为只能证明“当前实现表现如何”，不能反向证明素材语义正确；只要素材语义仍未裁定，测试结果一律视为现象记录，不得作为录入正确性的最终证据。

## 七、图片与索引补充规范

当素材涉及 atlas / index / crop 时，必须额外记录：

- 原始大图路径
- 裁片路径
- 裁片顺序依据（从上到下、从左到右或官方编号）
- 最终运行时索引字段
- 该素材是“真相源裁图”“正式运行时资源”还是“中间产物”
- 本轮采用的旧实现 / 旧角色 / 旧资源接线对照依据

如果图片索引尚未确认：

- 可以先录 `defId` 和文案
- 但必须把 `previewRef` 或索引字段标为未完成
- 不得伪造正式索引占位

额外强制规则：

- 不得从后处理核对图直接反推“这一格其实是两张”“这个 slot 不是正式卡位”“运行时必须改成单卡图”
- atlas 语义、slot 语义、运行时 `previewRef` 合同，必须回到原始真相源、旧角色基线和真实 UI 消费链一起裁定
- 如果核对图与原始真相源、旧角色基线冲突，优先怀疑核对图生成链路有问题，而不是先改运行时代码

当 `previewRef`、atlas frame、手牌图集接线方式无法从现有文档唯一推出时：

- 先对照同游戏旧实现、现有运行时代码和专项规范
- 若仍有多种合理解释，必须先问用户，不得自行裁决
- 允许“一张正式图片对应多个运行时对象”，但这类复用关系必须显式登记，不能靠肉眼猜

## 八、游戏专属补充

- 某个游戏若要求特定爬虫、比对脚本、裁图规则、索引结构或字段命名，必须写到该游戏自己的 `rule/` 文档或专项规范中。
- 例如大杀四方若要求使用项目内爬虫核对 Wiki，应在大杀四方规则/专项文档中明确，而不是提升成全局默认。
