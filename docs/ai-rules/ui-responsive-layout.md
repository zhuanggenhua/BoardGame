# UI 双端与响应式布局规范

> 来源：从 `docs/ai-rules/ui-ux.md` 无损拆出。本文档承载多端布局、参考分辨率、双端架构分层和单位选择规则；`ui-ux.md` 只保留入口摘要。

## 多端布局策略 (Multi-Device Layout Strategy)

- **双端并行，不是双份 UI**：默认只有一套 React UI 架构，通过 `manifest + runtime viewport + 终端能力探测 + layout preset` 做条件化分支；**禁止**为同一游戏长期维护两套互相漂移的 `DesktopBoard` / `MobileBoard`。
- **PC 仍是固定构图类基线**：棋盘、战区、固定多栏面板、角色布局等几何关系明确的界面，仍以桌面版为结构真相源；移动端优先同构缩放，再处理 rail、dock、overlay、触控入口。
- **固定牌桌不得移动端重做**：对 `board-shell` / 固定牌桌，顶栏、分数、手牌、中央牌区、主按钮、主操作区默认都是同一张 PC 构图的一部分；移动端不得把这些主区域拆成新的右侧 dock、底部 rail、独立按钮区或另一套字号/间距体系。
- **移动端是一等输入终端**：移动端不再只是“能打开就行”。凡是共享组件、共享交互、共享布局，只要预计会出现在移动端，就必须在方案阶段同时考虑安全区、触控命中区、长按/armed 等替代入口和方向约束。
- **宽限度约束 (Constraints)**：平台/网页 UI 通过 `max-w-7xl` 等容器限制内容延展，确保视觉焦点集中。

### 默认参考分辨率（强制）

- **PC 默认主参考分辨率固定为 `1920x1080`**。
  - 这是桌面端唯一默认权威基线；未特别说明时，桌面截图、桌面布局对照、PC 同构验收都优先以此为准。
  - 不再默认混用 `1440x900`、`1600x900`、`1366x768` 作为并列基线；这些尺寸若要使用，必须说明只是补充排查，不是主裁决口径。
- **移动端默认主参考分辨率固定为 `375x812`**。
  - 这是移动端唯一默认权威基线；未特别说明时，移动端截图、适配验收、对照证据默认使用它。
  - 若某游戏主打手机横屏或老板明确指定横屏分辨率，再按当轮任务单独声明，不在全局规范里默认保留第二套移动端主基线。

### 参考分辨率使用规则（强制）

- 先看该界面的**主参考分辨率**结果，再决定布局是否成立。
- 当老板明确指定分辨率（如 `1920x1080`）时，以老板指定为准；未指定时，按本节默认值执行。
- 正式 E2E 的职责是验证行为，不是服务某次截图取证。**特定分辨率截图需求应走独立取证路径，不得为了出图把正式 E2E 改写成专用脚本。**

- **响应式策略指南 (Responsive Strategy Guidelines)**：
    - **信息交互层 (UI & HUD)**：
        - **场景**：大厅卡片、侧边栏、模态框、文字阅读区。
        - **建议**：**稳定性优先**。推荐使用标准 `rem`，必要时配合 `clamp()` 锁定物理最小值（12px/14px），保证全环境可读。**不要**用裸 `vw` 作为正文、按钮文案、常规表单控件的主字号来源。
    - **沉浸视效层 (Immersive & Board)**：
        - **场景**：游戏棋盘、全屏背景、核心对战区域。
        - **建议**：**比例优先**。优先使用 `aspect-ratio`、`%`、壳层统一 `scale(...)`、以及运行时 viewport 变量；`vw/vh` 只能作为局部比例辅助单位，**不再推荐**作为固定构图类界面的主适配手段。
    - **布局流动层 (Layout Flow)**：
        - **场景**：列表网格、工具栏排列。
        - **建议**：**内容驱动**。利用 Flex/Grid 的自然流特性（如自动填充、自动换行）来适配屏幕宽度，而非依赖硬编码的断点控制。

### 双端 UI 架构分层（强制）

- **L1 页面路由层**：负责路由、页面语义、`Suspense fallback`、错误兜底、方向提示、运行时环境门禁；不直接承担某个游戏的细部布局。
  - 对局页统一通过 `getGamePageDataAttributes()` / `syncGamePageDocumentAttributes()` 输出 `data-game-page`、`data-mobile-profile`、`data-mobile-layout-preset` 等属性。
- **L2 页面壳层 / 运行时层**：负责真实 viewport、安全区、键盘 inset、终端能力探测、根级 CSS 变量同步。
  - 统一使用 `useRuntimeViewport`、统一 runtime helper，禁止页面各自重算一套 viewport 和原生壳判断。
- **L3 游戏壳层（layout shell）**：负责 `MobileBoardShell`、top rail、side dock、bottom rail、缩放舞台、board-shell / portrait-simple / map-shell preset。
  - 这层解决“桌面结构如何映射到移动端”，不承载游戏规则。
- **L4 游戏画布层（scene / board）**：负责棋盘、卡牌、角色区、日志区、手牌区等游戏内容本身。
  - Board 组件默认只关心壳内内容区域，不再直接读取原始视口高度去自建第二套移动壳。
- **L5 交互适配层（interaction adapter）**：负责 hover 替代、long press、armed activation、drag fallback、触控命中区增强。
  - 这层只能改变“如何触发”，不能改变“是否可用”的业务真值。
- **L6 原生壳边界层**：负责 `Capacitor`/Android/iOS 专属能力、返回桥、更新检查、原生包逻辑。
  - 原生壳行为必须停留在统一 helper 与 App shell 层，不能泄漏到共享业务 UI。

### 双端设计裁决（强制）

- **先判断界面类型，再决定适配手法**：
  - 固定构图类：优先等比缩放 + 局部让位；同一牌桌内的顶栏、手牌、主按钮、分数和中央区不得被当成可自由重排的流式工具栏。
  - 流式信息类：优先响应式重排 + 抽屉/标签页/单列化。
- **允许设备差异，不允许语义分叉**：
  - 可以桌面 `hover`、移动 `long press`。
  - 可以桌面单击、移动 armed 后二击。
  - 不可以桌面和移动分别维护两份 `canUse / isSelectable / showUsed`。
- **缩放舞台只能有一层主真值**：如果页面已经位于 `board-shell` 统一缩放容器内，页面内部默认禁止再套第二层整页 scale-to-fit。
- **固定牌桌的中心轴与尺度链必须单一来源（强制）**：
  - 顶栏、中央牌河、手牌区、主动作等若属于同一套 live 牌桌，必须共享同一条几何中线与同一套缩放来源。
  - 禁止手牌区、中央牌区、按钮区分别使用互不相关的 `vw` 宽度公式、绝对定位魔数或额外 `transform scale` 去拼出“截图里像是居中”的结果。
  - 只要改动影响其中任一块的宽度、间距或锚点，就必须回到真实宽桌面与真实窄桌面同时验证中线、单卡宽高和主动作落点。
- **HUD 与 Scene 分治**：棋盘/地图/战区优先保持固定几何关系；日志、帮助、设置、按钮轨道可以让位、悬浮或抽屉化。
- **主 HUD 与次要 HUD 分治**：回合按钮、确认按钮、分数、阶段提示、手牌操作这类主 HUD 如果已经嵌在固定牌桌构图里，默认跟随牌桌统一缩放；只有日志、帮助、设置、聊天、反馈等次要 HUD 才默认允许移动端让位、悬浮或抽屉化。
- **端能力判断只进边界层**：`pointer: coarse`、`Capacitor.isNativePlatform()`、`window.androidBridge` 这类探测不应散落在业务组件中，必须先进入统一 helper 或 Hook。

### 单位选择规则（强制）

- **文本、按钮、表单、日志、常规 HUD**：
  - 优先 `rem`
  - 必要时 `clamp(minRem, preferred, maxRem)`
  - 原因：可读性稳定，桌面与移动不会随 viewport 宽度一起失真
- **固定构图类主布局**：
  - 唯一主方案是 `px` 设计画布 + 外层统一等比 `scale`
  - 标准公式：`scale = min(availableWidth / designWidth, availableHeight / designHeight)`
  - 原因：保持几何关系，避免局部元素各自按 `vw/vh` 漂移
  - 横屏常由高度约束、竖屏常由宽度约束，只能作为统一公式的计算结果，不得拆成“横屏 `vh`、竖屏 `vw`”两套主单位
- **壳层高度 / 移动端可视高度**：
  - 优先运行时同步的 viewport 变量
  - 在 `board-shell` 内禁止直接依赖裸 `100vh/100dvh`
- **局部比例型装饰尺寸**：
  - 可少量使用 `vw` / `vh`
  - 例如纯视觉徽章、背景装饰、局部舞台内的相对偏移
  - 前提：它不承担可读性和主布局稳定性的职责
- **触控命中区**：
  - 优先 `px/rem` 下限，例如 `44px`
  - 不要用 `vw` 让命中区跟着屏幕宽度忽大忽小
- **历史 `vw` 代码处理原则**：
  - 桌面固定构图下如果效果稳定，可暂时保留
  - 但新增代码不应再把裸 `vw` 当成默认主单位
  - 一旦该区域进入 `board-shell`、双端同构或移动端主链路，应优先迁移到“设计宽度 + 统一缩放”或 `clamp/rem`
