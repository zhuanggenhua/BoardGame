# 测试审计核心原则与矩阵门禁

> 来源：从 `docs/ai-rules/testing-audit.md` 无损拆出。本文档承载 fail-close 审计速查、全面审计完成定义、录入/图片/旧 evidence 边界、交互入口语义矩阵和技能完整流程矩阵；`testing-audit.md` 只保留入口摘要、证据分层和流程路由。

## 核心原则

- **fail-close 审计速查（强制）**：凡对象涉及阶段推进、共享伤害链、共享状态/token、支付/拒绝、攻击后续或其它容易“中间态看起来对了”的链路，正式写“已审计/已收口”前，至少要先过这四卡点：
  1. **最终权威状态**：必须说清最终要验证的是哪一个现实结果，例如血量、资源、token、区域归属、阶段收口；若证据还停在 `prompt/pending/sourceAbilityId/currentChoice`，只能算中间态。
  2. **流程收口**：必须证明交互结束后不会误跳阶段、不会残留 pending、不会卡在 halt、不会吞掉后续结算；至少补 1 条负向断言。
  3. **共享链来源归属**：只要进入 shared helper / resolver / consumer，就必须写清“谁授予、谁持有、谁消费、谁清理”，并证明缺少该来源时不会误生效。
  4. **来源例外**：若对象属于共享家族但规则里有特定来源/时机/目标例外，必须单列“不应被家族共性自动外推”的断言；没有这条，不得判通过。
- **规则 bug 修复先走专用入口（强制）**：当用户反馈“规则不对 / 低级和高级不一样 / 不是这个等级能做 / 你审计漏了 / 为什么回归”时，先读 `.codex/skill/rule-bug-fix-workflow/SKILL.md`、`docs/ai-rules/rule-contract-audit.md` 和 `docs/ai-rules/regression-closeout.md`。本文档只保留全面审计、证据分层和 D 维度入口；规则 bug 的三条不变量是：先判断录入合同是否被实现正确消费；只有合同缺失、未锁或与反馈冲突才回图面/规则源；修复必须同步回写录入合同、中文/英文描述、静态定义、测试和 evidence。
- **全面审计为主，测试工具为辅（强制）**：审计是思维框架（告诉你"该检查什么"），测试工具是执行手段（帮你"自动化检查"）。审计必须先做（人工思考），测试工具是补充（自动化覆盖）。
- **“审计”默认就是全面审计（强制）**：用户或文档只说“审计 / 重审 / 审过 / 收口审计”时，默认含义是对当前目标范围内**所有对象、所有相关维度、所有适用证据层级**做完整审计，而不是抽样、专项或静态检查。这里的“所有”指对象全集、规则子句全集和适用维度全集，**不等于对所有对象、房间、卡牌、骰面、状态和玩家排列做无限全组合测试**。若实际只做抽样、专项、L1 静态或代表链验证，必须在任务名、evidence 标题和汇报里显式写成“抽样审计 / 专项审计 / L1 结构审计 / 代表性验证”，禁止简称为“已审计”。
- **审计缺口分类先行（强制）**：每个待补项必须先判断现实含义：① `功能实现阻塞`：规则对象、玩家合法动作、候选、结算、最终权威状态或共享消费者确实不对；② `当前范围验证缺口`：实现可能已对，但还缺当前范围必要证据、关键组合证明或真实入口截图；③ `审计留档缺口`：证据没有被总账消费、旧结论未回写或截图索引不足；④ `非阻塞扩展`：不改变当前发布范围规则正确性，只是额外组合、额外截图或更宽覆盖。只有第 ① 类能直接阻塞“规则实现正确”；第 ② 类阻塞“审计完成口径”；第 ③ 类只阻塞证据可追溯；第 ④ 类必须登记为范围外或后续扩展，不得冒充实现缺口。
- **全面审计完成定义（强制）**：全面审计至少必须同时满足：① 建立目标对象全集清单；② 对每个对象逐项覆盖适用 D 维度；③ 对每个对象标明 L1/L2/L3/L4 当前证据等级；④ 所有规则效果至少达到 L2 行为证据，或明确写入阻塞/不适用原因；⑤ 所有真实 UI 交互入口达到 L3，或明确归入等价代表链并说明为何可代表；⑥ 所有时序/窗口/队列/跨阶段/共享根因对象达到 L4；⑦ 关键组合矩阵、旧结论失效回写与残余范围均已分类。缺任一当前范围必需项，不得写“全面审计完成”；只剩非阻塞扩展时，必须明确写在当前范围外，不能继续叫当前实现缺口。
- **“彻底做到底”定义（强制）**：当用户说“全面审计 / 深入审计 / 没有死角 / 做到底”时，默认不是“每类对象抽一条代表链”，而是要把当前范围内每个对象的真相源子句、实现入口、行为证据、真实入口与最终权威状态逐项打穿。除非已经证明多个对象共用**完全同一条共享链路**，且差异仅为静态配置、数值、文案、图集索引或目标集合配置，不新增时机、资源消耗、候选生成、流程态、清理、窗口或分支语义，否则不得用代表链替代对象级深审。
- **`shared / 共享` 不能单独作为结论（强制）**：任何对象行若复用代表链，`共享链路 / 复用依据` 至少必须写清：① 共享链名称或 ID；② 被复用的代表对象；③ 该对象与代表对象在触发时机、候选生成、交互入口、payload 字段、resolver/handler、最终权威状态六项上的判等依据；④ 本对象仍然独有或未覆盖的差异。只写 `shared`、`共享链已覆盖`、`同构`、`同 helper` 或“和某对象类似”一律只能算 `representative_only`，不得写 `passed`、`已审计` 或 `已收口`。
- **新增 / 实施中批次对象默认按全面审计执行（强制）**：当任务语义是“新增派系 / 新英雄 / 新角色 / 新对象接入 / 从素材做到可玩”，或当前游戏目录 / UI / 配置里已有多个对象被标记为“实施中”时，默认交付就包含**该批次对象级全面审计 + evidence 留档**。除非用户明确把范围缩成“只录入 / 只修一个 bug / 只做静态接入”，否则不得再追问“要不要补审 / 要不要留档 / 要不要全面审计”。
- **抽样/专项不得冒充全面审计（强制）**：抽样审计只能发现问题或提高信心，不能替代全集逐项矩阵；专项审计只能证明该专项维度，不得顺带宣称整体审计完成；静态矩阵只算 L1，不能单独支撑“可合并/可发布/已收口”。
- **审计文档是完成态证据（强制）**：凡是汇报“已审计/已收口/已审过”的对象，必须在 `evidence/` 下有对应审计文档；**没有文档就视为没有完成审计**。禁止把口头结论、临时对话、零散测试通过，当成审计完成的凭证。
- **审计文档必须可复查（强制）**：文档不能只写“已核对正常”。至少要包含：① 审计范围 ② 权威来源 ③ 逐项/逐卡判断 ④ 命中的审计维度（如 D1/D5/D8/D34/D48/D49/D50）⑤ 对应实现入口 ⑥ 已验证测试/证据 ⑦ 未覆盖风险或待补项。
- **全面审计完成后必须跑自检（强制，不接发布门禁）**：凡 evidence 或审计汇报要写“全面审计完成 / 当前发布口径已收口 / 当前代码验证口径已收口 / 已审计 / 已收口 / 已审计完成 / full_audit”，必须在审计完成后运行 `npm run audit:evidence:selfcheck -- <evidence 文件>`，并把命令与结果写入该 evidence。脚本只检查留档结构和高风险证据是否齐全，不替代人工判断，也不默认阻塞提交、push、release 或 deploy；脚本失败时禁止换成“代表性验证通过”继续声称全面收口，只能补齐文档、降级结论或记录残余范围。
- **批次总范围变更必须同步回写子审计文档（强制）**：当当前任务的审计范围从单对象扩到一批对象、从局部样本扩到全集，或批次对象名单发生变化时，除了更新总汇总文档，还必须同步回写所有已存在的单对象/子范围审计文档。每份子文档至少要明确：① 本文档只覆盖哪个子范围；② 当前整批总范围是什么；③ 总范围汇总文档入口在哪里。禁止只改总文档，让旧子文档继续被误读成整批范围证明。
- **审计不替代数据录入（强制）**：凡是图片、玩家板、棋盘、卡图、图集、布局图本身就能直接定义槽位/区域/顺序/空槽/display-only/可交互区，这类“可视合同”首先属于数据录入职责，必须先落在真相源表/录入核对表里。审计的职责是检查“这份描述/合同是否被实现正确消费”，而不是把本该录入阶段完成的合同发现工作长期挪到审计阶段。
- **先查已有录入合同，不得默认判“没录入”（强制）**：审计阶段如果遇到规则原文、对象归属、能力描述或图面合同缺口，必须先检索当前仓库既有录入合同、规则原文矩阵、source map、crop manifest、evidence 和状态文件。若已有记录但状态是 `blocked/disputed/待建合同`，只能说“已有录入入口但合同未锁定/归属未裁定”；不得把检索不充分、合同未锁或状态争议，汇报成“用户没录入数据”或“需要重新录入”。只有确认所有既有入口都没有命中对象，才允许写“未找到录入记录”。
- **中文录入优先中文汇报（强制）**：若录入合同、卡图、i18n、用户截图或用户故事里的对象名/能力名/规则描述是中文，审计报告、修复汇报、表格和提交说明必须优先展示中文对象名、中文能力名和中文规则描述/合同原文；英文官方名、英文原文、能力 id、代码标识只作为附证或定位补充。禁止只给英文原文、英文能力名或代码 id，让用户自己反推中文能力。
- **原文列必须填原文，不得用状态句顶替（强制）**：凡审计表格、修复表格或 evidence 表格列名包含“规则原文 / 合同原文 / 中文规则描述 / 能力描述”，该单元格只能填已录入的逐字原文或明确写“未找到原文记录”。不得填“已有录入入口”“合同未锁定”“对象归属未裁定”“待裁定候选线索”“规则原文/归属未锁定”这类状态句来冒充原文。若原文未找到，必须另列“已查入口/合同状态/下一步”，把状态和原文分开。
- **图片可判定合同的审计口径（强制）**：当审计对象的权威描述本身就是图片或图片派生合同表时，审计必须直接对照该描述核查实现；若审计时发现这张合同表根本不存在、内容不完整或与权威图片矛盾，结论必须写成“数据录入未完成/录入合同错误”，并据此判定审计不能收口。审计文档仍需写清“图上实际看到什么”，不得用“可能/大概/推测”替代可直接观察的结论。
- **已 locked 合同不得反复回录入层（强制）**：审计必须尊重录入合同状态。`locked` 对象的下一步是实现对照、最小行为补证、真实入口补证、L3/L4 补证或最小修复；不得因为“再确认一下数据”就重新 OCR、重新裁图或重新抄原文。只有审计发现合同字段缺失、来源互相冲突、对象归属不清，或用户明确要求复核时，才把对象降级为 `blocked/disputed` 并回录入层。
- **图片读取只服务当前审计问题（强制）**：审计使用图片读取、OCR、截图核对或子代理时，输入必须是当前审计正在验证的具体需求，例如“录入这张房间牌文字合同”或“判断这个已实现效果是否符合合同”。输出形态随需求变化：录入返回详细字段，验收返回通过/失败与失败点。禁止把图片读取变成独立审计报告，也禁止让子代理接管审计任务；应把当前需求和判定口径传给它，让它只返回当前需求需要的结论。
- **录入质量通过合同字段守门，不通过重读图续命（强制）**：如果担心录入没做好，先检查合同是否包含主真相源、完整单对象图/可读裁图、对象归属、规则原文、原子子句、索引入口和对照差异；缺项就降级并补合同，齐全就必须继续实现审计。禁止在合同齐全且状态为 `locked` 时，用反复读图替代实现链路核对。
- **不得把旧共享语义外推当成合同（强制）**：若当前实现的槽位/区域/atlas/候选映射，来源只是“旧对象同名槽位通常如此”“共享 helper 过去一直这么用”“slotId 看起来语义一致”，而不是当前对象自己的图片合同、规则文本或明确用户故事，则审计结论必须直接写成“录入靠猜/合同错误”，不能降格成普通 UI 偏差或一次性样式问题。发现这类问题后，至少要同时回查：① 录入核对表是否缺少可视合同；② UI 高亮/可点击/候选生成是否也消费了这份猜测映射；③ 同批兄弟对象是否复用了同一外推。
- **图面槽位与可交互性必须同审（强制，通用）**：凡玩家板、技能板、提示板、图集、状态栏图片本身已经定义了槽位/区域/被动位/防御位/展示位，审计不能只核对“对象名放进去了”，还必须同时核对：① 运行时 `slot -> object` 映射是否与图面一致；② UI 高亮、可点击态、可选边框、动画起点是否落在正确槽位；③ display-only / 被动槽 / 非交互槽不得冒充主动可选入口。若图面合同要求“这里是被动位/防御位”，却在运行时被高亮成其它技能或可选入口，必须直接记为实现错误，而不是样式问题。
- **玩家反馈挑战图面录入时，先回原图再下结论（强制）**：如果玩家反馈直接质疑“图上是不是这个意思”“这条是不是录错了”“你是不是看错图标了”，默认不得先用旧录入表、旧测试绿灯或现有 i18n 去反压反馈。必须先回到当前对象的原始图面证据，必要时重新切更高清裁片，并把同角色提示板、状态图标、骰面说明等辅助图一起并排核对。若现有裁片清晰度不足、图标语义存在歧义或不同图面之间互相打架，结论必须写成“当前图面证据低置信度/需重切图或补更高清真相源”，不得继续把旧录入当硬真相。
- **规则修复不得先改写牌面语义（强制）**：当玩家反馈涉及“能不能移动/打出/选择/触发/替代/取消/继续结算”这类规则边界时，动代码前必须先用已录入规则、规则书、Wiki 或用户故事回答三件事：① 牌面/规则是否允许这个动作；② 动作后通用规则如何继续结算；③ 当前修法是在恢复规则结果，还是为了止血而改变了允许范围。若只能通过“减少可选目标、跳过触发、吞掉后续结算、禁止原本允许的动作”来避免卡死，默认只能标成止血或错误修法，必须先找规则允许动作后的收口问题。测试必须覆盖“规则允许目标 + 后续通用规则收口”，不能把“禁止该目标出现”当成规则正确性证据。
- **卡死反馈审计必须真实状态回放（强制）**：当用户反馈是“卡死 / 阻塞 / 不能继续 / 一直弹 / 操作后没下文”时，审计重点必须落在“真实状态从卡点继续跑是否能收口”。必须先注入该反馈自带的真实状态、操作日志或诊断快照，跑通至少一条可选后续路径；若怀疑某个分支会卡死，必须实际跑该分支。禁止用假设局面替代真实反馈状态，例如在未核对快照前预设“所有目标都被占了”“无处可移动”“一定是某对象导致”。如果真实状态在当前代码下能跑通，结论应写成“当前树未复现 / 当前树已恢复 / 原反馈未证实现存 bug”，不能继续包装成已定位 bug；若只是加了防循环或兜底但未回放原始状态，只能标成相关风险防线或止血。
- **真相源推翻旧测试时必须降级旧测试（强制）**：当图片、规则书或正式合同直接推翻了既有静态数据 / i18n / 结构化字段时，所有基于旧错误合同编写的单测、行为测试、E2E 和 evidence 结论，必须立即降级为“只能证明旧实现曾如此运行”，不得继续作为“规则正确”证据。测试变绿不能覆盖真相源；先回写录入合同与 evidence，再重写测试断言。
- **修复汇报必须同时附规则原文和现有实现（强制）**：涉及卡牌、技能、Token、状态或阶段能力的修复，不能只汇报内部 id、测试名、文件名，也不能用“现有实现描述”冒充规则来源。必须给出用户能核对的两列：① 中文规则描述/已消费合同原文，必要时附英文官方原文；② 现有实现行为。随后再写中文对象名、代码标识、能力中文名、能力 id、修复动作、验证证据、当前结论状态。若规则原文未找到，原文列必须写“未找到原文记录”，并把结论标为候选或 disputed，不得汇报成已证实修复。
- **旧审计被推翻必须回写（强制）**：如果后续发现“已审计”对象仍存在漏审、误判或规则理解错误，必须回写原审计文档，标出失效结论、失效原因、修复提交点和新增回归测试；禁止让旧文档继续以“已收口”状态误导后续开发。
- **旧 rule/evidence 结论不是当前实现真相（强制）**：继续实施、扩审或判定“未实现/已实现”前，必须先把旧 `rule/`、旧 `evidence/`、旧截图与**当前代码 + 当前测试 + 当前真实入口证据**对账。旧文档写“未实现”“已对齐”“已收口”都只能算历史结论，不能直接当成当前实现状态。
- **旧文档与当前代码冲突时，先降级旧文档再继续审计（强制）**：如果当前代码/测试已经证明某对象与旧文档结论相反，必须先把旧文档标成“旧结论失效/仅保留历史轨迹”，写清替代证据与残余范围，再继续扩审兄弟对象。禁止一边沿用旧文档当真相，一边据此继续宣布“又发现未实现”或“这批已完成”。
- **旧文档失效回写不得只停在顶部声明（强制）**：如果旧文档内部仍保留会误导当前状态的矩阵行、对象结论、残余范围或“只到入口/仍待补 L3/L4”表述，回写时必须把这些高风险正文同步改成“历史快照 + 当前替代证据”，或在对应行旁直接注明失效与现行口径。只在文首加一段“以新文档为准”但保留正文旧结论原样不动，不算完成回写。
- **批次残余从对象级收敛到治理级时必须回写旧矩阵（强制）**：如果当前真相已经从“某对象未实现/对象级 L4 未补”收敛成“批次级 L4 判等、旧文档统一收口、治理尾项”，则所有旧 evidence / rule 中仍把残余写成对象级缺口的矩阵行、总结段和未完成范围，都必须同步改口；否则不得对外表述成“已完成补审”或“当前残余已更新”。
- **新对象必须和成熟旧对象做共享契约对比（强制）**：新增角色 / 派系 / 模块 / 新接入资源链，只要复用了旧系统，审计时必须至少选 1 个成熟旧对象做并排对比；至少覆盖“状态落点、共享 helper、验证门禁、UI 消费链、测试 / evidence 口径”五个面。禁止只写“新对象自己现在能跑”就宣布与旧体系一致。
- **规则文本逐句/子句覆盖（强制，通用）**：所有游戏的卡牌、技能、Token、状态、按钮、装备、基地、角色能力都必须先把真相源文本拆成可编号的子句（如 `C1` 时机、`C2` 主效果、`C3` 替代入口、`C4` 额外触发、`C5` 例外/限制）。审计 evidence 必须逐子句写明：实现入口、共享消费点、状态写入/消耗点、测试或截图证据。**对象级一行 “passed” 不能覆盖未拆出的子句**；只要任一子句没有映射到实现和证据，整对象最多写“部分通过 / scoped-debt”，不得写“已审计完成”。
- **房间/场地效果不得被拓扑审计吞掉（强制，通用）**：凡房间、地图格、区域、场地、事件触发点或等价非卡牌对象带有规则效果，审计必须和卡牌/技能一样逐对象拆子句，至少覆盖进入/停留/离开/翻开触发、效果目标、掷骰或支付、状态写入、持续时间、清理、负向断言与最终玩家可见结果。只审“门位 / 朝向 / 楼层适用性 / 图集帧 / 能渲染”只能算空间或资源合同审计，不能替代房间效果审计。
- **卡牌审计必须显式包含具体效果实现（强制，通用）**：凡物品、预兆、事件、行动牌、装备牌、状态牌或等价牌对象进入发现池、牌堆、持有区或弃牌区，审计必须在同一对象下同时覆盖“对象真相/牌堆归属”和“具体效果实现”。只证明牌名、正面图、atlas 格位、抽取顺序、持有区渲染或数量不重复，不能写成该卡牌已审计；具体效果实现必须补候选生成、使用时机、目标、消耗/弃置、分支、失败路径、清理与最终权威状态。
- **漏审默认先归因到审计方法（强制，通用）**：若一个对象在“已审计/已收口”后又被发现漏了规则子句、替代入口、触发链、消耗路径或拒绝路径，默认不是“单卡意外”，而是当前审计矩阵缺了某个通用门禁。必须先回答并记录：真实根因、影响边界、应固化的不变量、规范落点；再决定是否扩审兄弟对象和更新 `docs/ai-rules/` / 项目 skill。禁止只补当前 bug 后继续保留原审计口径。
- **漏审后必须补机器可发现信号（强制，通用）**：如果漏审点本可通过 evidence 结构发现，例如没有对象全集、没有完整单卡裁图清单、没有 L0-L4 层级、没有 D 维度、没有最终权威状态、没有负向断言、没有旧结论失效回写，则必须同步更新 `scripts/verify/audit-evidence-completeness.mjs` 或本文档的脚本门禁要求。禁止只在复盘里写“以后注意”。
- **`SELECT_ABILITY` / 变体点击不等于对象已结算（强制，通用）**：凡对象从真实玩家板槽位、变体 modal、simple-choice、攻击修正或其他交互入口进入 `offensiveRoll / targetingRoll`，审计不得把“点了入口 / 变体按钮 / prompt 选项”直接当成对象效果已闭环。必须继续证明：① `pendingAttack` 或等价中间态已按该对象建立；② 真实 `ADVANCE_PHASE` / Continue / 交互确认后，正确进入防御、choice continuation 或直接收口；③ 最终 `ATTACK_RESOLVED` / phase 收口 / 权威状态变化已发生。缺任一项，只能算入口或中间态证据，不能算对象级 L3/L4。
- **攻击链内副伤害不得顶替主攻击伤害（强制，通用）**：凡攻击链中同时存在主攻击伤害和直接伤害、状态爆炸伤害、维持伤害、自伤、反击附属伤害等副作用伤害，审计必须分账证明：① 副伤害按自己的来源和类型正确扣血；② 主攻击伤害仍按原攻击链继续防御、响应和收口；③ `pendingAttack` 或等价攻击收口状态只消费“本次攻击伤害”，不能只按目标玩家相同就消费任意伤害事件。只测副伤害单独生效或主攻击单独生效，不能证明组合链已收口。
- **静态定义空壳不能视为“已实现”（强制）**：如果能力 / 卡牌 / 模块的声明层已经暴露给注册表、UI 或审计入口，但定义本身是空壳（如缺少 `trigger`、`effects`、handler 绑定），实现却藏在别的 `flowHooks` / `if (id===...)` / 旁路硬编码里，必须直接记为高优先级 finding。若运行时也未生效，这是功能级重大 bug；若运行时靠旁路仍能工作，这是结构级重大 bug，禁止因为“玩家暂时能用”就判定已收口。
- **展示占位与可执行定义必须分离（强制）**：如果某个实体存在的主要目的只是占一个 UI 槽位、展示名字/描述、维持布局映射或升级层级，就不能继续挂在“可执行注册表”里伪装成完整能力/卡牌定义。必须改成显式的 display-only 元数据，或补齐真实执行合同。禁止让“为了 UI 先放个壳”成为空实现混入审计的理由。
- **批量重审必须先建对象清单（强制）**：当任务语义是“全部重审 / 全部重录 / 这批都做完”时，审计前必须先建立对象清单，并标明每项当前层级（L0/L1/L2/L3/L4）。未建清单不得以“已经补了几张”作为暂停理由。
- **对象全集缺行即未审（强制）**：全面审计结论只能覆盖“本轮对象清单里明确列出的对象”。只要某个技能、升级版、Token、专属卡、分支对象或共享消费者没有独立行、独立层级或独立残余说明，它就是“未审/待补”，不得被兄弟对象、代表链或“同家族应该差不多”外推覆盖。尤其是 `基础版 vs 升级版`、`同名对象不同时机`、`共享入口但对象语义不同` 的情况，必须分行列出。
- **技能/卡牌必须审查完整流程，禁止只测触发点（强制）**：审计任何技能、卡牌、Token、状态或按钮时，不能只证明“条件满足后可触发 / UI 可点 / prompt 出现”。必须按对象逐项核对完整生命周期：真相源语义 → 静态定义 → 候选生成/可用性 → UI 高亮或入口 → 命令/handler → 资源消耗 → 目标/归属 → 主效果 → 分支/可选/否定路径 → 防御/响应/不可防御等交叉规则 → 后续阶段/回合结束/清理 → 最终权威状态与玩家可见反馈。缺任一必需段，结论最多写到已覆盖层级，不得写“流程已审完 / 当前发布口径已收口”。
- **对象全集不等于组合全排列（强制）**：对象全集要求“每个对象都有独立行、独立子句、独立层级和残余说明”；组合审计只要求“会改变规则结果的关键消费者组合”有矩阵行。不得把未跑完所有房间×所有卡牌×所有状态×所有骰面×所有玩家排列，直接写成当前功能未实现；也不得把真正影响触发、候选、消耗、流程态或最终状态的关键组合降级成非阻塞扩展。
- **对象承接语义必须先分类（强制，通用）**：审计任何 Token、状态、技能、卡牌、装备、按钮或交互对象前，必须先明确它属于哪一种承接语义，并把结果写入对象矩阵：`主动响应/主动消耗`、`被动自动触发`、`阶段触发`、`持续生效`、`一次性写入后由后续消费者读取`、`纯展示位`。未先分类时，禁止把“有数值效果”直接当成“可点资源”，也禁止把“会弹一个 UI”直接当成对象本体语义。
- **被动效果不得实现成主动窗口，主动资源不得伪装成被动（强制，通用）**：若真相源语义是“自动减少伤害/自动施加/自动移除/阶段开始时触发/命中后自动清理”，则审计必须明确证明它不会错误地进入主动响应窗、主动消耗窗、可点击资源栏、额外确认弹窗或其它需要玩家主动发起的壳层。反过来，若真相源语义要求玩家“可以/必须选择是否使用”，也不得被实现成无条件自动触发。只要“承接语义”错了，即使数值结果偶尔对，也必须直接记为实现错误。
- **静态/声明类审计不得冒充玩法语义正确（强制，通用）**：定义存在、注册完整、`interactionChain` 已声明、custom action 已注册、i18n/Wiki 对齐，只能证明“对象可被系统识别”或“结构上看起来完整”；不能直接证明“真实玩法中的时机、窗口、宿主、范围、清理和来源归属正确”。凡对象涉及攻击修正、响应窗口、奖励骰、自动移除、跨阶段 continuation、deferred/finalize，必须额外补对象级行为证据；仅凭静态/声明审计通过，不得写成“该对象规则已对齐”。
- **同一提示 UI / 同一选择窗不等于同一规则时机（强制，通用）**：对象即使复用了同一个 prompt、同一种 modal、同一个 simple-choice 或同一个奖励骰展示壳层，也必须单独锁定它真实结算在哪个阶段/窗口，例如“攻击掷骰结束后”“防御前”“防御后”“造成伤害后”“回合结束时”。只证明“弹窗出现了”“能点选了”不能推出时机正确；凡窗口位置会影响规则结果，必须补窗口级断言与至少 1 条相邻窗口的负向断言。
- **效果宿主、作用范围、清理方式必须同审（强制，通用）**：凡对象会修改伤害、资源、候选、行动次数、阶段推进或响应资格，审计时必须同时锁 5 件事：① 效果挂在谁身上；② 实际修改的是谁的什么值；③ 只作用于哪类范围（如攻击伤害/直接伤害/当前回合/下一次/本阶段）；④ 触发后是否自动扣层、自动移除、持续保留或延后清理；⑤ 清理失败时会不会残留到下一条链路。五项缺任一项，不得写“该对象语义已对齐”。
- **共享效果链必须单独验证“来源归属”而不只看结果（强制，通用）**：若多个对象共用同一条奖励骰链、伤害修正链、响应链、清理链或 shared helper，审计不能只看到“最终结果对了”就收口；还必须证明“是谁授予了这次效果”“由谁消耗/清理”“缺少该来源时不会错误继续生效”。也就是说，共享消费者跑通只能证明链路存在，不能证明来源对象没绑错；凡对象之间可能发生“借壳生效/错绑到兄弟资源”的风险，必须补来源级正反断言。
- **必须补一条“不会发生什么”的负向断言（强制，通用）**：只要对象存在“容易被误实现成别的语义”的风险，审计/测试必须至少补 1 条负向断言，例如“不应打开响应窗口”“不应作用于直接伤害”“不应在未命中时触发”“不应在同回合新获得后立即可用”“不应由展示槽位变成可点击入口”。只证明正向效果成立，不能防住语义跑偏。
- **命中后续链必须双向断言（强制，通用）**：凡效果的后续状态、Token、选择窗或 continuation 依赖“这次攻击是否真正造成了有效伤害”，审计/测试必须同时覆盖 `damageDealt > 0` 和 `damageDealt = 0` 两条路径，分别证明“命中时会继续”与“未命中时不会继续”。如果实现采用 `postDamage/onHit` 门禁，负向断言必须落在真实后续消费者上，不能只看前置事件是否发出。
- **漏审暴露通用缺口时，先修审计门禁而不是只补当前对象（强制，通用）**：如果某个对象在“已审计/已收口”后又暴露出“被动做成主动、宿主挂反、direct/attack 作用范围混淆、自动移除漏掉、展示位变成交互位”这类基础语义错误，默认应先把审计矩阵和 evidence 模板补上对应通用门禁，再回头修对象本身。禁止只把当前对象补绿，却不更新总审计方法。
- **不可防御 / 非攻击伤害必须反查“共享防御消费合同”而不只看 damage payload（强制，通用）**：当描述出现“不可防御伤害 / 不可阻挡 / skip defense / 不进入防御阶段 / 直接伤害 / 附属伤害 / 非攻击来源伤害”，审计不能只看到 `damage(unblockable=true)`、日志里 `unblockable: true`、custom action `categories` 包含 `'damage'`，或某条局部伤害事件就收口。必须同时反查：① 录入合同是否锁定图面颜色、伤害类型、是否攻击伤害、是否触发防御投；② 攻击建立时 `isDefendable` 从哪里决定（如 ability/variant tags、shared helper、choice effect patch、`ATTACK_MADE_UNDEFENDABLE`）；③ 真实流程里是否真的会或不会打开防御窗口；④ 若是“选择后才转为不可防御 / 直接结算 / 附属目标伤害”，必须验证选择解决前后时序都符合合同。缺任一项，不得写“不可防御已实现”或“防御入口正确”。
- **一句话多效果不得合并验收（强制，通用）**：真相源中同一句或相邻句同时包含“触发 X / 改为 Y / 额外 Z / 而不是 / 直到 / 每回合一次 / 否则 / 其余 / 任意顺序”等多个语义时，必须拆成多个验收项。测试只覆盖其中一个效果时，只能证明该子句；不能因为主效果成功就顺带判定替代入口、额外触发、状态清理或例外语义也通过。
- **句号分句不得默认脑补 `if you do`（强制，通用）**：当真相源写成两个独立分句/句子（如“做 A。做 B。”），且第二句前没有 `if you do / 若如此 / 以此法 / then if` 等显式依赖词时，审计与实现都**不得**默认把 B 绑定为“A 必须最终成功后才结算”。必须先把两句分别拆成子句，再核对是否存在明确的条件连接词、代词回指或规则书术语证明 B 依赖 A 的成功结果。允许例外：文本明确写了“若如此”“如果你这样做”“若其以此法被……”“否则”等依赖连接；最低证据：① 真相源原文 ② 子句拆分表 ③ 依赖词是否存在的逐字说明。缺任一项，不得把“句号后的第二句”实现成隐式条件效果。
- **代表链只能证明共享链路，不能替代对象语义（强制）**：真实入口 E2E、共享槽位、共享 handler、共享 resolver、共享奖励骰 UI 只能证明“这段共享链路曾被某个对象走通”。它不能自动证明另一个对象的数值、骰面映射、升级差异、替代语义、分支限制也正确。若两个对象只共享入口而不共享完整语义，证据必须分别落到各自对象行；最多只能写“共享入口已由代表链证明，对象特有语义仍待补”。
- **共享链判等后不得重复深审，但必须登记复用依据（强制）**：当多个对象已经证明共用同一条共享链路，且这轮核对确认它们在入口类型、上下文携带、资源消耗、主效果类别、收口/清理语义上都等价时，后续对象可以复用同一条 L3/L4 代表链，**不需要把完全相同的真实入口或截图再跑一遍**。但每个对象仍必须保留独立矩阵行，并明确写出：① 复用的是哪条共享链/代表对象；② 为什么判定等价；③ 本对象特有语义还有没有额外差异待补。缺少这三项时，不得把“避免重复审计”当作跳过留档的理由。
- **共享链路“仅配置不同”判定门禁（强制）**：只有同时满足以下条件，才允许把对象 B 复用对象 A 的 L3/L4 深审结果：① 同一 handler / resolver / interaction family / finalize 链路；② 同一触发时机与窗口；③ 同一资源消耗与使用限制模型；④ 同一候选生成与 skip/拒绝路径；⑤ 同一流程态与清理语义；⑥ 差异仅存在于静态配置值，例如 `defId`、数值、文案、图集索引、目标筛选参数。只要对象 B 比对象 A 多出新的分支、排序、多选、reaction、deferred、替代结算或清理差异，就必须独立做到对象级 L3/L4，不得继续说“同链路只是配置不同”。
- **“只差配置”必须按共享链逐项判等（强制）**：只有当对象之间共享同一真实入口、同一 validator / handler / resolver / reaction session、同一资源消耗与收口清理，差异仅剩 `id/名称/文案/数值/目标枚举/筛选参数` 这类配置项时，才允许把它们归为“同链路仅配置不同”。只要还存在额外子句、不同阶段、不同可选/强制语义、不同后续触发、不同队列窗口、不同状态写入点或不同拒绝路径，就必须分开补对象级证据，禁止继续借“看起来差不多”复用代表链。
- **批次 L4 必须产出共享链判等矩阵（强制）**：凡当前任务范围是“新派系 / 新英雄 / 一整批对象全面审计 / 同类对象补审”，且你准备在最终口径里复用代表链或声明“剩余只差 L4”，evidence 里必须单列一张 `L4 共享链判等矩阵`。每个对象至少写明：① 对象名；② 共享链名称或 family；③ 代表对象；④ 是否满足“仅配置不同”；⑤ 判等依据；⑥ 本对象剩余差异/残余风险。没有这张矩阵时，不得把“L3 都有了”升级成“整批只剩治理尾巴”或“已全面审计完成”。
- **状态家族 completion audit 不得只停在“状态已写入”（强制）**：凡当前范围内有多个对象写入同一状态/token，或同一新英雄/新派系存在一组状态家族，evidence 必须为每个状态至少列出：① 写入 seam（如 direct `grantStatus`、`customAction`、`choiceResolved`、被动/阶段钩子）；② 共享消费者（如 stack limit、accept/decline gate、upkeep、`passiveTrigger`、cleanup、transfer、response gate）；③ 已验证的代表入口；④ 当前不能互相外推的差异。没有这张 `写入 seam -> 消费点 -> 清理/后续` 对照表时，不得因为“多张牌都能写这个状态”就把该状态家族升级成 `L4` 或“只差治理尾项”。
- **升级/替换链不得只审“升级牌壳”（强制）**：凡对象通过 `replaceAbility`、升级牌写槽、双面切换能力集或类似“先替换定义，再跑新定义”的方式生效，审计必须拆成两层：① 升级/替换壳是否成立（打牌、扣费、离手、`abilityLevel` / `upgradeCardByAbilityId` / 能力集切换是否正确）；② 被替换后的能力 seam 是否成立（新的 `trigger / variants / customAction / tags / postDamage continuation` 是否真实收口）。只证明“升级牌写进升级槽 / 角色翻面成功”最多算壳层通过，不能自动证明 replacement ability 本体已经完成 `L4`。
- **奖励骰/bonus overlay 不得只审“特写壳”（强制）**：凡多个对象都经过 `rollDie`、`BONUS_DIE_ROLLED`、奖励骰特写或 `displayOnlySettlement`，审计必须继续拆出：① 特写壳是否真实打开/关闭且流程可继续；② 不同骰面最终落到哪类消费者（`drawCard / grantToken / damage / status / extraAttack / selectPlayer / damageShield`）；③ 是否还有 `postDamage`、额外进攻、选择确认或其它 continuation。只看到“奖励骰特写出现了”或“写了 `BONUS_DIE_ROLLED / displayOnlySettlement`”不能把兄弟对象判成同一 `L4` family；真正的判等边界必须落在后续消费者与 continuation。
- **同类已修 bug 必须扩审兄弟对象（强制）**：一旦某个对象因完整流程审计发现实现错误，必须立刻查找同游戏/同系统/同新增批次中共享相同时机、handler、resolver、UI 入口或资源合同的兄弟对象，并把这些对象纳入同轮重审。禁止只修用户点名对象后继续保留同类漏审。典型：防御技能 effect timing 修复后，必须扩查所有新增防御技能是否也能被防御 resolver 消费；资源图集合同修复后，必须扩查所有共享消费者是否被新素材反向覆盖。
- **框架消费合同必须反向审计（强制）**：审计不能只从数据定义、卡图文字或 helper 命名正向推导“应该会执行”，还必须从实际 resolver / system / pipeline 消费点反查字段合法性。任何 `timing`、`phaseId`、`customActionId`、`status timing`、`command payload`、`targetType`、资源 atlas/index 等字段，只要是被共享系统按枚举值消费，就必须证明该字段值会被对应消费点读取。若类型允许的值多于某个消费点实际处理的值，必须建立合同测试或显式白名单；禁止让“定义存在但消费点静默跳过”的对象通过审计。典型：DiceThrone 防御 resolver 只消费 `withDamage/postDamage`，防御技能 effect 若写成 `immediate/preDefense/default`，即使 customAction handler 单测通过，也不能视为防御技能已实现。
- **共享枚举消费必须列“声明值 -> 消费点 -> 证据”对照（强制）**：只要对象语义依赖共享框架枚举或消费合同（如 `timing`、`phaseId`、`customActionId`、`resolutionMode`、`targetType`、骰面/符号映射、资源槽位映射），审计文档必须至少写清三件事：① 声明层实际填了什么值；② 哪个 resolver/system/helper 在何处消费该值；③ 哪条 L2/L3/L4 证据证明这个消费点真的按该值执行。没有这张对照，就不能把“定义里有这个字段”写成“框架已正确消费”。
- **选择后改写攻击合同必须单独验收（强制，通用）**：若某对象在 `CHOICE_RESOLVED`、token 响应、奖励骰分支或 continuation 里才决定“变为不可防御 / 改目标 / 改伤害范围 / 跳过防御 / 直接收口”，必须把“选择前中间态”和“选择后最终态”拆开审。最低证据：① 选择前 `pendingAttack` / phase / interaction 处于预期中间态；② 选择后共享合同确实被改写（如 `ATTACK_MADE_UNDEFENDABLE`、`choiceEffect` patch、目标快照更新）；③ 真实入口下不会误开旧窗口或漏掉后续收口。禁止把“最终结果看起来对”当作选择链无 bug 的替代证据。
- **重投/再投/奖励骰次数语义必须拆成独立子句（强制，通用）**：凡真相源出现“可重掷/可再投/重投其中 N 颗/至多 N 次/奖励骰可重投/防御掷可重投”等文本，审计与实现都必须把“次数/上限”视为独立子句，不能并入主伤害或主结算一并带过。evidence 至少要写明：① 声明层用哪个字段表达该上限；② 哪个共享 reducer / resolver / settlement / commandValidation 真正消费了这个字段；③ 哪条证据证明到达上限后 UI 或命令会被阻止。只证明最终伤害、token 或状态正确，不能替代“可再投几次”已经实现。
- **“还能再投几轮”与“每轮最多重投几颗”不得混成同一合同（强制，通用）**：凡真相源同时出现“可重掷至多 N 颗 / 可重掷其中 N 颗 / 可重投 1 次 / 可以同一颗重掷多次 / 奖励骰可再掷”等语义，必须先拆成两类独立合同：① 总共还能触发几轮重投；② 每一轮最多能重投几颗骰子。evidence 至少要分别写清：`rollLimit`、`selectCount`、`maxRerollCount`、`rerollDieLimit` 中到底是哪一个字段承载了哪一层语义；哪个共享消费者真正读取了它；若当前对象不使用其中某个字段，也要显式写 `N/A`，禁止只看到一个“重投上限字段”就宣称整条卡面语义已实现。
- **真实 UI 可操作性不得被“触发成功”替代（强制，通用）**：对象语义若依赖玩家在真实界面继续做“保留/重掷/再投/确认奖励骰/结束防御”等动作，审计必须把“入口已出现”和“入口仍可继续操作”分开留证。L2 合同测试最多证明共享字段和最终状态；若要写玩法收口，L3 必须额外证明真实 UI 中按钮、可选骰子、确认态或禁用态与规则上限一致。像“防御技能已进入 defensiveRoll”“奖励骰 prompt 出现了”“custom action 被调用了”都不能单独证明玩家真的还能按规则继续重投。
- **系统交互存在不等于真实 UI 可点（强制，通用）**：凡实现创建了 `sys.interaction.current`、simple-choice、prompt、状态横幅或等价系统交互，审计必须继续证明玩家在真实 Board/PromptOverlay/StatusBanners/手牌区/棋盘区能看见并点击对应选项，且点击提交的是同一份 `optionId/value`。只断言系统状态里有交互，不能证明 UI 链路可用；若没有可见按钮、候选卡、地图高亮或列表项，必须判为 UI 交互链路未收口。
- **每回合一次按钮能力必须审使用后可用态（强制，通用）**：凡技能/卡牌写有“每回合一次 / once per turn / usesPerTurn”，且真实入口是按钮或按钮后目标选择，审计必须同时证明三件事：① 首次使用后权威使用次数或等价资源已写入；② 真实 UI 按钮在同一回合内隐藏、不可见或禁用；③ 旧按钮、重复点击或重放 `ACTIVATE_ABILITY` 不会再次打开目标选择或二次结算。只证明第一次效果正确，不能把该能力判成 L3/L4 收口。
- **`fixed-view / owner-sensitive / off-turn` 场景不得把不可点直接判成“未实现”（强制，通用）**：凡真实入口跑在固定视角、本地双页、旁观/非当前回合、私有 prompt、response window 或 owner-only UI 上时，只看到 `disabled UI`、按钮点不动、某页没入口、点击后无反应，还不能直接下“能力没实施 / shared field 没消费”的结论。审计必须至少先核对：① 命令实际用哪个 `playerId dispatch` 发出；② `interaction.current.playerId` / 当前 prompt owner 是否就是当前页；③ `responseWindow.currentResponder` 与 `pendingDamage.responderId` 是否要求另一个响应者；④ 页面是否启用了 `followCurrentTurnPlayer` 或其他自动跟随当前行动方逻辑；⑤ 真实 DOM 命中层是否被视觉层、3D 层、overlay 或相邻元素截走。只有排除“错视角 / 错 owner / 错 responder / 点击命中层异常”后，才允许把红点归因为实现缺失。若 harness 直接发命令可通过、但真实 UI 点击失败，必须优先记为 UI 命中链问题，而不是技能未实现。
- **direct E2E / 真实入口 closeout 必须回到最终权威状态（强制，通用）**：凡对象经过变体选择、奖励骰、防御重投、response window、pendingDamage、deferred/finalize 或其他中间态链路，L3/L4 证据都不能停在 `prompt/modal 出现`、`pendingAttack.sourceAbilityId 命中`、`isDefendable 改了`、`pendingBonusDiceSettlement 存在` 这类中间字段。至少要继续证明：① 玩家从真实入口完成整条链；② 最终 HP/token/手牌/资源/状态等权威结果正确；③ `pendingAttack / pendingDamage / pendingBonusDiceSettlement / interaction` 等临时态按预期清空或进入下一合法阶段。缺任一项，只能写入口证据或中间态证据，不得写玩法收口。
- **`simple-choice / CHOICE_RESOLVED` 不得用 forged reducer 事件冒充完整验证（强制，通用）**：当对象效果依赖 `SYS_INTERACTION_RESOLVED -> CHOICE_RESOLVED -> choiceResolvedEventHandler/followup events` 这条链路时，直接手造一个 `CHOICE_RESOLVED` reducer 测试，最多只能证明锚点校验、通用 token/status 增量或清理逻辑，不能自动证明 followup handler 真的生效。L2 至少要满足其一：① 走带有当前 choice 锚点的真实 `SYS_INTERACTION_RESOLVED` 事件链；② 显式调用已注册的 `choiceResolvedEventHandler`，并同时证明 source/customId/当前锚点一致。若对象还有真实弹窗按钮或 simple-choice UI，L3 仍必须补真实点击后的最终权威状态，不能只看 `CHOICE_REQUESTED` 或 reducer 绿灯。
- **测试不得吞掉未预期命令失败（强制）**：使用 GameTestRunner、E2E helper 或任何批量命令 runner 时，除非用例目的就是验证失败路径，否则必须断言所有关键命令成功或 `actualErrors` 为空。禁止只断言最终 HP/手牌/阶段而忽略中途 `ability_not_available`、`invalid_target`、`validation_failed` 等错误；这类测试只能证明“最终状态碰巧相同”，不能证明真实链路执行过。
- **E2E 场景真值必须先过 `defId` 预检（强制）**：凡是通过状态注入或预置棋盘构造场景的审计 / E2E，用到的 `defId` 必须先确认真实存在；由假 `defId` 导致的失败必须单列为“场景真值错误”，禁止混写成玩法实现 bug。
- **reaction session 不得被单测观察面替代（强制）**：如果真实入口里会经过 `smashup_reaction_choose`、response window 或其他中间反应态，就必须在 L4 审计里单独核对并留证；不能因为单测里看起来是“直接进入后续提示”就跳过中间流程态。
- **数据驱动优先，禁止硬编码（强制）**：实现任何游戏机制时，优先将规则/配置/效果做成可枚举数据，由引擎解析执行。禁止用 switch-case/if-else 逐个硬编码技能/效果/卡牌逻辑。新增同类机制时应提取抽象（通用 handler/executor/模板），而非复制粘贴再改参数。
- **测试用固定值代替随机（强制）**：测试中涉及随机数（骰子、抽牌、洗牌等）时，必须使用固定值或可控的伪随机序列，禁止依赖真随机。做法：① GameTestRunner 的 `random` 参数传入返回固定值的函数 ② 使用 `applyDiceValues` 等调试面板 API 注入预设值 ③ 测试 setup 中直接构造确定性初始状态。目的：确保测试结果可重复、可调试、不因随机波动导致偶发失败。
- **多次随机/多骰 E2E 必须使用序列策略（强制）**：如果一次交互会连续消费多个随机值（例如防御掷 3 骰、攻击修正投 5 骰、奖励骰后再分支），E2E 注入必须使用 `randomPolicy.mode='sequence'` 或等价队列，并断言每个关键骰面分支都被消费。`fixed` 模式只适合“所有随机都应同值”的场景；禁止传入数组后仍使用 `fixed`，这会把多骰路径误测成同一个骰面重复。
- **同类测试去重**：多个实体共享同一 handler/executor/reducer 分支时，只需一个代表性行为测试，其余用契约测试覆盖数据定义。≥5 个同类用 `test.each`。仅当条件分支/交互路径/边界行为/交叉影响不同时才需独立测试。
- **事件发射 ≠ 状态生效**：必须断言 reduce 后的最终状态，禁止只测注册/写入就判定"已实现"。
- **多系统协作必须断言所有相关系统状态（强制）**：涉及多个引擎系统协作的功能（如响应窗口+交互系统、流程系统+交互系统），测试必须同时断言所有相关系统的状态字段，不能只断言其中一个。典型：测试只断言 `sys.interaction.current` 存在但不断言 `sys.responseWindow.current` 仍打开 → 测试通过但功能实际无效；若设计允许 `responseWindow + simple-choice` 并存，还必须继续断言响应命令仍可通过，而不是只检查两个状态“都在”。
- **改实现就必须改对应测试（强制）**：任何会改变规则语义、交互链时序、事件类型/字段、状态结构或校验逻辑的实现修改，都必须同步更新/新增能证明该变更的测试（单元/行为/E2E 选其适配者）。如果你本轮修的是“合并 PR 引入的业务变更”，必须把旧断言升级为新口径；禁止让测试长期停留在旧语义，靠“临时跳过/注释/放宽断言”糊过去。
- **`prompt -> onResolve -> helper` 不得只测 prompt 出现（强制）**：凡对象实现经过 runtime prompt、simple choice、reaction choose、branching choice、custom action resolve 或其他分段 callback seam，测试与审计都不能停在“prompt 建出来了 / 候选列表对了”。至少要补 1 条真实 `respond/resolve` 路径，验证 helper / resolver 真的执行到了最终权威状态；若规则存在可选拒绝/取消/空选，也必须补 1 条否定路径。像“把内联事件改成 shared helper”这类重构，旧测试如果只覆盖 prompt 创建，视为证据失效，必须升级到结算层。
- **私有/owner-only prompt 必须补恢复态验证（强制）**：凡 prompt、reorder editor、reaction 窗口或 extra-play 入口只应归某一玩家所有，L3/L4 不能只证明“第一次出现时 owner 正确、guest 没看到”。至少要补 1 条真实恢复态链（优先 `hidden -> visible -> manual-resync`），同时断言：① owner 页恢复后仍保有同一交互或同一继续入口；② 非 owner 页不会接管 prompt、不会错误出现 waiting overlay；③ 最终收口后双方页都无残留私有 UI。没有这条恢复态证据时，只能写 owner-only 首次归属已验证，不得写该私有 prompt family 已收口。
- **审图必须区分“合法等待层 / 真实候选 / 旧残留”三类（强制）**：当截图里看起来“有很多选项”或“页面还挂着一个 overlay”时，审计不能直接下“选项太多 / UX 不合格 / 还残留旧层”的结论，必须先把当前画面分类成三类之一：① 合法候选卡本体；② 合法等待层（例如 after-scoring / me-first / owner-only waiting）；③ 旧 spotlight / reveal / prompt 残留。只有第③类才能作为 UX 脏态或回归结论。若组件可能以 hidden mounted 方式存在，审计/测试必须以 `visible/hidden/detached` 语义判定，禁止把 `count=0` 当成“不存在”的唯一证据。**若当前交互是固定编辑器/重排器/双列表分配器，截图里的对象卡面默认按“被编辑对象本体”审，不得直接当成并列动作按钮统计；只有真实动作控件、确认/跳过控件和第二步入口才算“选项数量”。**
- **`skip / 让过` 后必须继续区分“合法后续 prompt”与“旧层残留”（强制）**：当当前动作只是“放弃这一次机会”时，测试和审图不能机械要求 `skip` 后立即 `interaction.current == null`。如果规则链后面还存在合法 follow-up reaction / response / afterScoring prompt，那么 `skip` 后继续出现下一层 prompt 本身是允许的；真正要判失败的是：① 旧 prompt 的标题、按钮、计数、浮动操作栏或辅助 overlay 仍与新 prompt 同屏残留；② 候选被强制执行；③ 控制权串到错误页面。凡修这类链路，至少要补一条“`skip` -> 下一层 prompt -> 最终收口”的完整断言，而不是只断言 `skip` 当下那一帧。
- **shared helper 替换必须审 seam 依赖泄漏（强制）**：当代码从手写事件构造切到抽牌 helper、随机选择 helper、掷骰 helper、排序 helper、伤害结算 helper 或其他共享 primitive / helper 时，除了验证行为不变，还必须审查 callback seam 本身是否新增了 `random`、`timestamp`、`matchState`、`interactionData`、`actorId` 等运行时依赖。若声明层对象本身只表达“抽牌/摸牌/结算/造成伤害/重掷/选择目标”等效果意图，就不应再让声明层手工透传底层 runtime 依赖；优先收敛到接受整份 runtime args/context 的 helper，避免解构漏参型回归。
- **runtime seam 职责边界必须单向（强制）**：所有游戏通用地把实现分成三层看：① 声明层/规则层，只表达效果意图与业务参数；② runtime seam 层，负责把本次交互、时间戳、随机数、状态快照等运行时上下文打包传递；③ primitive / helper 层，负责真正消费这些运行时依赖并产出权威事件或状态。禁止让声明层跨过 seam 直接拼底层 runtime 依赖；也禁止把“牌库空则洗回再抽”“多骰顺序消费”“伤害结算前后窗口”等 primitive 语义上浮到单个业务对象重复实现。
- **回归修复必须先做提交归因（强制）**：凡是用户明确反馈“回归 / 又坏了 / 以前能用现在不能用 / 大量回归”，修复前必须先用 `git blame`、`git log -S/-G`、必要时 `git bisect` 定位疑似引入提交，并记录该提交改动了哪条语义、哪条测试/审计结论失效；禁止只凭当前代码猜根因后直接改。若无法在合理时间内锁定单一提交，必须汇报候选提交范围、排除依据和下一步最小验证。
- **UI 回归必须先锁“交互载体”与“提示壳层”角色（强制）**：当用户反馈“以前是手牌直点 / 棋盘直点 / 中间有个弹窗 / 现在变成另一种选择方式”时，回归排查必须先分别写清：① 真正承接点击的是哪个现有对象（手牌、基地、随从、PromptOverlay、system interaction）；② 中间弹窗/提示条/MeFirst/等待框只是提示 UI，还是实际交互入口。禁止把“屏幕中间有弹窗”直接等同于“交互承接发生在中间弹窗”；禁止在没锁定这两个角色前就回滚或新做一层中间选择 UI。最低证据至少包括：旧截图/旧 evidence/旧实现三者之一，以及当前实现中谁在消费 `optionId` / 点击事件 / `targetType` 的定位结果。
- **交互语义必须单一真相（强制）**：凡涉及“候选生成 / UI 高亮或置灰 / 用户点击提交 / validator / resolver / reducer 生效”的链路，必须明确唯一权威来源：要么 UI、提交和 resolver 都消费同一份 `PromptOption`/`optionId`，要么全部通过同一个 `validate(...)`/查询 helper 派生。禁止 UI 用一套近似条件高亮、handler/resolver 再用另一套条件拒绝；禁止用 `defId`、`baseIndex`、标签、局部状态等弱标识替代真实 option 的 `uid`/稳定标识；禁止“看起来可选但提交后无效”的双重/多重真相。若确实需要多层校验，后层只能做活体性/权限复核，不能引入与候选来源不一致的新业务口径；测试必须至少覆盖：候选出现、UI/命令选择同一 option、响应成功、最终权威状态变化。修复任一双重真相 bug 时，必须扩审同 targetType / 同 UI 组件 / 同 helper 的其他调用点，不能只修两张牌。
- **交互入口语义必须审计（强制）**：凡规则、卡牌、技能或按钮描述包含“选择 / 移动 / 打出到 / 从...到... / 另一个 / 你的 / 敌方 / 任意 / 至多 / 可以 / 然后 / instead / then / choose / move / target”等用户动作链，审计时必须拆出**第一用户选择对象**，并核对 UI 入口、command payload、validator、resolver/handler 消费字段是否同一语义。典型检查：① 描述动作链是“选择 A → 对 A 做事 → 再选择 B”，不得把 B 误当前置入口；② 直接入口字段（如 `playNeedsBase` / `playNeedsMinion` / `targetType` / `position` / `targetPlayerId`）必须与第一选择对象一致；③ 第二步及后续选择必须携带第一步上下文（如 `sourceUid`、`sourceBaseIndex`、`originPosition`、`selectedCardUid`、`selectedPlayerId`），不得靠“当前基地 / 第一个匹配对象 / 当前 UI 选中态”猜；④ 若某能力选择“任意数量 / 至多 N / 可选执行”，UI 多选、validator、resolver 的数量与 skip 语义必须一致。该维度是通用审计门禁，不得只按某张卡或某个游戏写特例关键词。
- **升级/替换 family 必须拆“升级牌壳”和“被替换能力 seam”（强制）**：凡对象通过 `replaceAbility`、升级牌、双面能力集切换或其它“先替换定义，再由新定义继续运行”的方式生效，审计时必须分两层写证据：① **升级牌壳/替换壳**是否真实完成打牌、扣费、离手、`abilityLevel` / `upgradeCardByAbilityId` / 能力集切换写入；② **被替换后的能力 seam**是否真实完成 `trigger / variants / customAction / tags / postDamage continuation`。禁止只因为“升级槽写对了 / abilityLevel 变了”就把整条升级链判成 `L4`。
- **奖励骰/特写 family 必须拆“展示壳”和“后续消费者 seam”（强制）**：凡多个对象都走 `rollDie`、奖励骰 overlay、`BONUS_DIE_ROLLED`、`displayOnlySettlement` 或类似 bonus 特写，审计时必须继续回答：① overlay 是否真实打开、关闭并允许流程继续；② 结果最终落到哪类消费者：`drawCard / grantToken / grantStatus / bonusDamage / damage / extraAttack / selectPlayer / damageShield`；③ 是否还存在 `postDamage`、额外进攻、选择确认等 continuation。禁止只因为“都能看到奖励骰特写”或“都发出了 `BONUS_DIE_ROLLED`”就把它们登记成同一 `L4` family。

#### 交互入口语义矩阵（强制，通用）

> 本矩阵是上条“交互入口语义必须审计”的执行表。它适用于所有游戏、卡牌、技能、按钮和 UI 动作，不允许写成某个游戏、某张卡、某个字段名的特例。

审计对象只要包含玩家选择、移动、打出、交换、替代、跳过、排序、数量选择或后续连锁，就必须在 evidence 里至少写出下列字段：

| 矩阵项 | 必填问题 | 必查实现层 | 常见错误 |
| --- | --- | --- | --- |
| 文本子句覆盖 | 真相源能拆成哪些独立子句？每个子句是否都有编号和证据？ | 图片/规则书/OCR、i18n、录入核对、evidence clause table | 只把整张卡写一行，主效果测过后漏掉第二句“特殊/改为/否则/其余”。 |
| 第一入口对象 | 玩家第一下应该选什么：base / minion / card / player / zone / position / button / none？ | UI 可选态、command payload、validator、handler 首参 | 把“移动 A 到 B”的 B 当第一入口；把目的地当源对象。 |
| 目标归属 | 目标属于 self / opponent / any / active player / source owner / chosen player？ | 静态字段、候选 helper、validator、handler 二次复核 | UI 允许任意目标，handler 私下只接受己方目标。 |
| 数量语义 | one / exact N / up to N / any number / all / optional skip？ | Interaction `multi`、确认按钮、skip option、validator 数量检查 | “至多”被实现成必须选满；“任意数量”没有空选/跳过。 |
| 动作链顺序 | 文案能否拆成 A → B → C？后一步是否依赖前一步？ | `continuationContext`、interaction queue、events 顺序、reducer 最终态 | 后续目标提前成入口；第一步上下文丢失后靠当前状态猜。 |
| 上下文携带 | 后续步骤需要哪些稳定字段：sourceUid / sourceBaseIndex / sourceDefId / selectedCardUid / selectedPlayerId / originPosition / baseDefId？ | prompt data、handler context、deferred/session/frame | 只存 baseIndex，基地替换/清场后命中错误对象。 |
| 可选/自动执行 | 文案是“可以/you may/choose”还是强制？是否允许玩家拒绝？ | skip/confirm UI、autoResolveIfSingle、handler 空结果 | 把“你可以”自动执行；把“必须”错误做成可跳过。 |
| 排序/选择权 | 文案要求“任意顺序/选择其中一张/选择其余”吗？ | order interaction、deck/discard reducer、测试断言最终顺序 | 自动选第一张；按原顺序回顶，吞掉玩家排序权。 |
| 单一真相 | UI、validator、resolver、reducer 是否消费同一份 option / helper / 字段？ | shared helper、optionId、payload schema、领域校验 | UI 高亮一套条件，提交后 validator/handler 用另一套条件。 |
| 收口状态 | 交互解决后是否清空 pending，是否进入下一阶段/后续触发？ | `sys.interaction`、triggerQueue、responseWindow、finalState | prompt 关闭但触发队列残留；后续 deferred 丢失。 |

强制输出格式（审计文档逐对象至少要有这些列）：

```markdown
| 对象 | 动作链 | 第一入口 | 字段/命令 | 目标归属 | 数量/可选 | 上下文携带 | 验证层级 | 结论 |
```

#### 技能完整流程矩阵（强制，通用）

> 本矩阵用于所有游戏的技能、卡牌、Token、状态、被动按钮和攻击修正。它补充“交互入口语义矩阵”，重点防止只测“可触发”却漏掉真实执行、后续收口或交叉规则。

每个可执行对象在 evidence 里必须至少列出下列字段；不适用项必须写 `N/A` 和理由，不能留空：

| 矩阵项 | 必填问题 | 必查实现层 | 常见错误 |
| --- | --- | --- | --- |
| 真相源语义 | 图片/规则/用户故事到底要求什么？时机、目标、伤害/资源/状态数字是什么？是否已拆成 `C1/C2/C3...` 子句？ | 图片、规则书、录入核对、用户故事、子句表 | 只按旧实现猜；把图片上的主阶段牌录成投掷修正；整张卡一行 pass 导致漏掉第二句。 |
| 子句实现映射 | 每个子句分别落在哪个字段、handler、resolver、reducer、UI 入口或清理逻辑？ | 数据定义、command schema、validator、handler、pipeline、reducer、UI | 只实现主效果，漏掉“改为打出”“否则放回”“每回合一次”“其余任意顺序”。 |
| 静态定义 | `type/timing/trigger/effects/cost/tags/previewRef` 是否能独立解释对象行为？若 `effects: []` 但运行时已由 helper / execute / abilityResolver / systems 旁路消费，是否已有“旁路消费证据映射”？ | 数据定义、注册表、i18n、图集索引、旁路消费者证据表 | 运行时靠旁路硬编码，定义层是空壳或错误时机；或把空效果简单误判为未实现，漏掉实际消费者。 |
| 候选生成 | 什么时候出现在可用列表？骰面/阶段/资源/状态条件是否完整？AI legal-actions、auto-continue/watchdog 是否消费同一合法动作真相？ | rules/helper/canActivate/validator、AI legal-actions、auto-continue/watchdog | UI 高亮条件和 reducer 接受条件不一致；AI 只看到 `advance-phase` 并提前结束阶段。 |
| 入口与贴图 | 玩家点哪里？图像槽位、按钮、卡牌、token 与对象 ID 是否一一对应？ | UI 组件、slot mapping、data-testid、截图 | 新对象素材规格不同却复用旧槽位；打 A 显示成 B。 |
| 命令与执行 | 点击/打出后发什么命令？handler 是否消费同一个对象 ID？ | command payload、move、handler、reducer | 点击 prompt 成功但最终执行的是另一个能力。 |
| 消耗与限制 | CP、卡牌、Token、once-per-turn、堆叠上限何时变化？失败/取消是否回滚？ | reducer、resource/token systems、event log、UI button state | 效果生效但未消耗；取消也扣费；每回合一次效果已执行但按钮仍显示或二次打开选择。 |
| 主效果 | 伤害、治疗、抽牌、改骰、加伤、状态、token 是否写入权威状态？ | effects、attack resolver、deck/resource reducers | 只发事件不 reduce；只显示徽章不改伤害。 |
| 分支/否定路径 | 选择、可选、至多、跳过、失败骰面、不可防御、防御免疫等是否覆盖？ | choice handlers、token response、defense resolver | 只测成功分支；不可防御后仍执行防御。 |
| 后续与清理 | pending/interaction/responseWindow/triggerQueue 是否清空？阶段能否继续？ | systems、flowHooks、postProcess、phase advance | prompt 关了但 pending 残留，后续阶段卡死。 |
| 证据等级 | L1/L2/L3/L4 分别有什么证据？缺口是否降级写明？ | Vitest、E2E、截图、evidence | 用一条代表 E2E 外推全部技能。 |

强制输出格式（每个可执行对象至少一行）：

```markdown
| 对象 | 真相源 | 静态定义 | 候选/入口 | 命令/执行 | 消耗/限制 | 主效果 | 分支/否定 | 后续清理 | 证据层级 | 结论 |
```

最低门禁：

1. 只证明“可触发 / 可高亮 / 可点击”最多算入口证据，不能证明对象流程正确。
2. 每个对象至少必须有 L1 完整流程矩阵；任何有运行时效果的对象必须至少有 L2 权威状态验证，或明确标为未覆盖。
3. 有真实 UI 入口的对象若要写“玩法已验证”，必须有 L3 证据；无 UI 的自动/被动对象必须写明为什么没有玩家入口，并用 L2/L4 证明后续清理。
4. 涉及响应窗、防御、不可防御、奖励骰、跨阶段或回合结束的对象必须单独覆盖分支/否定路径；代表性“能触发”不能替代完整流程。
5. 涉及 AI、自动玩家、自动跳过、watchdog 或 phase gate 的对象，必须至少补一条“存在合法动作时不只剩结束阶段/不会提前推进”的消费者断言；人工 UI 或 executor 单测不能替代。
6. 新增派系 / 新角色 / 新英雄 / 当前标记为实施中的批次中发现一处漏审并确认属于审计维度缺口时，补审范围默认升级为该批次对象全集；如果实施中批次包含多个派系 / 角色 / 英雄，必须先按配置真相源列出全集，每个对象都标明“命中该维度 / 不适用该维度”的原因，不能只补用户点名对象或单个派系。
7. 审计发现旧 evidence 曾把触发证据写成流程收口时，必须回写旧文档降级，并在新文档列出替代证据或残余缺口。

最低门禁：

1. 任何“移动 A 到 B / 交换 A 和 B / 从 X 到 Y”的对象，必须证明 A 与 B 的入口顺序没有反转。
2. 任何出现“你的 / 对手 / 其他玩家 / 任意玩家”的对象，必须证明 UI 候选、validator 和 handler 归属一致。
3. 任何出现“可以 / 至多 / 任意数量 / 任意顺序”的对象，必须证明 skip / multi / order 语义存在；若没有 UI，必须写明自动执行的规则依据。若该对象在有合法候选时仍允许玩家拒绝执行，测试必须补一条“合法候选存在但选择跳过/空选后最终状态不变”的否定路径，不能只用成功执行路径证明规则正确。
4. 任何多步交互必须有上下文携带字段；只靠“当前选中 / 第一个匹配 / 当前基地”的实现不得通过审计。
5. 如果第一入口已经由命令 payload / UI 点击对象确定，handler 必须直接消费该入口；不得再创建同 targetType 的二次选择 prompt 让玩家重复选择同一入口对象。
6. 只跑静态测试最多算 L1；只有行为测试证明最终权威状态变化才算 L2；只有真实入口 E2E + 看图证据才算 L3。
7. 如果交互本身只是在改写 deferred event、post-scoring frame、response continuation、finalize payload、待补发事件或其他“收口后才真正生效”的中间态，那么看到 prompt、点掉 prompt、甚至看到局部临时状态变化，都不足以收口。必须继续证明：交互解决后 deferred/finalize 确实被消费，最终权威状态真的变化，且后续链没有被吞掉。像“替换基地 + 重排剩余基地 + 继续后续 afterScoring 交互”这种链，至少要覆盖 `prompt 出现 -> 玩家响应 -> finalize 消费 -> 最终状态 -> 后续链继续/收口`。
8. 如果对象复用旧 prompt / 旧 simple-choice / 旧 response window，但本对象新增了独有触发时机、候选过滤、特殊模式、是否执行、跳过语义或结算后状态，只能写成“旧壳复用的新对象级交互链”。它不一定是新的 UI 类型，但仍必须有本对象 L2 行为证据；若玩家真实入口可见，则还必须补 L3 E2E 与截图，不能只借旧壳代表链。
