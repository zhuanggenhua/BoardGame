# 交互弹窗一闪而过调试归档

本文是旧交互弹窗排查指南的精简归档，不作为当前交互系统规范。当前交互行为以现有 `ChoiceRequest`、`InteractionSystem`、游戏实现和测试为准。本文保留当时的问题形状、日志模式和排查顺序。

## 当时问题

交互弹窗短暂出现后立刻消失。现实后果是玩家还没来得及选择，交互就被解决、替换或清空，表现为“按钮一闪而过”“弹窗刚出来就没了”。

## 当时添加的日志

旧指南记录过两个重点日志入口：

- `queueInteraction`：记录交互被创建、入队、替换或跳过。
- `resolveInteraction`：记录交互被响应、清理或完成。

当前日志入口可能已经改名；排查时应寻找现实含义相同的“创建交互”和“解决交互”记录。

## 排查顺序

### 1. 复现并看完整日志链

先确认同一次玩家动作里是否出现：

- 创建了交互。
- 交互 ID 或来源变了。
- 交互立即被 resolve。
- 交互选项为空。
- 后续能力或系统又改了牌库 / 状态。

不要只看最终 UI 消失；必须找到“谁创建、谁清掉、是否同一个交互”。

### 2. 检查 optionsGenerator

旧问题常见于 `optionsGenerator` 闭包引用了会变化的牌库、手牌或状态。排查点：

- 生成选项时读到的对象是否仍存在。
- 闭包捕获的是旧数组还是当前 state。
- 选项为空时系统是否自动 resolve。
- 同一张牌或能力是否被重复调用。

### 3. 检查交互 ID

旧记录中一个关键症状是交互 ID 从稳定 ID 变成带时间戳的 ID，例如：

```text
robot_hoverbot_0 -> robot_hoverbot_1772270392399
```

这类变化会让系统把本该是同一次交互的内容识别成新交互，或让旧交互的响应落不到正确对象上。

### 4. 检查交互解决时机

重点看：

- 是否在创建后立即进入默认响应。
- 是否被自动跳过。
- 是否因选项为空被清理。
- 是否由其它能力链继续推进时清掉。
- 是否玩家响应到达前，状态版本已经变更。

## 当时已知修复

旧指南记录过一次修复：`optionsGenerator` 闭包引用问题。核心方向是让选项生成读取当前可信状态，或在创建交互时保存必要快照，避免 UI 打开后目标对象已经变化。

## 当时备选方案

旧文档列过两个临时方向，只能在证据确认后使用：

- 使用稳定 `cardUid` 作为交互 ID，避免时间戳导致同一交互身份漂移。
- 在 `queueInteraction` 中检查重复入队，避免同一来源连续创建多个交互。

这些都不是默认兜底；如果当前系统已经有更正式的 Choice Request 身份模型，应优先按当前模型修。

## 需要收集的最小证据

排查报告至少应说明：

- 用户原始操作是什么。
- 第一次创建的交互 ID、来源和候选选项。
- 弹窗消失前发生的 resolve / replace / clear 记录。
- 消失后当前系统状态里是否还有 pending interaction。
- 如果是选项为空，空的原因是对象不存在、过滤过严，还是状态读错。

## 当前使用口径

- 本文只保留历史排查套路。
- 当前修复必须回到真实游戏、真实交互系统和当前测试。
- 不能只用“加防重复”掩盖状态来源错误；如果身份模型或状态生命周期错了，应修源头。
