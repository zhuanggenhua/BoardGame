## Context
首页大厅排序依赖两类信息：游戏注册表里的展示状态，以及后台统计里的真实游玩热度。本次事故中，热度请求实际打到了错误入口，前端失败后回退为空对象，排序再落到固定精选顺序，导致“没人玩”的实施中游戏可以出现在首位。

现有问题不是缺一个 `if`，而是三个 Module 都偏浅：
- 热度加载 Module 的 Interface 只暴露 `Record<gameId, number>`，调用方无法区分“真的没有热度”和“请求失败”。
- 请求入口散落在 hook / 页面里，调用方必须知道哪个路径属于认证入口、哪个路径属于后台入口。
- 排序 Module 返回排序后的游戏列表，但没有暴露排序因子，测试只能看最终顺序，难以及时发现热度、状态、回退顺序哪一层失效。

## Goals / Non-Goals
- Goals:
  - 让前端请求入口成为集中 Module，路径选择和错误模式在同一处可测试。
  - 让大厅热度链路显式表达加载成功、失败、禁用和空数据。
  - 让大厅排序成为可解释 Module，排序结果和排序原因都能被测试。
  - 防止新页面/新 hook 继续复制错误路径拼接方式。
- Non-Goals:
  - 不在本 change 重写整个后台统计系统。
  - 不改变后台 `/admin/stats` 当前响应结构，除非实现阶段发现必须补字段。
  - 不把所有现存后台页面一次性迁移到新请求 Module；本 change 先覆盖首页/大厅和新增代码门禁。

## Decisions
- Decision: 新增 `frontend-api-contracts` 能力，而不是把规则塞进 `admin-dashboard`。
  - Reason: 这次问题发生在普通首页消费后台统计，不是管理员页面本身；真实缺口是前端请求合同与消费状态。
- Decision: 大厅排序 Module 的 Interface 同时支持“排序结果”和“解释结果”。
  - Reason: 商业级防线需要让测试断言“为什么排第一”，而不是只断言某次最终数组。
- Decision: 热度加载 Module 不再只返回 `{}` 作为失败兜底。
  - Reason: 空数据和请求失败现实含义不同，混在一起会掩盖线上故障。
- Decision: 实施中状态优先级高于热度分。
  - Reason: 用户看到的大厅是产品货架，未完成游戏不应靠异常热度或脏数据冲到已上线游戏前面。

## Risks / Trade-offs
- Risk: 一次迁移所有后台请求会扩大影响面。
  - Mitigation: 首批只迁移首页/大厅热度链路，并增加禁止新增散落路径的检查；存量后台页面后续分批迁移。
- Risk: 排序解释因子暴露过多内部细节。
  - Mitigation: 解释因子作为测试和开发态诊断 Interface，不强制进入用户 UI。
- Risk: 热度加载失败可见化后可能暴露现有环境噪声。
  - Mitigation: UI 可继续使用固定排序作为降级展示，但日志、状态和测试必须能区分失败原因。

## Migration Plan
1. 新增集中请求 Module，提供后台统计读取 Adapter。
2. 将首页热度 hook 改为调用该 Module，并返回加载状态。
3. 将大厅排序改为可解释排名 Module，保留现有 UI 调用的简化入口。
4. 补齐合同测试、排序解释测试和首页渲染测试。
5. 增加静态检查或单元测试，阻止首页/大厅新增直接拼后台入口。
