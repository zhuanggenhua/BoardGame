# Design: 山屋惊魂首剧本运行时链路

## Context

当前 `Board.tsx` 已有可点击预演逻辑，但它只存在于组件本地状态；`game.ts` 的 `validate` 固定失败，`commandTypes` 为空。要证明首剧本可跑通，必须把“选择角色 -> 探索宅邸 -> 结束首剧本”的状态变化下沉到领域层。

## Goals

- 领域层暴露真实业务命令，支持联机管线执行。
- Board 组件按阶段渲染三屏，使用同一套 `GameBoardProps` 和 `dispatch`。
- 运行时 UI 以 `v4` 为基线，保持五大区结构和短标签文案；按钮说明只允许 hover/title 或帮助层。
- 为未来 100 个游戏保留可复用方向：阶段化 Board、命令/事件/状态拆分、首剧本黄金链 E2E。

## Non-Goals

- 不实现完整 haunt 剧本书、叛徒隐藏信息和怪物 AI。
- 不裁正式房间图，不替换当前结构化房间占位。
- 不新增大厅产品入口或本地模式捷径。
- 不把本轮局部 shell 提升为共享框架，除非代码中自然出现可安全抽取的小 helper。

## Decisions

- Decision: 本轮先在 `src/games/betrayal/game.ts` 内完成领域闭环，再按复杂度逐步拆分。
- Rationale: 当前文件仍低于正式玩法规模，先保证状态机真实可跑通；若命令/事件继续增长，再按项目规范拆到 `domain/`。

- Decision: 运行时保留现有预演视觉结构，但动作执行优先调用 `dispatch`。
- Rationale: 现有 UI 已接近首剧本要素，直接重写会扩大风险；把同等行为迁入领域层能最快证明真实玩法。

- Decision: 终局由明确首剧本命令触发，并记录探索统计、幸存者、失败叛徒占位。
- Rationale: 本轮目标是“至少跑通第一个剧本”，不假装完整 haunt 已完成。

## Risks / Trade-offs

- 风险：Board 为兼容组件测试可能保留少量本地选择态。
- Mitigation: 只允许保留 UI 临时态，例如移动选目标、选中持有物、参考卡开关；规则状态必须来自 `G.core`。

- 风险：v4 位图含细节材质，前端无法逐像素复刻。
- Mitigation: 验收以同构图、同层级、同入口、2D 印刷语法为准，不追逐 AI 纹理。
