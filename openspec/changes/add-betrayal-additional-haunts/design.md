# Design: 山屋惊魂更多作祟剧本接入

## Context

当前正式运行只开放作祟剧本 1。剧本 3、12、33 的官方文本已经在本地剧本书里，且事件牌合同已经锁定三张触发事件：

- 作祟剧本 3：一瓶微尘，隐藏叛徒、Sickness token、Research token、Search / Cure 行动。
- 作祟剧本 12：大宅饿了，邪教徒、Number Track、搬运尸体、Feed Her、回合末全英雄伤害。
- 作祟剧本 33：说“茄子”！，魔法相机、Phantom Photographers、Essence token、摄影/视线攻击、摧毁相机。

结构化合同详见 `haunt-contracts.md`。正式实现必须以该合同为最低输入，不得直接从事件牌成功分支脑补剧本状态。

实现前代码落点和阻塞详见 `implementation-readiness.md`。其中玩家视图过滤、自由混战胜负结构和剧本 runtime 分层是正式代码完成前的硬门槛。

## Goals

- 每个新增剧本都从官方剧本文本结构化为配置、运行时状态、命令、事件、UI 行动、AI 行动和测试证据。
- 每个新增剧本都能通过正式事件牌成功分支进入对应作祟状态。
- 对应事件牌只有在剧本完整链路通过后才进入正式运行事件牌堆。
- 继续保留未完成剧本门禁，直到该剧本自身完成；不得用“跳过/失败分支可跑”证明成功作祟分支完成。

## Non-Goals

- 不一次性实现 50 个作祟剧本。
- 不把剧本书详情层替换为 TTS 书本模型。
- 不把房间背面、楼层板资源合同、未来新增对象真相混入本 change。
- 不用临时页面、静态说明、隐藏按钮或 Board-local 预演状态替代正式领域链。

## Decisions

- Decision: 保持 `BetrayalScenarioId` 扩展为明确剧本 id，而不是用数字裸值驱动运行态。
- Decision: 保持事件成功分支先检查 `BETRAYAL_IMPLEMENTED_HAUNT_CARD_NUMBERS`；每个剧本实现完成并通过门禁后再加入对应编号。
- Decision: 每个剧本必须有独立 runtime state 子结构，避免把 3、12、33 的 token、轨道、怪物和胜负条件塞进首剧本字段。
- Decision: 页面行动只展示当前剧本可执行动作；常驻主 UI 不塞长规则说明，剧本文本进入帮助/参考层。
- Decision: AI 只消费领域层暴露的合法动作，不为新增剧本开旁路。

## Risks / Trade-offs

- 剧本 3 有隐藏叛徒信息，必须区分全局状态、玩家视图和审计日志，避免把隐藏身份泄漏给英雄玩家。
- 剧本 12 需要尸体和邪教徒怪物状态，必须复用或扩展现有尸体 / 怪物模型，而不是写一套只服务单剧本的重复对象。
- 剧本 33 依赖魔法相机归属与视线判定，必须复用现有持有物和房间连通/视线能力；如果现有空间真相不足以支持视线，需要先记录为实施阻塞。
- 三个剧本都可能影响事件牌运行池；任何一个剧本未完成时，对应事件仍应保持运行态门禁。

## Verification

- OpenSpec strict validation.
- 每个剧本至少一组领域层测试覆盖：触发、核心动作、怪物/标记、英雄胜利、叛徒胜利或等价失败条件。
- 每个剧本至少一条真实页面 / E2E 代表链覆盖：从事件牌成功作祟分支进入剧本，并完成一个关键动作到可见状态变更。
- 审计文档必须记录每个剧本的实现状态、验证命令、证据路径和仍未覆盖边界。
