## Context
召唤师战争当前已经有较清晰的 TypeScript 配置对象、卡牌注册表和自定义牌组引用式存储；这不是必须立刻重构的高优先级债务。真正需要收口的是后续新游戏和玩家可审查配置的默认选型：让配置格式、表格视图、导入导出和玩家修正都穿过同一个 Interface，而不是让每个新游戏各自维护一套“看起来像表格”的实现。旧项目可以继续临时使用自己的方案，只有在明确需要统一审查或结构化修正提案时再 opt-in 接入。

## Goals / Non-Goals
- Goals:
  - 建立跨游戏复用的 `GameConfigPackage` 数据模型和校验流程。
  - 支持把配置包渲染为表格，供玩家审查当前实现是否正确。
  - 支持玩家提交结构化配置修正提案，并由 AI 做首轮审查。
  - 让新游戏从第一天按配置包方式录入静态事实。
  - 允许现有游戏保留当前方案，并在需要统一审查时通过 adapter 可选接入。
- Non-Goals:
  - 本变更不要求一次性迁移召唤师战争全部现有 TypeScript 配置。
  - 本变更不把召唤师战争列为首批必须改造目标。
  - 本变更不允许玩家提交或执行任意规则代码。
  - 本变更不把 XLSX 定义为仓库中的官方真相源。
  - 本变更不替代复杂能力、特殊规则和领域执行代码。

## Decisions

### Decision: 配置包是项目内 Module，不是第三方包
`GameConfigPackage` 是项目内稳定 Interface。它定义游戏静态事实的结构、校验要求、版本信息、运行时物化输出和错误语义。第一阶段官方仓库真相源统一为严格 JSON；JSONC/YAML/XLSX 只能作为导入、导出或编辑辅助，进入系统前必须转换成 JSON。

Alternatives considered:
- 直接用 XLSX 作为主源：不采用。XLSX 对玩家友好，但 Git diff、冲突合并、审查和自动校验都弱，不适合作为官方仓库真相源。
- 直接用 YAML 作为唯一格式：不采用。YAML 可读性好，但隐式类型、锚点和缩进风险会增加维护成本，不进入第一阶段官方源。
- 继续用 TypeScript 配置对象：不作为新游戏默认。它有类型提示，但把数据修改、代码审查和玩家结构化反馈绑定太紧。

### Decision: 官方真相源优先使用 schema 化文本数据
官方配置包统一以严格 JSON 存放在仓库中，并必须通过 schema 校验。运行时不得直接消费未校验的原始文本，也不直接解析 JSONC、YAML 或 XLSX。

### Decision: 表格是视图，不是运行时依赖
表格 UI 从配置包物化结果生成。玩家看到的表格和运行时使用的配置来自同一数据源；不得另维护一份只供展示的配置表。配置审查主表是玩家录入 / 修正视图，不是 debug 或 schema 浏览器：玩家可理解、可录入或可修正的静态事实字段必须进入可见单元格；内部对象 ID、字段路径、来源上下文、图集 ID、帧索引、源码路径和运行时 debug 字段只进入结构化 payload、隐藏上下文、开发工具或后台审查视图。素材字段以卡图预览、状态或音效试听呈现，不要求玩家阅读图集和帧编号。

### Decision: 旧游戏 adapter 必须先建字段覆盖清单
旧游戏通过只读 adapter 接入配置审查表时，第一步不是写 UI 列，而是从规则真相源和运行时消费链反推字段覆盖清单。字段清单必须记录现实含义、字段 key、值类型、适用对象、字段路径、值读取方式、是否必审和证据来源；表格页面只能消费该清单生成列、读取值、判断适用对象和解析编辑值。这样可以避免“牌组符号”这类真实构筑字段因为 UI 列表或 adapter 临时字段没有显眼命名而被漏审。

### Decision: 特殊效果使用能力 ID 绑定代码实现
配置包只声明 `abilityId`、参数、可见说明和实现状态。真正的特殊效果由代码中的能力/规则 Module 实现，并通过能力注册表解析。配置包加载时必须能报告“能力 ID 不存在”“能力需要代码支持但未实现”“参数不符合能力 schema”等错误。

### Decision: 玩家修正是结构化提案，不是直接改官方配置
玩家从表格单元格中提交修正时，系统保存字段路径、机器可审查的当前值 / 修改后值、玩家可见对象名、玩家可见字段名、当前显示值、修改后显示值、说明、证据、游戏版本、对象 ID 和上下文。该提案复用反馈式体验，但数据结构必须支持 AI 审查和后续自动生成 patch。已有对象的字段修正必须是字段级提案，不使用模糊的“整行修正”；新增或删除对象才允许走对象级提案。表格默认以只读单元格展示，玩家明确进入编辑态（例如双击单元格或等价动作）后才能暂存修改后值；多个字段修正可以先在页面内形成草稿，再通过单独提交按钮一次性发送为配置修正提案批次。

### Decision: AI 审查先给结论，人工/发布流程决定是否合入
AI 审查可以标记提案为建议接受、建议拒绝、需更多证据、需人工确认或需代码支持。AI 不得直接把玩家提案写入官方配置；正式合入仍走仓库变更、测试和发布流程。

## Risks / Trade-offs
- Risk: 新系统被误解为必须先重构旧游戏，导致主线停滞。
  - Mitigation: 第一阶段以共享 Interface、新游戏默认选型和修正提案流程为主；旧游戏 adapter 只在明确批准或明确需要表格审查时进入任务。
- Risk: 配置字段过度泛化，无法表达具体游戏差异。
  - Mitigation: 核心包只定义通用静态事实；游戏可扩展命名空间字段，但必须纳入该游戏 schema。
- Risk: 玩家把“修改表格”理解成能立即改变官方游戏。
  - Mitigation: UI 必须明确区分“官方配置”“个人/房间覆盖”和“待审修正提案”。
- Risk: AI 审查误判。
  - Mitigation: AI 审查只作为首轮分类和建议，合入仍需要人工确认或正式门禁。

## Migration Plan
1. 建立共享配置包 schema、加载器、校验器和物化接口。
2. 建立玩家结构化修正提案提交和 AI 审查状态。
3. 建立配置表格审查页面，读取配置包物化结果。
4. 新游戏从配置包数据源开始。
5. 现有游戏继续保留当前配置方案；如后续需要统一审查，再按游戏单独建立只读 adapter 或迁移计划。

## Open Questions
- 第一批落地是否先做“新游戏配置包空样板”，还是选择一个低风险游戏做样板；召唤师战争不默认纳入首批改造。
- 已决策：配置修正提案第一阶段复用现有 feedback collection 扩字段，并由反馈页展示；如后续吞吐或权限复杂度上升，再拆独立 collection。
- 已决策：官方真相源第一阶段统一严格 JSON；新游戏在 proposal 或 design 内声明 JSON 文件位置。JSONC/YAML/XLSX 仅作为后续导入、导出或编辑辅助。
- 待后续：本轮只实现 AI 审查状态模型和后台可见性，实际 AI 审查 runner / 工作台接入另立任务。
