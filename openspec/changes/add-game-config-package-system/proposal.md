# Change: 新增可复用游戏配置包系统

## Why
当前部分游戏把单位、卡牌、派系、牌组构成、起始部署和素材索引写在 TypeScript 配置文件里。该形态适合早期快速实现，旧项目可以继续临时沿用；但对于后续新游戏和需要玩家审查的配置，代码内静态对象不利于按“某一行某一列”审查，也不利于玩家提交结构化修正后由 AI 审查并进入官方配置。

需要建立一套跨游戏复用的游戏配置包系统：官方配置以 schema 化数据为真相源，运行时通过统一加载和校验链路消费，前端可以把同一份配置渲染为表格，玩家修正则复用反馈式提交体验但保存为结构化配置修正提案。

## What Changes
- 新增 `game-config-package` capability，定义游戏配置包的边界、格式、校验、运行时物化和表格审查能力。
- 配置包使用严格 JSON 作为官方仓库真相源；JSONC/YAML/XLSX 仅允许作为导入/导出或编辑辅助，进入系统前必须转换成 JSON。
- 配置包覆盖静态事实：游戏 ID、版本、派系、卡牌/单位/事件/建筑、牌组构成、起始部署、素材引用、能力 ID 和参数。
- 特殊效果继续由代码中的能力/规则 Module 实现；配置包只声明 `abilityId + params`，不得上传或执行玩家提交代码。
- 新增结构化配置修正提案机制：玩家可从表格视图提交字段级修正，系统记录当前值、建议值、证据说明、来源上下文和审核状态。
- AI 审查作为配置修正提案的第一道审核层，输出接受、拒绝、需人工确认或需代码支持等结论；最终是否进入官方配置仍由人工/发布流程控制。
- 新游戏默认使用配置包系统承载静态配置；现有游戏默认不强制迁移，可继续使用当前方案，只有明确需要统一审查或修正提案时才通过 adapter 可选接入。

## Impact
- Affected specs: `game-config-package`（新增）
- Affected code:
  - `src/game-config/` 或等价共享配置包加载与校验模块
  - `src/games/<gameId>/` 的新游戏配置包或旧游戏可选配置接入 adapter
  - `src/pages/devtools` 或管理/审查页面中的配置表格视图
  - `apps/api/src/modules/feedback` 或新增配置修正模块，用于结构化提案存储与状态流转
  - 相关验证脚本、schema、测试与文档
