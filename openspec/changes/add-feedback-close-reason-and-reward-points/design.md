## Context
- 反馈系统当前已经有来源字段与用户权限范围，但关闭操作只有 `status`，没有关闭理由、奖励积分和用户侧追踪视图。
- 右上角用户菜单已经承载后台入口、对战记录、通知等能力，适合作为“我的反馈”和积分展示的统一入口。
- 本轮需求横跨反馈 schema、用户资料接口、管理端关闭流程、用户菜单和反馈提交动效，属于跨模块的数据合同更新。

## Goals / Non-Goals
- Goals:
  - 为手填反馈建立可追溯的关闭理由字段与关闭门禁。
  - 让已登录用户能直接查看自己的反馈处理进度、关闭理由和奖励积分。
  - 以最小模型记录反馈积分，并同步到右上角展示。
- Non-Goals:
  - 不在本轮定义积分兑换、排行榜、商城或消费规则。
  - 不重做现有反馈后台的信息架构，只补必要输入与展示。
  - 不为历史已关闭反馈批量补全关闭理由。

## Decisions
### Decision: 用 `closedReason` 作为反馈关闭的一等字段
- 在 feedback 文档上新增 `closedReason`，由手动关闭动作写入。
- 当反馈属于自动反馈（基于 `reporterType = system` 或等价来源语义）时，允许关闭时不提供理由。
- 当反馈属于用户手填反馈时，关闭动作必须附带 `closedReason`；重新打开时清空关闭理由或至少不再将其视为当前关闭结论。

### Decision: 复用现有反馈查询权限模型承载“我的反馈”
- 用户侧“我的反馈”不新建独立权限体系，沿用现有反馈列表的登录态与 own-scope 能力。
- 前端在用户菜单中新增“我的反馈”入口；若当前用户有后台入口，则该按钮放在后台入口下方，否则放在退出前。
- 普通 `user` 角色不再展示后台入口，只保留“我的反馈”等用户侧入口。
- “我的反馈”列表重点展示当前状态、关闭理由、时间线与奖励积分，不暴露其他用户数据。

### Decision: 积分先做累计值 + 单条反馈奖励快照
- 在 user 文档上新增累计反馈积分字段，用于右上角展示。
- 在 feedback 文档上记录本条反馈奖励积分快照，保证后续能回溯“哪条反馈给了多少分”。
- 本轮不引入独立积分流水表；如果未来需要审计级流水，再基于该最小模型扩展。

### Decision: 反馈成功正反馈收敛为积分样式提示
- 在反馈提交流程成功后，不新增独立庆祝动效或覆盖层。
- 成功描述需要直接展示“星形 SVG 积分图标 +1”样式，让用户明确知道提交成功且获得积分。

## Risks / Trade-offs
- 历史已关闭反馈没有关闭理由：接受为空，但仅对新关闭动作强制校验。
- 不做积分流水会降低财务级审计能力：当前仅是产品占位需求，优先保持模型简单。
- 复用现有反馈查询接口会让一个接口同时服务后台与用户侧：需要在返回字段和权限范围上继续收窄，避免越权暴露。

## Migration Plan
1. 为 feedback / user 增加新字段，历史数据使用默认值兼容。
2. 更新 auth `/me` 等用户资料返回，带出累计反馈积分。
3. 更新反馈关闭接口与前后端 UI，先支持新字段读写。
4. 最后接入用户侧“我的反馈”与成功积分提示样式，确保前后端契约一致。

## Open Questions
- 单条反馈的基础奖励分值是否固定；在未明确前可先用常量配置承载。
- “解决进度”是否仅使用现有 `open / in_progress / resolved / closed` 四态；本提案默认沿用现有状态枚举。
