## Context

`GameDebugPanel` 目前由 `import.meta.env.DEV` 或 E2E 标志控制。生产游戏服务器只验证玩家座位凭据；CheatSystem 会执行 `SYS_CHEAT_*` 等状态修改命令，但没有管理员角色判断。应用 JWT 只含 `userId`、`username`，当前角色由认证服务从用户记录读取。旁观者的普通命令入口必须保持只读。

## Goals / Non-Goals

- Goals: 让已验证的管理员在任意生产线上对局查看并使用现有面板，无须占座；服务端拒绝普通用户伪造调试命令；权限变更后以当前角色为准。
- Non-Goals: 开放 `/dev/*` 素材 / 特效 / 音频工具页面；授予 `developer` 角色生产调试权限；改变游戏规则、教程注入或普通玩家命令语义。

## Decisions

1. **使用独立的管理员调试通道。** 客户端角色缓存只用于显示提示，不作为授权凭据。线上调试命令携带登录令牌进入专用服务端入口；服务端验证令牌并向可信用户角色源确认当前角色为 `admin`。管理员角色不从客户端字段或 JWT 中臆造。
2. **复用权威游戏管线。** 管理员命令仍由 `GameTransportServer` 执行、持久化并广播。普通 `/game` 命令通道继续验证座位凭据，并拒绝调试 / CheatSystem 命令；系统从 CheatSystem 的正式命令 owner 派生受保护命令集合，避免在 socket 路由另维护命令清单。
3. **不改变旁观者合同。** 管理员通过专用调试通道操作，不把普通旁观者 `dispatch` 改成可写。面板状态页只展示现有对局页面收到的状态，不新增一套状态投影。
4. **记录必要审计信息。** 服务端记录管理员 ID、对局 ID、命令类型、成功 / 拒绝结果和时间；不写入完整命令载荷。
5. **保护房间生命周期操作。** 若创建新房间会离开并销毁当前线上房间，先要求管理员显式确认。

## Alternatives Considered

- 只在 `GameDebugPanel` 检查 `user.role === 'admin'`：不采用。客户端角色可伪造，原有 socket 命令入口仍可能直接执行 CheatSystem。
- 仅允许管理员在自己创建的测试房间调试：不采用。用户已确认范围是所有线上对局。

## Risks / Trade-offs

- 管理员可以改变真实对局状态；这是本次授权能力本身。审计日志用于追查操作者和命令类型。
- 每次调试操作都要确认当前管理员角色，增加一次服务端校验成本；不得为减少开销而信任过期角色缓存。
- 调试命令集合必须由 CheatSystem / 游戏调试命令的正式 owner 提供，不能按字符串前缀猜测。

## Migration Plan

无需数据迁移。客户端与游戏服务器需一并部署；旧客户端不会显示管理员面板，服务器仍必须拒绝未授权的调试命令。

## Open Questions

- 无。管理员范围、线上对局范围及无须占座均按本提案定义；如用户审批时有不同预期，再调整方案。
