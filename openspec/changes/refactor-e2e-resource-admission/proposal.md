# E2E 按实际资源调度并保留共享服务复用

## 为什么修改
教程验收在可用内存仍有数 GB 时排队 1800 秒，直接原因是任务名称互斥、E2E 组固定权重上限 1，以及全局 runtime 等待；不是实时性能检查拒绝。

用户已在本轮明确要求“应该只有性能限制，给我重构”“复用同一个服务……性能、效率都要考虑到”。据此实施本变更，不新增确认环节。

## 修改内容
- 任务登记用于诊断；取消按名称、数量、权重或无关 runtime 的固定并发限制。
- CPU、可用内存作为准入依据；保留运行中的危险内存监控与原有测试检查。
- 同 worktree 优先复用健康服务，各次测试保留独立会话；只锁同一服务的检查 / 冷启动过程。
- 保留真实端口冲突隔离、精准清理及活跃 owner 保护。

## 影响
影响 `e2e-runtime-management`、重任务资源调度、runtime manager 与诊断入口。通过领域化基础设施测试及真实并发教程 E2E 验证；教程内容与截图任务继续执行。
