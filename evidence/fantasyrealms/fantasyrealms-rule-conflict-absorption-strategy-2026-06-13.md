# Fantasy Realms 项目级规则冲突吸收策略（2026-06-13）

> 历史过程说明：
> 本文记录的是当时若要把专项成果带回主线，项目级规则文件应如何吸收的过程策略。
> 它不是今天的实施指令，也不等于今天应继续执行回主线、执行 merge，或按本文顺序直接操作。
> 文中出现的 `stacked`、`回主线`、`merge` 等表述，都应理解为当时的过程上下文，而不是当前正式 UI 或当前执行动作。

## 目标

明确回答一个问题：

当 `fantasyrealms` worktree 当时若最终回 `main` 时，哪些项目级规则文件应以根目录当前版本为准，哪些 worktree 独有条目值得人工吸收，哪些不应再带回。

## 现场

- 根目录当前主线现场：`D:\gongzuo\webgame\BoardGame`
- Fantasy Realms worktree：`D:\gongzuo\webgame\BoardGame\.worktrees\fantasyrealms`
- 本轮比较方法：
  - `git diff --no-index` 对比两边当前文件内容
  - `rg` 定位双方是否已包含相同门禁语义

## 总原则

1. **根目录当前版本是项目级规则吸收基底**：不得让 worktree 的旧规则版反向覆盖 `main` 当前更强的版本。
2. **只吸收 worktree 里仍然独有、且能直接拦住本次事故的条款**：不做整份覆盖。
3. **若 worktree 只是旧版措辞、结构搬运或重复展开，不回主线**。
4. **凡是能在根目录当前规范里直接落位的，优先补强原条目，不新增平行重复文档**。

## 一、直接以根目录当前版本为准，不从 worktree 反向覆盖

### 1. `AGENTS.md`

裁决：

- **完全以根目录当前版本为准**
- **不吸收 worktree 整份内容**

原因：

- 根目录当前版本已经明确补强了这次事故真正缺失的门禁：
  - 多 worktree 必须先锁实施落点
  - 当前 UI 证据必须与当前执行现场同源
  - bug 修复目标不得迁移
  - 回归还原目标未唯一锁定时必须先停下或询问
- worktree 版本明显更旧，若直接覆盖，会把这轮刚补强的硬门禁冲掉。

### 2. `.spec/knowledge/README.md`

裁决：

- **以根目录当前版本为准**
- 只检查它是否继续正确路由到测试、UI/UX、设计稿实现、动效等专项文档

原因：

- `doc-index` 的职责是入口路由，不应被专项 worktree 旧版倒灌。

### 3. `.spec/decisions/document-consolidation.md`

裁决：

- **以根目录当前版本为准**
- 不把 worktree 版本直接带回

原因：

- 该文档本质是项目级规范整理台账，不是 Fantasy Realms 本体资产。

### 4. `docs/e2e-testing-guide.md`

裁决：

- **以根目录当前版本为准**
- 不从 worktree 反向覆盖

原因：

- 根目录当前版本已经形成正式入口 / 对局场景 / harness 三分法与时长约束，属于项目级基础设施文档。

### 5. `design-system/game-ui/MASTER.md`

裁决：

- **不整份回主线**
- 根目录当前版本已覆盖相同核心规则语义

原因：

- 当前 worktree diff 主要是把 `Never Looks Dead` 从后文提升到前面，并改成更展开的四点写法。
- 这属于**结构重排与措辞展开**，不是新的独立不变量。
- 根目录当前版本已经有等价约束，因此不需要把 worktree 版本整份带回。

## 二、应人工吸收 worktree 独有有效条目的文件

### 1. `.spec/knowledge/standards/e2e-verification.md`

裁决：

- **以根目录当前版本为基底**
- **人工吸收以下 worktree 独有高价值条目**

建议吸收条目：

1. **“从开局验证”语义澄清**
   - 不得再把“开局”默认脑补成 `match` 内代表态。
   - 若指真实规则开局，必须对应 `turn=1 + stage=draw + discardPile=[]`。
   - 若指测试最近起点，必须显式写“`match` 内代表态”，不能再直接简写成“开局”。
2. **桥接式组合验证**
   - 入口黄金链 / 中段代表态链 / 终局前代表态链 三段式收口。
3. **“流程跑通”口径必须锁开始点与结束点**
   - 禁止只说“跑通了”，不写本轮承诺的开始点和结束点。
4. **核心决策位必须提供 `触发前 -> 触发后` 截图对**
   - 尤其适用于用户要求“看图是否能继续”的游戏流程验收。

不建议整份覆盖的原因：

- 根目录当前版本已经有更强的多 worktree / 真实入口 / 截图验收 / 长链停损基础门禁。
- 直接覆盖会把主线现有更完整条目打回旧结构。

### 2. `docs/testing-best-practices.md`

裁决：

- **以根目录当前版本为基底**
- **人工吸收以下 worktree 独有条目**

建议吸收条目：

1. **测试驱动不等于先把长链写满**
   - 先最窄失败证据，再最小修复，再最窄回归。
2. **完整流程默认拆成组合矩阵**
   - `entry / opening / midgame / near-end / review` 分层证明。
3. **已删除旧 UI 文案不得继续用“应当不存在”制造遗留**
   - 只要旧长句已经退出正式合同，测试就不应再长期保留“某旧文案不存在”这类反向断言来维持遗留。
   - 这一条直接对应本轮用户指出的“只剩在单测里的应当不存在断言”的问题，值得抬回主线。

保留根目录当前版本的原因：

- 根目录当前版本已有 seam、层级、状态注入、真实场景真实性等主骨架。
- worktree 版本里也有一些对根目录现版来说已重复或已被更强规则取代的段落，不宜整份覆盖。

### 3. `.spec/knowledge/standards/ui-ux.md`

裁决：

- **以根目录当前版本为基底**
- **人工吸收以下 worktree 独有条目**

建议吸收条目：

1. **同一游戏跨断点不得分裂成两套独立 UI 家族**
   - 这条直接针对本轮“桌面 / 旧命名为 stacked 的历史横屏候选，看起来像两个游戏”的事故。
2. **正式视觉稿不自动包含交互合同**
   - 视觉稿不能直接脑补出交互承接方式。
3. **交互模式必须有来源表**
   - 防止凭个人偏好发明“点哪里/怎么确认/谁承接”。
4. **主推进交互不得隐式到不可见**
   - 合法状态不能只靠懂规则的人才能发现下一步。
5. **正规流程优先于临时收口**
   - 看起来像卡死时，默认回到正式 UI 重构流程，而不是临时塞一个小按钮糊过去。
6. **固定牌桌类游戏的 PC live 默认禁止页面级滚动**
7. **固定牌桌类游戏不得用禁用主按钮充当步骤提示**
8. **动效验收必须回到真实帧证据**

原因：

- 这些条目都能直接拦住这次 Fantasy Realms UI 事故的具体错误动作。
- 根目录当前版本已有大量截图、来源页、真实入口门禁，因此应补强而不是覆盖。

### 4. `.spec/knowledge/standards/generated-design-implementation.md`

裁决：

- **以根目录当前版本为基底**
- **人工吸收以下 worktree 独有条目**

建议吸收条目：

1. **正式视觉稿不自动包含交互合同**
2. **交互模式必须先锁来源**
3. **规则语义优先于美术发挥**
   - 游戏 UI 的隐藏信息、旁观者可见性、终局前可见对象不能被生图擅自补全。
4. **复刻失败必须降级，不得堆装饰硬凑**
5. **错稿污染必须重建实现基线**
6. **设计资产目录必须先锁语义再删留**

原因：

- 这些条目正面对应了本轮“错稿带偏”“把视觉稿偷渡成交互稿”“删目录前没先锁正式稿语义”的事故。

### 5. `.spec/knowledge/standards/animation-effects.md`

裁决：

- **吸收 worktree 当前新增的一条**

建议吸收条目：

- **对象转移动效只绑定变化对象**
  - 卡牌、token、资源从 A 区到 B 区时，只允许变化对象动，禁止整排、整列、整容器一起被重播动画。

原因：

- 这是本轮“动效不合理”里最明确、最可执行、最能直接拦错的一条。

## 三、当前不建议再从 worktree 抬回主线的条目

### 1. `.spec/knowledge/standards/ui-ux.md` 里的 Skill 路由细节

裁决：

- **不建议原样抬回主线**

原因：

- 这部分混合了项目内 skill 路由、全局 skill 绝对路径和专项组合读法。
- 若要固化，应优先落到更合适的项目 skill 或全局 skill，而不是继续把根项目文档写成 skill 调度说明。

### 2. `docs/testing-best-practices.md` 中已被主线更强规则替代的旧段落

裁决：

- **不回主线**

原因：

- worktree 版本里删除或替换了一些当前主线已更完整的测试门禁，不值得反向覆盖。

## 四、执行顺序建议

后续真正回主线时，项目级规则应按这个顺序处理：

1. 先保留根目录当前 `main` 版本作为规则基底。
2. 再从本文件第二部分列出的 5 份文档里，人工抬回仍独有的有效条目。
3. 确认这些条目已经进入主线后，再处理 Fantasy Realms 本体 merge。
4. 不要让 `feat/game-fantasyrealms` 里的项目级规则文件整份覆盖 `main`。

## 五、当前结论

1. worktree 已经是 Fantasy Realms 实现真相源，但**不是**项目级规则真相源。
2. 项目级规则回主线必须采用“`main` 当前版本为基底 + 手工吸收 worktree 独有有效条目”的方式。
3. 当前最值得从 worktree 抬回主线的规则，集中在：
   - 测试组合矩阵与长链停损
   - UI 不得分裂成两套游戏
   - 视觉稿不等于交互稿
   - 正式交互必须有来源表
   - 动效只能绑定变化对象
