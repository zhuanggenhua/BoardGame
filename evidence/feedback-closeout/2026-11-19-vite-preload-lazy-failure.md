# 预加载失败误报为空模块

- 线上反馈 6afc799af6f035b1676b3a91：`undefined is not an object (evaluating 'v._result.default')`。反馈上下文为 iPhone Safari；源站同来源、相同时间的反馈 POST 后多次请求首页，未记录到关联 JS 请求；不能从这些日志确定最初模块失败的原因或该机制就是历史异常的唯一原因。
- 生产版本 6506f292f 的 `vite:preloadError` 处理在触发刷新后调用 preventDefault。Vite 预加载器遇到被阻止的模块导入异常时，Promise 会成功返回 undefined；React.lazy 随后读取 default 再抛异常。使用当前 Vite 构建、真实 Chromium 和失效模块 URL 对照，旧处理复现空模块异常，不阻止时保留原始模块加载异常。
- 修复：预加载恢复不再阻止原始异常；只在同一原始异常传播到 React、启动或游戏加载处理时避免重复刷新，不影响同页面独立错误的恢复。CSS 加载失败同样保留原始错误，不再绕过样式失败继续加载。
- 真实 Vite 浏览器构造验证：JS、CSS 分别覆盖首次失败后恢复与持续失败；恢复时加载成功，持续失败时原始错误可见，均最多刷新一次。项目正式入口单个新增用例通过（Node 24.22.1、Chromium）；此前 24.1.0 的同文件两用例通过过，但后续扩展后一次 worker 在执行前以 0xC0000374 退出。相关组件及恢复单测 52 项，游戏 runtime 定向 1 项通过；更宽测试中的两条大厅测试因现有 useLocation mock 缺失失败。
- 原反馈没有保存那次失败的模块请求；只证明相同异常可由已修复缺陷造成，不能把历史反馈确定为该根因，保持 open。修复尚未发布，未覆盖原 iPhone Safari。
- 追加 WebKit 对照：本地 WebKit 26 旧版复现与线上异常文字逐字相同；带 CSS 的懒加载 JS 首次 404 后，即使 HTTP 404 使用 no-store，重载仍可能不重新请求同一模块。真实本地 HTTP 复现排除了 Playwright 拦截特有行为。修复仅在发现同源指纹模块预加载失败且即将刷新时记录失败地址；刷新后通过一次性 import map 对失败模块使用新请求地址，不改变正常路径的预加载。记录限制为最近 8 秒、最多 32 项，地址严格校验并单次消费。
- 2026-11-19 本地正式 E2E 入口：WebKit 和 Chromium 分别通过，覆盖 JS / CSS 首次失败恢复、持续失败保留原始错误及最多刷新一次，以及两个 JS 模块同时失败后恢复。相关单元测试 12 项通过，修改文件 ESLint 通过。WebKit 为桌面浏览器引擎模拟，未在反馈设备上验证；历史模块请求原因仍未知，反馈保持 open，修复尚未部署。
- 同日补充异步网络时序：两个 JS 模块请求失败，其中依赖模块的 404 延迟 200ms，真实 HTTP 下 WebKit 成功恢复。该情景加入正式 E2E 后，整个文件 3 项通过，涵盖跨版本旧资源读取及 Chromium / WebKit 的加载恢复；不代表历史实际请求时序。
- 同日追加实际项目生产 Vite 构建验证：以当前项目 `vite.config.ts` 构建到隔离目录，构建成功，输出 HTML 确认恢复脚本在模块脚本之前。将该构建用本地 HTTP 服务加载，分别对首页 `App` JS 和 `HomeEntry` CSS 首次请求返回 404；Chromium、WebKit 四个场景均只发生一次重新加载，随后显示 12 个游戏卡片，未捕获页面未处理异常。该构建执行 Vite 阶段，未执行 `npm run build` 的预构建和资源裁剪脚本；它包含当前工作区其他在途改动，不是已发布版本，也不代表历史事件根因。
- 同日持续故障与手动恢复：实际构建的首页 App JS 持续返回 404 时，之前首页停留在加载中；现复用启动失败提示并提供刷新按钮。故障恢复后，旧方案在 WebKit 中仍因失败模块缓存无法重试；现为每次重试生成新地址，并保留待手动刷新使用的失败地址。真实 HTTP 下 Chromium、WebKit 均在自动刷新一次后展示提示，服务恢复后点击按钮成功显示游戏首页，总导航次数为三次。原始加载错误仍保留；此处理不消除持续 404 的服务端原因。
- 同日补充存储受限场景：模拟浏览器访问 `sessionStorage` 抛 `SecurityError` 且首页入口 JS 持续 404，旧实现 2.5 秒内 Chromium 发生 101 次导航、WebKit 发生 23 次导航。修复后不能记录刷新标记时不自动刷新，保留原始错误并显示失败提示；实际构建两种引擎均仅一次导航。此处理避免刷新循环，不代表资源故障已修复。
- 进一步发现会话存储被拒时，即使资源正常，UUID 模块加载阶段的 `typeof sessionStorage` 也会触发异常并阻塞首页；将读取和写入均纳入原有异常处理后，两种引擎的实际构建均显示 12 张游戏卡片。极端环境下的 UUID 最终降级分支原本只生成 8 位尾段，已补齐到标准 12 位并以单测验证。测试服务没有大厅 socket / API，不能据此声称联机可用。
- 存储被拒且模块加载曾失败时，资源恢复后 Chromium 手动刷新成功；WebKit 同标签页仍可能复用失败缓存，实测新开标签页可正常加载，因此首页失败提示补充关闭标签页后重新打开的操作。此为受限环境下的恢复指引，不证明线上历史 Safari 故障采用了这一环境。
- 后续已修正上述同标签页限制：`sessionStorage` 不可用时，将刷新标记与待重试模块记录在当前历史记录中，保留路由原有状态字段；若历史状态无法安全扩展，则不自动刷新、保留提示。真实项目 Vite 构建、本地 HTTP 和 Chromium / WebKit 下，首次 JS 请求失败后均自动刷新一次并显示 12 张游戏卡；持续失败时均自动刷新一次，服务器恢复后点击原页面按钮进入首页，路由状态保持。真实 iPhone 和线上未验证；本地服务不含大厅 socket / API。相关单元测试 16 项、项目浏览器回归 3 项通过。
- 后续覆盖启动窗口之后的玩家操作：真实项目首页停留 9 秒后点击王权骰铸，注入游戏详情 JS 首次 HTTP 404。旧实现的 WebKit 连续刷新两次后才打开详情；原因是启动窗口结束时未记录失败模块，而详情错误边界仍会刷新。修复后不改变自动刷新门槛，仅为后续错误边界的刷新记录失败模块；实际项目构建在普通和会话存储受限两种条件下均只刷新一次，成功显示王权骰铸详情。补充启动窗口结束后的两类浏览器回归，整个项目测试文件 3 项通过；相关单元测试 16 项通过。此模拟不是历史线上故障现场，未验证联机服务，代码尚未部署。
