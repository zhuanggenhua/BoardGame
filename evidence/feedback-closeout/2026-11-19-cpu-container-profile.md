# CPU 高占用诊断：容器内采样验证

- 线上两条历史告警均为 game-server CPU 持续超过 80% 后重启；现有现场不能将具体 CPU 样本与当时对局或操作直接关联，根因未确认，均保持 `open`。
- 本地使用已有 `ghcr.io/zhuanggenhua/boardgame-game:f7fb28a` 镜像创建无外网、无端口映射的临时容器，通过同样隔离的 MongoDB 容器提供数据库，使用测试密钥并确认游戏服务保持运行。真实 `watch-game-server-cpu.sh` 以阈值 0、人为触发一次采样和重启；成功收集并解析 V8 profile（919 个采样），重启后游戏容器仍在运行，两个临时容器已删除。测试未发送反馈或触碰生产。
- 第一次独立采样只覆盖启动瞬间，随后发现该容器缺少启动密钥而退出；已补数据库和配置重做完整守护链。完整链在 Windows Git Bash 下还需避免把容器内 `/tmp` 参数转换成 Windows 路径；这是本地测试宿主差异，不代表 Linux 生产已经验证。
- 该结果证明上述本地镜像、隔离配置和人为触发条件下，守护脚本可采样并重启游戏服务；没有真实对局或生产数据库，不能证明生产配置、线上高负载时 Inspector 可用、采样包含某个玩家操作，也不能还原两条历史告警。采样代码尚未部署。
- 复核发现：在线 AI 即时决策超过 1 秒但未执行动作时，原调度器不调用慢决策日志，可能漏掉决策阻塞、命令失败或状态变化导致的慢次调用。现已在既有 trace owner 中记录此类已返回结果的对局、状态版本、决策时长、动作类型、命令类型与已有失败原因；原恢复顺序不变，快速未执行结果不额外记日志。此分支没有独立执行计时，现不输出 `executionMs`，避免将未知耗时误记为零。若决策一直没有返回或服务在返回前重启，仍不能依靠这条日志定位。
- 新增用例先复现原代码无日志，再验证修正；即时执行调度和服务端 AI 测试共 12 项通过，测试结构检查和 ESLint 通过。此为后续采集补全，不证明两条历史告警的根因；代码尚未部署。
